# Goldens library: architecture review of 9.26-1 and 9.26-2

Date: 2026-09-29

**Daniel's level of review / sign-off for this note:** Daniel reviewed the notes this doc was drafted from. The review and the naming decisions were discussed in session.

This session reviewed the architecture in 9.26-1 (the direction) and 9.26-2 (the pass-1 plan) against two long-term goals:

1. Guard all the main surfaces in this project.
2. As a bonus, grow into a general-purpose library that other ML projects could use.

A local HTML architecture map was made to support the review: `tmp/2026-08-goldens-1st-cut-notes/2026-09-28-goldens-architecture-map.html`. It isn't maintained and is already partly stale, but it may still be useful as a picture of the layers.

## Takeaway

The review looked for big blockers. A big blocker is something the design would struggle to adapt to, forcing large, complex modifications to core parts of the system and rework of the first-cut code. Changes to persisted artifacts counted for less, since changing the references layout costs a one-time re-bless.

No major blockers were found for the first cut. The core adapts well to the changes the review considered, for a few reasons:

- Tentative decision 2 from the implementation sketch ends up being quite valuable: computed entries only consist of an id and the content, without any config or the full Entry details.
- After compute, the rest of regen operates soley on an entry id plus its content. This means that any future reworking of fixtures, registries, and surfaces only touches the early layers (compute and the producers).
- Content is a set of named arrays, so a new surface mostly needs a new producer.
- Equality is defined in one place, `diff_content`.

There is one potential hurdle for goal 1: surfaces that consume the output of other guarded surfaces, such as forward, loss, and metrics. 9.29-2 describes it. It doesn't need solving now: the first cut has no such surfaces, since obs and supervision are both produced directly from the sim data. The first cut can be finished with the question left open.

Goal 2 is still speculative. A promising sign is that the design appears able to handle all the main surfaces of this project in a general way, assuming the downstream question is resolved satisfactorily.

## Near-term items

These items came out of the review and bear on work coming up soon: pass 1, and chunks 4 and 5 (revisions and the set digest).

- Tentative decision 2 from 9.26-2 seems important for keeping the design flexible and more easily extensible.
- Pass 1: building `RowHashes` in pass 1, instead of pass 2, is an option. The change is small, and it avoids a second re-bless.
- Pass 1, or when the first custom output is built: a direction for extra outputs, such as the channel summary. The user supplies a builder that receives the same inputs as the regen report builder. Claude's addition, not yet confirmed: anything the builder needs must be in the content.
- Before revision 0001: decide how references trees map to revision histories, in case there is ever more than one registry. Claude's lean is one tree per package.
- Chunks 4 and 5, when the revision kinds are rewritten for the new layout: add a kind for a config edit that changes bytes. None of the 9.18-1 kinds fits it, since a coverage change requires every surviving file's bytes to stay the same.

## Naming changes to 9.26-2

The review also went through the names in 9.26-2. These changes apply to the pass-1 implementation.

| 9.26-2 name | New name | Status |
|---|---|---|
| `Suite`, `SUITE` | `Registry`, `REGISTRY` | tentative |
| `Suite.load` | `load_fixture` | agreed |
| `store.load` | `load_reference` | agreed |
| `Content` | `EntryContent` | agreed |
| `Computed` | `ComputedEntry` | agreed |
| `Planned` (nests `Computed`) | `PlannedEntry`, flat: `id`, `content`, `status` | agreed |
| `Outcome` | `PlannedEntryStatus` | agreed |
| `Planned.outcome` | `PlannedEntry.status` | agreed |
| `count_outcomes` | `count_statuses` | agreed |
| `RegenPlan.items` | `RegenPlan.planned_entries` | agreed |
| `RegenPlan.removed` | `RegenPlan.unmatched_orphan_ids` | agreed |
| `TreeScan.entries` | `TreeScan.entry_ids` | agreed |
| `Added`, `Removed`, `LayoutChanged`, `RowsChanged` | `ArrayAdded`, `ArrayRemoved`, `ArrayLayoutChanged`, `ArrayRowsChanged` | agreed |

These names were reviewed and kept: `TreeScan`, `RegenPlan.tree`, `ContentDiff`, `diff_content`, `check_content`, `Surface`.

Two of the new names need a short explanation:

- `PlannedEntryStatus`: the status is set during planning, before anything is written, and describes what planning found. Apply is the only code that treats it as an action.
- `unmatched_orphan_ids`: orphans are stored entries that no computed entry claims, such as a point dropped from the registry. The orphans matched as a move source are excluded.
