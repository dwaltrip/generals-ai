Here's the session's design content

The problem, as we ended up stating it

The supervision references need a mapping from (config point, emitted key) to a stored reference. Each key's bytes depend on some subset of the config fields, and two points can share one stored array for a key exactly when they agree on that subset. The three layouts in the docs were three implicit answers to "what is that subset": the 8.12-2 union layout assumed it was empty for every key, the 8.25-1 per-point layout assumed it was every field, and the design we chose declares it per key.

The dependency table

- Each SupervisionKey declares deps, the config fields its bytes depend on. Points that agree on those fields form a group and share one stored array.
- The table describes the code, so it can go stale. Regen checks it: within a group, every point must produce byte-identical arrays, or regen refuses to bless. Over-declaration only costs duplicate storage.  Under-declaration is caught at the next regen, provided some fixture exercises the difference. That residual is the same fixture-coverage exposure every golden has.
- The regen check can't distinguish a stale table from a real code divergence. Both produce the same report, and the reader separates them by asking whether the disagreeing point differs on a field the key should now read.
- Why we preferred it over per-point storage: adding a config field already forces a registry edit (the strict-keys property), so the table update lands where attention already is. A change that leaks across keys happens in tail or precompute code with no reason to open the registry, and the table's check is what catches it. Per-point storage turns that case into an ordinary fire that can be rubber-stamped, which matters most during mid-branch iteration when fires are expected.
- Granular (field lists) over coarse (shared or per-point): a key that gains a dependency keeps its sharing and its consistency check among the points that still agree, instead of degrading to per-point. The cost is naming, which representative naming resolves.

Naming and storage

- Group naming: after the first registered point that emits the key and matches the group's field values. Adding a new value creates a new group and a new file without touching existing ones. Relocation happens only when a representative point is removed or the list is reordered, so the points list is append-only by convention.
- Path: references/supervision/<fixture id>/<rep>@<key>.npy, fixture-first, flat, separator as one constant. Obs stays references/obs/<point>/<fixture id>.npz.
- One uncompressed .npy per (fixture, key, group). Measured on the survivor fixture (T=566): 132 KB for supervision, over half of it the two [T, 8] int64 arrays at 36 KB each. Git compresses blobs at rest, so packfile cost should be well below that. .npy versus a compressed per-key file is still open.
- value_target stored [T], as the tail stacks it.
- Hash: blake2b 8-byte digest read as little-endian uint64, over C-order bytes in the emitted dtype. Channel hashes cover each channel's full history. The sha256 question is a TODO.

Registry shape

- Four typed lists: ObsPoint(name, cfg), SupervisionPoint(name, targets, emit_alive_mask, keys), SupervisionKey(name, deps, hashed=False), FixtureRecord. Lists rather than dicts because order is load-bearing for representatives.
- Config values are plain dicts converted at expansion. TargetsConfig, ObsConfig, and PartialEmitSpec have no field defaults and are keyword-only, so **d construction is the strict-keys assert, and a no-defaults guard at import keeps it that way. Embedding config instances directly was considered and is a small switch if wanted later.
- The keyset per point stays explicit. The representative for a group has to resolve statically, which requires knowing which points emit a key without running anything.
- Axis name: supervision points. "Emit" was set aside as an axis name at this layer.
- The asymmetry to revisit: an obs point is a named ObsConfig, a stored sub-config that is also its own emission contract. A supervision point is a named PartialEmitSpec, a derived per-build contract with no stored sub-config behind it. The registry stores contracts on both sides. A future supervision key that reads memory state would depend on obs fields and would push supervision points toward full EmitSpec values.

Regen

- It moved from a tier 3 leaf to the piece that validates the registry, and the first bless needs it. That reordered the build.
- Checks: emitted keys equal each point's keyset; within-group byte equality; a warning when two groups of a key are byte-identical on every fixture (over-declared or unexercised); orphan detection with move recognition. All fixtures are computed and checked before any file is written.
- Still prototype-grade: prints only, no baseline selection, no boundary record, obs orphans not handled.

Spike results

- Three throwaway fixtures, 18 entries, all unblessed before regen and green after. A second regen reports all unchanged with no warnings, so alive_mask agrees across its two precompute paths on these fixtures.
- Check A (divergence in precompute_for): fired on alive_mask for the elim points only, regen refused, nothing written. The difference was one frame per fixture, which is a concrete example of a fire small enough to rubber-stamp.
- Check B (time_bin_alt): one new file per fixture, no relocation. With the edges dependency removed, the new point fired against time_bin's file and regen refused with a contradiction between the two. After revert, the orphans were reported and removed.
- Check C (is_pass inverted): every entry fired on that key, regen reported one changed file per fixture.

Open items and sequencing

- Before the first committed bless, in some order: the next_elim_dt re-home, the hash algorithm pick, and the file format question. Each re-blesses.
- Regen orphan deletion is implemented as delete-and-report.
- Deferred as before: structural tests, parity test, environment record, mutation test, fire report and ledger, torch guards, the checkpoint sweep, fixture selection.

Here's the data first, since it settles most of the compression question.

What git actually stores. Loose objects are zlib-compressed, which is close to what a packfile holds before delta compression. For the survivor fixture (T=566):

┌────────────────────────────────────────────────────┬───────────────┬────────────────┐
│                        file                        │      raw      │ on disk in git │
├────────────────────────────────────────────────────┼───────────────┼────────────────┤
│ time_bin@elim_bin_target.npy ([T, 8] int64)        │ 36 KB         │ 0.9 KB         │
├────────────────────────────────────────────────────┼───────────────┼────────────────┤
│ next_death@next_elim_removal_dt.npy ([T, 8] int64) │ 36 KB         │ 8.2 KB         │
├────────────────────────────────────────────────────┼───────────────┼────────────────┤
│ core@legality_mask.npy ([T] uint64 hashes)         │ 4.7 KB        │ 3.9 KB         │
├────────────────────────────────────────────────────┼───────────────┼────────────────┤
│ each other [T] int64 or bool array                 │ 0.7 to 4.7 KB │ 0.1 to 1.2 KB  │
├────────────────────────────────────────────────────┼───────────────┼────────────────┤
│ all 36 reference files, 3 fixtures                 │ 190 KB        │ 45 KB          │
└────────────────────────────────────────────────────┴───────────────┴────────────────┘

So git already compresses the references about 4x, and the two big arrays are the most compressible things in the set. The hash file barely compresses, which no format can change. The working tree carries the raw size, and that's the only place uncompressed .npy costs anything.

Compression without changing the layout is available: np.savez_compressed with one array per file keeps one file per (fixture, key, group), and only the loader and writer change. But I'd now argue against it. A compressed blob can't delta against its previous version in the packfile, so a re-bless that changes a few frames costs a whole new compressed blob. A raw .npy blob deltas against the old one, so the same re-bless costs roughly the changed bytes plus zlib. Given 8.12-1's model where re-bless churn dominates repo growth, raw .npy should be cheaper over time, and the standing cost is already small. The working-tree size is the trade, at about 65 KB per fixture, which is 650 KB at ten fixtures.

Least settled design items

- .npy uncompressed. Now with data behind the lean, but still your call given the working-tree number.
- The identical-groups warning fires per fixture. The plan said once per key across all fixtures, since agreeing on one fixture is expected. I implemented the simpler per-fixture version. With today's points it can't fire at all (every multi-emitter key has one group), so nothing has exercised it.
- The obs/supervision asymmetry, and the cross-axis key case that would force supervision points to carry an obs config.
- Regen's second-pass scope: report format, baseline selection, boundary-record skeleton. Undesigned beyond what prints today.
- Sequencing before the first committed bless: next_elim_dt re-home, hash algorithm, file format.
- Representatives depend on list order with only a comment enforcing append-only. An assert is possible (for example, a stored list of point names in registration order) but it's more machinery than the problem has earned yet.

Judgment calls made during implementation, each small and easy to change:

- Registry helpers (spec_for, group_id, representative, the path builders) are public rather than private, since regen uses them.
- SupervisionEntry carries hashed_keys so the compare doesn't consult the registry.
- Dependency field names are bare ("elim_variant"), resolved against TargetsConfig first, then PartialEmitSpec.
- hashed has a default of False on SupervisionKey, the one default in the registry records.
- Keys are written out in full per point, no shared CORE_KEYS constant.
- FixtureRecord became keyword-only to match the other records.
- perspective_for takes a GameMeta and a slot.
- The loader treats any missing file as unblessed for the whole entry.
- Throwaway fixtures are copied corpus npz pairs, with the fixture list living in registry.py rather than a data file.
- Regen deletes orphans and reports them, handles only supervision orphans, prints each group's member points, exits 1 on a keyset mismatch or contradiction, and checks all fixtures before writing anything.
- Data root under tests/goldens/, separator "@".

The one I'd flag as a mismatch with what we discussed is the per-fixture warning. The rest were unremarkable picks where the plan left the shape open.
