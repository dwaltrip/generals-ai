# Goldens: a configs-primary registry, and the polish pass

Date: 2026-09-15

This session regrouped after the registry spike (9.04-1, 9.13-1), settled what a registry "point" is, and then polished the spike code in five commits on `goldens-1st-cut-build`. Most of the session went to the first of those, and that is the durable part of this note.

**Daniel's level of review / sign-off for this note:** I've only done light skimming / trimming / annotation.

## 1. A point is a config value

A golden test guards the mapping from (stored configs, fixture) to emitted bytes. The bytes are a function of four things: the configs, the fixture, the guarded code, and the environment. The registry's two axes are the first two. The guarded code is what the goldens exist to detect changes in. The environment will be pinned by the environment record. Every other input the emission code reads is held at a stated null value.

Under that model a point is a config value and nothing else:

- An obs point is an `ObsConfig`.
- A supervision point is a `TargetsConfig`.
- Nothing derived is stored on a point. The registry computes the derived things (the `PartialEmitSpec` the tail reads, and eventually the keyset) from the point, using prod code.

The rule that "which columns does this config emit" belongs to prod, so it now lives in `emit_spec.py` as `partial_emit_spec_from(targets, metrics)`, and `emit_spec_from` routes through it. Before this, the registry restated the rule by hand as an `emit_alive_mask` field on each point, which worked only because the values happened to match.

Configs are written in the registry as literal instances (`TargetsConfig(...)`, `ObsConfig(...)`), never as a reference to a named constant such as `OBS_CONFIG_DEFAULTS`. The registry pins values so that prod's defaults can move without re-describing what is guarded. Strict keys hold by construction, since the config classes have no field defaults, and an import-time guard keeps them that way for `TargetsConfig`, `ObsConfig`, `MetricsConfig`, and `PartialEmitSpec`.

### The metrics surface is not guarded

`MetricsConfig.include_alive_mask` is a column request: it changes which columns are present on the sample and never changes the bytes of any column. So the registry holds the metrics config at its null value (`include_alive_mask=False`, written inline) and no metrics field appears on a point. Three consequences:

- The `alive_only` point is gone. It guarded the no-variant branch of `precompute_for`, which only analysis code reaches. No checkpoint has that config.
- `next_death` no longer emits `alive_mask` in the goldens. Under that variant the column is dump-only, so it belongs to the unguarded metrics surface. Real next_death runs do emit it today, through the transitional `metrics_cfg_from`.
- `alive_mask` is guarded through `time_bin` only, stored as `time_bin@alive_mask.npy`.

Daniel's read: MetricsConfig becomes a real stored sub-config at the config bump, after the first cut. If we want `alive_mask` in dumps, that is the motivation to do it properly then.

If column requests are ever guarded, the supervision point type becomes the product of `TargetsConfig` and a column-requests sub-config. Splitting MetricsConfig into column requests versus other apparatus knobs (dump cadence, metric selection) would make that clean, because every field of the sub-config would then affect the references. There is one column request today and it may not survive the bump, so this waits.

### How we got here

8.23-3's "store emitted facts, not source configs" had three reasons. Under the dependency table, two of them no longer apply: duplicate-emitting points share every file, and the pinned packing flags are a minor point either way. The surviving reason is that MetricsConfig is a mixed bag, most of whose future fields won't affect emission. That is a fact about config design, and the registry should not compensate for it by storing derived values.

## 2. Registry layout: two point lists, for now

The registry keeps two point lists, two directory trees, and two test files (one per surface). The alternative discussed, "option 3", is one point list where a point is the full emission config block and the dependency table covers every key including `obs`. It is the purest form of configs-primary, and it would merge the registry, the path scheme, the dependency table, and the reference-form dispatch into one mechanism.

The framing that settled the choice: a surface is where a producer (the walk core, the tail) concretely emerges in the code. Option 3 does not dissolve surfaces. It moves them from the outer partition of the registry to a declared attribute of each key, and the producers stay two functions either way. With two surfaces and no third in sight, two lists is defensible. The triggers for revisiting are a memory-derived target (a supervision key that reads ObsConfig) or guarding column requests.

Cheap alignments toward option 3, done this session:

- Each supervision key declares a reference form (`RefForm.FULL` or `RefForm.FRAME_HASHES`), and `stored_form` dispatches on it. The two forms differ in one operation, so the dispatch is a single `match`. If obs ever joins the table as a third form, per-form objects (writer, loader, comparer, summary) would replace it.
- Per-key reference metadata is a typed `KeyRef(key, form, path)` record on the entry, replacing three loose fields.
- Regen plans both surfaces before writing anything.
- Dependency fields are bare `TargetsConfig` field names. Qualification comes the day a second sub-config joins a point.

Outputs that depend on a model (forward goldens, dump goldens, anything `dump_val_frames` controls) need a fixture type of replay perspective plus model. That is a second matrix, downstream of this one, and not a row in this registry.

**Daniel's takeaway:** Option 2 is the safe choice, for the time being. Option 3 could possibly be a leaky abstraction, as the guarded surfaces have different characteristics. It would need more exploration, and is probably isn't worth reconsidering until the goldens are more built out and battle-tested. But it can be a soft focal point in our design process, hence the cheap alignments listed right above.

## 3. SimGame and CorpusGame

The recorded game used to travel as a loose `sim` dict plus a `GameMeta` that unwrapped four of the dict's own entries. It is now two types in `bc.datapipe.sim_types`:

- `SimGame`: the replay parser's output schema as a frozen dataclass, one named field per array, with `T`, `H`, `W`, `deaths`, and `p_start` derived. The loader asserts the npz key set equals the field set.
- `CorpusGame(sim, perspectives)`: the sim plus the curated perspectives from the meta npz. Producers take a `SimGame` and one `PerspectiveMeta`, never a `CorpusGame`, which encodes the fact that they don't need the curated list.

The kernels are shared with live inference, which builds its own sim dict with growing lists for the per-tick fields. So the kernels keep their `sim["key"]` bodies, their parameter type widened to `Mapping`, and `SimGame` carries a temporary `__getitem__` shim marked `TODO(sim-typing)`. The shim comes out with the inference refactor, when the live path gets its own typed game and the kernels switch to attribute access behind a field protocol.

Two things deliberately not done: deriving `PerspectiveMeta` from the sim's death events (the meta's placement and elimination tick may encode surrender and tie handling the sim doesn't), and giving the schema one home shared with the parser (`training` doesn't depend on `replay_parser`, so that is a dependency-direction question for the layer-1 goldens).

## 4. What landed

The following commits:

- Obs producer wrapper and streaming hashes. `compute_obs` beside `compute_supervision`, an `ObsHasher` that consumes the walk one frame at a time (per-channel digests accumulated incrementally are byte-identical to the stack-based ones), and one `KeyDiff` row diff shared by the test message and regen's contradiction report. Two bugs fixed: the missing-keys set in `compare_supervision` was computed backwards, and the supervision test's unblessed label was not an f-string.
- The hash switched to sha256 truncated to 8 bytes. On the survivor fixture, hashing one walk took 0.16 s versus 0.34 s for blake2b, and the walk itself 0.26 s. The suite dropped from 3.4 s to 2.2 s.
- SimGame and CorpusGame, as above.
- The registry reshape from section 1, the emit-spec builder, `attach_sim_frame` moved off `PartialEmitSpec` onto `to_spec` as a required kwarg, and a fix to regen's move detection (it compared raw array bytes to `.npy` file bytes, so it could never match).
- Regen: plan-then-write for both surfaces, and one orphan sweep over the whole references tree, which now also catches files of a removed point or fixture.

The goldens served as the byte-neutrality proof for three of these (streaming, SimGame, and the registry reshape): each passed on the existing references without a re-bless.
