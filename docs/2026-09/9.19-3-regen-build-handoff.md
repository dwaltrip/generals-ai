## Chunk 4: revisions module and blocking test

- **The revisions module never sees the plan.** It takes plain inputs: the date, the digest, the changed surface labels, and the rendered extent text. The command line assembles those from the plan.
- **The blocking test imports only the revisions module, the store (for the digest), and the paths.** Nothing from planning, compute, or the guarded code. That keeps it cheap and independent of the code it guards.
- **Surface labels.** `Plan.changed_surfaces` returns the store's `Surface` values. The mapping to 7.20-2's labels (`obs`, `training-targets`) belongs in the revisions module with the kinds and impact labels.
- **The dependency.** python-frontmatter goes into the `training` package. Add it from the repo root with the package named, since this is a uv workspace and a sync from inside the package strips the root dev deps. The pre-commit hook regenerates the modal requirements file when the lock changes.
- **Red between chunks.** The blocking test fails on "no revisions" until chunk 5 writes revision 0001. The 8.12-1 posture allows that.
- `REVISIONS_DIR` goes in `paths.py`.

## Chunk 5: wiring and bootstrap

- **The early digest.** A pure digest function over (relative path, bytes) pairs, with the directory walk as a thin wrapper. The store gets serialization helpers that write through the same `np.save` and `np.savez` calls into a buffer, so the digest and the on-disk write can't drift. The mechanism golden pins the pure function. Serialization was checked deterministic on numpy 2.4.
- **The planned digest includes unrecognized reference files.** They stay on disk and count, so the pre-write digest is the planned files' bytes plus those files' bytes read from disk. The post-write verify would catch a miss here, but it should be right from the start.
- **Two renderers over one structure.** `render_extent` is the short form for the record's Extent block, beside `render_report`. The skeleton writer receives the rendered text.
- **Run order.** Plan, digest, read the newest revision, write, verify the tree's digest equals the planned one, then print the report with the revision outcome as its final line. `--dry-run` skips write and verify.
- **The final line has three forms.**
  - A skeleton was appended, with its number.
  - The set matches revision N. If any files were new this run, the line adds that they were restorations.
  - No revisions existed, so 0001 was appended.
- **Bootstrap.** Revision 0001 is filled as a coverage change, "initial throwaway bless". The README legend is adapted from 7.20-2 per 9.18-1 section 12.
