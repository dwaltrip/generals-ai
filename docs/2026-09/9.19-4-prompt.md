## A few useful guidelines / mental frames to carry into the coding work

### Software engineering principles

Some general software-enginneering wisdom that has been very helpful during refactors in recent weeks:

- Look for key interfaces and function signatures that don't feel right.
- Follow the trails and peel away the layers, as we try to make the interfaces are very clean and tight.
- Carve out mini-abstractions that feel conceptually strong and coherent, given the architecture of the related modules (and the broader codebase).
  - E.g. Type with dataclasses! Loose dicts are opaque and provide a much weaker conceptual handle. Dataclasses are more work up front, but less token-efficient in the long run.
- Don't treat existing code as a strict contract that must be adhered to.
  - Interfaces for older code should get a fresh look when we touch them.
  - Especially if the code hasn't received much attention in a while. Or if the new code we are working on isn't fitting together nicely with the older pieces.
  - Have we been circling a design question a few times? is something feel trickier or more confusing than expected? This may indicate that some existing code needs to be improved.

These ideas are generally useful for software work and are good to keep in mind. Please do so as we work.

### Working style notes

These bullets are copied from an ealier note, and reflect a good working style that emerged during that session. They may useful for us during this session.

- **Discussion before code, one piece at a time.** Each piece gets its shape agreed in chat before anything is written. Judgment calls are surfaced rather than resolved silently, and the pace is deliberately slower than default.
- **Tier by clarity.** Start with the pieces that are settled and hard to get wrong, then their consumers, and hold back what is genuinely ambiguous (the regen internals, the report writer).
- **Pull warm threads, with scope checks.** The alive_mask trace grew into the emit semantics, the decoupling scope, and the measurement-config note, and each expansion was worth it. The counterweight also applied: enthusiasm for a larger refactor (the TrainConfig restructure) was converted into a parked scoping step instead of immediate work.
- **Prose register.** The session put sustained effort into plain, de-slopified writing in both code comments and docs. The drafting process used for 8.15-2 (scratch notes, plainify passes, then the doc) is reusable for future substantial notes.
