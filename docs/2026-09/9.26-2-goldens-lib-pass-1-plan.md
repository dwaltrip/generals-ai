## Overview

The library will run one pipeline for every surface:

```
Registry
  ├─ compute_all ───> computed entries, grouped by surface ─┐
  └─ fixture_infos ─> list[FixtureInfo] ────────────────────┤
                                                            ▼
                                     plan(computed, fixtures, root) ─> RegenPlan
                                                                         ├─ apply ─> references tree
                                                                         └─ render_regen_report ─> text
```

The regen pipeline splits nicely into two halves:

- The front half is where the project's inputs come in: surfaces, points, and fixtures in the registry, along with producers and the fixture loader. The modules in this half (`registry` and `compute`) work with the project's types, such as training configs, fixture records, and loaded fixture data.
- The handoff between the halves primarily consists of the computed entries (grouped by surface).
    - Each computed entry is an entry id and its computed content.
    - `run_regen` also passes basic info about the fixtures to the back half (used in report rendering).
- The back half (`store`, `plan`, `apply`, and `report`) works solely off these received records. This results in a clean interface and minimal coupling across the pipeline.

The records that pass between the halves are defined in a shared module (`entry.py`). Thus the halves don't need to import from each other. The entry point for the pipeline, `run_regen`, orchestrates both halves.

**A large benefit of this design**: because the back half doesn't depend on the project's types, if we change how fixtures, registries, or surfaces work in the future, we should mostly need to update the front half code.

Looking at the steps in a bit more detail:

- Compute will load each fixture once, run every point of every surface on it, and return a `ComputedEntry` for each entry. The entries will be grouped by surface, in registry order.
- The computed data is then passed to `plan`, along with the fixtures and the directory path for the references.
  - It will scan the tree using the passed-in root, load the stored content for each entry, and then classify each entry as new, unchanged, changed, or moved.
  - Reference files that don't belong to any computed entry will be removed, as long as they are under one of the registry's surfaces.
  - The plan will hold one `SurfacePlan` per registered surface, along with the fixtures in registry order.
- The `apply` step will write what the plan says.
- Lastly, the regen report will be rendered from the `RegenPlan`, using pure functions to derive the report text from plan data.

The golden test will use the same pieces for one entry at a time: load the fixture, produce the content, load the stored reference, diff the two, and render any diff as the failure message.

The vocabulary follows 9.26-1:

- An entry is one (surface, point, fixture). It is the unit being guarded: one test case and one file on disk.
- A reference is an entry's blessed content, stored on disk.
- Computed content is an entry's freshly produced content. It is `got` in comparisons, and the reference is `stored`.
- Content is the general word for either. Its type is `EntryContent`, a `dict[str, np.ndarray | RowHashes]`. Each named array is stored either in full or as row hashes (see the content section below).

The lib modules fall into the following buckets:

- Shared: `content`, `entry`, `diff`, and `render`. These are plain data types and pure functions that are used across the pipeline.
- Front half: `registry` and `compute`.
- Back half: `store`, `plan`, `apply`, and `report`.
- `run`: the entry point which calls into both halves.
- `hashing`: this is a utility module the lib provides for project-side code so that producer functions can more easily return hashed data.

9.30-2 contains diagrams showing the dependencies between lib modules and how the modules will be used by project code.

`lib/__init__.py` will define the library's public API. Project code, including the project's tests, will import from `training.goldens.lib`. The library's own modules and tests will import from specific modules. Since project code won't import from `lib.registry` directly, the library's `registry.py`, which defines the `Registry` type, and the project's `registry.py`, which builds the project's instance, can share a name.

`regen.py` will replace the `regen/` sub-package, since the command line is all that remains of it on the project side. The command will stay `uv run python -m training.goldens.regen [--dry-run]`.

## The library

### Content

```python
@dataclass(frozen=True)
class ArrayLayout:
    shape: tuple[int, ...]
    dtype: np.dtype
    hashed_axis: int | None   # None: stored in full. Otherwise, shape and dtype are the raw array's.

@dataclass(frozen=True)
class RowHashes:
    hashes: np.ndarray        # uint64, one per index along layout.hashed_axis
    layout: ArrayLayout       # hashed_axis is set

type EntryContent = dict[str, np.ndarray | RowHashes]

def layout_of(value: np.ndarray | RowHashes) -> ArrayLayout: ...
def row_data(value: np.ndarray | RowHashes) -> np.ndarray: ...   # the array compared row by row
def content_id(value: np.ndarray | RowHashes) -> str: ...        # hash of layout and bytes, for the report's labels
```

A content value is either a plain array, stored in full, or a `RowHashes`: one hash per index along an axis of a raw array, together with the raw array's layout. Producers choose the form of each array (see the hashing section below). Because the raw layout is recorded, a dtype or shape change in hashed data will read as a layout change, instead of as every row changing. The diff handles both forms the same way, comparing layouts with `layout_of` and then rows with `row_data`.

`check_content(content)` will enforce 9.26-1's producer rules, along with rules that the store and the diff need:

- Names are non-empty strings with no `/`. Producers flatten any nesting, for example `policy.logits`.
- Reserved names: `__meta__` (used by the store, see below), and `file` and `allow_pickle` (keyword parameters of `np.savez`).
- No dtype holds Python objects (`dtype.hasobject`), since their stored bytes aren't a stable encoding of the content.
- Every array has at least one axis, since the diff locates changes along axis 0.
- For a `RowHashes`, the hashes are uint64, with one per index along `hashed_axis`.

A failed check will be an assertion error. It means a producer is broken, so regen will stop there instead of recording it in the plan.

### Hashing

```python
def row_hashes(arr: np.ndarray, axis: int = 0) -> RowHashes: ...

class StreamingRowHasher:
    def __init__(self, axes: tuple[int, ...]) -> None: ...
    def add(self, row: np.ndarray) -> None: ...         # the next slice along axis 0 of the raw array
    def hashes(self) -> tuple[RowHashes, ...]: ...      # one per entry of `axes`
```

`row_hashes` will hash each slice of an array along one axis. It will replace `hash_along_first_axis` and `stored_form`.

`StreamingRowHasher` will compute the same hashes for a raw array that arrives one slice at a time. It is a generalization of the existing `ObsHasher` (which hashes along `axes=(0, 1)`) and will replace it. The resulting `RowHashes` will be identical to those that `row_hashes` would return. The purpose of the streaming hasher is solely to reduce memory use when hashing large arrays (e.g. obs).

The axes refer to the raw array. Axis 0 will be hashed once per added slice. For each other axis, the hasher will keep one incremental hash per index, updated with that index's part of each slice. The hash function stays the same: sha256 over the C-order bytes, truncated to 8 bytes and read as a little-endian uint64.

The streaming hasher will assert that every added slice has the same shape and dtype as the first, and that at least one slice was added before `hashes()` is called. Today only the channel count and the non-empty case are checked.

The stored files will gain the raw layout (see the store section), but the hash values themselves won't change. 9.26-1 checked on a random tensor that `ObsHasher`'s output equals the batch row hashes along axes 0 and 1, and the review of this note repeated the check on fp16, fp32, and uint8 tensors. So the mechanism golden's pinned values will stay valid through the switch.

### The content diff

```python
@dataclass(frozen=True)
class ArrayAdded:
    name: str
    got: ArrayLayout

@dataclass(frozen=True)
class ArrayRemoved:
    name: str
    stored: ArrayLayout

@dataclass(frozen=True)
class ArrayLayoutChanged:
    name: str
    stored: ArrayLayout
    got: ArrayLayout

@dataclass(frozen=True)
class ArrayRowsChanged:
    name: str
    layout: ArrayLayout       # the same on both sides
    rows: tuple[int, ...]     # indices along axis 0 of row_data

type ArrayChange = ArrayAdded | ArrayRemoved | ArrayLayoutChanged | ArrayRowsChanged

@dataclass(frozen=True)
class ContentDiff:
    changes: tuple[ArrayChange, ...]   # ordered by array name

def diff_content(got: EntryContent, stored: EntryContent) -> ContentDiff | None: ...
```

`diff_content` will compare the two contents name by name. An array present on one side only is added or removed. An array present on both sides is compared by layout first, using `layout_of`, and if the layouts match, row by row on `row_data`, by bytes. Since the layout includes `hashed_axis`, a switch between full and hashed storage, or to a different axis, reads as a layout change. The byte comparison carries over from `diff_rows`: a NaN row equals itself, and `-0.0` differs from `0.0`.

One fix is needed: `diff_rows` reshapes each array to `(n_rows, -1)`, which raises an error for arrays with zero rows. The new diff will compute the row width explicitly, since an empty array is a normal case for a generic library (an event list with no events, for example).

Content will be equal exactly when `diff_content` returns `None`. This will be the one definition of equality, used by the golden test, by planning, and by move matching.

`ContentDiff` will wrap the tuple so that fields about the content as a whole can be added later, without changing the signature of every function that takes a diff. New kinds of array change, such as the ones row alignment and keyed matching would need (9.26-1 items 2 and 3), will be new members of the `ArrayChange` union.

Rows will be stored as a tuple of ints instead of an ndarray. This keeps test failure output readable, and lets diff records be compared with `==` (which doesn't work with numpy arrays). Note: equal records mean the same location changed, not that the values changed the same way.

`render.py` will hold the text form of a change, shared by the report and the test failure message:

- `render_rows(rows, n)` gives forms like `rows 12..15 of 138`, `row 40 of 183`, or `7 of 566 rows, from 500`.
- `render_change(change)` renders one array change on one line.
- `render_content_diff(diff)` renders the whole diff, one change per line, for a test failure.

The library gives no meaning to row indices, so pass 1 will render them as rows. Surface-specific labels (ticks for axis 0, channel names for obs) will come with the label hook in a later pass.

### Surfaces, points, fixtures, and the registry

```python
@dataclass(frozen=True)
class Point[CfgT]:
    name: str
    cfg: CfgT

@dataclass(frozen=True)
class Surface[CfgT, DataT]:
    name: str
    points: tuple[Point[CfgT], ...]
    produce: Callable[[CfgT, DataT], EntryContent]

class Fixture(Protocol):
    @property
    def id(self) -> str: ...

@dataclass(frozen=True)
class Registry[FixtureT: Fixture, DataT]:
    surfaces: tuple[Surface[Any, DataT], ...]
    fixtures: tuple[FixtureT, ...]
    load_fixture: Callable[[FixtureT], DataT]

    def __post_init__(self) -> None: ...   # unique, path-safe names

@dataclass(frozen=True)
class Entry[FixtureT: Fixture, DataT]:
    surface: Surface[Any, DataT]
    point: Point[Any]
    fixture: FixtureT

    @property
    def id(self) -> EntryId: ...

def entries[FixtureT: Fixture, DataT](registry: Registry[FixtureT, DataT]) -> list[Entry[FixtureT, DataT]]: ...

def fixture_infos(registry: Registry) -> list[FixtureInfo]: ...
```

`Point` and `Surface` follow 9.26-1 item 6, with tuples in place of lists so that the frozen records are immutable all the way down. The app's fixture type only needs an `id`, and the app supplies the loader. The loaded fixture data (`DataT`) is whatever the producers need, and the library won't look inside it. Every surface will run on every fixture.

9.26-1 left open whether surfaces, fixtures, and the loader are bundled into one record or passed separately. Every consumer needs all three together: compute, the golden test, and the command line. A bundle gives the project's `registry.py` one object to export, and gives the library one place to check names. The check will run in `__post_init__`, so any registry that exists is valid:

- Surface names are unique, point names are unique within a surface, and fixture ids are unique. The comparison uses `casefold()`, since the default macOS file system ignores case.
- Every name is non-empty, contains no `/`, and doesn't start with `.`, since all three become path components.
- A surface with no points is allowed. It produces no entries, and the regen report will show a warning line for it.

The registry won't hold the references root. The root will stay an explicit parameter of `plan` and of the store, so the same registry can be planned against a temporary tree in tests. The record will have no methods beyond the check.

`Entry` will hold the objects for one entry. It will be used on the compute side and by the golden test, and it won't be passed to planning.

`fixture_infos` will turn the registry's fixtures into `FixtureInfo` records (defined in `entry.py`), which hold each fixture's id. They will be passed to `plan`, so that the back half has the fixtures in registry order without depending on the app's fixture type.

### Entry identity and the store

```python
@dataclass(frozen=True)
class EntryId:
    surface: str
    point: str
    fixture: str
```

`EntryId` will be the identity of an entry, with plain string fields. It will be defined in `entry.py`, with the other records passed between the halves. It will replace `RefId`, which has an optional `key` and a `Surface` enum. The enum will go away, since surfaces will be defined by the registry.

The store will be the only module that reads or writes the references tree, as 9.19-1 set out for the current store. Planning, apply, and the digest will all go through it. It will be a set of module functions that take the root as a parameter. The root won't have a default, since the library doesn't know the project's paths. The public API will export the store as a module, so callers will write `store.load(eid, root)` and the functions can keep short names.

```python
def rel_path(eid: EntryId) -> Path: ...                  # <surface>/<point>/<fixture>.npz
def parse_rel_path(rel: Path) -> EntryId | None: ...     # the exact inverse of rel_path

@dataclass(frozen=True)
class TreeScan:
    root: Path
    entry_ids: list[EntryId]
    unrecognized: list[Path]   # .npz files that don't parse or are under an unknown surface, relative to root
    ignored: list[Path]        # other files, relative to root

def scan(root: Path, surfaces: Collection[str]) -> TreeScan: ...
def load(eid: EntryId, root: Path) -> EntryContent | None: ...   # rebuilds RowHashes from __meta__, and checks them
def save(eid: EntryId, content: EntryContent, root: Path) -> None: ...
def remove(eid: EntryId, root: Path) -> None: ...
def serialize(content: EntryContent) -> bytes: ...
def set_digest(root: Path) -> str: ...
```

The layout will be `<surface>/<point>/<fixture>.npz` for every surface. The obs references are already at these paths. The supervision references will move from `supervision/<fixture>/<point>@<key>.npy` to `supervision/<point>/<fixture>.npz`, with one member per key.

Other details of the store:

- A reference file will be an `.npz` file. `.npy` won't be a reference suffix, so an old supervision file left in the tree would be listed as ignored.
- `parse_rel_path` will work on relative paths and reject empty parts, which resolves the `parse_rel_path` item in 9.24-2.
- `TreeScan` is today's `ReferenceSet`, renamed. Dotted files will stay out of it, as they do today.
- `set_digest` will still hash file bytes, and chunk 5 will decide whether it moves to content. It will cover every `.npz` file under the root, as today's digest covers every file with a reference suffix. This includes the files that `scan` lists as unrecognized, such as those under a surface that is no longer registered. It is the safer choice for now, since a change to any `.npz` file in the tree changes the digest. Whether unrecognized files belong in the digest will be revisited with chunk 5's design, and the code will carry a TODO for it. Dropping `.npy` changes the value that `test_set_digest` pins, since its tree includes an `.npy` file. The re-pin is a mechanism change, done in the switchover while no revision exists.
- `load` will use `np.load` (with `allow_pickle=False`) and return the members as a dict. Also:
    - Rebuilds each `RowHashes` from the `__meta__` member (see the serialization paragraph below).
    - Raises an error if the metadata is malformed: meta entries don't match the file members or a hash count doesn't match the recorded layout.
- `save` will write the bytes from `serialize`.

**Files under an unknown surface.** When determining if a file is a golden reference, `parse_rel_path` will check a path's structure (three path parts ending in `.npz`, e.g. `<a>/<b>/<c>.npz`), not whether the names exist in the registry. As the design is to leave unknown files alone (9.19-1's rule), `scan` will filter by the names of the registered surfaces, and files under all other top-level directories will be listed as "unrecognized". This works because `plan` now receives its input grouped by surface, and treats this as the definitive list of registered surfaces. And thus it can ensure that only the files for a currently registered surface may be removed. In contrast, if a surface is dropped from the registry, its files are left in place (as unrecognized), and removing them is a manual cleanup.

**Serialization as a function of content.** `np.savez` output is deterministic for fixed inputs in one environment. 9.19-1 checked this, and it was checked again on numpy 2.4.4 for this note. But equal content can still serialize to different bytes in two ways:

- `np.savez` writes members in argument order. If a producer changed the order of its dict, the content would compare equal while the file bytes differed.
- `np.save` records Fortran order in its header, so a Fortran-ordered array serializes differently from a C-ordered array with the same values. This was checked on numpy 2.4.4.

`serialize` will sort the array names and convert each array to C order, which removes both. Without these two steps, a file whose content hasn't changed could still be rewritten with new bytes when an entry is saved, and show as modified in git.

A `RowHashes` will be stored as its hashes under the array's name. Its layout will go in a `__meta__` member: a JSON string, written with sorted keys, holding each hashed array's raw shape, dtype, and hashed axis. Plain arrays need no metadata, since their `.npy` header already records their shape and dtype.

Sorting doesn't make the bytes independent of the environment. The `.npy` header padding and the zip metadata written by Python's `zipfile` can differ across numpy versions, Python versions, and platforms. This matters for chunk 5. Unchanged entries aren't rewritten, so a planned digest computed by re-serializing their content could differ from the files on disk after a numpy upgrade, with no content change. Chunk 5 should use the bytes already on disk for unchanged entries (planning reads those files anyway), or compute the digest over content, for example through 9.26-1's manifest. The mechanism golden will pin `serialize`'s output for a small synthetic content, so a format change, whether from a code change or from a numpy or Python upgrade, will be caught.

At the switchover, every file changes anyway: the obs files gain `__meta__`, and the supervision files move to the new layout. The switchover will re-bless from an empty tree, so every file will be written by `serialize`.

### Compute

```python
@dataclass(frozen=True)
class ComputedEntry:          # defined in entry.py
    id: EntryId
    content: EntryContent

def produce[DataT](entry: Entry[Any, DataT], data: DataT) -> EntryContent: ...

def compute_all[FixtureT: Fixture, DataT](
    registry: Registry[FixtureT, DataT],
    *,
    on_fixture: Callable[[FixtureT, DataT], None] | None = None,
) -> dict[str, list[ComputedEntry]]: ...
```

`produce` will run one entry's producer on loaded fixture data and check the result with `check_content`. `compute_all` will load each fixture once, call `produce` for every entry on that fixture, and call `on_fixture` after each fixture. It will return the computed entries grouped by surface name, in registry order. The command line will use the callback to print the progress line, reading `T` and `end_t` from the project's fixture data. The golden test will call `produce` directly, so the test and regen will share the code that runs a producer.

Compute will have no checks of its own beyond `check_content`. The keyset check, `_check_agreement`, the identical-groups check, and `RegenAbort` will all go with the dependency table (9.26-1 item 1).

A computed entry will be only an identity and content. It won't carry the `Entry` or the point's config. This keeps planning and its data types independent of the registry, so planning tests can build computed entries from literals. A later hook that needs a point's config (such as obs channel names in the report) will have to receive it alongside the plan. That design is left for when the hooks are built.

Additional details:

- Registered surfaces without any points will still be included in the output (with an empty list). The full set of registered surfaces is used to decide which files on disk are removed.

### Planning

```python
# The statuses and PlannedEntry are defined in entry.py.

@dataclass(frozen=True)
class New: ...

@dataclass(frozen=True)
class Unchanged: ...

@dataclass(frozen=True)
class Changed:
    diff: ContentDiff
    stored: EntryContent  # for later compare hooks (9.26-1 item 3)

@dataclass(frozen=True)
class Moved:
    source: EntryId

type PlannedEntryStatus = New | Unchanged | Changed | Moved

@dataclass(frozen=True)
class PlannedEntry:
    id: EntryId
    content: EntryContent
    status: PlannedEntryStatus

@dataclass(frozen=True)
class SurfacePlan:
    surface: str
    planned_entries: list[PlannedEntry]
    planned_removals: list[EntryId]

@dataclass(frozen=True)
class RegenPlan:
    tree: TreeScan                  # the scan before the run
    fixtures: list[FixtureInfo]     # registry order
    surfaces: list[SurfacePlan]     # registry order, including surfaces with no points

    def planned_entries(self) -> list[PlannedEntry]: ...   # flat view across surfaces
    def is_noop(self) -> bool: ...                # every status Unchanged, nothing removed
    def changed_surfaces(self) -> set[str]: ...   # surfaces with any Changed status

def count_statuses(planned_entries: Iterable[PlannedEntry]) -> Counter[type[PlannedEntryStatus]]: ...

def plan(
    computed: dict[str, list[ComputedEntry]],
    fixtures: list[FixtureInfo],
    root: Path,
) -> RegenPlan: ...
```

`Changed` will carry the stored content, as 9.26-1 item 3 asks. Planning already loads it.

`plan` will be the only function in planning that touches the tree. It will:

1. Scan the tree, for the registered surfaces, taken from the grouped computed entries.
2. Find the orphans: scanned entries that don't belong to any computed entry.
3. Load each computed entry's stored content and classify it with `classify`.
4. Load the orphans' content, and change the status of matching `New` entries to `Moved` with `match_moves`.
5. Collect the orphans that weren't used as a move source. These are the planned removals.
6. Build one `SurfacePlan` per surface, in registry order.

The helpers will be pure functions over data:

- `classify(got, stored)` returns `New` when nothing is stored, and otherwise `Unchanged` or `Changed` according to `diff_content`.
- `match_moves(planned_entries, orphans)` takes the planned entries and a mapping from each orphan to its content. A `New` entry becomes `Moved` when an orphan has the same surface and fixture, and equal content. Each orphan is used at most once, in scan order.

The move rule carries over from 9.24-1. With per-point storage, a file can only move when a point is renamed, and the rule will match whole contents instead of single arrays. The coincidence that 9.19-1 guarded against (the alive and present masks are identical on some fixtures) won't cause the wrong files to be paired. A coincidence of whole contents is still possible. If one point is removed and a new point is added in the same run, and the two have identical content on some fixture, that fixture will read as a move. The files written will still be correct, and only the report's description will be off.

The byte-match notes will go away. Their main use was key renames, which will show up as added and removed arrays inside a file.

The plan will be grouped by surface. Each `SurfacePlan` will hold one surface's planned entries and removals, and `RegenPlan.planned_entries()` will give a flat view for code that doesn't need the grouping, such as apply and the headline counts. Most consumers work per surface: the report's sections and its empty-surface warning, and later chunk 4's impact pre-fill and the per-surface hooks.

The field name `RegenPlan.tree` is still provisional, as in 9.24-1.

### Apply and run

`apply(plan)` will save every planned entry whose status isn't `Unchanged`, carry out the planned removals, and remove the source of each move. It will match on the status, with no asserts.

```python
def run_regen[FixtureT: Fixture, DataT](
    registry: Registry[FixtureT, DataT],
    root: Path,
    *,
    write: bool,
    on_fixture: Callable[[FixtureT, DataT], None] | None = None,
) -> RegenPlan: ...
```

`run_regen` will call `compute_all` and `fixture_infos`, then `plan`, then `apply` (unless `write` is false). It will be the home for the run's sequence, which chunk 5 will extend with the digest, the revision step, and the post-write check.

It will return the `RegenPlan` directly. 9.24-1's `RegenResult` held the plan and the identical-groups warnings. The warnings will be gone, so until chunk 5 the result would only wrap the plan.

### The report

`render_regen_report(plan) -> str` will be a library function. It will be written in terms of named arrays, and it will work the same way for every surface. In pass 1 it will have no per-surface hooks. It will have four parts:

1. A title line and a headline of counts (changed, new, moved, removed, unchanged), counted per entry.
2. For each surface, the entries that are new, moved, or removed, grouped by point, with their fixtures. A surface with no points gets a warning line here.
3. For each surface, the changed arrays, as described below.
4. Stray files: unrecognized paths and ignored files, as today.

Under each changed array, there will be one block for each fixture where the array changed on at least one point. A block lists every point that has the array on that fixture, including points where it didn't change. A point has the array if the array is in the entry's computed or stored content, and the entry was compared (its status is `Changed` or `Unchanged`). Each line will show:

- where the array changed: the changed rows, a layout change, added, removed, or unchanged
- labels for the content before and after the run, such as `1-A -> 1-B`. An unchanged point shows one label.

The labels stand for content ids (from `content_id`, a hash of the array's layout and bytes). Letters are assigned per array and fixture, in order of first appearance, so equal content gets the same letter. The prefix is the fixture's number in registry order, so labels from different fixtures can't be confused. Points whose content is the same both before and after share one line. The fixtures where the array didn't change on any point are collapsed into one line.

The labels show which points held the same content before the run and after it, without the report interpreting the result. The location of a change can't show this by itself, since two points can change at the same rows in different ways. For example, if three points had identical `action_target` arrays and one of them now differs from the other two, the labels show it as `2-A -> 2-B` and `2-A -> 2-C`.

Entries that are new, moved, or removed have no diff, so they will appear only in the entry-level lines.

An example, for a hypothetical run against the current registry. It has one new supervision point, `next_death_v2`, and a new array, `next_elim_order`, emitted by `next_death`. The exact formatting will be settled when the report is built.

```

    Fixture 1 (ukRz7oSS8-s7)
      fp16_player_status_on        rows 101..102 of 110   1-A -> 1-B
      fp32_pre_player_status       unchanged              1-C
    unchanged on 2 fixtures
  frame_hashes
    Fixture 1 (ukRz7oSS8-s7)
      fp16_player_status_on        rows 60..137 of 138    1-A -> 1-B
      fp32_pre_player_status       unchanged              1-C
    unchanged on 2 fixtures

supervision
  new   next_death_v2   3 fixtures
  action_target
    Fixture 1 (ukRz7oSS8-s7)
      core, time_bin, next_death   rows 12..15 of 138     1-A -> 1-B
    Fixture 2 (xdZsRyX0O-s2)
      core, next_death             row 40 of 183          2-A -> 2-B
      time_bin                     row 40 of 183          2-A -> 2-C
    unchanged on 1 fixture
  next_elim_order
    Fixture 1 (ukRz7oSS8-s7)

The report will be kept minimal on purpose. A later report pass will cover:

- derived facts, such as noting where points that agreed before the run now differ
- new and removed entries in the array sections
- per-surface labels, such as ticks and obs channel names
- the formatting

## The project side

`registry.py` will keep the data and gain `REGISTRY`:

OBS_POINTS = (

SUPERVISION_POINTS = (

```

These will go away:

The import-time checks will shrink to `_assert_no_defaults` on the config classes. The name checks will move to `Registry`, and the `alive_mask` check will go with `keys`.

### Fixtures

`fixtures.py` will replace `loaders.py`. It will hold `FixtureRecord`, a `FixtureData` record with the `SimGame` and `PerspectiveMeta`, and `load_fixture`. `FixtureRecord` will move here from the registry, so that the registry can import the loader without an import cycle. `load_supervision_reference` will go away, since a supervision reference will be one file.

### Producers

`producers.py` will replace `goldens/compute.py`, as 9.24-1 planned:

- `produce_obs(cfg, data)` will walk the fixture with a `StreamingRowHasher(axes=(0, 1))` and return `frame_hashes` and `channel_hashes` as `RowHashes` values, with the same hash values as today.
- `produce_supervision(cfg, data)` will build the emit spec from the config, stack each key over ticks, and store `legality_mask` as `row_hashes(...)` along axis 0. Every other key will be stored in full, as today. The inert metrics config it needs will move here from the registry.

The default form for supervision keys (9.26-1 item 7) will stay open. Pass 1 will keep today's forms, so the switchover can be checked against the current references.

### The command line

`regen.py` will parse `--dry-run`, call `run_regen(REGISTRY, REFERENCES_DIR, write=not args.dry_run, on_fixture=...)`, print the progress lines and the report, and return 0. No abort path will remain, so there will be no failure exit code until chunk 5 adds one.

## Tests

In `tests/goldens_lib/`, all on synthetic input:

- `test_diff.py`, from `test_compare.py`: bytes versus values, layout changes (including a switch between full and hashed storage), added and removed arrays, and arrays with zero rows.
- `test_hashing.py`: the streaming hasher's output equals `row_hashes`'s along each requested axis on a random tensor, for both the hashes and the raw layout, and a slice with a different layout is rejected.
- `test_store.py`: path round trips and off-scheme paths on synthetic ids, a save and load round trip, a `RowHashes` round trip through `__meta__`, an error on malformed metadata, and serialization that doesn't depend on dict order or memory order.
- `test_plan.py`: `classify` and `match_moves` on literal inputs. A rename is a move, equal content on another fixture is not, and each orphan is used once.
- `test_regen.py`: a synthetic registry with toy fixtures and producers, regenerated into a temporary tree. The producers emit at least one hashed array. The base tree must re-plan as a no-op. Then each case edits a copy of the tree or the registry, checks the plan, applies it, and checks that the tree re-plans as a no-op. The cases:
    - A deleted file reads as new.
    - A renamed point directory reads as moved.
    - Edited rows read as changed at those rows.
    - An extra or missing array in a stored file reads as removed or added.
    - An edited `__meta__` layout reads as a layout change.
    - A point dropped from the registry reads as removed.
    - When all the points of a surface are dropped, the surface's files read as removed.
    - Stray files read as unrecognized or ignored, including an `.npz` file under a directory that isn't one of the registry's surfaces.

In `tests/goldens/`, on the project's registry:

- `test_goldens.py` will replace the obs and supervision golden tests. It will be parametrized over `entries(REGISTRY)`, with ids like `supervision/core/ukRz7oSS8-s7`. A missing reference will fail with "unblessed, run regen", and a diff will fail with `render_content_diff`.
- `test_mechanism_golden.py` will move to `row_hashes` and `StreamingRowHasher`, with the same pinned hash values. It will also pin `serialize`'s output for a small synthetic content (one plain array and one `RowHashes`). `test_set_digest` will be re-pinned for the `.npz`-only suffix rule (see the store section above).
- `test_regen_smoke.py` will run `compute_all` on the real registry once, apply the plan to an empty temporary tree, re-plan the same computed entries against it, check that the plan is a no-op, and render the report. It covers the parts of the project's wiring that the golden test doesn't use: `compute_all`, the full pipeline, and the report on real content.

Today's `test_regen.py` runs the real producers, which take about 12 s of the 14 s goldens suite (per 9.24-1). A synthetic registry will exercise the same planning paths in well under a second, and its edge cases can be set up directly instead of through the real registry. The real producers stay covered by the golden test and the smoke test. The criterion 9.24-2 proposed for the two test directories (synthetic input goes in `goldens_lib`) then holds without exceptions.

The report's rendering won't be tested, beyond the render calls in the regen tests that check it doesn't fail. It will be checked by reading real output at checkpoint B.

### Verifying the switchover

The verification has one precondition: on the commit before the switchover, the old golden tests pass and `regen --dry-run` reports no changes. Otherwise the comparison below would show differences that the switch didn't cause. Both held on 2026-09-26, when the first draft of this note was reviewed.

9.24-1's check (the report output stays byte-identical) doesn't apply, since the report and the layout both change. Instead, a one-off script in `tmp/` will compare the re-blessed tree with the previous commit's references. It will read the old files with `git show`, so it won't modify anything. It will check:

- **Obs:** each new file's content equals the old file's, member by member. The bytes will differ, since the files gain `__meta__` and the members will be sorted.
- **Supervision:** each point's new file has exactly the keys that the old registry declared in that point's `keys`. Each member equals the old `supervision/<fixture>/<rep>@<key>.npy`, where `rep` is the key group's representative. With the current configs every key has a single group, whose representative is the first point that emits the key.

This confirms that nothing guarded changed in the switch. It also checks the old keyset declarations one last time before they are deleted.

The script will also print each file's `__meta__`, so the recorded raw layouts can be read at checkpoint B.

The report will be checked by reading it. At checkpoint B, a few dry runs will be shown in the session, using an edited copy of the re-blessed tree or a modified registry. Examples: a change shared by every point, a divergence, a layout change in a hashed array, a dropped point, and a surface with no points. Optionally, a small real code change (such as the tick-seam nudge from the 9.19-1 build) would give one report on real diffs.
