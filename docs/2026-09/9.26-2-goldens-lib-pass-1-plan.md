## Tentative decisions

These are the calls that most shape the result. Each one is discussed below, in the section it affects, under a **Tentative** label.

1. **The registry record.** Surfaces, fixtures, and the fixture loader will be bundled into one record, `Registry`, which will also validate names when it is constructed. Lean: bundle them.
2. **What a computed entry holds.** Only the entry's identity and its content, with no `Entry` or config objects. Lean: yes.
3. **A flat plan.** `RegenPlan` will hold one list of planned entries for all surfaces, with the surface as part of each entry's identity. 9.24-1 had one sub-plan per surface. Lean: flat.
4. **Hashable diffs.** Diff records will store changed rows as a tuple of ints, so that identical changes can be grouped with a dict. Lean: yes.
5. **Serialization as a function of content.** The store will sort array names and write C-ordered arrays, so that within one environment a reference file's bytes will depend only on its content. As a consequence, the switchover will re-bless from an empty tree. Lean: yes.
6. **The report layout.** Within each surface, changes will be listed by array, then by fixture, with points grouped by identical change and any unchanged points named. Lean: this layout.
7. **The regen integration test.** It will move to a synthetic registry in `tests/goldens_lib`, with one project-side smoke test on the real registry. Lean: yes.
8. **Files under an unknown surface.** A reference file under a top-level directory that isn't one of the run's surfaces will be reported as unrecognized and left in place, instead of being removed. Lean: yes.
9. **Three smaller calls from the sync, not yet confirmed:**
    - `EntryId(surface, point, fixture)` will replace `RefId`, with the surface as a plain string name.
    - `run_regen` will return the `RegenPlan` directly. `RegenResult` will wait for chunk 5, when it has something to hold beyond the plan.
    - One parametrized golden test will cover every entry of every surface, replacing the two per-surface tests.

## Overview

The library will run one pipeline for every surface:

```
Registry --compute_all--> list[ComputedEntry] --plan(computed, root)--> RegenPlan --apply--> references tree
                                                                                  \--render_regen_report--> text
```

- Compute will load each fixture once, run every point of every surface on it, and return a `ComputedEntry` for each entry.
- Planning is where the tree's root will come in. It will scan the tree, load the stored content for each entry, and classify each entry as new, unchanged, changed, or moved. Reference files that no entry claims will be removed, as long as they are under one of the registry's surfaces.
- Apply will write what the plan says. The report will be rendered from the plan by pure functions.

The golden test will use the same pieces for one entry at a time: load the fixture, produce the content, load the stored reference, diff the two, and render any diff as the failure message.

The vocabulary follows 9.26-1:

- An entry is one (surface, point, fixture). It is the unit being guarded: one test case and one file on disk.
- A reference is an entry's blessed content, stored on disk.
- Computed content is an entry's freshly produced content. It is `got` in comparisons, and the reference is `stored`.
- Content is the general word for either. Its type is `EntryContent`, a `dict[str, np.ndarray]`.

```

    registry.py      # Point, Surface, Registry, EntryId, Entry

    compute.py       # ComputedEntry, produce, compute_all

    run.py           # run_regen
    report.py        # render_regen_report
  registry.py        # the points, the fixtures, and REGISTRY
  fixtures.py        # FixtureRecord, FixtureData, load_fixture (replaces loaders.py)
  producers.py       # produce_obs, produce_supervision (replaces compute.py)
  paths.py
  regen.py           # the command line (replaces the regen/ sub-package)
```

The library modules will be flat inside `lib/`. The regen modules (compute, plan, apply, run, report) could form their own sub-package later, but at this size a second level of nesting would add little.

`lib/__init__.py` will define the library's public API. Project code, including the project's tests, will import from `training.goldens.lib`. The library's own modules and tests will import from specific modules. Since project code won't import from `lib.registry` directly, the library's `registry.py`, which defines the `Registry` type, and the project's `registry.py`, which builds the project's instance, can share a name.

`regen.py` will replace the `regen/` sub-package, since the command line is all that remains of it on the project side. The command will stay `uv run python -m training.goldens.regen [--dry-run]`.

A small structural test will check that every import in `lib/` is from the standard library, numpy, or `lib/` itself. While the library lives inside the project, a project import could otherwise be added to it without anyone noticing.

## The library

### Content

```python
type EntryContent = dict[str, np.ndarray]
```

`check_content(content)` will enforce 9.26-1's producer rules, along with rules that the store and the diff need:

- Names are non-empty strings with no `/`. Producers flatten any nesting, for example `policy.logits`.
- Names can't be `file` or `allow_pickle`. The store will pass the arrays to `np.savez` as keyword arguments, and those two names collide with its parameters. `file` raises an error, but an array named `allow_pickle` is silently left out of the file.
- No dtype holds Python objects (`dtype.hasobject`), since their stored bytes aren't a stable encoding of the content.
- Every array has at least one axis, since the diff locates changes along axis 0.

A failed check will be an assertion error. It means a producer is broken, so regen will stop there instead of recording it in the plan.

### Hashing

```python
def row_hashes(arr: np.ndarray, axis: int = 0) -> np.ndarray: ...   # uint64, one per index along `axis`

class StreamingRowHasher:
    def __init__(self, axes: tuple[int, ...]) -> None: ...
    def add(self, row: np.ndarray) -> None: ...   # the next slice along axis 0 of the raw array
    def hashes(self) -> tuple[np.ndarray, ...]: ...   # one uint64 array per entry of `axes`
```

`row_hashes` will hash each slice of an array along one axis. It will replace `hash_along_first_axis` and `stored_form`. `StreamingRowHasher` will compute the same hashes for a raw array that arrives one slice at a time and is never stacked in memory. It will replace `ObsHasher`, which is the case `axes=(0, 1)`.

The axes refer to the raw array. Axis 0 will be hashed once per added slice. For each other axis, the hasher will keep one incremental hash per index, updated with that index's part of each slice. The hash function stays the same: sha256 over the C-order bytes, truncated to 8 bytes and read as a little-endian uint64.

The streaming hasher will assert that every added slice has the same shape and dtype as the first, and that at least one slice was added before `hashes()` is called. Today only the channel count and the non-empty case are checked. Recording that layout for the report is part of `RowHashes` in pass 2.

In pass 1, hashed arrays will be stored as plain uint64 arrays, as they are today. 9.26-1 checked on a random tensor that `ObsHasher`'s output equals the batch row hashes along axes 0 and 1, and the review of this note repeated the check on fp16, fp32, and uint8 tensors. So the stored hash values won't change, and the mechanism golden's pinned values will stay valid through the switch.

### The content diff

```python
@dataclass(frozen=True)
class ArrayLayout:
    shape: tuple[int, ...]
    dtype: np.dtype

@dataclass(frozen=True)
class ArrayAdded:
    name: str
    got: ArrayLayout

@dataclass(frozen=True)
class ArrayRemoved:
    name: str
    stored: ArrayLayout

@dataclass(frozen=True)
class ArrayLayoutChanged:
    name: str
    stored: ArrayLayout
    got: ArrayLayout

@dataclass(frozen=True)
class ArrayRowsChanged:
    name: str
    layout: ArrayLayout       # the same on both sides
    rows: tuple[int, ...]     # indices along axis 0

type ArrayChange = ArrayAdded | ArrayRemoved | ArrayLayoutChanged | ArrayRowsChanged

@dataclass(frozen=True)
class ContentDiff:
    changes: tuple[ArrayChange, ...]   # ordered by array name

def diff_content(got: EntryContent, stored: EntryContent) -> ContentDiff | None: ...
```

`diff_content` will compare the two contents name by name. An array present on one side only is added or removed. An array present on both sides is compared by layout first, and if the layouts match, row by row along axis 0, by bytes. The byte comparison carries over from `diff_rows`: a NaN row equals itself, and `-0.0` differs from `0.0`.

One fix is needed: `diff_rows` reshapes each array to `(n_rows, -1)`, which raises an error for arrays with zero rows. The new diff will compute the row width explicitly, since an empty array is a normal case for a generic library (an event list with no events, for example).

Content will be equal exactly when `diff_content` returns `None`. This will be the one definition of equality, used by the golden test, by planning, and by move matching.

`ContentDiff` will wrap the tuple so that fields about the content as a whole can be added later, without changing the signature of every function that takes a diff. New kinds of array change, such as the ones row alignment and keyed matching would need (9.26-1 items 2 and 3), will be new members of the `ArrayChange` union.

**Tentative: hashable diffs.** Rows will be stored as a tuple of ints instead of an ndarray, which makes every diff record hashable and comparable. The report's grouping (see below) can then use a plain dict keyed by the change. The cost is memory when many rows change in a long array. At this project's sizes that is at most a few thousand ints per change. If it becomes a problem, rows could be stored as runs of consecutive indices, which stay hashable and are also the form the renderer prints. Lean: tuples for now.

`render.py` will hold the text form of a change, shared by the report and the test failure message:

- `render_rows(rows, n)` gives forms like `rows 12..15 of 138`, `row 40 of 183`, or `7 of 566 rows, from 500`.
- `render_change(change)` renders one array change on one line.
- `render_content_diff(diff)` renders the whole diff, one change per line, for a test failure.

The library gives no meaning to axis 0, so pass 1 will render indices as rows. Surface-specific labels (ticks for axis 0, channel names for obs) will come with the label hook in pass 2.

### Surfaces, points, fixtures, and the registry

```python
@dataclass(frozen=True)
class Point[CfgT]:
    name: str
    cfg: CfgT

@dataclass(frozen=True)
class Surface[CfgT, DataT]:
    name: str
    points: tuple[Point[CfgT], ...]
    produce: Callable[[CfgT, DataT], EntryContent]

class Fixture(Protocol):
    @property
    def id(self) -> str: ...

@dataclass(frozen=True)
class Registry[FixtureT: Fixture, DataT]:
    surfaces: tuple[Surface[Any, DataT], ...]
    fixtures: tuple[FixtureT, ...]
    load_fixture: Callable[[FixtureT], DataT]

    def __post_init__(self) -> None: ...   # unique, path-safe names

@dataclass(frozen=True)
class EntryId:
    surface: str
    point: str
    fixture: str

@dataclass(frozen=True)
class Entry[FixtureT: Fixture, DataT]:
    surface: Surface[Any, DataT]
    point: Point[Any]
    fixture: FixtureT

    @property
    def id(self) -> EntryId: ...

def entries[FixtureT: Fixture, DataT](registry: Registry[FixtureT, DataT]) -> list[Entry[FixtureT, DataT]]: ...
```

`Point` and `Surface` follow 9.26-1 item 6, with tuples in place of lists so that the frozen records are immutable all the way down. The app's fixture type only needs an `id`, and the app supplies the loader. The loaded fixture data (`DataT`) is whatever the producers need, and the library won't look inside it. Every surface will run on every fixture.

**Tentative: the registry record.** 9.26-1 left open whether surfaces, fixtures, and the loader are bundled into one record or passed separately. Every consumer needs all three together: compute, the golden test, and the command line. A bundle gives the project's `registry.py` one object to export, and gives the library one place to check names. The check will run in `__post_init__`, so any registry that exists is valid:

- Surface names are unique, point names are unique within a surface, and fixture ids are unique. The comparison uses `casefold()`, since the default macOS file system ignores case.
- Every name is non-empty, contains no `/`, and doesn't start with `.`, since all three become path components.

The registry won't hold the references root. The root will stay an explicit parameter of `plan` and of the store, so the same registry can be planned against a temporary tree in tests. The record will have no methods beyond the check. Lean: bundle them.

`EntryId` will be the identity of an entry, with plain string fields. It will replace `RefId`, which has an optional `key` and a `Surface` enum. The enum will go away, since surfaces will be defined by the registry. `Entry` will hold the objects for one entry. It will be used on the compute side and by the golden test, and it won't reach planning.

### Entry identity and the store

The store will be the only module that reads or writes the references tree, as 9.19-1 set out for the current store. Planning, apply, and the digest will all go through it. It will be a set of module functions that take the root as a parameter. The root won't have a default, since the library doesn't know the project's paths. The public API will export the store as a module, so callers will write `store.load(eid, root)` and the functions can keep short names.

```python
def rel_path(eid: EntryId) -> Path: ...                  # <surface>/<point>/<fixture>.npz
def parse_rel_path(rel: Path) -> EntryId | None: ...     # the exact inverse of rel_path

@dataclass(frozen=True)
class TreeScan:
    root: Path
    entry_ids: list[EntryId]
    unrecognized: list[Path]   # .npz files that don't parse or are under an unknown surface, relative to root
    ignored: list[Path]        # other files, relative to root

def scan(root: Path, surfaces: Collection[str]) -> TreeScan: ...
def load(eid: EntryId, root: Path) -> EntryContent | None: ...
def save(eid: EntryId, content: EntryContent, root: Path) -> None: ...
def remove(eid: EntryId, root: Path) -> None: ...
def serialize(content: EntryContent) -> bytes: ...
def set_digest(root: Path) -> str: ...
```

The layout will be `<surface>/<point>/<fixture>.npz` for every surface. The obs references are already at these paths. The supervision references will move from `supervision/<fixture>/<point>@<key>.npy` to `supervision/<point>/<fixture>.npz`, with one member per key.

Other details of the store:

- A reference file will be an `.npz` file. `.npy` won't be a reference suffix, so an old supervision file left in the tree would be listed as ignored.
- `parse_rel_path` will work on relative paths and reject empty parts, which resolves the `parse_rel_path` item in 9.24-2.
- `TreeScan` is today's `ReferenceSet`, renamed. Dotted files will stay out of it, as they do today.
- `set_digest` will still hash file bytes, and chunk 5 will decide whether it moves to content. It will use the same suffix rule as `scan`, so that the digest covers exactly the files the scan treats as references. Dropping `.npy` changes the value that `test_set_digest` pins, since its tree includes an `.npy` file. The re-pin is a mechanism change, done in the switchover while no revision exists.
- `load` will use `np.load` with `allow_pickle=False` and return the members as a dict.
- `save` will write the bytes from `serialize`.

**Tentative: files under an unknown surface.** Today `parse_ref_path` accepts only the `obs` and `supervision` directories, and a reference file anywhere else is reported and left in place. With surfaces as plain strings, any `<a>/<b>/<c>.npz` would parse, so a file under a mistyped directory, or under a surface dropped from the registry, would become an orphan and be removed. `scan` will therefore take the known surface names, and files under any other top-level directory will be listed as unrecognized. `plan` will pass the surfaces of its computed entries, which keeps its signature as `plan(computed, root)`. This keeps 9.19-1's rule that regen doesn't delete files it can't identify as its own. A dropped point's files will still be removed, as they are today. Removing a whole surface will be a manual cleanup, which fits how rarely it happens. Lean: yes.

**Tentative: serialization as a function of content.** `np.savez` output is deterministic for fixed inputs in one environment. 9.19-1 checked this, and it was checked again on numpy 2.4.4 for this note. But equal content can still serialize to different bytes in two ways:

- `np.savez` writes members in argument order. If a producer changed the order of its dict, the content would compare equal while the file bytes differed.
- `np.save` records Fortran order in its header, so a Fortran-ordered array serializes differently from a C-ordered array with the same values. This was checked on numpy 2.4.4.

`serialize` will sort the array names and convert each array to C order before calling `np.savez`, which removes both. Without this, a file whose content hasn't changed could still be rewritten with new bytes when an entry is saved, and show as modified in git.

Sorting doesn't make the bytes independent of the environment. The `.npy` header padding and the zip metadata written by Python's `zipfile` can differ across numpy versions, Python versions, and platforms. This matters for chunk 5. Unchanged entries aren't rewritten, so a planned digest computed by re-serializing their content could differ from the files on disk after a numpy upgrade, with no content change. Chunk 5 should use the bytes already on disk for unchanged entries (planning reads those files anyway), or compute the digest over content, for example through 9.26-1's manifest.

The consequence for the switchover: the existing obs files were written in `frame_hashes`, `channel_hashes` order, which isn't sorted. Planning would classify them as unchanged and leave them in their current bytes. So the switchover will re-bless from an empty tree, and every file will be written by `serialize`. Lean: yes.

### Compute

```python
@dataclass(frozen=True)
class ComputedEntry:
    id: EntryId
    content: EntryContent

def produce[DataT](entry: Entry[Any, DataT], data: DataT) -> EntryContent: ...

def compute_all[FixtureT: Fixture, DataT](
    registry: Registry[FixtureT, DataT],
    *,
    on_fixture: Callable[[FixtureT, DataT], None] | None = None,
) -> list[ComputedEntry]: ...
```

`produce` will run one entry's producer on loaded fixture data and check the result with `check_content`. `compute_all` will load each fixture once, call `produce` for every entry on that fixture, and call `on_fixture` after each fixture. The command line will use the callback to print the progress line, reading `T` and `end_t` from the project's fixture data. The golden test will call `produce` directly, so the test and regen will share the code that runs a producer.

Compute will have no checks of its own beyond `check_content`. The keyset check, `_check_agreement`, the identical-groups check, and `RegenAbort` will all go with the dependency table (9.26-1 item 1).

**Tentative: what a computed entry holds.** A computed entry will be only an identity and content. It won't carry the `Entry` or the point's config. This keeps planning and its data types independent of the registry, so planning tests can build computed entries from literals. The cost falls on pass 2. The label hook will need a point's config (for obs channel names), so the report will look it up through the registry by `EntryId`, which takes a few lines. Lean: identity and content only.

### Planning

```python
@dataclass(frozen=True)
class New: ...

@dataclass(frozen=True)
class Unchanged: ...

@dataclass(frozen=True)
class Changed:
    diff: ContentDiff
    stored: EntryContent  # for later compare hooks (9.26-1 item 3)

@dataclass(frozen=True)
class Moved:
    source: EntryId

type PlannedEntryStatus = New | Unchanged | Changed | Moved

@dataclass(frozen=True)
class PlannedEntry:
    id: EntryId
    content: EntryContent
    status: PlannedEntryStatus

@dataclass(frozen=True)
class RegenPlan:
    tree: TreeScan            # the scan before the run
    planned_entries: list[PlannedEntry]
    planned_removals: list[EntryId]

    def is_noop(self) -> bool: ...                # every status Unchanged, nothing removed
    def changed_surfaces(self) -> set[str]: ...   # surfaces with any Changed status

def count_statuses(planned_entries: Iterable[PlannedEntry]) -> Counter[type[PlannedEntryStatus]]: ...

def plan(computed: list[ComputedEntry], root: Path) -> RegenPlan: ...
```

`Changed` will carry the stored content, as 9.26-1 item 3 asks. Planning already loads it.

`plan` will be the only function in planning that touches the tree. It will:

1. Scan the tree, for the surfaces of the computed entries.
2. Find the orphans: scanned entries that no computed entry claims.
3. Load each computed entry's stored content and classify it with `classify`.
4. Load the orphans' content, and change the status of matching `New` entries to `Moved` with `match_moves`.
5. Collect the orphans that weren't used as a move source. These are the planned removals.

The helpers will be pure functions over data:

- `classify(got, stored)` returns `New` when nothing is stored, and otherwise `Unchanged` or `Changed` according to `diff_content`.
- `match_moves(planned_entries, orphans)` takes the planned entries and a mapping from each orphan to its content. A `New` entry becomes `Moved` when an orphan has the same surface and fixture, and equal content. Each orphan is used at most once, in scan order.

The move rule carries over from 9.24-1. With per-point storage, a file can only move when a point is renamed, and the rule will match whole contents instead of single arrays. The coincidence that 9.19-1 guarded against (the alive and present masks are identical on some fixtures) won't be able to pair the wrong files. A coincidence of whole contents is still possible. If one point is removed and a new point is added in the same run, and the two have identical content on some fixture, that fixture will read as a move. The files written will still be correct, and only the report's description will be off.

The byte-match notes will go away. Their main use was key renames, which will show up as added and removed arrays inside a file.

**Tentative: a flat plan.** 9.24-1 had a `SurfacePlan` per surface, holding that surface's entries, removals, and byte matches. With one diff type and no byte matches, a per-surface record would only hold a filtered list. The surface is already part of every `EntryId`, and the report groups by it. The move rule keeps moves within a surface. Lean: one flat list. If chunk 4 or 5 needs per-surface summaries, a method on `RegenPlan` can provide them.

The field name `RegenPlan.tree` is still provisional, as in 9.24-1.

### Apply and run

`apply(plan)` will save every planned entry whose status isn't `Unchanged`, carry out the planned removals, and remove the source of each move. It will match on the status, with no asserts.

```python
def run_regen[FixtureT: Fixture, DataT](
    registry: Registry[FixtureT, DataT],
    root: Path,
    *,
    write: bool,
    on_fixture: Callable[[FixtureT, DataT], None] | None = None,
) -> RegenPlan: ...
```

`run_regen` will compute, plan, and apply (unless `write` is false). It will be the home for the run's sequence, which chunk 5 will extend with the digest, the revision step, and the post-write check.

It will return the `RegenPlan` directly, one of the smaller tentative calls listed above. 9.24-1's `RegenResult` held the plan and the identical-groups warnings. The warnings will be gone, so until chunk 5 the result would only wrap the plan.

### The report

`render_regen_report(plan) -> str` will be a library function. In pass 1 it will have no per-surface hooks. It will have four parts:

1. A title line and a headline of counts (changed, new, moved, removed, unchanged), counted per entry.
2. For each surface, the entries that are new, moved, or removed, grouped by point, with their fixtures.
3. For each surface, the changed arrays, grouped as described below.
4. Stray files: unrecognized paths and ignored files, as today. The warnings section will go away.

**Tentative: the report layout.** Changes will be listed by array first, because that is where the repetition is. When the code behind an array that every point emits (such as `action_target`) changes, every point on a given fixture will usually show the same row change. Across fixtures the changes differ, since each fixture is a different game. So the grouping will merge points within a fixture, and each fixture will keep its own lines.

A point "has" an array on a fixture when the array is in that entry's computed content or its stored content, and the entry was compared (its status is `Changed` or `Unchanged`). Under each changed array:

- Each fixture where the array changed on some point gets one line per distinct change, listing the points that share it. When more than one point has the array and all of them share the change, the list reads `all N points`.
- When a change hit only some of the points that have the array, the others are named on an `unchanged` line under it. A change that hit only some points can't be hidden this way.
- The fixtures where no point's array changed are collapsed into one `unchanged on N fixtures` line.
- A fixture where no point has the array is left out of that array's lines. This covers a new fixture, whose entries are all new.

Entries that are new, moved, or removed have no diff, so they will appear only in the entry-level lines.

### Fixtures

`fixtures.py` will replace `loaders.py`. ### Producers

`producers.py` will replace `goldens/compute.py`, as 9.24-1 planned:

- `produce_obs(cfg, data)` will walk the fixture with a `StreamingRowHasher(axes=(0, 1))` and return `frame_hashes` and `channel_hashes`, the same arrays as today.
- `produce_supervision(cfg, data)` will build the emit spec from the config, stack each key over ticks, and replace `legality_mask` with its row hashes. Every other key will be stored in full, as today. The inert metrics config it needs will move here from the registry.

### The command line

`regen.py` will parse `--dry-run`, call `run_regen(REGISTRY, REFERENCES_DIR, write=not args.dry_run, on_fixture=...)`, print the progress lines and the report, and return 0. No abort path will remain, so there will be no failure exit code until chunk 5 adds one.

## Tests

In `tests/goldens_lib/`, all on synthetic input:

- `test_diff.py`, from `test_compare.py`: bytes versus values, layout changes, added and removed arrays, arrays with zero rows, and equal changes that compare and hash equal.
- `test_hashing.py`: the streaming hasher matches `row_hashes` along each requested axis on a random tensor, and a slice with a different layout is rejected.
- `test_store.py`: path round trips and off-scheme paths on synthetic ids, a save and load round trip, and serialization that doesn't depend on dict order or memory order.
- `test_plan.py`: `classify` and `match_moves` on literal inputs. A rename is a move, equal content on another fixture is not, and each orphan is used once.
- `test_regen.py`: a synthetic registry with toy fixtures and producers, regenerated into a temporary tree. The base tree must re-plan as a no-op. Then each case edits a copy of the tree or the registry, checks the plan, applies it, and checks that the tree re-plans as a no-op. The cases:
    - A deleted file reads as new.
    - A renamed point directory reads as moved.
    - Edited rows read as changed at those rows.
    - An extra or missing array in a stored file reads as removed or added.
    - A point dropped from the registry reads as removed.
    - Stray files read as unrecognized or ignored, including an `.npz` file under a directory that isn't one of the registry's surfaces.
- `test_lib_boundary.py`: the structural check on `lib/` imports.

In `tests/goldens/`, on the project's registry:

- `test_goldens.py` will replace the obs and supervision golden tests. It will be parametrized over `entries(REGISTRY)`, with ids like `supervision/core/ukRz7oSS8-s7`. A missing reference will fail with "unblessed, run regen", and a diff will fail with `render_content_diff`.
- `test_mechanism_golden.py` will move to `row_hashes` and `StreamingRowHasher`, with the same pinned hash values. `test_set_digest` will be re-pinned for the `.npz`-only suffix rule (see the store section above).
- `test_regen_smoke.py` will run `compute_all` on the real registry once, apply the plan to an empty temporary tree, re-plan the same computed entries against it, check that the plan is a no-op, and render the report. It covers the parts of the project's wiring that the golden test doesn't use: `compute_all`, the full pipeline, and the report on real content.

**Tentative: the regen integration test.** Today's `test_regen.py` runs the real producers, which take about 12 s of the 14 s goldens suite (per 9.24-1). A synthetic registry will exercise the same planning paths in well under a second, and its edge cases can be set up directly instead of through the real registry. The real producers stay covered by the golden test and the smoke test. The criterion 9.24-2 proposed for the two test directories (synthetic input goes in `goldens_lib`) then holds without exceptions. Lean: yes.

### Verifying the switchover

The verification has one precondition: on the commit before the switchover, the old golden tests pass and `regen --dry-run` reports no changes. Otherwise the comparison below would show differences that the switch didn't cause. Both held on 2026-09-26, when this note was reviewed.

9.24-1's check (the report output stays byte-identical) doesn't apply, since the report and the layout both change. Instead, a one-off script in `tmp/` will compare the re-blessed tree with the previous commit's references. It will read the old files with `git show`, so it won't modify anything. It will check:

- **Obs:** each new file's content equals the old file's, member by member. The bytes will differ, since the members will be sorted.
- **Supervision:** each point's new file has exactly the keys that the old registry declared in that point's `keys`. Each member equals the old `supervision/<fixture>/<rep>@<key>.npy`, where `rep` is the key group's representative. With the current configs every key has a single group, whose representative is the first point that emits the key.

This confirms that nothing guarded changed in the switch. It also checks the old keyset declarations one last time before they are deleted.

The report will be checked by reading it. A second script will copy the re-blessed tree into `tmp/`, and call `run_regen(..., copy_root, write=False)` for each case. Most cases edit the copy of the tree and use the real registry:

- a change shared by every point
- a change on only some points
- an added and a removed array
- a renamed point
- a deleted file
- obs channel edits

The rest run a modified registry (built with `dataclasses.replace`) against an unedited copy, since they come from registry changes:

- a fixture dropped from the registry
- a point dropped from the registry
- a fixture added to the registry, which checks that a fixture with no baseline stays out of the array sections. An existing replay with a different perspective slot can serve as the added fixture, so no new fixture file is needed.

The outputs will be saved next to the script for review at checkpoint B. Optionally, a small real code change (such as the tick-seam nudge from the 9.19-1 build) would give one report on real diffs.
