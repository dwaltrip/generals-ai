# Goldens regen: what the build settled

Date: 2026-09-19

**Daniel's level of review / sign-off for this note:** skimmed the drafting passes.

9.18-1 designed the second pass on regen before any code was written. This session planned the build as five chunks and completed the first three: the store layer (with the set digest and the mechanism golden), the plan-time refactor, and the report renderer. This note is a record of what those chunks settled, refined, or added. Part 1 covers the regen tool. Part 2 collects broader notes that the rest of the first-cut work needs to keep in mind.

9.18-1 stays the design record and its vocabulary is used here. Where this note differs from it, this note is current. The sections it revises are listed at the end.

## Part 1: the regen tool

### The store holds the tree layout

One module, `store.py`, holds everything about the layout of the references tree. It defines a reference's identity (surface, point, fixture, and key for supervision) and converts identity to path and path to identity, as inverses. It lists the tree, loads and saves each surface's file type, and computes the set digest. No other module builds or parses paths. Registry entries carry identities rather than paths, and the representative rule stays in the registry.

Every store function takes the tree's root as a parameter, with the committed tree as the default. This removes a module global, and that is what makes other consumers possible later: a test on a temporary tree, a tool that diffs two trees, or carrying a tree between checkouts in the two-boundary land recipe. A parameter was the smaller change to make now, and it puts fewer constraints on the calling code than a class holding the root would. If more state needs threading through the planner, the likely move is a small context parameter rather than a class.

One planning function, `plan_fixture`, still reads the registry directly. It plans the registry's entries for one fixture, and it needs real fixtures to do anything, so decoupling it from the registry would gain little. Everything after it works on plain data plus a root.

### One plan structure, three layers

Regen is a sub-package with three layers. Planning computes every reference, compares it with the file on disk, and records a status (new, unchanged, changed, or moved), along with the diff for changed files. A file on disk that no registry entry claims is an orphan, and orphans become removed files. The write step saves only what changed and removes only what the plan says. The report is rendered from the plan by pure functions. The command-line entry point sequences these steps and prints.

One structure, `Plan`, is both the plan (the content to write) and the extent (what changed). Everything downstream reads it and nothing else. Warnings are records rather than strings, so their wording belongs to the renderer. The `--dry-run` flag came out of this split at almost no cost. It plans and prints without writing, which made every check of the report non-destructive.

### Primitives, not judgment

Three decisions came up separately during the build and resolved the same way: regen does the simple thing and reports what it sees, and judgment stays with the developer.

- A pending skeleton is never replaced. Each run appends a new one, so repeated regen without filling the skeleton leaves one per run. The suite goes red on completeness only, since the newest digest still matches disk. To go green mid-branch, fill them, or delete all but the newest and renumber. The land recipe erases them anyway.
- A file that regen did not plan is never deleted.
- A move is never guessed from bytes alone.

In each case a smarter variant was considered. Each one required regen to read state it doesn't own: whether the previous record is complete, what a stray file is for, which of two identical orphans is the real predecessor. Each had a case where the guess is wrong and nothing flags it. The smarter variant also turns a small rule into a harder problem, with more edge cases and more places to be brittle. The plain rule reports only what it can verify, and it stays small. The move rule and the stray-file rule are worked out in the next two sections.

### What "moved" means

A move is a new file whose bytes match an orphan with the same fixture and the same key. Only the point may differ. This is the one move the design describes: the representative point for a key changed because points were reordered or one was removed.

Matching on bytes alone was rejected because two keys can legitimately hold identical arrays. The present mask and the alive mask are byte-identical on two of the three current fixtures, because they differ only when a player's death and removal fall on different ticks. Under a byte-only rule, a registry edit that removed one point and renamed another could pair the new alive mask with the old present mask on those fixtures and list the true predecessor as removed. The counts come out right and the pairing wrong, and the three fixtures disagree with each other. A tiered rule (key match first, bytes as a fallback) only moves the same failure to key renames.

The byte information is still valuable, so leftover coincidences between new files and orphans are reported as notes. A key rename reads as one new file, one removed file, and a note that their bytes match.

### Stray files and the digest's scope

A reference file is one with an `.npy` or `.npz` suffix. A reference file at a path that doesn't parse is reported and left in place: path-scheme changes are rare and cleaning up by hand is safer. Every other file is ignored by regen, with a one-line mention in the report, so a README can live in the tree.

The set digest covers reference files only. An unparseable reference file counts, so the blocking test fails until it is cleaned up. Non-reference files don't count. This narrows 9.18-1 section 10, which had the digest over every file under `references/`. The mechanism golden re-pinned once for this change, which is the purpose of that test.

### The post-run digest comes from the plan

This was decided this session and will be built with the digest-and-revision step. The plan holds every file's exact bytes, and npz and npy serialization is deterministic and identical in memory and on disk (checked on numpy 2.4). So the post-run digest can be computed before anything is written. The run order becomes: plan, digest, compare to the newest revision, write, verify that the tree's digest equals the planned one, print. This reorders 9.18-1 section 9.

What follows from computing it early:

- The report carries the revision outcome inline.
- `--dry-run` shows what the revision step would do.
- The post-write verify is a free consistency check between serialization and the store.
- When the post-run digest equals the newest revision's, every file reported as new this run was a restoration of something already blessed, and the final line says so. That is the whole of what the tool can say about a deleted reference, since per-file provenance can't be recovered from one hash. The better move for a hand-deleted reference is still to restore it from git.

### The report, after seeing real output

- The point-first obs pivot showed gating directly: a tick-seam nudge fired the fp16 point's status channels and left the fp32 point untouched.
- The supervision header lists unchanged points only when every block below it is a byte change, so it never sits above a new, moved, or removed row.
- Channel labels show the index beside the name. Part 2 explains why.
- A channel-count change renders as one count line per fixture, with no channel list.

## Part 2: broader notes

### Channel names are a hand-maintained mirror

Consumers read the obs layout from `ObsConfig.channel_names`. The base list it builds from lives in `constants.py` and mirrors the stacking order in `build_obs` by hand. Its own docstring calls it reference documentation. The only guard is the count assertion in `build_obs`, so a wrong order within the base block would pass silently. Gated groups are better off: their names and builders are keyed by the same group key.

Detection is unaffected, since the hashes are positional. Labels inherit the risk, in the regen report now and in the channel summary report later. That is why the report shows the index beside each name: the index is ground truth and the name is a hint.

The durable fix is for the channel builders to return names with their arrays, so the list derives from assembly and the mirror goes away. It touches the hot obs path, so it is its own pass, with the goldens as the byte-neutrality check. It is not scheduled. Revisit when building the channel summary report, which leans harder on names.

Two related questions are parked. A name-keyed diff on a channel-count change would need channel names to serve as stable identities across code versions.

- This would require checking the naming code for robustness first, as it wasn't designed explicitly to be used as a stable identifier for tooling like this. A few possible wrinkles: the dense-history names encode their lag, the per-opponent names are numbered by slot, and a rename would read as a removal plus an addition. The current code shape itself is probably not right for this task and would be some rethinking. That code (mainly `constants.py` ) is also rather old and less polished than most code from the past few months.
- Storing names in the obs npz should be cheap in git terms, since the names don't change between re-blesses, but it has no consumer until that question is settled.

### The channel summary report is built for tweaks to existing channels

Every use case in 7.22-2 section 6 is about values moving in channels that are present on both sides of a re-bless. Additions get a thinner treatment: a gated addition is a new point with no diff, an ungated one shows as added rows that the classification map must cover, and a reclassification moves rows between tables. That matches the gate-or-accept posture, and it is another reason not to build cross-version name identity now.
