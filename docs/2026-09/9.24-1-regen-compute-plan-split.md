# Regen refactor: the compute/plan split and the plan data model

Date: 2026-09-24

This note sketches a refactor of the regen sub-package, to be done before chunks 4 and 5 of the regen build (9.19-3). It came out of a review of the goldens package, which started from Daniel's notes in 9.23-1. It addresses items 1 through 5, 7, and 8 of those notes, and part of item 6.

The first two sections describe how regen works today and what the refactor is for. Then comes the design: the data model, the plan side, and the compute side with `run_regen`. None of the design is built yet. The last sections cover the module layout, tests, the build sequence, how chunk 5 fits, and what was left for later.

## Background: how regen works today

A regen run recomputes every golden reference, compares each one with the file on disk, and writes what changed. The code is organized as 9.19-1 describes. A planning step builds one structure, `RegenPlan`. A write step, `apply`, carries it out, and the report is rendered from it. `__main__` sequences the three.

Planning happens in two functions:

- `plan_fixture` handles one fixture. It loads the fixture, runs the producers, checks the registry's declarations against their output, and compares each result with the file on disk.
- `assemble` combines the fixtures. It runs the identical-groups check across fixtures, scans the references tree, finds orphans, and detects moves.

The registry builds the supervision key groups once, and they are then used by planning, the identical-groups check, and the report builder.

### What the refactor addresses

- Planning mixes producing content with reading the tree, and `_plan_supervision`, which does both, is hard to follow (9.23-1 item 1).
- The regen integration test can't re-plan without re-running the producers, so it takes about 12 s of the roughly 14 s goldens suite. Planning also can't be tested on synthetic input (item 4).
- `plan_fixture` and `assemble` each take the tree's root, with the committed tree as the default, so a caller can pass it to one and not the other.
- The run's sequence lives in `main` (item 5). Chunk 5 will add the digest, the revision step, and a post-write check to that sequence.
- Planned items are flat records: a `status`, plus `diff` and `moved_from` fields that are valid only for some statuses. The types don't encode that rule, so the report asserts `is not None` before each use.
- `_detect_moves` loads orphans from disk, runs parallel loops for the two surfaces, and returns a 4-tuple (items 2, 3, and 8).
- `RegenPlan` copies three fields from `ReferenceSet`, and it holds both surfaces' removed files and byte matches in flat lists that the report filters by surface (items 6 and 7).

## Three kinds of work

A regen run does three kinds of work, which are interleaved today:

1. **Producing content.** Each fixture is loaded and the producers are run. The result is the content every reference file should hold. This depends on the registry's data, the fixture format, and `training.bc`, and it takes almost all of the run time.
2. **Checking the registry's declarations.** The keyset check confirms that each point emits the keys it declares. `_check_agreement` confirms that the points in a key group emit identical bytes. The identical-groups check looks for two groups of one key that are identical on every fixture, which suggests an over-declared dep or a fixture coverage gap. These checks compare the registry with the producers' output and never read the tree. A failure in either of the first two aborts the run, and the third produces warnings.
3. **Reconciling with the tree.** For each reference, the old file is loaded and the reference is classified as new, unchanged, or changed. The tree is scanned for orphans and stray files, and moves are detected. This needs reference identities, content, and comparison functions, but no producers, fixtures, or registry data.

The refactor separates the first two kinds of work from the third. What passes between them is the content the tree should hold: one item per reference file, with enough metadata for the report.

The third kind of work follows a general pattern: compare a desired state with an actual one and classify the differences, as `git status` or `terraform plan` do. That makes it the part of regen that could most plausibly become generic later. The refactor doesn't attempt that, but it keeps this part separate from the rest.

## The data model

The central change is how a planned item is represented. Today a planned item is one flat record holding both the computed content and its classification against the tree. In the new model, a planned item is a computed item paired with an outcome.

```python
# regen/types.py

# --- Computed items: the content the tree should hold ---

@dataclass(frozen=True)
class ComputedObs:
    entry: ObsEntry
    digest: ObsDigest

    @property
    def ref(self) -> RefId: ...

@dataclass(frozen=True)
class ComputedSupervision:
    group: KeyGroup
    fixture: FixtureRecord
    array: np.ndarray             # stored form

    @property
    def ref(self) -> RefId: ...

@dataclass(frozen=True)
class ComputedFixture:
    fixture: FixtureRecord
    T: int                        # T and end_t are for the progress line
    end_t: int
    obs: list[ComputedObs]
    supervision: list[ComputedSupervision]

# --- Outcomes: one computed item compared with the tree ---

@dataclass(frozen=True)
class New: ...

@dataclass(frozen=True)
class Unchanged: ...

@dataclass(frozen=True)
class Changed[D]:
    diff: D                       # ObsMismatch or KeyDiff

@dataclass(frozen=True)
class Moved:
    source: RefId

type Outcome[D] = New | Unchanged | Changed[D] | Moved

def count_outcomes(items: Iterable[Planned]) -> Counter[type[Outcome]]: ...

# --- Plans ---

@dataclass(frozen=True)
class Planned[C, D]:
    computed: C
    outcome: Outcome[D]

type PlannedObs = Planned[ComputedObs, ObsMismatch]
type PlannedSupervision = Planned[ComputedSupervision, KeyDiff]

@dataclass(frozen=True)
class SurfacePlan[C, D]:
    items: list[Planned[C, D]]
    removed: list[RefId]
    byte_matches: list[tuple[RefId, RefId]]   # (new file, removed file)

    def is_noop(self) -> bool: ...        # every outcome Unchanged, nothing removed
    def has_changed(self) -> bool: ...    # any Changed
    def bytes_only(self) -> bool: ...     # only Changed or Unchanged, nothing removed

@dataclass(frozen=True)
class RegenPlan:
    tree: ReferenceSet                    # the tree scan, before the run
    obs: SurfacePlan[ComputedObs, ObsMismatch]
    supervision: SurfacePlan[ComputedSupervision, KeyDiff]

    def is_noop(self) -> bool: ...
    def changed_surfaces(self) -> set[Surface]: ...

# --- The run ---

@dataclass(frozen=True)
class IdenticalGroups:
    a: KeyGroup
    b: KeyGroup

@dataclass(frozen=True)
class RegenResult:
    plan: RegenPlan
    warnings: list[IdenticalGroups]
    # chunk 5 adds the planned digest and the revision outcome
```

### Computed items

`ComputedObs` and `ComputedSupervision` are what the compute side produces. Each carries the content for one reference file, plus the registry object it came from: the obs entry, or the key group and fixture. Each has a `ref` property giving its `RefId`. `ComputedFixture` groups them by fixture.

### Outcomes

An outcome is the result of comparing one computed item with the tree. `Changed` carries its diff and `Moved` carries its source, so each field exists exactly when it applies. The report and `apply` will `match` on the outcome, with no asserts.

The outcome classes also serve as the kinds of outcome. Code that counts outcomes, such as the report headline and the per-point obs summary, will use `count_outcomes`, which counts by class. The display labels ("new", "changed", and so on) will live in the report. `RefStatus` goes away.

Removed files are not an outcome. They have no computed item, so they stay a list of `RefId`s on each surface.

### Planned items and surface plans

`Planned[C, D]` pairs a computed item with its outcome. It is generic over the computed type and the diff type, and two aliases keep the familiar names `PlannedObs` and `PlannedSupervision`. The generics use the PEP 695 syntax, which the codebase already uses elsewhere.

`SurfacePlan` holds one surface's planned items, removed files, and byte matches. Moves and byte matches always stay within one surface: a move requires the same fixture and key, and a byte match compares content of the same type. So these lists belong on the surface.

The methods on `SurfacePlan` answer the questions asked of one surface: whether it is a no-op, whether any bytes changed, and whether the changes are byte changes only. The report's supervision header rule needs the last one. Today the report computes it itself.

`RegenPlan` holds the tree scan and the two surface plans. The scan replaces the three fields copied from `ReferenceSet`, and chunk 5 needs it as well (see "Fit with chunk 5" below).

### The run result

`RegenResult` holds the plan plus everything else the run found or decided. For now that is the identical-groups warnings. Chunk 5 will add the planned digest and the revision outcome.

| reader | reads |
|---|---|
| `apply` | `RegenPlan` |
| `render_extent` (chunk 5) | `RegenPlan` |
| the regen report | `RegenResult` |

9.19-1 set out a principle: one structure is both the plan and the extent, and everything downstream reads it. This design refines it. The plan stays the single description of the extent, and the result wraps it for the report. The report needs more than the plan: the warnings now, and after chunk 5 the revision outcome for its final line.

Every field of the result is decided before anything is written. In a normal run the result describes what was done, and in a dry run it describes what would have been done. A run that aborts raises `RegenAbort` and returns no result.

## The plan side

`plan(computed, root) -> RegenPlan` will be the entry point for planning. It is also where the tree's root is explicitly passed in to the system. `plan` scans the tree, finds the orphans (reference files on disk with no matching computed item), and plans each surface.

Each surface gets its own planning function, and the two share a set of pure helpers:

- `_outcome` classifies one item against its old value, or against the absence of one.
- `_same_slot` is the move rule's slot test: the same fixture and the same key. Obs refs have no key, so one test serves both surfaces.
- `_match_moves` turns a `New` item into a `Moved` one when an orphan in the same slot has the same content. Each orphan is used at most once.
- `_byte_matches` pairs the remaining `New` items with remaining orphans of the same content, in any slot.

Apart from the tree scan in `plan`, the per-surface functions do all of the tree reads. Each one loads the old values of its items and of its orphans, then calls the helpers. Since the helpers don't read the tree, they can be tested on synthetic input. The move rule and the byte-match notes are unchanged from 9.19-1.

### Equality

Each surface will have a single definition of equal content. Its planning function defines "same content" as "the surface's diff function returns no diff" (`compare_obs` for obs, `diff_rows` for supervision) and passes that test to the helpers. Classification and move matching then agree by construction, and `_same_digest` goes away.

The compute side keeps using `same_bytes` in `_check_agreement` and the identical-groups check. Those compare points with each other, not with the tree, so a second equality function there doesn't create an inconsistency.

### One function for both surfaces (deferred)

A single generic `_plan_surface`, taking the load and diff functions as parameters, would remove the remaining duplication between the two per-surface functions. It is parked / deferred for now (see below). The two surfaces we are guarding (as well as future additional surfaces we may guard) have enough differences to make this something that should be considered with great care, at a later point. We don't want to build a leaky abstraction.

## The compute side and the run

`regen/compute.py` will hold the first two kinds of work:

- `compute_fixture(fx) -> ComputedFixture` loads one fixture and runs the producers for every obs entry and supervision point. It runs the keyset check and `_check_agreement`, and converts each key group's array to its stored form.
- `check_identical_groups(computed)` runs across all fixtures and returns the warnings.
- `RegenAbort` moves here, since every abort is raised here.

This will be the one regen module that runs producers or checks the registry's declarations.

`regen/run.py` will hold `run_regen(root, *, write, on_fixture) -> RegenResult`, which sequences a run:

1. Compute each fixture, calling `on_fixture` after each one. `main` uses it to print the progress line.
2. Check for identical groups.
3. Plan against the tree.
4. Apply the plan, unless it is a dry run.
5. Return the result.

Every fixture is computed and checked before planning starts, so, as today, an abort leaves the tree untouched. Chunk 5 will add the digest and the revision decision between steps 3 and 4, and the post-write check after step 4.

`__main__` will keep only argument parsing, printing, and the exit code.

The golden tests won't use `compute_fixture`. They compute and compare per registry entry, since pytest parametrizes by entry, and they don't need key groups. They share the producer wrappers and the compare functions with regen.

## Module layout

```
regen/
  types.py      # the data types above, and count_outcomes
  compute.py    # compute_fixture, the declaration checks, RegenAbort
  plan.py       # plan, the per-surface functions, the pure helpers
  apply.py
  report.py
  run.py        # run_regen
  __main__.py
```

`goldens/compute.py` holds the producer wrappers (`compute_obs`, `compute_supervision`). It will be renamed to `goldens/producers.py`, so that the package doesn't have two modules named `compute`.

The separation has one limit. The plan side will import registry types (`ObsEntry`, `KeyGroup`, `FixtureRecord`), and the registry imports configs from `training.bc`. So the plan side will be separate in what it does, but not in the import graph. Separating the registry's types from its data would fix that, and it belongs with any later work on making the machinery generic.

## Tests

- `test_regen.py` will compute every fixture once at module scope, then plan against each edited tree. A full plan takes about 1.2 s on the current fixtures, almost all of it compute, and the test currently plans about ten times.
- `test_plan.py` will test the pure helpers directly, on synthetic items with no tree.
- The report's smoke call in `test_regen.py` will take a `RegenResult`.

Broader synthetic tests of planning are left for later, when the split between `tests/goldens` and `tests/goldens_lib` is revisited.

## Build sequence

The refactor will be built in two commits:

1. **The data model.** Add `regen/types.py`, and rewrite planning, `apply`, the report, and the regen tests against it. Compute stays in `plan.py` for this commit, where it produces the `ComputedFixture` values that `plan` consumes.
2. **The split.** Move compute and the declaration checks into `regen/compute.py`, add `run_regen`, reduce `main`, and rename `goldens/compute.py`.

The first commit is large. Splitting it further would need temporary glue code between the intermediate states, which isn't worth it. A commit in the sequence doesn't need to pass on its own.

### Verification

The report output should stay byte-identical through both commits. The check that we used for the key group change will also work for this refactor: render reports for an edited copy of the references tree, both before and after the code changes, and verify that they are identical. The only thing this check doesn't cover is the contradiction abort, which should be manually checked. The scripts are in `tmp/keygroup-check/` (local, uncommitted).

## Fit with chunk 5

Chunk 5 (9.19-3) will compute the planned digest before anything is written. The digest covers every reference file that will be on disk after the run. In this model those are:

- every planned item, whatever its outcome, serialized from its computed content
- the unrecognized reference files, which stay in place, read from disk using the tree scan

Removed files and move sources are left out, since they will be deleted. Ignored files are outside the digest. As far as we can see now, the model holds everything the digest needs. The serialization helpers in `store` are part of chunk 5.

The rest of the handoff stands, with new names. `Plan.changed_surfaces` becomes `RegenPlan.changed_surfaces`, `render_report` becomes `render_regen_report`, and the run order described there becomes the body of `run_regen`.

## Deferred

- **A single `_plan_surface`.** Revisit if the two per-surface functions end up close enough that merging them reads well.
- **`compare_arrays` in place of `diff_rows`.** `diff_rows` takes a key only to label its result (`KeyDiff.key`). A `compare_arrays` returning an `ArrayMismatch` without the key would pair naturally with `compare_obs` and `ObsMismatch`. Nothing in this refactor needs it. It would help if the single `_plan_surface` is built.
- **Splitting `RefId` by surface.** `RefId.point` is the owning point for obs and the key group's representative for supervision. Separate `ObsRef` and `SupervisionRef` types would give each field one meaning, and remove the check that `key` is set exactly for supervision. To be discussed.
- **Content-addressed storage for supervision.** Each array would be stored once under its hash, with a text manifest mapping each (point, fixture, key) to a hash. This would remove the representative point and the append-only rule for the point list, and supervision re-blesses would show up in git as manifest line changes. The dependency table would stay, as a check that grouped points share a hash. It is a large redesign. Revisit if reviewing supervision re-blesses becomes a real problem.
