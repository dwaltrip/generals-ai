# Supervision References

Date: 2026-09-13

This doc describes some design options we've considered for the layout and structure of the golden references. A key question of the design: which reference values are shared between config points, and how is this sharing specified and managed?

Note: We went with the dependency table. It was the strongest option after our latest analysis and design discussion.

**Refresher:**

- For the supervision goldens tests, we are guarding the values in `FrameSupervision`, which are produced by `emit_tail` (in `bc/datapipe`).
- We are guarding these under certain chosen sets of configs.

## Layout Design Ideas - Pros and Cons

### Dependency table

In the table, each key declares which config fields its emitted array depends on. If two config points have the same values for those specific fields, then, according to the table, they must produce the same data for that key. This means that we only need to store that data as a golden reference once and it can be shared by all of the aforementioned config points.

This forms the basis for how we de-duplicate golden reference data. For each key, we look at the dependency table and find its listed config fields. Config points are then grouped by the values for those fields. During regen, the guarded code path is run, producing the output data for that key. The data is then saved as the golden reference for that key and config point group.

Note, the above was implicitly imagining just a single fixture. The output data for each guarded key obviously varies with different game state inputs. So the grouping and de-duplication process occurs for each fixture.

The largest benefit of this layout is that it has the strongest coherence. The following now all match:

- The file structure and stored data layout for the golden references
- The registry entries and code which interface with that data. The key piece here is the dependency table.
- And most importantly, the actual structural relationships between training config values and the data emitted on the guarded code paths.

A more complete list of the pros and cons:

**Pros:**

1. The dependency structure is explicitly stated in code.
2. Storage layout matches the structural relationships. Nothing is stored twice unless the bytes differ.
3. A change to a shared key shows up once in a diff, and the diff can name the group's members.
4. Regen will compare the points within a group against each other. We expect this to catch a change that leaks into a key it was not meant to affect. In contrast, the per-point layout can only show such a change as one more changed file.
5. A new config value that splits a group creates a new file and leaves the existing files in place.

**Cons:**

1. The table describes the code, so it has to be kept accurate. An entry can be incorrect due to a missing config field or because a listed field isn't actually a dependency. However, in both cases, the risk is limited and the tooling can provide awareness when it happens (for most cases).
2. The comparison across points reaches only the config values that registered points cover, and only the behavior the fixtures exercise.
3. The registry needs more code: grouping, resolving a group's file, and per-key file lookup in the tests.

### Per-point layout

This is the layout from 8.25-1 §7.1. Each point stores its own copy of every key it emits, either as one npz per point and fixture or as one npy per point, fixture, and key.

In effect, every key is stored as if it depends on every config field.

**Pros:**

1. It is correct for any config field, current or future, because no sharing is assumed.
2. There are no declarations to maintain.
3. It is the simplest code. A test compares against one point's file or files.

**Cons:**

1. Identical arrays are stored once per emitting point. Today that is four copies of each core key and three of `alive_mask`.
2. A change to a shared key appears as several identical file changes in a diff.
3. There is no comparison across points. If two code paths diverge, the divergence shows up only as a change relative to the previous bless. That change looks the same as an intended one. If there is no previous bless, the divergence is not reported at all.
4. The sharing structure is not stated anywhere. A reader cannot tell from the layout which keys are meant to match across points.

A variant of this layout uses one npy per key and relies on git to store identical file contents once. That reduces the repository size cost of the duplicate copies and leaves the other limits in place. It also has two problems of its own. The size benefit depends on git's object store, so it applies only inside `.git`. A checkout or a tarball has every copy. The sharing structure is recoverable from storage but never stated, and a structure that has to be recovered from storage is worse than one stated in code.

### Union layout

*Fundamentally broken. It does not support the full range of training configs we need. Described here for completeness.*

This is the layout from 8.12-2 §6. Each key is stored once per fixture in a single npz file, and every point that emits the key shares that array. A keyset table records which keys each point guards.

In effect, every key is stored as if it doesn't depend on any config fields.

**Pros:**

1. It is the simplest storage. Every array is stored once, in one file per fixture.
2. There are no dependency declarations to maintain.
3. A change to a shared key shows up once in a diff.

**Cons:**

1. It is correct only while every key's bytes are identical across all the points that emit it. That happens to be true of the current keys.
2. It cannot represent two points emitting different bytes for the same key. A config field that changes an existing key's bytes has no place in the layout, so the layout would have to be replaced at the first such field rather than extended. The nearest example is a second `time_bin` edge set: two byte patterns for `elim_bin_target`, and only one stored array for both.
3. Nothing detects when the assumption stops holding. Regen would write one point's bytes into the shared slot, and which point's bytes are used is undefined.

### Group files: naming and paths

A group's file will be named after the first registered point that emits the key and matches the group's field values. The path will be `references/supervision/<fixture id>/<rep>@<key>.npy`.

For example, with the current code, each fixture directory will have the following files:

```
- core@legality_mask.npy
- core@action_target.npy
- core@is_pass.npy
- core@value_target.npy
- alive_only@alive_mask.npy
- time_bin@elim_bin_target.npy
- next_death@next_elim_target.npy
- next_death@next_elim_dt.npy
- next_death@next_elim_removal_dt.npy
- next_death@present_mask.npy
```

This naming scheme has one consequence worth noting. When a new config value causes a group to be split into two, the original group's representative point and file name are unchanged, and a new file is created only for the new group. Existing files are renamed only if their representative point is removed from the registry, or if the point list is reordered. To prevent both of these cases, we've decided that the point list should be append-only. We currently don't have any enforcement. It's merely documented as a convention in a code comment.

One clarification when looking at the directory: it looks like a per-point layout. Seeing `core@is_pass.npy` and no `time_bin@is_pass.npy` does not mean `time_bin` omits `is_pass`. It means `time_bin` shares the file named after `core`.

### Stale table - catching a missing field

Imagine that, in the main codebase, we update an emitted key to depend on a config field, without also updating the dependency table in the goldens registry. This is of course an issue.

Fortunately, in many cases, regen can check for this. Regen already has to run every point on every fixture to produce the references. Before updating any stored references, we will do an initial check. For all config points in a group, we take the new output data and verify they all match.

If there is a mismatch, then we've caught an issue. Regen will abort without updating any references, and alert us to the mismatch.

Limitations for this check:

1. At least one of the chosen fixtures would need to hit the code path in question. More specifically, we need a fixture that produces different data for the modified key under at least two different registered config points *that are currently in the same group*. If none does, we have a "fixture coverage gap".
2. It only works for cases where the existing config points in the registry would surface the mismatch. However, if they don't, this means we have an unguarded variant of the guarded code path. The fix is to add the missing config point, if it's a variant that we care about guarding. This is a broader concern, and isn't specific to the layout design.

The first one is the more significant one, in the context of this doc.

### Inaccurate table - an extra field (incorrectly listed as a dependency)

- An extra, inaccurate dependency (the entry lists a field the key's bytes do not depend on) splits a group that should be one.
- Regen should flag this as an error: two groups of a key are byte-identical across all fixtures.
- Until it is fixed, the arrays will be stored once per split group, and the points on either side of the split will not be compared against each other.

### Concrete examples: Two situations with the same regen report

#### Example 1: a stale table

This example is hypothetical, and the numbers in it are illustrative.

Suppose a config field is added that changes how `is_pass` is computed, but the table is not updated. Concretely: a field `use_pass_v2` is added to `TargetsConfig`, a new point `core_pass_v2` is registered with it set to True, and the four existing point dicts gain the field set to False, because the strict-keys check requires every stored dict to name every field. The entry for `is_pass` still declares no dependencies.

The tests show the four existing points passing and the new point failing as unblessed. Regen stops with something like:

```
contradiction on fixture rB3x9k2-s4: key 'is_pass' deps=()
  agree:  core, alive_only, time_bin, next_death
  differs: core_pass_v2 (212 of 940 frames, first t=17)
```

The fix is to add `use_pass_v2` to the deps for `is_pass` and run regen again. The four v1 points keep their shared array, the new point gets its own file, and nothing else changes.

#### Example 2: a real divergence

No config changes in this example. `precompute_for` builds the player-status table in one of two ways:

- when a variant is set, from the elim context, via `make_elim_ctx`
- when no variant is set, via `precompute_player_status`

Both ways are meant to produce the same table. `alive_mask` is built from whichever one the point's config selects.

Suppose someone changes the elim-context path, for example how a death tick is recorded, intending to change the elim targets. `alive_mask` under `time_bin` and `next_death` now differs from `alive_mask` under `alive_only`.

The tests show `alive_mask` failing for the two elim points, with `alive_only` passing. Regen stops with something like:

```
contradiction on fixture ukRz7oSS8-s7: key 'alive_mask' deps=()
  agree:  alive_only
  differs: time_bin (1 of 138 frames, first t=82)
  differs: next_death (1 of 138 frames, first t=82)
```

Here the table is correct and the code is wrong. This report is verbatim from the spike, where the change was a one-tick shift of `death_by_slot` in the elim branch.

#### Manual assessment required

In both scenarios, the reports have the same shape and there isn't any programmatic way of determining the cause. The developer needs to assess what changed in order to make the determination.

If the change added or altered a config field, it is example 1. If the change only touched code, with no config change, it is example 2.

### Identical groups check: across all fixtures, not per fixture

For a given key, two groups can produce the same data on a particular fixture. This is expected and normal. For example, imagine we have two `time_bin` points with different edge sets. The two edge sets only produce different bins when a death occurs in the tick range where the edges differ. If a fixture has no deaths in that range, the output for `elim_bin_target` will be identical under both points.

So the check needs to look at all fixtures together. If two groups produce the same data on every fixture, then something is off. Either the table lists a field that the key doesn't depend on, or none of the fixtures reach the situation where the field matters. In the first case the fix is in the registry. In the second case we have a fixture coverage gap, and the fix is a new fixture.

The check should be reported once per key, after all fixtures have been processed.

Note: the current prototype does this check per fixture. It needs to be updated to the version described here. This is also required before the check can be upgraded from a warning to an error, as a per-fixture error would block regen on ordinary fixtures.

### Why each config point lists its keys

Each `SupervisionPoint` in `SUPERVISION_POINTS` has a `keys` tuple. This is the explicit list of keys that the point emits.

The list is needed because of how group files are named. A group's file is named after the first registered point that emits the key and has the group's field values. To find that point, the registry has to know which points emit which keys.

One option would be to run the guarded code for each point and look at the output. This doesn't work here, as the tests need the file paths at collection time, before anything is run. The registry is also intended to be plain data that expands without running any code. So the keyset is stored as data on each point, and the representative point is computed from that.

The keyset is a claim about the code, in the same way that the dependency table is. Regen verifies it. When regen runs each point, it compares the emitted keys to the declared keys, and stops on any mismatch.

### Implementation spike results (so far)

This session, we built a first pass of this layout design. We populated the registry with the specific config points described in previous first-cut design sketches. We also built a rough protoype of the regen tooling.

#### Initial results

We then used the new implementation with three temp, throwaway fixtures. Initial results:

- 18 registry entries (config point and fixture pairs) across the obs and supervision tests.
- Every entry failed as unblessed before regen and passed after.
- A second regen reported every file unchanged with no warnings. This is how we learned that the two `precompute_for` paths agree on these fixtures.

#### Hand checks

After that, we did three temp "hand-check" smoke tests to see if the system is performing well for a few initial basic use cases:

1. The code was modified with a one-tick shift in the elim branch of `precompute_for`. This is the same change described in example 2 above. The report shown in that section was actually produced during this hand-check run.
2. We added a fifth config point, `time_bin_alt`, with different values for `elim_bin_edges`. Regen produced one new file per fixture. No existing files were renamed (this would happen if their representative point changed). As a follow-up change, we removed `elim_bin_edges` from the deps for `elim_bin_target`. The new point then resolved to the `time_bin` file, its test failed on that key, and regen refused with a contradiction between the two points (`time_bin` and `time_bin_alt`). This is the closest the current configs can get to the scenario in Example 1 above (since there is no new field to add).
3. We modified `is_pass`, inverting its value in the output of `emit_tail`. Every supervision entry correctly failed on that key, and regen correctly reported one changed file per fixture, `core@is_pass.npy`.

### Grab bag: smaller misc notes

- In our first-cut implementation work so far, we placed `next_elim_dt` in the dependency table under the `next_death` group. It will leave the table if it is moved to a meta field, as 8.31-1 leans.
- If we added a new supervision key that depends on memory state (e.g. a new aux head target), it would also transitively depend on `ObsConfig` fields. The dependency table could be updated to express that, but supervision points would need to contain an obs config as well.

The current relationship that SupervisionPoint has with EmitSpec is awkward, as it is an intermediate type that is fully downstream of the actual training configs.
