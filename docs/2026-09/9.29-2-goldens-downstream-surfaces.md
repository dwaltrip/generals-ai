# Goldens beyond the first cut: surfaces downstream of other surfaces

Date: 2026-09-29

**Daniel's level of review / sign-off for this note:** Daniel reviewed the notes this doc was drafted from. The problem was discussed in session. The ideas below are speculative and were not worked through.

This note records an open design question for goldens work beyond the first cut. It came up in the architecture review (9.29-1), which used two long-term goals: guarding all the main surfaces in this project (goal 1), and growing into a general-purpose library that other ML projects could use (goal 2). This question is the one potential hurdle the review found for goal 1. Nothing here is designed or decided.

## The problem

Some surfaces that the goldens may guard later consume the output of other guarded surfaces. The forward pass takes obs, and the loss and metrics take model outputs and targets. When upstream behavior changes, the downstream surfaces fire too.

If only upstream code changed, the commit's diff shows that, and the downstream fires are expected. The risk is masking. An intended upstream change can hide an accidental change to downstream behavior, for example through a shared helper. The downstream fire gets read as a consequence of the upstream change, and the accidental change is re-blessed without anyone noticing.

The first cut isn't affected. Obs and supervision are both produced directly from the sim data, with no guarded surface in between.

## Frozen full inputs

Storing a downstream surface's inputs in full, as frozen fixtures, seems the most robust approach and the truest to the goal of the goldens. A downstream fire would then mean the downstream code changed.

It isn't clear yet how this would be done. Disk size seems a substantial hurdle. For example, the forward pass's input is the obs tensor: at 110 channels of 32 × 32 in fp16, one frame is about 225 KB, so a 500-frame game comes to roughly 110 MB per fixture before compression, far more than the repo's size ceiling allows. There may be other hurdles too.

For goal 2, the downstream problem is significantly softened by one fact: a general-purpose library would likely need storage for large inputs anyway. Other ML projects are likely to have fixtures or input data too large to commit to git, such as image datasets or model weights. Solving the size hurdle here would then mostly mean building a capability the library needs regardless. 9.26-1 item 5 already leaves an opening for this: one advantage it listed for the tabled blob store was room for large data, since blobs could live outside git.

For goal 1, which matters more, the fact helps less. In this project, storage outside git would add its own work, and the frozen inputs would still need to be kept in sync with the current code.

Two speculative notes:

- Storing a subsample of frames might reduce the size. An idea to investigate.
- The frozen inputs might need regenerating whenever the upstream surface fires, to stay in sync with the current code and config points. Unclear.

## Other ideas

These are speculative and listed briefly.

- Recompute upstream on real fixtures. Always current, but not isolated from upstream changes.
- Synthetic inputs generated from hashes. Isolated, and no storage cost, but less realistic. 7.09-1's forward golden design uses this.
- Pair an isolated surface (frozen or synthetic inputs) with an integrated one. If only the integrated one fires, the change is upstream.
- Frozen, synthetic, and recomputed inputs appear to be different kinds of fixture, needing no change to the library's core. Not verified.
- When a chain of surfaces fires together, a revision's pre-filled impacts would list too many surfaces. The person completing the record would trim them.
