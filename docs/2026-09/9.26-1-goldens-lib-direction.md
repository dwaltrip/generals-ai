# Goldens: a better design, and working towards a reusable library

Date: 2026-09-26

Decisions and insights from a design discussion that started as a review of 9.24-1. Several of them replace large parts of 9.24-1's design. Merging the two docs into one plan is left for the next session.

In this doc, "the library" means the generic part of the goldens tooling, which we are starting to separate from the project-specific code. It has no dependence on this project's surfaces, configs, or fixture format. For now it is a boundary inside `training.goldens`, not a separate package.

## Item 1. Per-point storage layout for references

**Decision: We will remove the dedupe of supervision references across points and use a simplified per-point storage layout for references across the board (all surfaces). This also lets us drop the dependency table.**

There is one reference file per (surface, point, fixture). The dependency table is dropped, along with everything tied to it: `KeyGroup`, group ids, representative points, the append-only rule for the supervision point list, the contradiction abort, and the identical-groups warning. This revisits the layout chosen in 9.13-1.

The table did two jobs. It determined storage, since points that agree on a key's deps shared one file. It also declared which points should emit identical bytes, and regen checked that declaration.

Reasoning:

- The storage dedupe was a large source of complexity.
    - Entries and reference files were no longer one-to-one, which led to representative points, two meanings for `RefId.point`, moves caused by representative changes, the key-first report pivot, and separate planning code for each surface.
    - It also made it harder to see how the tool could become more generic, toward a possible library later.
- The space saved is small.
    - In a rough scenario (10 fixtures, 12 supervision points, 20 boundaries), the working tree is 2.3 MB with dedupe and 3.9 MB without. Git history grows by 1.4 MB with dedupe and at most 4.8 MB with one `.npz` per reference, after git's compression.
- The declaration check turned out to be quite low-value, upon further reflection.
    - Daniel realized that careful review of the regen report is already a required step, because the tooling can only detect a change. Whether a change was expected, and whether it makes sense, takes judgment and can't be automated. Reviewing the report key by key is part of that review, and a change that hit some points but not others is visible there, as long as the report presents it clearly. The check was designed naively, without thinking deeply about whether it was needed.
- Another benefit: the dependency table had to be kept in sync with the code by hand, and that work goes away with it.

Consequences:

- Obs and supervision have the same shape at the reference level: one file per (surface, point, fixture), holding named arrays. This is what makes a generic library possible, with one planning path, one diff type, and a `Surface` abstraction. 9.24-1's deferred single `_plan_surface` and its `Planned[C, D]` generics are no longer needed.
- An entry (point × fixture) and a reference file are the same unit on both surfaces.
- Regen's internals get simpler. Moves only happen when a point is renamed. Byte-match notes probably go away, since their main use was key renames, which become added and removed arrays inside a file. With the declaration checks gone, and the keyset check gone once `keys` is dropped (see the grab bag below), no compute-side abort remains, so `RegenAbort` may go as well.
- The report has to group repeated changes to a shared key, so a change to a core key (one emitted by every point, such as `action_target`) doesn't print once per point. The grouping must not hide a change that hit only some of the points.
- A change to a core key touches every point's files, which makes git noisier. This is minor.

## Item 2. Content model: named arrays with a primary axis

**Decision: A reference's content is a set of named arrays. Changes are located by row, along each array's primary axis (axis 0). Equality is byte-exact (see item 3).**

Proposed concrete type: `dict[str, np.ndarray]`.

Taking the diff for this content will be done name by name. The "types" of changes are: adding, removing, or modifying a specific named array. Modified arrays can have a layout change (shape or dtype) or have changed rows along the primary axis.

The primary axis has no fixed meaning in the library. It is the axis the diff reports locations on, and the surface supplies its meaning for display. In obs, axis 0 is the tick in `frame_hashes` and the channel in `channel_hashes`. A producer moves whichever axis it cares about to position 0. A surface that wants locations on more than one axis stores more than one array, as obs does.

Reasoning:

- The structure is flexible. Most ML outputs can be turned into named arrays with a small transform, so guarding a new surface mostly means writing a producer.
- It fits both current surfaces with no loss. Obs already stores two named arrays, and supervision's keys map directly to named arrays.
- In this project the tick is by far the most important axis, and it is axis 0 for nearly every array.

Rules for producers:

- Content is flat. Names are plain strings, and producers flatten any nesting in their outputs (for example `policy.logits`).
- No object dtypes. `np.save` writes object arrays with pickle, whose bytes are not a stable encoding of the content. Byte-exact equality and the set digest both depend on the stored bytes being stable.

Limits and future enhancements. A change is always detected. The limits are about how precisely it is located.

- Rows are compared by position. A shift, or an inserted or deleted row, reads as every row changed, and a length change gives no row indices. A diff that aligns rows as sequences, the way a text diff aligns lines, could report these precisely. The primary axis makes that easier to build, since the rows already form an ordered sequence. It would also handle channel insertions in obs.
- Some data has no single right axis: spatial data, axes whose order is arbitrary (such as opponent slots), and ragged data flattened with offsets. For ragged data, a surface's report hooks (item 6) may need the whole content of a reference, not one array at a time.

For now, the diff's result type should leave room to grow, and the per-surface report hooks should receive the whole content of a reference.

## Item 3. Comparison: byte-exact, with no custom diff types

**Decision: Equality stays byte-exact, and every surface uses the library's row diff. Custom diff types are not planned.**

The ML pipeline components we considered either fit the row diff directly, or fit it after a transform in the producer: padding variable-length data, putting unordered data in a canonical order, storing one hash per example, or storing extra arrays for other axes. The cases that still fit poorly fall into two groups. Each points to a generic diff strategy the library could add later, not to per-project diff types.

- Order-sensitive sequences, such as text, sample orders, and event lists. Row alignment (item 2) covers these. A text diff is essentially row alignment over lines.
- Keyed data, such as sparse coordinates or records with ids. A diff that matches rows by a key column, instead of by position, covers these.

Custom diff types would also be costly. Every consumer of a diff would need logic for each type: rendering in the regen report, the revision extent, and test failure messages, and the grouping of identical changes across points and fixtures, which needs diffs that can be compared. The type parameters that item 1 removes would also come back.

A lighter option, also not built yet: a surface could supply a compare function that receives the computed and stored content of a changed reference, and returns extra detail for the report. Its output would be supplementary and could not change outcomes. The only preparation needed now is for the `Changed` outcome to carry the stored content, which planning already loads.

## Item 4. Storage format: one `.npz` per reference

**Decision: Each reference is stored as one `.npz` file, with one member per named array. The alternative was a directory per reference, holding one `.npy` file per array.**

Reasoning:

- Simplicity is the biggest reason.
    - A reference is exactly one file, so the store, planning, moves, and removal all deal with one kind of thing.
    - The store in particular stays simpler. Saving and loading a reference is one `np.savez` or `np.load` call, with no loop writing one file per array and deleting files for arrays that are gone, and no reference that is only partly present.
- Fewer files. The directory layout has one file per array, which could grow into the hundreds over time.
- Another small benefit: the array names are mirrored in the file as member names without any code from us. With the directory layout, we would mirror the names in the file paths, but we would write that mapping ourselves.

What the directory layout would have given us:

- Smaller footprint: git stores identical arrays only once, across points.
- `git diff --stat` shows which arrays changed in a re-bless.
- Large arrays could move to Git LFS one at a time.
- A keyset change shows up as files added or removed.

One more note: `np.savez` writes an uncompressed zip, which is how the obs files are written now. Whether to compress is open. It is linked to whether the set digest covers file bytes or content, since compressed bytes can vary with the zlib implementation.

## Item 5. Content-addressed storage: tabled

**Decision: Content-addressed storage is tabled. It splits into two parts that can be considered separately, a blob store and a manifest. Neither is needed for the first cut, but the manifest leaves a useful opening for later.**

The blob store holds each array once, in a file named by its content hash.

- Pros:
    - Dedup at the array level, which the `.npz` layout gives up (item 4), without relying on internals of git.
    - Room for large data, since blobs could live outside git.
- Cons:
    - The original motivation is no longer present: 9.24-1 proposed it mainly to get rid of representatives and the append-only point rule, and item 1 already does that.
    - It's a specialized storage layer that would need to be implemented as another mini-lib inside of the goldens tooling.
        - Git already does most of this. A git tree maps paths to blob hashes, identical files are stored once, and Git LFS handles large files under any path layout.
        - E.g. blobs and manifests have to be kept consistent. Unreferenced blobs have to be collected, and planning happens at two levels.
    - Inspecting a reference by hand is harder.

The stronger idea turns out to actually be the manifest, by itself. This is an auto-generated piece of data that maps each (surface, point, fixture, array name) to the hash of that array's content.

It would be needed for content-addressed storage, which is how it came up. But thinking about it, we realized it has a few independent benefits:

- It would enable tooling that works with the revision history programmatically. Examples: finding the revisions where a given array changed, or checking whether anything guarded changed between two checkpoints' dates. Revision records are edited by hand, so it would be brittle to build such tooling on top of those instead.
- The set digest could be the hash of the manifest, which makes the digest independent of how files are encoded.
- Re-blesses show up in git as manifest lines changing hash.

## Item 6. The `Surface` abstraction, and fixtures

**Decision: `Surface` is the library's main container abstraction. A surface bundles a name, a list of guarded points (each a name plus a config), and a producer supplied by the app. The producer receives a point's config and the loaded fixture data, and returns the reference content. We will start building it in this refactor, kept minimal.**

```python
@dataclass(frozen=True)
class Point[CfgT]:
    name: str
    cfg: CfgT

@dataclass(frozen=True)
class Surface[CfgT, FixtureDataT]:
    name: str
    points: list[Point[CfgT]]
    produce: Callable[[CfgT, FixtureDataT], Content]
```

Reasoning:

- Both current surfaces reduce to this shape without being forced. With per-point storage and without `keys` (see the grab bag below), an obs point and a supervision point are both a name and a config. The supervision producer builds its emit spec from the config internally.
- It is the natural home for per-surface hooks, starting with obs channel labels in the report.
- It moves the code toward the library. We checked informally that the shape fits two likely future surfaces, the forward pass and the loss function.

Fixtures:

Users need to pass in the data that the configs run against, through each surface's guarded computation. So the library has a minimal fixture concept. The app's fixture type provides an `id: str`, and the app supplies `load(fixture) -> FixtureDataT`. The current `FixtureRecord` and `load_fixture` already fit. The library loads each fixture once and runs every point of every surface on it. For now, every surface runs on every fixture. Fixture data stays outside the references tree and outside the set digest.

Open:

- The shape of the label hook.
- Whether surfaces, fixtures, and the loader are bundled into one record or passed as separate parameters.
- Where 7.20-2's impact labels live, possibly on `Surface`.

## Item 7. Row hashes as a library concept

**Decision: Row hashing is a library concept. A content entry is either a plain array, stored in full, or `RowHashes`: one hash per slice of a raw array along an axis, plus the raw array's shape and dtype. Each producer chooses the form of each array, using hashing tools the library provides.**

Row hashes keep detection and the location of changed rows, and give up the stored values in exchange for size (8 bytes per row).

The library provides `row_hashes(arr, axis)` for arrays that fit in memory, and a streaming hasher for arrays too large to materialize. The obs producer uses the streaming hasher inside its walk loop, as `compute_obs` uses `ObsHasher` today. The supervision producer calls `row_hashes` for the keys it hashes (`legality_mask` today). This replaces the existing `RefForm` and `stored_form`.

Obs fits exactly. `frame_hashes` and `channel_hashes` are the row hashes of the same raw `[T, C, H, W]` tensor along axes 0 and 1. We checked, on a random tensor, that `ObsHasher`'s output equals the batch row hashes along those axes. So one concept replaces both `ObsHasher` and `hash_along_first_axis`, existing hash values don't change, and the mechanism golden's pinned values stay valid.

The streaming hasher generalizes `ObsHasher`. It takes the axes to hash along. Axis 0 is hashed once per added slice, and each other axis keeps one incremental hasher per index. It gets the raw layout for free, and should assert that the whole slice layout stays constant (today only the channel count is checked). Recording the raw layout lets the diff report a dtype or trailing-shape change as a layout change, where it would otherwise read as every row changed.

Open:

- The default form for supervision keys. Full keeps the old values readable when reviewing a change. Hashed is safer for size, and a better default for the library.
- How `raw_layout` and `axis` are written into the `.npz`.

## Item 8. What carries over from 9.24-1

**Carries over as written** (see 9.24-1 for details):

- The compute/plan split, and the framing of planning as reconciling a desired state with the actual one (as `git status` or `terraform plan` do).
- The outcome union (`New` / `Unchanged` / `Changed` / `Moved`) and `count_outcomes`, pairing a computed item with its outcome.
- `plan(computed, root)` as the one place the root enters, and `RegenPlan` holding the tree scan in place of copied fields.
- `run_regen` sequencing the run, and `__main__` reduced to argument parsing, printing, and the exit code.
- The test strategy: compute every fixture once, then plan against many edited trees, with pure helpers tested on synthetic input.
- Renaming `goldens/compute.py` to `producers.py`.
- The fit with chunk 5: the planned digest is computed before anything is written.

**Changes:**

- Three kinds of work become two. Compute only produces content, since the declaration checks are gone (item 1).
- The data model is simpler: one computed-item type, one diff type, and no generics (item 1). `Changed` also carries the stored content (item 3).
- One planning function replaces the per-surface ones, and byte matches go (item 1).
- `check_identical_groups` is gone (item 1). `RegenResult` loses its warnings, so until chunk 5 it may only wrap the plan.
- The build sequence (the two commits) and the verification method need rethinking, since the report output changes. See the open items.

**9.24-1's deferred and small items:**

- Resolved:
  - The single `_plan_surface`: there's one planning function now.
  - `compare_arrays`: replaced by the content diff.
  - Splitting `RefId`: it has no `key` now.

## Item 9. The library's scope, and where its value is

**The library does change detection. It pins the behavior of guarded code paths and reports when that behavior changes. It does not test whether the code is correct.**

Where the value is:

- The integration layer. A clean API makes it easy to add a surface in a robust way: the surface concept, a list of config points, a small producer that takes a config and returns named arrays, and so on. The core underneath (named arrays, row diffs, byte-exact equality) is simple and not novel, but making it easy to apply in an ML project is valuable in itself.
- The layers around the core:
    - An explicit registry of points and fixtures.
    - Regen as a reconcile step, with a plan, outcomes, a dry run, and a report of where changes are across the whole suite.
    - The revision history, tied to the references by the set digest. It answers "did guarded behavior change between these two dates or checkpoints, and does that matter for this comparison?" That question matters in ML research, where silent changes to data or targets can invalidate comparisons over time, as the tick-seam bug did.

Prior art: array snapshot testing already exists in other tools, for example `ndarrays_regression` in pytest-regressions. We haven't compared them in detail.

Numerics: byte-exact equality fits deterministic code on the data side well, such as preprocessing, target construction, and simulators. Whether it holds for model numerics (forward passes, losses) is the biggest open question for a general-purpose library, and would set its main limitations. An earlier look in this project found it less of a problem than one might expect.

## Grab bag

- **Dropping `keys`.**
    - After per-point storage, the only job left for `SupervisionPoint.keys` was the keyset check. Representative naming and building paths at test collection time are both gone.
    - A keyset change still shows up in the content diff as arrays added or removed, relative to the previous bless.
    - Dropping `keys` keeps `Point` the same across surfaces: a name and a config.
    - The `SUPERVISION_KEYS` table goes entirely, since its deps go with the dependency table and its forms become the supervision producer's choice (item 7). This reinforces a requirement the report already has: it should show added and removed arrays clearly.
- **`got` / `stored` in the comparison code.**
    - `ref` currently means two things: a reference's identity (`RefId`, the `.ref` properties), and the stored side of a comparison (`compare_obs(got, ref)`, `ObsMismatch.ref`, `KeyDiff.ref`).
    - The comparison side is renamed to `got` / `stored`, which removes one of the two meanings. This is pulled into this refactor, and covers the parameter-naming item parked in 9.24-2.
- **Vocabulary.**
    - Entry: one (surface, point, fixture). The unit being guarded: one test case, and one file on disk.
    - Reference: an entry's blessed content, stored on disk. "The references" is the whole tree.
    - Computed content (`got` in comparisons): an entry's freshly produced content.
    - Content: the general word for either, a `dict[str, np.ndarray]`.
    - A comparison is an entry's computed content against its reference (`got` against `stored`).
    - `RefId` needs to be rethought. It identifies an entry, not a reference. To discuss next session.

## Open items

- The set digest: computed over content or over file bytes, and whether to compress the `.npz` files, which depends on it (items 4 and 5). A manifest is one way to compute it over content.
- Whether the store is the only code that knows about files, with planning, `apply`, and the digest going through a small interface (list, load, save, remove).
- What a computed item holds: just an identity and its content, with no registry objects attached, or more. Tied to the `RefId` question in the grab bag.
- The report:
    - Grouping repeated changes to a shared key without hiding a change that hit only some points (item 1).
    - The shape of the per-surface label hook (item 6).
    - Showing added and removed arrays clearly (grab bag).
- Whether surfaces, fixtures, and the loader are bundled into one record or passed as separate parameters (item 6).
- Where 7.20-2's impact labels live, possibly on `Surface` (item 6).
- The default stored form for supervision keys: full or hashed (item 7).
- How `raw_layout` and `axis` are written into the `.npz` (item 7).
- Whether to introduce `RegenResult` now, when it only wraps the plan, or with chunk 5 (item 8).
- Verification: 9.24-1's check that the report output stays byte-identical no longer works, since the report and the storage layout both change.
- The build sequence for the refactor, and how it fits before chunks 4 and 5.
