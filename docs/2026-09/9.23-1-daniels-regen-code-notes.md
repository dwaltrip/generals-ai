## High-level goal - extract / separate out generic concepts from project-specfic details

*About this goal: This is a complex, high-level goal that we will need to carefully work towards over time, as the goldens tooling becomes more mature inside this project. We can and shoud keep it in mind even today with this code review. However, in general, there is a large risk of creating the wrong abstractions if we try to make the core goldens machinery fully generic at this point in time. The goldens tooling is tackling a very complex task and it will be hard to have a clean implementation even without thinking about some hypothetical generic version. That being said, I (Daniel) expect that there are low-risk steps we can take to move the code closer to this vision, now and in the neare future. We should keep a sharp eye out and sieze such opportunities when it isn't too burdensome.*

Last session, we added `training/tests/goldens_lib/` as a separate dir from `training/tests/goldens`. The goal was to start separating out the generic goldens machinery from the parts specific to my project. In the new dir, we put a simplistic, first pass integration test for the regen code (will need improving / re-write at some point). We also moved a few of the other test files into there (ones were closer to the lib / generic side of things).

The 2 golden tests themselves (that actually call the guarded code) are in tests/goldens/. Previous claude also left test_mechanism_golden.py alone as well (which I'm not 100% sure about).

The cut isn't deosn't feel exactly right, but I wanted to start working in that direction... And so we took a stab, in the spirit of learning by doing, knowing we will likely need to iterate on it further.

We can start also thinking about how to more cleanly separate out the generic pices in the actual implementation.

In reality, it will be non-trivial to try to make most of the implementation generic. The machinery is fairly intertwined with many specifics of
our Supervision data and the Obs data, for example.

There are some things we could definitely do... I have some ideas. But this could be a big, risky rabbit hole, if we aren't careful.

Mostly, we should keep this in mind, and look for opportunities to make things a bit more generic and less coupled, when isn't too hard to do so. It is more of a guiding thought to keep in mind.
