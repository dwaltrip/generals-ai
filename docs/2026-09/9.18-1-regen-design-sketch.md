Date: 2026-09-18

The design for the second pass on the goldens regen tool and the pieces around it. Worked out in discussion on 2026-09-17 and 2026-09-18, before any code.

## 1. What this doc covers

The second pass on regen and the pieces around it:

- the set digest and the mechanism golden

The other first-cut build items are unchanged by this doc: the channel summary report, the dataset migration onto the walk core, fixture selection, the environment record, the layer-1 goldens, the torch guards, and the workflow doc. Two questions that came up here are parked for later builds and listed in section 12.

Four examples run through the doc: the 2026-06-18 tick-seam fix (a boundary, already the example in 7.20-2), the 9.15 switch of the reference hash to sha256 (a mechanism change), the 9.15 removal of the `alive_only` point (a coverage change), and two branches that both fire the goldens (the case the numbering check exists for).

## 2. The mental model

The goldens pin the bytes of two guarded surfaces, obs and supervision, over a small fixture set and a registry of stored configs. When guarded code changes behavior, the tests fire.

Regen re-blesses. One run recomputes every reference, diffs each one against the file on disk, writes the references, and removes orphaned files. It then computes the set digest and compares it to the digest recorded in the newest revision. If they differ, it appends a skeleton revision. Finally it prints the regen report, which describes the extent of the run: which references changed, which are new, moved, or removed, and for the changed ones, which channels, keys, frames, and rows.

You complete the skeleton: set the kind, write the description and the comparisons invalidated, fill in the impacts, and rename the file.

The blocking test ties the references to the revisions. It requires that the newest revision's digest matches the references on disk, and that every revision is complete. You can skip the suite while iterating. Run it before moving on, and it will not pass without a filled record.

The revisions directory is the history of the reference set. One revision is one increment. Most revisions are boundaries. The rest are coverage, mechanism, or environment changes, and they carry the `NB` marker in the filename so that a directory listing separates them.

A boundary matters because of the confounds framework. Months later, someone comparing two checkpoints or two eval numbers looks at the boundaries between the two dates, reads the recorded impacts, and can tell whether the comparison is valid. The revision is the only permanent prose in the goldens system. Everything else is bytes, ephemeral output, or committed text whose meaning is in its git diff.

The tool does not distinguish temporary from permanent. It diffs against disk, appends, and never edits. This is the posture of git and of database migrations: you squash or rewrite history when that is appropriate, and the tool cannot know when that is.

Two things regen never decides, because both are judgment: what the baseline is, and what kind of change happened. The next two sections take them in turn.

## 3. Baseline and increments

Regen always diffs against the references on disk as they were before the run. There is no baseline flag. The baseline is a judgment: which commit does this branch's work start from, and does the branch hold one boundary or two? Tooling can't make that call. You make it, by deciding what is on disk before running regen.

Two consequences:

- A revision's extent is an increment relative to the previous revision. The revisions are ordered, and the net extent of a branch is the sum of its revisions. The tool never computes a net extent.
- The same printed extent means different things at different moments. Mid-branch, it is the increment since the last regen. At land, after restoring the references to the pre-branch state, it is the net extent of the whole branch.

The land recipe, for the usual case of one boundary per branch:

1. Decide the branch is done and how many boundaries it holds.
2. Restore the references directory from main, and delete the branch's mid-branch revisions. The newest revision is now main's, and its digest matches the restored references.
3. Run regen. The extent is the branch's net change. Fill in the skeleton properly.

When two branches both fire the goldens, the second one to land carries a revision whose increment is relative to the old main. After the rebase, the merged reference set matches neither branch's recorded digest, so the blocking test fails. The fix is the land recipe, run after the rebase. This is the migration-conflict analogy in practice: two such branches can't land independently, and the second one repeats its regen. If the two changes were independent, regen reports the same channels as before.

Details:

- Two boundaries on one branch: run steps 2 and 3 at the commit that finished the first boundary, then again at the tip. Carry the first run's references and revision to the second checkout, on a scratch branch or by copying the two directories.
- In the two-branch case, git may also report conflicts on reference files both branches changed. Those files are binary, so the resolution is to regenerate rather than merge.
- A hand-deleted or hand-edited reference is not a change. Regen restores it byte-identical, the post-run digest matches the newest revision, and no skeleton is appended. The report shows "new" or "changed" for that file, which is true relative to disk, and its last line says the set matches the newest revision. The better move is to restore the file from git.

## 4. The four kinds of revision

A revision's kind names the cause of the change to the reference set:

1. `boundary`. Guarded code changed behavior. The symptom is changed bytes. This is the only kind that carries confounds impacts.
2. `coverage-change`. The registry was edited: points or fixtures were added, removed, or reordered, or keys or deps were edited. The symptoms are new, removed, or moved files, and the bytes of every surviving file are unchanged. Example: removing the `alive_only` point removed its files and moved `alive_mask` from `alive_only@alive_mask.npy` to `time_bin@alive_mask.npy`, because the representative point for that key changed. Fixture selection at the end of the build will be one large coverage change.
3. `mechanism-change`. The goldens machinery itself changed: the hash function, a key's `RefForm`, the path scheme, the npz layout. The symptom is changed bytes or moved files with no behavior change. Example: the sha256 switch changed every obs npz and every legality-mask file, which looks like a total fire.
4. `environment-change`. A dependency or platform change legitimately moved the emitted bytes, such as fp16 rounding in a numpy release. The action is to update the environment record and re-bless. Rare.

The kinds are defined by cause, and regen only observes symptoms. Its file classification (new, unchanged, changed, moved, removed) does not identify the cause on its own: a total fire can be a boundary or a mechanism change, and moved files can be a coverage change or a mechanism change. So you set the kind, with three checks to help:

- The mechanism golden (section 11) separates a boundary from a mechanism change.
- The environment test, a future item, separates a boundary from an environment change.
- A run with only new, moved, or removed files is a coverage change.

## 5. The revisions directory

The revisions live at `packages/training/tests/goldens/revisions/`, beside `fixtures/` and `references/`. One file per revision:

- Boundary: `NNNN-<slug>.md`, for example `0012-tick-seam-fix.md`.
- Non-boundary: `NNNN-NB-<slug>.md`, for example `0013-NB-sha256-hash-switch.md`.
- Skeleton, as regen writes it: `NNNN.md`.

`NNNN` is four digits, zero-padded, starting at 0001 and shared across all kinds. The sequence is the timeline, and the newest revision is the highest number. Regen can't write the kind or the slug, since both are judgment. So completing a revision includes renaming the file from `NNNN.md` to its full name.

Numbering under the workflow: mid-branch revisions take the next numbers in sequence. At land they are deleted, and the real revision takes the number after main's newest, so the sequence stays contiguous. When two branches both claim the same next number, the blocking test fails on the duplicate.

Revision 0001 is the bootstrap. On the first run of the new regen there is no revision, so there is no recorded digest for the post-run digest to match, and a skeleton `0001.md` is appended. It is filled in as a coverage change, "initial throwaway bless". There is no special case in the tool, and the same recipe serves any future reset.

Details:

- `NB` is uppercase, and slugs are lowercase words joined by hyphens, so the marker can't be mistaken for a slug word.
- You choose the slug, and a complete revision must have one, since a readable directory listing is the reason for it.
- If a hand deletion leaves a gap, regen numbers from the highest existing revision plus one and never fills gaps. The contiguity check then requires you to renumber.
- If two branches produce identical filenames for the same number, git reports an add/add conflict, and the problem surfaces before the test runs.
- Deleting the references directory before the bootstrap run is optional and cosmetic. It makes the extent read "new" for every file rather than "unchanged".
- A `README.md` in the directory carries the legend, adapted from 7.20-2.
- On the names: "ledger" was dropped because not every entry is a boundary, and "bless record" because it is awkward as a noun. "Golden records" works out of context.

## 6. Record format

One markdown file per revision, with YAML frontmatter for the machine-read fields and prose under fixed headings for the rest. The frontmatter is parsed with python-frontmatter, a new dependency that wraps PyYAML.

Frontmatter fields:

- `date`: the local day. Regen fills it.
- `digest`: the set digest after this bless. Regen fills it.
- `kind`: one of the four values in section 4. You fill it.
- `recipe_change`: true or false. You fill it. This is 7.20-2's field: did the change alter training-time code or config, so that runs launched after it produce different weights? It is not a boundary by itself.
- `impacts`: a mapping from surface label to a list of impact labels, or the string `none`. You fill it, starting from regen's pre-fill.

Body headings:

- Description. You write it. Required.
- Comparisons invalidated. You write it. Required, and "none" is a valid fill.
- Extent. Regen writes it. Nothing parses it.
- Notes. Optional.

Example record, the tick-seam fix, written as `0012-tick-seam-fix.md`. The numbering is hypothetical and the keys in the extent are illustrative.

```
---
date: 2026-06-18
digest: 3f9a1c0e7b2d4a66
kind: boundary
recipe_change: true
# surfaces: obs, live-path, model-forward, training-targets, loss-func, eval-protocol, model-shape, game-rules
# impacts:  contract-break, contract-repair, metrics-change, mechanics-change
# TODO: link the doc that owns these terms
impacts:
  training-targets: [metrics-change]
---

## Description

Alive/present tick seam fixed (death > t became death >= t). The elimination tick now counts as dead, matching the sim's removal semantics.

## Comparisons invalidated

Elim metrics and training curves across this date.

## Extent

    obs: none
    supervision
      alive_mask       time_bin
      present_mask     next_death
      next_elim_dt     next_death

## Notes

(optional)
```

The skeleton regen writes for this run, `0012.md`, is the same file with `date`, `digest`, and the extent filled in. `kind` and `recipe_change` are empty, with the allowed values in the comment. `impacts` is pre-filled as `training-targets: []`. The Description and Comparisons invalidated headings have nothing under them.

A revision is complete when:

- The frontmatter parses. `date` and `digest` are present. `kind` is one of the four values. `recipe_change` is a boolean.
- `impacts` is either a non-empty mapping in which every surface has at least one label, or the string `none`. An empty list counts as unfilled.
- The Description and Comparisons invalidated sections are non-empty.
- The filename matches the full pattern, so `NNNN.md` fails.
- `NB` is present in the filename exactly when the kind is not `boundary`.

Content is never judged.

Details:

- The required set is the same for all four kinds. A non-boundary fills `impacts: none`, "none" under comparisons invalidated, and `recipe_change: false`. Writing those out rather than omitting them keeps every record the same shape.
- The impacts pre-fill uses 7.20-2's surface labels: `obs` for the obs surface and `training-targets` for supervision. Regen writes the surfaces whose bytes changed, each with an empty list. The risk is anchoring: a change that also touched `model-shape` or `loss-func` needs those surfaces added by hand, and the pre-filled list can make the two visible surfaces look like the whole answer. Hence the comment above the field listing all eight surfaces and all four impact labels. That comment carries a TODO to link the workflow doc, or whichever doc ends up owning the vocabulary.
- `impacts` lives in the frontmatter rather than the body because it is the field a future "list the boundaries" utility would read.
- The extent in the record might read better as a markdown table than as an indented block. That is a renderer choice, and since nothing parses the extent it can change at any time without touching existing records.

## 7. Blocking test

A test file beside the goldens tests, name to be decided. It is a pure function of the working tree, with no git and no assumptions about branches. The checks, in priority order:

1. Revision numbers are unique and contiguous from 0001. This catches the two-branch case, where a rebase leaves two files numbered 0011.
2. Every file in `revisions/` other than `README.md` matches either the skeleton pattern or the full pattern.
3. The newest revision's digest equals the digest of `references/` on disk.
4. Every revision is complete, per section 6. A skeleton fails here by construction.
5. `NB` appears in the filename exactly when the kind is not `boundary`.

The posture is the one 8.12-1 set out: the goldens enforce when the suite runs. Skip it while iterating. Have it pass before moving on to the next thing.

Details:

- The order matters for which message you see first, not for correctness.
- The record parser (frontmatter plus headings) is one module, shared with regen.

## 8. Regen report

The reader is the developer, right after running regen, at one of two moments. Mid-branch, the question is whether the change moved what you expected and nothing else. At land, the question is what the net extent is, so the record can be written from it.

A complete example first. The scenario: the player-status channels changed (all frames, fp16 point only), the tick seam was fixed (one tick on each eliminated fixture), and a new obs point was registered and blessed for the first time. The survivor fixture's length of 412 is made up.

```
regen: compared against the references on disk before this run

changed 9   new 3   moved 0   removed 0   unchanged 27

warnings: none

obs
  fp16_player_status_on   changed on 3 of 3 fixtures
    channels
      opp_1_is_alive     3 fixtures
      opp_2_is_alive     3 fixtures
      opp_3_is_alive     1 fixture   (ukRz7oSS8-s7)
    frames
      ukRz7oSS8-s7   all 138
      xdZsRyX0O-s2   all 183
      NAT6qThbE-s2   all 412
  fp32_pre_player_status   unchanged
  fp16_dense10   new, no baseline   (3 fixtures)

supervision   changed on: time_bin, next_death   unchanged: core
  alive_mask       time_bin
    ukRz7oSS8-s7   t=138
    xdZsRyX0O-s2   t=183
    NAT6qThbE-s2   unchanged
  present_mask     next_death
    ukRz7oSS8-s7   t=138
    xdZsRyX0O-s2   t=183
    NAT6qThbE-s2   unchanged
  next_elim_dt     next_death
    ukRz7oSS8-s7   t=138
    xdZsRyX0O-s2   t=183
    NAT6qThbE-s2   unchanged

revisions: appended skeleton 0012.md, complete it before running the suite
```

The layout follows the reader's questions, in the order they come up:

1. Did anything change at all? If not, one line, and no skeleton.
2. What kind of change? Changed bytes are a fire. New, moved, or removed files are a coverage change. Everything changed at once suggests a mechanism change. The headline counts answer this without the tool judging.
3. Where? For obs: by point, then which channels, then per-fixture frames. Pivoting by point first makes gating visible: if only `fp16_player_status_on` moved, the change was inside the gated channels. For supervision: by key, then the points it changed on, then per-fixture rows.
4. Does the shape of the change match my mental model? All frames or a range, all channels or a few, all fixtures or some. A tick-seam fix shows as one row per eliminated fixture at the elimination tick. A new channel shows as every frame on every fixture.
5. Anything suspicious? The identical-groups warnings, printed near the top so they are not missed.
6. What was this compared against? The first line says: the references on disk before this run.

Two facts about the data determine the layout.

The first is about obs. An obs reference has two independent hash lists: one hash per frame over all channels, and one hash per channel over all frames. So for a cell we know which frames changed and which channels changed, but not which frames changed for which channel. Channels and frames are therefore two sub-blocks under a point, and they do not nest.

The second is about supervision, and it is why the supervision section pivots by key rather than by point. Supervision references are shared between points that agree on a key's deps, and the shared file is named after a representative point (`core@action_target.npy`). This is a storage detail for deduplication, and you should mostly not have to think about it. Pivoting the report by point would either repeat a shared key's block under every point that emits it, or favor the representative point. Pivoting by key, with each key tagged by the points it changed on, mentions points and never groups. Obs stays point-first because an obs point owns its reference files outright.

Which parts are firm and which are first picks:

- Firm: summary first, warnings near the top, the baseline line, unchanged entries kept quiet, per-file status lines dropped, and the data-then-presentation split of section 9.
- First picks, open to change after use: the key-first supervision pivot (tentative, per Daniel), the fixture-count tags on channels, the four-case per-fixture rendering, the `all` marker, and the exact spacing.

Details:

- Unchanged entries: the headline carries the count. Each unchanged obs point gets one line, because "did the other obs point move?" is a question the reader has. Unchanged supervision keys are omitted.
- A key shared by several points reads as `value_target     core, time_bin, next_death` with its per-fixture lines beneath, once.
- The per-fixture line has four renderings, chosen by the shape of the changed indices: `all 138` when every frame changed, `t=138` for a single tick, `t=93..137` for one contiguous run, and `45 of 138, from t=93` when the changes are scattered.
- New, moved, and removed entries appear inside the surface sections, one line each. The headline already separates the kinds, and keeping them in place keeps the point list complete.
- Key groups come up in output only where the question is whether the dedup is declared correctly: the deps table in the registry, contradiction aborts, and identical-groups warnings.
- The regen report is not the channel summary report. It says which channels and keys changed and, for supervision, how many rows. How an obs channel's values moved is the channel summary's job.
- What regen prints beyond the report is operational: progress per fixture, abort messages (a keyset mismatch or a contradiction, with nothing written), and the identical-groups warnings. If the report ever needs to be written to a file, that is a small change.
- "Fire report" was dropped because it names the trigger rather than the output.

## 9. Extent structure and the plan-time refactor

Today `regen.py` decides each file's status (new, unchanged, changed) inside the write functions, after planning. The refactor moves the decision into planning. Every planned file carries a status (new, unchanged, changed, moved, removed) and, for a changed file, the diff: changed frame indices and changed channel names for obs, changed row indices for supervision. Then:

- The writers only save.
- The regen report and the skeleton's extent block are two renderers over the same typed structure, one full and one short.
- Regen knows before writing what the run will do.
- Move detection becomes a planning step for both surfaces.

The aggregations live in the renderers, not in the structure: fixture counts per channel, points per key, "changed on N of M fixtures", and the four-case per-fixture rendering. Changing a pivot is a renderer edit. The principle, in Daniel's words: data munging first, then a presentation layer, so that changing the output format is cheap.

The order of steps inside a run: plan (aborting on a contradiction or a keyset mismatch, with nothing written), write, remove orphans, compute the set digest, compare it to the newest revision's digest, append a skeleton if they differ, print the report and the final revisions line.

Details:

- Today each writer loads the old file, compares, saves, and prints its own line. The supervision writer returns its newly written arrays so the orphan sweep can label a file as moved. Obs has no move detection.
- For obs, move detection compares digest arrays.
- This is a reshuffle of roughly 240 lines with the same outputs. Verification: run regen and confirm the tree stays clean, which it does today.

## 10. Set digest

The set digest is sha256 over the sorted sequence of (relative path, file bytes) for every file under `references/`, with dotfiles skipped, truncated to 16 hex characters. It hashes files rather than arrays, so a moved file changes it.

It covers references only. Fixtures are inputs. A fixture edit that changes references shows up through the references, and one that doesn't is invisible to the goldens, as it should be.

Details:

- Reference bytes are deterministic (a no-op regen leaves the tree clean, checked 2026-09-17), so the digest is well-defined.
- If the digest function itself changes, every recorded digest goes stale, but only the newest revision's digest matters. It gets re-pinned by hand, which is an edit to a complete record with no reference change. The mechanism golden flags the change. This is rare and accepted.
- The alternative was a git diff of `references/` against main, requiring a record change whenever the references differ. It was dropped because it assumes main is the baseline, which section 3 rejects, and because it says nothing on main itself or in a checkout without main.

## 11. Mechanism golden

A small test that distinguishes a real fire from a change to the goldens' own machinery. It feeds a fixed synthetic input through that machinery and compares the output to literals pinned in the test. No fixture and no guarded code are involved.

It pins three things: `ObsHasher` (the per-frame and per-channel hashing), `stored_form` for each `RefForm` (full arrays and frame hashes), and the set digest function.

In use: if the goldens fire and the mechanism golden also fails, the change is a mechanism change. Re-pin the literals in the same commit and record the revision as `mechanism-change`. If the goldens fire and the mechanism golden passes, the change is a boundary, or a coverage change if only new, moved, or removed files appear.

Details:

- It does not cover the producer wrappers in `compute.py`, which are thin calls into guarded code, or the path scheme, since a path change shows up as moved files.
- It is the same shape of test as the numerics canary from the torch guards item.

## 12. Deferred and parked

- Channel summary versioning. Daniel leans to keeping every past summary as its own file, for editor convenience. Size is not a concern: 8.12-1 estimated about 4.5 KB per cell, which comes to roughly 9 MB of working tree under its big-picture scenario. The alternative is overwriting in place plus a small helper that extracts a past version from git. Kept copies have three design consequences: filenames keyed on the revision number, a directory of their own outside the orphan sweep, and manual pruning alongside the revisions at land. Decide at the channel summary build.
- The supervision "how" gap. `.npy` files diff as binary in git, so the reviewable trace of a supervision re-bless is the record's extent plus a rerun. A small tool that diffs two reference trees is possible later, since the references are full arrays.
- The README legend for `revisions/`. Adapt 7.20-2: `channels` becomes the extent, `kind` is added, `recipe-change` is spelled `recipe_change`, and the surface and impact labels are unchanged.
- The TODO link in the impacts comment, once a doc owns the vocabulary.
- The workflow doc. It carries the land recipe, the two-boundary and two-branch flows, and the note that a hand-deleted reference should be restored from git rather than regenerated.
