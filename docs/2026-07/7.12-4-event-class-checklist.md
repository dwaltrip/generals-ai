# Event-class checklist — first pass

*Date: 2026-07-12. Pre-build item 2 of the [behavior-goldens first cut](7.12-1-behavior-goldens-first-cut-v2-overview.md), derived from the code and the mechanics record ([game mechanics](../generals-io-game-mechanics.md), [resolved-ambiguities appendix](../game-mechanics-appendix-resolved-ambiguities.md)). This is explicitly a first pass: §8 names what it is known to miss and the follow-up work that completes it.*

This checklist is the coverage spec for fixture selection. The initial set is about 5 real corpus games, so selection has to be deliberate: the guarded code paths are only executed at test time if the frozen fixtures contain the events that reach them. The same class definitions feed the frozen-frame pick rule (event-adjacent frames, event-labeled by construction) and the freeze-time tags asserted at fixture production (7.12-1 §4).

## 1. Method: two vantage points

The classes below come from two enumerations with different completeness procedures.

**Game-state changes** are frame-pair transitions in the raw game: enumerable from the mechanics docs (a finite rule set) cross-checked against the sim's event emission (`sim-core/src/state.rs`) and the pipelines' consumption of the npz arrays. That enumeration is this pass's basis, and it is close to complete on its own terms.

**Obs-state changes** are richer than frame pairs: the obs holds memory of previous states (monotonic masks, `last_seen_*`, rolling dense-history buffers) and computes derived values on it, so each stateful channel defines its own equivalence classes over histories. That enumeration can only come from the channel code, walked channel by channel, and it is deferred to the sweep in §8. Until the sweep runs, this checklist should be treated as close to complete on events and provisional on conditions.

## 2. Tag shape

Every class below is an asserted tag, checked at fixture production against the fixture npz (and re-checked at regen).

- **Event and action tags are per-fixture**: predicates over the stored arrays (`death_events`, `capture_events`, `neutralize_events`, `actions_*`, `ownership[0]`). A line or two each.
- **Condition tags are per-(fixture, perspective)**: claims about what a perspective sees. Visibility is not stored in the npz. It is recomputed with the existing `training.bc.visibility.compute_visibility` (a pure function of one ownership row and a perspective slot), then the condition is evaluated over (ownership, armies, vis) with plain array ops.

Reusing pipeline helpers like `compute_visibility` inside the asserts is legitimate: tags are selection checks, not golden references, so there is no independence requirement (a vis-rule bug is the parity test's and the goldens' own job to catch).

The per-perspective shape means a fixture's spec carries: source replay, registered perspectives, event tags, and per-perspective condition tags, in one place. Perspective selection is therefore a real authoring decision per fixture: `capture_role`'s captured-by-self variant needs the captor registered as a perspective, and `general_revealed` needs a perspective that actually finds one.

Coverage can be verified through two mechanisms: manually at selection time, or through these codified tags. Because fixtures are frozen, coverage cannot rot, so a one-time manual verification stays valid until a fixture is regenerated. What the codified tags add over manual checking is specific: honesty at authoring (the selection is checked, not just intended), in-code documentation of each fixture's purpose, and automatic re-verification at schema-migration regen, the one moment coverage can silently change because every fixture is rebuilt from source.

The posture here revises the soft commitment of 7.12-1 §4. The checklist's goal is comprehensive coverage, because the goldens are only as strong as what the fixtures execute (a behavior change in an unexercised path fires nothing, and a green run gets read as broader than it is). Confidence in that coverage is worth keeping in code rather than in a one-time manual check, so the tags are intended to ship with the build and stay. Trimming remains available if the mechanism fights the build, but as a fallback, not an equal-weight outcome.

One sizing note. This outgrows 7.10-2's "plain asserts, a few dozen lines" estimate, modestly (the vis ingredient is a few lines, but the predicate count is higher and the condition tags add a perspective loop).

## 3. Event tags (per fixture)

- **living_capture**: a CaptureEvent with a same-tick DeathEvent for the captured slot. Exercises the `opp_captured_by` flip in `step_memory` and its cat-9 encoding, the simultaneous alive and present flips, the inheritance halving visible at the next snapshot, and the general-to-city transition.
- **surrendered_capture**: a CaptureEvent with no same-tick DeathEvent (the victim was already death-marked). The slot's death tick and removal tick differ, and the surrender window closes by transfer rather than neutralization.
- **surrender**: a DeathEvent with no same-tick removal event. Opens the `present & ~alive` window: the is_present/is_alive divergence in the status channels, time_bin's alive domain, and next_death keeping the surrendered slot nameable as a victim.
- **neutralization**: a NeutralizeEvent. The removal path where tiles go neutral with retained armies and the general becomes a neutral city.
- **no_removal_tail**: some real slot has a DeathEvent but no removal event at all (the game ended first). The frames past the last real removal exercise next_death's `target = -1` (ignore_index) branch.
- **removal_tie**: two removal events on one tick. Exercises next_death's argmin first-min tie rule and the soft target's even mass split. Two mechanisms produce it: chained captures (A captures B while B captures C, appendix §6) and two independent same-tick captures. Prefer a chained instance if the corpus offers one, since it additionally exercises the obs reading where a channel says "captured by B" while B's own channel says "captured by A".
- **phantom_slots**: fewer than 8 real slots in `ownership[0]`. Exercises the `is_real` masking that sits in every mask and target. 7.3% of parsed corpus games start with fewer than 8 players ([6.13-6](../2026-06/6.13-6-elim-head-stage0-corpus-measurements.md) §2). Training drops these games at split-manifest build time (`filters.is_eligible`, player count vs `ELIGIBLE_PLAYER_COUNT`), but the intermediate dir keeps them, so the fixture is directly available. Covering the path now means one less thing to remember if that filter constant ever changes.
- **multi_opponent**: 3 or more real players. Multi-opponent channel content, third-party captures observable from a bystander perspective, and real next_death competition.
- **spans_land_tick**: `T >= 51`. Covers all production-subtraction branches in `_encode_army_delta`. Note the case enumeration: odd t (no production), even t (city/general production), and `t % 50 == 0` (both). A "land tick only" case is impossible, since 50 is even and a land tick always coincides with the per-2-step tick.

## 4. Action tag (per fixture)

- **is50_move**: some `actions_is50` entry is set. Exercises `actions.encode`'s split-move branch in `policy_pass_target`. Pass and normal moves are ubiquitous in any real game and get no tags.

## 5. Condition tags (per fixture, perspective)

**Near-guaranteed** (expect these true for most perspectives of any real game, so the tag confirms rather than constrains selection):

- **vis_enemy_ownership_change**: a cell visible at t and t+1 changes owner between two non-perspective players. Feeds the opp-lost dense-history transition category and the `last_seen_owner` overwrite.
- **own_tile_lost**: the perspective loses a tile to an enemy. The self-lost transition category, plus the vision shrink that follows. The one near-guaranteed item that is genuinely per-perspective: a dominant perspective can go a whole game without it.
- **army_chip**: a visible cell's army drops with owner unchanged, in two variants (an own tile attacked, a visible enemy tile attacked). The army-delta combat signal and `last_seen_armies`.
- **tile_gain**: the perspective gains a tile, in two variants by the transition encoder's older-owner keying: from neutral (the +0.5 category) and from an enemy (the opp-lost category, requiring a combat win).
- **first_contact**: the first tick the perspective sees a tile owned by opponent p. The `opp_contacted` flip and the start of `opp_has_seen` accumulation.
- **seen_then_fogged**: a cell visible at some tick and fogged at a later one. `turns_since_seen` resumes incrementing and the `last_seen_*` values freeze.
- **stale_memory_refuted**: the perspective regains vision of a cell whose owner or army changed while fogged. The memory-overwrite path. Likely subsumed by `seen_then_fogged` in practice, kept separate because the overwrite is a distinct code action.

**Perspective-dependent** (the real selection constraints: common in games, not guaranteed for a given perspective):

- **general_revealed**: the perspective gains direct vision of an enemy general before its capture. The `general_locations` pin, `known_general`, and a BFS source activating mid-walk.
- **neutral_city_revealed**: the perspective gains vision of a neutral city it had only known as structure-in-fog. `structures_in_fog` resolves to `known_city`, the BFS graph grows, and the garrison becomes visible. The mountain sibling of this disambiguation is automatic at roughly 20% map density.
- **city_ownership_change**: a city visible to the perspective changes owner, ideally in both flavors (neutral-to-player via garrison combat, player-to-player). Consumers are `known_city` persistence and the BFS passability formula's inputs. Not `opp_city_inference`: that channel is zero-stubbed today.
- **capture_role**: a capture with the perspective as the captor, in one variant, and with a third-party captor in the other. The two `opp_captured_by` encoding branches (captured-by-self reads -1.0, a third-party captor reads its canonical channel index). Per-perspective but needs no vis, since capture events are global.

**Rare** (a §3 event plus a vision circumstance):

- **unobserved_general_to_city**: a capture or neutralize at tick e where the perspective has previously seen that general but lacks vision of the tile at e. The stale-`known_general` branch (`bc/obs/memory.py`, the vision-conditional general-to-city cleanup), the one fog path nothing else on this list reaches.
- **neutral_armies_visible**: post-neutralization neutral tiles with retained armies inside the perspective's view. Rides along with the neutralization tag but needs the vision circumstance.

## 6. Selection constraints

- **The board-size gate applies**: `max(w, h) <= MAX_BOARD_SIDE` (32), because the obs tensor is padded to [32, 32].
- **The player-count gate is deliberately skipped**: fixture selection reads the intermediate dir directly and has no obligation to apply the training filters, which is what makes the phantom-slot fixture available.
- **Truncation interacts with tags**: truncating a fixture at selection time (a valid runtime knob per 7.12-1 §9) must not cut away the tail frames that a fixture's `no_removal_tail` tag depends on.

## 7. Exclusions

Each with its evidence, so they stop being re-litigated:

- **Disconnects**: would appear as gap-1 AFK pairs, and zero were observed in a 5000-game sample (appendix §5). Unobservable in practice.
- **Stalemate-breaker deaths as a dedicated class**: the breaker emits ordinary DeathEvents (verified in the sim kill path, 7.10-2 §8), and its distinctive consequence (death without removal) is already the `no_removal_tail` tag.
- **Sim-resolution edge cases** (convergent moves, priority order, inward-first chains, the chained-capture resolution mechanics): the golden tests never run the sim, and the replay-parser fixture suite already covers these classes (`samet_chain`, `capture_during_surrender`, `multi_surrender`, `3way_action`).
- **Board-cell mechanics** (expansion, friendly merges, defender-holds combat, production events): automatic in any real game with combat and `T >= 51`. The per-perspective residue is captured by the §5 condition tags rather than by classes of their own.

## 8. What this pass misses

The goal is a completely comprehensive inventory of meaningful game-state change. Two pieces of work stand between this pass and that goal.

1. **The obs-channel sweep.** Per stateful channel, enumerate the distinct history shapes the channel responds to. This is the only procedure that can complete the condition list, because memory channels distinguish histories, not frame pairs (§1). Three examples already known to be missing from this pass: the dense-history buffer-fill boundary (frames with `t < n`), long fog spans as opposed to merely "fogged at some point" (large `turns_since_seen` values), and the BFS channels' behavior after a known general is captured (`general_locations` stays pinned while the `known_general` clearing is vision-conditional, and the actual behavior is unverified). The sweep has a second consumer: reviewing the frozen-frame pick rule. Event-adjacent frames capture event transients, but memory-state evolution lives between events, where only the stats layer watches. The sweep is the natural place to decide whether the pick rule needs memory-motivated additions, for example a frame deep inside a long fog span.
2. **A second comprehensiveness pass on the game-state side.** The §3-§5 lists came out of one derivation session and have not had a fresh-eyes review.
