## 1. Channel-count facts

Verified by running the config code:

- Default config (`OBS_CONFIG_DEFAULTS`: `dense_history_n=5`, `obs_dtype=fp16`, `player_status_channels=True`) yields `obs_channels` = 110.
- Legacy config (`LEGACY_OBS_CFG`: `dense_history_n=5`, `obs_dtype=fp32`, `player_status_channels=False`) yields `obs_channels` = 96.
- The `OBS_CHANNELS` module symbol (`obs_config.py:135`) is `OBS_CONFIG_DEFAULTS.obs_channels`, so it is 110.
- Decomposition: 86 base + 2×5 dense-history = 96, then + 14 player-status = 110.

There is one distinction that decides how the trails should be fixed. `obs_channel_count(n)` (`constants.py:141-143`) returns `_BASE_OBS_CHANNELS + 2*n`, which is 96 at n=5. It is the base-plus-dense count and deliberately excludes gated groups. `obs_cfg.obs_channels` (the property on `ObsConfig`) folds in the enabled gated groups and is 110 for the default. `build_obs` sizes its output buffer from `obs_cfg.obs_channels` (`build.py:106`), not from `obs_channel_count`. So a docstring that describes `build_obs`'s output as `obs_channel_count(n)` or as 96 is naming the wrong quantity now that a gated group ships on by default. The right fix references `obs_cfg.obs_channels` (110 default), not a bare `96→110` swap that leaves `obs_channel_count(n)` in place, since that function still genuinely returns 96.

## 3. The stale `memory.py` banner

The `TODO(obs-alive-tick-seam)` tag now appears only in `memory.py`: the banner at lines 219-228 (above `scoreboard_row`) and a short reference at lines 261-262 (inside `init_memory`'s vectorized army precompute). The elim-targets and player-status side carries no such tag anymore, because the fix already rewrote it.

The banner's false claim: it says `alive_mask` "uses `death>t` (event-time) and reads them DEAD at the same frame t", producing "a 1-frame obs/target inconsistency". Post-6.18, `alive_mask` uses `death_by_slot >= t` (`player_status.py:127`). A victim whose DeathEvent fires at t now reads alive at frame t, matching the pre-event board. The obs/target inconsistency the banner describes is structurally closed.

The banner's still-true claim: the scoreboard and army channels read `ownership[t]`, the pre-event board snapshot. At a capture-while-alive tick the victim's tiles have not transferred yet (they zero at t+1), so the frame still counts their army and land at t. That is the intended board-snapshot-time behavior, and it is now consistent with `alive_mask` and `present_mask` rather than at odds with them.

The verdict from 7.10-2 §8 holds: rewrite, do not delete. The rewrite should drop the closed obs/target claim, keep the board-snapshot-time description, and fold in the capture seam from §4 below. The short reference at 261-262 calls the value "board-snapshot-time army", which stays accurate, so only its `TODO` tag and pointer need updating to match the rewritten banner.

## 4. The capture seam: precise classification

At a capture tick t, `build_obs` runs after `step_memory(t)` has applied that tick's events. Two tick conventions then coexist in the single frame t.

Event-time (reflects the capture at tick t):

- `opp_captured_by`, the seven `opp_N_captured_by` channels of cat 9 (`_cat_contact_capture`, `channels.py:225-254`). `step_memory` sets `state.opp_captured_by[captured] = captor` for every capture event whose tick equals t (`memory.py:397-403`). So at frame t the victim's channel already reads "captured".

Snapshot-time (describe the pre-event board at frame t, where the victim is still on-board, alive, and present):

- Board channels: `_cat_visible_state` reads `ownership[t]` / `armies[t]` (`build.py:65-66`). The victim's tiles are still theirs at t and transfer at t+1.
- Scoreboard broadcasts: `_cat_scoreboard`, `_cat_self_broadcast`, and `_cat_opp_broadcast` read `*_count_history[t]`, computed from the pre-event board, so the victim's army and land are still counted.
- Player-status channels: `alive_mask` and `present_mask` use `>= t`, so the victim reads both alive and present at frame t.
- Dense-history (cat 10): the (t, t-1) transition and army-delta pair does not yet show the capture's tile transfer, which lands in the (t+1, t) pair.

So `opp_captured_by` is the lone event-time channel and every other channel is snapshot-time. Within the same frame t, `opp_N_captured_by` says the victim is captured while the board, scoreboard, and player-status channels all read the victim on-board, alive, and present. No comment in the code records whether this split is intended.

The decision (7.12-2 §2 item 4) is to document it as the known convention now and revisit after the first cut. A golden freezes it as-is, and a later fix would fire loudly and be recorded correctly. The cost asymmetry drives the call: documenting costs a comment, while fixing would be an ungated E2 boundary for every existing checkpoint, spent on a subtle semantic in roughly 1% of frames (capture ticks, an estimate carried from 7.09-1) with no evidence of harm. This documentation folds into the §3 banner rewrite, whose proposed text already carries it.

One note on the ~1% figure. 6.18-6 measured 1,118 frames (about 1% of the `cloud_24k_sub_5k` val split) for the old obs/target seam, which was capture-while-alive transients. The intra-obs seam here fires on the same capture-while-alive events, so the same order of magnitude applies, but the 1% carried into 7.12-2 is an estimate, not a fresh measurement of this seam.

## 5. Post-6.18 alive/present semantics (reference)

For accuracy when writing the banner and the status line, the current semantics, verified in `player_status.py`:

- `alive_mask` = `is_real & (death_by_slot >= t)` (line 127). `present_mask` = `is_real & (removal_by_slot >= t)` (line 139).
- `death_by_slot` is the first DeathEvent tick (surrender or capture-while-alive). `removal_by_slot` is the board-removal tick (capture or neutralize). The winner gets a large finite sentinel and a phantom slot gets -1.
- The surrender window is `~alive & present`, the gap between death and removal.
- The `>= t` test follows the sim-core convention that events fire pre-increment and become visible at `snapshot[e+1]`, so `snapshot[e]` is pre-event. `>= t` is the correct test against the obs's pre-event board.
- Both the obs player-status channels (`_cat_player_status`, `channels.py:305-318`) and the elim targets read these same masks, so the obs-vs-targets aliveness divergence that 7.09-1 §11-Q5 described is structurally impossible now (7.10-2 §8).
