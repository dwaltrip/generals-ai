# Behavior-goldens design sketch — an automatic tripwire for the behavior axis

*Date: 2026-07-09. Brainstorm notes plus a detailed sketch from one design session — substantial design work remains, and nothing here is built. This note seeds the eventual design doc and is not maintained. Vocabulary (surfaces, E1/E2/E3, boundaries) from [the confounds framework](../confounds-framework.md). Lineage: the behavior-changelog proto-plan ([7.06-2](7.06-2-ckpt-config-motivations-and-direction.md)) and the three surveyed boundaries ([7.08-1](7.08-1-confound-boundaries-survey.md)), which this design responds to.*

## 1. The goal, and the decision it enforces

The shape axis has a tripwire: a config-shape change without a `CONFIG_VERSION` bump fails a test. The behavior axis has nothing equivalent — behavior-affecting changes land silently, and the 7.08-1 survey found three that did. This sketch is the behavior-axis counterpart: an automatic check that makes a silent behavior change loud at commit time. The automatic-check property is the primary requirement; the rest of the sketch serves it.

The decision the tripwire forces: every behavior-affecting change is a **gate-or-not** decision, and not-gating is implicitly a checkpoint-support policy call — everything trained before the change just became degraded or unsupported on current code. The May–June boundaries were this decision made implicitly, as a side effect of how fixes landed. The record-keeping failure was retrieval, not existence (the 06-07 fix was recorded in a handoff note no later doc referenced), which is why a manual changelog alone was judged too weak: it depends on the author noticing, and it doesn't force the decision moment.

Gating itself has a location ladder, not a binary form: inline config-gated branches (the current pattern) → a module-level split (`BCModel` vs a hypothetical `BCModelLegacy`) → a routing seam (`LoadPlan`-style dispatch) → not gating at all (unsupported). All but the last are gating; what differs is where the behavioral split lives, and the accretion pain of inline gates (7.06-2 motivation #1) is the pressure that pushes splits up the ladder over time. The aux-head variants are a rough early instance of a higher-level split, scoped to one head. The goldens are agnostic to split location: a supported config point keeps its golden wherever its gate lives.

With the tripwire in place, the boundary record becomes machine-prompted output (a stub the regen tool writes, with fields a test refuses to leave unfilled) rather than remembered discipline. This partly subsumes the behavior-changelog plan — but only partly: surfaces the goldens can't see (§3) still need a manual path.

## 2. System sketch

A *golden test* freezes a known input plus the pipeline's current output for it; the test thereafter fails whenever the output changes. Four guards over the guarded surfaces:

- **Obs golden** — hand-built synthetic sim fixtures (code, not data) → frozen obs tensors.
- **Targets golden** — the same fixtures → frozen label arrays (elim targets, masks, policy targets).
- **Forward golden, one per supported model variant** — hash-fill weights (§4), full-size real configs, all output heads compared.
- **Live/training obs parity** — already exists (`packages/eval-tools/tests/test_obs_path_parity.py`, byte-exact obs+mask per tick/perspective on a real fixture game). Known gaps: perspective slot 0 only, no capture/neutralize/surrender events in the fixture.

Supporting machinery:

- **Verification layer** (§5) — health checks plus an exhaustive mutation check at every *bless* (accepting a golden's current outputs as the new frozen reference), making sensitivity a measured property.
- **Regen tool** (§7) — one linear core (build → run → check → write references + sidecar + stub); event-triggered modes (`--bridge`, `--environment`) deferred until their first triggering event.
- **Boundary stub + blocking test** — regen appends a stub with unfilled fields (gated? affected checkpoints? disposition?); a test refuses to pass while fields are unfilled.
- **Diffable sidecars** — per-golden JSON: array shapes/hashes/stats, environment metadata, mutation margins, coverage summary. Binary references alone would defeat diff review.
- **Size guardrail** — a test asserting the goldens directory stays under a few MiB, making the size ceiling structural rather than intentional.

## 3. Surface inventory

A green golden run means "no behavior change **in what these fixtures execute**" — not "behavior unchanged everywhere." The inventory keeps that clause visible:

| Surface | Status | Note |
|---|---|---|
| Obs encoding (sim dict → tensor) | guarded (designed) | obs golden |
| Targets / labels | guarded (designed) | targets golden; covers the tick-seam class |
| Model forward, per supported variant | guarded (designed) | forward goldens, hash-fill |
| Live vs training obs paths | guarded (exists) | parity test; slot/event coverage extensions optional |
| Eval protocol | partial | frozen eval-map-set pins maps; rest open |
| Action selection / decode | partial | eval-tools parity fingerprint covers it, but depends on a large external checkpoint |
| Replay→sim parser | open (deferred) | upstream of everything; golden pattern sketched (frozen small replay → frozen sim dict); revisit when touching the parser |
| Loss functions | open | frozen-artifact recompute pattern applies; seams unmapped |
| Metric definitions / aggregation | open | a definition change breaks old-vs-new number comparisons (framework: E3 ruler); same family as loss |
| Dataset sampling / filtering | open | a silent change alters training data with all goldens green |
| fp16 / MPS device branches | out of scope | goldens pin fp32 CPU; device consistency is a separate concern |
| Training-run reproducibility | out of scope | this system is about artifacts and comparability, not run determinism |

## 4. The forward golden: hash-fill weights

**Mechanism.** Every parameter's values are a pure function of its own name — a hash supplies the "random" numbers, so no RNG library is involved anywhere. Per parameter:

1. Hash the parameter's `state_dict` name with `shake_256`, an extendable-output hash (FIPS 202, spec-pinned): it emits any requested output length, here exactly `4 × numel` bytes.
2. Read those bytes as little-endian uint32s (`'<u4'`, explicitly) and map to uniform floats in [-0.5, 0.5). The values look statistically random but are fully determined by the name.
3. Apply a role-dependent scale — fan-in scaling for ordinary weights, `1 ± 0.2` for norm gammas, `± 0.2` for norm betas. This is the semantics-aware part, needed to keep activations in a range where the test stays sensitive (§5).

Because each parameter depends only on its own name and shape, construction order is irrelevant, and there is no library whose internals can drift under the test. Snippet in appendix C.

**Why not seeded RNG:** seeded init consumes one global stream in construction order, so a harmless registration reorder shifts every weight. PyTorch explicitly disclaims RNG stability across releases. And `manual_seed` has been broken for `randn` on MPS. **Why not stored weights:** a full-size state_dict is 16 MiB of incompressible random data per variant against an 11.7 MiB total repo history — a realistic trajectory (8 variants plus migration rewrites) reaches low hundreds of MBs, over the project's size ceiling. The retreat path (freeze the generated weights into files) stays one command away but is size-constrained to tiny configs, which carry their own risks (below).

**Golden configs are frozen config blocks, never built from live defaults.** A golden expressed as `build_model_cfg(**overrides)` would silently move its guarded config point whenever a default changes — the collapse-to-current hazard 6.26-5 flagged in `_arch_for_load`/`LEGACY_ARCH` (a frozen instance of a live class). Golden configs are stored dicts with `config_version`, riding the same migrate-once machinery as real checkpoints. Each golden fixture is thereby a miniature synthetic checkpoint plus an answer key, exercising the exact contract real old checkpoints depend on — including the config-migration seam, for free.

**Full-size real configs.** The default 4.2M-param model builds in 0.02s and forwards in 0.04s on CPU (measured), so there is no runtime reason to shrink, and hash-fill removes the storage reason. Tiny configs were rejected on three grounds: `_gn` picks GroupNorm group counts by divisibility, so a w=16 golden runs 16 groups where production runs 32 — a different computation graph; a tiny config guards a config point no checkpoint occupies; and sensitivity transfer from tiny to real is unverified.

**Guard-by-default.** One golden per occupied config point (the configs of supported checkpoints), parametrized over a variant registry: a registry entry with no frozen reference fails by construction ("unblessed — run regen"). There is no curation step to forget. Reference outputs are ~35–40 KiB per variant regardless of trunk width (head shapes don't scale with it). All output heads are compared — a measured lesson: perturbing the value head moves policy logits by exactly zero, so a policy-only golden leaves entire heads unguarded.

## 5. The verification layer

The key simplification: a golden model has **no realism requirement**. It needs exactly three properties — deterministic, finite, sensitive (a change anywhere in the computation visibly moves some compared output) — and all three are machine-checkable. "Did we enumerate every fill special-case?" therefore converts from a foresight problem into a verification problem.

At every bless, automatically inside the regen tool:

- **Health checks** — outputs finite, per-head variance in a healthy band (catches degenerate fills).
- **Exhaustive mutation check** — perturb every float tensor in the state_dict, one at a time, one forward each (~0.04s; roughly a minute across all variants), asserting each moves at least one compared head by a healthy margin. Coverage is complete by construction, not sampled: any tensor whose influence got crushed — by a fill-rule gap, an architecture quirk, anything — fails the bless with its name printed.
- **Activation-hook probes** — perturb each module's output activation, certifying parameter-free ops (interpolations, maskings) influence the result. ~20 lines against the same machinery.
- **Margins recorded** in the sidecar, giving a paper trail of detection power over the project's life.

Bless-time-only is sound because sensitivity has no realistic path to drift silently between blesses: a code change that would alter the model's behavior fires the golden itself first, which routes into a bless, which re-verifies. So the check runs at exactly the moments sensitivity could change (new variant, re-bless after code or environment change).

The measured basis for taking this seriously: with a semantically blind fill, GroupNorm gammas land in [-0.19, 0.19] (instead of ≈1), attenuating block interiors ~10× per norm layer behind the residual skips. The measured consequence: a mid-trunk 1e-3-relative perturbation moved the output only 1.5e-4 — marginal against any plausible tolerance. The norm-aware fill recovered ~20× (2.3e-3). The blind probe's outputs had *looked* healthy; health and detection power are independent properties, which is exactly why detection power is measured rather than assumed.

## 6. Comparison policy

**Exact on the canonical platform.** One machine, CPU, threads pinned to 1, fp32 obs: the forward is bit-for-bit deterministic (measured across processes). Between environment changes there is no variance to absorb, so the comparison is exact and the standing miss-window is zero — any nonzero difference fires. This is stricter than any surveyed project uses for floats, and justified only by the pinned-platform reality; the surveyed projects' tolerances exist to absorb CI-fleet variance we don't have.

**Environment upgrades are scheduled re-bless events.** A torch/numpy bump may fire every forward golden at once. The classification aid: per-head max|Δ| against two known scales — ulp-churn (last-bit float rounding differences: diffuse, ~1e-6-ish) and the recorded mutation floor (~1e-3+). Diffuse shifts orders of magnitude below the floor read as churn (re-bless as "environment"); anything near the floor or concentrated in one head reads as behavior (investigate first). Hygiene rule, shared with renames: never mix behavior changes into an upgrade commit.

**Modest multi-platform, designed in from day one** (~20 lines of foresight):

- The comparison function takes a mode: exact on the canonical platform, tolerance band elsewhere.
- The sidecar records the blessing environment.
- Mutation margins are recorded per bless, so "is tolerance mode safe on platform X" is a lookup.

The classic tolerance weakness — a silent miss-window — is bounded here by measured headroom (churn ~1e-7–1e-5 vs certified floor ~1e-3). Per-platform baselines (the HF `Expectations` pattern) remain available if exactness on two platforms is ever wanted. The numpy paths (obs, targets) are plausibly byte-stable even cross-platform (elementary IEEE ops are bit-identical; the risk is transcendentals and reduction order) — a cheap Modal experiment would settle it.

## 7. Flows — minimal initial versions

Day-one core is flows 0–3: the golden tests, a linear regen (build → run → check → write references + sidecar + stub), and the stub-blocking test (~10 lines of it; ~200 lines all told). An AGENTS.md note telling agents what a golden failure means and which flow applies rides with the build. `--bridge` and `--environment` are deferred until their first triggering events. Uncertain parts are marked *(open)*.

**Flow 0 — normal work.** Goldens pass silently. ~95% of commits.

**Flow 1 — add a gated variant.**
1. New registry entry lands with the variant code.
2. The parametrized golden test fails: "variant X unblessed — run regen."
3. `regen --bless X`: build the hash-filled model from the frozen config → health + mutation checks (loud failure if the fill or sensitivity is off) → write references + sidecar.
4. Commit code + golden files together. No stub — no boundary was created.

**Flow 2 — intentional ungated change (the boundary path).**
1. Goldens fail with a magnitude report: which channels/heads, how big.
2. If intended: `regen` rewrites the references **and appends a boundary stub** — date, goldens moved, magnitudes, and unfilled fields: `gated? / affected checkpoints? / disposition?`.
3. A test refuses to pass while stub fields are unfilled — the gate-or-not decision and the support call happen in writing, in the same commit.
4. Commit = code + regenerated goldens + completed stub, one reviewable diff. *(open: where stubs live — boundaries ledger vs support-policy doc — is undecided, §11.)*

**Flow 3 — unintentional change (the catch).**
1. A golden fails unexpectedly.
2. Investigate — no regen. Fix the accidental behavior change.
3. Goldens pass again. Nothing regenerated, no stub. This flow is the one the system exists for.

**Flow 4 — environment upgrade** *(deferred; first occurrence handled manually).*
1. All forward goldens fire with diffuse magnitudes far below the mutation floor.
2. Classify as churn via the report; re-bless everything; one stub classified "environment"; new environment stamped in manifests.
3. Hygiene: no behavior changes in the same commit. *(open: classification thresholds are judgment calls until calibrated on the first real upgrade.)*

**Flow 5 — rename refactor** *(deferred: cannot be built until the first state_dict key migration exists — none does yet).*
1. Goldens fire (hash-fill weights follow names).
2. `regen --bridge <migration>`: fill the new model under the **old** names via the key-migration map → outputs must match the existing references — a continuity proof, no old code checkout needed.
3. Re-bless under new names; stub records "rename, continuity verified." A bridge failure means a real change hid in a "pure" rename — flow 3 in disguise.
4. Generalizes to value-transforming migrations (regenerate old-name weights, push through the real migration — which tests the migration itself with a known-answer input). *(open: mapping mechanics need a dedicated pass for hidden complexity — partial renames, where migrations live, shared-vs-duplicated name maps.)*

**Flow 6 — retire a variant.** Delete the registry entry and its golden files. The deletion is the policy change, visible in the diff.

The mutation check runs automatically inside every bless (flows 1, 2, 4, 5) — never a separately remembered step.

## 8. Red-teaming results for hash-fill

The hash-fill idea was deliberately red-teamed ("too good to be true" check). Seven weaknesses, each with its disposition:

**W1 — the fill is semantically blind.** state_dict entries have roles (norm affine params, running stats, gates, embedding padding rows, tied weights); blind filling is wrong for several, and the failure can be silent (degraded sensitivity) rather than loud (NaN).

- Measured: active today via the GroupNorm gammas (§5 numbers) — and the original probe's healthy-looking outputs masked it.
- Response: module-type fill rules (two today — default fan-in, norm affine; future rules added reactively), plus the verification layer making any incompleteness loud.
- Residual: nothing silent — an unhandled future module type fails its bless loudly.

**W2 — sensitivity unverified per architecture.** Converted from hoped to measured-and-enforced: the exhaustive mutation check re-verifies at every bless, exactly the moments sensitivity could change. Residuals:

- Perturbation scale and margin threshold are calibration judgment calls.
- Parameters behind genuinely saturating ops may need documented exceptions.
- Changes below the comparison threshold are W5's territory (nil on the canonical platform under exact compare).

**W3 — renames lose the continuity proof.** The concern: stored weights can prove a rename refactor preserved behavior (migrate the keys, outputs must match), while hash-fill weights change whenever names change — so a rename's re-bless looks blind. Largely dissolved:

- Hash-fill weights are reconstructible from historical names, and git has the names — the old golden model is never lost.
- The bridge (flow 5) fills the new model under the old names via the key-migration map, so outputs must match the existing references: a continuity proof. The migration has to exist anyway, or `strict=True` breaks every old checkpoint.
- The ceiling is better than stored weights — the bridge tests the migration itself with a known-answer input. The floor, if the bridge is skipped, is a blind re-bless: the original state, no worse.
- Residual: the bridge is a prompted procedure, not automatic, and its mechanics need the deferred deep-dive.

**W4 — endianness assumption in the byte decode.** Fixed by construction: explicit `'<u4'`.

**W5 — tolerance is a line in the sand.** Dissolved on the canonical platform (exact compare, zero standing miss-window; §6). Off-canonical, the tolerance mode's miss-window is bounded by measured margins rather than hope. Residual: a behavior change landing in the same window as an environment upgrade could hide under churn classification — mitigated by the no-mixed-commits hygiene rule.

**W6 — coverage bounded by what executes.** Three gaps:

- *Config coverage* — solved by construction: goldens are the occupied config points, and registration forces a bless. Residue: keeping the registry in sync with the supported set is the coupling to route-1 (the pending supported-checkpoints policy call from the checkpoint-config work).
- *Data-dependent branches* — tractable: the domain's event classes are enumerable and small, so fixture design against a checklist is an afternoon. A `coverage.py` report scoped to the guarded modules lists unexecuted lines in the sidecar, turning silent gaps into a visible list.
- *Environment branches* — out of scope, labeled (see §3).

Complement for input-space breadth: invariant/property tests (appendix A, family 3).

**W7 — re-bless fatigue (rubber-stamping).** Four defenses:

1. Regen never yields a green run by itself.
2. The stub's unfilled fields block the suite — the decision is a test requirement, not an honor-system note. This is the strongest deviation from snapshot-testing culture, where updating is one flag.
3. Everything reviewable is diffable text.
4. Base-rate control: fires are structurally rare (flow 1 once per variant; flows 4–5 a few per year; flow 2 a few per quarter on project history).

Also in this design's favor: most commits here are agent-authored, and deterministic named-command procedures are the shape agents follow reliably.

## 9. Design constraints

- **Repo size, structurally.** Nothing on any growth path approaches hundreds of MBs: committed artifacts are outputs (~35–40 KiB) plus sidecar, ~40–50 KiB/variant in all (100 variants ≈ 5 MiB), and the guardrail test enforces the ceiling rather than trusting intentions. This constraint plus full-fidelity configs jointly eliminated stored weights.
- **Modest multi-platform.** Designed in at ~20 lines (§6); the single-machine assumption is an exploited default, not a foundation.
- **Tooling stays simple.** One linear regen core; modes accrete at the rate of rare events, built at first occurrence. The flow walkthrough describes the mature system, not the initial build.
- **Guard-by-default.** No curation step between "variant exists" and "variant guarded."
- **Project precedent: no structure without a consumer.** The bridge waits for the first key migration; `--environment` waits for the first upgrade; `arch_version` stays unreserved — the goldens deliver the detection that stamp was for, without reserving a checkpoint-format slot.

## 10. Measured / designed / assumed

**Measured this session:** hash-fill determinism across processes (default model, 4.2M params); blind-fill sensitivity marginal (mid-trunk 1.5e-4 vs ~1e-4 tolerance) and norm-aware recovery (~20×, 2.3e-3); all-heads lesson (value-head perturbation → 0 on policy logits); build+forward 0.02s+0.04s CPU; stored-weight sizes (16.10 MiB default fp32, incompressible) and repo pack size (11.73 MiB).

**Verified in code/research:** pure numpy seams for obs/targets; the existing parity test; two in-repo freeze→compare→regen precedents; the practices survey (appendix B).

**Designed, unbuilt:** the semantic fill module, mutation-check harness, stub-blocking test, sidecars, classification report, fixtures, the regen tool itself. The bridge cannot be built yet.

**Assumed:** numpy paths byte-stable cross-platform (cheap Modal experiment would answer); fires stay rare enough to avoid ritual fatigue (base-rate argument from project history); compressed obs references land well under 500 KiB (to be measured at first freeze).

## 11. Open questions

1. **Registry mechanics.** A machine-readable supported-config-point set doesn't exist — hand-listed file vs derived from supported checkpoints' stored configs. This is the route-1 coupling: route-1 and the golden build aren't fully separable.
2. **Stub destination.** The stub needs a home: a standalone boundaries ledger, or a section of the support-policy doc route-1 will produce. Undecided.
3. **Sequencing vs core work.** The elim arc is waiting. Rough sizing: fill + mutation harness ~0.5d; obs/targets goldens + fixtures ~1d; forward goldens + regen core ~1d; stub wiring ~0.5d. A partial cut exists: obs/targets goldens first — cheapest tripwires, covering two of the three historical boundary classes.
4. **Bridge mechanics deep-dive** — hidden-complexity check on the mapping story (flagged during the session).
5. **Fixture event-class checklist** — the domain enumeration (an afternoon or less). One known trap to encode deliberately: the intentional one-frame obs-vs-targets asymmetry at capture-while-alive ticks (`bc/obs/memory.py`, ~1% of frames).
6. **Loss/metrics seam-mapping** — the unguarded measurement surface; elim-arc work touches exactly this class.
7. **Mutation-check calibration** — perturbation scale, margin factor, saturating-op exceptions.
8. **Platform set** — which platforms actually matter near-term; run the Modal byte-stability experiment when one does.
9. **Parser golden** — deferred; revisit when touching the parser.

Not replaced by this design: the retroactive record of the three known boundaries, the route-1 policy call, and the 6.18 trail repair all remain queued.

## Appendix A — check mechanism families (condensed survey)

Eight families, organized by what they compare against:

1. Reference/golden checks — frozen input → stored output.
2. Differential/parity — two implementations that must agree. No frozen artifact, no re-bless case; only exists where redundancy exists.
3. Invariant/property checks — version-independent assertions. Catch bugs, not deliberate changes.
4. Source-hash stamps — a version constant tied to file/AST hashes. Free, imprecise in both directions.
5. Diff-triggered process hooks — paperwork enforcement at commit time.
6. Frozen-artifact recompute — recompute metrics on stored dumps. The only family covering measurement-definition drift.
7. Statistical drift monitors — run-over-run stats. Broad, noisy, after-the-fact.
8. Load-time contract checks — protect *use* rather than *change*; need machine-readable boundary records.

Two organizing axes: failure class caught (accidental divergence vs unacknowledged deliberate change vs innocent misuse after a boundary) and precision-vs-fixture-burden. The three historical boundaries wanted different families: the stale-live-obs bug wanted parity; the obs-content and tick-seam fixes wanted a ritual-forcer. The metrics surface — never a past boundary, but the same reasoning — wants recompute. This design composes families 1+2 for the guards and a hook-like ritual (5) for the record; family 8 becomes available later if boundary records are structured data. Families 4 and 5 (as primary mechanisms) were downgraded once the code map showed the fixture costs they avoid were mostly already paid.

## Appendix B — practices research (condensed)

From a sourced survey of HF transformers, torchvision, PyTorch core, and snapshot-testing systems (2026-07-09; primary sources where noted):

- **Output pinning:** HF hardcodes small expected slices at `rtol=atol=1e-4` fp32, gated to a slow nightly tier on fixed hardware, with an `Expectations` table per (device, compute capability); torchvision freezes pickled full outputs with `EXPECTTEST_ACCEPT=1` regen. Nobody freezes hashes of float outputs; exactness is reserved for integer dtypes.
- **Test weights:** committed tiny-random checkpoints (HF, doubling as Hub fixtures) or seeded in-process construction for structural asserts only. PyTorch's reproducibility notes, verbatim: "Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms." No established project was found doing hash-derived weights (bounded-search absence, not proof).
- **Behavior versioning:** no load-time behavior-stamp convention exists anywhere surveyed; ONNX's three-axis split (file format / operator semantics / weights identity) is the one principled precedent, and it validates this project's shape/behavior/provenance separation.
- **Regen rituals:** insta (pending files, interactive per-snapshot review, no CI auto-write), Jest (no auto-pass in CI, explicit anti-rubber-stamp guidance), pytest-regressions (`--force-regen` rewrites but still fails the run). The transferable line: binary or oversized snapshots defeat every defense because the diff can't be read — hence this design's diffable sidecars.
- **Deviation verdict:** hash-fill is off the trodden path but dodges exactly the disclaimed-stability and init-order problems that push others to committed binaries; exact float comparison is stricter than practice, justified only by the pinned platform, with the tolerance fallback one line away.

## Appendix C — probe measurements and fill essentials

Probes were tmp scripts in `tmp/behavior-goldens-probes/` (not committed). The essentials:

**Determinism:** hash-filled default `BCModel` (4,201,570 params), fixed hash-derived obs, CPU, threads=1 → byte-identical outputs across two fresh processes.

**Sensitivity (1e-3 relative perturbation → max|Δ policy_logits|):**

| fill | early conv | mid-trunk | value-head |
|---|---|---|---|
| blind | 8.5e-4 | 1.5e-4 | 0.0 (wrong head compared) |
| norm-aware | 2.0e-2 | 2.3e-3 | 0.0 (ditto) |

**Timing:** default model build 0.02s, forward 0.04s (CPU, M1).

**Stored weight sizes (state_dict, `torch.save`):** default 16.10 MiB fp32 / 8.08 fp16; w=64/64/96 one block/stage 3.49 / 1.77; w=16 0.32 / 0.18; w=8 0.16 / 0.10. Random weights are incompressible (`savez_compressed` ≈ raw). Repo packed history: 11.73 MiB.

**Fill sketch:**

```python
def hash_floats(tag: str, n: int) -> np.ndarray:
    raw = hashlib.shake_256(tag.encode()).digest(n * 4)
    u = np.frombuffer(raw, dtype="<u4").astype(np.float64)
    return ((u / 2**32) - 0.5).astype(np.float32)   # uniform [-0.5, 0.5)

# per state_dict entry (float tensors only; int buffers keep module defaults):
#   norm gamma:  1.0 + 0.4 * vals        # centered at 1 — measured 20x sensitivity vs blind
#   norm beta:   0.4 * vals
#   default:     vals * 2 * sqrt(6 / fan_in)
# tied weights: fill once per storage, keyed by canonical name (alias-detect via data_ptr)
```
