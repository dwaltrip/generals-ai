## 1. Goal and scope

The goal: detect behavior-affecting changes automatically, and enforce that each one is handled. "Handled" means a conscious decision (gate the old behavior, or accept a boundary) plus a durable record, made in the same commit as the change. The automatic-check property is the primary requirement. Everything else in the design serves it.

The cut consists of:

- **Obs goldens and targets goldens** over frozen fixtures.
- **The shared machinery**: the regen tool, diffable sidecars, boundary records with their blocking test, a size-budget test, and an AGENTS.md note for agents who hit a golden failure.
- **Layer-1 fixture goldens**, sequenced near the end of the build (§3).

The cut has strong standalone value: once it lands, every boundary class that has actually occurred in this project has a tripwire. The obs-content class is covered by the obs goldens, the targets/labels class by the targets goldens, and the live-path-divergence class by the existing obs-path parity test in eval-tools. The forward goldens guard a class that has produced zero boundaries here, which is why they can wait.

Sequencing is decided: the cut is built before the elim arc. The arc's targets changes then land on a guarded surface, where each in-place change becomes a loud event with a correctly shaped record. The arc's loss and metric-definition changes remain unguarded (the E3-ruler class stays the open surface).

## 2. The core principle

Everything that defines a golden is frozen, except the code it guards. A golden is a frozen input, a frozen config, and a frozen expected output. The pipeline code is the only live ingredient at test time.

The principle has two legs:

- **The data leg.** Fixtures are committed npz files (a sim dict and its meta), produced once at authoring time. The golden tests never run the sim or the parser.
- **The config leg.** A golden's config is a stored dict with every field explicit, never built from live defaults. A strict-keys assert makes a later-added defaulted field break every golden load loudly, forcing the "what was the historical value?" question at the right moment. Semantic drift in the config class itself is caught by the frozen outputs sitting next to it. The stored config is a bare sub-config (the ObsConfig fields, and a small new TargetsConfig for the dataset-side knobs), so a golden's identity (the config point it pins) doesn't inherit unrelated config-migration churn.

The payoff is attribution: on the pinned environment, a golden fire means the guarded code changed, not the input data and not a drifted default.

## 3. Architecture

The system splits into two layers:

1. **Fixture production** (source material → committed npz): authoring-time, rare.
2. **The goldens proper** (committed npz → frozen outputs): the tests themselves.

The test path is numpy-only. The obs pipeline and the target functions are pure numpy, so the golden tests need no Rust build and no torch. The frame-assembly seam above the numpy layer (variant dispatch, which keys a variant emits, `raw_order` construction, the tensor wraps) is deliberately unguarded in this cut.

**Layer-1 goldens** close the loop on the fixture-production layer: each fixture with a committed source gets a test that re-derives the npz from that source (the parser on its committed replay) and compares byte-for-byte. These tests live in the sim/parser test tier, since they need the Rust build. A few fixtures suffice, because layer-1 guards shared code, not per-fixture data.

Together the layers give clean attribution by construction:

- Layer-1 fires alone: the sim or parser changed.
- Layer-2 fires alone: the obs or targets code changed.
- Both fire: a fixture-schema migration. This is a named, rare event with a manual two-step (regenerate fixtures with pipelines unchanged and show the references unmoved, then land pipeline changes separately, never mixed in one commit).

A related follow-up refactor is planned separately and doesn't block the cut: unifying the two near-identical npz writers (the parser's `write_sim_output` and game-runner's `write_eval_game`), after which every npz producer shares one schema.

## 4. Fixtures

Fixtures are real games pulled from the replay corpus and parsed to npz by the real parser. Selection is a query over the parsed event arrays, guided by the event-class checklist (captures, surrenders, neutralizations, a production tick, a 3+-player game, a next_death tie, death-without-removal tail frames). Provenance rides along, since the parser stamps `replay_id` into the npz. Frozen data cannot rot: a fixture's events are baked in.

Realism is the coverage argument. The obs tensor is padded to a fixed shape regardless of board size, so realistic boards cost nothing in shape, and a toy board has a different fog and padding profile whose sensitivity transfer to production-sized inputs is unverified.

There are no committed toy fixtures. When a fire needs first-principles ground truth (what a cell's correct value should be, derived by hand), the technique is to author a throwaway scripted game on demand: the produce-fixtures command makes this cheap, and a throwaway game needs no blessed references.

Each fixture declares the event classes it exists to cover, and fixture production asserts them against the npz's event arrays. This is a lightweight mechanism (per-fixture tags plus a small tag-to-predicate dict, a few dozen lines) and a soft commitment: it may be trimmed or dropped during the build. Its unique value is at fixture regeneration, the one moment layer-1 comparison is suspended.

The initial set is about 5 fixtures. The checklist itself is a pre-build item, re-derived from the code.

## 5. References and comparison

The one hard commitment: references must support magnitude diagnosis, not just detection. A fire's report needs "which frames, which channels, how big", and the first environment upgrade's churn-vs-behavior classification (separating harmless numerical drift from new library versions from real behavior changes) needs per-channel deltas. Hashes alone can give neither.

Comparison is exact equality on the pinned platform, with a tolerance mode for off-platform runs (carried from 7.09-1).

Reference fidelity comes in three tiers:

1. **Full arrays at event-adjacent frames** (capture ticks and their neighbors, death ticks, the first production tick, the first and final ticks). The frames are picked by a deterministic rule over the fixture's event arrays, not a hand list, so every regen re-freezes the same frames.
2. **An all-frames stats layer** (per-frame per-channel, compact binary), so a fire between fully-frozen frames still localizes to a tick and channel with rough magnitude.
3. **Git as the deep fallback**: a frozen fixture plus a deterministic pipeline means old code reproduces any frame's exact old values on demand (approximately so across environment boundaries).

Because the pick rule derives from the event arrays, every fully-frozen frame is event-labeled by construction: a fire reads as "the capture-adjacent frame of fixture X", not as an anonymous tick. Fire reports additionally annotate diffs with nearby events from the fixture's event arrays. Whether the stats layer also carries per-frame hashes (making detection between frozen frames exact rather than stats-resolution) is a small open question, settled at build time.

The dtype rule: a golden freezes its config point's output as-is, in whatever dtype the config emits, with no higher-precision copies on the side. The default point freezes fp16, which is what training and inference consume (a change below fp16 resolution is invisible to production too). The legacy point freezes fp32 and doubles as the sensitive canary for numerical churn (fp32 registers the small drifts that fp16 rounding absorbs), covering the shared channels at high precision.

The sidecar records each channel's arithmetic class. Only 16 of the default config's 110 channels are log-scaled. Every other class can never legitimately churn across library versions, so any diff there is a behavior change. The sidecar itself is diffable JSON, so a bless commit shows what moved and by how much in review.

Targets references are tiny (per-frame scalars and small arrays), stored in full for all frames with no curation.

## 6. Configs, the registry, and guard scope

The registry is one data file listing (golden type, fixture, config dict, reference path). The golden tests parametrize over it, and an entry with no blessed references fails as "unblessed — run regen". Registration alone forces coverage.

The scope decision: guard every occupied config point now, and prune later under route-1 (the pending supported-checkpoints policy call). Over-guarding costs a registry line and some kilobytes, pruning is a reviewable deletion, and the build stays decoupled from the policy call. The occupied points today: the obs default (110 channels) and legacy (96 channels) configs, and four targets variants (core, alive-only, time_bin, next_death).

The guard rule: goldens guard code paths, and config points are the addressing scheme.

- Enum-like knobs (obs dtype, elim variant, the status-channel gate) guard every occupied value, because each value selects a different branch.
- Scalar knobs guard per regime, with the regime boundaries declared (dense_history_n: 0 vs greater than 0). A second point inside a guarded regime adds little, because the same code is already guarded at its sibling.

The rule is codified minimally as declared guard rules beside the registry, and it is the curation rule route-1 inherits. Checkpoints trained at n=20 exist and sit in the same regime as the guarded n=5, so they need no additional golden; whether they are supported is a route-1 question.

Coverage forcing is automatic exactly where code must register itself: a new elim variant lands in the aux-heads registry and auto-fails as unblessed, and a structural test asserts every gated channel group is enabled in at least one registry entry. The residue is occupancy that arrives with no code registration anywhere: a checkpoint trained at a new scalar value, or at a dtype outside the registry. Tracking it is manual, and under the guard rule the scalar case is low-stakes, while dtype's two occupied values are both already guarded.

Two supporting details. The legacy point's stored config also carries an equality assert against the live `LEGACY_OBS_CFG` symbol, so the golden and the checkpoint-load path cannot drift apart unnoticed. And the fixture-by-config matrix is asymmetric by choice: targets variants run on all fixtures (references are tiny), while the legacy obs config runs on a designated 2 to 3 fixtures that exercise the gate.

One caveat to keep visible: goldens do not guard default values. Changing a default fires nothing, because goldens pin explicit config points (a default change is an E1 recipe change, needing only a record). Green goldens must not be read as "defaults unchanged".

## 7. Boundary records and the ledger

The boundary record is the durable artifact the system exists to produce (previously called the stub). Its lifecycle at an intentional ungated change:

1. A golden fires with a magnitude report.
2. Regen rewrites the references and **opens** a boundary record: mechanical fields pre-filled (date, which goldens moved, magnitudes), judgment fields blank.
3. The blocking test (about 10 lines) refuses to pass while any record is open. Regen never turns the suite green by itself.
4. The author **completes** the record, and the commit lands as one reviewable diff: code, regenerated references, completed record.

The record leads with the effect class (E1, E2 break, E2 repair, E3 ruler, E3 task), and the class determines which follow-up fields must be filled. E2 asks "gated? affected checkpoints?". E3 asks which comparisons stop being valid across the date. E1 is record-only. Class-first matters because the elim arc's fires should be mostly E1 plus E3 targets changes with no E2, and asking E2 questions about them repeatedly would breed boilerplate answers.

Automation is staged. Version 1 is a class-shaped template: template text plus the blocking test, no machinery. Deriving the class automatically (from which golden fired, via the framework's surface table) and inferring gatedness from the fire pattern are deferred until fires demonstrate the need. The judgment fields can never be derived: the sign of an E2 (break vs repair), the depth of an E3 (ruler vs task), and the support disposition stay human.

Repeated regens on a branch update one open record in place. Once completed and committed, records become append-only. An abandoned regen reverts in one step, because the record rides the same diff as the references.

On fire rates: the arc will fire the targets goldens frequently and by design. The aim is fires that are cheap and correctly shaped, not rare.

Completed records accumulate in the **boundaries ledger**: a standalone, append-only, chronological file. Boundaries are events, consulted at comparison time ("does a boundary sit between these two numbers?"). Support status is derived state, and route-1's eventual policy doc is a downstream view computed from the ledger, not its container. The ledger is seeded at creation with the three known May–June boundaries, whose retroactive record has been queued since [7.08-1](7.08-1-confound-boundaries-survey.md). Entries stay lightly structured, so later tooling (for example a checkpoint loader that warns when a checkpoint predates a recorded boundary) can parse them.

## 8. What is guarded, and what is not

| Surface | Status | Mechanism |
|---|---|---|
| Obs content, per occupied config point | guarded | obs goldens |
| Targets/labels, per variant | guarded | targets goldens |
| Live vs training obs paths | guarded (pre-existing) | parity test in eval-tools |
| Fixture production chain (parser, writers, sim as executed) | guarded, late in build | layer-1 goldens |
| Frame-assembly seam (variant dispatch, key emission, tensor wraps) | not guarded, by choice | none |
| Default values of config knobs | not guarded, by choice | boundary record only (E1) |
| Loss functions | open | none |
| Metric definitions / aggregation | open | none |
| Dataset sampling / filtering | open | none |
| Eval protocol beyond the frozen map set | partial | frozen eval-map-set |
| Forward semantics (same shapes) | deferred | forward goldens (7.09-1) |

A green golden run means "no behavior change in what these fixtures execute", not "behavior unchanged everywhere". The open rows above are the difference.

## 9. Before and during the build

**Pre-build items** (three):

1. The 6.18 trail repair and the stale-96-channel sweep, detailed in 7.10-2 §9. This item also carries the capture-seam documentation: at a capture tick the frame mixes two tick conventions (`opp_captured_by` flips at the event tick while the board still shows the pre-event state). The sweep documents it as the known convention, to be revisited after the cut. A golden freezes it as-is, and a later fix would be loud and correctly recorded.
2. The event-class checklist, re-derived from the code.
3. The size-and-runtime probe: compressed size of a realistic fixture's references and per-fixture walk time. First build step, and at the project's remaining horizon (roughly six months of work) it is a measurement rather than a gate.

**Budgets** are sanity checks at the current scale and horizon, though the size-budget test still ships (ceilings as tests, not intentions). The recurring cost to watch is re-bless pack growth: every obs change re-blesses all obs references, and compressed npz barely delta-compresses in git.

**Runtime**: the suite must stay in the fast tier, because commit-time firing is the system's point. If the probe says it's needed, the knobs: cap registered perspectives per fixture, and truncate fixtures at selection time.

**Small open items**:

- Per-frame hashes in the stats layer (§5).
- The no-toys call is reversible if early fires demand scripted ground truth (§4).
- The freeze-time asserts may be trimmed or dropped (§4). *Update: [7.12-4 §2](7.12-4-event-class-checklist.md) revises this posture: comprehensive codified tags ship with the build, and trimming is a fallback rather than an equal-weight outcome.*
- n=20 checkpoint support belongs to route-1 (§6).
- Loss/metrics goldens remain the open surface (§8).
