# Checkpoint-config refactor — progress through 2026-07-04

*Date: 2026-07-04. The narrative record of the checkpoint-config refactor, from its start on 2026-06-27 through today: why the work exists, what chunk-1 built, and how it landed. The open-item inventory and the options for what comes next are deliberately excluded — they belong to the planning step.*

## 1. Why this refactor

Before this work, a checkpoint could not say what trained it. The `.pt` file recorded at most the architecture. The rest of the recipe — loss weights, learning rate, seed, data paths — lived only in the run directory's `args.json` sidecar, so a bare checkpoint had no authoritative config.

The sharper problem was silent drift. When a config field is added and an old checkpoint lacks it, the load path fills the field from the live default. Nothing fails, and the reconstructed model is quietly different from the model that was trained. Config shape changes arrive at roughly eighteen per month, mostly from unrelated work, so this was a standing hazard rather than a corner case.

The stakes come from the project's core workflow. Eval sweeps load weeks-old checkpoints beside fresh ones and compare them. Silent drift corrupts exactly that comparison.

The design work behind the refactor ([6.26-5](../2026-06/6.26-5-checkpoint-config-synthesis.md)) splits checkpoint faithfulness into two axes. *Shape* asks whether the stored config has the current field structure. *Behavior* asks whether current code reproduces what the checkpoint actually did. Behavior is the larger and mostly unsolved axis. Chunk-1 deliberately builds the shape axis alone, cut so that it bets on none of the open behavior-axis questions.

## 2. Where things stand

Chunk-1 is complete. A fresh-perspective review examined it on 2026-07-04, and its follow-ups are closed (§7). Concretely:

- Training runs write self-describing v1 checkpoints.
- `load_checkpoint` is the single loader. It reads both v1 and legacy checkpoints, and it migrates a stored config to the current shape before construction.
- The v1 key-set is frozen. A config-shape change without a matching version bump now fails a test, instead of silently defaulting fields on old checkpoints.

The behavior axis is untouched, by design. Also still open: chunk-2 (the `BCModel` re-scope), the v0→v1 normalizer, resume rewiring, and the sidecar rename.

The work spans 2026-06-27 to 2026-07-04 on branch `ckpt-config-refactor`, based on `ckpt-config-design-work`.

## 3. The v1 format

A v1 checkpoint is a seven-key dict:

| key | contents |
|---|---|
| `model` / `optim` / `scaler` | `state_dict`s — the runtime state |
| `epoch` | training progress |
| `in_ch` | input-channel checksum |
| `config` | the stored config block: `asdict(TrainConfig)` plus `config_version` |
| `code_sha` | git SHA of the training code, captured at launch |

- The config block is self-describing: `config_version` lives inside it, so the block can be interpreted on its own.
- Every checkpoint load uses `torch.load(weights_only=True)`. That rejects `Path` objects, so the block's `Path` fields are stored as strings and re-wrapped on read.
- The three stamps sit on separate axes: `config_version` for config shape, `code_sha` for code provenance, `in_ch` as a narrow integrity check. A fourth stamp, `arch_version`, was deliberately not reserved — it belongs to the behavior axis and arrives with it.
- A checkpoint without a config block is v0. The legacy read path serves those unchanged.

The layout landed exactly as designed (6.27-1 §2, confirmed in the review).

## 4. What was built

Five pieces, in rough build order. The module homes and the structural decisions behind them are recorded in the working doc ([6.27-3](../2026-06/6.27-3-checkpoint-config-working-doc.md) §2); this section stays at the level of what exists.

**The read side.** `load_checkpoint`, in the new `bc/storage/checkpoint.py`, is the single loader. It returns a `ConfiguredModel`: the model plus the full `TrainConfig` when the checkpoint carries one, or `None` for a legacy file. One discriminator routes between the two arms, and the legacy arm delegates to the old reconstruction unchanged. `build_model` is the single construction seam, shared by the loader and fresh training runs. The old `load_bc_model` is deleted, every load site in the repo was rewired onto the new loader, and the one dead consumer script was archived. The reshape required one correctness fix: `is_arch_bearing`, the predicate behind the inference model-key and cache behavior, learned the v1 form. The fix is additive, and tests lock the v0 answers in place.

**The config layer.** The new `bc/config` package owns the stored config block in both directions: `resolve_config` reads it, `serialize_config` writes it. The package also holds the migrate-once dispatch and the `Path` serde. The migration chain is empty at v1 — the machinery exists so the first real shape change has somewhere to land. The package is torch-free in what it touches (dicts, never tensors) but not yet in what it imports. Removing that import edge is a recorded follow-up.

**The writer and provenance.** `TrainingState` now carries the config and `code_sha` it was initialized from, and `save()` emits the v1 layout. Serialization is split: the training state produces its runtime dict, and the storage layer wraps it with the format. `code_sha` is captured at the launch site, because the cloud remote ships source without `.git`.

**Two additions from the review** (2026-07-04). First, the envelope/block boundary: the storage module owns the `.pt`'s top-level layout and treats the config block as opaque, while `bc/config` owns the block's contents. The planned v0→v1 normalizer is the one deliberate exception — v0's config material is spread across the file and the sidecar, so assembling a block requires reading both. Second, the key-set freeze and its guards: `config_schema/v1.json` records the v1 key-set, frozen at a moment verified correct. Tests now enforce the versioning contract: the stored shape must match the frozen key-set, every stamped version must have its migration, and every config field type must survive the `weights_only` load. Heavier bump tooling stays deferred ([6.24-4](../2026-06/6.24-4-checkpoint-config-versioning-design.md)).

**The strangler state.** The old `bc/checkpoint.py` was not rewritten. It keeps only the legacy reconstruction, the new storage module delegates to it, and it shrinks as logic moves out. Its header marks it superseded.

## 5. Did it work

The affected test suites pass: 44 tests across six files, re-run on 2026-07-04. An end-to-end smoke at the writer flip confirmed the real path — a local training run wrote a v1 checkpoint, and `load_checkpoint` reconstructed the model, arch, and full config from it. The smoke also surfaced a pre-existing crash in the FLOPs measurement, fixed on the branch. The smoke has not been re-run since.

Four surfaces remain untested: the cloud `code_sha` path, resume end-to-end against a v1 parent, elim-head configs through the round trip, and v0 and v1 checkpoints loaded in one process. They are recorded in the working doc (6.27-3 §7).

## 6. How chunk-1 landed

The build tracked the design. Where it deviated — a few names and homes, and one dropped abstraction — the deviations are documented in the working doc rather than left silent.

The strangler approach held. The indirection chunk-2 needs is already in place, so the coming storage flip won't touch callers a second time. The roughly ten sites that still read config off bare models are chunk-2's expected blast radius, not a surprise. The groundwork for the v0→v1 normalizer is similarly isolated and tagged in code.

The guardrail removes the time pressure that shaped the original sequencing. Config churn from other work — the eighteen shape changes a month — now fails a test instead of drifting silently.

The main payoff is real but not yet collected. Every v1 checkpoint carries the full training recipe, and nothing reads it yet. The first consumer — resume-from-checkpoint, or folding out the model-key re-read — starts collecting it.

The design got simpler on contact with the code. Two positions from the synthesis doc were reversed, both documented: the `LoadPlan` union was dropped, and no `arch_version` slot was reserved.

Three forward-looking notes, held loosely since the options analysis belongs to planning. The next increment probably wants to include a first consumer of the stored recipe. The old sequencing lean — guardrail first — is now satisfied, so the remaining order needs re-deriving rather than inheriting. And the gating decisions in [6.26-7](../2026-06/6.26-7-checkpoint-config-critical-questions.md) gate the broader behavior-axis path, not the next increment.

## 7. Process notes

A fresh-perspective review examined the whole branch on 2026-07-04: the full diff, the live tree, and the test suites, checked against the design docs. It found no correctness bugs and confirmed the design conformance. Its material findings were about process. The one item the design had marked do-at-chunk-1-time — the key-set freeze — had slipped, and the working doc claimed refactor-note coverage the code did not yet have. Both were fixed the same day, along with a pass of small fixes and the two §4 additions. A handful of smaller items stay open, recorded in the review scratchpad ([7.04-2](7.04-2-ckpt-config-chunk-1-review-scratchpad.md)) for the planning pass.
