# Boundary-record legend — draft

*Updated: 2026-07-22. Status: draft. The reader-facing legend for boundary records, drafted during the goldens naming pass ([7.20-1](7.20-1-goldens-naming-pass.md)). At build time this text becomes the ledger's header (or a README beside the records, if each record gets its own file). Field list and wording are draft-grade until the build.*

---

Each entry records one boundary: a change to behavior-shaping code and the date it landed. Consult the ledger when comparing checkpoints or numbers from different dates: the impacts recorded here, crossed with what you are doing, give the verdict ([confounds-framework](../confounds-framework.md) §2 has the verdict table and is the full reference for everything below).

## Fields

- **description**: Short summary of the code change as a whole.
- **date**: The date it landed (the boundary date).
- **channels**: The changed channels, copied from regen's printed extent.
- **comparisons invalidated**: Which cross-date comparisons stop being valid.
- **recipe-change**: `yes` or `no` — did the change alter training-time code or config, so that training runs launched after it produce different weights? This is the only impact that does not create boundaries on its own. It is a happy path change that produces a new model without impacting previously trained models or their metrics (see `confounds-framework.md` and session note `7.20-1`). For this reason, it is separate from the "impacts by surface" list that follows.
- **impacts by surface**: The main content of the record. Each line names one modified surface and the impacts that modification produced. The labels are defined below.

## Surface labels

Short forms of the framework §1 rows:

`obs`, `live-path`, `model-forward`, `training-targets`, `loss-func`, `eval-protocol`, `model-shape`, `game-rules`

The ninth framework row, training-only code/config, has no label: a change there is a pure recipe-change, which creates no boundary, so it never appears in a record.

## Impact labels

The four boundary-creating impacts (recipe-change is recorded separately, in its own field above):

- `contract-break`: Old checkpoints now run against code that differs from what they trained with.
- `contract-repair`: A fix brought runtime back into line with training. The pre-fix era's numbers reflect the prior broken behavior.
- `metrics-change`: The ruler changed (metric definitions, training-target definitions, or the eval protocol). The same labeled numbers recorded before and after now measure different things. Cross-date comparisons need a re-measure.
- `mechanics-change`: The game the bot plays changed. This is rarely the game itself, more often our implementation of it (bug fixes in sim rules or in what information reaches the bot). Cross-date numbers describe different games, permanently.

## Writing a new entry

- List a surface when a change in that part of the system creates a boundary, as defined by the tests in framework §1.
- Code that is part of a surface doesn't always map cleanly to the on-disk file structure. This means the actual content of the change must be evaluated, rather than simply looking at the parent module name.
- Each mapping line in the record can be self-checked against its surface's row in the framework §1 table: the impacts listed should match that row's ✓s (minus any conditional cells that didn't apply to this change).

## Illustrative entries

The 2026-06-18 tick-seam fix, sketched in this format:

```
description             : alive/present tick seam fixed (death > t → death >= t)
date                    : 2026-06-18
channels                : none (targets-only change: alive mask, next_death)
comparisons invalidated : elim metrics and training curves across this date
recipe-change           : yes
impacts by surface      :
    training-targets -> metrics-change
```

A hypothetical second entry showing a multi-surface block (the framework §1's union-rule example, an ungated obs-channel addition):

```
description             : (hypothetical) new obs channels added, ungated
date                    : yyyy-mm-dd
channels                : channel 1, channel 2, etc (or "none")
comparisons invalidated : gameplay-eval and analysis numbers across the boundary
recipe-change           : yes
impacts by surface      :
    obs         -> contract-break, mechanics-change
    model-shape -> contract-break
```
