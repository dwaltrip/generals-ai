# Boundary-record legend — draft

*Updated: 2026-07-22. Status: draft. The reader-facing legend for boundary records, drafted during the goldens naming pass ([7.20-1](7.20-1-goldens-naming-pass.md)). At build time this text becomes the ledger's header (or a README beside the records, if each record gets its own file). Field list and wording are draft-grade until the build.*

---

Each entry records one boundary: a change to behavior-shaping code and the date it landed. Consult the ledger when comparing checkpoints or numbers from different dates. Full framework: [confounds-framework](../confounds-framework.md).

Fields:

- **description / date**: what changed, and the date it landed (the boundary date).
- **channels**: the changed channels, copied from regen's printed extent.
- **comparisons invalidated**: which cross-date comparisons stop being valid.
- **recipe-change**: `yes` or `no` — did the change alter training-time code or config, so that training runs launched after it produce different weights? This is the one impact that flags no hazard: it marks the part of the change that is clean, letting cross-boundary model differences be attributed to the recipe rather than misread as a confound. An explicit `no` carries information too: the training path was untouched. A recipe-change creates no boundary on its own. That is why it sits outside the mapping block below, and why a change whose only impact is a recipe-change (training-only code/config: learning rate, data mix) gets no record at all. Attribution for those works the same as for any training run: through the train config saved in the checkpoint itself (checkpoints are self-describing).
- **impacts by surface**: the classification. One line per surface whose output the change altered, producing the boundary this record describes — not every area the diff touched. Each line maps that surface to the impacts its change produced, and should reconcile with the surface's row in the framework §1 table: the impacts are that row's ✓s, minus any conditional cells that didn't apply to this change.
    - The surfaces, one or more of: `obs`, `live-path`, `model-forward`, `training-targets`, `loss-func`, `eval-protocol`, `model-shape`, `game-rules` — short forms of the framework §1 rows. The ninth row, training-only code/config, has no label (see the recipe-change field above).
    - The impacts, one or more per line:
        - `contract-break`: old checkpoints now run against code that differs from what they trained with. When the break comes from a shape change it is "loud": old checkpoints fail at `load_state_dict(strict=True)` instead of silently degrading. The mapping line marks this case as `contract-break (loud)`.
        - `contract-repair`: a fix brought runtime back into line with training. The pre-fix era's numbers carry the old broken behavior.
        - `metrics-change`: the ruler changed: metric definitions, training-target definitions, or the eval protocol. Numbers recorded before and after carry the same name but measure different things. Cross-date comparisons need a re-measure.
        - `mechanics-change`: the game the bot plays changed: rarely the game itself, more often our implementation of it (bug fixes in sim rules or in what information reaches the bot). Cross-date numbers describe different games, permanently.

Illustrative entry (the 2026-06-18 tick-seam fix, sketched in this format):

```
description             : alive/present tick seam fixed (death > t → death >= t)
date                    : 2026-06-18
channels                : none (targets-only change: alive mask, next_death)
comparisons invalidated : elim metrics and training curves across this date
recipe-change           : yes
impacts by surface      :
    training-targets -> metrics-change
```

A hypothetical second entry showing a multi-surface block (the framework §1's union-rule example, an ungated obs-channel addition):

```
description             : (hypothetical) new obs channels added, ungated
date                    : yyyy-mm-dd
channels                : channel 1, channel 2, etc (or "none")
comparisons invalidated : gameplay-eval and analysis numbers across the boundary
recipe-change           : yes
impacts by surface      :
    obs         -> contract-break, mechanics-change
    model-shape -> contract-break (loud)
```
