# Behavior-goldens first cut — scope revision and hash-based references

*Date: 2026-07-15. A revision of the first cut's goals, reference design, and scope, made after the size-and-runtime probe ([7.15-1](7.15-1-goldens-probe-results.md), cited throughout as the evidence). This is the next link in the design chain (7.10-2 → [7.12-1](7.12-1-behavior-goldens-first-cut-v2-overview.md) → this doc): where it conflicts with 7.12-1 or 7.10-2, this doc takes precedence, and 7.12-1 stays authoritative for everything §3 lists as unchanged. The initial set of pre-build items from 7.10-2 (items 1–4) is closed. Item 1 was applied on 7.13, item 2's checklist has had its first pass (the queued second pass is follow-up, not a gate), item 3 is the probe itself, and item 4 became moot with the no-toys call. The next build step is fixture selection.*

## 1. The reframe

Two anchors drove this revision.

**This is a hobby project with one developer.** The prior design accumulated support machinery sized for higher stakes and more hands: a curated frozen-frame layer, a dense per-frame statistics layer, staged automation for boundary records. The pre-build pause was the right moment to recalibrate, and this doc is that recalibration.

**Two scenarios describe what the system actually has to do.**

1. **An accidental behavior change**: a change was made that was not meant to affect behavior, and it did. What is needed is the most basic alarm. Knowing which channels are affected is enough to start debugging quickly. Coarse summary stats are a nice bonus.
2. **An intentional behavior change**: the golden test should fire the way we expect, and coarse summary stats provide a sanity check that the fire matches the intent.

If any of this proves insufficient during actual usage, we revisit and extend, guided by the concrete shortcoming. Every artifact dropped below can be revived additively: nothing structural has to be unwound to add a layer or a tool later. (For continuity: these two scenarios are 7.09-1's flow 3 and flow 2.)

The primary requirement is unchanged from 7.12-1 §1: detect behavior-affecting changes automatically, and enforce that each one is handled with a conscious decision and a durable record in the same commit.

The argument structure of this revision, stated once so the rest reads correctly: the scenario analysis is the load-bearing justification. The dropped artifacts served diagnostic use cases that are themselves speculative (maybe never needed, rarely needed, or needed in some form whose details are unclear). The cheaper-alternatives mapping in §5 is secondary reassurance for whichever of those needs ever materialize. It is not a claim that every old capability was relocated.

One taxonomy used throughout: **deferred** means a named revival trigger exists and we expect to build the item when it fires. **Dropped** means no trigger: the item is superseded or has no consumer, and reviving it would need a new reason. Because revival is additive and cheap, dropping loses no option value.

## 2. The reference design

**Sharpening the definition of "fixture":**

A fixture is a (source replay, perspective) pair, as the replay itself is not enough to run a golden test. A fixture consists of the npz files for the source replay along with one selected perspective. Taking multiple perspectives from a single replay gives multiple fixtures, which share the npz files.

Earlier docs (and the probe record) use "fixture" for the replay alone, so their per-fixture counts and costs are for each replay, not per (replay, perspective) pair. Most of those counts assumed a single perspective per replay.

Fixture selection will involve selecting both the source replays and the relevant perspectives for each replay.

The frozen-frame and stats-layer reference format of 7.10-2 §4 is replaced. Per (fixture, config point), the committed references are now:

- **Per-frame hashes** (`[T]` uint64): each walked frame's exact bytes hashed to 8 bytes. This is the detector: exact detection at every walked tick, and the first mismatching tick localizes when behavior diverged. About 4.5 KiB.
- **Per-channel hashes** (`[C]` uint64): each channel's full history (`[T, 32, 32]`) hashed once. Purely attributional: at fire time it names the affected channels, which is the single most useful pointer toward the responsible code. About 0.9 KiB. Detection is fully carried by the frame hashes: a change is never visible here without being visible there.
- **The channel summary** (`channel-summary.json`, the artifact 7.10-2/7.12-1 called the sidecar, renamed to reflect a promoted role): per-channel whole-game aggregate stats, the channel arithmetic-class table, and hash provenance (algorithm, canonical serialization). It is the human-diffable content of a bless commit (the anti-rubber-stamp mechanism) and the only standing magnitude information at fire time. A few KB of JSON, which git diffs and deltas well.
- **Targets references**: unchanged in form, full arrays at all frames in as-emitted dtypes, including the legality-mask stack. Targets fires therefore come with exact per-value diffs, which matters because the elim arc's frequent expected fires are targets fires.

A fire report reads directly off these: which ticks changed (frame hashes), which channels changed (channel hashes), and how the channel aggregates moved (channel summary). The tick and channel sets are marginals rather than joint pairs, which is equivalent in practice for a single-cause fire and is accepted for the rare overlapping-cause case (the rerun recipe below covers it).

Mechanics worth pinning:

- Hash equality is **byte** equality over canonical bytes (C-order, the config's emitted dtype). This is marginally stricter than value equality: a `-0.0` where a `0.0` was flips a hash even though the floats compare equal. That is treated as a feature (it is a bit-level output change), noted here so a future investigation is not surprised. NaN is moot: the check phase asserts finiteness.
- The dtype rule carries over from 7.10-2 §4: hash what the config emits (fp16 for the default point, fp32 for legacy). The emitted bytes are the contract training consumes.
- The probe used blake2b with an 8-byte digest, and sha256 may be faster on this machine (hardware support). The choice is made at build time and recorded in the channel summary either way.
- Comparison policy: exact equality on the pinned platform (the 7.10-2 standard, now implemented by hashes). The M1 is authoritative. The environment test (§4) enforces the pinning: the suite fails when the running environment differs from the blessed stamp. 7.09-1's off-platform tolerance mode is retired from this cut, since tolerance comparison needs stored values we no longer keep. If a second standing environment ever needs the suite, three options are documented and cheap to reach: compare only the exact-class channels (the ~94 non-log channels hash identically across platforms), bless per-platform hash sets (kilobytes each), or store raw values for the 16 log-scaled channels and tolerance-compare only those. 7.15-1 §7's measurements say the eventual cost of any of these is small.
- One alternative was considered and rejected: hashing a coarsened (quantized) copy of the obs to buy cross-platform robustness. Quantization is a tolerance in disguise: values near grid boundaries still flip under tiny jitter (making flips negligibly rare needs grids coarser than real changes we care about), and on the pinned platform it only lowers the detection floor, for nothing.

The numbers that carried the decision (all from 7.15-1):

| quantity | value |
|---|---|
| standing reference bytes per fixture-config (hashes + summary) | ~10 KiB |
| pack growth per full obs re-bless, 30-fixture basis | ~200 KiB |
| suite runtime, 30 fixtures + 3 legacy | ~10–20s including hashing |
| the per-frame-per-channel hash alternative, per full re-bless | ~15 MiB |
| the dense stats layer, standing npz / per full re-bless | ~2.2 MiB / ~2.2 MiB |
| frozen frames (designed pick), standing | 1.67 MiB |

The frozen-frames row makes a point worth keeping: its bytes were never the problem. What the hash design eliminates is the pick rule's job of predicting, indefinitely, where future changes will manifest.

Robustness basis, briefly: walk determinism is demonstrated end-to-end at byte resolution on this platform (7.15-1 §6), hash collision odds are negligible by arithmetic (about 2⁻⁶⁴ per changed frame), and the "does the mechanism actually fire" gap is closed by a permanent mutation test (§4). The environment test (§4) guards the premise that the suite runs under the same environment where the references were blessed.

**What the hashes do not cover.**

The golden tests can only detect behavior changes in code paths that execute. Not every game of generals will hit every behavioral path. This means that full coverage depends on careful fixture selection.

As every tick is compared, every event or state change a fixture contains (including obs-memory changes that can span arbitrary tick ranges) is guarded in full. Most checklist classes appear in any typical 8-player game and therefore need no targeting. Selection concentrates on the remainder: the events and state changes that are less common. Neutralize events were the first measured example (1 of 5 sampled games, 7.15-1 §8). The coverage instruments are the event-class checklist (7.12-4) and the selection tooling built against it (§4).

One mitigation became cheap with this design:

A fixture now roughly costs only 100 to 250 KiB on disk and about 0.25s of test suite runtime. If we are struggling to get coverage for all behavior paths, we have breathing room to add more fixtures. We can comfortably exceed the estimated budgets from previous sketches of ~5 for the initial set and ~30 for the project lifespan number. Caveat: the amount of "breathing room" margin hasn't been worked out (it would need further analysis and discussion). Here we just note that it exists.

## 3. What stands unchanged from 7.12-1

Brief statements with pointers. 7.12-1 remains the authority for these.

- **Goal and the definition of "handled"** (§1).
- **The core principle and the config leg** (§2): everything frozen except the guarded code. The config leg in full: stored config dicts with every field explicit, the strict-keys assert, the small `TargetsConfig`, the legacy-config equality assert.
- **Two-layer architecture and the torch-free test path** (§3). Layer-1 fixture goldens stay in the cut, sequenced near the end of the build. New flag: they are the first-trim candidate if the build drags, and if trimmed, their revival trigger is the first sim or parser change.
- **Fixtures from the corpus, the realism argument, and the no-toys call** (§4). Two constraints added by the probe's findings (7.15-1 §8): fixtures must pass the training eligibility filter (8 players, board ≤ 32, T ≤ 2000), and the selection query must target neutralize events explicitly. (The optional phantom-slot fixture, if built, is a deliberate exception to the player-count leg, §8.) One item from §4 is not carried: the freeze-time tags are dropped (see "Dropped" below).
- **Registry, guard rules, coverage forcing, the fixture-by-config matrix, and the defaults-not-guarded caveat** (§6).
- **The boundary record lifecycle and the ledger** (§7): fire → regen opens a record → the blocking test refuses to pass without a filled record in the same commit → one reviewable commit. Class-first template, standalone chronological ledger (one file vs a file per record is a build-time packaging choice). One semantics revision to §7: records are disposable until the work lands, and append-only after. Landing, not committing, is the commitment point (the working-style pattern below is why). Two trims: regen no longer pre-fills magnitudes (it prints the fire's extent, and the author writes the five-line entry by hand), and seeding the ledger with the three known May–June boundaries moves out of the build into a follow-up task.
- **The guarded/not-guarded table** (§8), with hashes as the reference mechanism. Its closing caveat (green means "no behavior change in what these fixtures execute", not "behavior unchanged everywhere") is now the system's main residual exposure and should be read that way.
- **The flow inventory**: 7.09-1's flows 0 (normal work), 1, 2, 3, and 6 (retire a variant) survive this revision intact. Flow 1 (adding a gated variant) gets slightly stronger: existing config points staying green is now byte-verified, and the new point still fails as unblessed until its first regen. Flows 4 and 5 stay deferred as before.

One working-style pattern on the record mechanism, made explicit because the elim arc will fire targets goldens frequently and by design: the polished record is written once per landed batch of work, not per mini-experiment. Completing a record per regen would produce entries describing increments the ledger has no use for, so during branch iteration each regen keeps a placeholder record filled instead (one line naming the work in progress). That keeps every commit on the branch green, and an unexpected fire during iteration still stands out. At land time the batch collapses into one clean boundary: restore the references to their branch-point state, delete the placeholder, re-bless once against the final code, and write the real entry from that fire report. The land-time fire shows the batch's whole extent against the true baseline, so the entry is written from evidence rather than reconstructed from the increments. The step-by-step recipe goes in the goldens workflow doc (§4).

## 4. Shipped in the first cut

- **Fixture production and the walk core.** Fixture production and the frame-hash builder are promoted from the probe modules (`goldens_probe/fixtures.py` and `layers.py`). The walk core's shape is decided by the walk-seam discussion (§8): the probe's `walk.py` promoted as goldens-side code, or the walk logic factored out of `dataset.py` as shared infrastructure.
- **The initial fixture set**, selected against the 7.12-4 checklist by corpus query, with the eligibility gate and neutralize targeting. Count decided at selection time (§2: the ceiling is soft).
- **The selection helper module**: the checklist's classes as named predicates over the parsed npz, reusing `compute_visibility` for the per-perspective conditions. The fixture-selection tooling uses it to query candidates and to report what the chosen set covers, with uncovered classes recorded in the selection session's notes. Selection-time only: nothing in the test path reads it.
- **Reference writers**: frame hashes, per-channel hashes, the channel summary, targets.
- **The registry and config discipline**, per 7.12-1 §6.
- **The regen tool**, two commands (produce-fixtures, regen), each a single straight-through pass, printing the fire extent and requiring a ledger entry via the blocking test. No diff-against tool in this cut (§6).
- **The ledger and the blocking test** (~10 lines). Entries are hand-written: date, surface, the changed channels (copied from regen's printed extent), one line of what changed, effect class, and the class's one or two judgment answers.
    - We expect the changed-channel list to be an entry's highest-signal field. It lets a reader quickly assess what the entry was about.
- **A permanent mutation test**: perturb an in-memory copy of a walked frame and assert the hash comparison fires. This is the standing proof that the tripwire mechanism works, guarding against harness rot, at millisecond cost. (The rest of the input-mutation matrix stays deferred.)
- **Two structural tests**: the size-budget test (ceilings as tests) and the every-gated-channel-group-guarded test.
- **The environment record and its test**: a small committed file beside the registry, written by regen at bless time.
    - Three fields are asserted: the uv.lock hash, the Python interpreter version, and the platform arch.
    - Additional context is recorded but not asserted: the numpy version, the OS version, and the blessing machine's name.
    - The environment test compares the running environment against the asserted fields and fails on any difference, with a message pointing at the §6 procedure. The lock hash deliberately covers every dependency, not just the walk-relevant ones: a curated subset would require manual syncing.
        - The trade is that unrelated dependency bumps will also fire the test. But §6's green-vs-fire handling keeps those cheap: a green run needs only a one-line re-stamp.
- **The goldens workflow doc** (evergreen, written after the naming pass so it uses the final vocabulary): what a fire means and which flow applies, the branch-iteration and land-ritual pattern (§3), the environment procedure (§6), and the rerun recipe for exact old values (check out the old ref in a worktree, run the walk, diff the flagged channels: deterministic and about 0.2s per perspective). The AGENTS.md note shrinks to a pointer to it.
- **Layer-1 goldens**, near the end of the build (§3).

## 5. Dropped

Each dropped item with its reasoning. Under §1's argument structure: these served speculative diagnostic use cases, and the scenarios do not ask for them.

### Frozen frames, the deterministic pick rule, and its review

The frame hashes detect at every walked tick, which ends the pick rule's defining job: predicting where future changes will manifest so the right frames get frozen. That open-ended predictive burden was the real cost of the arrangement (7.15-1 shows the bytes were trivial either way). The diagnostic roles frozen frames played are covered in the mapping below.

### The obs-channel sweep

Its two consumers (7.12-4 §8) fared differently:

- Reviewing the frozen-frame pick rule died with the pick rule.
- Completing the condition-class list (enumerating what the memory channels respond to, so fixture selection can cover those histories) is weakened rather than dead. Full-game walks compared at every tick cover much of it for free: every fixture contains the buffer-fill boundary, and long fog spans are near-certain in real 8-player games.

The known gaps are handled without the sweep: a long fog span and a witnessed general capture go on the checklist, and the BFS-after-captured-general behavior stays a known unverified note. The sweep's other function, finding unknown gaps, is still needed to have confidence in the robustness of the obs goldens. Coverage now rests entirely on fixture selection (§2). And the condition side of the checklist still needs to be resolved.

During the selection work, we can meet these needs with a scoped-down skim: read the stateful channel code and enumerate condition classes, without the per-channel equivalence-class analysis or the pick-rule review. Its deliverable is additions to the rare-class list (§2): conditions not found in a typical game.

### Freeze-time tag asserts and the comprehensive-tags posture (7.12-4 §2)

The tags were to ship as standing asserts: every fixture's declared classes checked at fixture production and re-checked at schema-migration regen, with the full checklist codified. Both standing checks lost their consumers. The production-time check (the selection contains what it claims) happens at selection instead, through the same predicates the selection query runs. The regen-time check guarded against coverage changing when fixtures are rebuilt. But a fixture rebuilds from its own committed replay by a deterministic parse, so coverage can only change there if parser behavior changed, and that event is already made loud by the layer-1 goldens and the migration two-step. What survives is the selection helper module (§4). The checklist remains a full inventory, selection targets its rare classes (§2), and each fixture's purpose stays documented as a note in its registry entry.

### The dense `[T, C, n_stats]` stats layer

Its consumers were the speculative ones: instant magnitude without a rerun, and pre-filled record fields. The channel summary covers the coarse-magnitude need, the rerun recipe covers the exact need, and neither scenario asks for more. Not deferred, because the layer as designed has no revival trigger. The conditional future artifact is different and smaller (the log-channel value store, §6).

### Per-frame-per-channel hashes (`[T, C]`)

This approach costs about 15 MiB of incompressible pack growth per full re-bless (7.15-1 §5). The 15 MiB cost alone makes this not viable. Additionally, one of the main benefits was channel attribution, which we can get with the `[C]` layer alone for only 1 KiB.

### Record automation and magnitude pre-fill

A solo dev writes five lines. Automation was already gated on fires demonstrating a need (7.12-1 §7), and that gate stays.

### The runtime knobs

Specifically, we are dropping knobs for perspective caps, fixture truncation, and a fast/full split. The probe's run times (7.15-1 §3, extrapolated in §2's table) put the full suite at roughly 10 to 20 seconds, comfortably inside the fast tier, so we can just run with everything "always on".

### The 2-frame anchor set

An ad-hoc idea added to the probe mid-session: freeze just the first and last frames as exact exemplars. It was discarded once its roles moved to the mutation test and the env-upgrade dump. Its stronger successor, a small programmatically selected frozen-frame set, sits on the extension ladder (§7).

---

**The cheaper-alternatives mapping.** This table is the secondary reassurance described in §1: for each kind of information the dropped artifacts provided, it names where that information now comes from if a need materializes.

| information | source now | cost model |
|---|---|---|
| that something changed, and at which ticks | frame hashes | standing, ~5 KiB |
| which channels changed | per-channel hashes | standing, ~1 KiB |
| coarse magnitude, sanity check | channel summary | standing, few KB |
| exact old values, per-cell diffs | rerun the old ref's walk | on demand, recipe in the workflow doc (§4) |
| review integrity at a bless commit | channel-summary diff + the record's changed-channel list | standing |
| env-upgrade ground truth | old-env full-array dump at upgrade time | on demand, procedure in §6 |

The on-demand rows are argued but unexercised until the first real fire. That is acceptable because extension is additive and the first shortcoming will name what is actually missing.

## 6. Deferred

| item | revival trigger | interim covering |
|---|---|---|
| diff-against-ref tool | first fire needing per-cell detail | the rerun recipe |
| off-platform support (exact-class subset, per-platform bless, or log-channel value store) | a second standing environment runs the suite | the environment test (§4) fails the suite on any other environment |
| environment-upgrade handling | the upgrade itself (manual at first occurrence, per 7.09-1 flow 4) | the dump obligation below |
| fixture-schema migration | a sim-dict schema change | the manual two-step (7.10-2 §7) |
| ledger seeding (the three retro May–June boundaries) | one of the first sessions revisiting the first-cut code after it's implemented | ledger starts empty of retro entries |
| input-mutation matrix beyond the permanent mutation test | fires demonstrating a need | the mutation test |
| programmatic frozen-frame set | see the extension ladder (§7) | hashes + channel summary |
| forward goldens, hash-fill, loss/metrics goldens, rename bridge | unchanged, 7.09-1 territory | out of this cut |

While environment-upgrade handling is deferred for the first cut, its first step is fixed as: **retiring the authoritative environment must start with a full-array dump of every fixture's walk on the old environment.** Retirement covers any change to the environment whose walk produces the blessed bytes: a library upgrade in the walk path, or moving bless authority to a new machine. The dump is the ground truth for separating numerical churn from real behavior changes across the boundary. It costs no committed bytes, and it can only be produced while the old environment exists. A skipped dump is recoverable after a library bump: checking out the pre-bump ref lets uv rebuild the old environment from its lockfile, as long as the machine itself hasn't changed. Moving off the machine has no such recovery, which is why the dump runs before the old machine is retired.

The environment test (§4) makes the boundary loud: it fails on the first run under any environment that differs from the blessed stamp, whatever the reason for the difference (a dependency bump, a Python upgrade, or a new machine such as a second dev box or a CI runner). What to do next depends on what the goldens say in the same run:

- **The goldens are green.** The environment changed and no reference byte did, so the references remain valid and no boundary occurred. Re-stamp the environment record in a one-line commit.
- **The goldens fire as well.** This is a real environment boundary. The deferred environment-upgrade procedure above applies, manually at this first occurrence: produce the old-environment dump, use it to separate numerical churn from behavior changes, and re-bless with one boundary record once the diff is understood.

## 7. The extension ladder

If hashes plus the channel summary prove insufficient in real use, the escalation rungs, in order:

1. **The fire-report event annotation**: annotate each flagged tick with nearby events from the fixture's event arrays (already in the npz), so a fire reads as "capture-adjacent" rather than an anonymous tick. A formatting step in the fire report, no new storage. Trigger: fires where interpreting the flagged ticks meant looking up the event arrays by hand.
2. **The diff-against tool**: exact per-cell diffs against any git ref, on demand, no new storage. Trigger: the rerun recipe gets used enough to be worth automating.
3. **A small programmatically selected frozen-frame set**: automated selection over the fixture's events and conditions (not hand-picked, and better than first-and-last). Trigger: repeated fires where marginal attribution plus the summary were not enough to orient.
4. **The log-channel value store or per-platform blessed hashes**: only if the shortcoming is cross-platform rather than diagnostic depth.

Each rung waits for a concrete observed shortcoming, per §1's extension principle.

## 8. Open items and next step

- The naming pass: the effect-class codes (E1/E2/E3) and the channel-class labels read as too dense. The concepts stay, and the vocabulary gets a friendlier pass (next session).
- The channel summary's contents: which aggregates per channel class. Needs its own short discussion. The starting material: for binary channels, nnz, flip counts against the previous frame, and center of mass (all three carry information a bag-of-values stat cannot). Distributional stats (mean, max, percentiles) are reserved for the channels that have distributions, meaning the log-scaled ones.
- The walk-composition seam, to settle in a design discussion before the build: it directly gates only the walk-core step, but an early decision reduces the risk of architecture churn. The prototype walk from the probe (`packages/training/scripts/goldens_probe`) uses its own copy of the walk logic from `IterableDataset._walk`. We intended to promote the probe's walk into infra for the actual golden tests. However, a naive duplication is problematic. If the dataset's walk code changes, the golden test is no longer faithfully testing what it claims. Candidate resolutions:
    - Refactor the battle-tested walk logic out of `dataset.py` into shared infrastructure that the golden tests consume. This removes the seam. A decoupled walk also has a potential third consumer: the frozen-probe analysis toolkit (`packages/training/training/analysis/probes`). This exact refactoring question came up when that was built (and was deferred).
    - Add a dataset-vs-goldens parity test in the torch tier, the same move as the existing live-vs-training parity test.
    - Accept the seam and record it in the guarded/not-guarded table.
- The initial fixture count, decided at selection time against the checklist (the ceiling is soft, §2).
- The residual checklist classes for 7.12-4 (long fog span, witnessed general capture), the scoped-down channel skim at selection time (§5), and the queued second comprehensiveness pass on the checklist.
- Phantom-slot coverage, resolved to obs-only and optional. At implementation, either pad the goldens walk's `initial_generals` (the live path's existing `pad_initial_generals` seam) so a sub-8-player fixture walks, or drop the class entirely (it is a nice-to-have). Targets get no phantom coverage either way: the target functions have never run on sub-8 inputs, and the `is_real` branch stays a known unexercised note.
- The ledger's packaging (one file vs a file per record), decided at build time (§3).
- The ledger-seeding follow-up task (§6).

**Next steps**: the second set of pre-build items — the naming pass, the channel-summary contents, and the walk-seam discussion (sequence in [7.15-3](7.15-3-goldens-handoff.md)) — then the build per §4's ships list. Within the build, fixture selection (against the 7.12-4 checklist via corpus query) is deferrable to near the end: until it runs, the build tests against randomly picked, eligibility-gated fixtures whose references are throwaway and stay uncommitted.
