# Behavior-goldens first cut — scope revision and hash-based references

*Date: 2026-07-15. A revision of the first cut's goals, reference design, and scope, made after the size-and-runtime probe ([7.15-1](7.15-1-goldens-probe-results.md), cited throughout as the evidence). This is the next link in the design chain (7.10-2 → [7.12-1](7.12-1-behavior-goldens-first-cut-v2-overview.md) → this doc): where it conflicts with 7.12-1 or 7.10-2, this doc takes precedence, and 7.12-1 stays authoritative for everything §3 lists as unchanged. Pre-build status: all four pre-build items are closed (item 1 applied 7.13, item 2's checklist has its first pass with a second pass queued, item 3 is the probe, item 4 became moot with the no-toys call). The next build step is fixture selection.*

## 1. The reframe

Two anchors drove this revision.

**This is a hobby project with one developer.** The prior design accumulated support machinery sized for higher stakes and more hands: a curated frozen-frame layer, a dense per-frame statistics layer, staged automation for boundary records. The pre-build pause was the right moment to recalibrate, and this doc is that recalibration.

**Two scenarios describe what the system actually has to do.**

1. **An accidental behavior change**: a change was made that was not meant to affect behavior, and it did. What is needed is the most basic alarm. Knowing which channels are affected is enough to start debugging quickly. Coarse summary stats are a nice bonus.
2. **An intentional behavior change**: the golden test should fire the way we expect, and coarse summary stats provide a sanity check that the fire matches the intent.

If any of this proves insufficient during actual usage, we revisit and extend, guided by the concrete shortcoming. Every artifact dropped below is additive to revive: nothing structural has to be unwound to add a layer or a tool later. (For continuity: these two scenarios are 7.09-1's flow 3 and flow 2.)

The primary requirement is unchanged from 7.12-1 §1: detect behavior-affecting changes automatically, and enforce that each one is handled with a conscious decision and a durable record in the same commit.

The argument structure of this revision, stated once so the rest reads correctly: the scenario analysis is the load-bearing justification. The dropped artifacts served diagnostic use cases that are themselves speculative (maybe never needed, rarely or barely needed, or needed in some form whose details are unclear). The cheaper-alternatives mapping in §5 is secondary reassurance for whichever of those needs ever materialize. It is not a claim that every old capability was relocated.

One taxonomy used throughout: **deferred** means a named revival trigger exists and we expect to build the item when it fires. **Dropped** means no trigger: the item is superseded or has no consumer, and reviving it would need a new reason. Because revival is additive and cheap, dropping loses no option value.

## 2. The reference design

The frozen-frame and stats-layer reference format of 7.10-2 §4 is replaced. Per (fixture, config point), the committed references are now:

- **Per-frame hashes** (`[T]` uint64): each walked frame's exact bytes hashed to 8 bytes. This is the detector: exact detection at every walked tick, and the first mismatching tick localizes when behavior diverged. About 4.5 KiB per fixture.
- **Per-channel hashes** (`[C]` uint64): each channel's full history (`[T, 32, 32]`) hashed once. Purely attributional: at fire time it names the affected channels, which is the single most useful pointer toward the responsible code. About 0.9 KiB. Detection is fully carried by the frame hashes: a change is never visible here without being visible there.
- **The channel summary** (`channel-summary.json`, the artifact 7.10-2/7.12-1 called the sidecar, renamed to reflect a promoted role): per-channel whole-game aggregate stats, the channel arithmetic-class table, and hash provenance (algorithm, canonical serialization). It is the human-diffable content of a bless commit (the anti-rubber-stamp mechanism) and the only standing magnitude information at fire time. A few KB of JSON, which git diffs and deltas well.
- **Targets references**: unchanged in form, full arrays at all frames in as-emitted dtypes, including the legality-mask stack. Targets fires therefore come with exact per-value diffs, which matters because the elim arc's frequent expected fires are targets fires.

A fire report reads directly off these: which ticks changed (frame hashes), which channels changed (channel hashes), and how the channel aggregates moved (channel summary). The tick and channel sets are marginals rather than joint pairs, which is equivalent in practice for a single-cause fire and is accepted for the rare overlapping-cause case (the rerun recipe below covers it).

Mechanics worth pinning:

- Hash equality is **byte** equality over canonical bytes (C-order, the config's emitted dtype). This is marginally stricter than value equality: a `-0.0` where a `0.0` was flips a hash even though the floats compare equal. That is treated as a feature (it is a bit-level output change), noted here so a future investigation is not surprised. NaN is moot: the check phase asserts finiteness.
- The dtype rule carries over from 7.10-2 §4: hash what the config emits (fp16 for the default point, fp32 for legacy). The emitted bytes are the contract training consumes.
- The probe used blake2b with an 8-byte digest, and sha256 may be faster on this machine (hardware support). The choice is made at build time and recorded in the channel summary either way.
- Comparison policy: exact equality on the pinned platform, unchanged in standard, now implemented by hashes. The M1 is authoritative. Off-platform runs skip the goldens: 7.09-1's off-platform tolerance mode is retired from this cut, since tolerance comparison needs stored values we no longer keep. If a second standing environment ever needs the suite, three options are documented and cheap to reach: compare only the exact-class channels (the ~94 non-log channels hash identically across platforms), bless per-platform hash sets (kilobytes each), or store raw values for the 16 log-scaled channels and tolerance-compare only those. 7.15-1 §7's measurements say the eventual cost of any of these is small.
- One alternative was considered and rejected: hashing a coarsened (quantized) copy of the obs to buy cross-platform robustness. Quantization is a tolerance in disguise: values near grid boundaries still flip under tiny jitter (making flips negligibly rare needs grids coarser than real changes we care about), and on the pinned platform it only lowers the detection floor, for nothing.

The numbers that carried the decision (all from 7.15-1):

| quantity | value |
|---|---|
| standing reference bytes per fixture-config (hashes + summary) | ~10 KiB |
| pack growth per full obs re-bless, 30-fixture basis | ~200 KiB |
| suite runtime, 30 fixtures + 3 legacy | ~10–20s including hashing |
| the per-frame-per-channel hash alternative, per full re-bless | ~15 MiB |
| the dense stats layer, standing npz / per full re-bless | ~2.2 MiB / ~2.2 MiB |
| frozen frames (designed pick), standing | 1.67 MiB |

The frozen-frames row makes a point worth keeping: its bytes were never the problem. What the hash design eliminates is the pick rule's job of predicting, indefinitely, where future changes will manifest.

Robustness basis, briefly: walk determinism is demonstrated end-to-end at byte resolution on this platform (7.15-1 §6), hash collision odds are negligible by arithmetic (about 2⁻⁶⁴ per changed frame), and the "does the mechanism actually fire" gap is closed by a permanent mutation test (§4).

**What the hashes do not cover.** Detection is perfect only for what the fixtures execute. A behavior change in a condition no fixture contains fires nothing. Coverage therefore lives entirely in fixture selection, which this revision elevates accordingly: the event-class checklist (7.12-4), its condition tags, and the selection query are the coverage instruments, and the residual exposure of the whole system sits there. One mitigation became cheap in this design: a fixture now costs roughly 100 to 250 KiB standing (the npz pair, hashes, summary, and targets, with the T-scaling mask stack the variable part) and about 0.25s of suite runtime, so the fixture-count ceiling is soft. The initial set can grow past the old ~5 if the checklist wants more coverage, and the ~30-lifetime planning number is no longer load-bearing.

## 3. What stands unchanged from 7.12-1

Brief statements with pointers. 7.12-1 remains the authority for these.

- **Goal and the definition of "handled"** (§1).
- **The core principle and the config leg** (§2): everything frozen except the guarded code. The config leg in full: stored config dicts with every field explicit, the strict-keys assert, the small `TargetsConfig`, the legacy-config equality assert.
- **Two-layer architecture and the torch-free test path** (§3). Layer-1 fixture goldens stay in the cut, sequenced near the end of the build. New flag: they are the first-trim candidate if the build drags, and if trimmed, their revival trigger is the first sim or parser change.
- **Fixtures from the corpus, the realism argument, the no-toys call, and the freeze-time tags** with the comprehensive-tags posture (§4, 7.12-4 §2). Two constraints added by the probe's findings (7.15-1 §8): fixtures must pass the training eligibility filter (8 players, board ≤ 32, T ≤ 2000), and the selection query must target neutralize events explicitly.
- **Registry, guard rules, coverage forcing, the fixture-by-config matrix, and the defaults-not-guarded caveat** (§6).
- **The boundary record lifecycle and the ledger** (§7): fire → regen opens a record → the blocking test holds the suite red until it is completed → one reviewable commit. Class-first template, one pending record updated in place across regens, append-only once committed, standalone chronological ledger file. Two trims: regen no longer pre-fills magnitudes (it prints the fire's extent, and the author writes the five-line entry by hand), and seeding the ledger with the three known May–June boundaries moves out of the build into a follow-up task.
- **The guarded/not-guarded table** (§8), with the reference mechanism now hashes. Its closing caveat ("green means no change in what these fixtures execute, not behavior unchanged everywhere") is now the system's main residual exposure and should be read that way.
- **The flow inventory**: 7.09-1's flows 0, 1, 2, 3, and 6 survive this revision intact. Flow 1 (adding a gated variant) gets slightly stronger: existing config points staying green is now byte-verified, and the new point still fails as unblessed until its first regen. Flows 4 and 5 stay deferred as before.

One working-style note on the record mechanism, made explicit because the elim arc will fire targets goldens frequently and by design: the ritual runs once per landed batch of work, not per mini-experiment. Iterating freely on a branch regenerates references without tending the record, and the pending record is completed when the work lands. This is what the one-pending-record semantics were designed for.

## 4. What the first cut ships

- **Fixture production and the walk core**, promoted from the probe modules (`goldens_probe/fixtures.py` and `walk.py`, plus the frame-hash builder from `layers.py`).
- **The initial fixture set**, selected against the 7.12-4 checklist by corpus query, with the eligibility gate and neutralize targeting, and with freeze-time tags. Count decided at selection time (§2: the ceiling is soft).
- **Reference writers**: frame hashes, per-channel hashes, the channel summary, targets.
- **The registry and config discipline**, per 7.12-1 §6.
- **The regen tool**, two commands (produce-fixtures, regen), linear core, printing the fire extent and requiring a ledger entry via the blocking test. No diff-against tool in this cut (§6).
- **The ledger and the blocking test** (~10 lines). Entries are hand-written: date, surface, one line of what changed, effect class, and the class's one or two judgment answers.
- **A permanent mutation test**: perturb an in-memory copy of a walked frame and assert the hash comparison fires. This is the standing proof that the tripwire mechanism works, guarding against harness rot, at millisecond cost. (The rest of the input-mutation matrix stays deferred.)
- **Two structural tests**: the size-budget test (ceilings as tests) and the every-gated-channel-group-guarded test.
- **The AGENTS.md note**: what a golden failure means, which flow applies, and the rerun recipe for exact old values (check out the old ref in a worktree, run the walk, diff the flagged channels: deterministic and about 0.2s per perspective).
- **Layer-1 goldens**, near the end of the build (§3).

## 5. Dropped

Each item with its reasoning. Under §1's argument structure: these served speculative diagnostic use cases, and the scenarios do not ask for them.

- **Frozen frames, the deterministic pick rule, and its review.** The frame hashes detect at every walked tick, which ends the pick rule's defining job: predicting where future changes will manifest so the right frames get frozen. That open-ended predictive burden was the real cost of the arrangement (7.15-1 shows the bytes were trivial either way). The diagnosis roles frozen frames played are in the mapping below.
- **The obs-channel sweep.** Its two consumers (7.12-4 §8) fared differently. Reviewing the pick rule died with the pick rule. Completing the condition-tag list (enumerating what memory channels respond to, so fixture selection can cover those histories) is weakened rather than dead: full-game walks compared at every tick cover much of it for free (every fixture contains the buffer-fill boundary, and long fog spans are near-certain in real 8-player games). The residual: add cheap condition tags for the named gaps (a long fog span, a witnessed general capture), and the BFS-after-captured-general behavior stays a known unverified note.
- **The dense `[T, C, n_stats]` stats layer.** Its consumers were the speculative ones: instant magnitude without a rerun, and pre-filled record fields. The channel summary covers the coarse-magnitude need, the rerun recipe covers the exact need, and neither scenario asks for more. Not deferred, because the layer as designed has no revival trigger. The conditional future artifact is different and smaller (the log-channel value store, §6).
- **Per-frame-per-channel hashes** (`[T, C]`). About 15 MiB of incompressible pack growth per full re-bless (7.15-1 §5) to buy channel attribution the `[C]` layer provides at about 1 KiB. The general lesson: hashing units that compress to ~25 bytes into 8 incompressible bytes keeps roughly a third of the cost of storing the data while keeping none of its value.
- **Record automation and magnitude pre-fill.** A solo dev writes five lines. Automation was already gated on fires demonstrating a need (7.12-1 §7), and that gate stays.
- **The runtime knobs** (perspective caps, fixture truncation, a fast/full split). Closed by measurement rather than dropped: the suite runs in seconds (7.15-1 §3).
- **The 2-frame anchor set.** An ad-hoc idea added to the probe mid-session (freeze just the first and last frames as exact exemplars), discarded once its roles moved to the mutation test and the env-upgrade dump. Its stronger successor, a small programmatically selected frozen-frame set, sits on the extension ladder (§7).

The cheaper-alternatives mapping. Secondary reassurance, per §1: for each kind of information the dropped artifacts provided, where it now comes from if a need materializes.

| information | source now | cost model |
|---|---|---|
| that something changed, and at which ticks | frame hashes | standing, ~5 KiB |
| which channels changed | per-channel hashes | standing, ~1 KiB |
| coarse magnitude, sanity check | channel summary | standing, few KB |
| exact old values, per-cell diffs | rerun the old ref's walk | on demand, recipe in the AGENTS note |
| review integrity at a bless commit | channel-summary diff | standing |
| env-upgrade ground truth | old-env full-array dump at upgrade time | on demand, procedure in §6 |

The on-demand rows are argued but unexercised until the first real fire. That is acceptable because extension is additive and the first shortcoming will name what is actually missing.

## 6. Deferred

| item | revival trigger | interim covering |
|---|---|---|
| diff-against-ref tool | first fire needing per-cell detail | the rerun recipe |
| off-platform support (exact-class subset, per-platform bless, or log-channel value store) | a second standing environment runs the suite | off-platform runs skip the goldens |
| environment-upgrade handling | the upgrade itself (manual at first occurrence, per 7.09-1 flow 4) | the dump obligation below |
| fixture-schema migration | a sim-dict schema change | the manual two-step (7.10-2 §7) |
| ledger seeding (the three retro May–June boundaries) | follow-up task, no event trigger | ledger starts empty of retro entries |
| input-mutation matrix beyond the permanent mutation test | fires demonstrating a need | the mutation test |
| programmatic frozen-frame set | see the extension ladder (§7) | hashes + channel summary |
| forward goldens, hash-fill, loss/metrics goldens, rename bridge | unchanged, 7.09-1 territory | out of this cut |

One obligation lands now rather than at its trigger. **The environment-upgrade procedure must include, as its first step, a full-array dump of every fixture's walk on the old environment.** This is the ground truth for classifying churn against behavior across the boundary, it costs zero committed bytes, and it can only be generated while the old environment still exists. The same applies to machine replacement, which is an environment-upgrade-shaped event: the pinned-platform posture couples reference validity to this specific machine, so a new machine means running the dump before retiring the old one.

## 7. The extension ladder

If hashes plus the channel summary prove insufficient in real use, the escalation rungs, in order:

1. **The diff-against tool**: exact per-cell diffs against any git ref, on demand, no new storage. Trigger: the rerun recipe gets used enough to be worth automating.
2. **A small programmatically selected frozen-frame set**: automated selection over the fixture's events and conditions (not hand-picked, and better than first-and-last). Trigger: repeated fires where marginal attribution plus the summary were not enough to orient.
3. **The log-channel value store or per-platform blessed hashes**: only if the shortcoming is cross-platform rather than diagnostic depth.

Each rung waits for a concrete observed shortcoming, per §1's extension principle.
