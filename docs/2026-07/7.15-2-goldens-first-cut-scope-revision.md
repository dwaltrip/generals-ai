## 1. The reframe

Two anchors drove this revision and its reduced scope.

**Anchor 1: This is a hobby project with one developer.** Prior design work ended up with some over-engineered aspects that are likely overkill for this project. A few examples: a curated frozen-frame layer, a dense per-frame statistics layer, staged automation for boundary records, and so on. This doc is an attempt to recalibrate.

**Anchor 2: Two scenarios that emphasize the key requirements:**

1. **Accidental behavior changes**: a change was not meant to affect "behavior", yet it did. The most important thing here is a basic alarm, which the goldens provide. Beyond that, seeing the affected channels lets us know where to start debugging. Coarse summary stats are a nice bonus.
2. **Intentional behavior changes**: golden tests should fire as designed. The coarse summary stats provide a sanity check that the fire matches the intent.

If this scope proves insufficient during actual usage, at that point we revisit and extend, guided by the concrete shortcoming. We expect that the reduced scope won't overly inhibit any extensions needed in the future.

**Primary goals are unchanged from 7.12-1 §1:**

1. Detect behavior-affecting changes automatically.
2. Enforce that such changes are handled with an intentional decision to either gate the change (e.g. code stays backwards-compatible) or to accept a boundary.
3. When boundaries are accepted, create a durable record capturing the relevant details. Ideally, in the same commit or PR as the change causing the boundary.

The scenario analysis is the meaningful test for what goes in the first cut. The dropped artifacts served diagnostic use cases that are themselves speculative (maybe never needed, rarely needed, or needed in some form whose details are unclear). The cheaper-alternatives mapping in §5 serves as a secondary reassurance for deferred or dropped items.

One taxonomy used throughout: *deferred* means a named revival trigger exists and we expect to build the item when it fires. *Dropped* means there isn't a trigger: the item is superseded or doesn't have a meaningful use case.

Continuity note: the two scenarios listed above are flows 2 and 3 from 7.09-1.

## 2. The reference design

First, a brief clarification on the definition of "fixture":

- A fixture is a specific player perspective from a specific replay (e.g. a `replay_id, perspective_slot_id` tuple).
  - In training, each sample is also pulled directly from specific perspectives in specific replays. The first cut goldens guard the obs tensor and the targets used in training, so they build off the same core data source.
  - Concretely, this consists of the npz files for the source replay along with the index of the selected perspective. Multiple perspectives from a single replay are considered multiple fixtures (that happen to share the npz files).
- Earlier docs (and the probe record) use "fixture" for a replay alone (no specified perspective), so their per-fixture counts and costs are for each replay. Most of those counts assumed a single perspective per replay, so the numbers shouldn't change much.
- When doing fixture selection, we will select the source replays along with the desired perspective(s).

### Primary artifacts

We've replaced the frozen frame and heavier stats layer reference format from 7.10-2. Per `(fixture, config point)`, the committed references are now:

- **Per-frame hashes** (`[T]` uint64): each walked frame's exact bytes hashed to 8 bytes. This is the detector: exact detection at every walked tick, and the first mismatching tick localizes when behavior diverged. About 4.5 KiB.
- **Per-channel hashes** (`[C]` uint64): each channel's full history (`[T, 32, 32]`) hashed once. Purely attributional: at fire time it names the affected channels, which is the single most useful pointer toward the responsible code. About 0.9 KiB. Detection is fully carried by the frame hashes: a change is never visible here without being visible there.
- **The channel summary** (named "the sidecar" in 7.10-2/7.12-1, renamed to reflect a promoted role):
  - This artifact records per-channel whole-game aggregate stats. It also documents the classes for each channel and our hashing methodology (e.g. algorithm, canonical serialization). Expected size is a few KBs.
  - It serves as a highly visible and legible diff of key changes in a bless commit or when investigating an unintended behavior change. The format should be human-readable (e.g. JSON, markdown, plain text) and it should diff cleanly.
  - Finally, it provides the only magnitude information when the goldens fire (with dense statistics being dropped, see §5).
- **Targets references**: unchanged in form, full arrays at all frames in as-emitted dtypes (including the legality-mask stack). Targets fires therefore come with exact per-value diffs. This will be immediately useful in the next phase of elim-head work, as we expect frequent fires for the targets.

A fire report pulls directly from these primary artifacts. We see which ticks changed (frame hashes), which channels changed (channel hashes), and how the channel aggregates moved (channel summary). We've dropped the combined form (which channel changed on which tick), as it is prohibitively heavy on disk for little gain (see "Per-frame-per-channel hashes" in §5 below).

### Key mechanics

**Hash equality**

In the golden tests, hash equality is computed as byte equality over the canonical bytes. The canonical representation consists of numpy arrays in standard "C-order" memory layout (row major, last axis varies fastest), with the dtype given by the config.

The canonicalization is a key part of the tests working properly. As hashing reads raw memory, the same values in a different layout (e.g. a transposed view) would produce different bytes.

Notes:

- Byte equality is marginally stricter than value equality. The values `-0.0` and `0.0` are equal with the latter but not the former. The extra strictness is a small bonus. Mentioning for completeness, as it is perhaps a bit surprising.
- NaN is not a concern. The regen's check phase asserts finiteness.
- The dtype rule carries over from 7.10-2 §4: hash what the config emits (fp16 for the default point, fp32 for legacy). These emitted bytes are the contract expected and consumed by the training loop.
- The probe used blake2b with an 8-byte digest, and sha256 may be faster on this machine (hardware support). The choice is made at build time and recorded in the channel summary either way.

**Environment notes**

- Exact equality on the pinned platform (the 7.10-2 standard, now implemented by hashes). Daniel's dev machine (an M1 macbook pro) is authoritative. The environment test (§4) enforces the pinning: the suite fails when the running environment differs from the blessed stamp. 7.09-1's off-platform tolerance mode is retired from this cut, since tolerance comparison needs stored values we no longer keep.
- In the future, if we need to run the test suite on a second standing environment, a few options have been discussed. Each seems relatively easy to implement, and the probe results (7.15-1 §7) indicate the disk size cost would be small. The discussed options:
  - (1) Compare only the exact-class channels (the ~94 non-log channels hash identically across platforms)
  - (2) Bless per-platform hash sets (small, a few KBs each)
  - (3) Store raw values for the 16 log-scaled channels and tolerance-compare only those.

**Quantized hashes (rejected alternative to pinning the environment)**

*Noted for posterity.*

We considered quantized hashes as an alternative to a pinned environment (with exact hashes). Hashing coarsened values would absorb small cross-platform floating-point noise, giving cross-platform stability for the committed hashes. This in turn would provide increased flexibility for our development workflows, by removing the limitation that they must run on the pinned environment (Daniel's laptop).

In our case, the details don't pan out. The noise we want to absorb would cause values near bucket boundaries to unpredictably flip from one bucket to the next. One might try to coarsen the buckets until these flips are sufficiently rare, but this would also mask a subset of meaningful changes. This undermines the main purpose of golden tests (detect all behavioral changes) and makes the approach nonviable.

It was also concluded that, in practice, restricting to Daniel's laptop is unlikely to be a significant blocker anytime soon. So the primary benefit isn't needed with any urgency. And we can defer further work that seeks to loosen the environment constraint.

### Measurements informing these decisions

From the probe results:

| measurement | value |
|---|---|
| standing reference bytes per fixture-config (hashes + summary) | ~10 KiB |
| pack growth per full obs re-bless, 30-fixture basis | ~200 KiB |
| suite runtime, 30 fixtures + 3 legacy | ~10–20s including hashing |
| the per-frame-per-channel hash alternative, per full re-bless | ~15 MiB |
| the dense stats layer, standing npz / per full re-bless | ~2.2 MiB / ~2.2 MiB |
| frozen frames (designed pick), standing | 1.67 MiB |

Robustness notes, briefly (details in the results doc):

- The walk was shown to be deterministic end-to-end at byte resolution on Daniel's dev machine (7.15-1 §6).
- The chance of a hash collision is effectively zero (about 2⁻⁶⁴ per changed frame).
- The "does the mechanism actually fire" gap is closed by a permanent mutation test. The environment test asserts that the goldens are running under the same conditions as those that produced the blessed references. See §4 below.

### Limitations

The golden tests can only detect behavior changes in code paths that execute. Not every game of generals will hit every behavioral path. This means that full coverage depends on careful fixture selection.

For each fixture, the goldens compare every tick. This means that all events and state changes occurring in a selected fixture are fully guarded. This includes obs-memory changes that can span arbitrary tick ranges.

Most checklist classes appear in any typical 8-player game and should require minimal effort to cover during fixture selection. Selection concentrates on the remainder: the events and state changes that are less common.

Neutralize events were the first measured example (1 of 5 sampled games, 7.15-1 §8). The coverage instruments are the event-class checklist (7.12-4) and the selection tooling built against it (§4).

If we are struggling to get coverage for all behavior paths, there is a cheap extension / mitigation enabled by the current design. Fixtures now cost only ~100-250 KiB of committed data each (and ~0.25 seconds of test runtime). This means we have breathing room to add more fixtures than previously budgeted. Guesstimating, we can comfortably exceed earlier fixture counts of ~5 for the initial set and ~30 for the project lifespan. Note: this hasn't been analyzed in detail and is mostly a rough assessment, given the artifact design changes.

## 3. What stands unchanged from 7.12-1

Brief statements with pointers. 7.12-1 remains the authority for these.

- **Goal and the definition of "handled"** (§1).
- **The core principle and both its legs** (§2). The principle: everything is frozen except the guarded code. The config leg, in brief: stored config dicts with every field explicit, the strict-keys assert, the small `TargetsConfig`, the legacy-config equality assert. The data leg's fixture story was restated and refined in this doc's §2.
- **Two-layer architecture and the torch-free test path** (§3).
- **Fixtures from the corpus, the realism argument, and the no-toys call** (§4). Two constraints added by the probe's findings (7.15-1 §8): fixtures must pass the training eligibility filter (8 players, board ≤ 32, T ≤ 2000), and the selection query must target neutralize events explicitly. (The optional phantom-slot fixture, if built, is a deliberate exception to the player-count leg, §8.) One item from §4 is not carried: the freeze-time tags are dropped (see "Dropped" below).
- **Registry, guard rules, coverage forcing, the fixture-by-config matrix, and the defaults-not-guarded caveat** (§6).
- **The boundary record lifecycle and the ledger** (§7): fire → regen opens a record → the blocking test refuses to pass without a filled record in the same commit → one reviewable commit. Impacts-first template, standalone chronological ledger (one file vs a file per record is a build-time packaging choice). One semantics revision to §7: records are disposable until the work lands, and append-only after. Landing, not committing, is the commitment point (the working-style pattern below is why). Two trims: regen no longer pre-fills magnitudes (it prints the fire's extent, and the author writes the five-line entry by hand), and seeding the ledger with the three known May–June boundaries moves out of the build into a follow-up task.
- **The guarded/not-guarded table** (§8), with hashes as the reference mechanism. Its closing caveat (green means "no behavior change in what these fixtures execute", not "behavior unchanged everywhere") is now the system's main residual exposure and should be read that way.
- **The flow inventory**: 7.09-1's flows 0 (normal work), 1, 2, 3, and 6 (retire a variant) survive this revision intact. Flow 1 (adding a gated variant) gets slightly stronger: existing config points staying green is now byte-verified, and the new point still fails as unblessed until its first regen. Flows 4 and 5 stay deferred as before.
- **Layer-1 goldens**: stay in the cut, sequenced near the end of the build (description in §4). Not urgent, but expected to be fairly easy, so the aim is a minimal version. They are the first-trim candidate if the build drags, and if trimmed, the revival trigger is the first sim or parser change.

One working-style pattern on the record mechanism, made explicit because the elim arc will fire targets goldens frequently and by design: the polished record is written once per landed batch of work, not per mini-experiment. Completing a record per regen would produce entries describing increments the ledger has no use for, so during branch iteration each regen keeps a placeholder record filled instead (one line naming the work in progress). That keeps every commit on the branch green, and an unexpected fire during iteration still stands out. At land time the batch collapses into one clean boundary: restore the references to their branch-point state, delete the placeholder, re-bless once against the final code, and write the real entry from that fire report. The land-time fire shows the batch's whole extent against the true baseline, so the entry is written from evidence rather than reconstructed from the increments. The step-by-step recipe goes in the goldens workflow doc (§4).

## 4. Shipped in the first cut

- **Fixture production and the walk core.** Fixture production and the frame-hash builder are promoted from the probe modules (`goldens_probe/fixtures.py` and `layers.py`). The walk core is built as shared torch-free infrastructure, with a dataset parity test shipping alongside it, per the walk-seam settlement ([7.23-1](7.23-1-walk-infra-design-sketch.md)).
- **The initial fixture set**, selected against the 7.12-4 checklist by corpus query, with the eligibility gate and neutralize targeting. Count decided at selection time (§2: the ceiling is soft).
- **The selection helper module**: the checklist's classes as named predicates over the parsed npz, reusing `compute_visibility` for the per-perspective conditions. The fixture-selection tooling uses it to query candidates and to report what the chosen set covers, with uncovered classes recorded in the selection session's notes. Selection-time only: nothing in the test path reads it.
- **Reference writers**: frame hashes, per-channel hashes, the channel summary, targets.
- **The registry and config discipline**, per 7.12-1 §6.
- **The regen tool**. Two commands (produce-fixtures, regen). They print the fire extent and require a boundary record (per the blocking test).
- **The ledger and the blocking test** (~10 lines). Entries are hand-written: date, surface, the changed channels (copied from regen's printed extent), one line of what changed, the impacts, and their one or two judgment answers. Field definitions live in the record legend ([7.20-2](7.20-2-boundary-record-legend.md)).
    - We expect the changed-channel list to be an entry's highest-signal field. It lets a reader quickly assess what the entry was about.
- **A permanent mutation test**: perturb an in-memory copy of a walked frame and assert the hash comparison fires. This is the standing proof that the tripwire mechanism works, guarding against harness rot, at millisecond cost. (The rest of the input-mutation matrix stays deferred.)
- **Two structural tests**: the size-budget test (ceilings as tests) and the every-gated-channel-group-guarded test.
- **The environment record and its test**: a small committed file beside the registry, written by regen at bless time.
    - Three fields are asserted: the uv.lock hash, the Python interpreter version, and the platform arch.
    - Additional context is recorded but not asserted: the numpy version, the OS version, and the blessing machine's name.
    - The environment test compares the running environment against the asserted fields and fails on any difference, with a message pointing at the environment-boundaries note below. The lock hash deliberately covers every dependency, not just the walk-relevant ones: a curated subset would require manual syncing.
        - Routine workflow for dependency changes: apply the bump and run the suite. The environment test fires, and the goldens stay green in the vast majority of cases, as most dependencies play no role in the reference computation. Re-stamp the environment record in a one-line commit, and the bump is done. (If the goldens fire too, see the environment-boundaries note below.)
- **The goldens workflow doc** (evergreen, written after the naming pass so it uses the final vocabulary): what a fire means and which flow applies, the branch-iteration and land-ritual pattern (§3), the environment procedure (the routine workflow above and the environment-boundaries note below), and the rerun recipe for exact old values (check out the old ref in a worktree, run the walk, diff the flagged channels: deterministic and about 0.2s per perspective). The AGENTS.md note shrinks to a pointer to it.
- **Layer-1 goldens**, near the end of the build (§3). These guard the layer that *produces* fixtures. For a few fixtures, the source replay is committed alongside the npz, and a test re-runs the parser + sim on it and compares the resulting arrays against the committed npz. A sim or parser behavior change then fires this test. A few fixtures suffice, as this guards shared code rather than per-fixture data. The test would go in the sim or replay-parser test suite (it needs the Rust build). This is not urgent, but it's expected to be fairly easy to add, so we aspire to build a minimal version.

**Environment boundaries.** When a dependency change fires the goldens as well as the environment test, the environment itself changed the emitted bytes: a real boundary. These should be rare, as numpy is nearly the only dependency in the reference computation. The handling is manual. Rebuild the old environment from the old lockfile, dump every fixture's walk under it as full arrays (a local, uncommitted artifact), and use the dump to separate numerical churn from real behavior changes. Once the diff is understood, re-bless with one boundary record. If real boundaries arrive noticeably more often than expected, or the manual handling proves inconvenient, we re-evaluate possible tooling (current candidates in §6).

If we ever switch to a new dev machine (changing the "pinned environment"), the dump must happen before the switchover. Without it, we can't characterize any churn from the environment change, and it needs to be produced while the old machine is still available.

## 5. Dropped

Each dropped item with its reasoning. Under §1's argument structure: these served speculative diagnostic use cases, and the scenarios do not ask for them.

### Frozen frames, the deterministic pick rule, and its review

Comprehensive per-frame hashes make hand-selected "frozen frames" entirely redundant. The design saves us from having to carefully maintain and update a set of frames that cover all behavior, even as the behavior changes in the future. This on-going burden, which relies on discipline (and not forgetting), was the real cost of the arrangement. The 7.15-1 probe showed that disk size was not an immediate dealbreaker (see the "frozen frames" row above in §2). The diagnostic roles frozen frames played are covered in the mapping below.

### The obs-channel sweep

Its two consumers (7.12-4 §8) fared differently:

- Reviewing the frozen-frame pick rule died with the pick rule.
- Completing the condition-class list (enumerating what the memory channels respond to, so fixture selection can cover those histories) is weakened rather than dead. Full-game walks compared at every tick cover much of it for free: every fixture contains the buffer-fill boundary, and long fog spans are near-certain in real 8-player games.

The known gaps are handled without the sweep: a long fog span and a witnessed general capture go on the checklist, and the BFS-after-captured-general behavior stays a known unverified note. The sweep's other function, finding unknown gaps, is still needed to have confidence in the robustness of the obs goldens. Coverage now rests entirely on fixture selection (§2). And the condition side of the checklist still needs to be resolved.

During the selection work, we can meet these needs with a scoped-down skim: read the stateful channel code and enumerate condition classes, without the per-channel equivalence-class analysis or the pick-rule review. Its deliverable is additions to the rare-class list (§2): conditions not found in a typical game.

### Freeze-time tag asserts and the comprehensive-tags posture (7.12-4 §2)

The tags were to ship as standing asserts: every fixture's declared classes checked at fixture production and re-checked at schema-migration regen, with the full checklist codified. Both standing checks lost their consumers. The production-time check (the selection contains what it claims) happens at selection instead, through the same predicates the selection query runs. The regen-time check guarded against coverage changing when fixtures are rebuilt. But a fixture rebuilds from its own committed replay by a deterministic parse, so coverage can only change there if parser behavior changed, and that event is already made loud by the layer-1 goldens and the migration two-step. What survives is the selection helper module (§4). The checklist remains a full inventory, selection targets its rare classes (§2), and each fixture's purpose stays documented as a note in its registry entry.

### The dense `[T, C, n_stats]` stats layer

Its consumers were the speculative ones: instant magnitude without a rerun, and pre-filled record fields. The channel summary covers the coarse-magnitude need, the rerun recipe covers the exact need, and neither scenario asks for more. Not deferred, because the layer as designed has no revival trigger. The conditional future artifact is different and smaller (the log-channel value store, §6).

### Per-frame-per-channel hashes (`[T, C]`)

This is the combined form (mentioned in §2) that details exactly which channels changed on which ticks.

It is quite heavy, adding 0.5 MiB per fixture-config on each obs re-bless (from 7.15-1). Git keeps every committed version of the references indefinitely and the hash data doesn't compress. With 30 fixtures, these `[T, C]` hashes permanently grow the repo size by ~15 MiB on every full re-bless. That alone is a non-starter.

The loss from dropping this is small, as most fires are clearly understood with the two lists. For uncommon scenarios with complex overlapping causes, we can dig deeper with the rerun recipe, if needed. The other main use case, channel attribution, is easily met by the per-channel hashes (the `[C]` layer) for a mere ~1 KiB.

### Record automation and magnitude pre-fill

A solo dev writes five lines. Automation was already gated on fires demonstrating a need (7.12-1 §7), and that gate stays.

### The runtime knobs

Specifically, we are dropping knobs for perspective caps, fixture truncation, and a fast/full split. The probe's run times (7.15-1 §3, extrapolated in §2's table) put the full suite at roughly 10 to 20 seconds, comfortably inside the fast tier, so we can just run with everything "always on".

### The 2-frame anchor set

An ad-hoc idea added to the probe mid-session: freeze just the first and last frames as exact exemplars. It was discarded once its roles moved to the mutation test and the env-upgrade dump. Its stronger successor, a small programmatically selected frozen-frame set, sits on the extension ladder (§7).

---

**The cheaper-alternatives mapping.** This table is the secondary reassurance described in §1: for each kind of information the dropped artifacts provided, it names where that information now comes from. Or how it can be produced if needed, for capabilities that are fully dropped or deferred.

| information | source now | cost model |
|---|---|---|
| that something changed, and at which ticks | frame hashes | standing, ~5 KiB |
| which channels changed | per-channel hashes | standing, ~1 KiB |
| coarse magnitude, sanity check | channel summary | standing, few KB |
| exact old values, per-cell diffs | rerun the old ref's walk | on demand, recipe in the workflow doc (§4) |
| review integrity at a bless commit | channel-summary diff + the record's changed-channel list | standing |
| env-upgrade ground truth | old-env full-array dump at upgrade time | on demand, procedure in §4 |

The on-demand rows are argued but unexercised until the first real fire. That is acceptable because extension is additive and the first shortcoming will name what is actually missing.

### Environment-upgrade tooling

Real environment boundaries should be rare (§4), and the manual procedure is expected to be sufficient (the common case is just the one-line re-stamp). If this isn't the case, some tooling ideas:

- Dump command: walk every registry entry and write the full arrays locally. Replaces any ad-hoc dump scripts (from the "manual" workflow).
- Churn-classification report: compare the new walk against the dump and summarize the per-channel diffs. Details are speculative until a first occurrence, including what a real behavior change from a dependency upgrade would even look like.

## 7. The extension ladder

If hashes plus the channel summary prove insufficient in real use, the escalation rungs, in order:

1. **The fire-report event annotation**: annotate each flagged tick with nearby events from the fixture's event arrays (already in the npz), so a fire reads as "capture-adjacent" rather than an anonymous tick. A formatting step in the fire report, no new storage. Trigger: fires where interpreting the flagged ticks meant looking up the event arrays by hand.
2. **The diff-against tool**: exact per-cell diffs against any git ref, on demand, no new storage. Trigger: the rerun recipe gets used enough to be worth automating.
3. **A small programmatically selected frozen-frame set**: automated selection over the fixture's events and conditions (not hand-picked, and better than first-and-last). Trigger: repeated fires where marginal attribution plus the summary were not enough to orient.
4. **The log-channel value store or per-platform blessed hashes**: only if the shortcoming is cross-platform rather than diagnostic depth.

Each rung waits for a concrete observed shortcoming, per §1's extension principle.
