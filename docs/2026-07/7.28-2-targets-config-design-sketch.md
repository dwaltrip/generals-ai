# TargetsConfig design sketch

*Date: 2026-07-28. Settles `TargetsConfig`: the piece of the goldens first cut's "registry and config discipline" work ([7.15-2 §4](7.15-2-goldens-first-cut-scope-revision.md)) that earlier docs named but never specified ([7.12-1 §2](7.12-1-behavior-goldens-first-cut-v2-overview.md) introduces it in one clause). This sketch covers that one topic. The registry's own shape, how stored configs are serialized, and the variant enumeration mechanics are separate topics for later sketches. Constraints inherited: `dataset.py` is not touched during the cut ([7.23-1](7.23-1-walk-infra-design-sketch.md)), and the loss surface stays unguarded (7.12-1 §8).*

Questions answered in this sketch:

1. Which knobs belong in TargetsConfig, and by what rule?
2. Why is TargetsConfig separate from LossConfig, given the two are usually edited together?
3. What are its fields and stored config points?
4. How much does the production training code adopt TargetsConfig during the first cut, and when does the rest happen?

## 1. The seam between target encoding and loss

Target encoding runs per frame on the CPU (in the dataloader workers) and can read the sim and meta dicts. Loss runs per batch on the GPU after the forward pass and sees only the sample dict. The sample dict is the interface between the two.

The sample dict is kept small in practice: every key adds per-sample transfer and collate cost, and is another thing the loss and metrics code depend on. Once the goldens exist, growth also becomes visible: a new emitted key fires the targets goldens, so it can only land through a re-bless and its boundary record.

Some computation could run on either side of the seam: any transform that is a pure function of tensors already being emitted (softening a label, digitizing a delta). For these, transfer cost decides placement. A transform that shrinks the data belongs before the transfer (encode side), and one that expands the data belongs after (loss side). Softening expands an int label into a distribution, which is why it sits loss side.

Code locality is a separate consideration. Targets code and loss code are closely related, so it is natural to want them near each other in the codebase. `AuxHeadSpec` satisfies this without moving any computation across the seam: `encode_targets` and `loss` sit on one class while executing on opposite sides.

The goldens freeze the seam's current placement. If a transform later moves across the seam, the emitted bytes change and the targets goldens fire, which is correct: that is a real boundary for anything consuming those bytes.

## 2. TargetsConfig vs LossConfig

The rule: TargetsConfig holds the knobs that change the emitted target bytes. LossConfig holds the knobs that transform those bytes after the seam.

The rule's "emitted target bytes" are the numpy layer's output: the goldens call the numpy target functions directly (`value_target`, `policy_pass_target`, `time_bin_targets`, `next_death_target`, `alive_mask`), not `encode_frame` or `spec.encode_targets`, which are thin torch wraps above them. The wrap layer is unguarded by the goldens (a deliberate 7.12-1 §3 choice) and is covered by the parity test instead, which compares the prod dataset's output against the goldens-side computation.[^numpy]

TargetsConfig and LossConfig get edited together because a variant is naturally a bundle: an encode part, a loss part, and a head. The aux-head spec object reflects this. TargetsConfig addresses only the encode part.

Worked example: the value head. The emitted target is the placement class with no softening and no knobs. Everything tunable about the value head (`value_target_tau`, `lambda_value`) is a LossConfig field. Switching to soft value targets never changed an emitted byte.

## 3. Fields and stored config points

Fields:

- `elim_enabled: bool`
- `elim_variant`: None, `"time_bin"`, or `"next_death"`
- `elim_bin_edges`: tuple of ints, or None

Validation: a variant requires `elim_enabled`, `time_bin` requires edges, and everything else requires edges to be None.

The four stored config points:

| point | elim_enabled | elim_variant | elim_bin_edges |
|---|---|---|---|
| core | False | None | None |
| alive_only | True | None | None |
| time_bin | True | "time_bin" | (10, 20, 40, 80, 160, 320, 640) * |
| next_death | True | "next_death" | None |

\* To be confirmed against real checkpoints when the registry entries are written.

The class follows ObsConfig's construction: frozen dataclass, torch-free, no inline field defaults, and loading a stored dict asserts its keys match the fields exactly. It lives in the production tree near the targets code. The config is entirely about the elim head because the core targets (action, pass, value, mask) have no knobs.

One rule the goldens depend on: the golden test path must not read any live default anywhere, whether from a config object or from a defaulted function parameter. Every value the emitted bytes depend on comes from the stored config.

## 4. Adoption: how far, and when

Adoption has three stages. During the cut, only the goldens use TargetsConfig. In the first follow-up, the dataset constructor takes a TargetsConfig, built from `arch` at the call sites, with no change to the stored checkpoint config. In the second follow-up, the elim fields move into a nested targets sub-config inside the checkpoint config block, which is a schema change (version bump, frozen keyset, migration), mirroring how the obs fields became `arch.obs`.

The first stage's cost is narrow: behavior changes to the target functions are guarded regardless. What is exposed is the addition of new knobs. A knob added outside TargetsConfig gives (a) config points that never enter the registry, and (b) defaulted parameters that the goldens silently follow, so a later default change fires the goldens while looking like a code change. This is accepted for the cut: the surface is three fields, it changes only during deliberate elim work, and the window is short.

Leaving these as follow-ups for after the cut provides a nice side benefit. The changes can serve as an early test of the new machinery: goldens green plus parity test green across a plumbing commit shows it changed no guarded behavior. The second follow-up also exercises the whole apparatus at once: the schema test fires while the goldens stay green.

One rule guides both follow-ups: downstream of config parsing and validation, code uses TargetsConfig. Handling of the old shape is confined to the parsing layer and the migration.

## 5. Handoffs to the registry and goldens test design work

Questions raised here that belong to those design passes or the build:

- What makes up a golden's stored identity (the full set of values that determine its reference bytes) beyond (fixture, obs dict, targets dict), and how a registry entry would carry a knob that lives in TrainConfig if one appears.
- Where in the test path stored dicts become ObsConfig and TargetsConfig instances, and what else the walk needs alongside them.
- Whether the registry schema reserves a slot now for values that affect the emitted bytes but sit outside the two configs, or grows one when needed (the likely answer: grow it when needed).

## 6. Open ambiguity: future knobs that fit neither config

The reference scheme assumes obs references depend only on (fixture, ObsConfig) and targets references only on (fixture, TargetsConfig). Two future knob placements would not fit:

- A knob on the mask (which is stored with the targets references). TargetsConfig is the sensible home. The docstring gets one sentence saying the config covers everything the walk emits except the obs tensor.
- A knob on the walk itself (a truncation rule, say). It would change both reference sets, so neither config feels like a proper home. The fallback: put it in TrainConfig in production, and store its value in the registry entry alongside the two dicts. A golden's identity is the full set of knob values the emitted bytes depend on. The two configs are today's complete inventory of that set.

No such knob exists today. This section names the situation so that whoever adds such a knob later recognizes it instead of improvising.

## 7. Related directions

Both are out of scope for the goldens work. They are recorded here so they stay visible:

- Generalize the ObsConfig pattern of keeping defaults out of config objects, with defaults applied at the parsing layer instead (LossConfig currently has inline defaults). Real but broad, and it deserves its own effort.
- A quick survey of what the existing dataset.py tests cover, before or during the build, to see what the goldens plus the parity test still leave uncovered.

## 8. Cut list (can solve during the build)

- Module path and file name, and whether it gets helpers like `ObsConfig.validate_partial`.
- The `from_arch` mapping, including how `elim_enabled` is derived (the alive-only path), to be confirmed when the first follow-up is built.
- Where the validation asserts live (`__post_init__` vs registry load).
- Confirming the edge set against real checkpoints, and deciding which guard rule applies to `elim_bin_edges` (moot with one occupied value).
- Wording of the class comment that names the adoption gap.
- The goldens-side elim context construction duplicating a few dataset.py lines during the cut (the shared extraction lands with the dataset migration, per 7.23-1).
- Stored dict serialization format (a question for the registry sketch).
- Pinning the targets reference dtypes explicitly: some numpy target functions return plain Python values, and prod's dtypes come from the torch wrap layer the goldens never run. The goldens-side assembly declares the dtypes (matching the prod sample dict), and the parity test verifies the match.
- The parity test's comparison set must cover every emitted sample-dict key, since the wrap layer's guarding rests on it (see §2). 7.23-1 §4 names obs, mask, and targets; this pins down "targets" as all of them.
- Whether the targets references store the keys shared across all four points (mask, action, pass, value) once per fixture or once per point (a layout question for the registry sketch).

# Footnotes

[^numpy]: A refresher on why the goldens are numpy-only: blessed references compare live bytes against stored bytes, so every library touching the computation is part of what can churn or break them, and the guarded math is already pure numpy in prod (the torch layer above only wraps). The proposed parity test (7.23-1) has no stored bytes, which is why dataset.py in general is free to use torch (e.g. in a later refactor).
