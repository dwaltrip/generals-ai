Companions: [7.05-2](7.05-2-ckpt-config-open-items-triage.md) (the item-by-item triage, kept current via its tick marks) and [7.06-1](7.06-1-obs-fix-barrier-hypothesis.md) (the obs-fix hypothesis that surfaced during this discussion).*

## The broadened motivations

The refactor began as a fix for silent config drift. As the work progressed, the motivation set grew. Daniel's list:

1. **Prevent the sprawling accretion of additive-gated variant code** — the scattered if/elses that supporting every historical model variant in one codebase produces. More behavior-axis than shape-axis.
2. **Have a process for less-obvious changes that affect model behavior.** The live example: a recent obs-tensor bug fix that changes what older checkpoints see as input, captured nowhere ([7.06-1](7.06-1-obs-fix-barrier-hypothesis.md)).
3. **Make future iteration on model design smoother.**
4. **Increase confidence that no silent critical errors creep into evals, metrics, and obs changes** — especially across models over time.
5. **Meta: understand the actual problem.** Several important aspects took a while to see.

His own qualifier, worth keeping attached: much of this can be deferred or chipped away at slowly.

## How this maps onto the existing frame

Most of the list was already mapped conceptually. #1 is the synthesis doc's "cost of staying barrier-free" ([6.26-5](../2026-06/6.26-5-checkpoint-config-synthesis.md) — the elim-head if/elses in the train loop, metrics, and logging are its cited example). #2 and #4 are the behavior axis's two faces: behavioral reproduction (obs + forward) and measurement comparability (loss + metrics). #5 is largely achieved and banked in the 6.24–6.27 design docs.

What the discussion changed is weight, not concepts. The triage doc filed the behavior axis under "consciously parked, costs little to leave open" — a framing that implicitly assumed the shape axis was the motivation that mattered. With half the motivation set sitting on the behavior axis, the parked *decisions* (co-residency, fidelity scope) still survive — one motivation list doesn't make those answerable earlier — but the gap in *recording discipline* does not survive. That gap is what the obs-fix example exposed.

## The direction conclusion: records, not machinery

Walking the motivations shows they mostly ask for cheap records and decisions that can wait, not for machinery:

- #2 wants, at minimum, a *record* — a ledger, not detection. Detection (golden tests, `arch_version`) stays parked.
- #4 is partially served by the same ledger plus the co-resident load test that landed this session. Full service is golden tests, deferred.
- #1's real responses — push spec-ification harder, or accept barriers with a Compat tier — are exactly the parked Q1/Q2 questions, still rightly decided when the pain is concrete.
- #3 is served eventually by chunk-2 and the config consolidation, and more cheaply by returning to real model iteration and letting friction show what hurts.

The discussion named the trap explicitly: broad motivations pull toward building the full behavior axis now. The refactor's own precedents point the other way — the `LoadPlan` union was dropped and the `arch_version` slot was not reserved, both for the same reason: structure without a present consumer has no value.

Bottom line, agreed in the discussion: nothing on the open-items list blocks core work. The near-term additions are records plus one investigation.

## The behavior-changelog proto-plan

The minimal answer to motivation #2 — proposed, well-received, not yet built:

- A plain markdown ledger of behavior-affecting changes, kept as an evergreen doc. An entry: date, what changed (a sentence or two), which surface (obs semantics / forward path / loss / metric definitions), and who is affected ("checkpoints trained before this see different inputs on current code"). Commits named by date and description, not SHA.
- Bug fixes included — an in-place behavior-changing fix is precisely the class of change that goes unrecorded.
- A line in AGENTS.md makes it stick: a change that alters obs semantics, the forward computation, or loss/metric definitions gets an entry.
- Seed entry: the obs fix, once the 7.06-1 investigation identifies it.
- Honest limits: it is discipline-dependent, so it catches the *known-but-unrecorded* class of change — on current evidence the common one — not the truly-unnoticed class, which needs golden tests and stays parked. It composes with that deferred machinery rather than competing: if golden tests or `arch_version` are ever built, the ledger is the event list they must account for.
- Cost: roughly an hour.
