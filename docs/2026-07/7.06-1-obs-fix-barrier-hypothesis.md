# Obs-fix barrier hypothesis — an unrecorded behavior change

*Date: 2026-07-06, from the 2026-07-05 planning discussion. A hypothesis record, written before any investigation — every claim below is labeled at its actual strength. Companion to the direction note ([7.06-2](7.06-2-ckpt-config-motivations-and-direction.md)).*

## The hypothesis

During the planning discussion, Daniel recalled making a bug fix to the obs tensor "relatively recently" — a fix that changes what older checkpoints see as input when they run on current code. His recollection is that the change was never recorded anywhere, and his concern: "I think this may be a live bug: any older checkpoints may perform somewhat worse if ran on the fixed code, as the input is different."

What is *not* known yet:

- **Which commit it is.** Not identified during the session. One candidate to rule in or out: the obs/alive tick seam ([6.18-6](../2026-06/6.18-6-obs-alive-tick-seam.md)) — though that is a documented, deferred *discrepancy*, not a shipped fix, so it may be unrelated.
- **Whether any eval crossed it.** Daniel believes no eval comparison mixed checkpoints from both sides of the fix, but is not certain.
- **The size of the effect.** Depends entirely on what the fix changed — which channels, on what fraction of frames.

## Why it matters

The synthesis doc ([6.26-5](../2026-06/6.26-5-checkpoint-config-synthesis.md)) describes exactly this case: a silent obs-encoder change is behavioral-reproduction drift — the model sees different inputs and produces different outputs, `load_state_dict(strict=True)` is blind to it, and no version stamp moves. In that doc's vocabulary, a behavior-changing fix applied in place, with no config gate, is a *barrier*.

Two consequences if the hypothesis holds:

- The claim that the repo is barrier-free — which 6.26-5 states as "maintained deliberately, not by luck" — was already false when written. The first barrier exists, erected unknowingly. The critical-questions doc ([6.26-7](../2026-06/6.26-7-checkpoint-config-critical-questions.md) Part B) anticipated this case: a bug fix never *forces* a barrier — the old path can be kept, or the affected checkpoints declared degraded. But that is meant to be a conscious choice, and here it was made by default, with no record.
- The triage doc ([7.05-2](7.05-2-ckpt-config-open-items-triage.md)) parks the behavior-axis questions partly on the barrier-free premise. The parking verdict likely survives (one known barrier does not demand the machinery), but the premise needs the correction.

The practical stake is the core workflow: any comparison between a pre-fix and a post-fix checkpoint, run on post-fix code, carries a confound of unknown size.

## Investigation plan

1. **Find the commit** — search the git history for recent obs-encoder fixes.
2. **Characterize the input delta** — which channels and values change, on what fraction of frames.
3. **Enumerate affected checkpoints** — which surviving checkpoints were trained pre-fix.
4. **Audit eval history** — did any recorded comparison mix pre-fix and post-fix checkpoints?
5. **Decide the disposition consciously** — accept and record degraded fidelity for pre-fix checkpoints (route-1 caveat territory), or gate the old behavior if those checkpoints matter enough.

Whatever step 1 finds becomes the seed entry of the proposed behavior-changelog (7.06-2). The supported-versus-degraded call for pre-fix checkpoints belongs to the route-1 policy decision.
