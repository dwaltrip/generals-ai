## Baseline

Nothing on this list blocks core work. The version-bump guardrail landed 2026-07-04, so config-shape churn from unrelated work now fails a test instead of silently drifting old checkpoints. The loader serves both formats, and training and eval run fine today. The one standing gap of the opposite kind: every v1 checkpoint now carries its full training recipe, and nothing reads it yet — the refactor's main payoff is not yet collected.

The original sequencing lean ("guardrail first") is satisfied, so this triage re-derives priority from scratch rather than inheriting an order.

## A — small items worth doing before switching back

1. **Route-1: the supported-checkpoint policy call.** Decide which historical checkpoints stay loadable and which are declared unsupported. It is a pure decision — no machinery — and it is the cheapest high-leverage item on the list: it lets chunk-2 *delete* the legacy reconstruction instead of relocating it, bounds the v0→v1 normalizer's scope, and unlocks removing `value_head_variant` from the loader signature.
2. [done 2026-07-05] **The v0+v1 co-resident load test.** An eval sweep loading an old checkpoint next to a fresh one is the core workflow this refactor exists to protect, and it is the one format combination never exercised in a single process. A cheap test closes it.
3. [done 2026-07-05] **Re-run the end-to-end smoke.** The train → write-v1 → load smoke has not been re-run since the FLOPs fix landed on the branch. Minutes of work.
4. [done 2026-07-05] *(optional)* **Elim-variant v1 round-trip test.** The elim head is the active core-work arc, and its configs are unexercised on the v1 path. Landed against `next_death` (the variant future v1 checkpoints will actually carry) rather than `time_bin`, whose checkpoints are all v0 — see the re-scoped gap line in 6.27-3 §7.
5. *(added 2026-07-06)* **Obs-fix investigation + behavior-changelog** — two items from the follow-on discussion: pin down the possibly-unrecorded obs barrier ([7.06-1](7.06-1-obs-fix-barrier-hypothesis.md)), and build the ledger its finding seeds (proto-plan in [7.06-2](7.06-2-ckpt-config-motivations-and-direction.md)).

## B — the natural next build increment (value, not need)

Both candidates here are the same move: build the first consumer of the stored recipe. Current resume works through the sidecar, so nothing forces this now — it is deferrable without risk, and the recipe doesn't decay while unread. Two candidates:

- **Resume rewiring** (the larger one). Source the resume config from the `.pt` instead of the sidecar, fold out the `from_checkpoint` double-read, and fix the dormant arch-gate (it keys on the v0 layout and never fires for v1 resumes). The resume-end-to-end-with-a-v1-parent test gap rides along naturally. It also forces the stored-block-contents decision: the block currently carries invocation-local fields (`run_dir`, `device`, ...) that would mislead a resume reader, so building this decides whether to filter the block or have readers re-derive those fields.
- [done 2026-07-05] **model_key fold-out** (the smaller one). `BCModelHandle.load` re-read the checkpoint file just to compute `model_key`. Built on a new `RawCheckpoint` wrapper (`bc/storage/raw_checkpoint.py`): one read, the key comes from `raw.arch_bearing`, and the path-taking discriminators are absorbed as properties.

Lean: if one increment happens before returning to core work, resume rewiring collects more of the payoff. Doing neither now is also a reasonable outcome.

## C — real work that waits until something pulls it in

- **Chunk-2: the `BCModel` re-scope.** `cfg` and variant-meta move onto the wrapper; `BCModel` becomes pure torch. This buys structure, not correctness, and the strangler indirection is already in place, so waiting costs nothing. Roughly ten call sites are the known blast radius. Includes the `ModelOut`/`output_key` seam and the follow-on `BCModelHandle` revisit.
- **Config-family consolidation into `bc/config`.** Move `train_config`, `model_config`/`obs_config`, and `LossConfig` into the package. Leaning yes; decide when scoping chunk-2. It carries the path-serde two-homes cleanup with it and overlaps the torch-free-import follow-up (the `LossConfig` lift is easy; the `aux_heads.REGISTRY` edge is its own refactor).
- **Typing the v1 format contract.** The layout keys are bare strings across four functions today; a TypedDict or shared constants turns a key typo into a type error. Doing it triggers the planned split of `storage/checkpoint.py` into format-contract and I/O halves. Do it the next time the format itself is edited.
- **The v0→v1 normalizer.** Scope depends directly on route-1, and it contains the uniform-vs-graded fork (does `ConfiguredModel.config` ever stay `None`). It is the one sanctioned crossing of the envelope/block boundary.
- **Sidecar rename + config-representation reconciliation.** `args.json` → `config.json`, folded together with reconciling the three config copies a run dir now holds (sidecar, `config.input.json`, the `.pt` block). The traps are pre-mapped in [6.26-2](../2026-06/6.26-2-survey-sidecar-config-io.md).

## D — consciously parked: the behavior axis

The two gating questions — co-residency strategy (in-process Compat vs the repo-copy orchestrator), then fidelity scope (how many version boundaries to keep fidelity across) — gate the *broader* behavior-axis path, not any near increment. Their trigger is the first barrier: a non-additive change old checkpoints can't be carried past. Barriers are always a choice, and current practice (additive, config-gated evolution) erects none, so leaving these questions open costs little for now. Everything behind them — `arch_version`, golden tests, the Compat builder — stays parked with them. Detail lives in [6.26-7](../2026-06/6.26-7-checkpoint-config-critical-questions.md) and [6.26-5](../2026-06/6.26-5-checkpoint-config-synthesis.md).

This parking is a verdict, not an omission: these read like "open questions to resolve soon" in the records, but nothing near-term needs their answers.
