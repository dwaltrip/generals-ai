# Goldens naming pass — working record

*Date: 2026-07-20. Status: complete. Item 1 of the second set of pre-build items ([7.15-3](7.15-3-goldens-handoff.md)): replace the effect-class codes (E1/E2/E3) and the channel-class labels with plainer vocabulary. Concepts unchanged. The vocabulary originates in [the confounds framework](../confounds-framework.md), which gets the renames once the pass concludes. How far beyond it they reach is an open item below.*

## Settled

**Impact labels** (formerly the effect classes):

| old | new |
|---|---|
| E1 (recipe change) | `recipe-change` |
| E2 break | `contract-break` |
| E2 repair | `contract-repair` |
| E3 ruler | `metrics-change` |
| E3 task | `mechanics-change` |

Notes on the choices:

- `mechanics-change` replaces "task" because the old name invited a misreading: the bot's task never changed, and what usually draws this boundary is our implementation of the game changing. The full class definition lives in the legend.
- The labels compose: one change usually carries several impacts.

**Record field names**: the classification is the `impacts by surface` block (formerly the "effect class" field) plus a `recipe-change: yes/no` field. Each line of the block maps one boundary-producing surface to the impacts it generated. The recipe-change field sits apart because a recipe-change creates no boundary on its own. Field definitions live in the legend ([7.20-2](7.20-2-boundary-record-legend.md)). The framework's word "surface" was kept rather than replaced with something self-describing: it does prose work across the docs ("a guarded surface"), and the legend defines the fields at the point of reading.

**Surface labels**, shortened for record use:

| framework row | record label |
|---|---|
| Obs build, shared path | `obs` |
| Live inference path (obs build, action decode) | `live-path` |
| Forward semantics (same model shape) | `model-forward` |
| Training targets / labels | `training-targets` |
| Loss definition | `loss-func` |
| Eval protocol / metric definitions | `eval-protocol` |
| Model shape | `model-shape` |
| The game itself | `game-rules` |

The framework's ninth row, training-only code/config, deliberately has no label: a change there is a pure recipe-change and produces no boundary record (the legend covers this).

Two deliberate non-collisions: the eval-protocol surface is never labeled "metrics" (that word belongs to the `metrics-change` impact), and the game-rules surface stays distinct from the `mechanics-change` impact (a fog-leak fix has surface `obs` and impact `mechanics-change`).

**The legend**: records are decoded by a reader-facing legend that lives with the ledger, drafted in [7.20-2](7.20-2-boundary-record-legend.md).

**Channel-class labels** (7.10-2 §4's arithmetic classes, recorded per channel in the channel summary), with the default config's census as evidence the labels fit:

| old (7.10-2 §4) | new | members (default 110-channel config) |
|---|---|---|
| exact {0,1} indicator | `binary` (values 0 and 1) | 58: visibility, ownership masks, persistent map, last-seen-owner one-hot, historically-seen, opp-has-seen, opp-contacted, player-status, city-inference (zero-stub) |
| exact small rational | `category-encoded-exact` | 12: ownership-transition history (codes 0, −1, +0.5, 1 + k/8), opp-captured-by (codes −1, 0, 1..7) |
| correctly-rounded constant division | `int-scaled-by-divisor` | 24: army and land broadcasts, timestep, land-delta (a data-dependent integer over a fixed divisor) |
| log-scaled | `log-scaled` (unchanged) | 16: visible army magnitude, last-seen armies, turns-since-seen, BFS ×8, army-delta history ×5 |

Notes on the choices:

- The middle two classes are both bit-stable across platforms and library versions, for different reasons, and the names reflect the split. `category-encoded-exact`'s code palette uses only small ints and power-of-2 denominators, which floating point represents exactly, so no rounding occurs anywhere. `int-scaled-by-divisor`'s values do round (1/100 is not exactly representable), but IEEE-754 fully specifies division rounding, so equal inputs give equal bytes everywhere. "Small rational" was dropped from both names because it distinguishes nothing: both classes hold small rationals, and what separates them is dyadic (power-of-2) denominators vs not.
- The four classes stay distinct rather than collapsing the middle two into one exact class: the table is cheap, the why-stable distinction is what the env-upgrade churn classification reads, and the channel summary's stats treatment will differ by class anyway.
- A forward pointer for the channel-summary contents discussion: class is not the only axis. About half the channels (the broadcast planes: scalars, contact/capture codes, player status) hold one value over the board, where spatial stats like nnz or center of mass carry nothing.
