# Cold-read design review prompt — goldens first cut

Drafted 2026-07-15 for a later fresh-session review. Before launching: confirm the doc set is still current (7.15-2 still the authority, no newer revision) and spend a minute checking for session-only facts the docs don't carry.

---

You are doing a fresh-eyes **design review** of the "behavior goldens" first cut: a golden-test tripwire for the training pipelines of a generals.io bot project. No code exists yet beyond a measurement probe, so review the design, not an implementation.

**Fixed constraints** (inputs to the design, not up for review — though "this design violates its own constraints" is always in scope):

- Solo hobbyist developer, roughly six months of remaining project life.
- A hard repo-size ceiling, including git-history growth.
- The tests must fire at commit time on the developer's pinned machine (M1, pinned Python environment). That machine is the authoritative platform.

**The documents**, in reading order, all under `docs/2026-07/` unless noted:

1. `7.15-2-goldens-first-cut-scope-revision.md` — the current design authority. Where any docs conflict, this one wins.
2. `7.12-1-behavior-goldens-first-cut-v2-overview.md` plus its appendix `7.12-2-departures-from-7.10-2.md` — authoritative for everything 7.15-2 §3 lists as carried forward.
3. `7.09-1-behavior-goldens-design-sketch.md` — the original sketch. Still the record for the flows vocabulary (flow 0 through flow 6) and the deferred goldens for `model.forward()`.
4. `7.15-1-goldens-probe-results.md` — the measurement record backing 7.15-2's numbers. Treat it as evidence, and feel free to check whether the design's claims actually follow from it.

An earlier detailed design (`7.10-2-behavior-goldens-first-cut-design.md`) is largely superseded; consult it only if you need the deep detail behind something 7.12-1 compressed.

**Approach this however you think most valuable.** Candidate angles, none mandatory:

- **Chain coherence.** The docs form a supersedence chain, and the authoring convention is that changes are called out (precedence headers, 7.15-2 §3's carried-forward list, update lines). Audit whether that convention worked: assemble the single design the chain describes and look for statements in the older docs that land on neither side of the carried/superseded boundary, carried-forward text that silently assumes artifacts the revision dropped, terms whose meaning drifted since 7.09-1 coined them, and inventories (the guarded/not-guarded table, the deferred lists, the flows) that no longer agree across docs.
- **Fit to purpose.** 7.15-2 §1 gives two scenarios as the system's purpose. Does the reference design actually serve them? And is the two-scenario model itself right, or is there a realistic third scenario it misses?
- **The coverage exposure.** Under this design, detection is exact for what the fixtures execute and blind to everything else, so fixture selection carries the system's residual risk. Is that weight placed well, and is the fixture-selection apparatus (the event-class checklist, its tags, the corpus query) up to carrying it?
- **The drop/defer record.** 7.15-2 §5–§6 drop or defer substantial machinery, each with reasoning. Given the constraints above, is anything dropped that the constraints and scenarios actually demand? Argue specific items, not the general posture.
- **Unstated assumptions and risk surface.** What is the design quietly relying on that could fail, and what happens when it does?
- **Build-readiness.** Could a competent developer implement the first cut from these documents alone? Name anything underspecified, ambiguous, or apparently living only in unstated context.

**Output**: rank findings by severity, and for each one cite the doc and section, state the problem plainly, and separate genuine design risks from documentation inconsistencies from clarity or taste issues. Be direct — if a decision seems wrong, say so and argue it. If something is good, you can say that too, briefly; the review's value is in what needs attention. Take whatever length the review needs.
