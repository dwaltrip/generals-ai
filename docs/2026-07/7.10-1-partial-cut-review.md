# Design review — behavior-goldens partial cut (7.09-1 §11-Q3)

*Date: 2026-07-10. Fresh-perspective technical design review of the partial first cut only: obs golden + targets golden with synthetic fixtures, plus the shared machinery (linear regen core, sidecars, boundary stub + blocking test, size guardrail) and flows 0–3. Forward goldens and hash-fill are context, not targets. Claims were checked against the code (`packages/training/training/bc/`, `packages/eval-tools/tests/test_obs_path_parity.py`) and the companion docs (confounds framework, 7.08-1, 7.06-2).*

## Verdict in brief

The partial cut is a sound idea and its standalone value is, if anything, understated by the doc: after it lands, all three historical boundary classes have a tripwire (two via the new goldens, the third via the existing parity test), while the forward goldens guard a class that has never actually produced a boundary here. But the partial cut inherits the doc's weakest sections. The design effort so far went overwhelmingly into the forward goldens (hash-fill, mutation check, comparison policy), and the obs/targets goldens are sketched at one line each — yet they are the half being proposed for building first. Four things need design decisions before build: the fixture route (genuinely undecided, though the doc reads as if settled), the verification story (the partial cut has no equivalent of §5), the config-point scope of the obs/targets goldens (the guard-by-default principle is only designed for forward variants), and the obs reference storage format (which silently determines whether flows 2 and 4 can be diagnosed at all). One factual problem: §11-Q5's "intentional obs-vs-targets asymmetry" appears to restate a stale TODO banner that 7.08-1 already flagged as misdescribing the code — encoding it into fixtures as written would bake a wrong model of current behavior into the tripwire.

Findings ordered by severity.

## 1. The fixture route is the biggest open design choice, and the doc treats it as settled

§2 says "hand-built synthetic sim fixtures (code, not data)" — one line, no alternatives discussed. But "code, not data" is ambiguous between two genuinely different routes:

- **(a) Hand-built sim dicts**: code that constructs the `sim` arrays directly (ownership/armies snapshots, `death_events`, `capture_events`, `neutralize_events`, `cities_present_at`, …).
- **(b) Scripted sim games**: code that drives `sim_core` with deterministic controllers and reads the realized game back — the existing parity test's approach (`test_obs_path_parity.py` marches a general down a lane and round-trips through `write_eval_game`).

These differ on almost every axis that matters to the partial cut:

- **Validity.** The sim dict has consistency invariants nothing checks: a capture event must match the tile-transfer in the ownership snapshots, `cities_present_at` must match general→city transitions, and so on. Route (a) can silently produce a fixture that *means* to encode a neutralize but doesn't cohere — the golden blesses fine and guards a nonsense input, and the event-class checklist is satisfied only on paper. Route (b) gets consistency for free.
- **Event-class control.** Route (a) places events exactly where the checklist wants them (a `t % 50 == 0` production tick, a tied removal, a capture at a chosen frame). Route (b) has to *provoke* them through play — plausible (the `afks` parameter in `step_tick` gives surrender control; captures are scriptable), but brittle: a sim tweak can change the realized game so the intended capture never happens.
- **What fires the golden.** Under (b), a sim-rule change moves the fixture's realized game and fires the obs golden. Read against the framework, that's arguably a feature — "the task itself" is a surface in the framework's §1 table with no row in the sketch's §3 inventory, and sim-rule changes are exactly the E1+E2+E3-task class. But it muddies attribution: "obs golden fired" no longer means "obs code changed." Under (a), sim-rule changes are invisible to the goldens entirely (and the parser golden is deferred), so that surface stays fully unguarded.
- **Live-path reuse.** The live obs path needs a `sim_core.State` (`state_to_view` in the parity test) — hand-built dicts can't drive it. Route (b) fixtures could be fed to the existing parity test directly, closing its known event-coverage gaps as a side effect of the same work. Route (a) fixtures can't.

A hybrid handles route (b)'s brittleness: scripted games plus **fixture self-asserts** — each fixture declares which event classes it must contain, and a check fails loudly if the realized game stops containing them ("fixture no longer covers class X" instead of a confusing golden diff). That also turns the §11-Q5 checklist from a design-time artifact into a standing machine check.

I lean toward (b) with self-asserts, mainly on the validity and live-path-reuse points. But the actual recommendation is weaker: the doc should *make* this decision explicitly, with the trade-offs on the table, before the "~1d fixtures" estimate is trusted. Route (a)'s consistency burden in particular could blow through that estimate (hand-building coherent snapshots around a capture — tile transfer, army halving — is fiddly), or worse, be met by cutting corners on coherence.

## 2. The partial cut has no verification story — §5 doesn't transfer, and the doc doesn't say so

§5's central claim — "'Did we enumerate every fill special-case?' converts from a foresight problem into a verification problem" — is the doc's best idea, and it applies **only to the forward goldens**. For the obs/targets goldens, the equivalent question is "did the fixtures exercise the paths and event classes that matter?", and the answer offered is:

- a `coverage.py` line-coverage report in the sidecar (W6), and
- a manual event-class checklist (§11-Q5).

Line coverage measures *execution*, not *sensitivity*: it can't tell you a fixture contains a capture-while-alive tick, a `t % 50` production tick, or a tied removal — those are semantic properties of the data, not lines of `memory.py`. And the checklist is precisely the foresight-dependent enumeration §5 congratulates itself on eliminating for forwards. So the half of the system being built *first* ships with the *weakest* assurance, and the doc's framing ("coverage-report sidecar, turning silent gaps into a visible list") overstates what it delivers.

This is fixable cheaply, and the fixes belong in the design:

- **Fixture self-asserts** (finding 1) — the checklist encoded as executable assertions on each fixture's realized events. This is the real analogue of "guard-by-default": a checklist entry with no fixture asserting it fails, the way an unblessed registry entry fails.
- **Input-side mutation spot-checks** at bless time: perturb a fixture input (shift an event tick by one, move a general, toggle a visibility-relevant tile) and assert the frozen outputs change. A handful of these certifies the golden isn't comparing something insensitive to its input — a miniature of §5's idea, pointed at the data instead of the weights. Cheap, and it reuses the same regen "check" phase.
- If route (a) is chosen anyway: a sim-dict validity checker (events consistent with snapshots) as a bless-time health check.

Related: the regen core's "check" phase (build → run → **check** → write) has designed content only for forward goldens (health + mutation). For the partial cut it is currently an empty box. Deciding what goes in it is part of the build, not an afterthought — otherwise the linear core's shape gets frozen around "check = nothing."

## 3. §11-Q5's "intentional obs-vs-targets asymmetry" contradicts the current code — resolve before fixture design

§11-Q5 says: "One known trap to encode deliberately: the intentional one-frame obs-vs-targets asymmetry at capture-while-alive ticks (`bc/obs/memory.py`, ~1% of frames)."

Checked against the code, this describes the **pre-6.18** state, not the current one:

- 6.18-6 documented the asymmetry when `alive_mask` used `death > t` (victim reads dead at frame `t` while the obs board still shows their tiles).
- The 6.18 fix moved the masks to `>= t`, and `player_status.py` now documents this explicitly as "the correct test against the obs's pre-event board snapshot" — i.e. the fix *removed* the obs-vs-targets asymmetry (`player_status.py:119-139`).
- Stronger: aliveness cannot diverge between obs and targets anymore, because both read the same functions — `channels._cat_player_status` imports `alive_mask`/`present_mask` from `bc.player_status` (`channels.py:41,315-316`), the same functions `elim_targets` re-exports.
- The likely source of the stale claim is the surviving `TODO(obs-alive-tick-seam)` banner in `memory.py:219-228`, which still says alive_mask "uses death>t … reads them DEAD at the same frame t" — exactly the artifact 7.08-1 flagged as misdescribing the code after the fix.

There *is* a residual one-frame seam at capture ticks, but it's a different one, and it's intra-obs: `step_memory` applies capture events at their event tick (`memory.py:397-403`), so the `opp_captured_by` broadcast channel flips at frame `t` while the board snapshot at `t` is pre-event. Whether that's intentional is undocumented.

Consequence for the partial cut: fixture design intends to "encode the trap deliberately" — but as written, the trap description is wrong, and a fixture built to it would freeze a wrong mental model into the system meant to be the ground truth about behavior. The queued 6.18 trail repair (fix or retire the stale banner, status-line 6.18-6) should happen **before or with** fixture design, and §11-Q5 should be re-derived from the code rather than from the banner. This also demonstrates the doc's own point about record rot — the stale record propagated into the design doc for the system meant to prevent stale records.

## 4. Config-point scope of the obs/targets goldens is unspecified — §3's "guarded" rows are over-broad as designed

Guard-by-default ("no curation step between 'variant exists' and 'variant guarded'") is designed concretely only for the forward goldens, via the variant registry. The obs/targets goldens have no stated analogue, and they need one:

- **Obs**: there are at least two occupied obs-config points — the current default (`player_status_channels=True`, 104 channels) and `LEGACY_OBS_CFG` (the frozen 96-channel config that keeps pre-status checkpoints supported). If the obs golden freezes only the default, the gated legacy path — the very gating mechanism that *prevents* E2 boundaries — is unguarded: a regression in legacy reconstruction breaks old checkpoints silently with all goldens green. Same question for `dense_history_n` variants if any non-default value is occupied.
- **Targets**: the elim variants (`time_bin`, `next_death`, the alive-only path) plus core targets (policy, value, mask) each need frozen coverage, or §3's "Targets / labels — guarded (designed)" is really "the default variant's targets — guarded."

This has two knock-ons the doc doesn't note:

- The route-1 coupling (§11-Q1) applies to the **partial cut**, not just the forward goldens: "which obs-config points get fixtures" is the same supported-set question. A hand-listed interim set is fine for a first cut, but that's a curation step, and it should be labeled as a deliberate, temporary violation of the guard-by-default constraint rather than left implicit.
- Flow 1 is written in forward-variant vocabulary ("registry entry lands with the variant code"). Its obs analogue — a gated channel-group addition, like the player-status channels were — must leave existing config points' goldens green (the gate's whole promise) while requiring a bless for the new point. That works only if obs goldens are per-config-point. Worth one sentence in the flows.

## 5. Obs reference storage is unresolved, and it silently determines whether flows 2 and 4 are diagnosable

Numbers: one obs frame is `[96–104, 32, 32]` fp32 ≈ 390–420 KiB raw. A 16-tick, 2-perspective fixture, all frames frozen, is ~13 MiB raw per config point; multiple fixtures × two config points lands in the tens of MiB raw. Compression will crush it (the arrays are mostly zeros and broadcast constants — the parser-output precedent measured ~30:1 on similar data), but "compressed obs references land well under 500 KiB" is listed as assumed, and the plausible compaction move — storing hashes instead of arrays — has a cost the doc doesn't surface:

- Flow 2 step 1 promises "a magnitude report: which channels, how big." Against a hash, no magnitude is computable — only "changed."
- Flow 4's churn-vs-behavior classification (§6) needs per-channel deltas. Against hashes it is impossible. And note the partial cut has **no mutation-margin floor either** (that instrumentation is forward-golden machinery, out of scope here) — so the reference format is the *only* classification signal the obs golden will have.

The design should commit to a reference format that keeps diagnosis possible: e.g. full arrays for a sampled subset of (tick, perspective) frames plus per-frame-per-channel hashes and stats for the rest; or full arrays throughout if the measured compressed size permits. Either is fine — the point is that "shapes/hashes/stats" in the sidecar bullet is currently hiding a decision with flow-level consequences, and appendix B's own transferable lesson ("binary or oversized snapshots defeat every defense because the diff can't be read") cuts against the compact end of the spectrum.

Targets references are per-frame scalars and [8]-arrays — no issue there.

## 6. Environment churn will hit the numpy goldens too, and the partial cut has no aid for it

§6's environment-upgrade story (classification against the mutation floor, `--environment` mode) is forward-golden machinery. But the obs path is not churn-immune: `log1p` appears throughout the obs channels (visible armies, last-seen armies, turns-since-seen, the signed-log army deltas), and transcendentals are exactly the category §6 itself names as the byte-stability risk across numpy versions (SIMD dispatch and libm changes have moved last-bit results in numpy's history). On the pinned machine with a pinned numpy, exact compare is fine; the first numpy upgrade is the test, and with only flows 0–3 built it will be handled manually.

Manual is acceptable for a first occurrence — that's the doc's own deferral policy — but one cheap structural aid is worth designing in now, because it falls out of the reference format (finding 5): **split the diff report by channel arithmetic class**. Most obs channels are exact {0,1} indicators or small integer ratios — those can *never* legitimately churn, so any diff there is behavior, full stop. Only the log-scaled channels can carry ulp churn. That two-line classification rule is the numpy-path analogue of the mutation-floor aid, and it costs nothing if channel classes are recorded in the sidecar at bless time.

## 7. The stub's fields are E2-shaped, but the upcoming fires are mostly E1+E3 — and repeat-regen mechanics are unspecified

The stub asks: `gated? / affected checkpoints? / disposition?` — the vocabulary of an E2 model-contract break. But walk flow 2 through the actual next stretch of work: the elim arc modifies target definitions, and per the confounds framework's own emphasized case ("the case easiest to misread is a targets or loss change"), an in-place targets change is **E1 + E3-ruler, with no E2** — target code never executes at inference. For that class, "gated?" is close to a category error and "affected checkpoints?" is the wrong question; the meaningful record is the measurement-comparability line — which metrics/curves/dumps stop comparing across the date (exactly what 7.08-1 §boundary-3 records for the 6.18 fix). If the ritual forces engineers to answer E2 questions about E1 changes several times in a row, the answers become boilerplate, and boilerplate is the on-ramp to the rubber-stamping W7 worries about.

Fix is cheap and aligns the stub with the framework the whole design is built on: make **effect class (E1 / E2 break / E2 repair / E3 ruler / E3 task)** the first stub field, and let it drive which follow-up fields must be filled (E2 → gated?/affected checkpoints; E3 → comparability line; E1 → record only). Surprising, given the lineage, that the stub fields don't mention the framework's classes at all.

Second ritual-under-load gap: flow 2 says regen "appends a boundary stub," and active experimentation means regenerating several times on a branch before landing. Five regens → five stubs? The rule needs stating: one *pending* (unfilled) stub per golden set, updated in place by subsequent regens, becoming append-only once filled/committed. Without it, the ritual degrades into stub-janitoring exactly during the arc.

On W7's base-rate argument itself: "flow 2 a few per quarter on project history" is roughly consistent with the record (three boundaries in the May–June month), but the coming quarter is *targeted* at the targets surface, so the rate will spike by design. That doesn't invalidate the ritual — each fire is a genuine boundary of exactly the class the 6.18 incident shows needs recording, and firing on intentional changes is the system working. But the doc should stop leaning on "fires are structurally rare" for this period and lean instead on "fires are cheap and correctly-shaped" — which is only true after the two fixes above.

## 8. Sequencing accounting: the partial cut is ~2d, not ~1d, and it covers about half the elim arc's contact surface

Two honesty adjustments to §11-Q3's framing:

- **Cost.** The Q3 sizing buries the regen core inside the "forward goldens + regen core ~1d" line item and the stub wiring in its own ~0.5d. The partial cut needs both (linear regen, sidecars, stub + blocking test, size guardrail, AGENTS.md note). Realistic partial-cut cost is fixtures+goldens ~1d **plus** most of the shared machinery — call it ~2d — before the design work findings 1–5 call for.
- **Coverage during the arc.** The elim arc touches targets *and* loss/metrics (§11-Q6 says so itself). The partial cut guards the targets half; loss and metric definitions stay open — and per the framework those changes are the E3-ruler class that corrupts curve and metric comparability, the exact confound type the arc's own analyses (6.13–6.21 pre/post-fix comparability line) have already tripped over once. So "build the partial cut, then do the arc" buys a tripwire for half the surfaces the arc will move. Still plausibly worth it — but the sequencing decision should be made with that fraction visible.

## 9. Standalone value: stronger than claimed — worth stating correctly

§11-Q3's "covering two of the three historical boundary classes" is accurate but undersells the position after the partial cut lands:

- Boundary class 1 (obs-content, shared path) → obs golden. ✓
- Boundary class 3 (targets/labels) → targets golden. ✓
- Boundary class 2 (live-path-only divergence) → already guarded by the existing parity test — verified: it is differential, byte-exact per tick, and drives the live handshake exactly as the runner does.

So after the partial cut, **every class that has actually produced a boundary in this project has a tripwire**, while the forward goldens guard a class (in-place forward-semantics change, same shapes) that is historically empty here — shape changes fail loudly at `load_state_dict(strict=True)` per the framework, and the forward path has produced zero surveyed boundaries. That is a genuinely strong argument for the partial cut as a standalone artifact, and the doc doesn't make it. (It cuts the other way too: it weakens the urgency of the forward goldens, whose design absorbed most of the session.)

One synergy to bank if route (b) wins finding 1: the parity test's known gaps are event coverage and player count — the same event-rich scripted fixtures the goldens need would close them nearly for free by running the parity comparison over the fixture games.

## 10. Smaller notes

- **Parity-gap description inaccurate (§2).** "Known gaps: perspective slot 0 only" — the test actually iterates *all* perspectives of its fixture (`for s in range(n_players)`, both paths). The fixture is 2-player (`small-1.txt`: g0, g1), so the real gaps are: only 2 real slots (though slots 2–7 are exercised *as phantoms*), one small map, and no capture/neutralize/surrender events. Fix the line — it matters because finding 9's "class 2 is guarded" claim leans on an accurate account of what parity covers.
- **fp32 pin vs fp16 production default.** Goldens pin fp32 obs, but production default is fp16 obs; the divergence point is only the final buffer-write cast in `build_obs`, and §3 labels device/dtype branches out of scope — fine, but worth one sentence acknowledging the golden guards a dtype path production no longer runs by default, so the label is a known scope choice rather than an oversight.
- **Freeze below the torch seam.** The numpy-seams claim checks out (`build_obs`, `build_mask`, `elim_targets`, `player_status` are torch-free), but `encode_frame` itself returns torch tensors — the goldens should freeze at the numpy layer beneath it and say so, leaving the (trivial) tensor-conversion layer unguarded by choice.
- **Fixture `meta`.** The targets golden's value target reads `value_target(meta, k)` — synthetic fixtures need a `meta` dict (placements) too. Unmentioned; trivial, but belongs on the fixture checklist.
- **Shared-machinery forward compatibility (review angle 6): low risk.** The linear regen core, registry notion, and stub are generic. One schema note: mutation margins and coverage summaries are golden-type-specific sidecar sections — make them optional per golden type now so the obs/targets sidecars (which have neither, or have input-mutation results instead per finding 2) don't need a schema migration when forward goldens arrive.
- **Stale-stub edge case.** The stub-blocking test makes repo-wide `pytest` hostage to a prose file's state. That's the design's point, but one edge needs a rule: an unfilled stub left by an abandoned branch/regen blocks everyone until hand-deleted. Cheap answer: regen without a subsequent bless-commit should be trivially revertable (stub lives in the same diff as the regenerated references — which flow 2 already implies; just state it).

## Summary of what should change before building

1. Decide the fixture route explicitly (hand-built dicts vs scripted sim games); recommendation: scripted games + fixture self-asserts (findings 1, 2).
2. Give the partial cut a verification story: self-asserts as the executable event-class checklist, input-side mutation spot-checks at bless, and a defined "check" phase for obs/targets blesses (finding 2).
3. Re-derive §11-Q5 from the code after the 6.18 trail repair; as written it encodes a stale claim (finding 3).
4. Specify per-config-point scope for obs/targets goldens (default + `LEGACY_OBS_CFG`; all elim variants), and label the interim hand-listed set as a temporary guard-by-default exception (finding 4).
5. Commit to an obs reference format that preserves magnitude diagnosis, and record channel arithmetic classes in the sidecar for churn classification (findings 5, 6).
6. Make effect class the stub's first field and specify pending-stub update-in-place semantics (finding 7).
7. Re-state the sequencing trade with honest cost (~2d) and coverage (targets yes, loss/metrics no) — and with the stronger standalone-value claim the doc is entitled to (findings 8, 9).
