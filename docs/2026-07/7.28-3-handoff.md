## 1. Next session: the registry sketch

The main questions:

- **Medium and internal shape.** The registry must reconcile "one reviewable data file" with three mechanisms that are not plain data: elim variants enumerated from `aux_heads.REGISTRY`, the asymmetric fixture-by-config matrix (targets variants run on all fixtures, legacy obs on 2 to 3 designated ones), and per-fixture purpose notes. The current preference is a hybrid Python module: config-point dicts as literals, the fixture list as data with notes, and the pairing as a few lines of code. The design test for any candidate shape: how reviewable is the diff when a new point becomes guarded.
- **The elim-variant enumeration mechanic.** Two forms: a cross-check test (every variant in `aux_heads.REGISTRY` has at least one goldens entry) or auto-generated entries. The wrinkle favoring the cross-check form: a new variant has no stored config yet, and if it brings a new knob, even the shape of its config is unknown, so there is nothing to auto-generate. Confirm this rather than assume it.
- **The legacy equality assert.** The stored legacy obs dict is asserted equal to the live `LEGACY_OBS_CFG` symbol, so the golden and the checkpoint-load path cannot drift apart. Simple, and just needs a home.
- **Smaller decisions**, any of which can be left to the build:
  - Reference paths: stored per entry, or derived from (golden type, point name, fixture id). Leaning toward derived (one less thing that can drift).
  - Naming for the two obs points ("default" / "legacy" or otherwise). The names end up in directory paths, test IDs, and ledger entries. The four targets point names are already fixed (7.28-2 §3).
  - Directory layout under `packages/training/tests/goldens/`: fixtures, references, registry, environment record, ledger. Interacts with the report naming item (7.22-2 §8) and the layer-1 committed-replay location.
  - Where the strict-keys and legacy-equality asserts live: at registry load, or as standalone tests.
  - How an entry without blessed references fails. Essentially no freedom here: a parametrized test that fails with a "run regen" message.
  - Writing down the guard rules beside the registry (minimal per 7.12-1 §6: likely a structured comment or a small dict).

Inputs from 7.28-2: the §5 handoff questions (what makes up a golden's stored identity, where stored dicts become config instances, and whether the registry reserves a slot for values outside the two configs) and the cut-list items that point at the registry sketch (stored dict serialization format, and whether shared target keys are stored once per fixture or once per point).

Facts carried from this session so they are not re-derived:

- The two obs point dicts: default is `{dense_history_n: 5, obs_dtype: "fp16", player_status_channels: True}`, and legacy is the same with `obs_dtype: "fp32"` and `player_status_channels: False` (plus the equality assert above).
- `elim_bin_edges` likely has one occupied value: the live default and the checkpoint back-fill are the same tuple. Verify against real checkpoints when the registry entries are written. If it holds, the question of which guard rule applies to edges (enum or scalar) is moot.

One scoping call to make at the session's start: whether the regen tool and fire report design folds into the registry sketch (the surfaces are adjacent) or gets its own session.

## 2. What still needs design thought

This session ranked the first cut's items by importance and by how underspecified they are. The list below is what survives: the items that still need design attention, with current status. Everything absent from it (the walk core, the hash reference writers, the ledger and blocking test, the environment record and its test, the mutation and structural tests, the promotion of the probe modules) was judged ready to build in that review.

- **Registry and config discipline**: half settled. TargetsConfig is done (7.28-2). The remainder is §1.
- **The regen tool and its fire report**: undesigned. Neither the CLI shape nor the printed fire report has had a design pass. The fire report is what an author reads at every fire, and ledger entries copy the changed-channel list from it. Once the registry sketch lands, this is the least clear high-importance item left.
- **Targets references**: much improved this session. The guarded layer is pinned to the numpy target functions, and two details that would otherwise have surprised the build (reference dtypes, shared-key layout) are named in 7.28-2's cut list. The remainder (file layout and registry keying) rides with the registry sketch.
- **The channel summary report writer**: designed (7.22-2), with its writer-design session still expected before that part of the build.
- **The dataset parity test**: well specified (7.23-1 §4), with one care added this session: its comparison must cover every emitted sample-dict key, because the torch wrap layer's guarding rests entirely on it (7.28-2 §2 and cut list).
- **Fixture selection**: deliberately not pre-designed. It is an exploratory session whose outcomes cannot be known in advance, and it stays deferred to near the end of the build.
