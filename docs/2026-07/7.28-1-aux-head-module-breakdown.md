Here's the breakdown. I read the whole module, every consumer in `bc/`, the checkpoint/inference path, the analysis-side consumers, the tests, and the 6.21-1 design doc.

## What the module is

`bc.aux_heads` is the variant-gated auxiliary-head machinery that came out of the elim-head arc (design doc: `docs/2026-06/6.21-1-aux-head-spec-registry-refactor.md`). Before the refactor, "which elim variant is on" was an `if variant == ...` branch at roughly eight call sites across the pipeline. Now each variant is a **spec**: a stateless singleton object bundling everything the pipeline needs from that head, and the call sites loop over specs instead of branching.

Four files:

- `base.py` defines the `AuxHeadSpec` Protocol and `AuxLossResult` (a metrics dict plus the head's own count tensor).
- `registry.py` holds `REGISTRY` (variant string → spec singleton) and `spec_for(variant | None)`.
- `time_bin.py` — per-player time-to-elimination over ordinal bins, on the death/`alive_mask` domain.
- `next_death.py` — one cross-player softmax per frame for "who is removed next", on the board-removal/`present_mask` domain, with an optional soft target (`next_elim_target_tau`).

A spec carries two kinds of things:

- **Static string attrs** (`output_key`, `metric_keys`, `term_key`, `count_key`, `weight_attr`) that let generic code fold the head into totals and reports without knowing the variant. `weight_attr` names the `LossConfig` field holding the head's loss weight, read via `getattr`.
- **Methods spanning three runtime contexts**: `encode_targets` runs in numpy-land in dataloader workers; `build_head` / `loss` / `dump_records` run on the torch/train side; `build_eval_meter` / `eval_update` / `eval_summary` run in the val loop. `validate` checks cross-cutting config rules. Imports inside methods are lazy so workers stay numpy-light.

The per-game precompute (`ElimCtx`) is deliberately *not* in the spec: it's variant-independent and lives in `bc/targets/elim_targets.py` (which itself sits on `bc/player_status`, the alive/present-mask logic shared with the obs encoder).

## The dispatch spine

The variant string lives in one config field, `ModelConfig.elim_head_variant` (`None` = off, the default). Only three places resolve it:

1. `BCModel.__init__` calls `spec_for`, builds the head module via `spec.build_head`, and stores `active_aux_specs` (a tuple, empty or one element today).
2. `dataset.encode_frame` calls `spec_for` in the worker (the model object isn't available there).
3. `TrainConfig.__post_init__` loops over the whole `REGISTRY` for `spec.validate`.

Everything downstream never re-resolves: `active_aux_specs` is threaded `BCModel` → `ModelOut` → `LossOut`, and the accumulator, val loop, and dump capture all iterate that tuple. Both `ModelOut` and `LossOut` assert in `__post_init__` that the declared specs' keys were actually emitted.

## Angle 1: a training run

- **Config.** Arch knobs (`elim_head_variant`, plus the time_bin-only `elim_bin_edges` / `elim_pool` / `elim_head_hidden`) live in `ModelConfig`; objective knobs (`lambda_elim`, `elim_target_tau`, `elim_bin_weights`, `next_elim_target_tau`) in `LossConfig`. Validation is layered: `ModelConfig` checks the variant string against `ELIM_HEAD_VARIANTS` (a torch-free duplicate of the registry keys — `model_config` deliberately can't import the torch-bearing registry, and a test pins the two lists in sync), and `TrainConfig` enforces the cross-cutting rules ("λ_elim > 0 requires a head", plus each spec's own rules like "next_elim τ requires the next_death variant", checked over *all* registry specs so a knob aimed at the wrong variant is caught).
- **Data.** `train.build_dataloader` passes the variant and edges into `IterableDataset`. Per game, the dataset builds one `ElimCtx` via `precompute_elim`; per frame, `encode_frame` always emits `alive_mask` (when any elim context is requested) and then adds `spec.encode_targets(...)` for the active variant. A separate `emit_alive_mask` flag serves consumers (probes) that want aliveness with no head.
- **Model.** The head is constructed only when a variant is set, so an off model carries zero extra state_dict keys and pre-elim checkpoints load `strict=True`.
- **Loss.** `bc_loss` loops `active_aux_specs`, each returning an `AuxLossResult`. `_assemble_total` is the single definition of the total (shared between the per-batch tensor path and the epoch-mean float path in `LossAccumulator.summary`, so the two can't drift): it adds `getattr(cfg, weight_attr) * metrics[term_key]` per spec. Convention across heads: the hard CE is the cross-run-comparable reporting metric, the soft variant is the trained objective, and they're the same tensor at τ=0.
- **Accumulation/logging.** Each head's epoch means are weighted by its *own* count (alive-pair count for time_bin, defined-next-victim frames for next_death), not the sample count. Per-batch JSONL rows and the console "Aux" row are generic loops over specs (with a flagged-as-hack dedup so τ=0 doesn't print identical hard/soft numbers twice).
- **Checkpoints.** The arch (including the elim fields) rides in the `.pt`, so an elim checkpoint self-describes. `checkpoint.py` handles history: pre-elim checkpoints back-fill `elim_head_variant=None` from `LEGACY_ARCH`, and the retired `elim_head_enabled` flag migrates to `"time_bin"`. Notably, the *loss* config (λ_elim, the τs) is not in the checkpoint — it lives only in `args.json`, a gap 6.21-1 explicitly defers.

## Angle 2: evaluating

- **In-loop val (`eval/run.py`).** `run_val` pairs each active spec with a meter from `build_eval_meter` (specs are shared singletons, so per-pass mutable state lives in the meter, not the spec). time_bin gets `ElimMeter` (top-1 bin accuracy, soft-floor margin, prediction-entropy collapse alarm); next_death returns `None` — its only in-loop number is the CE passing through from the accumulator, everything else is offline. `eval_summary` merges each head's numbers into the val dict that lands in `epochs.jsonl`.
- **Val dumps.** `FrameRecordCapture.add_batch` loops `out.active_aux_specs` and pushes each spec's `dump_records` columns (fp16 prob distributions, hard per-frame CE, targets, masks) alongside the core policy/value columns. The same capture serves two producers: the in-training per-epoch dump (`dump_val_frames`) and the offline `scripts/stratified_val_loss_analysis.py dump` run against a saved checkpoint, both over the shared `iter_val_forward`. `write_val_dump` prints a dump-vs-val-loss cross-check per head.
- **Game-play eval (eval-bot / Modal).** Checkpoint load reconstructs the model from the recorded arch, so an elim-trained checkpoint *does* rebuild its aux head (the strict state_dict load requires it) and the forward computes aux logits that `decode_batch` simply ignores. One flag: `inference.py`'s docstring says "inference builds no aux head", which is misleading for arch-bearing elim checkpoints — the head is built, its output is just unused.

## Angle 3: analysis on an arch variant

The dump columns are the interchange format, and the analysis side deliberately does *not* go through the specs:

- `analysis/elim_metrics.py` computes time_bin confusion/per-bin metrics from dump columns.
- The fq toolkit's `families/elim_head_debug.py` builds the next_death table (targets + army columns + the lowest-army rule) by calling `bc/targets/elim_targets.py` directly, then `join_dump` merges a model dump's predictions in. Consumers: `head_vs_rule_by_margin.py`, `victim_gap_distribution.py`, `family_a_victim_baselines.py`.
- `probe_runs/who_dies_next.py` (frozen-trunk probe) reuses the dataset's `next_elim_target` with its own head.

So the target logic has two consumer paths: production encoding goes builders → spec → dataset, while analysis goes straight to the builders. `elim_targets.py`'s docstring names itself the intended shared home, and that has held.

## On the goldens intersection (general thoughts only, as asked)

`scripts/goldens_probe/walk.py` already builds **both** variants' targets by calling `elim_targets` directly (one `ElimCtx` per variant, since the sentinel is edges-dependent) rather than dispatching through `spec.encode_targets`. That means today's golden walk pins the target *builders*, not the spec adapter layer (the numpy→tensor packaging and key naming in `encode_targets`). Whether the goldens should also cover the spec layer, or whether the existing walk-parity test already closes that gap, is the seam question your build will hit. The registry's "enumerate all variants" shape is a natural fit for goldens (loop `REGISTRY`, emit each spec's targets), so the eventual intersection looks tractable.

## Improvement observations (secondary)

Most of the real debts are already flagged in-repo, which is itself a good sign:

- **Residual variant-keyed sites outside the spec seam.** `train.py`'s val console block checks `val_summary.get("elim_soft")` / `get("next_elim")` directly, `write_val_dump`'s cross-checks are per-variant `if`s, and the time_bin-only `elim_bin_edges` dump-meta line is a documented residual. Harmless at two mutually-exclusive heads; a third head would multiply them. Candidate spec hooks if that happens: a per-spec console-row formatter, dump-meta contribution, and dump cross-check.
- **Naming skew.** The machinery is head-neutral ("nothing here names elim") but every boundary field is elim-named: `ModelConfig.elim_head_variant`, `BCModel.elim_head`/`elim_output_key`, the dataset's `elim_*` constructor params, and `next_death` actually keying on board-*removal*. 6.21-1 defers the rename because the strings are config/dump/checkpoint-facing; fine, but it's the main comprehension tax on a fresh reader.
- **Single shared `lambda_elim` / single gate.** Safe only because the variants are mutually exclusive. The loss loop is already additive-ready (per-spec `weight_attr`), but a genuinely additive second head needs a per-head λ and a config shape change. Known and deferred; worth keeping in mind since your aux-head arc memory says the strategic fork is still open.
- **Loss config not persisted in checkpoints.** An elim checkpoint self-describes its arch but not its objective (λ, τs). Already the leaning-yes deferred item in 6.21-1, and it intersects your checkpoint-config-versioning arc more than this module per se.
- **Loose typing at the seam.** The Protocol takes `ctx: Any`, `cfg: Any`, `arch: Any`, `meter: Any`, and `LossOut.aux` is an untyped dict (with an in-code TODO). Works, but pyright can't catch a spec reading a key the dataset didn't emit. The `_aux_keys_without_tau0_dup` helper also hard-assumes exactly a (hard, soft) metric pair.
- **Small stale docstring** in `inference.py` (the "builds no aux head" line noted above).

Overall the design is in good shape for what it does today: one config field gates everything, the spec threading means downstream code can't disagree with the model about which heads are live, the shared `_assemble_total` keeps batch and epoch totals consistent, and the test file pins exactly the wiring (registry ↔ config-list sync, output-key mapping) that could silently drift.
