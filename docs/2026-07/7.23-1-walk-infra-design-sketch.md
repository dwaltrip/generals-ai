# Walk infrastructure — design sketch

*Date: 2026-07-23. Settles the walk-composition seam question, the last pre-build item for the goldens first cut ([7.15-2](7.15-2-goldens-first-cut-scope-revision.md) §8, [7.15-3](7.15-3-goldens-handoff.md)): the decision, the reasoning behind it, and the work that is deferred. Convergence vocabulary (materialize, F1, derivers) from [6.17-3](../2026-06/6.17-3-fq-probe-convergence.md).*

## 1. The decision

- The walk core is built as shared, torch-free infrastructure. Candidate home: `training/bc/walk.py`, a sibling of `obs.py` and `mask.py`. It is not goldens-side code to be promoted later.
- The goldens are its only initial consumer. `dataset.py` is not touched during the cut.
- Targets stay consumer-side, permanently: a design choice, not a deferral (§3).
- A standing dataset-vs-shared-walk parity test ships with the cut (§4).
- The dataset migration is a queued follow-up after the cut lands (§5). The fq migration happens when fq itself needs the walk (§6). Two small extractions (`walk_end_t` and `make_elim_ctx` becoming shared functions) touch `dataset.py`, so they land with the dataset migration instead of the cut.

This approach lets us prototype the shared walk infra without risking changes to the battle-tested `dataset.py` code that runs during training.

## 2. The seam, briefly

The goldens probe's prototype walk (`scripts/goldens_probe/walk.py`, from the 7.15-1 measurements) duplicates about 40 lines of orchestration from `IterableDataset._walk`: the per-tick ordering (visibility, then `step_memory`, then `build_obs` and `build_mask`), the `end_t` truncation rule, `ElimCtx` construction, and `raw_order` assembly.

The remaining core logic for training data assembly (obs, mask, memory state, visibility, the target functions) is already abstracted out in separate modules. The new golden tests guard these.

The `dataset.py` code is relatively complex and finicky. It has some testing, but it isn't comprehensive. Additionally, the new goldens don't guard `IterableDataset._walk`. This is why a parity test (§4) is important for the full refactor.

## 3. The walk module, v1

The API sketch: the walk takes `(sim, meta, k, obs_cfg)` and returns an iterator of per-frame `(t, obs, mask)` plus a context bundle (likely the board dims and slot order: `H`, `W`, `perspective_slot`, `opp_slots`, with exact contents confirmed at build time). The generator owns `init_memory` and BFS-cache setup, the per-tick visibility → step → build ordering, and the `end_t` bound.

The interface works because two lines coincide at the yield: the torch-free/torch line, and the line where the consumers stop agreeing. All three consumers want the loop byte-identically. The parts they want differently all happen after the yield: the goldens compute every target variant per frame, the dataset emits one spec-mediated variant per instance, and fq wants columns.

Full unification would also be expensive here: the spec layer (`spec.encode_targets`) emits torch tensors, so a shared walk that also emitted targets would require hoisting the numpy/torch boundary out of the specs. Keeping targets consumer-side avoids that work.

The design discipline is to design for three consumers while building for one. Nothing goes into v1 that only a future consumer would exercise: no timer hooks, no emit knobs, no skip-obs flag. The usual risk of designing for absent consumers is low here because all three consumers' requirements can be read from existing code (the dataset's from `_walk` itself, fq's from the workarounds in `build_frame_table`).

The probe's `walk_fixture` minus its targets block is approximately the right module already. The build work is mostly relocation: move the file into its shared home, move the targets block out to the goldens consumer, and add comments documenting the situation.

## 4. Validation for the full refactor

The "parity test" runs a committed goldens fixture through both implementations: (1) the prod `IterableDataset` and (2) the newly built shared walk.

The resulting obs, mask, and targets from both are compared, expecting byte-level equality. The emitted bytes can change depending on both ObsConfig and the elim-head variants, so the full test matrix is: ObsConfig point × elim-head target variant. The inputs for the matrix are pulled from the registry's stored configs. This test doesn't share the goldens' numpy-only constraint (no blessed references), so `IterableDataset` using torch is not an issue.

It is corpus-free. `IterableDataset` takes `(sim_path, k)` pairs pointing at a sim/meta npz pair, and committed goldens fixtures are exactly that format. (Contrast the one existing walk test, `test_walk_stops_at_elim_timestep`, which depends on the local corpus, skips when it is absent, and asserts only a frame count.)

The test has three roles:

1. It guards the interim seam: dataset-walk drift becomes a loud test failure instead of a silent divergence.
2. It is the first content-level test `_walk` has ever had.
3. It is the dataset migration's acceptance test, built early.

The first passing run is also the first direct check that the two walks agree. The scenario of a goldens walk that silently differs from `_walk` is therefore ruled out at ship time.

Handling a parity fire takes one extra step compared to a goldens fire: the author either updates the shared walk to match (the goldens then fire, and the boundary record follows) or reverts the dataset change.

The parity test has a limited lifespan, at least in part:

- Its purpose is to verify that (1) the new shared implementation matches the old dataset.py code and that (2) this remains true for the period where both implementations exist as live code. 
- Once the full migration is complete and `dataset.py` uses the new shared walk, the obs and mask comparisons become trivially true and can be deleted.
- On the other hand, the targets comparison remains meaningful after the migration. Target construction is intended to stay on the consumer-side indefinitely (§3), so dataset.py and the goldens will continue computing targets via different code paths. One might reasonably ask if it is worth keeping the parity test around to guard this remaining surface. This sketch leaves that as an open question.

At migration time, the parity test is complemented by a one-off check: run the dataset before and after the change on a few real games and compare the output bytes. This covers real-game variety beyond the committed fixtures. It is a throwaway script, deleted after the migration lands.

## 5. The dataset migration (queued follow-up)

In the migration, `_walk` becomes a thin consumer of the shared walk. Torch packing, the `frame_info`/`sim_frame` attachments, the group/load/shuffle layers, and the per-game amortization (npz load and elim precompute shared across a game's perspectives) all stay dataset-side.

The tests already treat `_walk` as a swappable seam (`_IdentityDataset` overrides it), and `test_walk_stops_at_elim_timestep` transfers cleanly: after the migration it pins the shared walk's `end_t` rule through the dataset path, complementing the goldens pinning it through theirs.

The biggest predicted complication is profiling. The dataset's timer sections (`perspective_setup`, `encode_frame`) cut across the part of the loop the generator would own. After the migration, obs-build time folds into the cost of `next()` and init time into the first iteration. The resolutions are mundane (pass an optional timer in, or accept coarser sections and re-baseline the throughput profile), but this is where the design is least clean. The question is settled at migration time, with throughput measured against the real placement.

The migration is verified by the parity test plus the one-off byte comparison (§4). The `walk_end_t` and `make_elim_ctx` extractions land here as well.

## 6. The fq migration (pull-based)

The shared walk is the materialize primitive of the fq↔probe convergence direction: 6.17-3's mature picture has materialization as a walk producing columns with provenance. We will try to lightly keep this fq-aware posture as we build v1, while focusing mostly on the single near-term consumer: the golden tests.

Two payoffs arrive with the migration:

- Deletion: `build_frame_table`'s identity workarounds (the `sample_idx` to full-split-position mapping, game boundaries recovered by pointer identity on the sim dict, the forced `shuffle_buffer_size=0`), its use of the `unsafe_attach_sim_frame` seam, and the numpy→torch→numpy round-trip all disappear. fq loops its own games and gets indices directly.
- The import graph: fq's F1 standalone rule is stated in 6.17-3 as an import-graph constraint, yet `frame_table.py` imports `training.bc.dataset`, which drags in torch and the training loader. After the migration, F1 holds at the import graph, not just in spirit.

One design question attaches to the migration: `emit_cols` currently free-rides on the dataset's target encoding, and calling the numpy target functions directly likely dissolves it into ordinary derivers. This is probably a simplification, but it changes how specs are declared, so it needs its own design pass rather than a mechanical port.

The probe toolkit is not a fourth walk consumer: its own migration is gated on the fq-table engine proving out (6.17-3 §6), and it would consume fq tables, not the walk, leaving the walk's consumers at three.

## 7. Accepted residue and future pressure

- After the full refactor, there is a small, fairly simple loop or shell that stays duplicated between the dataset and fq. For each game, we load the npz, build the elim ctx, and then run the walk for each perspective. This is likely not worth refactoring out at any point.
- The per-consumer target calls stay duplicated: a small surface (which shared functions get called with which arguments). The upcoming elim-head work will likely touch this logic. The parity test provides coverage for the `dataset.py` implementation.
- `fq` may want an option to skip the obs construction. It dominates the runtime of the walk and not every `fq` table will need it. See the deferred lazy-obs/FrameView idea from 6.17-3 §6. This isn't part of v1, but we should try to leave the door open for a "skip obs" flag while implementing the shared walk.
