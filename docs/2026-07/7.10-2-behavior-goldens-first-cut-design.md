# Behavior-goldens first cut — obs and targets goldens over frozen fixtures

*Date: 2026-07-10. Design for the partial cut that 7.09-1 §11-Q3 named, worked out in this session against the [7.10-1 review](7.10-1-partial-cut-review.md) and a code investigation. [7.09-1](7.09-1-behavior-goldens-design-sketch.md) remains the record for the forward goldens and hash-fill; its comparison policy (§6), flows (§7), and design constraints (§9) carry over here except where amended. Vocabulary (E1/E2/E3, boundaries, surfaces) from [the confounds framework](../confounds-framework.md).*

## 1. Scope and standalone value

The cut: an **obs golden** and a **targets golden** over frozen fixtures, plus the shared machinery they need — the regen tool, diffable sidecars, the boundary stub with its blocking test, and the size guardrail — supporting flows 0–3.

The standalone value (adopting 7.10-1 finding 9): once this lands, every boundary class that has actually occurred in this project has a tripwire. The obs-content class (incident 1) gets the obs golden, the targets/labels class (incident 3) gets the targets golden, and the live-path-divergence class (incident 2) is already guarded by the existing obs-path parity test in eval-tools. The forward goldens guard a class — in-place forward-semantics change with unchanged shapes — that has produced zero boundaries here, which is why they can wait without leaving a historical failure mode uncovered.

Out of scope, deferred deliberately: forward goldens and hash-fill, the sim golden (§2), loss/metrics goldens, and the flow 4–5 tooling (environment upgrades and rename bridges are handled manually at first occurrence, per 7.09-1's deferral policy).

## 2. Architecture — goldens read a frozen input layer

The goldens never run the sim or the parser. Each fixture is a **committed pair of npz files** — the sim dict plus its `meta` (the parser-output format) — and the golden tests load it, run the obs/targets pipelines, and compare against frozen references. This gives the property everything else leans on: **a fire can never be an input change**, because the input is a file in git. On the pinned environment that means a fire is an obs/targets code change. Across an environment upgrade, the §4 channel-class split classifies the diff.

This splits the system into two layers:

1. **Fixture production** (source material → committed npz) — authoring-time, rare.
2. **The goldens proper** (committed npz → frozen obs/targets outputs) — this cut.

A layer-1 golden (re-derive each npz from its source and compare) is deferred: sim_core changes very little these days, and the no-structure-without-a-consumer rule applies. When built, it would guard the sim rules and the duplicated writer paths (`write_eval_game` is a hand-copied near-twin of the parser's `write_sim_output`). Until then those surfaces stay unguarded, same as today.

Two implementation consequences of the frozen layer:

- **No sim_core or torch at test time.** The obs pipeline and the target functions are pure numpy. Torch first appears in the frame-assembly layer (`encode_frame` and the aux-head specs' tensor wraps), and the goldens freeze and compare at the numpy layer beneath that, so the test path needs no Rust build and no torch. The assembly seam itself (variant dispatch, which keys a variant emits, `raw_order` construction) is thereby **deliberately unguarded** in this cut, the same labeled-gap status as the layer-1 writers above.
- **The committed shape follows an existing precedent**: `replay-parser/tests/fixtures/` already commits input blob + expected output per scenario with separate seed/regen/test scripts. The goldens reuse that pattern under `packages/training/tests/goldens/` (fixtures, references, sidecars, registry), next to the code they guard and clear of every gitignore rule.

## 3. Fixtures

**Primary source: pulled from the replay corpus.** Fixtures are real games selected from the collected replays and parsed to npz by the real parser. At no authoring cost, this buys realistic boards, real event configurations, and real `meta` (placement, perspective ids, elimination timesteps — no synthesis needed). Selection is a query over the parsed event arrays rather than fixture authoring, and provenance rides along since the parser stamps `replay_id` into the npz. It also composes with existing coverage instead of duplicating it: the replay-parser fixtures already guard wire → sim-dict, so a replay-pulled fixture extends a chain whose upstream link is already tested. And frozen data cannot rot — a fixture's events are baked in, so "the fixture no longer contains the capture" is not a failure mode.

One note on the committed data: the meta file carries real player usernames — fine while the repo is private, worth a fresh look if that ever changes.

The costs: events land wherever the corpus offers them, not at surgically chosen ticks; and when a golden fires inside a real game, nobody knows from first principles what tick 137 "should" contain. Mitigation for the second: keep **one or two tiny scripted toy fixtures** (in the style of the parity test's marching-general game) purely for debuggability when investigating a fire. The architecture is identical — a toy is scripted once, written to npz, and committed like any other fixture. Two schema obligations come with that. First, toys stamp the provenance keys the parser writes (`replay_id` placeholder, `version` — `write_eval_game` omits them today), so all fixtures share one npz schema. Second, toys need `meta` synthesized: the parser's metadata builder consumes parser-internal `ReplayData` and computes little itself (mostly `elim_timestep` — placement and perspective ids are supplied by its caller), so reuse would buy schema conformity rather than logic. The plan is a small toy-side helper that conforms to the parser's meta schema.

**Realistic board sizes, by choice.** The obs tensor is `[C, 32, 32]` regardless of board size — padding fills the rest — so board realism costs nothing in shape and shows up only as content (a realistic board fills ~half the padded area, a 5×6 toy ~3%). Realism is the lower-risk option by the same argument 7.09-1 used to reject tiny model configs for forward goldens: a toy board has a different fog/BFS/padding profile, and whether sensitivity on a toy transfers to production-sized inputs is unverified. The toys of the previous paragraph are debugging aids, not the coverage backbone.

**Count and growth.** Planning basis: 20–30 fixtures over the project's life — estimated by counting obs-affecting deltas to date (roughly 6–8 in two months of active work: two fog-leak fixes, the army_delta production subtraction, game_progress→timestep, the stale-live-obs fix, the status-channel group, dense history) and assuming each future change of that kind tends to want a targeted fixture. (The extrapolation implicitly assumes the delta rate falls off after the current buildout phase — continued at the historical rate it would pass 30 within a year.) The initial build is a small set (~5) covering the event-class checklist: captures, surrenders, neutralizations, a `t%50` production tick, a 3+-player game, and a next_death tie case. The checklist itself is a pre-build item (§9) and must be re-derived from the code — not from 7.09-1 §11-Q5, whose "intentional obs-vs-targets asymmetry" restates a stale banner (§8).

**Freeze-time asserts.** Each fixture declares the event classes it exists to cover, and fixture production asserts them against the npz's event arrays — plain asserts, no reporting framework. On frozen data these fire again only if a fixture file itself is regenerated (the schema-migration event, §7). Their day job is to make the initial selection honest and to document each fixture's purpose in code.

## 4. References and comparison

The frozen reference serves two consumers with different needs, and the format follows from separating them:

- **The machine, at test and fire time.** Pass/fail is exact equality on the pinned platform (7.09-1 §6 carries over: zero standing miss-window, tolerance mode available off-platform). On a fire, the magnitude report — which frames, which channels, how big — is computed live by diffing the new outputs against the stored arrays. Full diagnosis therefore requires stored arrays, not hashes — hashes alone would reduce every fire to "changed."
- **The human, reviewing a bless commit.** Binary npz diffs are unreadable, and 7.09-1's own survey lesson is that unreadable snapshots defeat every regen defense. The JSON sidecar exists for this reader: per-channel stats and hashes as diffable text, so a regen commit shows what moved and by how much in the diff itself.

**What gets frozen.** Every frame is computed — the obs memory is path-dependent (`init_memory → step_memory(0..t) → build_obs(t)`), so there is no skipping ticks. But only **event-adjacent frames are frozen as full arrays**: capture tick ±1, death ticks, the first production tick, t=0, the final tick. The choice sits between two rejected alternatives. Freezing *all* frames doesn't fit the size budget at the planning ceiling (the top of §3's range, ~30 fixtures). Freezing only the *final* frame under-guards: dense-history channels hold a sliding window and `last_seen_*` values get overwritten, so early transients wash out of later frames — and the event-adjacent frames are exactly where the guarded transients live. The pick is a **deterministic rule over the fixture's event arrays**, implemented in the regen tool rather than kept as a hand list, so every regen re-freezes the same frames and the pick survives fixture re-parses. Per-fixture additions, if any, go in the registry.

An all-frames layer rides along for localization: per-frame-per-channel stats, so a fire between frozen frames still points to a tick and channel with rough magnitude, though without the exact old values (recoverable from old code via git if ever needed). At corpus game lengths this layer is not small — ~2 KiB/frame across T in the hundreds is megabytes per fixture as JSON — so it is stored as **compact binary alongside the references and counted in the size budget**. The reviewable JSON sidecar carries only per-channel aggregates plus the frozen frames' stats — a multi-MiB stats JSON would itself be the unreadable diff the sidecar exists to prevent.

**Dtype: freeze what the config produces.** The default config's contract is fp16 output — that is what training and inference consume — so its golden freezes fp16, with no fp32 shadow: a change below fp16 resolution is invisible to production too. The legacy config's golden is fp32 and doubles as the sensitive canary: fp16's coarse mantissa absorbs most ulp-level churn, so environment-upgrade noise lands densely in the fp32 references and only sparsely in fp16 (a last-bit fp32 change survives the downcast only when it straddles an fp16 rounding boundary). Expect a scattering of flipped fp16 values across the suite, not zero. Both patterns read as churn when confined to log-scaled channels.

**Channel arithmetic classes.** The sidecar records each channel's class: exact {0,1} indicator, exact small rational, correctly-rounded constant division, or log-scaled. Only 16 of the default config's 110 channels are log-scaled (the single transcendental transform in the pipeline). Everything else is exact or correctly-rounded and **can never legitimately churn across numpy versions — any diff there is a behavior change**. This classification is the numpy-path analogue of the forward goldens' mutation-floor aid, and it is what makes the first environment upgrade classifiable by hand under flows 0–3.

**Targets references** are per-frame scalars and [8]-arrays — full storage, all frames, no curation.

**Size budget.** Raw per frozen frame: ~384 KiB (96-channel fp32) or ~220 KiB (110-channel fp16). At ~15 frozen frames per fixture that is 5–6 MiB raw fp32. Compression on realistic boards is the open variable — plausibly anywhere from ~3:1 to the ~30:1 measured on parser `[T,HW]` arrays — which is why the **size-and-runtime probe (§9 item 3) is the first build step**. Acceptance thresholds: ~1–2 MiB compressed per fixture is tolerable, and the repo stays well under 100 MB (packed history is ~11.7 MiB today, and committed fixture inputs are small — parser output averages ~55 KiB/game). The **size guardrail test** asserts the goldens directory stays under its ceiling. It is net-new (no size-asserting test exists in the repo) and ships with the cut, making the ceiling structural. Whether references pack as one npz per (fixture, config) or one per fixture is a build-time packaging choice with no design weight.

The directory budget is not the whole budget: **git history grows under regen churn**, and the guardrail can't see it. An obs-surface fire re-blesses every obs reference (obs code is shared across fixtures), and compressed npz barely delta-compresses in git, so each full re-bless adds roughly one reference-set of permanent pack growth — tens of MiB at the planning ceiling. And §3's own planning basis says such fires recur. The growth trajectory is therefore part of the budget: expected re-blesses per year × bytes per re-bless must sit well inside the repo's rough overall size budget, set by Daniel to keep the repo lightweight. That pushes toward fewer and smaller frozen frames (the §9 probe informs how hard), and toward the regen tool printing the pack-size delta at every bless — keeping history growth visible where the guardrail is blind.

**Suite runtime is a budgeted quantity too.** Every test run recomputes the full obs walk per (fixture, config, perspective) — path dependence allows no skipping. The project's throughput work found obs-build to be the bottleneck, so at the planning ceiling this is plausibly minutes of pytest. The standard escape (demote to a slow tier) would quietly forfeit the commit-time-tripwire property that is the system's primary requirement, so the knobs get chosen deliberately, with measurements in hand: cap registered perspectives per fixture, truncate fixtures at selection time (a game prefix ending shortly after the last needed event is a valid sim history), and only if those fall short, split into a fast default subset with the full battery pre-merge. The §9 probe measures per-fixture walk time alongside compressed size.

## 5. Golden configs and the registry

**Identity: a bare sub-config dict, every field explicit.** An obs golden's config is the three `ObsConfig` fields (`dense_history_n`, `obs_dtype`, `player_status_channels`); a targets golden's is the dataset-side knobs (`elim_head_variant`, `elim_bin_edges`, `emit_alive_mask`). Those knobs are bare dataset-constructor kwargs today — no class declares them — so the cut introduces a small **`TargetsConfig` dataclass** that the dataset consumes and the golden anchors on. Without a declared field set the strict-keys assert below has nothing to check, and the next target-affecting kwarg added with a default would silently stay out of golden identity.

The identity is not a full `StoredConfigBlock`: a full block drags the entire `TrainConfig` (learning rate, batch size, paths) into the golden's identity and picks up migration churn whenever any config field anywhere changes. The miniature-synthetic-checkpoint idea from 7.09-1 §4 earns its keep for forward goldens, which have state_dicts and exercise checkpoint loading. It is deferred with them, and different golden types carrying different identity granularity is fine.

**The collapse-to-current hazard, closed in three parts.** The hazard 7.09-1 §4 worried about — a golden config that silently moves with live code — decomposes into three mechanisms, each with its own answer:

1. *Config built from live defaults* (`build_model_cfg(**overrides)`-style): avoided by storing every field explicitly. Settled in 7.09-1 already.
2. *A later-added field back-filled by its dataclass default*: caught by a **strict-keys assert** (~5 lines) — the stored dict's keys must exactly equal the dataclass's field set, so adding a config field breaks every golden config load loudly, and the fix is writing the historical value into each frozen dict: a manual mini-migration forced at the right moment. (`ObsConfig` currently has no field defaults, so incomplete construction already fails. The assert is insurance for fields added later *with* defaults, which is the usual way fields get added.)
3. *Semantic drift in the config class itself* (a `__post_init__` behavior change, a field reinterpretation): no storage format catches this — but the paired frozen outputs do, because semantic drift moves the produced obs/targets and fires the reference diff. The frozen-instance-of-a-live-class hazard becomes self-detecting once the instance has an answer key attached.

**The legacy point gets one extra line of protection**: its golden config is stored as its own independent dict, plus an equality assert against the live `LEGACY_OBS_CFG` symbol. Independence means an edit to `LEGACY_OBS_CFG` cannot silently move the guarded point. The assert means the golden and the checkpoint-load path cannot drift apart unnoticed. The assert lives in its own small test file — `LEGACY_OBS_CFG`'s module imports torch (and is itself slated to move in the checkpoint refactor), and the golden tests proper stay torch-free.

**The guarded set (all occupied config points today):**

| Golden | Config points |
|---|---|
| Obs | default (n=5, fp16, status on → 110 channels); legacy (n=5, fp32, status off → 96 channels) |
| Targets | core targets (policy, value, the policy-legality mask from `build_mask`, and `valid_mask` — always on); alive-only (`emit_alive_mask` with no elim head); `time_bin`; `next_death` |

`dense_history_n` occupies only 5 (the N-sweep never ran). Elim variants key off the `aux_heads` `REGISTRY` (not the duplicate `ELIM_HEAD_VARIANTS` tuple) — and as **test parametrization**, not just a name source, so a newly registered variant auto-fails as unblessed.

**Over-guard now; let route-1 prune later.** The supported-checkpoints policy call (route-1) does not block this cut. Guarding an unsupported point costs a registry entry and some KiB, while pruning later is flow-6: delete the entry and its files in a reviewable diff. So the cut guards every occupied point, and the hand-listed registry is a deliberate, labeled interim curation step — the guard-by-default machinery (an entry with no reference fails as "unblessed — run regen") carries over from 7.09-1 unchanged.

One limit on that carry-over: guard-by-default fully transfers only where registration rides a code change, which here is the elim `REGISTRY`. Obs-point occupancy is a fact about trained checkpoints, not code — nothing fails if a checkpoint trains at `dense_history_n=10` tomorrow while the registry lacks that point. Two partial forcing functions:

- a structural test, shipping with the cut, that every `GATED_CHANNEL_GROUPS` key is enabled in at least one registry entry — so the next gated channel group cannot ship unguarded
- later, route-1 deriving the registry from the supported-checkpoint set

Until then, n/dtype occupancy stays manual — part of what the interim-curation label covers.

The registry is data — one file listing (golden type, fixture, config dict, reference path) — so the eventual route-1 policy can adopt or generate it rather than compete with it. Checkpoint↔config-point mapping stays out of the registry — "affected checkpoints" is a boundary-stub field, answered at fire time.

**The fixture × config matrix** is asymmetric, driven by storage cost. Targets: all variants on all fixtures — references are tiny. Obs: the default config on all fixtures, and the legacy config on a designated subset of 2–3 fixtures that exercise the gate. The legacy path is the same code with the status group disabled and fp32 output, so it needs gate coverage, not the full event battery. This is curation, and it is visible in the registry.

**What goldens deliberately don't guard: default values.** Changing a default (`elim_bin_edges`, a flag) fires nothing — goldens pin explicit config points, and a default change is an E1 recipe change, record-only territory. Green goldens must not be read as "defaults unchanged."

**Flow-1's obs analogue** (one sentence 7.09-1's flows lacked): a gated channel-group addition — the player-status group being the precedent — must leave existing config points' goldens green (that is the gate's promise) while the new config point fails as unblessed until its regen. This works because obs goldens are per-config-point.

## 6. The check phase at bless

The regen core's check phase has concrete v1 content for this cut (it was designed only for forward goldens in 7.09-1):

- **Required-event asserts** per fixture (§3), run at fixture production and re-run at bless.
- **Sanity checks**: shapes and dtypes match the config point, values finite, every registered perspective yields frames.
- **Channel-class table** written into the sidecar (§4).

Deferred from the check phase, explicitly: input-side mutation spot-checks (perturb a fixture input, assert frozen outputs move — real assurance, but separable) and line-coverage reporting. The event asserts carry most of the verification value for this cut.

## 7. Regen tooling and the boundary stub

**Two commands, not one tool with modes**, because the two regeneration acts differ in rarity and dependencies:

- **Fixture production** — authoring-time, rare; runs the parser (and sim_core for toys); produces committed npz.
- **Golden regen** — the flow-2 ritual; numpy-only; never touches the sim or parser. Linear core: load fixture npz → run the obs/targets pipelines → check phase (§6) → write references + sidecar + boundary stub.

**Fixture-schema migration is a named event** — the input layer's analogue of flow 4, and like it, handled manually at first occurrence. When the sim-dict schema changes (a new key, a dtype or shape revision — the format has been redesigned before), every committed fixture goes stale and must be regenerated from source, which suspends the frozen-input property for that commit. The hygiene at first occurrence is a two-step in the spirit of flow 5's bridge: regenerate fixtures with the pipelines unchanged and show the references byte-identical (or explain the diff), then land any pipeline change separately. Never mix the two in one commit.

**The stub leads with effect class.** Its first field is the confounds-framework classification — E1 / E2 break / E2 repair / E3 ruler / E3 task — and that field drives which follow-ups must be filled:

- E2 — gated? and affected checkpoints?
- E3 — which comparisons stop being valid across the date
- E1 — record only

The rationale (7.10-1 finding 7, adopted): the upcoming elim-arc fires are mostly E1+E3 targets changes with no E2, and forcing "gated? affected checkpoints?" on those several times in a row would breed boilerplate answers, which is how rubber-stamping starts.

**Pending-stub semantics**: one pending (unfilled) stub per golden set, updated in place by subsequent regens on the same branch, append-only once filled and committed. Active experimentation regenerates freely without tending the stub, and an abandoned regen reverts in one step because the stub rides the same diff as the regenerated references.

**The blocking test** (~10 lines) refuses to pass while a stub has unfilled fields — regen never yields a green run by itself.

On fire rates: the coming quarter's work lands on the targets surface, so flow-2 fires will spike by design. The defense is not 7.09-1's "fires are structurally rare" but "fires are cheap and correctly shaped" — the effect-class stub asks the right questions and the pending-stub rule keeps repetition out of the ritual.

An **AGENTS.md note** ships with the build: what a golden failure means and which flow applies.

The stub's destination file (a boundaries ledger vs a section of the eventual support-policy doc) remains open — 7.09-1 §11-Q2 unchanged.

## 8. Corrections to the prior record

The code investigation behind this design surfaced errors in both prior docs, recorded here so they stop propagating.

- **Channel counts**: the two occupied obs points are 96 (legacy) and **110** (default) — verified by running the config code. 7.10-1's "96–104" is wrong.
- **Parity-test gaps**: the test iterates *both* real perspectives of its 2-player fixture, and its fixture has no phantom slots 2–7 (8-slot padding is exercised only synthetically). The real gaps: 2-player only, one small map, no capture/neutralize/surrender events, t<50. This corrects 7.09-1 §2's "perspective slot 0 only" and refines 7.10-1 finding 10.
- **7.09-1 §11-Q5 is stale** (7.10-1 finding 3 confirmed): the 6.18 fix moved the alive/present masks to `>= t`, and the obs channels and elim targets read the same `bc.player_status` functions, so the obs-vs-targets aliveness divergence Q5 describes is structurally impossible in current code. Q5's claim traces to the surviving `TODO(obs-alive-tick-seam)` banner in `bc/obs/memory.py`, which still asserts the pre-fix behavior.
- **The residual seam is intra-obs and undocumented**: at a capture tick, the frame mixes two tick conventions. `step_memory` flips `opp_captured_by` on the tick itself (event-time), while the board and status channels of the same frame still describe the pre-event board (snapshot-time — tiles transfer at t+1). No comment records whether this is intended. A golden freezes it as-is. The intent call should be made — or explicitly deferred with a note — at first bless.
- **The banner needs a rewrite, not deletion**: its description of the scoreboard channel reading the pre-event board is still accurate; only its claim about `alive_mask` is false.
- **The tied-army stalemate breaker** emits ordinary DeathEvents — verified in sim_core's kill path. This closes a question from 7.10-1: the breaker is the one event class a scripted game can't be steered into, so it was the last candidate for a fixture authored directly by hand as a raw sim dict (the fixture route 7.10-1 recommended against). Since breaker deaths look like any other death, no fixture needs to contain one. One nuance survives the check: breaker deaths, like never-removed surrenders, are death-without-removal, whose tail frames exercise `next_death`'s no-real-removal branch — a distinct target path that belongs on the event-class checklist.

## 10. Cost, sequencing, and the deferred inventory

**Cost**: medium for the cut itself, with the pre-build items above on top. The effort splits roughly evenly between fixtures + goldens and the shared machinery (regen core, sidecars, stub + blocking test, guardrail, AGENTS.md note — accounting adopted from 7.10-1 finding 8).

**What the elim arc gets**: the arc's targets changes land on a guarded surface — every in-place targets change becomes a loud flow-2 event with a correctly-shaped record. Its loss and metric-definition changes remain unguarded (the E3-ruler class; 7.09-1 §11-Q6 stands). Sequencing this build against the arc is still an open call — this doc sizes the work but doesn't decide the order (7.09-1 §11-Q3).

**Deferred, in one place**:

- the layer-1 sim golden (§2)
- the frame-assembly seam (§2)
- input-side mutation checks and coverage reporting (§6)
- fixture-schema migration tooling (§7 — manual two-step at first occurrence)
- flow-4 environment tooling and the flow-5 rename bridge (with forward goldens)
- forward goldens and hash-fill (7.09-1)
- loss/metrics goldens (open surface)
- extending the parity test's event coverage via the new fixtures (optional synergy, not this cut)
