# Revision records in the goldens lib, and `dynamics-change`

Date: 2026-10-03

**Daniel's level of review / sign-off for this note:** drafted by Claude from the session discussion. Reviewed by Daniel.

This session started on chunks 4 and 5, adapting their design to the lib/project split from pass 1. The first question was how the revision record format divides between the goldens lib and the project. Answering it meant checking which parts of 7.20-2's impact vocabulary are generic, which led to a generic version of `mechanics-change`.

The framework terms used below all come from [`confounds-framework.md`](../confounds-framework.md): the surfaces and the three tests are in its §1, the wrinkles are at the end of §2, and the incidents are in §4.

## Decisions

- The goldens lib will own the revision record format, including the vocabulary of surfaces.
- Each guarded surface is one of the framework's surfaces (its §1 rows). The goldens and the framework share one surface vocabulary.
- The impact label `mechanics-change` is renamed to `dynamics-change`, defined below.

The rest of the revision record design, including the surface types and the revision kinds, is in 10.03-2.

## 1. The revision record format: lib vs project

The concepts behind the record come from the confounds framework. Its two contracts and three tests contain nothing specific to generals, so they appear to apply to any ML project that keeps checkpoints and recorded numbers. Most of 7.20-2 is therefore generic:

- the fields: description, date, comparisons invalidated, `recipe_change`, and the mapping from surfaces to impacts
- the impact labels: `contract-break`, `contract-repair`, `metrics-change`, and `dynamics-change`

One field is not generic. 7.20-2's `channels` lists the changed obs channels, and 9.18-1 replaced it with the Extent. Obs channel names would come from the per-surface label hook (9.26-1 item 6), and appear in both the regen report and the record's Extent.

The surfaces are generic as well, since each §1 row is a standard stage of an ML pipeline. The lib will own the list. Each guarded surface corresponds to one of these surfaces: `obs` to "Obs build, shared path", and `supervision` to "Training targets / labels". Future guarded surfaces would fit the same way, such as the forward pass (`model-forward`) and the loss (`loss-func`). 10.03-2 covers the details, including the mismatch between the names `supervision` and `training-targets`.

## 2. `dynamics-change`

### The concept

Test 3 in the framework asks whether a change alters what recorded numbers mean, and it splits the answer in two:

- The ruler: metric definitions, label definitions, and eval protocol. A change here is a `metrics-change`.
- The world: in the framework's current wording, "game rules, or the information the game exposes to the model". A change here is a `mechanics-change`.

The world half has a generic version. A `dynamics-change` is a change to the world the model acts in. The same model, measured the same way, now faces a different problem. The world includes:

1. how it is generated or initialized (map generation, spawn placement)
2. how it evolves on its own, independent of anyone's actions (army growth, city production)
3. which actions are possible, and how they affect the world
4. what the world allows the model to observe (fog of war)

In practice the world is usually our implementation of it, such as a simulator. Fixing a bug in our sim is a `dynamics-change` in general, including a fix that brings the sim closer to the real game. A part of the world only matters if it can reach the training data, the model's actions or observations, or the evals. Anything that can't reach them usually isn't in the sim at all.

### What is not part of the world

- Which situations we choose to train or measure on. The rules that generate maps belong to the world, but the choice of which maps to evaluate on is protocol. Likewise, a training data mix or filter change is a recipe-change, and a new eval map set, opponent pool, player count, or test set is an eval-protocol change, so a `metrics-change`.
- Other agents. Their actions play out through the world's rules, but who they are is either data (the players in the replays) or protocol (the opponent pool, per wrinkle (g) on checkpoints inside the apparatus).
- Reward, labels, and metrics. These belong to the ruler.

### Relation to `metrics-change`

The two impacts both come from Test 3. Both break the measurement contract, and both have the same cure: re-measure the old side under current conditions. A `dynamics-change` does not also carry a `metrics-change` by default. When the world changes, eval numbers stop comparing because the game is different, and that effect is what `dynamics-change` records. `metrics-change` records a change to the ruler's definitions. A change carries both labels only if it touches the ruler too.

This holds even when a world change shifts the values of training targets. An elimination-rule fix in the sim would change the `next_death` target values, but the target code is unchanged. That is the dynamics change reaching data-derived numbers, not a `metrics-change`.

### Scope

The label fits projects where a model acts sequentially in some world: RL, imitation learning, game AI, robotics, and agents. In other projects it rarely applies. Without actions, the main case is a leak: an input carrying information the model shouldn't have at prediction time, such as target leakage. A fix to the code that produces the raw data can also be one, when it changes what the data says about the world, as a sim fix does here. Ordinary feature changes are input changes, as in section 3. Real-world drift is a separate case, covered in section 4.

### Why this name

- `environment-change` is the standard RL term. But the RL environment also includes the reward and the other agents, which the framework puts in the ruler and the protocol.
- `world-change` matches Test 3's wording, but isn't a standard ML term, and "world model" means something different.
- `dynamics-change` uses a standard term for how a world evolves, and is precise about the core of the concept. Strictly, RL's dynamics exclude the observation function, so our definition is a little broader.

## 3. Observability vs the obs surface

Both concern what the model sees, at different levels:

- Observability is part of the world: what the world allows the model to see. It is set by rules, such as fog of war. In generals the real game sets this allowance and our sim implements it.
- The obs surface is the concrete recipe for building the model's input from that allowance: which of the allowed information the model uses, and how it is encoded. It is on the subject side, in the runtime path.

This distinction suggests a rule for classifying obs-side changes. The rule is a proposal and isn't in the framework yet:

| Change | Example | Impacts |
|---|---|---|
| Re-encoding, same information | army_delta minus expected production | contract-break |
| More or less information, within the allowance | `dense_history_n`, a staleness fix | contract-break for a change to the shared path, or contract-repair for a fix to the live path only (incident 2). Numbers still compare as model quality, since the game didn't change and only the model's inputs did |
| Information beyond the allowance, or a fix for it | the fog-of-war leaks (incident 1) | contract-break and `dynamics-change`. Our implementation of the world was wrong, and the model played an easier game than the real one |
| A change to the observation rules themselves | a fog-of-war rule change in the sim | `dynamics-change`, plus a contract-break if the meaning of state fields changes (wrinkle (h)) |

The third row is the subtle one. A leak lives in obs code, but it is a bug in our world. The framework already notes that the location of an edit is only a loose guide to its surface.

Incident 2, the stale-live-obs fix, shows the rule at work. The world showed the current board, and our live encoder built the obs from the previous one. Only the inference path had the bug, so the model's inputs at inference differed from training, and the fix is a contract-repair. More generally, when the model sees something late, the classification depends on where the delay comes from. A delay introduced by our code is a contract problem. A delay introduced by the world is dynamics.

## 4. Notes for a later pass on the framework

None of these change the framework yet. The rename of `mechanics-change` to `dynamics-change`, in the framework and in 7.20-2, is also left for that pass.

- **The allowance rule refines wrinkle (a).** Wrinkle (a) covers obs changes that alter the information available, and treats each one as a world change. Incident 2 is labeled `mechanics-change` on that basis ("a blinder game"). Under the rule above, incident 2 is a contract-repair only. As far as we can tell nothing is lost, since the contract-repair column already marks the old era's eval numbers as incomparable.
- **Val set construction.** The val set is part of the eval protocol for the numbers measured on it: training curves and val-based analysis. Changing which samples it contains is a `metrics-change` for those numbers, unless each run pins its own val set. In this project each run does, by recording its split manifest (`bc/splits.py`), which includes `filter_version`. A filter change or a new manifest then only affects the runs that use it. Comparing curves across manifests needs a caveat, since they were measured on different val sets, but the history needs no boundary.
- **The name `metrics-change`.** The label means the definitions changed, not the values. The name invites the second reading. The pre-rename code, "E3 ruler", was more direct. Possible renames include `ruler-change` and `measure-change`.
- **One world.** The framework treats training and deployment as one world. A sim-to-real gap, such as live-server latency delaying observations in a way the training data never shows, isn't covered. This doesn't seem pressing unless live-server numbers start to matter. By contrast, a world change that reaches only some pipelines is already covered by Test 3's scoping rule: the affected kinds of numbers are the ones whose pipeline contains the changed code.
- **Incident 1's game-length leak was training-only.** The fix (`e04cad6`) changed the `game_progress` channel from `t / true_length` to `t / 1000`. The edited code, `build_obs`, is shared, but the live path already passed a 1000-turn hint in place of the true length, so live play never had the leak. The framework's incident 1 row ("the leaks made the earlier game easier") holds for the two fog-of-war leaks, which reached both paths, but not for this one. Classified per kind of number:
  - training curves and val-based analysis: `dynamics-change`, since they were measured with the leak
  - gameplay-eval numbers: no change
  - old checkpoints in live play: a train/serve skew from the start, which the fix doesn't change
  - training: a recipe-change

  More generally, shared code can have path-specific effects when its inputs differ by path. Test 3's scoping rule already handles this, but the framework doesn't point it out.
- **Real-world drift.** In projects whose data comes from complex, dynamic real-world processes, the world can change gradually, without any commit. This is in contrast to domains with simpler data, such as this project, which involves a game with well-specified rules. When a researcher knows that new data reflects a meaningful change in the world, they can optionally treat it like a new game version (see the worked example below): decompose it into data mix, protocol, and dynamics parts, and write a manual record. This is a judgment call, with no tooling behind it.

Ideas worth discussing later:

- **A pinning principle.** When an artifact records which version of something it used, a change to that thing may need only a caveat at comparison time, not a boundary. The val set note above is one instance, and gating is another.
- **Boundaries from data operations.** Events like a corpus regeneration change things without a commit. The framework doesn't say how to treat or date them.
- **The dynamics and metrics verdicts nearly coincide.** Saying so would lower the stakes of borderline classifications between the two.
- **Dependency and platform changes as surface edits.** A dependency bump that alters what a surface produces is a change to that surface, the same as an edit to project code. The framework implies this (a change belongs to a row when it alters what that surface produces), but doesn't say it. 10.03-2 relies on it for `test-environment-change`.
- **Where the world ends, generically.** A test for whether a preprocessing step belongs to the world or to the inputs. Only relevant if the lib becomes general-purpose.

### Worked example: a new generals.io version

A new version of the game, with its replays added to the corpus, breaks down into separate changes:

1. The sim supports the new rules, gated on the replay's version. This adds a second world alongside the first, and creates no boundary.
2. The new replays are added to the corpus. That changes nothing by itself. A new split manifest built from the larger corpus is a recipe-change for the runs that use it. Its val set also differs, which each run records through its manifest (see the val set note above).
3. Gameplay evals switch to the new rules. This is the `dynamics-change` itself, for gameplay-eval numbers.
4. The release itself is outside the framework, since no commit of ours caused it. It reaches our numbers only through steps 1 and 3.

Which rows are involved depends on what the version changed:

- No rule change, such as the v30.9.2 `lbSort` change, which changed the server's ranking and not the game. Only the data mix changes.
- Moves work differently: the same action has a different effect. That is a dynamics change. An old checkpoint's contract still holds, but it is playing a different game.
- Rule changes visible in the state, such as a new terrain type. If the obs needs new channels, the change also touches the obs and model-shape rows.
- Rule changes not visible in the state, such as a new army growth rate. The model faces a mixture of worlds it can't tell apart, which suggests giving it the version as an input.
- Actions are encoded differently. This touches training targets, the live-path decode (which mirrors the target encoding), and model shape if the policy head's size changes. Ungated, it is a contract-break for old checkpoints, and the fix is an encoding version in the config. If the new action space is a superset of the old one, old replays and checkpoints stay usable. If not, old replays need their own encoding, a lossy conversion, or exclusion.
