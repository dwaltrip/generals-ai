## Summary

Part 1b of the pass-1 plan (9.26-2) is built. The project side now runs on the goldens library: the registry, fixtures, producers, regen command, and golden tests all go through `training.goldens.lib`. The old modules and tests are deleted, and the references are re-blessed in the new layout.

## To settle before revision 0001: the default stored form for supervision keys

Pass 1 kept the existing forms: `legality_mask` is stored as row hashes, and every other supervision key is stored in full. 9.26-1 item 7 left the default open and noted the trade-off. Storing in full keeps the old values readable when reviewing a change. Hashing is safer for repo size, and 9.26-1 judged it the better default for the library.

Changing the default rewrites every supervision file. Before revision 0001, that is only a re-bless. After it, the change has to be recorded as a revision. So this pass-2 item should be settled before the first revision is recorded in chunks 4 and 5.

## Notes

- **The design docs predate parts of the build.** 9.26-2 and 9.30-2 weren't updated during 1a or 1b, so the code is authoritative on names and module structure. 10.02-1 lists the differences from 1a. The change most likely to mislead a reader is the regen command, which is now `uv run python -m training.goldens.regen_cli [--dry-run]`. Its logic lives in the library, in `lib/cli.py`.
- **Notable renames from 1b:** `plan` to `plan_regen`, `apply` to `apply_regen`, and `store.read_references` to `store.load_references`.
- **`lib/testing.py` is the interface for library users adding goldens to their project.** A project's golden test needs only `load_test_context`, `entry_test_id`, and `assert_entry_matches`.
- **The shared fixtures are the first constraint a downstream surface would run into.** Every surface runs on every fixture, through one loader and one fixture-data type. Supporting a surface with its own kind of fixture (9.29-2) would take either a union data type or a second registry. A second registry brings in 9.29-1's open question of how references trees map to revision histories. 9.29-1 already lists that question for before revision 0001, and this case is an input to it.
- **A planned digest over file bytes would need a second read.** 9.26-2 suggests that chunk 5 compute the planned digest from the bytes already on disk for unchanged entries. `load_references` keeps only the decoded content, so this means reading those files again, which is cheap. One option is to factor `set_digest` into a function over (path, bytes) pairs, shared by the on-disk and planned digests.
- **No test checks that the real tree holds only registered entries.** For example, a leftover file from a dropped point goes unnoticed by the tests until regen runs. We left this as minor hygiene for now. The check becomes more useful with chunk 5: the set digest covers every `.npz` file under the root, so once revisions record the digest, a stray file would change it. Adding the check to the regen smoke test, which already computes every producer, would cost about 6 ms.
