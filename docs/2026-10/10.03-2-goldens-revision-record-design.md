# Revision record design after the lib split

Date: 2026-10-03

**Daniel's level of review / sign-off for this note:** drafted by Claude from the session discussion. Reviewed by Daniel.

This note continues 10.03-1. It covers the parts of the revision record design that changed with the lib/project split: where the surface types live, the revision kinds, how fixture refreshes are recorded, what `revisions/` holds, and two record fields. 9.18-1 remains the base design for the rest: the directory, numbering, the NB marker, the frontmatter and headings, completeness, and the blocking test. Where the two conflict, this note is current.

The design belongs to the lib and is generic. Where a point depends on this project's setup, such as its fixtures or its first-cut surfaces, the text says so.

## Summary

- The lib owns the list of surface types, alongside the impact labels.
- Each guarded surface is exactly one surface type.
- There are five revision kinds, defined by cause: `boundary`, `coverage-change`, `surface-change`, `test-mechanism-change`, and `test-environment-change`. A record lists one or more of them in a `kinds` field.
- A fixture refresh after an upstream code change (in this project, the sim or parser) is a `boundary`. A change to which fixtures are guarded is a `coverage-change`.
- `revisions/` is meant to be the full boundary history, from revision 0001 on. Boundaries on unguarded surfaces are recorded by hand, as optional manual records.
- `date` is the date the record was created, and `impacts` starts blank in the generated skeleton.

## 1. Surface types

### The lib owns the list

10.03-1 put the impact labels in the lib because the framework's tests are generic. The surfaces those tests apply to are generic too, since each §1 row is a standard stage of an ML pipeline. So the lib will own the list of surface types. Project-defined custom types are a later feature.

The generic names will get their own small pass. A rough starting point:

| Current label (7.20-2) | Rough generic name |
|---|---|
| `obs` | `inputs`, or keep `obs` |
| `live-path` | `inference-path` |
| `model-forward` | `model-forward` |
| `model-shape` | `model-shape` |
| `training-targets` | `targets` |
| `loss-func` | `loss` |
| `eval-protocol` | `eval-protocol` |
| `game-rules` | `world` |

The framework's training-only row has no label, since its only impact is a recipe-change, which the `recipe_change` field already records.

Leans, not yet confirmed:

- Do the names pass before revision 0001, since records persist the names.
- Represent the types as exported instances of a small frozen dataclass, not an `Enum`, so that custom types stay possible. Description text for the legend could live on the type.

### One surface per type

Each guarded `Surface` is exactly one surface type, with no separate name. The registry API will express this directly, with surfaces keyed by type:

```python
Registry(
    surfaces=dict(
        targets=Surface(points=SUPERVISION_POINTS, produce=produce_supervision),
        # ...
    ),
)
```

The details are deferred, including whether the keys are strings validated against the vocabulary or the type objects themselves.

The alternative was several guarded surfaces per type. The case for it was a guarded live path, where live obs construction and action decode would both be `inference-path`. No such surface is planned. If one is ever needed, the change is additive: an optional name, and no uniqueness requirement.

In this project, the targets surface also carries a few target-adjacent fields, such as `legality_mask` and the alive and present masks. These fields are why the surface was named `supervision` instead of `targets`. Refactors over the past month (the walk core and `emit_tail`, `bc/datapipe`, `MetricsConfig`) have shrunk the mismatch, but the guarded output is still mostly `FrameSupervision`. The `targets` type is close enough to accept for now. Splitting the extra fields into their own surface would make a good first test case for custom surface types.

Since a surface has no name apart from its type, the `supervision` name goes away from the lib-side artifacts: this project's reference paths (`targets/time_bin/<fixture>.npz`), test ids, and report output. The project's own code names, such as `produce_supervision`, are unaffected. Regen doesn't detect moves across surfaces, so the rename means a re-bless, which is fine before revision 0001.

## 2. Revision kinds

### The five kinds

| Kind | Cause |
|---|---|
| `boundary` | A behavior change reached the guarded outputs. Either guarded code changed, or the fixture contents were refreshed after an upstream code change (see section 3). The only kind that carries impacts. |
| `coverage-change` | The registry's points or fixtures changed, as a choice of what to guard: points or fixtures added, removed, or renamed, a point's config or a fixture's registry entry edited, or fixture selection. |
| `surface-change` | What a surface guards changed: the producer calls different project code, or adds or drops a guarded field. |
| `test-mechanism-change` | How the guarded data is recorded changed, and the data didn't. This covers the lib's machinery (hashing, `serialize`, the path scheme, the digest) and the producer's goldens-specific transforms (full arrays or `RowHashes`, array names, axis order). The mechanism golden detects lib-side changes. Project-side ones show up in the producer's diff. |
| `test-environment-change` | A change that exists only in the environment the goldens run in, such as the machine or OS, moved the guarded bytes. Training never sees it. |

Notes on the kinds:

- **`boundary`** includes guarded changes with little apparent impact, such as refactor churn that flips a few fp16 roundings, or a dtype change with identical values. The person writing the record can describe it as minor in the Description, or however else fits. Treating these differently would complicate the definition of a boundary, and small numerical changes can still have an impact.
- **`coverage-change`** no longer requires every surviving file's bytes to stay the same, as 9.18-1 had it, since a point-config edit changes bytes. This closes the gap 9.29-1 raised. A realistic example in this project is fixing the `time_bin` edges, if the checkpoint sweep finds them wrong.
- **`surface-change`** means the producer calls different project code, so the project's output bytes change, before any goldens-specific transforms are applied. A producer updated only to follow a refactor of the project code, with the same output bytes, isn't a `surface-change`, and produces no revision at all. Keeping this kind separate from `coverage-change` leaves coverage scoped to points and fixtures.
- **`test-mechanism-change`** covers lib-side and project-side changes alike, and the Description says which. If the lib became an independent package, its changes would reach the project as version upgrades, and this would need some rethinking.
- **`test-environment-change`** is defined by whether training also sees the change. A dependency or interpreter change that training also uses changes the code that trains and runs models, the same as an edit to project code. So when it moves guarded bytes, it's a `boundary`, with the dependency named in the Description, and possibly described as minor. 7.15-2's procedure (rebuild the old environment, dump, and diff) helps separate numerical churn from real behavior changes when writing that record. Cross-platform identical goldens are a future goal.
  - In this project, the goldens run on an M1 Mac, while training runs on Modal (Linux, CUDA) with requirements generated from the same lock. So a macOS upgrade is a `test-environment-change`, while a numpy bump that moves guarded bytes is a `boundary`.

### Telling the kinds apart

A producer does two things. It calls guarded code, and the choice of what it calls defines the surface. It then turns the results into content, applying any goldens-specific transforms, such as hashing. When the producer itself was edited, one question tells `surface-change` and `test-mechanism-change` apart:

- Did the project's output bytes change, before any goldens-specific transforms? If yes, it's a `surface-change`. If not, it's a `test-mechanism-change`.

An edit to the project code the producer calls is a `boundary` instead, as with any guarded code change.

For fixtures, the test is about identity versus content. A fixture's identity is its registry entry, and its content is the data loaded for it. In this project, those are a replay id with a perspective slot, and the parser output for that replay.

- If the identities changed, a different slice of data was chosen to guard, and it's a `coverage-change`.
- If only the content changed, because the data-prep code changed, it's a `boundary`.

A point-config edit fits the same pattern. The point keeps its name, but someone chose to guard a different config, so it's a `coverage-change`.

### `kinds` is a list

One regen can include more than one cause, such as a boundary and a new point together. So the field is a list, with one entry in most cases:

```yaml
kinds: [boundary, coverage-change]
```

- A complete record has a non-empty list of known kinds, with no duplicates.
- The NB marker is in the filename exactly when `boundary` is not in the list.
- `impacts` is filled when `boundary` is in the list, and is `none` otherwise.

A list also makes the non-boundary parts queryable. For example, the history of fixture selection is every record whose `kinds` include `coverage-change`.

### Changes that produce no revision

- A fixture refresh for a parser format change, where the content is unchanged.
- Encoding drift from a dependency upgrade. Planning compares content, and unchanged entries aren't rewritten, so regen reports nothing. Only the mechanism golden's `serialize` pin catches this.

### Names

- `environment-change`, the name in 9.18-1, was dropped. An RL reader would take it to mean the world changed, which is close to the opposite meaning: a non-boundary, compared with a `dynamics-change` boundary.
- "Harness" was considered for `test-mechanism-change`, but it fits poorly for a switch between full arrays and hashes, and this project already has several harnesses (overfit, offline, probe, eval, dump). "Mechanism" matches the existing mechanism golden test, which detects the lib-side cases.
- The `test-` prefix ties both names to the goldens. For `test-environment-change`, it also says what the kind covers: the goldens' own environment, which training never sees. For `test-mechanism-change`, it keeps "mechanism" apart from the retired `mechanics-change`.

## 3. Fixture refreshes and upstream changes

When fixtures are snapshots of a project's training data, code upstream of that data can change their content without any change to guarded code. The goldens should guard what training runs, so the fixtures should be refreshed along with the training data. This is a manual workflow rule, since the goldens can't monitor training data (any run can train on new data).

In this project, the fixtures are frozen parser output, the same kind of file as the training corpus (`CorpusGame.load` reads them with `SimGame.from_npz`). This creates two delays between a sim change and the goldens:

1. **Sim commit → corpus regeneration.** The framework already treats these as two boundary events with their own dates (the note under the game row in §1). The goldens can't see the first one, since the world isn't a guarded surface. Its record is a best-effort manual record (see section 4). For a sim change that reinterprets state fields (wrinkle (h)), that record also covers the live path, which reads the new meanings from the sim commit on.
2. **Corpus regeneration → fixture refresh.** This one is specific to the goldens.

The workflow rule closes the second delay. In this project it reads: **when a corpus regeneration changes the contents of existing replays, refresh the fixtures at the same time.** It belongs in the workflow doc.

Corpus growth needs no goldens action. Adding replays changes nothing by itself. A new split manifest is a recipe-change for the runs that use it, and each run records its own val set (see 10.03-1's note on val set construction).

The ways this project's fixtures can change, and how each is recorded:

| Change | Recorded as |
|---|---|
| Fixture selection, or adding or removing a fixture | `coverage-change` |
| A fixture's perspective slot changed | `coverage-change` |
| Refresh after a sim or parser fix that changes how the game unfolds | `boundary`, with `dynamics-change` |
| Refresh after a sim change that reinterprets state fields (wrinkle (h)) | `boundary`, with a contract-break on obs, plus `metrics-change` if target code reads the field |
| Refresh for a parser format change, with the same content | no revision |
| Refresh because guarded code needs a new parser field | `boundary`, from the guarded code change |

The two refresh rows show that impacts follow whose mapping from game situation to output changed, not which code was edited or which bytes moved. After a fix to how the game unfolds, a given situation still produces the same obs, and the game reaches different situations, so it's a world change. After a reinterpretation of state fields, the obs code is unchanged, but the same situation now produces a different obs, which makes it a contract-break on obs. Test 2's hands-on check separates the two: build the obs for one real situation before and after.

## 4. `revisions/` as the full boundary history

`revisions/` is meant to be a project's full boundary history, as 7.20-2 intended for its ledger. The history starts at revision 0001, and earlier boundaries aren't backfilled. It has two parts:

- **Guarded surfaces: enforced, within what the guarded entries exercise.** A behavior change that moves the bytes of any guarded entry moves the digest, and the blocking test fails until a revision records it. A change that no entry exercises moves nothing. Examples: a change that only shows up under a config no point pins, in situations the fixtures don't contain, on a platform other than the one the goldens run on, or in upstream data that the fixtures haven't been refreshed from (see section 3).
- **Unguarded surfaces: best effort.** A surface the project doesn't guard has no references, so a boundary on it doesn't move the digest, and nothing checks that it was recorded. Guarding a surface moves it into the first part.

The legend will state these limits. A missing record doesn't prove that no boundary happened. For an unguarded surface it says nothing, and for a guarded surface it means only that no guarded entry was affected.

In this project after the first cut, only obs and targets are guarded. Until more surfaces are guarded, the best-effort part covers the forward pass, the loss, the eval protocol, the live path, and the world (sim commits).

Boundaries on unguarded surfaces are recorded as manual records, written by hand:

- the next number
- `kinds: [boundary]`
- impacts on the unguarded surfaces
- the newest revision's digest, copied unchanged
- "none" under Extent

The blocking test passes as designed, since the newest digest still matches the tree. No new lib machinery is needed, with one rule: the lib must never reject a revision whose digest equals the previous one's.

For the workflow doc: a manual record made on a branch is a real record. It survives the land recipe's "delete the mid-branch revisions" step, and gets renumbered to follow the regen revision.

## 5. Record fields: `date` and `impacts`

- **`date`** is the date the revision record was created. Regen fills in the day it runs. It doesn't need to match the date of the code change.
- **`impacts`** is blank in the generated skeleton. This replaces 9.18-1's pre-fill, for three reasons:
  - The Extent already shows which guarded surfaces changed.
  - Impacts are entirely judgment, and 8.12-1's rule for the skeleton is to pre-fill only simple fields.
  - The surfaces whose bytes changed aren't always the surfaces that changed. In this project, a fixture refresh after a sim fix moves bytes on obs and targets, but the change is to the world. Chained surfaces would add more cases later (9.29-2): an obs change would also fire a guarded forward pass and loss.

Lean, not yet confirmed: the comment above `impacts` in the skeleton lists the surface and impact vocabulary, generated from the lib.

## 6. Operational docs stand alone (tentative)

The goldens' operational docs (the `revisions/` README, any prose in the lib, and the planned workflow doc) will stand alone, without pointing to `confounds-framework.md`. They will borrow heavily from the framework and build on it. But the framework is dense, incomplete in places (the wrinkles list, and the issues in 10.03-1's section 4), and wasn't written as an operational doc. This is a tentative lean. The framework may still be refined and cleaned up before the end of the first cut.

Consequences:

- The README legend carries its own definitions: the surfaces, the impact labels (including `dynamics-change` and the allowance rule from 10.03-1), the kinds, and the limits of the history from section 4.
- The comment above `impacts` in the skeleton points to the README. 9.18-1 had it point to whichever doc owns the vocabulary.
- The framework's rename to `dynamics-change` and its other refinements aren't needed before revision 0001.

## 7. Parked

- **Layer-1 goldens as a proper surface.** Layer 1 is fixture production (the parser and sim). As a lib surface, it would record the sim commit at its own date. It also connects to 9.29-2: the fixtures are already frozen full inputs for obs and targets, and layer 1's references could be the fixtures themselves, so refreshing the fixtures would mean re-blessing layer 1. The costs are the Rust build at test time (7.10-2 keeps sim_core out of the goldens tier), the lib's one-fixture-type constraint (10.02-2), and scope. To decide when layer 1 is scheduled.
- Cross-platform identical goldens.
- Custom surface types.
- An optional git-hash field.
- A helper that appends a skeleton without running regen, filling in the date and digest.
- A fixture provenance check, comparing a parser or sim version recorded in `.meta.npz` against the current corpus version.

## 8. Docs and code this revises

- 9.18-1: the kinds (four became five, renamed and redefined), `kind` becomes the `kinds` list, the NB rule, the impacts pre-fill, and the meaning of `date`.
- 9.18-1's heuristics for reading a regen run, which no longer hold in every case, since a point-config edit is a `coverage-change` that changes bytes:
  - §4: "A run with only new, moved, or removed files is a coverage change."
  - §8: changed bytes read as a fire.
- 9.29-1: the config-edit gap is closed by the new `coverage-change`.
- 7.20-2: `date` changes from "the date it landed" to the record's creation date.
- 9.18-1 §11: "if the goldens fire and the mechanism golden passes, the change is a boundary". That misses project-side recording changes, which the mechanism golden doesn't cover.
- `test_mechanism_golden.py`: it pins only lib machinery, so it moves to the lib's tests in `tests/goldens_lib`. Its docstring names the old `mechanism-change` kind, and says intentional changes always need a revision, which doesn't hold for encoding drift.

## Open items for the rest of chunks 4 and 5

### To settle before revision 0001

These affect what records contain, so they should be settled before the first record is written.

- **Manual records under the land recipe.** A manual record made on a branch gets renumbered at land to follow the regen revision. That makes it the newest revision, so the digest copied into it is stale and the blocking test fails. One option: manual records carry no digest, and the blocking test checks the newest record that has one.
- **One history per project.** 9.29-1 asks how references trees map to revision histories, in case a project ever has more than one registry. Calling `revisions/` the project's full boundary history implies one history per project. This should be stated, or the question kept open.

### Smaller items for the build

- Where the README legend lives: hand-written in `revisions/`, or owned by the lib.
- Whether the references root and the revisions dir are passed as one type or as two parameters.
- The short Extent form for the record.
- Whether the planned digest is computed over file bytes or content.
- The stored form for the targets surface's arrays: full or hashed.
- python-frontmatter, or hand parsing with PyYAML.
- The stray-file check, and the CLI exit code.
