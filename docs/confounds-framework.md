# The confounds framework: how behavior changes affect checkpoints and recorded numbers

*Date: 2026-07-08. Status: evergreen reference.*

When code that shapes model behavior changes — obs building, forward semantics, targets, loss, metric definitions, eval protocol — the change draws a boundary in time: checkpoints and recorded numbers from before it no longer automatically mean the same thing as those from after. This doc classifies such changes and reads off, for any use of an old artifact, whether the result is trustworthy, confounded, or merely in need of a caption. The sub-cases are generated by one rule plus three ingredients (surface, effect, activity), so the enumeration is systematic rather than ad hoc.

## The two contracts

Every confound in this space is a break of one of two implicit promises:

- **The model contract**: a checkpoint's runtime behavior today equals its behavior at training time. It holds as long as the code that executes for that checkpoint — input construction and the forward pass — computes what it computed when the checkpoint was trained.
- **The measurement contract**: two recorded numbers with the same name mean the same thing. It holds as long as everything that produces the number — metric definitions, label definitions, eval protocol, the task itself — is stable.

Seen from the comparison side, the two separate cleanly:

- Comparing two checkpoints **run today under identical conditions** can only be corrupted by a model-contract break: the older checkpoint loses for mismatch reasons rather than ability. The measurement conditions are identical for both by construction.
- Comparing a number recorded **before** the boundary with one recorded **after** can only be corrupted by a measurement-contract break. The models on both sides may be perfectly healthy — it's the numbers that aren't commensurable.

The cures differ accordingly: a measurement-contract confound can be re-run away (re-measure the old artifact under current conditions), while a model-contract confound cannot — the old checkpoint is intrinsically out of contract on current code.

## The generating rule

A confound exists exactly when an activity executes changed code against an artifact from the other side of the boundary. "Artifact" means a checkpoint or a recorded number (and, per wrinkle (d) below, recorded data such as val dumps).

Genuine model differences are never confounds: a change to training-time code (targets, loss, training inputs) makes later checkpoints *actually different*. That is a recipe change — the same category as changing the learning rate — and comparing across it measures something real.

Classifying a change takes three ingredients, one per section below:

1. **Surface** — what kind of code changed, and where that code executes (§1).
2. **Effect** — what the change does to checkpoints and numbers, derived mechanically from the surface (§2).
3. **Activity** — what is being done right now, with which artifacts; the verdict table crosses activities with effects (§3).

## 1. Surfaces — what changed, and where it executes

The execution columns drive everything downstream.

| Surface | Runs at training | Runs at gameplay | Runs at analysis/metrics | Example |
|---|---|---|---|---|
| Obs build, shared path | ✓ | ✓ | ✓ | incident 1 (§5) |
| Obs build, live path only | – | ✓ | – | incident 2 (§5) |
| Forward semantics (same weight shapes) | ✓ | ✓ | ✓ | (hypothetical: changing a normalization constant) |
| Targets / labels | ✓ (gradients) | – | ✓ (scoring) | incident 3 (§5) |
| Loss definition | ✓ | – | ✓ (loss-type metrics) | soft targets, loss-weight changes |
| Eval protocol / metric definitions | – | – | ✓ | new map set, sampling temperature |
| Arch shape / channel count | ✓ | fails loudly at load | fails loudly | ungated channel additions |
| The task itself | ✓ | ✓ | ✓ | information-leak fixes, sim-rule changes |

Two rows are special:

- **Shape changes** fail loudly at `load_state_dict(strict=True)`. They pose a support decision — which old checkpoints stay loadable — but never a *silent* confound. Everything else in this doc is about the silent kind.
- **Task changes** get their own row because fixing an information leak or changing sim rules doesn't just change code — it changes how hard the game is. No contract-honoring measurement can undo that: numbers from the two eras describe different tasks.

## 2. Effects — what a change does, derived from the surface

A change produces one or more of these, mechanically from the execution columns:

- **E1 — recipe change** (surface runs at training): checkpoints trained after it are genuinely different models. *Never a confound* — it's the experiment. Its only need is a record, so later readers can attribute model differences to it.
- **E2 — model-contract effect** (surface runs at gameplay or analysis): checkpoints trained before the change now execute against different code than they trained with. **Signed**: a *break* (their inputs or computation now differ from training) or a *repair* (a fix brings runtime *into* line with training — the contract was broken all along, and the change ends it). Live and recurring while unresolved: it re-occurs on every run of an affected checkpoint.
- **E3 — measurement-contract effect** (surface runs where a number is produced): numbers from the two eras don't mean the same thing. "Where a number is produced" spans two columns of the §1 table: analysis/metrics, and also gameplay whenever the number is a gameplay-eval result — an eval run is itself a measurement, so a gameplay-only surface still carries an E3 for eval numbers. **Two depths**: the *ruler* changed (same task, different metric or label definitions) or the *task* changed (the game itself got easier or harder, so even measurements that were each taken in-contract don't compare across the boundary). Frozen: future work is untouched, and the confound only surfaces when a comparison crosses the date.

Two notes:

- **Gating prevents E2.** A change is gated when the old behavior stays available behind a config switch keyed to the checkpoint, so that a checkpoint's stored config selects the semantics it trained with. Gated changes leave the model contract intact. In-place ungated changes are the ones that break it.
- **The case easiest to misread is a targets or loss change.** It makes later checkpoints genuinely different (E1 — the gradients flowed differently, including through any shared trunk), but target and loss code never executes at inference, so a frozen old checkpoint's gameplay behavior is untouched — no E2 there. The only contract residue is on the analysis side: scoring an old head against the new label definition (activity 2 below).

## 3. Activities × effects — the verdict table

Six activities exhaust the ways artifacts get used: a checkpoint alone, checkpoint vs checkpoint, checkpoint vs its own record, number vs number, a checkpoint continued in training, a number alone. "Old" and "new" mean before and after the boundary — an artifact's *vintage*.

| Activity | E1 recipe | E2 break | E2 repair | E3 ruler | E3 task |
|---|---|---|---|---|---|
| **1. Old vs new ckpt, both run now** | clean — the difference is real and includes the recipe effect | **confounded** — the old side mixes ability with mismatch | clean | clean | clean |
| **2. Old ckpt analyzed now** | – | **confounded** if the analysis walks the changed path | clean | the number is valid but measures the *new* definition — caption it | valid (today's task) |
| **3. New number vs old recorded number** | comparable — and measures the recipe change | see wrinkle (a) | **incomparable** — old numbers carry the broken era | **incomparable** — curable by re-measuring | **incomparable** — permanently; only re-measured numbers compare |
| **4. Old ckpt rerun vs its own old number** | eval numbers reproduce; rerunning *training* is a new experiment | fails to reproduce — expected | fails — expected, and the new number is the truer one | fails — expected | fails — expected |
| **5. Resume / fine-tune old ckpt now** | the result is a cross-recipe hybrid — legitimate, label it | starts out-of-distribution; continued training *adapts* it (a cure) | fine | its curves kink at the resume point for definition reasons, not learning reasons | trains on today's task |
| **6. Read or deploy one artifact alone** | caption: which recipe | caption: contract status on current code | caption: that era's numbers are systematically off | caption: which definition | caption: which task era |

Row 4 carries the biggest practical trap: a reproduction gap has five possible causes in this table, so a surprising "this doesn't reproduce" must be attributed to a known boundary before being read as a regression or as nondeterminism.

### Wrinkles that don't fit in cells

- **(a) Native-vs-native numbers under an input change.** If each era's number was measured in-contract (old checkpoint on old code, new on new), both faithfully measure "how good was this model in its environment." They compare as recipe quality *only if* the input change didn't alter the information available. A leak fix does alter it — the old task was easier — which pushes this case into the task column.
- **(b) Same-side comparisons under a shared E2 break.** Two old checkpoints compared today are *equally* out of contract, so the relative read plausibly survives — but that assumes both are equally sensitive to the mismatch, which is an assumption, not a guarantee. (Head-to-head evals run while a shared live-path bug was still in place — incident 2 in §5 — have exactly this status.)
- **(c) Boundary-spanning checkpoints.** A run resumed across a boundary is neither vintage. A checkpoint census needs a "hybrid" category, not just pre/post.
- **(d) Frozen artifacts, not just frozen numbers.** Recorded dumps (e.g. per-epoch val dumps) bake the era's label definitions into *data*. Recomputing metrics on an old dump with new analysis code mixes eras inside a single pipeline — an E3 that hides in storage.
- **(e) Trunk coupling.** A targets or loss change (pure E1 on paper) still moves *gameplay* across the boundary, because aux-head gradients shape the shared trunk that the policy head reads. Still not a confound — but "only the labels changed" does not imply "gameplay is identical across the boundary."
- **(f) The mismatch is symmetric.** Running a *new* checkpoint on *old* code (e.g. checking out an old commit) breaks the same contracts in the other direction. The rule is vintage mismatch, not age.

## 4. Cures — one set per effect

- **E1:** nothing to cure. Record it so model differences stay attributable.
- **E2 break:** three cures — gate the old behavior (a config branch keyed to the checkpoint), declare the affected checkpoints degraded or unsupported (a supported-checkpoints policy call), or fine-tune them into the new contract. Re-running measures the confound but never removes it.
- **E2 repair:** nothing to cure going forward; the old era's numbers inherit an E3.
- **E3:** re-measure the old artifact under current conditions — works whenever its model contract holds. Where re-measuring is impossible, the old number keeps a permanent caveat.
- **All of them:** recording the boundary — date, surface, effects — cures nothing by itself, but every verdict in §3 is computable only when the boundary is known to exist. An unrecorded boundary silently turns the confounded cells above into wrong conclusions.

## 5. Worked examples — three boundaries from this project (2026)

1. **Obs-content fixes (2026-05-21 and 2026-05-27).** Three ungated fixes changed existing obs channel values in place, in the shared path: "Close two obs-tensor fog-of-war leaks" (`2e6b2df`) and "Subtract expected production from army_delta channels" (`5a2beb0`) on 05-21, then "Replace game_progress channel with timestep (fix future-info leak)" (`e04cad6`) on 05-27, which replaced a channel that leaked the true game length with a fixed-divisor timestep.
2. **Stale-live-obs fix (2026-06-07).** "Fix one-tick-stale obs in live inference path" (`bc4bb19`, with same-day companion `49b335d` fixing the eval-bot's world model): the live path double-seeded tick-0 history, so every live encode saw the previous tick's board. The training-data path never had the bug.
3. **Elim-target tick-seam fix (2026-06-18).** "Add bc/player_status; fix the obs/alive tick seam" (`4aace8b`): the alive/present masks moved from `death > t` to `death >= t`, ungated, on the targets side only — obs channels untouched. The elim head's death-frame target became `dt = 0`.

| Incident | E1 | E2 | E3 |
|---|---|---|---|
| 1. Obs-content fixes | yes — later models train on cleaner obs | **break** — earlier checkpoints see different inputs on current code | task — the leaks made the earlier game easier |
| 2. Stale-live-obs fix | no — the training path was never wrong | **repair** | task/ruler — all earlier gameplay-eval numbers measured a blinder game |
| 3. Elim-target fix | yes — labels, and gameplay via trunk coupling | analysis-side residue only (an old head scored on new labels) | ruler — elim metrics and training curves |

## Completeness

The enumeration is believed complete in this sense: the six activities exhaust the ways the artifact types can be used alone, paired, or continued; the effects derive mechanically from where a surface executes; and each wrinkle is a composition of base cases rather than a new one. A change that resists classification here is a reason to extend this doc.
