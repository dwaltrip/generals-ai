# The confounds framework: how behavior changes affect checkpoints and recorded numbers

*Date: 2026-07-08. Status: evergreen reference.*

*Update 2026-07-20: the impact vocabulary was renamed (formerly coded E1 / E2 break / E2 repair / E3 ruler / E3 task). The rename map is in [7.20-3](2026-07/7.20-3-goldens-naming-reference.md).*

When code that shapes model behavior changes (obs building, forward semantics, targets, loss, metric definitions, eval protocol), the change draws a boundary in time. Checkpoints and recorded numbers from before the boundary no longer automatically mean the same thing as those from after. This doc classifies such changes and reads off, for any use of an old artifact, whether the result is trustworthy, confounded, or merely in need of a caption. The sub-cases are generated by one rule plus three ingredients (surface, impact, activity), so the enumeration is systematic rather than ad hoc.

## The two contracts

Every confound in this space is a break of one of two implicit promises:

- **The model contract**: a checkpoint's runtime behavior today equals its behavior at training time. It holds as long as the code that executes for that checkpoint (input construction and the forward pass) computes what it computed when the checkpoint was trained.
- **The measurement contract**: two recorded numbers with the same name mean the same thing. It holds as long as everything that produces the number is stable: metric definitions, label definitions, eval protocol, and the game itself.

Seen from the comparison side, the two separate cleanly:

- Comparing two checkpoints **run today under identical conditions** can only be corrupted by a model-contract break: the older checkpoint loses for mismatch reasons rather than ability. The measurement conditions are identical for both by construction.
- Comparing a number recorded **before** the boundary with one recorded **after** can only be corrupted by a measurement-contract break. The models on both sides may be perfectly healthy: it is the numbers that no longer compare.

The cures differ accordingly. A measurement-contract confound can be re-run away (re-measure the old artifact under current conditions). A model-contract confound cannot: the old checkpoint is intrinsically out of contract on current code.

## The generating rule

A confound exists exactly when an activity executes changed code against an artifact from the other side of the boundary. "Artifact" means a checkpoint or a recorded number (and, per wrinkle (d) below, recorded data such as val dumps).

Genuine model differences are never confounds: a change to training-time code (targets, loss, training inputs) makes later checkpoints *actually different*. That is a recipe change, in the same category as changing the learning rate, and comparing across it measures something real.

Classifying a change takes three ingredients, one per section below:

1. **Surface** — what kind of code changed, and where that code executes (§1).
2. **Impact** — what the change does to checkpoints and numbers, derived mechanically from the surface (§2).
3. **Activity** — what is being done right now, with which artifacts. The verdict table crosses activities with impacts (§3).

## 1. Surfaces — what changed, and where it executes

The execution columns drive everything downstream.

| Surface | Runs at training | Runs at gameplay | Runs at analysis/metrics | Example |
|---|---|---|---|---|
| Obs build, shared path | ✓ | ✓ | ✓ | incident 1 (§5) |
| Obs build, live path only | – | ✓ | – | incident 2 (§5) |
| Forward semantics (same weight shapes) | ✓ | ✓ | ✓ | (hypothetical: changing a normalization constant) |
| Targets / labels | ✓ (gradients) | – | ✓ (scoring) | incident 3 (§5) |
| Loss definition | ✓ | – | ✓ (loss-type metrics) | soft targets, loss-weight changes |
| Eval protocol / metric definitions | – | – | ✓ | new map set, sampling temperature |
| Arch shape / channel count | ✓ | fails loudly at load | fails loudly | ungated channel additions |
| The game itself | ✓ | ✓ | ✓ | information-leak fixes, sim-rule changes |

Two rows are special:

- **Shape changes** fail loudly at `load_state_dict(strict=True)`. An old checkpoint cannot silently degrade on mismatched arch code, because it refuses to load at all. The change instead poses a support decision: which old checkpoints stay loadable. The rest of this doc concerns confounds of the silent kind.
- **Game changes** get their own row because fixing an information leak or changing a sim rule doesn't just change code: it changes how hard the game is. No contract-honoring measurement can undo that, and numbers from the two eras describe different games.

## 2. Impacts — what a change does, derived from where its code executes

A change's impacts are read off where its changed code executes: each execution site the surface occupies contributes at least one impact family. A single change therefore often carries several impacts at once: incident 1's shared-obs-path fixes executed at training, gameplay, and analysis, and carried all three families (§5). The last column names the scenarios in which each impact's confound materializes. §3 gives the full activity-by-activity verdicts.

| changed code executes at | impact | affected pre-existing artifacts | confound scenarios |
|---|---|---|---|
| training | `recipe-change` | none | none: the later checkpoints are simply new models* |
| gameplay or analysis | `contract-break` / `contract-repair` | checkpoints | runs of a checkpoint on code of the other vintage (either direction, wrinkle (f)) |
| wherever a number is produced | `metrics-change` / `mechanics-change` | recorded numbers | any cross-boundary comparison of recorded numbers |

\* New models compare and evaluate cleanly against older ones, provided the same change carries no other impact (a shared-path change usually does).

The third row's key is deliberately not a §1 column. "Wherever a number is produced" spans two of them: analysis/metrics, and also gameplay whenever the number is a gameplay-eval result, because an eval run is itself a measurement.

**`recipe-change`**: checkpoints trained after the change are genuinely different models, because the gradients flowed differently. This is not a confound: the difference is the experiment itself. The change needs only a record, so that later readers can attribute model differences to it. The pure case is a hyperparameter or training-data change (learning rate, optimizer, data mix), which nothing downstream of training executes. A change to code that also runs at gameplay or analysis is not pure: it carries the corresponding impact families as well.

**The model-contract impacts**: old checkpoints now execute against code that differs from what they trained with. The two differ by direction:

- **`contract-break`**: the change pushes runtime *away* from training conditions. Old checkpoints get inputs or computation they never trained with.
- **`contract-repair`**: a fix brings runtime back *into* line with training. The contract was broken all along. The change ends the breach, and the damage moves to the old era's numbers (they measured the broken behavior).

Gating prevents a contract-break: a change is gated when the old behavior stays available behind a config switch keyed to the checkpoint, so each checkpoint's stored config selects the semantics it trained with. In-place, ungated changes are the ones that break the contract.

**The measurement-contract impacts**: numbers recorded before and after the boundary stop meaning the same thing.

- **`metrics-change`**: the measuring stick changed (metric or label definitions, eval protocol) while the game stayed the same. Curable: re-measure the old artifact under today's definitions.
- **`mechanics-change`**: the game the bot plays changed, rarely the game itself and more often our implementation of it. Even numbers that were each measured honestly in-contract describe different games, and no re-measurement can bridge the recorded ones.

**The case easiest to misread is a targets or loss change.** It makes later checkpoints genuinely different (a recipe-change: the gradients flowed differently, including through any shared trunk), but target and loss code never executes at inference, so a frozen old checkpoint's gameplay behavior is untouched: no contract-break. The only contract residue is on the analysis side: scoring an old head against the new label definition (activity 2 below).

## 3. Activities × impacts — the verdict table

Six activities exhaust the ways artifacts get used: checkpoint vs checkpoint, a checkpoint analyzed alone, number vs number, a checkpoint rerun against its own record, a checkpoint continued in training, and one artifact read or deployed alone. "Old" and "new" mean before and after the boundary: an artifact's *vintage*.

| Activity | recipe-change | contract-break | contract-repair | metrics-change | mechanics-change |
|---|---|---|---|---|---|
| **1. Old vs new ckpt, both run now** | clean — the difference is real and includes the recipe change | **confounded** — the old side mixes ability with mismatch | clean | clean | clean |
| **2. Old ckpt analyzed now** | – | **confounded** if the analysis walks the changed path | clean | the number is valid but measures the *new* definition — caption it | valid (today's game) |
| **3. New number vs old recorded number** | comparable — and measures the recipe change | see wrinkle (a) | **incomparable** — old numbers carry the broken era | **incomparable** — curable by re-measuring | **incomparable** — permanently; only re-measured numbers compare |
| **4. Old ckpt rerun vs its own old number** | eval numbers reproduce; rerunning *training* is a new experiment | fails to reproduce — expected | fails — expected, and the new number is the truer one | fails — expected | fails — expected |
| **5. Resume / fine-tune old ckpt now** | the result is a cross-recipe hybrid — legitimate, label it | starts out-of-distribution; continued training *adapts* it (a cure) | fine | its curves kink at the resume point for definition reasons, not learning reasons | trains on today's game |
| **6. Read or deploy one artifact alone** | caption: which recipe | caption: contract status on current code | caption: that era's numbers are systematically off | caption: which definition | caption: which game era |

Row 4 carries the biggest practical trap: a reproduction gap has five possible causes in this table, so a surprising "this doesn't reproduce" must be attributed to a known boundary before being read as a regression or as nondeterminism.

### Wrinkles that don't fit in cells

- **(a) Native-vs-native numbers under an input change.** If each era's number was measured in-contract (old checkpoint on old code, new on new), both faithfully measure "how good was this model in its environment." They compare as recipe quality *only if* the input change didn't alter the information available. A leak fix does alter it (the old game was easier), which pushes this case into the mechanics-change column.
- **(b) Same-side comparisons during a shared breach.** Two old checkpoints compared today are *equally* out of contract, so the relative read plausibly survives, but only on the unverified assumption that both are equally sensitive to the mismatch. (Head-to-head evals run while incident 2's shared live-path bug was still in place have exactly this status: the pre-fix era of a contract-repair is such a breach.)
- **(c) Boundary-spanning checkpoints.** A run resumed across a boundary is neither vintage. A checkpoint census needs a "hybrid" category, not just pre/post.
- **(d) Frozen artifacts, not just frozen numbers.** Recorded dumps (e.g. per-epoch val dumps) bake the era's label definitions into *data*. Recomputing metrics on an old dump with new analysis code mixes eras inside a single pipeline — a metrics-change that hides in storage.
- **(e) Trunk coupling.** A targets or loss change (a recipe-change with only analysis-side residue, per §2) still moves *gameplay* across the boundary, because aux-head gradients shape the shared trunk that the policy head reads. Still not a confound, but "only the labels changed" does not imply "gameplay is identical across the boundary."
- **(f) The mismatch is symmetric.** Running a *new* checkpoint on *old* code (e.g. checking out an old commit) breaks the same contracts in the other direction. The rule is vintage mismatch, not age.

## 4. Cures — one set per impact

- **recipe-change:** nothing to cure. Record it so model differences stay attributable.
- **contract-break:** three cures — gate the old behavior (a config branch keyed to the checkpoint), declare the affected checkpoints degraded or unsupported (a supported-checkpoints policy call), or fine-tune them into the new contract. Re-running measures the confound but does not remove it.
- **contract-repair:** nothing to cure going forward. The old era's numbers inherit a measurement-contract impact.
- **metrics-change / mechanics-change:** re-measure the old artifact under current conditions, which works whenever its model contract holds. Where re-measuring is impossible, the old number keeps a permanent caveat.
- **All of them:** recording the boundary (date, surface, impacts) cures nothing by itself, but every verdict in §3 is computable only when the boundary is known to exist. An unrecorded boundary silently turns the confounded cells above into wrong conclusions.

## 5. Worked examples — three boundaries from this project (2026)

1. **Obs-content fixes (2026-05-21 and 2026-05-27).** Three ungated fixes changed existing obs channel values in place, in the shared path: "Close two obs-tensor fog-of-war leaks" (`2e6b2df`) and "Subtract expected production from army_delta channels" (`5a2beb0`) on 05-21, then "Replace game_progress channel with timestep (fix future-info leak)" (`e04cad6`) on 05-27, which replaced a channel that leaked the true game length with a fixed-divisor timestep.
2. **Stale-live-obs fix (2026-06-07).** "Fix one-tick-stale obs in live inference path" (`bc4bb19`, with same-day companion `49b335d` fixing the eval-bot's world model): the live path double-seeded tick-0 history, so every live encode saw the previous tick's board. The training-data path never had the bug.
3. **Elim-target tick-seam fix (2026-06-18).** "Add bc/player_status; fix the obs/alive tick seam" (`4aace8b`): the alive/present masks moved from `death > t` to `death >= t`, ungated, on the targets side only (obs channels untouched). The elim head's death-frame target became `dt = 0`.

| Incident | recipe-change | model-contract impact | measurement-contract impact |
|---|---|---|---|
| 1. Obs-content fixes | yes — later models train on cleaner obs | **contract-break** — earlier checkpoints see different inputs on current code | mechanics-change — the leaks made the earlier game easier |
| 2. Stale-live-obs fix | no — the training path was never wrong | **contract-repair** | mechanics-change / metrics-change — all earlier gameplay-eval numbers measured a blinder game |
| 3. Elim-target fix | yes — labels, and gameplay via trunk coupling | analysis-side residue only (an old head scored on new labels) | metrics-change — elim metrics and training curves |

## Completeness

The enumeration is believed complete in this sense:

- the six activities exhaust the ways the artifact types can be used (alone, paired, or continued),
- the impacts derive mechanically from where a surface executes, and
- each wrinkle is a composition of base cases rather than a new one.

A change that resists classification here is a reason to extend this doc.
