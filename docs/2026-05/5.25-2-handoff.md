## TODOs from second Opus review pass

These were flagged in the second review but not yet addressed in the spec. Fix in the spec at the start of next session.

1. **`has_recent_attack` baseline mismatch (§6c.1).** The eating baseline only exists when a ThreatWindow is active. If the window was cleared (player left vision), there's no baseline to reuse. Also, the eating baseline is anchored to window-open, not a rolling window — two different temporal semantics stitched together. Needs a design decision on how `has_recent_attack` works when no ThreatWindow baseline exists.

2. **`commit` is computed but never consumed by gather_tree (§5 vs §6.3/§6c.4).** Defend, explore, and attack all compute a commit amount, but §5 never references it — the gather just grabs whatever tiles are nearby. The design question: does commit cap side-gathers? Filter source candidates? Truncate the gather? Or is it purely a post-hoc feasibility check (gather what you can, then see if it meets the threshold)?

3. **Attack hysteresis not in the tick loop pseudo-code (§2).** The prose describes hysteresis-based re-evaluation for attack plans, and `ATTACK_SWITCH_THRESHOLD` is in the constants table, but there's no corresponding step in the tick loop where the re-evaluation actually runs.

4. **Side-gather dist-2 needs multi-step moves (§5.2).** A dist-2 side-gather tile needs two moves (tile → intermediate → path tile), but the spec shows a single move. Should introduce a tunable `MAX_SIDE_GATHER_DIST` and account for the full travel cost of each side-gather in the move sequence. Non-trivial but an approximate solution should work — design next session.
