# Batched eval runner — design (`5.30-3`)

**Status:** Design locked and de-risked; ready to build. Continues Phase A from [`5.30-1`](./5.30-1-eval-perf-and-model-agent-refactor.md), which put the encode/decode seam in place. This doc is the build spec: architecture, interfaces, the correctness oracle, and the build order.

## 1. Goal

A 100-game eval takes ~1hr on the M1 because the model forward runs batch-size-1 on MPS, one game at a time — the GPU is starved. A vectorized runner drives many games in lockstep, filling the GPU. Expected win: **~4.4× end-to-end** (forward + serial obs-build), with the forward itself batching ~5×; the residual is host-side obs-build (Phase B, deferred).

## 2. The load-bearing finding: decode must be vectorized

`BCPerspective.decode` interleaves GPU math (argmax/softmax/topk/sigmoid) with ~9 `.item()` GPU→CPU syncs per call. At batch-1 that's the known ~7ms sync tax; in a batched runner, calling it per-row would issue B×9 syncs/tick and cancel the batch win.

Measured (`scripts/bench_decode_sync.py`, M1 Max, epoch_005):

| B | forward ms | naive per-row decode ms | vectorized decode ms |
|---|---|---|---|
| 1 | 8.7 | 3.4 | 1.2 |
| 32 | 57 | **95** | **1.3** |
| 48 | 84 | 144 | 1.4 |

Each `.item()` ≈ 0.33ms. Naive per-row decode *overtakes the forward* by B=8 and is 1.67× it at B=32. Vectorized decode (all math batched, one bulk sync) is flat ~1ms — 76× cheaper at B=32. **Vectorizing decode is mandatory**: naive caps the speedup at ~2.5×, vectorized unlocks the full ~4.4×.

## 3. De-risk results (empirical basis for the design)

All run 2026-05-30; probes under `packages/eval-tools/scripts/`.

- **The forward is not bitwise batch-invariant on any device** (`probe_row_independence.py`): `forward(B=1)` vs row of `forward(B=32)` differs ~1e-4 (CPU policy logits) / ~1e-5 (MPS) — MKL/MPS pick different conv algorithms by batch size. But **argmax/pass decisions are robust**: 0 flips across 32 real obs on both devices (decision gap ~0.24 ≫ delta). Consequence: batched ≈ sequential everywhere, modulo rare sub-1e-4 near-ties — and the oracle must be **tolerance-based** (this is set by the batched *forward*, not by the decode reshape).
- **MPS is decision-stable run-to-run** (`probe_mps_stability.py`): 0/200 divergent ticks × 5 maps, matching a CPU control.
- **MPS `torch.Generator` is fully supported** (multinomial/bernoulli, reproducible) → per-game generators work directly on MPS; no CPU-sampling fallback needed.
- **EvalBot uses global unseeded `np.random`** (`expand.py:160,278`) → evalbot games are non-reproducible run-to-run. Byte-exact comparisons must be NN-only.
- **`BCPerspective`'s growing `_ownership`/`_armies` lists are vestigial for live reads** (only `[t]`+`[0]` are read; real history is in bounded structures) but entangled with the training path's shared `[t]` indexing → leave it; memory is a non-issue at local B.

## 4. Architecture

### 4.1 Dependency layering

```
game-types (numpy)      StaticMap, PlayerView, ObsBundle           [unchanged]
   ▲
game-runner (numpy+sim) policy.py:  Policy, GameResult             [unchanged]
   │                    brain.py:   ModelHandle, BatchablePolicy   ← NEW protocols
   │                    batched.py: run_batched, PendingGame       ← NEW runner
   │                    runner.py:  run_game, _build_result        [_build_result reused]
   ▲
self-play               NNAgent  (satisfies BatchablePolicy)       [thinned]
training/bc             inference.py: forward_batch, decode_batch,
                          RowDecision, DecodeConfig, select_action [reshaped]
   ▲
eval-tools              run_adhoc (rewired), oracle script
```

Invariant: **`game_runner` stays torch-free and `bc`-free.** The runner depends only on the `brain.py` protocols and shuttles *opaque* forward-outputs and decode-configs between `forward_batch` and `decode_batch` without inspecting them. No import cycles — `bc.inference` *structurally* satisfies the protocols without importing `game_runner`.

### 4.2 The decode reshape (the spine)

Split `decode` at the sync boundary into a batched GPU-math half (one bulk sync, perspective-state-free) and a sync-free CPU bookkeeping half:

```
build_obs(view) → ObsBundle              CPU/numpy, per perspective
forward_batch(stack) → batched dict      GPU, async (0 syncs)
decode_batch(out, masks, configs) → [RowDecision]   GPU math + 1 bulk sync
select_action(RowDecision) → move        CPU, sync-free (counters + diag series)
```

`NNAgent.act` becomes this spine at batch-of-1, so the single-game and batched paths share `decode_batch` — the B=1 parity oracle is then near-tautological.

### 4.3 `game_runner/brain.py` (new)

```python
class ModelHandle(Protocol):
    model_key: str
    def forward_batch(self, obs_batch: np.ndarray, valid_batch: np.ndarray) -> Any: ...
    def decode_batch(self, out: Any, mask_batch: np.ndarray, configs: list[Any]) -> list[Any]: ...

class BatchablePolicy(Protocol):          # runner duck-types this to find NN slots
    model_handle: ModelHandle
    decode_config: Any                     # opaque; gathered per row for decode_batch
    def build_obs(self, view: PlayerView) -> ObsBundle: ...
    def select_action(self, decision: Any) -> tuple[int, int, int]: ...
```

`ModelHandle` moves here from `nn_agent.py` and gains `decode_batch` + `model_key`. The per-`(game,slot)` `Perspective` protocol stays in `self_play` as NNAgent's internal collaborator — the runner never sees it. A slot with no `build_obs` (EvalBotAgent) is a CPU policy → `act()`.

### 4.4 `training/bc/inference.py` (reshaped)

```python
class BCModelHandle:
    model_key: str
    def forward_batch(obs_batch, valid_batch) -> dict      # batched dict, NO per-row split
    def decode_batch(out, mask_batch, configs) -> list[RowDecision]   # all GPU math + ONE bulk sync

@dataclass(frozen=True, slots=True)
class RowDecision:        # opaque to runner
    flat_idx: int; category: str; diag: dict

@dataclass(frozen=True, slots=True)
class DecodeConfig:       # opaque to runner; what decode_batch reads per row
    force_move: bool; sample: bool; temperature: float; generator: Any

class BCPerspective:
    decode_config -> DecodeConfig
    def select_action(decision: RowDecision) -> move    # sync-free bookkeeping
    # encode() unchanged; decode() removed (split into decode_batch + select_action)
```

`NNAgent` thins to `model_handle`/`decode_config` properties, `build_obs`→`encode`, `select_action`→`perspective.select_action`, and `act()` riding the spine.

### 4.5 `game_runner/batched.py` (new) — the runner

```python
@dataclass
class PendingGame:
    game_id: int
    map_data: StaticMap
    policies: Sequence[Policy]          # fresh per game; runner calls init_for_game at pool entry
    on_tick: OnTickCallback | None = None
    ctx: Any = None                     # opaque caller payload (collector, replay_id, slot_map…)

@dataclass
class FinishedGame:
    game_id: int; result: GameResult; policies: Sequence[Policy]; ctx: Any

def run_batched(
    pending: Iterable[PendingGame], *, pool_size: int, max_turns: int = 2000,
) -> Iterator[FinishedGame]: ...
```

A **generator** that owns the pool/refill/gather/group/forward/decode/scatter/step loop and yields each game *as it completes* (out of order; `game_id` keeps it sortable). It is I/O-free; the caller writes files. Per tick:

- **Gather**: for each live game's alive slots, build the obs of `BatchablePolicy` slots (`view = state_to_view(state, map, slot)` → `policy.build_obs(view)`); call `act()` on CPU (evalbot) slots. Keep each row as a coherent record `(obs, mask, config, target_policy, game, slot)` — never parallel hand-indexed arrays (this is what makes scatter misalignment structurally impossible).
- **Forward + decode**: group rows by `policy.model_handle.model_key`; per group, `forward_batch(stack)` → `decode_batch(out, masks, configs)`. One forward per distinct model (head-to-head A-vs-B = 2/tick; self-play / NN-vs-evalbot = 1).
- **Scatter**: `zip(rows, decisions)` → `policy.select_action(decision)`; assemble each game's move list (NN + evalbot rows), `step_tick`, run `on_tick`.
- **Refill**: when a game terminates (`alive_count ≤ 1` or `timestep ≥ max_turns`), build its `GameResult` (`_build_result`), `yield FinishedGame`, then pull the next `PendingGame` into the freed slot. Fresh policies per game ⇒ diagnostics are captured at yield, before any reuse, automatically.

`pool_size` is in **concurrent games**; GPU batch rows ≈ `pool_size × nn_per_game`, so run_adhoc derives it to hit ~24–32 rows.

### 4.6 `run_adhoc` rewiring

The sequential loop collapses to: build all `PendingGame`s (fresh policies + a `MetricsCollector` each, stashed in `ctx`), then

```python
for fin in run_batched(pendings, pool_size=B, max_turns=...):
    collector, replay_id, slot_map, swapped = fin.ctx
    metrics = collector.finalize(fin.result, fin.policies)
    write_eval_game(...); write meta/metrics; append results.jsonl; accumulate stats
```

Rows land in completion order, each tagged with `game_index`; consumers sort if they care.

## 5. Correctness: the multi-game oracle

A disposable dev **script** (`packages/eval-tools/scripts/`) — retires once `run_game` collapses to a `pool_size=1` wrapper.

- **Reference**: live `run_game` per spec, compared game-for-game, matched by `game_index`. Chain of trust: existing `test_parity.py` pins `run_game` ≡ pre-refactor; this pins `batched ≡ run_game`.
- **Setup**: CPU (run-to-run reproducible, so flags are debuggable), `force_move`+argmax, NN-only (evalbot only in the pool=1 plumbing case, `np.random` seeded).
- **Cases**: C1 pool=1 reduces-to-run_game · C2 pool=1 NN-vs-evalbot plumbing · C3 refill+ragged (5 games, pool=2) · C4 multi-model (2 `model_key`s, pool=2) · C5 4p FFA NN-only.
- **Compare**: moves + winner + length + player_stats + curves → **exact**; on divergence, report first `(game, tick)` + the top1−top2 logit gap (tiny ⇒ benign forward-noise near-tie flip; structural/early/wrong-perspective ⇒ scatter bug). Diagnostics → **`allclose`** (atol ≈ 1e-3; the ~1e-4 forward delta flows into them).
- **Plus** a standalone *exact* check: `vec_decode` vs per-row `decode` on identical forward output → bitwise equal (pins the decode reshape free of forward noise).

## 6. Decisions

- **CPU = correctness truth** (reproducible, byte-comparable); MPS/cloud = throughput, with inherent (pre-existing) and acceptable nondeterminism in aggregate stats.
- **Tolerance-based oracle** from day one — the batched forward is never bitwise-equal to the sequential one; argmax robustness carries moves/outcome, `allclose` carries diagnostics.
- `pool_size` knob is **concurrent games**; run_adhoc translates from a target-rows setting.
- **Per-game generator seeded by `game_id`** — reproducible sampling across `B`/refill timing ([`5.30-1`] note 5).
- **Eager `PendingGame` construction** — cheap; heavy per-perspective state allocates at `init_for_game` (pool entry), not `__init__`.
- **Fix `_handle_cache` key** (`policy_spec.py`) to include `value_head_variant` — needed for correct batch grouping (`model_key` already includes it).

## 7. Build order

Correctness first, perf second, oracle as the gate between. **Commit after each chunk.**

1. **Move protocols → `game_runner/brain.py`** (+ `BatchablePolicy`); `NNAgent` references the new home. Behavior-preserving.
2. **Reshape decode** in `bc.inference` (`forward_batch` dict return, `decode_batch`, `RowDecision`, `DecodeConfig`, sync-free `select_action`, `NNAgent.act` spine). Guarded by `test_parity.py` (single-game equivalence) + the standalone exact `vec_decode` check. Fix `_handle_cache`.
3. **Naive batched runner** (`game_runner/batched.py`) — per-row decode is fine here; correctness only.
4. **Oracle script** green across C1–C5.
5. **Wire `run_adhoc`** onto `run_batched`; end-to-end eval parity + benchmark.

## 8. Deferred

- **Phase B** — overlap obs-build under the forward (or fan across cores) to approach ~7×; mandatory on cloud where the forward is nearly free. Measure that obs-build is the binding constraint first.
- **Collapse `run_game`** into `run_batched` at `pool_size=1` once the runner is trusted ([`5.30-1`] note 5).
- **EvalBot per-instance RNG** — would make mixed games reproducible run-to-run (currently global `np.random`).
- **O(1) perspective memory** — only if cloud-scale B makes the vestigial history lists matter.
