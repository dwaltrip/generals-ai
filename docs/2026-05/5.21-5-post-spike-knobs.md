# Post-spike: knobs worth turning next

**Date:** 2026-05-21
**Branch:** `main`
**Status:** Forward-looking planning note. Spike is closed; this seeds the next training-and-eval cycle.

## Where the spike landed

The training-spike-1 results are captured across [`5.21-1`](./5.21-1-debugging-value-head.md), [`5.21-2`](./5.21-2-spike-triage.md), and [`5.21-4`](./5.21-4-probe-findings.md). Together they form the spike-outcome record: pipeline works end-to-end, value head is mechanically broken (dead-ReLU), trunk encodes weak placement signal under linear probe, large list of deferred work in [`5.21-2`](./5.21-2-spike-triage.md).

This note ranks the next knobs to turn and proposes a clustering for sequencing.

## Framing — what we expect each knob to actually do

The most important framing for prioritization: **the architecture-fix isn't a slam-dunk for eval-this-checkpoint** purposes, but fixing the value head structurally **is a precondition for any value-gradient-driven trunk learning** in Phase 4 / PPO. The Mode B probe was performed on a trunk trained with ≈0 value gradient (head was dead from early epoch 1); it does not tell us what a trunk trained with a working value head would look like. So "swap option B value head for option C" doesn't fix current numbers — it's load-bearing in sequence, not in isolation.

This shape applies elsewhere too. Most individual knobs are necessary-but-not-sufficient pieces. The biggest wins compound rather than coming from any single change.

### Post-shuffle-buffer update

After landing the shuffle buffer (#2) and running a side-by-side PoC comparison: train value loss drops from ~2.0 (flat, dead-ReLU signature) to ~0.30 with the buffer on — the head is no longer stuck as a constant predictor. Val value worsens (1.97 → 3.42, well past the marginal floor), the same memorization signature as the spatial probes in [`5.21-4`](./5.21-4-probe-findings.md). Policy + top1 also improve modestly (val top1 0.519 → 0.570).

This sharpens the dead-ReLU framing from [`5.21-1`](./5.21-1-debugging-value-head.md) / [`5.21-4`](./5.21-4-probe-findings.md): the dominant driver was **batch class-starvation** (value_target = placement, constant per perspective → 64 copies of one class per baseline batch), not architectural fragility. The same option-B value head substantially unsticks just by getting class-diverse batches. Implication: the value-head structural fix (#7) is no longer a precondition for value-gradient flow — it's an architectural-capacity improvement that becomes load-bearing once data is sufficient to evaluate value-head generalization, and when the head's expressivity matters in PPO.

## Knob-by-knob, leverage ranked

In rough order of expected impact on output-move quality (Phase 1's actual success criterion):

### High leverage

1. **Scale: more data + more epochs.** PoC was 2k games × 5 epochs against a 180k-game corpus. Most ML quality wins come from "more learning signal," not "smarter architecture at the same scale." Loss curves at end-of-spike were still descending. Cloud H100 makes a 50k-150k game run cheap. Likely dwarfs every other knob in this list.
2. ✅ **Shuffle buffer (chunk 6 of the original [`5.17-4`](./5.17-4-training-spike-plan.md) plan).** Landed; default `--shuffle-buffer-size 2048` in `train_bc.py`. Per-batch policy + pass stdev roughly halved in the buffer-on PoC comparison; throughput cost is in the noise. Largely fixed the dead-ReLU symptom as a side effect (see post-shuffle-buffer update above).
3. **Board-symmetry augmentation (D4).** ~4-8× effective data through cell-position + direction-channel permutation. Cheap regularization win. Carries the "highest-blast-radius bug" warning from [`5.21-2`](./5.21-2-spike-triage.md) because the direction-channel round-trip under v-flip / h-flip / 180° is easy to get wrong — needs a unit-test gate before the augmentation goes live.
4. **Obs tensor fidelity fixes (from [`5.21-2`](./5.21-2-spike-triage.md) §Encoding gaps):**
   - ✅ Dense-history encoding: signed ownership-transition + production-subtracted delta landed. See [`5.21-6`](./5.21-6-obs-fidelity-handoff.md).
   - `opp_N_city_inference` channels are still all-zero stubs (7 of 96 channels = ~7%).
   - ✅ `opp_N_has_seen` channels landed (96-channel obs). See [`5.21-6`](./5.21-6-obs-fidelity-handoff.md).
   These compound at scale — every batch sees worse-than-design input.

### Medium leverage

5. **Trunk width: half → full (128/128/160 → 256/256/320).** ~4× params, ~4× FLOPs. The half-width was a v1 spike choice for M1 iteration speed; on cloud H100 the cost is acceptable. The PoC's policy + pass losses were still descending at epoch 5 — circumstantial evidence we're not over-capacity, so full-width should help. Defer until cloud is set up; M1 at full width makes iteration painful.
6. **Multi-worker dataloader.** Single-worker `IterableDataset` is fine at M1 scale (170 samples/sec was bearable for the PoC) but becomes a bottleneck at cloud scale where the GPU should never wait on data. Implementation gotcha: worker-aware splitting needs to be added to `IterableDataset.__iter__` — running `num_workers > 1` today yields each sample N times.
7. **Real v1 value head (option C — PyramidModule before projection).** Worth doing before the value head matters in earnest: the PyramidModule extension gives the head meaningfully more expressive capacity than option-B's "compute into 1 channel → linear project," and that matters once data is sufficient to train the head + when it's load-bearing in PPO. Not immediately next. Stubs in `training/bc/model.py:473-482`; conversion is ~half a day.

### Lower leverage (real but tune-late)

8. **Larger batch size (64 → 256-512).** Second-order. Affects gradient noise + wall-clock per step + slightly affects generalization; doesn't fix fundamental issues. Memory permits the bigger sizes at cloud scale.
9. **Slot-permutation augmentation** (separate from canonicalization which is already on). Cheap data multiplier; deferred from the spike for implementation-cost reasons. Picks up cross-game role generalization.
10. **Loss-weight tuning (`λ`, `μ` in `bc/loss.py`).** Initial weights are educated guesses; revisit if a head dominates or stagnates.
11. **Probe-script methodology fixes** (open items from [`5.21-4`](./5.21-4-probe-findings.md) §Open methodology gaps). Pre-req if we want to re-probe under different conditions.

## Skip connections — clarification

The trunk **already has skip connections** (encoder ConvResBlock pushes input as a skip; symmetric DeconvResBlock consumes via 1×1 projection + sum). The heads currently don't have internal residuals, which matches the DeepNash spec. If "implement skip connections" comes up again, clarify which layer is meant — the trunk's are already wired.

## Proposed clustering for sequencing

Three clusters, partly parallelizable. Each is sized to be a meaningful unit of work.

### Cluster A — "Make the next training run actually meaningful"

Local-iterable improvements that fix known gradient-quality and signal-quality bugs. M1 sufficient for smoke runs.

- ✅ Shuffle buffer (#2)
- Value head structural fix to option C (#7)
- Board-symmetry augmentation with round-trip unit test (#3)
- Obs-fidelity fixes (#4): ✅ dense-history encoding + ✅ `opp_N_has_seen` landed; `opp_N_city_inference` still pending

Validated by re-running the existing PoC training recipe (2k games × few epochs) on M1 and confirming loss curves look meaningfully different.

### Cluster B — "Cloud bring-up on Modal"

Independent of A; can proceed in parallel.

- Modal image with uv workspace + torch (probable friction: `uv sync` inside the image)
- Data shipping: parsed corpus → Modal Volume (~10 GB)
- Wrap `train_bc.py` as a Modal `@app.function(gpu="H100")`
- Pull artifacts back (checkpoints + JSONL)
- Smoke run: tiny slice, ensure end-to-end flow works

Auth + workspace already set up (per `zzz_test_modal.py` smoke). Estimated half-day to working smoke run; full-day to a clean kick-off / pull-results loop.

### Cluster C — "First real cloud run"

Depends on A landed locally and B brought up. The actual quality experiment.

- Full corpus subset (50k+ games, vs. spike's 2k)
- More epochs (10-20, vs. spike's 5)
- Start at half-width to iterate cheaply; go full-width once half-width result looks meaningful
- Multi-worker dataloader (#6) if data-loading throttles GPU
- Larger batch size (#8) if memory allows

This is the run that actually decides whether the pipeline produces a quality bot.

## Open questions for the next session

- **Which cluster to start on first?** A is necessary regardless of cloud timing; B unblocks scale; doing them in parallel is plausible if energy/focus permits.
- **Half-width or full-width as the iteration default once cloud is up?** Lean half-width for faster cycles, then a single full-width run at the end. But that's a hunch — could re-evaluate when the first cloud run finishes.
- **Corpus subset size for Cluster C's first real run?** 50k seems like a reasonable middle ground — big enough to dwarf the spike (25×), small enough to keep iteration cost low. Could go bigger if hours-per-run is acceptable.
- **Do we wait on the probe-methodology fixes before re-running probes, or just push directly to a real training run?** Probably the latter — direct training-run signal is more informative than probe signal right now.
