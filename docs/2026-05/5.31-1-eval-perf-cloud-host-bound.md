# Eval perf — the bottleneck flips by device (`5.31-1`)

**Status:** Investigation done. The batched runner now carries an opt-in per-region timer; we measured the per-tick split on M1/MPS and on a Modal T4. Key result: **eval is forward-bound on the M1 but obs-build-bound on cloud** — which reconciles the [`5.30-4`](./5.30-4-batched-runner-handoff.md) handoff (right about cloud) with what the M1 alone showed. Phase B (host-side gather overlap) is now empirically motivated — for cloud, not for the M1 dev loop. Build context: [`5.30-3`](./5.30-3-batched-runner-design.md) design, [`5.30-1`](./5.30-1-eval-perf-and-model-agent-refactor.md) original perf investigation.

Date: 2026-05-31

## TL;DR

- Added an opt-in per-region timer to `run_batched` (`game_runner.tick_timing`, env `BATCHED_TIMING`). Splits each tick into gather (`state_to_view` / `build_obs` / `cpu_act`), `fwd_decode` (the GPU region), and `step`.
- **M1/MPS: forward-bound.** Forward is 81% (self-play) / 65% (vs-evalbot). obs-build is only 9–14% — *not* the ~1.25 ms/row the handoff assumed; in-situ it's ~0.44 ms/row.
- **Modal T4: host-bound.** The gather (56%) exceeds the forward (44%), and `build_obs` alone (47%) is larger than the entire forward+decode. This is the crossover Phase B targets; the M1 stayed forward-bound across our runs.
- `sim_core` (Rust/pyo3) builds and runs on Modal with a ~3-line image recipe (rustup + maturin at image-build time).
- The cloud probe needs **no uploads** — checkpoint and maps both come from existing Modal volumes.

## The timer (`BATCHED_TIMING`)

`game_runner.tick_timing.TickTiming` is a start/lap stopwatch the runner annotates the loop with. Off by default (single `enabled` check, no `perf_counter` calls); set `BATCHED_TIMING=1` to print a per-region report when the pool drains. Buckets:

- **gather** (serial host-side CPU): `state_to_view` + `build_obs` per NN row, `cpu_act` per CPU-policy (evalbot) row.
- **fwd_decode** (GPU region): forward and decode timed *together* on purpose — on MPS the forward dispatch is async and the GPU→CPU sync lands inside `decode_batch`, so splitting them would misattribute the wait.
- **step**: `step_tick` + `on_tick` (metrics), excluding the yield.

Run it through `run_adhoc`:

```
BATCHED_TIMING=1 ./packages/eval-tools/scripts/run_adhoc.py \
  --policy checkpoint:<ckpt>.pt:force_move=true,value_head_variant=pyramid \
  --policy evalbot --maps random:40
```

Caveat that makes the timer non-trivial: the GPU region must be measured at its boundaries (`decode_batch`'s `.cpu()` is the sync barrier), not by wrapping `forward_batch` — naively timing the forward makes it look free and dumps its cost onto decode.

## Core finding: M1 is forward-bound, cloud is obs-build-bound

Self-play (NN-vs-NN), per-region, M1 vs T4:

| metric | M1 MPS (2p maps) | T4 (8p maps) |
|---|---|---|
| avg batch | 25.1 rows | 23.4 rows |
| build_obs / row | 0.438 ms | **1.614 ms** |
| state_to_view / row | 0.132 ms | 0.299 ms |
| forward+decode / row | 2.46 ms | 1.52 ms |
| forward+decode / tick | 61.9 ms | 35.5 ms |
| **gather share** | 19% | **56%** |
| **forward share** | 81% | 44% |

On the M1 the forward dominates; on the T4 the host-side gather overtakes it and `build_obs` is the single largest term. The original handoff's instinct — "with the forward batched, serial host-side CPU is the binding constraint" — was right *about the cloud regime*; we'd been measuring on the M1, where it doesn't hold. Both are true at once: **M1 forward-bound, cloud obs-build-bound.**

## Two surprises + one confound

- **The T4 only modestly speeds up the forward** (~1.6×/row vs M1 MPS — a clean comparison, since the obs tensor is padded to a fixed size, so the forward shape is identical for 2p and 8p maps). The forward is still 35 ms/tick, and per-tick wall (~80 ms) is in the same ballpark as M1 self-play (~76 ms). The T4 is a poor eval target.
- **obs-build per-row is ~3.7× higher on the T4** (0.44 → 1.61 ms/row). Unlike the forward, `build_obs` runs on the CPU and scales with actual board size, so this rise could be the slower cloud CPU, the bigger 8p boards, or both — confounded here (see below). Either way, the gather rising plus the forward dropping (faster GPU) is what tips eval host-bound on cloud.
- **Confound to resolve:** the runs used different map sets — M1 self-play on 2-player maps, T4 on 8-player maps (625–899 cells, measured; the 2p sizes weren't recorded). `build_obs` scales with actual board size, so the 3.7× per-row rise could be the slower cloud CPU, the differing boards, or both — these two runs can't separate them. An M1-on-8p run holds the maps fixed and isolates the CPU effect.

(In NN-vs-evalbot games the largest host-side term on the M1 is actually the evalbot's `cpu_act` at 22%, not obs-build — but that's evalbot-specific; self-play has none.)

## What this means for Phase B

Phase B (overlap/parallelize the serial gather) buys ≤14% on the M1 — skip it for the dev loop. On cloud it's where the headroom is, and the levers are:

- **Fan the gather across cores.** It currently runs serial on a slow, possibly few-core container. The first thing to check is how many vCPUs the T4 container even had — and whether requesting more + parallelizing `build_obs`/`state_to_view` shrinks the gather. (Open question from `5.30-1`: does obs-build release the GIL? If not, this needs processes, not threads.)
- **Overlap gather with the forward** via a two-pool software pipeline (while pool A's forward runs on the GPU, build pool B's obs on the CPU). Sidesteps the GIL question; the naive single-pool double-buffer doesn't work because of the per-tick step dependency.
- **A faster GPU** (L4/A10/H100) shrinks the forward further, pushing obs-build to the clear majority and making the host overlap the dominant win.

## Open / next

- **M1-on-8p isolation run** — re-run self-play on the same 8-player maps to separate cloud-CPU speed from the map differences in the 3.7× obs-build jump. Cheap; local 8p intermediate npz is available.
- **Faster-GPU probe** — run the same probe on L4/A10/H100 (`--gpu`) to see the forward collapse and confirm obs-build becomes the clear majority.
- **Check the T4 container's vCPU count** and re-run with more requested, to size the "fan across cores" headroom.
- **Then decide Phase B scope** with cloud numbers in hand.
