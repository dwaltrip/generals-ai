# Eval Bot Spec

**Date:** 2026.05.25

**Purpose:** Precise behavioral spec for the hand-coded eval bot. Pseudo-code level — enough for a fresh reader to understand the bot's decision logic without reading the implementation. Companion to the design doc (`5.24-3-eval-bot-design-doc.md`), which captures the design rationale and tradeoff discussions.

## 1. Game state interface

What the bot reads each tick. All sourced from `sim_core.State` + `MemoryState` (fog-tracking memory from `training.bc.obs`).

**Current-tick board (god-state arrays, but the bot fog-filters via visibility):**
- `ownership[H, W]` — int8. -2=mountain, -1=neutral, 0..7=player slot.
- `armies[H, W]` — int16. Army count per cell.
- `alive[P]` — bool. Per-player alive status.
- `timestep` — int. Current tick.

**Visibility (recomputed each tick):**
- `vis[H, W]` — bool. Moore-neighborhood dilation of owned tiles. Each owned tile sees all 8 surrounding cells (including diagonals).

**Fog-tracking memory (from MemoryState, advanced by `step_memory`):**
- `known_mountain[H, W]` — confirmed mountains (monotonic).
- `known_city[H, W]` — confirmed cities (monotonic).
- `known_general[H, W]` — confirmed live generals (cleared on capture→city).
- `is_structure[H, W]` — cells known to be some structure (mountain, city, or general). Visible through fog per game mechanics, but type unknown until directly observed.
- `historically_seen[H, W]` — cells ever visible (monotonic).
- `last_seen_owner[H, W]` — last observed owner. -2=never seen.
- `opp_contacted[P]` — bool. Ever had vision of player p's tile.
- `opp_captured_by[P]` — int8. -1=alive, 0..7=captor slot. Overlaps with `alive` but from MemoryState (tracks *who* captured, not just dead/alive). ContactSet uses `opp_captured_by`; scoreboard iterates `alive`.
- `general_locations[P]` — flat cell index of each known general. -1=unknown. Persists through re-fog (generals don't move).

**Scoreboard (visible input — public info per game mechanics §8):**
- `land[P]` — tile count per player.
- `army[P]` — total army per player.

The scoreboard is canonically visible to all players every tick, regardless of fog. In the sim environment, the bot computes these from the full ownership/armies arrays; this is equivalent to reading the in-game scoreboard.

## 2. Tick loop

```
each tick:
    1. update world model
       - compute visibility
       - advance MemoryState (fog tracking, contact detection, capture events)
       - update scoreboard
       - update ThreatWindow for each contact player
       - evaluate IncursionThreat for each contact player

    2. if active plan exists:
         if spent → clear plan, fall through to step 3

         if plan.gate == "defend":
             re-evaluate IncursionThreat
             if threat cleared → clear plan, fall through to step 3
             if most-severe player changed → replace with new defend plan

         if plan.gate not in ("defend", "killshot"):
             if defend would fire → preempt, create defend plan

         emit next move from plan
         done

    3. pick_target — walk decision ladder top-down:
         defend       → if IncursionThreat fires
         killshot     → if revealed enemy general and feasible (§6b)
         thin expand  → if expandable tiles above ratio threshold (§4.3, no plan)
         explore      → if unoccupied frontier exists (§4.4, creates plan)
         attack       → if PrimaryTarget exists
       first gate to fire → emit move (thin expand) or create plan → emit first move
       if no gate fires → pass
```

**Plan lifecycle:**
- **Created** when a gate fires. Holds a pre-computed move sequence.
- **Executed** one move per tick.
- **Completed** when all moves emitted (target reached).
- **Spent** when the plan can't make progress (see §5.4).
- **Preempted** when a higher-priority interrupt fires (defend preempts explore/attack).

**Re-evaluation and stickiness:**

Only **defend** actively re-evaluates mid-plan — it re-checks IncursionThreat each tick and reacts to changing threats (threat cleared, different player becomes most severe). This is the "no stickiness" from the design doc: defense is reactive, lingering wastes economy.

**Explore** plans are static once created — the pre-computed move sequence runs to completion. The bot does not re-run sector scoring or re-pick the fog target mid-gather. This is an intentional simplification: explore gathers are short (bounded by `EXPLORE_MAX_PLAN_TICKS`), so the target is unlikely to become stale before the plan completes. "No stickiness" for explore means: when the plan completes, re-plan fresh rather than auto-chaining in the same direction. Not "re-evaluate every tick."

**Attack** is somewhat-sticky via hysteresis — the current target gets a scoring bonus, so a new target must outscore it by `ATTACK_SWITCH_THRESHOLD` to trigger a mid-plan switch. Prevents churn between close-scoring alternatives while allowing switches to dramatically better opportunities (e.g., a contacted player suddenly weakened by a third-party fight).

**Kill-shot** is fully sticky while in-flight. Highest-value, most time-sensitive target — abandoning mid-gather wastes the investment.

All non-defend/killshot plans are freely preempted by defend (the highest-priority interrupt).

## 3. World model update

Runs at the top of each tick before any gate logic.

### 3.1 ContactSet

```
ContactSet = { p : opp_contacted[p] and opp_captured_by[p] == -1 }
```

Populated by `step_memory` when the bot's visibility overlaps an opponent's tile. Eliminated players filtered out at read time.

### 3.2 Scoreboard

```
for each alive player p:
    land[p] = count(ownership == p)
    army[p] = sum(armies where ownership == p)
```

Stored in a rolling history buffer for delta-based metrics.

### 3.3 RelativeStrength

```
RelativeStrength(p).army = army[p] / mean(army[q] for alive q != p)
RelativeStrength(p).land = land[p] / mean(land[q] for alive q != p)
```

Values > 1 = above field average.

### 3.4 ConflictFlag

```
land_delta[p] = land[p, now] - land[p, now - CONFLICT_WINDOW]

ConflictFlag(p) = true if:
    land_delta[p] < -CONFLICT_THRESHOLD
    and exists q != p where land_delta[q] > +CONFLICT_THRESHOLD
    and abs(land_delta[p] + land_delta[q]) < CONFLICT_MATCH_TOL
```

Detects two players fighting by mirrored land deltas.

### 3.5 ThreatWindow

Per-player sliding buffer tracking the largest visible enemy stack.

```
for each p in ContactSet:
    visible_p = vis & (ownership == p)

    if no visible tiles for p:
        clear window[p], clear eating_baseline[p]
        continue

    best_pos = argmax(armies where visible_p)

    # identity check — stack moves at most 1 cardinal tile per tick
    if window[p] is not empty:
        prev_pos = window[p][-1].pos
        dr = abs(best_pos.row - prev_pos.row)
        dc = abs(best_pos.col - prev_pos.col)
        if dr + dc > 1:
            clear window[p], clear eating_baseline[p]
            # TODO: handle merging stacks (two enemy stacks combining
            # causes a position jump that breaks identity tracking)

    # snapshot ownership baseline when window opens fresh
    if window[p] is empty:
        eating_baseline[p] = copy of (ownership == my_slot)

    window[p].append({
        pos: best_pos,
        army: armies[best_pos],
        dist_to_general: bfs_dist(best_pos, my_general)
    })
```

Window length is `THREAT_WINDOW_LEN`. Oldest entries fall off the deque automatically.

### 3.6 IncursionThreat

```
IncursionThreat(p) = Closing(p) AND Eating(p)
```

Both conditions must hold — a stack getting closer without capturing tiles is passing by; tiles flipping without an approaching stack is border skirmishing.

**Closing — moving average of distance deltas:**

```
if len(window[p]) < 2:
    return false

deltas = [window[i].dist - window[i-1].dist for consecutive pairs]
return mean(deltas) < CLOSING_THRESHOLD
```

Negative mean = distance to general trending down. Naturally handles pauses (one tick of no movement dilutes the average but doesn't kill the signal).

**Eating — tile flips within Manhattan radius:**

```
threat_pos = window[p][-1].pos

eaten = count of cells where:
    manhattan_dist(cell, threat_pos) <= EATING_RADIUS
    and eating_baseline[p][cell] == true    # was mine at window-start
    and ownership[cell] == p                # now theirs

return eaten >= EATING_MIN
```

NOTE: Manhattan is an approximation — doesn't account for mountains shaping the actual reachable area. Acceptable at small radii.

The eating baseline is a bool snapshot of `(ownership == my_slot)` taken when the window opens. Held for the window's lifetime, discarded on identity break. Anchored on past ownership so the metric doesn't cannibalize itself as tiles flip.

## 4. ExpandOrExplore

The bot's default mode. Two sub-modes switched by a ratio.

### 4.1 Metrics

**ExpandableTiles:** owned tiles with army >= 2 adjacent to at least one neutral 0-garrison tile. These are free single-step expand moves.

**UnoccupiedFrontier:** owned tiles adjacent to at least one neutral tile (any garrison). The outward-facing border surface.

All orthogonal neighbors of owned tiles are visible (Moore neighborhood), so no fog filtering needed for these metrics.

### 4.2 Mode switch

```
if UnoccupiedFrontier == 0:
    fall through (nothing to expand or explore into)

elif ExpandableTiles / UnoccupiedFrontier >= EXPAND_EXPLORE_THRESHOLD:
    expand mode

else:
    explore mode
    if explore returns no move, fall back to expand if any expandable tiles
```

### 4.3 Expand mode

Thin BFS crawl. No plan, no gather — single-step moves.

```
pick a random expandable tile (uniform over the set)
move it onto a random adjacent empty neighbor
```

Randomized selection avoids directional bias from deterministic iteration order. Expand moves are cheap and plentiful after land ticks — the distribution smooths out over many moves.

### 4.4 Explore mode

Push toward the least-explored sector using gather_path (§5).

**Target selection:**

```
1. bucket all non-structure never-seen tiles into 4 quadrants from general
2. winning sector = quadrant with most passable fog tiles
3. frontier_edge = owned tiles adjacent to fog in winning sector
4. multi-source BFS from all frontier_edge tiles into fog
   target = random fog tile at exactly depth EXPLORE_FOG_DEPTH;
            if none at that depth, random among deepest available (≤ EXPLORE_FOG_DEPTH)
5. plan = gather_path(target, max_moves=EXPLORE_MAX_PLAN_TICKS,
                      min_army=EXPLORE_MIN_ARMY, gate="explore")
6. if plan is None → fall through (can't assemble enough army in time)
```

The target is a fog tile deep enough to reveal meaningful new territory. Structures are visible through fog (§7), so BFS paths through unexplored terrain are reliable. `EXPLORE_FOG_DEPTH` and `EXPLORE_MAX_PLAN_TICKS` are independent knobs — depth controls how far into fog the bot aims, while max_moves caps total plan duration. If the depth target is unreachable within the time budget, gather_path returns None and the bot falls through.

## 5. gather_path

The shared "assemble a stack and sweep it to a destination" primitive. Used by Explore, Defend, Attack, and Kill-shot.

```
gather_path(target, max_moves, min_army=None, gate=...) -> plan or None
```

- `target` — the actual destination cell (fog tile, intercept point, enemy general, enemy frontier tile). The caller determines this.
- `max_moves` — hard cap on total plan length (side-gathers + sweep combined). The caller sets this based on context: tunable constants for explore/attack, invader ETA for defend.
- `min_army` — optional feasibility floor. If the best plan within `max_moves` can't deliver at least this much army (per §5.3 estimate), return None. The caller falls through to the next gate.
- `gate` — which gate is calling (affects reserve behavior).

**TODO — best-effort fallback:** When `min_army` isn't met, some gates (defend especially) may benefit from executing the best available plan rather than abandoning entirely. For v1, return None uniformly; revisit if defend feels under-responsive.

### 5.1 Source selection

```
source = argmax over owned tiles:
    effective_army(tile) - SOURCE_DIST_WEIGHT * bfs_dist(tile, target)
```

Balances army size against distance. The general often wins (most army), but a closer fat stack can beat it. Source selection is implicitly constrained by `max_moves` — a source whose BFS distance to target exceeds `max_moves` cannot produce a valid plan.

**General's effective army (reserve-aware):**

```
reserve_amount = int(RESERVE_FRACTION * total_army)

if gate bypasses reserve (Defend):
    effective = general.army - 1                  # normal move, full drain

elif ceil(general.army / 2) >= reserve_amount:
    effective = floor(general.army / 2)           # split move

else:
    effective = 0                                 # general unavailable
```

The reserve is a fraction of total army, so it scales with game phase. The general can only send `army - 1` (normal) or `floor(army / 2)` (split) — the split mechanic is how the bot retains army on the general without violating move rules.

**Mobile army and commit budgets:**

```
mobile_army = total_army - reserve_amount
```

The army the bot is willing to spend on non-defensive actions. Explore and Attack commit budgets are fractions of this:

```
commit_amount = int(RISK_FRACTION * mobile_army)
```

`RISK_FRACTION` controls how much mobile army the bot commits per plan. Higher = more aggressive pushes, but strips the frontier. Lower = lighter touches, less threat projection.

### 5.2 Pre-computed move sequence

The gather produces a flat list of moves, emitted one per tick. Total moves must not exceed `max_moves`.

```
path = bfs_path(source, target)
sweep_cost = len(path) - 1
remaining = max_moves - sweep_cost

# phase 1: side-gathers (fatten the path before the sweep)
# budget: whatever moves remain after the sweep is accounted for
max_side = min(remaining, floor(SIDE_GATHER_FRACTION * len(path)))
candidates = owned tiles within BFS dist 1-2 of any path tile,
             army >= 2, not on the path
candidates.sort(by army, descending)
side_gathers = candidates[:max_side]

for each side-gather s, ordered by injection point (source→target):
    moves.append(s → nearest path tile, is50=0)

# phase 2: sweep (roll army from source to target)
for i in 0 .. len(path) - 2:
    is50 = 1 if path[i] is general and gate respects reserve, else 0
    moves.append(path[i] → path[i+1], is50)

# feasibility check
if min_army is not None and army_estimate(§5.3) < min_army:
    return None
```

Side-gathers ordered by their injection point (the path tile each side-gather pushes onto), from source-end to target-end of the path. This ensures side-gathered army is on the path before the sweep reaches it.

If `max_moves` is too small to fit even the sweep (source too far from target), that source is skipped in source selection and the next-best source is tried.

### 5.3 Army estimate

```
gather_set = path tiles + side-gather source tiles
arriving = sum(tile.army for tile in gather_set) - (len(gather_set) - 1)
```

Each participating tile except the target leaves 1 army behind. The general contributes `floor(army / 2)` instead of `army - 1` when using a split move. Computed at plan creation — does not account for production or combat during the gather.

### 5.4 Spent detection

Checked each tick before emitting a move. If spent, plan is cleared and the bot re-plans.

```
spent if:
    - leading tile has army == 1 (can't advance)
    - leading tile faces enemy garrison >= its own army (blocked)
    - for kill-shot plans: attacking army < target general's army (infeasible)
```

## 6. Defend

The highest-priority gate. Interrupt — preempts any active Explore or Attack plan.

### 6.1 Trigger

```
fires when IncursionThreat(p) is true for any p in ContactSet
if multiple: pick most severe (closest to general, then largest army)
```

### 6.2 Severity and response target

```
path_bleed = sum of my army on BFS path from threat to my general

if threat_army > armies[my_general] + path_bleed:
    # high severity — genuine survival threat
    target = my_general

else:
    # intercept — meet them before they arrive
    path_to_general = bfs_path(threat_pos, my_general)
    idx = min(INTERCEPT_LOOKAHEAD, len(path_to_general) - 1)
    target = path_to_general[idx]
```

### 6.3 Commit and plan creation

```
commit = threat_army + DEFEND_MARGIN
max_moves = window[p][-1].dist_to_general - INTERCEPT_LOOKAHEAD
plan = gather_path(target, max_moves=max_moves,
                   min_army=commit, gate="defend")
```

The time budget is derived from the invader's ETA — the bot must assemble and intercept before the threat reaches the general. Reserve is bypassed for defend (§5.1).

### 6.4 Exit

No stickiness. `IncursionThreat` is re-evaluated each tick. When it goes false (stack retreated, destroyed, or collision resolved), the defend plan is cleared and the bot re-plans immediately.

## 6b. Kill-shot

Fires when a revealed enemy general exists and the bot can feasibly capture it. Highest-value, most time-sensitive target — capturing a general grants all of that player's territory via inheritance.

### 6b.1 Trigger

```
travel_time = len(plan.moves)  (total ticks: side-gathers + sweep)
margin = KILLSHOT_MARGIN_BASE + KILLSHOT_MARGIN_PER_STEP * travel_time

KillShotFeasible(g) =
    revealed enemy general g exists
    and gatherable_army >= g.army + path_bleed + margin
```

Margin scales with travel time — longer travel gives the defender more time to reinforce. The static estimate intentionally undershoots against alert defenders; the bot reliably finishes undefended or distracted generals.

**TODO — `gatherable_army`:** This is the army the bot could deliver to the enemy general. Non-trivial to estimate without speculatively building a full gather path. Needs a cheaper feasibility heuristic — possibly `sum(army on owned tiles within BFS radius R of the enemy general) - path_costs`, or just the §5.3 army estimate from a speculative source selection. The inputs and precision tradeoff need to be worked out.

**TODO — `path_bleed` in kill-shot context:** In Defend (§6.2), path_bleed is the bot's own army along the path from threat to its general (the "speed bumps" the invader must chew through). In kill-shot, path_bleed should be the *enemy's* army along the path from the bot to *their* general — but this needs to be stated precisely. The term is overloaded between the two contexts.

Discovered generals persist in memory (structures never move; a general only disappears when captured, which is globally announced).

### 6b.2 Reserve behavior

Same-player kill-shot (the kill target is the same player triggering IncursionThreat) bypasses the reserve — the kill resolves the threat via inheritance. Kill-shots against other players respect the reserve.

### 6b.3 Defend interaction

If the player triggering IncursionThreat has a revealed general, and the bot wins the race, kill-shot preempts defend:

```
my_time_to_their_general < invader_time_to_my_general + RACE_MARGIN
```

`my_time_to_their_general` = `len(plan.moves)` (total plan ticks). `invader_time_to_my_general` = invader's `dist_to_general` from ThreatWindow. This override only applies when the kill target is the same player attacking the bot.

**TODO — race condition units:** `my_time` includes gather overhead (total plan ticks). `invader_time` is BFS distance in cells, which equals ticks only if the invader moves one cell per tick toward the general with no pauses or combat. The two sides are in different units. Either normalize both to the same unit, or ensure RACE_MARGIN is large enough to absorb the asymmetry. Needs to be worked out.

Fully sticky while in-flight (see §2).

## 6c. Attack

Target = `PrimaryTarget`'s nearest visible frontier tile (or revealed general if known). Doubles as general-hunting — vision flows toward the target as the bot pushes into their territory. Reserve is respected. Somewhat-sticky via hysteresis (see §2).

### 6c.1 ThreatScore / TargetScore

Two composite rankings over ContactSet, sharing the same inputs with opposite polarity on strength.

**ThreatScore(p)** — "who do I avoid opening a front against":

```
min_dist(p) = BFS dist from p's nearest visible tile to my general

ThreatScore(p) = w1 * RelativeStrength(p).army
               + w2 * (1 / max(1, min_dist(p)))
               + w3 * has_recent_attack(p)
               - w4 * ConflictFlag(p)
```

`has_recent_attack(p)`: tiles the bot owned have flipped to player p, detected via the eating baseline machinery — `eating_baseline[my_slot]` marks tiles that were mine, current visibility shows tiles now owned by p. Reuses the same infrastructure as the Eating metric (§3.6).

NOTE: with perfect information, this would track all tile flips over a rolling window. The fog-limited version only detects flips in currently visible tiles, which biases toward detecting attacks on the bot's active frontier (where vision exists) and missing attacks on distant territory that has re-fogged. This is acceptable — frontier attacks are the ones that matter for threat assessment.

**PrimaryThreat** = argmax ThreatScore over ContactSet.

**TargetScore(p)** — "who can I profitably kill":

```
if RelativeStrength(p).army > 1.0:
    TargetScore(p) = 0                        # hard gate: don't initiate against stronger
else:
    TargetScore(p) = w1 * (1 / max(0.1, RelativeStrength(p).army))
               + w2 * (1 / max(1, min_dist(p)))
               + w3 * (land_delta(p) > 0)     # growing = closing window, urgency
               - w4 * ConflictFlag(p)          # don't provoke distracted strong player
```

**PrimaryTarget** = argmax TargetScore over ContactSet, excluding zeros. Can be None (everyone in contact is stronger).

Weights (w1..w4) are tuning levers. Low-leverage when ContactSet has 1-2 players (no ranking needed); becomes important for difficulty tiers.

### 6c.2 Contact reclassification

An explore push that gains vision of enemy tiles checks whether to continue:

```
if plan_leading_tile_army > visible_enemy_frontier_army:
    keep pushing (the explore push becomes an attack; pick_target picks it up)
else:
    push is spent — stop, re-evaluate
```

### 6c.3 De-escalation

On contact with a non-PrimaryTarget, the push is spent and the bot re-evaluates. The bot declines to open a new front but holds position. A holding bot can't be herded; only a fleeing one can.

### 6c.4 Commit and time budget

```
commit = RISK_FRACTION * mobile_army
plan = gather_path(target, max_moves=ATTACK_MAX_PLAN_TICKS,
                   min_army=commit, gate="attack")
```

Same budget-based formula as explore. Time budget is a tunable constant — attack plans that take too long risk stale targeting as the board evolves.

## 7. Passability

BFS throughout the bot uses a known-passable mask:

```
passable = not (known_mountain or known_neutral_city or structure_in_fog)
```

- `known_mountain` — confirmed mountains. Permanently impassable.
- `known_neutral_city` — confirmed neutral cities (`known_city` and not owned by any player). Treated as impassable — the bot doesn't capture neutral cities in v1 (city capture is a scope exclusion).
- `structure_in_fog` — cells known to be structures but whose type is unknown (mountain vs. city is indistinguishable behind fog). Treated as impassable.
- `known_city` tiles owned by the bot or an opponent are passable (ownership means the garrison has already been resolved).

All BFS is 4-connected (cardinal directions only — generals.io moves are orthogonal).

## 8. Tunable constants

Every tuning knob, its default, and what adjusting it does.

### Defend sensitivity

| Constant | Default | Effect |
|---|---|---|
| `THREAT_WINDOW_LEN` | 8 | Deque maxlen. Longer → more history before closing signal is reliable, slower to react. Shorter → twitchier, more false positives. |
| `CLOSING_THRESHOLD` | -0.3 | Moving average of distance deltas must be below this to count as closing. More negative → requires faster approach to trigger. Less negative → triggers on slower drift. |
| `EATING_RADIUS` | 3 | Manhattan radius around threat for tile-flip count. Larger → catches wider attacks but risks false positives from distant skirmishes. |
| `EATING_MIN` | 3 | Minimum flipped tiles within radius to qualify as eating. Higher → more lenient (ignores small incursions). Lower → twitchier. |

### Defend response

| Constant | Default | Effect |
|---|---|---|
| `DEFEND_MARGIN` | 5 | Extra army committed above threat size. Higher → safer collision outcome but more army diverted from economy. |
| `INTERCEPT_LOOKAHEAD` | 3 | Steps ahead of invader to place intercept tile. Higher → meet the threat earlier but risk gathering to empty space. Lower → tighter intercept but less reaction time. |

### Economy / risk posture

| Constant | Default | Effect |
|---|---|---|
| `RESERVE_FRACTION` | 0.25 | Fraction of total army held on general for non-defend gates. Higher → safer against surprise attacks but less mobile army for expansion. Lower → more aggressive but vulnerable. |
| `RISK_FRACTION` | 0.5 | Fraction of mobile army committed per explore/attack plan. Higher → bigger pushes, more threat projection, but strips the frontier. Lower → lighter touches, less impact per push. |
| `EXPAND_EXPLORE_THRESHOLD` | 0.4 | ExpandableTiles / UnoccupiedFrontier ratio below this → explore mode. Higher → more exploring, less passive filling. Lower → more expanding, less fog-pushing. |
| `EXPLORE_FOG_DEPTH` | TBD | How many tiles past the frontier edge the explore target is placed. Deeper → more map revealed per push but more army/time committed. Shallower → lighter, more frequent pushes. |
| `EXPLORE_MIN_ARMY` | TBD (possibly 4 or 5) | Flat minimum army floor for explore plans. Explore pushes through empty fog, so this is a low sanity check ("don't bother if we can barely move"), not a combat-scale commitment. |

### gather_path

| Constant | Default | Effect |
|---|---|---|
| `SOURCE_DIST_WEIGHT` | 1.0 | `k` in `effective_army - k * dist`. Higher → prefer closer sources over fatter distant ones. Lower → prefer raw army size regardless of distance. |
| `SIDE_GATHER_FRACTION` | 0.5 | Cap on side-gather count as fraction of path length. Higher → fatter gathers but more ticks before the sweep starts. Lower → leaner, faster gathers. |
| `EXPLORE_MAX_PLAN_TICKS` | TBD | Max moves for an explore plan. Bounds how far the bot pushes into fog per exploration cycle. |
| `ATTACK_MAX_PLAN_TICKS` | TBD | Max moves for an attack plan. Longer plans risk stale targeting. |

**TODO — dynamic time budgets:** The static constants above could be replaced by cheap dynamic heuristics (proportional to map size, scaled by game phase, responsive to board density). For v1, static constants are sufficient; revisit if the bot over- or under-commits at different map scales.

### Kill-shot

| Constant | Default | Effect |
|---|---|---|
| `KILLSHOT_MARGIN_BASE` | TBD | Flat army margin added to the kill-shot feasibility check. Absorbs estimation error independent of distance. |
| `KILLSHOT_MARGIN_PER_STEP` | TBD | Additional margin per step of travel time. Accounts for defender reinforcing during the gather. Higher → more conservative (only commits to close/weak generals). |
| `RACE_MARGIN` | TBD | Ticks of slack in the defend-vs-killshot race condition. Higher → less willing to race (safer). |

### Attack

| Constant | Default | Effect |
|---|---|---|
| `ATTACK_SWITCH_THRESHOLD` | TBD | Hysteresis bonus for the current attack target. A new target must outscore the current one by this margin to trigger a mid-plan switch. Higher → more committed to current attack. Lower → more opportunistic switching. |

### Conflict detection

| Constant | Default | Effect |
|---|---|---|
| `CONFLICT_WINDOW` | 20 | Ticks over which land deltas are measured. Longer → smooths out noise but slower to detect new conflicts. Shorter → faster detection but noisier. |
| `CONFLICT_THRESHOLD` | 3 | Minimum land loss/gain over the window to count as fighting. Higher → ignores minor border skirmishes. Lower → more sensitive. |
| `CONFLICT_MATCH_TOL` | 5 | How closely two players' land deltas must mirror (abs of sum). Lower → stricter pairing. Higher → more permissive matching. |

## 9. Algorithmic costs

All operations are O(H×W) or cheaper. FFA maps go up to ~30×30 (900 cells).

The bot runs in eval/self-play (no external clock) — the constraint is throughput (games per unit wall time), not a per-tick deadline. At 900 cells with pure-Python BFS, a full game (~500 ticks) takes roughly 200–300ms. Sufficient for v1 eval runs; if scaling to large self-play batches later, the Python-loop BFS is the first optimization target (Rust extension like sim_core, Cython, or numpy-based).

### Per-tick (every tick, mandatory)

| Operation | Cost | Notes |
|---|---|---|
| Visibility (Moore dilation) | O(H×W) | Numpy shift ops, vectorized |
| step_memory (fog tracking) | O(H×W) | Boolean mask updates |
| Scoreboard (land/army per player) | O(P × H×W) | P=8, effectively O(H×W) |
| known_passable_mask | O(H×W) | Combine boolean arrays |
| ThreatWindow update | O(H×W) per contacted player | Argmax of enemy armies in vision |
| IncursionThreat (eating check) | O(EATING_RADIUS²) | Bounded by small radius, trivial |

### Plan-creation tick (once every N ticks)

| Operation | Cost | Notes |
|---|---|---|
| Frontier / expandable tile masks | O(H×W) | Numpy shift ops |
| Sector scoring | O(H×W) | Iterate cells, bucket into quadrants |
| BFS (4–5 calls) | O(H×W) each | Source selection, path, side-gathers, target selection |
| Source selection scoring | O(owned_tiles) | ≤ O(H×W) |
| Side-gather candidate search | O(H×W) | Multi-source BFS from path tiles |

### Trivially small

| Operation | Cost |
|---|---|
| RelativeStrength | O(P) |
| ConflictFlag | O(P²) |
| Plan emit (non-creation ticks) | O(1) — index into pre-computed move list |

### Summary

The numpy-vectorized operations (visibility, masks, scoreboard) are effectively free. The Python-loop BFS calls are the "slowest" item and complete in well under 1ms at this grid scale. Plan-creation ticks are heavier (clustering several BFS calls) but still under 10ms total. No approximations needed for compute reasons — BFS is the natural tool at this scale and can be used freely throughout the design.
