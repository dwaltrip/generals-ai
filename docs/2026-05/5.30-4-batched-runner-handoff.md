# Batched eval runner — handoff (`5.30-4`)

**Status:** Phase A complete — the batched eval runner is built, validated against `run_game`, and wired into `run_adhoc`. Next focus: **obs-build performance (Phase B)**, which is now the binding constraint. Build spec with full interfaces: [`5.30-3`](./5.30-3-batched-runner-design.md). Original perf investigation: [`5.30-1`](./5.30-1-eval-perf-and-model-agent-refactor.md).

## What landed

Eval was forward-bound: the model ran batch-size-1 on MPS, one game at a time, starving the GPU (~1hr for 100 games). The fix is a vectorized runner that drives many games concurrently through one batched forward per tick. `game_runner/batched.py`'s `run_batched` keeps a fixed pool of concurrent games, gathers the live NN perspectives each tick, groups them by model for one forward + decode per model, scatters the results back, steps every game, and refills finished slots from a pending queue. `run_adhoc` now drives all its games through it.

Measured end-to-end on the M1/MPS (`run_adhoc`, pool=1 vs auto, same maps/seed): **~4.2× on NN-vs-evalbot** (81.1s → 19.2s, 20 games — this is the true B=1 baseline, the original "batch-size-1" problem) and **~2.7× on self-play** (39.1s → 14.4s, 12 games — lower only because its pool=1 baseline already batches the 2 NN perspectives into B=2). The residual is serial host-side CPU (obs-build, `state_to_view`, evalbot `act`, `step_tick`, metrics) — see Phase B.

## Design decisions worth remembering

**The load-bearing problem was decode, not the forward.** Each `.item()` GPU→CPU sync costs ~0.33ms on MPS, and the per-tick decode did ~9 of them. Calling the old per-row `decode` inside a batched loop would issue B×9 syncs/tick — at B=32 that's ~95ms, *larger than the ~57ms forward it was meant to amortize*. Vectorizing the decode (all math batched, one bulk sync, flat ~1ms) is what actually unlocks the win; naive per-row decode would have capped it at ~2.5×. This is the non-obvious insight the whole design hangs on.

**Decode is split at the sync boundary, and the single-game path rides the same spine.** `BCModelHandle.forward_batch` → `decode_batch` (all GPU math + one bulk sync → plain-CPU `RowDecision`s) → `BCPerspective.select_action` (sync-free bookkeeping). `NNAgent.act` is just this spine at batch-of-1, so `run_game` and `run_batched` share the exact same decode — which is why the parity guarantee is essentially free.

**`game_runner` stays torch-free and model-agnostic.** It depends only on the `brain.py` protocols (`ModelHandle`, `BatchablePolicy`) and shuttles *opaque* forward-outputs and decode-configs between `forward_batch` and `decode_batch` without inspecting them. The BC specifics live in `bc.inference`, which satisfies the protocols structurally. Multi-model eval (head-to-head, sweeps) falls out of grouping rows by `model_handle.model_key` — one forward per distinct model.

**CPU is the correctness oracle; the batched forward is never bitwise-equal to the sequential one.** Measured: the forward is *not* bitwise batch-invariant on any device (~1e-4 on CPU, ~1e-5 on MPS — MKL/MPS pick different conv algorithms by batch size), but argmax/pass decisions are robust to it (the decision margin is ~0.24, ~3-4 orders larger). So: moves/winner/length/stats compare *exact*, diagnostics compare *allclose*. MPS eval carries inherent (pre-existing) run-to-run nondeterminism and is throughput-only; CPU is where we prove correctness.

**Correctness is gated by a disposable multi-game oracle.** `scripts/oracle_batched_parity.py` runs each spec through both runners and compares full per-game artifacts. ALL PASS across reduces-to-run_game, evalbot plumbing, refill, multi-model grouping/scatter (epoch_003 vs epoch_005), and 4-player multi-perspective. Chain of trust: `test_parity` pins `run_game` ≡ pre-refactor → the oracle pins `batched` ≡ `run_game`. It retires once `run_game` collapses into `run_batched` at pool=1.

**EvalBot is nondeterministic** (global unseeded `np.random` in `expand.py`), so any byte-exact comparison involving it must be NN-only — the oracle uses evalbot in just the single-game plumbing case with a seed.

## Next: obs-build performance (Phase B)

With the forward batched and decode cheap, **serial host-side CPU is the next ceiling** — the Amdahl wall behind the measured ~4.2×. The biggest unbatched term is obs-build (`BCPerspective.encode`, ~1.25ms/perspective; at B=32 that's ~40ms/tick of *serial* CPU against a ~57ms forward), but it isn't the only one: `state_to_view`, evalbot `act`, `step_tick`, and metrics all run serially per game/tick too. `step_tick` (mutates the sim) and metrics are inherently serial, so the realistic Phase B ceiling is set by how much of the *gather* (state_to_view + obs-build) can be overlapped/parallelized, not the raw forward ceiling.

Where it lives: obs-build is `BCPerspective.encode` (`training/bc/inference.py`), called via `NNAgent.build_obs` in `run_batched`'s **gather** step (`game_runner/batched.py`) — all rows' observations are built serially before the forward. That serial gather is the Phase B target.

Levers (from [`5.30-1`] §4):
- **Pipeline / double-buffer** — build wave *t+1*'s observations on the CPU while the GPU runs wave *t*'s forward, so the two overlap instead of serialize.
- **Fan obs-build across cores** — the M1 has 8 P-cores and the pipeline is numpy-heavy. **Caveat to verify first:** this rests on the assumption that obs-build releases the GIL. If it's actually GIL-bound pure-Python, threads won't help and you'd need processes (with serialization cost). Check before committing to the threaded approach.
- **Measure first** — instrument `run_batched` to confirm obs-build is the binding constraint before adding concurrency; the per-tick split between gather (obs) and forward+decode is the thing to log.
- **Cloud makes it mandatory** — on a fast GPU the forward is nearly free, so host-side obs-build *is* the bottleneck. Phase B (plus enough vCPUs) is what makes cloud eval fast, not a bigger batch.

## Deferred / be aware

- **Fork #4 — reproducible sampled eval.** Per-game `torch.Generator` is threaded through `decode_batch` but seeded `None` (global RNG). Seed it by `game_id` to make sampled eval reproducible across batch size / refill timing. The common path (force_move + argmax) is fully done and unaffected. MPS generators verified working.
- **Collapse `run_game` into `run_batched` at pool=1** once the runner is fully trusted, removing the duplicate game loop (and retiring the oracle).
- **EvalBot per-instance RNG** would make mixed games reproducible run-to-run.
- **`pool_size` is in concurrent games**; GPU batch rows ≈ `pool_size × nn_per_game`. Sweet spot is ~24-32 rows on the M1; the optimum is device-specific and far larger on cloud GPUs.
- **Disposable artifacts:** `scripts/{bench_decode_sync, probe_mps_stability, probe_row_independence}.py` and the oracle are diagnostic/dev scripts, kept as the empirical record — not load-bearing.
