# Eval perf investigation + ModelAgent refactor (`5.30-1`)

**Status:** Phase 0 (the refactor) done on branch `refactor-model-agent` (6 commits, `61ac905`→`c9c3681`, tree clean, 209 tests pass). Phase A (the actual speedup — a batched runner) is sketched but **not built**. Perf findings also saved to auto-memory `project_eval_perf_batched_runner`.

## 1. Perf investigation (why eval is slow)

Question: a 100-game eval run takes ~1hr on the M1. Profiled it (probes in `tmp/perf_probe/bench_*.py`). Findings (M1 Max, epoch_005 pyramid):

- **~95% of per-`act()` time is the model forward + GPU sync.** CPU obs-build is ~1.25ms/act (~5%); evalbot is ~1.7ms/act. Neither is worth touching.
- The forward runs **batch-size-1 on MPS**: ~14ms forward + ~7ms of `.item()` sync tax (the per-tick diagnostics fire ~9 GPU→CPU `.item()` reads). Games run strictly sequentially, one tick at a time → the GPU is starved.
- **Batching is the win.** MPS forward per-sample: batch 1 = 10.4ms, batch 8 = 2.6ms, batch 24–32 = ~2.2ms (peak ~460 acts/s), flat/slightly-worse beyond. So ~5x throughput from filling the GPU.
- "Switch to CPU" is a non-starter: CPU is *slower* than MPS even at batch 1 (~25–30ms). The `direct` value head is ~20% cheaper than `pyramid` at batch 1.
- Sweet spot **B ≈ 24–32** with slot-refill (games are ragged, ~165–1000 ticks). The knee is device-specific: a cloud GPU's optimal B is far larger, and there the bottleneck moves to **host-side obs-build**, so size it from an end-to-end bench, not the forward sweep alone. (Warmup/thermal checked: ascending vs descending sweeps agree within ±8%; curve is trustworthy.)

## 2. Refactor (Phase 0 — behavior-preserving)

`ModelAgent` (in `self-play`) was overloaded — perspective state, obs encoding, forward, decode, diagnostics — mixing model interiors and game mechanics into a package meant for generic orchestration, and blocking the batched runner. Split it:

- **`packages/game-types`** (numpy-only): `PlayerView` / `ObsBundle` contracts that cross the game↔model boundary.
- **`bc.inference`** (sim-free): `BCModelHandle` (shared model + `forward_batch`) + `BCPerspective` (per-slot `encode`/`decode`/diagnostics). Consumes `PlayerView`, never `sim_core`.
- **`game_runner.state_to_view`**: the sole `sim_core.State` reader (`State → PlayerView`).
- **`self_play.NNAgent`**: ~50-line generic brain→Policy adapter, zero model/game knowledge.

Key property: **`training` stays free of `sim_core`** — `bc.inference` consumes `PlayerView`, not `State`, so it imports with zero `sim_core` in its graph and Modal training images stay lean. Validated by a frozen **parity oracle** (`packages/eval-tools/tests/test_parity.py`): the `NNAgent` path reproduces the old `ModelAgent` game byte-for-byte. Metrics/`policy_diagnostics` schema unchanged.

## 3. Batched runner sketch (Phase A — next)

The refactor put the seam in place: `NNAgent.build_obs(view) → ObsBundle` and `select_action(out_slice) → move` are split around `BCModelHandle.forward_batch` (batch=1 today). A vectorized runner (e.g. `game_runner/batched.py`) drives B games in lockstep:

- **Gather**: each tick, collect the `(game, slot)` cells that are `alive && NN`, build each one's obs (CPU, per-perspective), stack.
- **Forward**: group by `handle.model_key`, one `forward_batch` per distinct model (so head-to-head A-vs-B = 2 forwards/tick; self-play/NN-vs-evalbot = 1). The model is GroupNorm, so rows are provably independent — mixing games in one batch is identical to running them alone.
- **Scatter**: hand each row's output to its `select_action`; assemble per-game move lists (NN rows + evalbot CPU rows), `step_tick`, run metrics, check termination.
- **Refill** finished games into freed slots to keep the batch near-full through the ragged tail.

**Gotcha that's load-bearing:** the per-tick diagnostic `.item()` syncs must be deferred/vectorized, else B×~9 syncs/tick cancel the batch win. With that handled, Phase A lands around ~3–4x end-to-end — the serial CPU obs-build then becomes the next floor (→ Phase B).

## 4. Follow-up — Phase B (obs-build overlap, optional)

Once the forward is batched down to ~2.2ms/sample, building B observations *serially* on the CPU each tick (~1.25ms/agent, ~5% today) dominates again — Amdahl caps Phase A around ~3–4x despite the ~5x forward win. Phase B closes the gap toward the ~6–10x the forward ceiling allows:

- **Pipeline / double-buffer:** build wave *t+1*'s observations on the CPU while the GPU runs wave *t*'s forward, so the two overlap instead of serializing.
- **Or fan obs-build across cores:** the M1 has 8 P-cores and the per-perspective obs pipeline is numpy-heavy (releases the GIL in places), so threads/processes can parallelize it.
- **Measure first:** instrument Phase A to confirm obs-build is actually the binding constraint before adding concurrency — the Phase-A diagnostics-sync fix may already shift the balance.
- **Cloud makes it mandatory:** on a fast GPU the forward is nearly free, so host-side obs-build *is* the bottleneck — Phase B (plus enough vCPUs) is what makes cloud eval fast, not a bigger batch.

## 5. Notes for next session

- **Retire `run_game` after Phase A.** It's kept now as the frozen parity oracle and the single-game path. Once the batched runner is trusted, collapse the duplicate loop: make `run_game` a thin convenience wrapper around the batched runner at B=1, rather than maintaining two game loops. (This was the deferred "fold into one path" from the module-layout call — keep them separate only until parity is proven.)
- **RNG reproducibility is a real subtlety.** Sampling (`torch.multinomial`/`bernoulli`) draws from *global* torch RNG, so in a batched/refilled runner the draw *order* depends on how games are packed into the batch → sampled eval stats wouldn't reproduce across different `B` or refill timing. Give each game (or perspective) its own seeded `torch.Generator`. Argmax / `force_move` runs are already deterministic — that's what the parity oracle relies on.
- **Two cheap test oracles for Phase A:** (a) the batched runner at B=1 must reproduce `run_game` byte-for-byte (extend `test_parity`); (b) row-independence — `forward_batch(stack)[i]` must equal the single-perspective forward (GroupNorm guarantees it; pin it with a unit test).
- **`run_adhoc` rewiring.** The batched runner replaces the per-game sequential loop in `_play_and_record_game`, but must still emit per-game `npz` / `meta` / `metrics` + `results.jsonl`. With refill, games finish out of order — decide whether `results.jsonl` preserves `game_index` or completion order, and capture each perspective's `get_diagnostics()` before its slot is reused.
- **Minor latent:** `policy_spec._handle_cache` keys on `(path, str(device))` — *not* the value-head variant — while `BCModelHandle.model_key` includes the variant. Reconcile when grouping batches by `model_key`, so two same-checkpoint perspectives truly share one handle.
