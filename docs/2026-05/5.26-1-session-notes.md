## Architectural decisions and what prompted them

Several user questions during discussion drove the architecture beyond the initial plan. Documenting these because the pattern of questioning was productive and the resulting decisions should inform future work.

### WorldModel + PlayerView separation

**"Where is the world model update occurring? If it's in `act` I think we might want to move it out."** Led to extracting WorldModel as a class that owns raw sim state and the per-tick update pipeline. `act()` became pure decision logic.

**"Let's think about two views of game state: total world model vs. bot's perspective of the game."** Created the PlayerView concept — a frozen dataclass with everything the bot can legally see. Established the fog boundary as an architectural constraint, not just a calling convention.

**"Let's try out creating fog-filtered copies. It might be less code overall actually."** The alternative was passing vis + god-state arrays and letting each caller fog-filter explicitly. PlayerView carries `np.where(vis, god_state, sentinel)` arrays. This simplified all downstream code — ThreatWindow's `own == p` finds only visible enemy tiles without explicit vis intersection. The safety argument hinged on reading `training/bc/visibility.py` in full: Moore dilation means all cardinal neighbors of owned tiles are visible, so all M1 decision paths access tiles within visibility range. Fog-filtered and god-state arrays produce identical results for the current code.

**"`act` doesn't do any updates. It just receives the updated world state. Where does this get orchestrated?"** Moved orchestration to the driver: `view = bot.world.update(state, static)` then `bot.act(view)`. Raw sim state flows into WorldModel; only PlayerView reaches decision logic.

### Plan lifecycle

**"We could have a dataclass union that is returned from `_pick_new_plan`."** Created `GateResult = Plan | SingleMove | None`. Expand returns SingleMove (fire-and-forget), multi-tick gates return Plan variants. Clean type-based dispatch.

**"Should we put that defend-specific data on a 'DefendPlan' variant?"** Led to Plan variant hierarchy via inheritance (DefendPlan, ExplorePlan, with gate-specific metadata). Type IS the gate identity — isinstance dispatch, no string matching.

**Key lifecycle insight:** `_tick_active_plan` only clears or emits — never creates new plans. Re-evaluation that needs a replacement (defend target changed, attack target switched) just clears the plan; `_pick_new_plan` runs immediately after and recreates via the decision ladder. No plan creation in two places.

### gather_path design

**"`_estimate_arriving_army` could be more generic / re-usable if it's mobile army for tiles right?"** Reshaped the army estimate helper from gather_path-specific to a generic `mobile_army(tiles, ...)`. General's split contribution handled by the caller. Reusable for kill-shot margins and attack commit estimates.

**"It should return a warning if any of the tiles are not owned by us."** Added an invariant warning that caught a real bug during explore testing — non-owned path tiles (neutral territory between source and target) were being passed to the army estimate. The warning pattern proved its value and should be applied to more helpers: gather_path source validation, plan move validity checks, BFS connectivity assumptions.

### Build order

**"I would move 2 and 3 to the end."** (gather_path and spent detection, originally early in the build order.) These are standalone primitives that other items depend on. Building them last meant their implementation was grounded by all callers already existing. The stub pattern (define signature, return None, fill in later) kept everything compiling and testable throughout.

## External code dependencies

Code outside `packages/eval-bot/` that was read in detail during implementation:

- **`training/bc/obs.py`** — MemoryState dataclass (all fields, shapes, dtypes), `init_memory` and `step_memory` signatures. WorldModel wraps these; PlayerView exposes MemoryState (with a TODO to cherry-pick fields instead of passing the full object).
- **`training/bc/visibility.py`** — read in full (62 lines). `compute_visibility` does Moore dilation via 8 numpy shifts on owned tiles. Critical for proving the fog-filtering-in-PlayerView decision was zero-behavior-change.
- **`self_play/agent.py`** — `pad_initial_generals` signature (pads initial_generals to 8 slots). Imported by WorldModel.
- **`self_play/sim_adapter.py`** — `_capture_events_to_array` signature (packs capture events to numpy). Imported by WorldModel.

The eval-bot has cross-package deps on `training.bc` (fog tracking, visibility) and `self_play` (general padding, capture events). These are called as-is — the pragmatic posture is to reuse existing functionality with minimal modification rather than refactoring across packages.

## Testing gaps

The smoke test (`test_smoke.py`) runs two EvalBots for 500 ticks on a real map and checks that both expand. This verifies the bot doesn't crash and makes moves, but doesn't cover:

- gather_path edge cases (source == target, unreachable target, empty side-gathers, split moves)
- Spent detection conditions (army == 1, blocked by garrison, source captured)
- ThreatWindow identity breaks (position jumps, window clearing)
- IncursionThreat trigger/clear conditions
- Defend severity routing (rally vs intercept), time budget edge cases
- Plan lifecycle (preemption, re-evaluation, plan completion)
- Reserve mechanics (split threshold, general unavailability)

The warning-as-invariant-check pattern (`mobile_army` warning on non-owned tiles) partially compensates — it surfaces bugs at runtime without requiring targeted tests. More helpers should adopt this pattern. But dedicated tests for the above scenarios are needed before tuning.
