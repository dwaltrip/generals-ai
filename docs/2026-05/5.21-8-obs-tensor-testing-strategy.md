# Obs tensor testing strategy

**Date:** 2026-05-21
**Status:** Design — drives a follow-up session focused on obs-tensor test hardening
**Audience:** anyone picking up the obs-tensor test work
**Related:** [`5.21-7-obs-tensor-testing-gaps.md`](./5.21-7-obs-tensor-testing-gaps.md) (punch list this strategy addresses)

## 1. Why obs-tensor testing has its own shape

Four things make the obs tensor unusual to test:

- **High stakes.** It's the model's input. A subtle bug here teaches the model wrong dynamics for the entire training run. Cost of a missed bug is much higher than for most code.
- **Domain-specific logic at high volume.** ~96 channels, each with precise generals.io-specific derivation rules — Moore-nbhd vision, capture-event timing, production-subtraction math, slot canonicalization, fog/persistence semantics. The rules don't match generic patterns LLMs have strong priors on, and the per-channel logic is subtle enough that "looks right" routinely isn't. LLM-authored channel code AND LLM-authored tests against that code share the same blind spots. Hand-verified fixtures are the antidote — a human deriving expected values from the spec is the only loop that breaks correlated LLM bugs.
- **Heterogeneous channel sources.** Cats are derived from raw sim, from MemoryState, from precomputed scoreboard, from BFS — each has its own correctness story. No single oracle works for all of them.
- **High invariant leverage.** Despite the heterogeneity, three sweeping properties cover most failure modes. One well-designed invariant test catches the entire class. This is unusual — most code wants targeted tests because invariants are hard to formulate.

The two fog leaks fixed recently (5-21) are evidence: both would have been caught by one fog-respect invariant test, but neither was caught by any of the targeted tests we had.

## 2. The three load-bearing properties

### 2.1 Fog-respect

**Property.** `build_obs` output depends only on what the perspective could legitimately observe — i.e., the sim filtered through the perspective's vision, plus a specifically enumerated set of *legitimate globals* (scoreboard totals, capture events, mountain positions, `cities_present_at`).

**Test shape.** Generate two variants of the same sim where every cell outside the perspective's cumulative vision is replaced with different arbitrary values (randomized differently in each variant). Call `build_obs` on both. Assert byte-identical outputs. One test, catches the entire class.

**What it catches.** All fog leaks, current and future. Including: any new cat someone adds that reads `sim["ownership"][t]` raw without masking; any future change to `MemoryState` that accidentally caches hidden info; the dense-history leak we just fixed.

**Subtlety.** "Legitimate globals" needs a precise definition. Otherwise the test either misses real leaks (too lenient) or fails on correct behavior (too strict). Probably worth defining as a single helper `fog_filter_sim(sim, perspective, vis_history)` that strips hidden state but preserves the enumerated globals.

### 2.2 Slot canonicalization

**Property.** Same game viewed from K different perspectives produces K obs tensors that are related by the canonical slot permutation. Specifically:

- Perspective-invariant channels (mountains, structures_in_fog, BFS topology *modulo source*) — identical across perspectives.
- Self/opp-relative channels — `opp_i_owned` for perspective A equals `self_owned` for the perspective at canonical slot i.
- Scoreboard broadcasts — permute according to `canonical_slot_order(p)`.

**Test shape.** Build all K obs tensors for one game. Assert the symmetries cat-by-cat.

**What it catches.** Off-by-one in `opp_slots` indexing; the dead "captor not in opp_slots" fallback at obs.py:639-644; any new per-opp channel that doesn't follow the contract; channel-ordering drift between `CHANNEL_ORDER` and the assembly code.

### 2.3 Temporal consistency

**Property.** Three sub-claims:

- *Monotonicity.* `historically_seen`, `known_mountain`, `known_city`, `known_general`, `opp_contacted`, `opp_has_seen[p]` only grow tick-to-tick.
- *Sentinel stability.* Never-seen cells keep their sentinels (`last_seen_owner=-2`, `last_seen_armies=-1`, `turns_since_seen=-1`); `general_locations[p]` only transitions `-1 → cell`, never back; `opp_captured_by[p]` only transitions `-1 → slot`, never back.
- *Capture timing.* Capture events at action-t take effect during `step_memory(t)`; ownership transitions show in `snapshot[t+1]`.

**Test shape.** Walk one game; per-tick, diff state against the previous tick; assert the constraint set holds.

**What it catches.** Any regression that resets a monotonic field; any future change that accidentally clears sentinels; any drift in the capture-timing convention.

## 3. Fixture strategy

Two fixtures, deliberately complementary:

### 3.1 Hand-built fixture

**Purpose.** Precise correctness oracle. Author hand-derives expected MemoryState + channel values; tests assert against those.

**Requirements.**

- At least 3 players, so canonicalization is non-trivial.
- Visible→fogged AND fogged→visible transitions (currently missing in `test_fog_parity`).
- At least one capture-with-vision AND one capture-without-vision.
- At least one initial city captured by an opp (currently missing).
- All structure types represented (mountain, initial city, general, fog-structure).
- Documented derivation in the fixture docstring: trajectory, expected vision-at-each-tick, expected channel values at sampled checkpoints.

**Process.** Build the fixture in a separate sub-session, with a careful manual derivation pass — ideally with a human in the loop on the expected-value derivation, since this is the one piece of the test loop that can't safely be LLM-generated without re-introducing the correlated-bug problem from §1. Fixture errors are silent and devastating — the cost of getting it wrong is "all tests built on it lie."

### 3.2 Real-replay fixture

**Purpose.** Catches parser↔obs interface drift that synthetic fixtures can't see.

**Source.** A small `.gior` replay (preferably 1v1 or small FFA) run through the real parser. The parser output dict becomes the fixture sim.

**Tests against it.** Limited to property-style assertions — value ranges, fog-respect invariant, cross-perspective parity. We don't hand-derive expected channel values from a real replay; that's too brittle.

### Why no Python reference implementation

A second implementation costs maintenance and tends to share the same bugs as the production code (correlated failures) — doubly so when both are LLM-authored. Fixtures + invariants give us what a reference would give us at lower long-term cost.

## 4. Test taxonomy

### Phase 1 — invariant tests (the spine)

Three tests, one per property. High leverage; expected to surface real bugs on first run.

- `test_obs_fog_respect.py::test_build_obs_ignores_hidden_state` — fog-respect invariant.
- `test_obs_canonicalization.py::test_cross_perspective_parity` — slot canonicalization invariant.
- `test_obs_temporal.py::test_memory_state_invariants_over_walk` — temporal consistency walk.

These use the hand-built fixture. Some can be repeated against the real fixture in Phase 3.

### Phase 2 — targeted gap-fills (the 5.21-7 punch list)

For things invariants can't catch by construction:

- Specific encoding values (`_encode_*` lookup tables) — `test_obs.py` already covers some.
- Channel-ordering pins (`CHANNEL_ORDER` matches assembly order).
- `_cat_dense_history` orchestration (buffer indexing, fog masking).
- `compute_known_passable` policy categories (`test_bfs_policy.py` already covers most).
- Capture-without-vision branch (subsumed into the hand fixture above).
- Multi-event captures at same tick.

### Phase 3 — real-corpus integration

Extend `test_dataloader_smoke.py` from shape/NaN to:

- Per-channel value-range checks (binary in {0,1}, log channels ≥ -1, etc.).
- Per-tile partition invariants (e.g., `self_owned + Σ opp_N_owned + neutral_visible ≤ 1` per visible cell).
- Cross-perspective parity run on the real fixture.

## 5. Deliberately out of scope

- **Python reference implementation.** Costs more than it gives; bugs correlate (especially LLM↔LLM).
- **Golden-tensor snapshots.** Too noisy during active obs design (Phase 1d, Phase 2 work). Revisit once design is stable.
- **Adversarial / fuzz fixtures beyond fog-randomization.** Hypothesis-style property tests sound appealing but the obs-tensor shape doesn't fit well — most channels aren't pure functions of small inputs. Skip unless a specific case justifies it.
- **Performance regression.** Separate concern; lives in dataloader benchmarks, not correctness tests.

## 6. Open design questions

1. **Precise definition of "legitimate globals"** for the fog-respect test. Probably a single `fog_filter_sim(sim, perspective, vis_history)` helper. Worth nailing before writing the test.
2. **Real-replay fixture selection.** What replay? Smallest reasonable game; ideally one we've already used in dataloader smoke. Pin the bytes so it's stable.
3. **Cross-perspective parity granularity.** Cat-by-cat assertion is verbose; whole-tensor assertion with a permute helper is more compact. Decide early.
4. **Failure handling during the session.** Per discussion: failing tests at session-end are fine as long as the tests are correct. Capture failures as a follow-up punch list, don't block on fixing them.

## Appendix: Session starter

A 1-2 page note that boots the session, references this doc for depth.

**Decisions made (do not re-litigate).**

- Fixtures are the oracle. No Python reference implementation.
- One carefully verified hand-built fixture + one real-replay fixture.
- Skip golden tensors.
- Failing tests at session-end are OK — capture in a follow-up.

**Recommended order of attack.**

1. Build the hand-built fixture (`tests/fixtures/obs_hand.py` or similar). Allocate real time here — fixture errors poison everything downstream. Document derivation in the fixture docstring. Human-in-the-loop on the expected values.
2. Wire up the real-replay fixture: pick a replay, snapshot its parser output as test data.
3. Write the fog-respect invariant test. Single highest-leverage test; expect it to reveal something.
4. Write cross-perspective parity test.
5. Write temporal-invariants walk.
6. Cherry-pick from the 5.21-7 punch list as time permits.

**What "done" looks like.**

- Three invariant tests written and running.
- Hand-built and real-replay fixtures committed with documented derivations.
- Any tests that surface real bugs are left red, with a follow-up entry in the gaps doc or a new ledger item.
