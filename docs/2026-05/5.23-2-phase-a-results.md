|---|---|---|---|---|---|
| bs=256 FP16 | 314 | ~490 | 41% | 711 | Re-baseline on new slice |

| bs=1024 FP16 | — | — | — | — | OOM (T4=16 GB) |

Cross-check vs probe_500: prior bs=256 FP16 was 323 sps / 42% MFU. New 314 sps / 41% MFU on cloud_24k. Within noise — slice size doesn't materially affect throughput at this model size.

MFU 45% of FP32 peak = ~3.5% of T4's FP16 tensor-core peak. Same story as the prior tracker: GroupNorm/softmax fp32-overhead is the ceiling. Tensor-core headroom only opens with a substantially larger model. H100 not justified at current model size.

## The key finding: headline sps is a small-test artifact

The "headline" sps in the epoch summary is dragged down by a per-epoch startup cost. Per `batches.jsonl` analysis (per-batch wall-time deltas), per-batch durations are essentially flat:

| Run | Epoch | First 50 batches mean | Second 50 batches mean | Per-batch speedup |
|---|---|---|---|---|
| bs=256 | 1 | 519 ms (493 sps) | 518 ms (494 sps) | 1.00× |
| bs=256 | 2 | 536 ms (477 sps) | 521 ms (491 sps) | 1.03× |
| bs=512 | 1 | 1024 ms (500 sps) | 1027 ms (498 sps) | 1.00× |
| bs=512 | 2 | 1080 ms (474 sps) | 1053 ms (486 sps) | 1.03× |

What looked like a "warmup ramp" in the rolling-sps log lines (258 → 494 sps within epoch 1) is actually the **24-sec batch-0 spike being averaged into the first 50 batches**. Sources of the spike:
- Epoch 1: CUDA kernel init + first DataLoader worker spawn.
- Epoch 2: DataLoader worker re-spawn (workers torn down between epochs because `persistent_workers=False`, guarded by `assert_safe_loader`).

The second 50 batches don't include the spike, so "rolling sps" looks ~2× faster than "rolling sps at batch 50."

**Implications:**
- For our 100-batch tests, ~30 sec per-epoch startup is ~30% of train time → drags headline sps down significantly.
- For a real-run epoch with ~58k batches (50k games at bs=512), 30 sec is ~0.1% of train time → vanishes.
- **Real-run train sps will be ~490, not 346.** The headline is a small-test artifact.

## Decisions & gotchas captured

**Throughput / sizing:**
- bs=512 is the T4 FP16 sweet spot at the current 4.2M model. bs=1024 OOMs on T4 (16 GB). No reason to try bs=2048.
- Real-run throughput estimate is ~490 sps (per-batch steady-state), not the headline 346. Update mental model accordingly.
- Slice size doesn't materially affect throughput at this model size. probe_500 vs cloud_24k differ within noise.

**Operational gotchas (worth remembering):**
- **macOS APFS case-insensitivity is a cross-platform trap.** Slices built on macOS for Linux deployment have dir-name collisions. The `bc.splits.samples_for_split` patch is a runtime workaround — proper fix is building slices on a case-sensitive FS (sparse image, Docker, etc.) and is deferred.
- **Modal V1 volumes don't support recursive cp.** Renaming a multi-GB dir on a V1 volume requires re-upload. We have an `intermediate-cloud-20k/` ↔ `cloud_24k.json` cosmetic mismatch as a result (volume path is internal, harmless).
- **Per-file overhead dominates Modal uploads at our shape.** 1.1 GB / 38k files = 20 min wall (~31 ms/file). Raw bandwidth (140 Mbps measured) isn't the bottleneck.
- **`modal run --detach` is disconnect insurance, not "fire-and-forget."** Local CLI still streams logs; ctrl-c kills only the local process; remote continues. The `phase_a_sweep.sh` pattern (`nohup ... --detach &`) survives shell exit on both ends.
- **`| tail -N` on long-running pipes hides progress.** `tail` buffers until stdin closes. Use direct file output + a separate `tail -f` for live monitoring of long-running Modal commands.
