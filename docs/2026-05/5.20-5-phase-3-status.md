## Decisions log

Durable choices made during Phase 3. Rationale lives in the linked commits / code; this list is the index.

- **BFS-policy v1: enemy generals impassable + city army-ratio formula.**
  - City passability: `total_army > city_army * 4`. Own cities always passable. Uses `armies[t]` if visible, `last_seen_armies` if fogged.
  - Structures-in-fog stay impassable.
  - Per-frame BFS cache invalidation. Stayed on unweighted BFS; Dijkstra deferred.
  - *Where:* commit *"Phase 3 BFS-policy v1: enemy generals impassable, city army-ratio formula"* + `bc/bfs.py` knob header + `bc/obs.py::compute_known_passable`.
- **`obs.py` cat-helper extraction.**
  - `build_obs` is a thin orchestrator; each category is a private `_cat_*` helper returning a list of channels in `CHANNEL_ORDER` position.
  - Full module-folder split deferred — revisit when a future `obs.py` change provides a natural consumer.
  - *Where:* commit *"Refactor obs.py: extract per-category channel helpers"*.
- **Split manifest = the training-set contract.**
  - `bc/splits.py` builds `training/data/splits/<name>.json` from a seeded shuffle of eligible `(replay_id, perspective_k)` pairs, 95/5.
  - Per-perspective shape (not per-game) so future perspective-quality filters are a non-breaking extension.
  - Manifest provenance fields: `filter_version`, `git_sha`, `corpus_size`, `dropped_games`, `kept_pairs`, `built_at`, `intermediate_root`.
  - `IterableDataset(samples, seed)` consumes the resolved `(Path, k)` list. No defensive eligibility filter — the manifest is the contract.
  - Game-level + perspective-level filters live in `bc/filters.py`. `FILTER_VERSION` is a manually-bumped tag stamped into the manifest.
  - *Where:* `bc/{splits,filters}.py` + `bc.utils.sim_path_for`.
- **`training/shared/` subpackage for cross-package torch infrastructure.**
  - Sibling to `bc/` (and future `ppo/`) — houses code not specific to one training approach. `device.py` is the first file; subsequent generic torch-script helpers land here rather than inside `bc/`.
  - `pyproject.toml` declares `packages = ["bc", "shared"]`.
  - *Where:* `training/shared/{__init__,device}.py`, `training/pyproject.toml`.
- **Training loop scaffold + sample-weighted epoch metrics.**
  - `training/scripts/train_bc.py` is the BC training entry point. Reads a manifest, walks train via `IterableDataset`, AdamW + `bc_loss`. Console output only — JSONL → chunk 3, val → chunk 5, ckpt → chunk 4. `--max-batches` caps a run for smoke testing.
  - `LossAccumulator` (`bc/loss.py`) does sample-weighted epoch means: policy weights by `n_non_pass`, value/pass by batch_size, total derived from components so `total == policy + λ·value + μ·pass` reconciles at every aggregation level.
  - Config knobs are CLI args; revisit YAML/TOML when knob count grows past ~15 or sweeps land. `args.json` provenance dump deferred to chunk 3.
  - `bc.splits build --scan-limit N` builds cheap smoke manifests; stamped into manifest provenance.
  - *Where:* `training/scripts/train_bc.py`, `bc/loss.py`, `training/shared/device.py`, `bc/splits.py`.
- **Per-epoch checkpointing: state_dict only, keep-all, inside the run dir.**
  - End-of-epoch save to `<run-dir>/checkpoints/epoch_NNN.pt`. `epochs.jsonl` records the ckpt filename per row.
  - Payload is `model.state_dict()` only. Optim state, RNG, epoch-in-payload deferred — resume-from-checkpoint isn't on the spike's path.
  - Keep-all retention. ~16 MB per ckpt at current BCModel size; revisit if a real run actually fills disk.
  - "Best" checkpoint deferred to chunk 5 (needs a val metric).
  - *Where:* `training/scripts/train_bc.py` (`_save_checkpoint`).
- **Per-run logging: `<out-dir>/<YYYYMMDD-HHMMSS>/`.**
  - Each run gets its own directory under `--out-dir` (default `training/data/runs/`).
  - `args.json` captures the full CLI invocation for provenance.
  - Two JSONL streams: `batches.jsonl` (one record per batch) + `epochs.jsonl` (one record per epoch). Epoch logs get their own file for convenient headline number scanning. Val/ckpt log records will land later in phase 3.
  - *Where:* `training/scripts/train_bc.py`, `training/.gitignore`.

## Follow-ups discovered this phase

New items not in [`5.20-1`](./5.20-1-phase-2-status.md). Awareness-level unless flagged otherwise.

- **`step_memory.graph_grew` return is informational only.** The sole caller (`dataset.py::__iter__`) invalidates the BFS cache unconditionally per frame now, so the return value is no longer load-bearing. Cleanup candidate — drop the return + simplify the docstring.
- **Stale `known_general` flag is now slightly over-restrictive.** Pre-existing wart: a captured-general → city transition that the perspective doesn't have vision of leaves `known_general=True` for that cell. Old BFS treated both as passable; v1 BFS treats enemy generals as impassable + enemy cities as maybe-passable, so the stale flag now slightly over-restricts the graph until the perspective re-sights the cell. TODO already noted in `bc/obs.py::step_memory`; not fixed.

## Open questions

In-flight uncertainties. None block Phase 3 start; some calibrate choices that come up mid-phase.

- **Multi-worker dataset support.** Current `IterableDataset` is single-worker (docstring flags it). On M1 MPS, dataloader-CPU is often the bottleneck, not the GPU. May or may not surface as a problem before first run — decide on the basis of chunk 2's throughput numbers, not in advance.
- **Throughput calibration for subset-size pick.** Plan §3 Phase 3 step 2's "20–45 min/epoch raw, 2–5× dataloader overhead" is back-of-envelope. Chunk 2 will produce real samples/sec. Use that to pick between path (a) ~2–4k games (proof-of-concept) and path (b) ~10–20k (scale-up).
- **Phase 3 success bar (pre-load for Phase 4 planning).** What top-k accuracy / loss-curve shape counts as "Phase 3 succeeded"? Technically a Phase 4 eval question, but worth flagging now so the answer doesn't get rushed under post-training pressure.
