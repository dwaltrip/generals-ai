# Eval Bot Design

**Date:** 2026.05.24

**Purpose:** Detailed design doc that is nearly ready for implementation. The goal is to build a hand-coded greedy bot that serves as a fixed evaluation opponent for neural-net FFA bots. Successor doc to the older design sketch (`2026-05/5.24-2-greedy-bot-design-sketch.md`); incorporates all resolved design decisions.

**Companion docs:** `generals-io-game-mechanics.md` (rules), `2026-05/5.02-8-ffa-strategic-intuitions-interview.md` (strong-human strategic intuition — deliberately out of scope for this bot, see §1).

---

## 1. Purpose & scope

The eval bot is a **fixed, frozen opponent** for benchmarking NN training progress. It targets "competent beginner human" — good enough that beating it requires real economy and basic combat, weak enough that the NN can surpass it with moderate training.

Three properties, in priority order:

1. **Defends its general.** Without this, the NN learns one cheese rush, win rate pins at 100%, and the metric is worthless. The single biggest failure mode of a hand-coded eval opponent.
2. **Expands competently.** Can't be trivially out-economy'd.
3. **Makes occasional attacks.** Not purely passive.

**The exploitability test** (applied throughout): can the opponent trip the trigger cheaply and unilaterally, and does tripping it reward real skill or cheese? A weakness exploitable only through real strategy is a good weakness for a benchmark. A weakness that's a free, local, repeatable lever is a bad one.

**v1 scope exclusions:**
- No city capture (see §6.3 note)
- No multi-front modeling
- No alliance behavior or meta-reasoning about being seen
- No sophisticated FFA politics (relative-strength pivots, conflict exploitation)

These belong in the NN, not the benchmark.

**Frozen bot philosophy:** a shipped eval bot is never patched. Weaknesses are data, not bugs. To raise the bar, add a new bot to the eval ensemble with different Layer-2 config (see §9). Frozen bots give clean comparisons across model checkpoints.

## 2. Architecture

### 2.1 Core abstraction: target + route

All bot modes (defend / expand / explore / attack) are the same operation with a different target. The entire decision each tick collapses to:

- **`pick_target()`** — a fixed priority ladder that returns a target and a commit amount.
- **`route_to(target)`** — emit one move that advances army toward it.

There is no explicit state machine. The "mode" is whichever branch of `pick_target` fired. Re-running `pick_target` each tick *is* the transition logic.

### 2.2 One move per timestep

The bot emits exactly one move per timestep (500ms). This doc uses **"tick"** as shorthand for "timestep" — the atomic unit. See §8 for the full time-unit glossary. Every productive action (killing a general, winning a collision, pushing through fog) requires consolidating army across many timesteps before the payoff move lands. `gather_tree` (§7.2) is the shared primitive that resolves this.

### 2.3 Plans

A plan is the bot's current multi-tick intention:

```
Plan = (target, source, path, commit_amount, gate_origin)
```

- `target` — the destination tile.
- `source` — the tile army is gathering from.
- `path` — the route from source to target, computed by `gather_tree` or BFS (stored on the plan for execution; `gather_tree` computes it, the plan holds it).
- `commit_amount` — how much army the plan aims to deliver.
- `gate_origin` — which gate created the plan (Defend / Kill-shot / ExpandOrExplore / Attack), used for stickiness rules.

A thin expand move (frontier tile onto adjacent empty) doesn't need a plan — it's a single move with no consolidation.

## 3. Tick loop

Each tick, in order:

1. **Update world model** (Layer 0, §4). Recompute all derived state from current vision and scoreboard.
2. **Check plan status.** If no active plan, or active plan is spent (§7.4), go to step 3. Otherwise go to step 4.
3. **Run `pick_target`** (§5). Walk the decision ladder top-down. First gate to fire produces a new plan. If no gate fires above ExpandOrExplore, the bot does thin expand or fog-explore (§6.3).
4. **Check interrupts.** If an active plan exists and its `gate_origin` is *not* Defend or Kill-shot, check whether Defend or Kill-shot would fire. If so, preempt: discard the current plan, create a new plan from the interrupt gate.
5. **Emit one move** from the active plan (the next `gather_tree` step or single-step push).

### 3.1 Plan lifecycle

- **Creation:** `pick_target` fires a gate → new plan with target, source, path, commit_amount.
- **Execution:** each tick emits one move (gather step or path step).
- **Completion:** target reached and commit delivered. Plan cleared, next tick runs `pick_target` fresh.
- **Spent:** plan is no longer making progress (§7.4). Plan cleared, next tick re-plans.
- **Preempted:** a higher-priority interrupt fires. Current plan is discarded (not saved/resumed — replanning is cheap). Interrupt gate creates a new plan.

### 3.2 Stickiness rules

Re-running `pick_target` every tick risks thrashing between close-scoring alternatives. Stickiness rules prevent this:

- **Defend:** no stickiness. Exits as soon as `IncursionThreat` clears. Defense is reactive; lingering wastes economy.
- **Kill-shot:** sticky while in-flight. Highest-value target; abandoning mid-gather wastes the investment.
- **ExpandOrExplore:** no stickiness. Plans are cheap (short gathers or single moves). Easy to re-plan.
- **Attack:** sticky while in-flight. Mid-gather churn between close-scoring targets wastes the consolidation investment. Holds until complete, spent, or preempted by an interrupt.

### 3.3 Thrash prevention

If Defend or ExpandOrExplore shows threshold-flicker (repeatedly firing and releasing on consecutive ticks), apply hysteresis: the fire threshold is higher than the release threshold. **Not implemented by default** — add only if thrashing is observed in gameplay.

## 4. World model (Layer 0)

Recomputed each tick before any gate runs. This is the bot's perception of the game state.

### 4.1 `ThreatWindow` (per-player)

A per-player sliding buffer of the last `N` ticks, tracking that player's largest visible stack as `(pos, army, dist_to_general)`.

**Identity tracking:** each tick, find the player's largest visible stack and match it to the previous tick's tracked position by spatial proximity (same-color stack within BFS distance 1-2 of the previous position). Army amount is not used for matching — it changes every tick as the stack moves through tiles. If no match (stack entered fog, was destroyed, or split beyond recognition), start a fresh window for that player.

**Why per-player:** the Closing metric (§6.1) requires identity continuity to measure distance trends. A global-max window that jumps between players produces garbage distance signals. Per-player windows also detect incursions from any player, with the bot responding to the most severe (the decision ladder picks one target).

Only populated for players in `ContactSet`. Empty windows are inert.

### 4.2 `ContactSet`

Set of opponents the bot has ever had vision of (owned a tile adjacent to one of theirs). The on/off switch for threat/target machinery: empty early game (bot just expands), populated mid-game (threat and target scoring activate). **Eliminated players are removed** — their `ThreatWindow` is cleared and they no longer contribute to `ThreatScore`/`TargetScore`. Elimination is detected via the global chat announcement (§9 of game mechanics).

### 4.3 Scoreboard reads

Derived from the always-visible scoreboard. Computed over **all players** (the scoreboard is global — no vision or contact required):

- **`RelativeStrength(p)`** — player `p`'s army and land totals relative to the field.
- **`CityCountEst(p)`** — inferred from peacetime army growth rate: `growth_per_turn - 1 = city_count`.
- **`ConflictFlag(p)`** — land-delta correlation: is `p`'s land shrinking while another player's is growing at a similar rate? If so, `p` is likely fighting a third party.

These feed into `ThreatScore`/`TargetScore` (§4.4), which are themselves gated by `ContactSet` since they require proximity and positional data that only contact provides.

### 4.4 `PrimaryThreat` / `PrimaryTarget`

Two derived rankings over `ContactSet`, sharing the same inputs but treating relative strength with **opposite sign**:

- **`ThreatScore(p)`** — "who do I avoid opening a front against." High when: recently attacked me, close to my general, similar or greater strength. Reduced when busy fighting someone else (`ConflictFlag`).
- **`TargetScore(p)`** — "who can I profitably kill." High when: close, weak relative to me. Gated: stronger-than-me → score ≈ 0 (don't initiate). Stronger + busy elsewhere → suppressed further (don't provoke). Weak + growing → urgency bump (closing window).

**`PrimaryThreat`** = argmax `ThreatScore`. **`PrimaryTarget`** = argmax `TargetScore`.

### 4.5 Expansion metrics

- **`ExpandableTiles`** — count of owned frontier tiles with army ≥ 2 that are adjacent to at least one empty (neutral, 0-garrison) tile. Measures the supply of cheap expand moves available right now.
- **`UnoccupiedFrontier`** — count of owned frontier tiles adjacent to fog or unowned territory. Measures the surface area available for pushing outward.

These two values drive the expand-vs-explore mode switch in §6.3.

## 5. Decision ladder (`pick_target`)

Evaluated top-down each tick. The first gate to fire sets the target.

| Priority | Gate | Type | Fires when | Target |
|----------|------|------|------------|--------|
| 1 | **Defend** | interrupt | `IncursionThreat` (any player) | Intercept tile or general |
| 2 | **Kill-shot** | interrupt | `KillShotFeasible` | Revealed enemy general |
| 3 | **ExpandOrExplore** | default | always | Empty tile (expand) or fog tile (explore) |
| 4 | **Attack** | fallback | `PrimaryTarget` exists | `PrimaryTarget`'s frontier |

Defend and Kill-shot are **interrupts**: they preempt any in-progress plan from a lower gate. ExpandOrExplore and Attack are the default flow.

**Defend vs. Kill-shot interaction:** Defend always takes precedence over Kill-shot, with one exception: if the attacking player (the one triggering `IncursionThreat`) has a revealed general, `KillShotFeasible` passes, **and the bot wins the race**, Kill-shot preempts Defend. Killing the attacker resolves the threat via inheritance — the kill *is* the defense.

Race condition:

```
my_time_to_their_general < invader_time_to_my_general + margin
```

`my_time_to_their_general` = gather depth + path length from the `gather_tree` feasibility check. `invader_time_to_my_general` = the invader's `dist_to_general` from `ThreatWindow`. Both numbers are already computed. Without this check, the override is baitable: an opponent reveals their general, the bot commits army toward the kill, and the opponent rushes the now-undefended general. The race condition closes this — the bot only commits to the kill when it arrives first.

This override only applies when the kill target is the same player attacking you; a kill-shot against a different player does not preempt defense.

## 6. Per-gate detail

### 6.1 Defend (interrupt)

**Trigger: territory incursion, not "big army nearby."** The question is "is an opponent on a sustained attack path driving into the heart of my territory?"

```
IncursionThreat(player) = Closing(player) AND Eating(player)
```

Defend fires when `IncursionThreat` is true for **any** player in `ContactSet`. If multiple players trigger it, respond to the most severe: ranked by proximity to general (closest = most urgent, primary criterion), then by stack size (largest = tiebreaker).

**Closing** — distance to general is trending down over the `ThreatWindow`. Robust form: distance decreased in ≥ `M` of the last `N` steps. Distance is BFS graph distance over known-passable tiles, not Manhattan (Manhattan lies around mountain walls).

**Eating** — within radius `R` of the threat's current position, the count of tiles the bot owned at window-start that are now enemy-owned is ≥ `eat_min`. Anchored on past-ownership so the metric doesn't cannibalize itself as the attack advances.

**Response target — by severity:**

```
CanReachGeneral(stack) = stack_army > general_garrison + PathBleed
```

where `PathBleed` = sum of bot's army on the BFS shortest path from threat to general.

- **High severity** (`CanReachGeneral` true) → target = **general tile**. Passive rally, used only for genuine survival threats.
- **Otherwise** → target = **intercept tile**, the tile `lookahead` steps from the invader along the shortest known path from invader to general. Intercepting gives defender's advantage (ties go to defender).

**Commit amount:** gather until arriving army ≥ `ThreatWindow` stack army + `margin`.

**Source selection:** per the unified rule in §7.2. Defend may empty the general's reserve (survival case).

**Exit:** `pick_target` re-runs each tick; `IncursionThreat` goes false when the army turns, shrinks, or the collision resolves.

### 6.2 Kill-shot (interrupt)

A revealed enemy general is the highest-value, most time-sensitive target (capturing it is +N land via inheritance, and it's perishable — once anyone takes it, the prize is gone permanently).

```
KillShotFeasible(g) = revealed enemy general g exists
                      AND gatherable_army >= g.army + PathBleed + Margin(travel_time)
```

- **`Margin(travel_time)`** scales with gather-tree depth / path length. Longer travel → more time for the defender to reinforce → larger margin needed.
- **Discovered generals persist in memory.** A general seen once stays known (structures never move; a general only stops being a general when captured, which is globally announced). The implementation must not forget a general when it re-fogs.
- **Competence ceiling (by design):** the static estimate undershoots against an alert defender. The bot reliably finishes undefended or distracted generals and won't out-micro an active defense. Clean, legible ceiling.

**Source selection:** per the unified rule in §7.2. Same-player kill-shot (attacker = kill target) may breach the general's reserve floor.

**Sticky while in-flight** (see §3.2).

### 6.3 ExpandOrExplore (default)

A single gate with two modes, switched by the ratio of `ExpandableTiles` to `UnoccupiedFrontier`:

```
if UnoccupiedFrontier == 0:
    fall through to Attack (nothing to expand or explore into)
elif ExpandableTiles / UnoccupiedFrontier < expand_explore_threshold:
    explore mode
else:
    expand mode
```

**Expand mode** — thin BFS crawl. Pick any tile from the `ExpandableTiles` set (owned frontier tile with army ≥ 2 adjacent to an empty tile) and move it onto the adjacent empty tile. Single-step move, no `gather_tree` needed. Fills the local pocket densely with good land-per-move efficiency.

**Explore mode** — gather a modest stack and push a line into unexplored territory. Dual purpose: increases frontier surface area and reveals map (generals, cities, topology, enemy positions).

Explore target selection:

1. From the general, bucket all in-bounds tiles into sectors (4 quadrants or 8 octants).
2. Score each sector by count of **passable fog tiles** (non-structure tiles not currently visible). Structures are globally visible but mountain vs. city is indistinguishable behind fog — both are treated as impassable in v1 (neutral cities are technically capturable, but city capture is out of scope).
3. Winning sector = largest unexplored region.
4. Target = a specific passable fog tile at depth `D` (tunable, ~10-15 tiles) from the frontier edge in the winning sector. Pathfinding works through fog because the passable/impassable topology is globally known.
5. Uses `gather_tree` to consolidate a modest stack, then pushes toward the target. If the push encounters enemy tiles, contact reclassification applies (§6.4).

**v1: pure least-explored.** Explore always targets the sector with the most passable fog, with no directional bias. Future variants may bias toward `PrimaryTarget`'s frontier to prevent turtle-blob behavior (the passivity dial).

**Early game:** `ExpandableTiles` is naturally low (all tiles are thin 1-army) and `UnoccupiedFrontier` is high, so the bot leans explore — pushing outward from the general, revealing map, finding empty pockets to fill. This is correct early-game behavior.

> **Note — city gate (future):** city capture slots between ExpandOrExplore and Attack as an opportunistic gate: nearest known neutral city when a frontier stack ≥ garrison + 2 is already available, no active threat, early enough to pay back. Not in v1; the bot is deliberately out-scaled in long games.

### 6.4 Attack (fallback)

Target = `PrimaryTarget`'s nearest visible frontier tile (or its revealed general if known). Attacking the nearest frontier doubles as general-hunting — vision flows toward them.

**Source selection:** per the unified rule in §7.2. Attack respects the general's reserve floor.

**Contact reclassification:** a stack executing a fog-explore push that gains vision of enemy tiles checks `my_stack_army > visible_enemy_frontier_army`. If yes, keep pushing (the explore push becomes an attack; `pick_target` picks it up on the next tick as the Attack gate). If no, the push is spent — stop, re-evaluate.

**De-escalation is the weak form.** On contact with a non-`PrimaryTarget`, the spent → re-evaluate behavior is the de-escalation. The bot declines to open a new front but holds position. A holding bot can't be herded; only a fleeing one can.

**Sticky while in-flight** (see §3.2). Once the bot commits an attack gather, it holds until complete, spent, or preempted by Defend/Kill-shot.

## 7. Shared machinery (Layer 3)

Fixed scaffolding shared by all gates. Nothing in this layer changes between difficulty tiers.

### 7.1 `bfs_dist(a, b)` / `path(a, b)`

BFS graph distance and shortest path over known-passable tiles. **"Known-passable"** = any tile that is not a structure. Structure existence is globally visible (even behind fog), but mountain vs. city is indistinguishable behind fog — both are treated as impassable in v1. Non-structure tiles are known to be passable land (ownership and army counts are unknown behind fog, but traversability is certain). This means BFS works across the entire map including fogged regions.

One routine serves: Defend distance metric, `PathBleed`, intercept point, travel-time estimates, and fog-explore pathfinding.

### 7.2 `gather_tree(target, commit_amount)`

The single "assemble a stack at a point" primitive. Defend, Kill-shot, Attack, and Explore all call this identically.

**Source selection:** one source tile, chosen by:

```
source = argmax(tile.army - k * bfs_dist(tile, target))  over owned tiles
```

This balances army size against distance. The general usually wins (it accumulates the most army via the peacetime reserve), but a fat frontier stack closer to the target can beat it. `k` is a tuning coefficient.

**Reserve floor:** the general's army is only available down to a floor, which varies by gate:

- **Defend:** may empty the general entirely (survival trumps reserve).
- **Kill-shot (same-player as attacker):** may breach the floor (the kill resolves the threat).
- **Attack / Explore:** may only draw the general down to the floor. Army above the floor is spendable; army at or below is held back. The floor is the bot's risk posture in a single number.

For source selection, the general's `tile.army` in the argmax is clamped to `max(0, tile.army - reserve_floor)` for gates that respect the floor.

**Algorithm (v1):**

1. **Path:** BFS shortest path from `source` to `target` over known-passable tiles.
2. **Side-gather:** scan for owned tiles within BFS distance 1-2 of the path that have high army. Move these onto the nearest path tile first (one move each), fattening the path before the sweep.
3. **Sweep:** move army inward along the path toward the target, one step per tick. Army accumulates as the sweep passes through each tile.

**Army estimate:**

```
arriving_army = sum(tile.army for all tiles in gather set) - (num_tiles - 1)
```

Each non-target tile leaves 1 army behind when it moves. The target keeps its own army plus everything that flows in.

**Stop condition (per-gate):**

- **Defend / Kill-shot:** gather until `arriving_army_estimate >= commit_amount`. The plan specifies how much army is needed to meet the threat or take the general.
- **Attack / Explore:** budget-based. `commit_amount = risk_fraction * mobile_army`, where `mobile_army` = total army across all owned tiles minus the general's reserve floor. `risk_fraction` is a tuning lever controlling how much the bot commits to offensive actions.

**Returns:** `(next_move, arriving_army_estimate, depth)`. Used for both planning (feasibility checks in Kill-shot, Defend commit) and execution (next move to emit this tick).

**What v1 does not do:** path-weighting optimization (choosing a longer route that accumulates more army). Shortest path + side-gather is sufficient. Path selection is a tuning knob for stronger bot variants.

### 7.3 `route_to(target)`

Dispatches to:
- **Single-step push** for expand moves (frontier tile → adjacent empty tile, no consolidation needed).
- **`gather_tree` step** for everything else (the next move from the active gather).

### 7.4 `spent_push(plan)`

Detects a plan that is no longer making progress. The plan is cleared and the bot re-plans on the next tick.

**v1 conditions (checked each tick):**

1. **Can't advance (empty).** The army on the leading tile of the plan's path is 1 (can't move — moving requires army ≥ 2).
2. **Can't advance (blocked).** The leading tile faces an enemy tile whose garrison is ≥ the leading tile's army. The bot can't capture forward and would lose army trying. Covers explore pushes and attacks that run into unexpected resistance.
3. **Kill-shot infeasible.** For Kill-shot plans: the bot's attacking army is less than the army on the target general (last seen or currently visible). The attack can't succeed; stop and re-assess.

### 7.5 Utility functions

- **`LargestFrontierStack()`** — owned tile on the frontier with the highest army count.
- **`nearest_empty(from)`** — nearest neutral 0-garrison tile reachable from `from` via BFS.

## 8. Edge cases & bootstrapping

**Terminology note:** this doc uses "timestep" as the atomic unit (500ms, one move allowed), matching the game mechanics doc. "Turn" = 2 timesteps (generals/cities produce +1 army per turn). "Round" = 25 turns = 50 timesteps (land tick). The tick loop runs once per **timestep**.

**First timesteps.** The general starts at army 1 and gains +1 per turn (every 2 timesteps). The bot can't move until army ≥ 2, which happens at turn 1 (timestep 2). The tick loop handles this naturally — no `ExpandableTiles`, so ExpandOrExplore leans explore, but no tile has army ≥ 2 yet, so no move is emitted. The bot waits.

**Before contact.** `ContactSet` is empty, so `ThreatWindow`, `ThreatScore`, `TargetScore`, `PrimaryThreat`, and `PrimaryTarget` are all inert. Defend and Kill-shot can't fire (no players to track, no generals seen). Attack can't fire (no `PrimaryTarget`). The bot does ExpandOrExplore exclusively until first contact.

**Land tick timing.** The per-round army burst (every owned tile gets +1, every 25 turns) is not explicitly modeled in v1. The bot doesn't time gathers around land ticks. Acceptable — the burst benefits both sides equally, and timing it is an optimization for stronger variants.

**General placement guarantee.** Generals are always ≥ 10 Manhattan distance apart. The bot doesn't need to model this explicitly, but it means early-game fog-explore won't stumble into an enemy general in the first few moves.

## 9. Tuning levers

Ordered most → least consequential. Difficulty tiers (Easy / Medium / Hard) are all threshold changes across these levers — no routing or machinery changes.

1. **Defend sensitivity: `N` (window length), `M` (closing-steps required), `eat_min`.** Jointly set twitchy-vs-lax. This decides whether the bot is a valid benchmark at all.
2. **Kill-shot margin + travel-time coefficient.** The bot's main teeth. Too eager → throws stacks at defended generals; too timid → never commits.
3. **`reserve_floor` (general's held-back army).** The bot's entire risk posture. Too high → turtles with idle army; too low → dies to counter-rushes after committing forward.
4. **`k` (source selection distance weight).** Balances "use the fat general" vs. "use the closer stack." Higher k → prefers closer sources.
5. **`expand_explore_threshold` (ExpandOrExplore ratio).** The passivity dial. Too high → never explores, turtles; too low → abandons free economy to push fog early.
6. **`risk_fraction` (Attack/Explore commit budget).** How much mobile army the bot spends on offensive actions. Too high → strips frontier; too low → never threatens.
7. **Fog-push depth `D`.** How far into fog each explore push reaches. Shorter = safer, more frequent re-evaluation; longer = more map revealed per push.
8. **Defend severity margin in `CanReachGeneral`.** How often the bot drops into passive rally-to-general vs. intercept.
9. **Commit margins (Defend collision).** Over-commit strips the frontier; under-commit loses the collision.
10. **`lookahead` (intercept projection).** Too short → collide too late; too long → gather to empty space.
11. **Sector granularity (4 quadrants vs. 8 octants).** Affects explore direction precision.
12. **Hysteresis thresholds.** Zero by default; introduce per-gate only if thrash is observed.

## 10. Known limitations

- **Single-threat response.** Per-player `ThreatWindow` detects multiple incursions, but the bot responds to only one (the most severe). Acceptable, legible limitation.
- **No city economy.** The bot is out-scaled in long games by anything that captures cities. Games are decided in the opening and early-mid. Acceptable and deliberate (§6.3 note).
- **Static kill-shot estimate.** Undershoots against alert defenders. The bot finishes distracted generals, not defended ones.
- **No multi-front modeling, no alliance behavior, no meta-reasoning.** These belong in the NN.
- **Gather-tree uses shortest path only.** No path-weighting optimization. Side-gather within 1-2 tiles compensates.

## 11. Eval harness considerations

The bot is the easy part; these determine whether the eval number is signal or noise.

- **Denser metrics than win rate.** Binary win/loss in 8-player FFA is sparse and noisy. Track average final placement (1–8), survival time, and peak land/army share for a smooth improvement curve.
- **Hold the eval bot out of training.** If it's also a curriculum opponent, win-rate-vs-it stops being unbiased. Keep at least one frozen, eval-only version.
- **Reduce variance with fixed seeds.** Map gen, spawns, and tie-breaks seeded so checkpoints face identical scenarios. Run hundreds of games per checkpoint; report confidence intervals.
- **`1 NN vs 7 bots` layout.** Give each bot its own seed to avoid degenerate symmetric dynamics.
- **A difficulty ladder beats a single opponent.** Watch the NN climb Easy → Medium → Hard. Each rung is a Layer-2 config, trivial to define.
- **Keep it cheap.** Pure heuristics + BFS on a small grid. No beam-search or heavy solvers.

## 13. Pseudo-code grounding: concerns and open questions

Notes from the pseudo-code pass that traced each heuristic, metric, and gate back to concrete game-state fields. The machinery is sound — these are tuning questions and stress-test priorities, not design problems.

### 13.1 ThreatScore / TargetScore weight arbitrariness

Both scoring functions are weighted sums of heterogeneous signals (proximity, strength, recency, busyness) with unspecified weights. The inputs are well-grounded but the combination function is design-by-feel. Low-leverage for v1 — ContactSet will usually have 1-2 players, so rankings are trivial. Becomes important when tuning difficulty tiers across the lever set (§9).

### 13.2 Pre-gathered attack and the IncursionThreat detection delay

The AND of Closing + Eating means an opponent who gathers a large stack just outside the bot's border doesn't trigger defense until the actual invasion starts. The bot reacts from behind against pre-gathered rushes.

Two reasons this is acceptable:

1. `reserve_floor` is the real first line of defense. The general always holds back army, and in the high-severity case the bot rallies everything (including the reserve) locally — no gather delay.
2. The AND filter prevents false positives. Without Eating, every border contact triggers defense and the bot wastes half the game gathering toward its general. The cost is slightly delayed detection; the benefit is not being exploitable by "park a stack nearby and watch the bot panic."

Stress-test priority: does the reserve floor provide enough local defense to survive the detection delay against a real rush?

### 13.3 Eating baseline management

The Eating metric needs to know what the bot owned at window-start (design doc says "anchored on past-ownership so the metric doesn't cannibalize itself"). This requires a per-player ownership snapshot stored when the ThreatWindow opens — new state not mentioned elsewhere in the design. Small cost (one bool [H,W] per active window), but it's load-bearing and implicit. The snapshot is held for the window's lifetime and discarded on identity break.

The eating radius `R` is also a fiddly parameter: too small and the metric flickers on and off; too large and distant border skirmishes trigger defense.

### 13.4 Stress-test priorities for early gameplay

These are the first things to watch when the bot plays real games:

- **Does the Closing M-of-N window fire in time against a real rush?** If M is too high or N too long, detection lags behind fast attacks.
- **Does the reserve floor survive the IncursionThreat detection delay?** The gap between "opponent starts eating" and "defense gather arrives" is bridged entirely by local army.
- **Does explore-mode push in useful directions?** Sector scoring by passable-fog count could send the bot into dead-end mountain pockets. The BFS target selection mitigates this (unreachable tiles don't get selected), but narrow corridors could waste pushes.
