# cloud-poc landed; path to a real training Modal entrypoint

**Date:** 2026-05-21
**Branch:** `cloud-train-poc`
**Status:** POC validated end-to-end on CPU + T4 GPU. Real training entrypoint is the next deliverable.

## What we proved

A tiny throwaway package (`cloud-poc/cloud_train_poc`) was wired up as a Modal function that:

- Builds an image on `debian_slim(python_version="3.14")` with the full CUDA-bundled torch stack
- Installs from a fully-pinned `modal_requirements.txt` generated from the workspace `uv.lock`
- Has its own source installed as a separate cached image layer
- Returns `tensor_sum=45.0`, `cuda_available=True` when run with `gpu="T4"`

The full chain works: Modal-blessed install path, Python 3.14 in the image, reproducible deps, fast layer cache, real GPU access. See [`working-with-modal-cloud-gpu.md`](../working-with-modal-cloud-gpu.md) for the patterns and gotchas this exploration produced.

## What's on the branch

Working tree at the close of this session:

- `cloud-poc/` — throwaway workspace member with one Python file (`work.py`) that returns a torch-computed value, plus `modal_entry.py` (the reference Modal entrypoint) and `modal_requirements.txt` (generated pinned deps).
- `tools/regen_modal_reqs.sh` — regenerates `modal_requirements.txt` from `uv.lock`; stubbed to add `training` later.
- Workspace `pyproject.toml` + `uv.lock` updated to include `cloud-poc` as a member.

The branch is not yet merged. Easy to keep or discard depending on whether `cloud-poc` is worth keeping as a long-lived Modal smoke-test.

## Going from POC to real training entrypoint

### Direct extensions of the POC pattern

| Item | Detail |
|---|---|
| Training entrypoint file | `training/scripts/train_modal.py` (mirrors `cloud-poc/modal_entry.py` shape) |
| Regen script | Uncomment the `regen training training/modal_requirements.txt` line already stubbed in `tools/regen_modal_reqs.sh` |
| Install both `training` and `utils` | `training` imports from `utils`; both are workspace members. Likely needs two separate `uv_pip_install` calls (utils first, training second). Need to verify `uv_pip_install("/path/to/local")` handles workspace cross-deps cleanly |
| GPU | `gpu="H100"` for real runs; consider parameterizing per-call (`--gpu` flag) for flexibility |
| Function signature | Native call via `from training.scripts.train_bc import _build_arg_parser, run; run(parser.parse_args(cli_args))` |
| Timeout | Default 5 min is way too short; needs `timeout=24*3600` for overnight runs |
| Detached invocation | `modal run --detach training/scripts/train_modal.py ...` for real runs |

### New machinery the POC didn't need

| Item | Detail |
|---|---|
| Volume for corpus | One-time upload of ~10 GB parsed corpus via `modal volume put`. Mount RO at e.g. `/data/corpus/` |
| Volume for outputs | Either same volume RW or separate. Training writes to `/data/runs/<timestamp>/` inside container; pull back via `modal volume get` |
| Path translation | `train_bc.py` writes to `training/data/runs/<ts>/` locally vs `/data/runs/<ts>/` in cloud. Cleanest fix: make `train_bc.py` take both input and output paths via CLI args (the Modal wrapper passes cloud paths; local invocation passes local paths) |
| Run naming convention | Suggest `cloud-<timestamp>` prefix for cloud-origin runs so they're distinguishable from local runs in the same `runs/` directory |
| Image source exclusions | `training/` has `data/` (176 MB), `tests/`, `scripts/`, `investigations/`, `tmp/`. Need either targeted `add_local_dir` calls or `ignore=` patterns to keep these out of the image |

### Decisions to make explicitly

1. **Output flow.** Auto-pull artifacts when the function returns? Or leave on Volume, pull on demand? Recommend leaving on Volume and pulling on demand — keeps the Modal function simple, Volume storage is essentially free at our scale, and the `runs/` directory becomes a shared archive.
2. **GPU type — hardcoded or parameterized?** `gpu="H100"` baked in vs. `--gpu H100` flag. Lean parameterized for sweep flexibility (and to enable T4 smoke runs of the same entrypoint).
3. **What goes on the corpus Volume.** Parsed `.npz` + manifests for sure. Split files (`poc_2kish_perspecs.json` etc.) probably too. Anything else?
4. **Should `cloud-poc` survive?** It's useful as a "does Modal still work for our setup" smoke test, but it's also dead weight if the training entrypoint becomes the canonical reference. Either keep as a reduced-scope smoke or delete after the training entrypoint lands.

### Things to validate (smoke run sequence)

Before the first real H100 run, work up gradually:

1. **CPU smoke.** Image builds with `training` + `utils` installed. Function can `import training.scripts.train_bc`. No GPU, no Volume, no actual training step.
2. **CPU smoke with Volume.** Upload a tiny test slice to a Volume; mount; function reads a sample to confirm path translation works.
3. **T4 smoke.** Same as above but with `gpu="T4"` — verify torch sees the GPU and a single training step actually runs.
4. **H100 trial.** Single epoch on a small corpus subset. Confirm cost/time matches expectations.
5. **First real run.** Cluster C from [`5.21-5`](./5.21-5-post-spike-knobs.md): 50k+ games × 10-20 epochs.

### Open questions

- **Tiny test slice availability.** Is there an existing slice small enough for smoke runs (a few hundred perspectives)? If not, generating one is pre-work for step 2 above.
- **Re-verify training's dep graph.** Earlier in this session we confirmed `training` imports only from `bc.*`, `utils.*`, and `torch.*` — but if obs/test work since then has added a cross-member import, the assumption would shift. Worth re-checking before writing the Modal entrypoint.
- **`train_bc.py` filesystem assumptions.** Some scripts compute defaults from `__file__` paths or expect a particular `cwd`. Need to verify those still resolve correctly inside the Modal image (cwd is wherever the container starts; `__file__` resolves to the in-image path).
- **Auto-regen check.** A pre-commit / CI step that fails if any `modal_requirements.txt` is stale vs `uv.lock`. Discussed in this session, not yet implemented. Probably worth a one-page bash script in `tools/`.

## Suggested sequence for next session(s)

Small and concrete; each step independently shippable.

1. Add `regen training training/modal_requirements.txt` to `tools/regen_modal_reqs.sh`; run it; commit `training/modal_requirements.txt`.
2. Write `training/scripts/train_modal.py` mirroring cloud-poc's shape. Native-call pattern (`from training.scripts.train_bc import _build_arg_parser, run`).
3. CPU smoke first — no GPU, no Volume, just import-and-call. Validates the image builds with the real training stack.
4. Wire up Volume for corpus; small slice; CPU read smoke.
5. Wire up Volume for outputs; verify write + pull-back.
6. Add `gpu="T4"`; verify CUDA flow + a single training step.
7. `gpu="H100"`, small slice, single epoch, real-money trial run.
8. First real Cluster C run.

If we're disciplined, steps 1-3 fit in one short session. Steps 4-7 are probably one session each (each one adds non-trivial machinery worth testing in isolation). Step 8 is its own evening.
