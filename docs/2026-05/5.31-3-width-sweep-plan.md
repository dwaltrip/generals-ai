# Width sweep — planning note

**Date:** 2026-05-31
**Branch:** `quick-model-arch-sweep`
**Status:** Forward-looking plan, intentionally thin. Blocked on the model-config refactor ([`5.31-2`](./5.31-2-model-config-refactor-design.md)) — the sweep needs self-describing checkpoints so multiple widths can coexist in one eval process. Recipe specifics are deferred until the config work lands; the open questions below are deliberately unresolved.

## What it is

Train the BC trunk at several widths (current is the half-width `128/128/160`), hold everything else fixed, and read **eval win-rate head-to-head** to decide how wide the big run should be — and therefore its GPU class. Runs fan out as parallel Modal jobs: cheap, off-laptop, and a forcing function for config discipline.

**Caveat that shapes how we read it.** The evidence so far points more at *data/epoch-limited* than *capacity-limited* (val_policy still descending in every run; nothing near saturation even at 10 epochs / 12h). A short sweep can't saturate the 1× model, so a flat result reads as "width didn't help *at this budget*," not "width never helps" — informative, not definitive.

## Settled

- **Parallel Modal runs**, one per width, identical except the `arch` block.
- **Eval protocol** = the [`5.28-1`](./5.28-1-pyramid-eval-sweep.md) codified minimum: head-to-head at temp=0.5, n≥80, with swap-slots + self-vs-self noise floor + per-tick diagnostics. The batched runner (5.30–5.31) makes this much cheaper than the old B=1 path.
- **Budget:** ≤1hr per run; deliberately not-fully-saturated / not-100%-scientific is accepted.

## Open questions

- **Width set + control point.** Lean is widths *above* the current half-width (multipliers relative to current: 1.5×, 2× = DeepNash-full `256/256/320`). Open: keep a sub-current point (0.5× = `64/64/80`) as a control? It's the only thing that diagnoses *which regime we're in* — if 0.5× ≈ 1×, we're not capacity-bound, and a flat high end is just under-budget rather than "width is useless."
- **Recipe under the ≤1hr budget.** Epochs / data-slice size / `max_batches` — what fixed recipe yields a usable signal in under an hour? (Explicitly deferred until config lands.)
- **GPU class per width + the bs=512 floor.** Wide cells (1.5× / 2×) at bs=512 may exceed T4/L4 VRAM. Bigger card, or gradient accumulation (preserves the value-head class-diversity property the bs=512 floor exists for)?
- **How to act on an unsaturated result.** What win-rate gap counts as "go wide for the big run" vs "noise — redirect the compute to data/epochs"?
