# Width sweep — planning note

**Date:** 2026-05-31
**Branch:** `quick-model-arch-sweep`
**Status:** Recipe settled; launch script written ([`training/scripts/width_sweep_2026-05-31.sh`](../../training/scripts/width_sweep_2026-05-31.sh)). The model-config refactor it depended on ([`5.31-2`](./5.31-2-model-config-refactor-design.md)) has landed, so widths now self-describe and coexist in one process. First pass reads loss curves across widths; head-to-head eval is the deferred follow-on (see Decisions).

## What it is

Train the BC trunk at several widths (current is the half-width `128/128/160`), hold everything else fixed, and read the result across widths — loss curves as the first screen, head-to-head eval as the follow-on — to decide how wide the big run should be (and therefore its GPU class). Runs fan out as parallel Modal jobs: cheap, off-laptop, and a forcing function for config discipline.

**Caveat that shapes how we read it.** The evidence so far points more at *data/epoch-limited* than *capacity-limited* (val_policy still descending in every run; nothing near saturation even at 10 epochs / 12h). A short sweep can't saturate the 1× model, so a flat result reads as "width didn't help *at this budget*," not "width never helps" — informative, not definitive.

## Settled

- **Parallel Modal runs**, one per width, identical except the `arch` block.
- **Eval protocol** = the [`5.28-1`](./5.28-1-pyramid-eval-sweep.md) codified minimum: head-to-head at temp=0.5, n≥80, with swap-slots + self-vs-self noise floor + per-tick diagnostics. The batched runner (5.30–5.31) makes this much cheaper than the old B=1 path.
- **Budget:** ≤1hr per run; deliberately not-fully-saturated / not-100%-scientific is accepted.

## Decisions

The launch script bakes these in; recipe knobs are flags (`--epochs`, `--max-batches`, …).

- **Width set + control.** `{0.5×, 1×, 1.5×, 2×}` = `64/64/80` · `128/128/160` (anchor) · `192/192/240` · `256/256/320`. 0.5× is kept as the **regime control**: if 0.5× ≈ 1× we're not capacity-bound, and a flat high end reads as under-budget rather than "width doesn't help."
- **Recipe (fixed across cells, only width varies).** bs=512, `epochs=2`, `max_batches=800` (~820k sample-draws), seed=0, on the `cloud_24k` slice already on the Volume. Deliberately short — re-run with more data if a result is unclear.
- **GPU.** Uniform **A100** for every cell — headroom for bs=512 at all widths, removes the card as a confound. Gradient accumulation isn't needed (the A100 fits 2×+pyramid+bs512 directly) and isn't implemented. T4/L4 are proven in the run record; A100 is exercised for the first time here — verify via `args_cloud.json`'s `cuda_device_name`.
- **Value head.** `pyramid`, fixed. We read **policy + pass quality**, not the value head — in 2-player eval the value head is OOD-uninterpretable (5.28-1), so short-run value-head overfitting is expected and ignored.
- **Reading the result.** Loss-curve screen first (final val_policy + pass_frac across widths). Because loss is a poor proxy for skill (5.28-1), a promising/ambiguous result **graduates to head-to-head eval** before any big-run width commitment; the rule there is "win iff the Wilson-CI lower bound over 1× clears the self-vs-self noise band," with 0.5× disambiguating the regime.
- **Resume-onto-wide footgun (fixed).** `run_bc_modal.py` now fails loud if a `--resume` overlay omits `gpu`, instead of silently provisioning T4 (which OOMs a wide run). Fresh sweep cells are unaffected — they read `config.gpu` directly.

## Deferred

- **Eval in the cloud.** Running the head-to-head eval on Modal (checkpoints already live on the training-runs Volume, so no local pull) needs the eval packages + a Linux `sim_core` build + the map SQLite DB on the container + an output redirect to the run dir. Deferred until the eval step is actually needed.
