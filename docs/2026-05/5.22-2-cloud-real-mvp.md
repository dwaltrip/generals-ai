## Where we are

- `training/scripts/run_bc_modal.py` — Modal cloud entrypoint. Step-1 shape only: builds the image, mounts source via `add_local_python_source`, runs a CPU `smoke()` function that imports `bc.train` + `bc.train_cli` and reports container info. Verified end-to-end: image builds, imports succeed, Python 3.14.2 + torch 2.12.0+cu130.
- `training/scripts/run_bc_local.py` — local CLI wrapper sibling. Same factoring; both call `bc.train.bc_run(config)`.
- `bc/train.py` — pure training runner (`TrainConfig` dataclass + `bc_run`). No CLI knowledge.
- `bc/train_cli.py` — CLI scaffolding (`build_arg_parser` + `config_from_args`). Shared between wrappers.
- `tools/regen_modal_reqs.sh` — `uv export` now passes `--no-emit-workspace`. Pre-commit hook re-stages the requirements files when `uv.lock` changes.

## Findings worth carrying forward

- **`add_local_python_source` beats `add_local_dir + uv_pip_install("/pkg")` for pure-Python packages.** Modal resolves the modules via the local-env import path and drops files at `/root/` (on PYTHONPATH). No synthetic install paths, no pyproject re-resolution, no hatchling build. Use the pip-install path only if a package needs entry points / console scripts / build hooks (none of ours do).
- **`uv export` needs `--no-emit-workspace`.** Without it, workspace cross-deps appear as `-e ./packages/<name>` in the requirements file. Modal's `uv_pip_install(requirements=...)` runs before any `add_local_*` layer, so the path doesn't exist in the container → image build fails. Documented in [`working-with-modal-cloud-gpu.md`](../working-with-modal-cloud-gpu.md).
- **The dep audit was right about what `training` pulls in:** torch + numpy + matplotlib + utils. The earlier `replay-collector` transitive bloat (from `utils.player_name_lists` → `replay_collector.usernames`) is gone since the `usernames` module moved into `utils/`.
- **`pick_device("auto")` now prefers CUDA → MPS → CPU** and `pick_device("cuda")` raises if CUDA isn't available — silent CPU fallback would have been a footgun on a paid GPU box. `--device auto` from the cloud wrapper does the right thing.
- **Manifests are already cloud-portable.** `samples_for_split` takes `intermediate_root` from the caller, not from the manifest's recorded `intermediate_root` field (which is informational). Step 2's anticipated "path translation" problem dissolved — the cloud function just calls `samples_for_split(m, "train", Path("/data/intermediate"))` and IDs resolve under the Volume mount.
- **Volume naming convention.** `generals-ai.<role>` as a pseudo-namespace inside the default environment. Inputs Volume is `generals-ai.parsed-replays`; outputs Volume (step 3) follows the same pattern. Real Modal environments are overkill for one user + one app.
- **Slice helper.** `training/scripts/build_cloud_slice.py` builds a self-contained slice (`sim` + `meta` + manifest) from any manifest. ~23 MB / 868 files for the probe_500 slice; trivial to upload. Re-usable for any future cloud slice.
- **`bc.train_config` extracted.** `TrainConfig` + `make_run_id()` now live in `bc/train_config.py`. `TrainConfig.run_dir` is the full path to *this* run's directory (was `out_dir`, the parent). Wrappers compose `run_dir = args.out_dir / make_run_id()`. Run-id format is UTC `YYYY-MM-DDTHH-MM-SSZ`, identical local + cloud.
- **Auto-commit covers single-shot writes.** Writes inside a Modal function become visible on the Volume on clean function exit — no `vol.commit()` needed for step 3. Mid-run commits will matter for long training runs (step 5+) when we want to pull intermediate checkpoints.
- **`modal volume get` gotcha.** With a non-existent local destination (or trailing slashes), the CLI collapses recursive contents into a single output file. Always `mkdir -p` the target first and drop trailing slashes. Documented in [`working-with-modal-cloud-gpu.md`](../working-with-modal-cloud-gpu.md#gotchas-worth-knowing).

## Next: step 4 — T4 GPU smoke (single training step)

Goal: first real `bc_run` call on a Modal GPU. CPU pipeline already works; this exercises CUDA, the full dataset → forward/backward → optimizer path, and the round-trip artifact pull-back. T4 first (cheap — $0.59/hr) to validate the code; H100 is a later vertical scale.

Sub-tasks:

1. **Real `local_entrypoint`.** Graduate from the no-arg smokes to the documented [`*arglist` passthrough pattern](../working-with-modal-cloud-gpu.md#native-vs-shell-out-function-design). Cloud-only flags (`--gpu`) parsed locally; everything else forwards to `bc.train_cli.build_arg_parser()`. Defaults supplied by the cloud wrapper: `--intermediate /data/intermediate`, `--manifest /data/probe_500.json`, `--out-dir /runs`, `--device cuda`.
2. **Generate `run_id` laptop-side.** Local entrypoint calls `make_run_id()`, prints the resulting path (`/runs/<run_id>/`) *before* the `.remote()` call so the operator sees it and can `modal volume get` mid-run later.
3. **Wire both Volumes into the training function.** Inputs RO at `/data`, outputs RW at `/runs`. Decorate with `gpu="T4"` (overridable via `with_options(gpu=...)`).
4. **Run `--max-batches 1 --epochs 1`.** Confirms one full forward/backward/optim step + ckpt save lands on the Volume.
5. **Pull back + inspect.** `modal volume get` the run dir; verify `args.json`, `batches.jsonl` (one finite-loss row), `epochs.jsonl`, `checkpoints/epoch_001.pt` are all present.

### Open questions for step 4

- **Flag namespace collisions.** Cloud-only `--gpu` doesn't conflict with anything in the existing parser, but namespace-by-prefix (`--modal-gpu`) is the safer pattern if the surface grows. Decide at implementation time.
- **`cuda_available` skin.** `pick_device("cuda")` raises if CUDA isn't available — good for catching a botched image. But T4 cold-start may print noisy CUDA-init warnings; we'll see and decide whether to suppress.
