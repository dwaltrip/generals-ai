## Where we are

- `training/scripts/run_bc_modal.py` — Modal cloud entrypoint. Full shape: `train` local-entrypoint extends `build_arg_parser` with `--modal-gpu` (required); `train_remote` `@app.function` (T4 default, both Volumes mounted) runs `initialize_run_dir` → `_write_args_cloud` → `bc_run`. Pull-back command printed after return.
- `training/scripts/smoke_modal_prototyping.py` — earlier `smoke` / `smoke_volume` / `smoke_outputs` functions, renamed to mark them as exploratory/scaffolding. Kept for regression smokes.
- `training/scripts/run_bc_local.py` — local sibling. Calls `initialize_run_dir(config)` then `bc_run(config)`.
- `training/scripts/build_cloud_slice.py` — manifest → self-contained slice (sim + meta + manifest) builder, for `modal volume put`.
- `bc/train.py` — runner. Exposes `initialize_run_dir(config)` (mkdir + args.json + announce) and `bc_run(config)` (precondition: run_dir exists). `bc_run` does not know how the dir got there. Threads a typed `IterableDataset` reference through `run_loop → train_one_epoch` so `dataset.set_epoch(epoch)` is called on the typed object, not `loader.dataset` (which is base `Dataset`).
- `bc/train_config.py` — `TrainConfig` (frozen dataclass with `run_dir: Path` as the full per-run path) + `make_run_id()` + `json_default`. Carries DataLoader knobs (`num_workers=2`, `pin_memory: bool | None = None`, `prefetch_factor=2`); pedagogical comment on `pin_memory` documents pinned-memory mechanics + the args.json/console.log provenance split.
- `bc/train_cli.py` — shared parser. `--manifest`/`--intermediate`/`--out-dir` all non-required at argparse level; `config_from_args` validates post-parse. Carries `--num-workers`, `--pin-memory {auto,true,false}`, `--prefetch-factor`.
- `bc/dataset.py` — `IterableDataset` is multi-worker safe. `set_epoch(epoch)` (mirrors `DistributedSampler.set_epoch`) + `_iter_groups(rng, worker_id, num_workers)` helper that shards `self._groups` by `i % num_workers == worker_id`. Caller-driven epoch so the value survives the worker fork. Module also exports `assert_safe_loader(loader)` — startup-time check that raises if `persistent_workers=True` is set, since that flag silently breaks the `set_epoch` mechanism (workers fork once and never see epoch mutations). Called from both `bc_run` and `run_val` right after `DataLoader` construction.
- `shared/device.py` — `dataloader_kwargs(*, num_workers, pin_memory, prefetch_factor, device) -> dict` centralizes device-aware resolution; both train and val unpack it. `move_batch` uses `non_blocking=True` to pair with `pin_memory=True` for async H2D overlap.
- **Volumes on Modal:** `generals-ai.parsed-replays` (RO inputs, ~23 MB probe slice), `generals-ai.training-runs` (RW outputs).

## Findings worth carrying forward

- **`add_local_python_source` beats `add_local_dir + uv_pip_install("/pkg")` for pure-Python packages.** Modal resolves the modules via the local-env import path and drops files at `/root/` (on PYTHONPATH). No synthetic install paths, no pyproject re-resolution, no hatchling build. Use the pip-install path only if a package needs entry points / console scripts / build hooks (none of ours do).
- **`uv export` needs `--no-emit-workspace`.** Without it, workspace cross-deps appear as `-e ./packages/<name>` in the requirements file. Modal's `uv_pip_install(requirements=...)` runs before any `add_local_*` layer, so the path doesn't exist in the container → image build fails. Documented in [`working-with-modal-cloud-gpu.md`](../working-with-modal-cloud-gpu.md).
- **The dep audit was right about what `training` pulls in:** torch + numpy + matplotlib + utils. The earlier `replay-collector` transitive bloat (from `utils.player_name_lists` → `replay_collector.usernames`) is gone since the `usernames` module moved into `utils/`.
- **`pick_device("auto")` now prefers CUDA → MPS → CPU** and `pick_device("cuda")` raises if CUDA isn't available — silent CPU fallback would have been a footgun on a paid GPU box. `--device auto` from the cloud wrapper does the right thing.
- **Manifests are already cloud-portable.** `samples_for_split` takes `intermediate_root` from the caller, not from the manifest's recorded `intermediate_root` field (which is informational). Step 2's anticipated "path translation" problem dissolved — the cloud function just calls `samples_for_split(m, "train", Path("/data/intermediate"))` and IDs resolve under the Volume mount.
- **Volume naming convention.** `generals-ai.<role>` as a pseudo-namespace inside the default environment. Inputs Volume is `generals-ai.parsed-replays`; outputs Volume (step 3) follows the same pattern. Real Modal environments are overkill for one user + one app.
- **Slice helper.** `training/scripts/build_cloud_slice.py` builds a self-contained slice (`sim` + `meta` + manifest) from any manifest. ~23 MB / 868 files for the probe_500 slice; trivial to upload. Re-usable for any future cloud slice.
- **`bc.train_config` extracted.** `TrainConfig` + `make_run_id()` now live in `bc/train_config.py`. `TrainConfig.run_dir` is the full path to *this* run's directory (was `out_dir`, the parent). Wrappers compose `run_dir = args.out_dir / make_run_id()`. Run-id format is UTC `YYYY-MM-DDTHH-MM-SSZ`, identical local + cloud.
- **Auto-commit covers single-shot writes.** Writes inside a Modal function become visible on the Volume on clean function exit — no `vol.commit()` needed for step 3. Mid-run commits will matter for long training runs (step 5+) when we want to pull intermediate checkpoints.
- **`modal volume get` gotcha.** With a non-existent local destination (or trailing slashes), the CLI collapses recursive contents into a single output file. Always `mkdir -p` the target first and drop trailing slashes. Documented in [`working-with-modal-cloud-gpu.md`](../working-with-modal-cloud-gpu.md#gotchas-worth-knowing).
- **Extended-parser beats two-parser.** Cloud-only flags (`--modal-gpu`) `add_argument`'d to the *same* parser as training flags. Single source of truth + collisions raise `ArgumentError` at startup (explicit, not silent). Two-parser `parse_known_args` would silently steal future training flags from the operator.
- **`initialize_run_dir` extracted from `bc_run`.** Cloud entry can drop `args_cloud.json` into the run dir *before* training starts. `bc_run`'s precondition: `config.run_dir` must already exist; error message reports the failure, not the fix (callers may init the dir however).
- **`args_cloud.json` confirmed `Tesla T4` at runtime.** The `cuda_device_name` field is the load-bearing one — confirms Modal honored the requested GPU class. Worth grepping in retrospect if a future run reports a fallback variant.
- **T4 is 1.6–3.3× slower than M1 Max at the pre-DataLoader-fix baseline (nw=0, bs=64, probe_500 slice).** T4 epoch-2: 22 sps train / 177 sps val. M1 Max epoch-2: 70 sps train / 284 sps val. Attributed to data-pipeline bottleneck (Volume reads + `num_workers=0` DataLoader + no `pin_memory`), not GPU compute. The val-faster-than-train shape is present locally too (IterableDataset cost), but amplified on cloud by network FS. **Superseded by the post-fix numbers** in newer findings + the 4.5c batch-size sweep — keep this entry as the historical baseline, not the current picture.
- **DataLoader sharding fix pattern.** PyTorch's `IterableDataset` requires explicit per-worker sharding (`get_worker_info()`) AND caller-driven epoch state (`set_epoch`) — internal `self.x += 1` mutations don't survive the worker fork. Test the sharding helper (`_iter_groups`) directly; trust PyTorch to wire `get_worker_info` correctly. Real-worker DataLoader tests on macOS Py3.14 trip a fork-in-multi-threaded-process `DeprecationWarning` once any prior test has touched PyTorch's intra-op thread pool.
- **`pin_memory=True` only earns its full keep with `non_blocking=True`.** Without non_blocking, pinned memory just skips the pageable→pinned staging copy (small win). With it, the H2D transfer is queued on a CUDA stream and overlaps with the prior batch's GPU compute (the big win). `move_batch` does this unconditionally — safe to leave on for non-CUDA targets (silently ignored).
- **`num_workers` sweet spots differ per platform.** M1 Max peaks at nw=2 then declines (train sps: 100 → 82 → 74 across nw=2/3/4); T4 climbs monotonically (99 → 96 → 116). Opposite curve shapes from the same code. **Why each platform behaves this way is open** — candidate factors include CPU layout (P/E cores, vCPU count), I/O substrate (local SSD vs network FS), per-batch IPC overhead, and main-process ↔ worker contention, but we haven't isolated which dominate. Practical takeaway: don't carry one platform's sweet spot to another; sweep per-target.
- **Batch size revealed GPU underutilization at our small-model size.** T4 at bs=128/nw=4 is ~2x GPU-underutilized: bs=256 doubles train sps (116 → 238); bs=512 is flat (237) with *exactly* 2x per-batch scaling — signature of a non-GPU ceiling at ~4.2ms per sample. At our 4.2M-param model, throughput tops out around bs=256.
- **T4 ≈ M1 throughput at our current 4.2M-param model: looks more workload-shaped than hardware-shaped, but unconfirmed.** Both top out at ~100-240 sps train. The T4 bs sweep evidences that GPU compute had headroom at bs=128 (doubling batch doubled sps), so "T4 should be faster" doesn't obviously hold at this model size — but we haven't directly measured GPU utilization to verify where the ceiling actually sits. Tentative reframing of the H100 question: not "is it faster on our current model" but "does T4's bottleneck (and H100's potential advantage) even show up unless the architecture work yields a model substantive enough to exercise the GPU".
- **Val is more data-pipeline-bound than train.** Adding workers nearly doubled T4 val sps (279 → 529 from nw=2 to nw=4) while train barely moved (99 → 116). No backprop ⇒ per-step time dominated by data prep + collation, so val benefits disproportionately from any pipeline fix. Worth remembering if val ever lands on a critical path (e.g., frequent eval cadence).
- **`assert_safe_loader` chokepoint pattern.** Converts a silent forked-state failure (`persistent_workers=True` would freeze the per-epoch shuffle) into a startup-time `RuntimeError`. Co-located helper + loud WARNING on the affected method (`set_epoch`) is a defensible pattern for any other knob that interacts subtly with fork-based workers.

## DataLoader detour — done

Goal was to validate that the T4 bottleneck was data-starvation by exposing DataLoader knobs and re-measuring. Confirmed: T4 train sps went 22 → 99 (4.5x) at bs=128/nw=2 after the knob work, 22 → 116 at nw=4. The follow-on batch-size sweep (next section) revealed there's still headroom past this and a new non-GPU ceiling.

1. ✅ **DataLoader knobs + multi-worker safety.** Commits `3b65190` (sharding + `set_epoch`), `6b301b8` (CLI knobs + async H2D), `fa37589` (helper extraction). `--num-workers/--pin-memory/--prefetch-factor` default to `2 / auto / 2`.
2. ✅ **Re-ran local + cloud with bigger workload + `num_workers` sweep.** M1 Max sweet spot: nw=2. T4 sweet spot: nw=4. Per-platform numbers in the Findings entry. Detail and full curves in "Investigating T4's current bottleneck" below.
3. ✅ **Persistent-workers safeguard.** While wiring the knob plumbing, surfaced that `set_epoch` is incompatible with `persistent_workers=True` (silent frozen-shuffle failure). Added `assert_safe_loader(loader)` chokepoint in `bc/dataset.py` (commit `02ab6a2`) + loud WARNING on `set_epoch`. Enabling `persistent_workers=True` is now a startup-time `RuntimeError` until the proper epoch-propagation refactor lands.

See the WARNING in `bc/dataset.py:set_epoch`.

## Investigating T4's current bottleneck

Goal: understand what limits T4 throughput at our current 4.2M-param model, so we can make an informed call on what's worth investing in next: data pipeline work, model architecture work, H100, or simply moving on to other parts of the project entirely (the cloud-GPU story may already be good enough for what's next). The bs sweep landed us at a ~237 sps ceiling that's clearly not GPU compute; the rest of this section is about figuring out what it *is* — but the answer might also be "doesn't matter right now."

### Sub-step 4.5c done — batch-size sweep on T4 (nw=4, max-batches=50, epochs=2)

| bs | Train sps | Val sps | Per-batch train | Per-sample train |
|---|---|---|---|---|
| 128 | 116 | 529 | 1.10s | 8.6ms |
| 256 | **238** | **548** | 1.08s | 4.2ms |
| 512 | 237 | 546 | 2.16s | 4.2ms |

Key finding: bs=128 → 256 doubles train sps (GPU had spare capacity at small batch). bs=256 → 512 is flat with *exactly* 2x per-batch scaling — signature of a non-GPU ceiling at ~237 sps / 4.2ms per sample. T4 sweet spot at current model size: **bs=256, nw=4**.

- `2026-05-23T00-40-02Z/` — bs=512

Per-platform `num_workers` sweet spots from the prior sub-step (separate `Findings` entry above for the headline + caveat): **M1 Max nw=2** (curve peaks then declines); **T4 nw=4** (curve climbs through nw=4; nw=5+ untested).

### Sub-step 4.5d queued — cheap profiling probes (do these first)

Two small one-shot Modal scripts that don't require modifying the training loop. Each takes <1 min of Modal time. Run these before deciding what to do next — they sharpen the working mental model and predict whether stage-to-SSD would actually help.

1. **Box specs probe.** Dumps `/proc/cpuinfo`, `/proc/meminfo`, `df -h /tmp`, `nvidia-smi` from a T4 container. Tells us actual vCPU count + model + RAM + `/tmp` size + GPU baseline. Resolves the "~4 vCPU" assumption and confirms staging headroom.
2. **File-read latency comparison.** Measures cold Volume reads vs warm Volume reads (page cache hit) vs reads after one-shot copy to `/tmp`. Plus the staging cost itself. Directly predicts whether stage-to-SSD would move the ceiling — without committing to the implementation. If warm Volume ≈ local `/tmp`, page cache hides the FS and staging won't help; if warm Volume is meaningfully slower, staging is worth implementing.

### Sub-step 4.5e gated — stage-to-SSD (only if 4.5d says it'll help)

Mechanism is well-understood: one-shot copy `/data/intermediate` → `/tmp/intermediate` at the top of `train_remote()`, then point `config.intermediate` at the new path before `bc_run`. Probably a `--stage-to-ssd` flag for clean A/B comparison. Effort estimate: ~30-60 min of focused work. The unknown isn't *how* but *whether it helps* — which 4.5d answers cheaply first.

### Other things to investigate (and brainstorm more next session)

Beyond the FS hypothesis, candidates for the source of the 4.2ms/sample ceiling. Pick based on what 4.5d-e reveals. **Next session, do a fresh-eyes pass on this list and add to it — this is a starting set, not exhaustive.**

- **GPU utilization sidecar.** Sample `torch.cuda.utilization()` every 1-2s during a training run, log to a sidecar JSONL. Most direct answer to "GPU-bound or CPU-bound" — settles the question 4.5d only predicts. Modest instrumentation; requires a training re-run to collect.
- **Pipeline-stage bisection.** Replace `build_obs` (or `step_memory`, `build_mask`, BFS) with a cheap no-op stub and re-run. If throughput stays flat, that stage isn't the bottleneck. Zero-instrumentation way to identify the dominant CPU phase.
- **`build_obs` microbench.** Standalone timing on synthetic data, outside the DataLoader context. Direct read on the most-likely CPU hot spot. No Modal cost.
- **BFS cache utilization.** Current code invalidates the BFS graph every frame (`bfs_cache.invalidate_graph()`), so the cache infra exists but the amortization never lands. Worth understanding what BFS actually costs per frame and whether per-frame invalidation is a real requirement or a TODO from earlier work.
- **Larger `prefetch_factor`.** We use 2 (default). Higher means workers prefetch more batches ahead — helps if main process empties the queue faster than workers fill it. One flag, one run.
- **M1 batch-size sweep for symmetry.** We only swept bs on T4. A matching M1 sweep would tell us whether M1 had hidden GPU capacity at bs=128 or was already saturated. Cheap baseline.

### Reframing questions worth asking before doing more optimization

- **What sps do we actually need for step 6 to be practical?** Rough math: 50k games × ~4 perspectives × ~hundreds of frames per perspective = millions of frames per epoch. Pick a target epoch wall time → derive minimum sps. We're at ~237 on T4. That tells us whether we're within striking distance of "good enough" or way off, and reframes the urgency of *all* further optimization work.
- **Connection to model architecture work.** The 4.2M-param model is our BC proof-of-concept — deliberately sized for the MVP, somewhat realistic but not necessarily where the final architecture lands. Future architecture work is a separate design problem with two goals at once: (1) the best architecture for the BC problem, and (2) good use of the hardware we have, so runs aren't slower than they could be. Throughput investigation here feeds (2), not (1). If that work yields a more substantive model, re-measuring T4 (or H100) with it tells us whether the current ~237 sps ceiling still binds — and whether the H100 question becomes substantive or stays speculative.
