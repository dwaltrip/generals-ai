# 5.20-3 — Model Architecture Implementation Notes

**Date:** 2026-05-20
**Branch:** `spike-phase-2`
**Scope:** What we committed in `bc/model.py` + `bc/loss.py` +
`training/scripts/overfit_one_batch.py` (`9ce1edf`), how it relates to
the prior design docs, and what's deferred.

The architectural lineage docs ([`network-architecture-design.md`](../network-architecture-design.md),
[`5.17-4-training-spike-plan.md`](./5.17-4-training-spike-plan.md), and
the DeepNash summary [`5.02-7-deepnash-summary-and-implications.md`](./5.02-7-deepnash-summary-and-implications.md))
specify the architecture at varying granularity; this doc captures the
implementation choices that landed when those docs were ambiguous, and
the places we deliberately deviated.

## What landed

- **Trunk:** 2-contraction Pyramid Module at half widths (128/128/160),
  N=2 outer / M=2 middle / M=2 inner ResBlocks. ~3.0M params.
- **Heads:** policy (small Pyramid Module N=1/M=0 → Conv→8; 1.1M params),
  pass (global pool + linear; 129 params), value (3×3 conv → flatten →
  linear; 9.4k params). Total: 4.2M params.
- **Loss:** policy CE (masked, ignore_index for pass frames) +
  0.5·value CE + 1.0·pass BCE.
- **Overfit harness:** single fixed batch trained to ~zero loss.

**Phase 2 exit criterion met.** M1 MPS, batch=16, 500 steps, ~71s wall
clock. Total loss 4.97 → 0.0003. Policy CE memorized by step 25;
pass BCE took the full 500 (slower convergence with the
single-linear-layer pass head).

**What the overfit run does and doesn't verify.** It's a pipeline
integration test: gradients flow end-to-end through all three heads,
no NaN/explosion, MPS doesn't fall back to CPU, mask applied as a hard
constraint. What it does *not* verify: architectural capacity for the
real task (4.2M params can memorize 16 fixed positions trivially), slot
canonicalization correctness (only 16 positions visible), generalization
of any kind. Phase 4 eval is where those questions land.

## Deviations from the prior design docs

For each, what the doc said vs. what we built, and why. Future revisits
of any one of these should start by re-reading the rationale here, not
re-deriving from scratch.

| # | Item | Prior design said | We built | Reasoning |
|---|---|---|---|---|
| 1 | **Normalization** | `network-architecture-design.md` §6: **LayerNorm** ("safe default for RL — BatchNorm interacts poorly with policy gradient") | **GroupNorm** (preferring 32 groups; falls to 16 for the 80-channel intermediate) | The design doc's *intent* is "per-sample norm, not BatchNorm" (any non-BN choice satisfies it). LN over `[C, H, W]` is awkward in PyTorch (`nn.LayerNorm` normalizes over the last dim, requiring a permute dance for NCHW). GN is the standard "LN-in-spirit, NCHW-native" choice (Wu & He 2018). Same intent as the inherited tentative pick; cleaner ergonomics. |
| 2 | **Value head shape** | Design doc §4 + DeepNash §1.4: **head-as-Pyramid-Module** (N=0/M=0) → 3×3 conv (1 ch) → flatten → Linear. Tentative; design doc explicitly invites a simpler fallback. | **Option B (no head-PM):** `Conv2d(C, 1, 3) → ReLU → flatten → Linear(H·W, 8)` | Spike v1; the projection part (conv → flatten → linear) is the load-bearing piece — it preserves per-cell spatial info via `flatten`, which is the right inductive bias for placement prediction (a global question). The head-PM in front adds ~50k params and ~50 lines of code that we don't need to verify pipeline correctness. Two `TODO(option C extension)` markers in `ValueHead` show exactly where to insert the head-PM if the corpus run shows value-head signal matters. |
| 3 | **Trunk dropout** | Design doc §3.3 paired-defaults: 0.05–0.10 dropout | **None** | The paired defaults are for the corpus run (regularizing the train/val gap). For an overfit harness, dropout actively *prevents* the exit criterion. Decision is "different scope" rather than a true deviation — add for Phase 3 corpus run. |
| 4 | **Overfit batch size** | Plan inherits 64 from the smoke test ("not a training-time commit") | **16** (with CLI override) | Smaller batch = fewer samples to memorize = easier convergence in 500 steps. Overfit-harness ergonomics; not a real-training commit. |
| 5 | **Skip-connection granularity** | Design doc §6: "Symmetric across encoder/decoder **at each level**" (reads as naive U-Net: one skip per level) | **Per-block skips** (every conv ResBlock contributes one skip, including the strided ones) | DeepNash-literal interpretation, **confirmed against the paper** (Perolat 2022 supplementary Fig. 7 + Neural Implementation §). The design doc's terse "at each level" underspecifies; the DeepNash lineage is per-block. Going literal preserves the existence-proof relationship: if the spike trains, that's evidence the inherited design works; if it doesn't, we don't have to wonder whether we deviated. |

## Ambiguities the prior docs didn't pin

These are choices the docs didn't speak to; we committed and documented.

- **Strided-block channel widening (middle → inner, 128 → 160).**
  Absorbed *inside* the strided ConvResBlock: its `out_ch` is the next
  level's width, intermediate is `out_ch/2`, and the 1×1 residual
  projection handles in→out channel + spatial halving in one step.
  Alternative would have been a separate 1×1 widener between strided
  block and inner ResBlocks — more lines, no advantage identified.

- **Skip projection stride.** The DeepNash spec says "optional S
  striding" on the 1×1 ConvTranspose2d that adapts skip channels.
  But by construction, skip source spatial (encoder block input)
  equals skip target spatial (decoder block post-first-deconv
  intermediate), so the projection's stride is always 1 — pure
  channel reduction. We commit to stride=1 everywhere; the "optional
  S" clause in the spec is a no-op in our wiring. (See `DeconvResBlock`
  docstring for the spatial-dim trace.)

- **GroupNorm group count.** All trunk widths {64, 80, 128, 160} accept
  16 groups; only 80 fails to divide 32. Helper picks the largest
  divisor of `channels` ≤ 32. Per-layer group counts: 32 for {64, 128,
  160}; 16 for {80}.

- **Pass-logit pooling treats padded cells as in-distribution.** Global
  avg pool over the full 32×32 trunk output averages ~40% padded cells
  in the mean. Padded activations are non-zero after convs (the conv
  has seen them and produced output). Spike accepts this bias; the same
  noise floor applies to the value head's flatten. Masked pooling over
  the unpadded region is the cleaner fix — flagged as a TODO in
  `PassHead`.

- **Overfit-batch composition.** The dataloader emits frames in
  `(game, perspective, timestep)` order, and the earliest timesteps of
  any game are mostly pass frames (players spam-pass while armies
  build). An all-pass batch would leave the policy head with zero
  gradient signal, masking pipeline bugs. The harness therefore
  searches the loader for a batch with at least `--min-non-pass-frac`
  (default 25%) non-pass frames before pinning it as the overfit
  target. **Phase 3 implication:** shuffle-buffer-style frame mixing
  across game boundaries is worth bringing forward for the corpus
  training loop — the current per-game-sequential walk is fine for
  an overfit harness but suboptimal for stochastic gradient training
  (correlated batches, early-game bias in the loss).

## What we explicitly didn't include in v1

- No `torch.compile`, no mixed precision, no checkpointing.
- No batch-size sweep.
- No model unit tests in `tests/` — the overfit harness is the
  integration test for the model; per-module smoke tests on top of it
  aren't pulling their weight at this stage.

## Forward-looking

What's tracked elsewhere but worth threading through:

- **Phase 3 dataloader work** should pick up the shuffle-buffer
  question raised by the early-game bias (above). Per-batch frame
  diversity matters more than per-game sequential walking for SGD.
- **Pass-head loss weight (`μ`) may want re-tuning.** The pass head
  was the bottleneck for total-loss convergence in the overfit run
  (policy + value memorized 16 samples by step 25; pass BCE took the
  full 500). Pass head has only 129 params and one binary signal per
  sample; its gradients are small relative to the model-wide gradient
  norm. The current `μ=1.0` is an inherited starting point — empirical
  retuning is a cheap follow-up once corpus training surfaces real
  per-component dynamics. Companion data: corpus-weighted pass rate is
  49.7% (per `training/investigations/5_18_pass_rate_sweep.py`).

  Follow-up at N=128 (`--batch-size 128 --steps 800 --log-every 20`)
  confirmed the bottleneck pattern: pass BCE descended through troughs
  at ≈0.23 → 0.17 → 0.03 → 0.025, but with intermittent loss bumps
  that grew larger as the loss approached zero (peak total ≈2.8 around
  step 380). The bumps are AdamW-near-minimum behavior: as gradients
  shrink, Adam's running second-moment denominator shrinks too,
  occasionally inflating the effective step size and launching the
  optimizer out of the basin it had found. **An overfit-harness
  artifact, not a Phase 3 concern** — corpus training won't approach
  zero loss, so the denominator stays healthy. The pass head reaching
  ≈97.5% confidence on the fixed 128-sample batch is fine; whether the
  head needs structural changes is a Phase 4 eval question, not a
  pre-Phase-3 redesign.
- **Policy head is 1.1M params (~25% of the model)** — the head
  Pyramid Module at N=1/M=0 is more parameter-heavy than the design
  doc's "small head" framing suggested. If width-trim becomes a lever
  (post-spike sweep, latency tuning), the policy head is the next-biggest
  after trunk widths. Roughly: head-PM params scale as width² (Conv2d's
  `C → C/2 → C` is the dominant cost), so halving the head width
  drops ~800k params.
- **Value-head option C** is a localized extension if Phase 4 eval
  signals a weak placement predictor. Two TODO markers in
  `ValueHead`; rest of the wiring is unchanged.
- **Pass-head masked pooling** is the cheapest cleanup if pass-rate
  signal looks degraded.
- **GroupNorm vs. LayerNorm sensitivity** is a post-spike sweep
  candidate. The intent is the same; whether the choice matters
  empirically is an open empirical question.
