## Head-architecture refinements: padding mask + pyramid value-head variant

**Date:** 2026-05-24
**Branch:** `model-arch-v2`
**Commits:** `e5cf5d5`, `8a5552e`, `0e13f0c`

Two related head-architecture changes landed, and the value-head variant menu is now a runtime knob instead of a code-edit. The architectural framing in [`5.21-5`](./5.21-5-post-spike-knobs.md) for these items is now stale; this note is the current pointer for what's wired up and what the next A/B looks like.

## What landed

1. **Padding mask plumbed through PassHead + ValueHead.** Per-sample `valid_mask: [B, 1, H_PADDED, W_PADDED] bool` rides in the batch dict; PassHead becomes a masked sum/count pool; ValueHead multiplies by the mask between ReLU and flatten. Fixes a real signal-quality bug — trunk activations at padded positions were non-zero (convs see the zero-padded input and write into the padded region), and both heads were folding that junk into their outputs in a per-game-size-dependent way.

2. **ValueHead `variant` arg with `direct` and `pyramid`.** Default `direct` is the v1 spike head (Conv→ReLU→flatten→Linear, ~9k params); `pyramid` inserts a shape-preserving PyramidModule(N=0/M=0/M=0, uniform width) before the projection. Surfaced as `--value-head {direct,pyramid}` on `train_cli`, `flops_probe`, `overfit_one_batch`, `value_head_probe`, and `self_play.agent.load_checkpoint(variant=...)`. Logged to `args.json` for run provenance.

3. **Fix `overfit_one_batch.eligible_perspectives` signature.** Pre-existing breakage unrelated to the architecture work — the harness was calling the 2-arg form after the function gained a required `curated_names` arg.

## Naming note

The 5.20-2 / 5.20-3 / 5.21-5 docs label these variants "option B" / "option C" — arbitrary letters with no architectural meaning. In code they're `direct` and `pyramid` (what the variant actually IS). ValueHead's docstring keeps the historical breadcrumb so the old session notes still navigate forward.

If we add the intermediate variants discussed this session, the natural extension is `stacked` (+N ConvResBlocks at full resolution, depth-only) and `wide_bottleneck` (Conv→k channels before flatten instead of →1, orthogonal axis). Not implemented; documented here so the design space stays legible if we revisit.

## Capacity / cost

From `flops_probe`:

| variant | params | fwd FLOPs | fwd+bwd FLOPs |
|---|---|---|---|
| `direct` | 4,185,442 | 3.599 GFLOPs | 10.571 GFLOPs |
| `pyramid` | 5,007,970 | 4.273 GFLOPs | 12.594 GFLOPs |
| delta | +822k (+20%) | +0.67 (+19%) | +2.02 (+19%) |

Wall-clock impact on T4 is probably smaller than +19% — per [`5.23-2`](./5.23-2-phase-a-results.md), the GroupNorm/softmax fp32 overhead is the current ceiling, so adding compute-in-the-conv-path doesn't translate 1-to-1 to step time. Real number will surface in the A/B.

Pyramid brings the value head into the same size class as the policy head (which already has its own head_pm at 1.14M). The "tiny value head" was anomalous; pyramid is the spec-aligned shape.

## Overfit-math recalibration (non-obvious)

Earlier framing — "850k params / 40k value labels = 21 params/label, overfit territory at 5k games" — was wrong. The value head trains per-frame, not per-(game, perspective). Each game contributes ~400 frames per perspective × 8 perspectives, all with varied trunk features even though they share a label. Effective sample size is closer to 16M frames (5k games × 8 × 400) than 40k labels.

The relevant signal is what the spike data already showed: the *9k-param* head memorized at 2k-game scale (train value 2.0→0.3, val value 1.97→3.42). Memorization wasn't a head-capacity issue — it was the head finding trunk features that distinguish train games but don't generalize. Bigger head probably won't change that qualitative picture much; it might extract more signal that helps the trunk OR just memorize harder. That's what the A/B answers.

Net: pyramid is reasonable at any data scale we've been running, not "wait for 50k+ before trying."

## Next A/B

Bundled change: in-flight 5k×8 baseline (no padding fix, `direct`) vs. next run with mask-fix + `pyramid`. Same recipe, same seed:

```sh
training/scripts/run_bc_modal.py \
    --manifest <same as baseline> \
    --epochs 8 --batch-size 512 --precision fp16 \
    --value-head pyramid
```

Cleanly compares baseline vs. fully-fixed-value-head. The mask-fix-only intermediate run was discussed and skipped — bundling saves a ~5hr cycle, attribution loss is acceptable.

**What to watch in the curves:**

- Per-head value loss: pyramid should drop faster on train (more capacity). Val value loss is the real story — if it tracks better than the 1.97→3.42 spike pattern, the trunk regularization is helping; if it gets worse, pyramid is memorizing harder without trunk benefit.
- Policy loss (the thing we actually care about for move quality): hoping for a small improvement from better trunk regularization. Honest expectation is "no big swing at small data scale."
- Pass loss: small but cleaner now that the masked pool excludes padded cells. Pass-rate sanity check on a held-out slice is the more useful read.

## Open knobs (deferred, not stale)

- **`stacked` intermediate variant.** +1 or +2 ConvResBlocks at full resolution before proj_conv. Cheaper than pyramid (+0.15M / +0.30M), but no multi-scale benefit — adds depth without growing effective RF as efficiently. Not obviously a better tradeoff than pyramid.
- **`wide_bottleneck` axis.** Conv(C → 8) instead of Conv(C → 1) before flatten. Orthogonal to RF — preserves more channel info through the bottleneck. ~+150k params. Could complement either direct or pyramid.
- **Width bump (half → full trunk: 128/128/160 → 256/256/320).** ~4× trunk params. Deferred from this session as too operationally heavy without first measuring pyramid's impact. Per [`5.23-2`](./5.23-2-phase-a-results.md), this is also the change that would make H100 worth using over T4.
