## Watch for

- Pinned smoke-test checkpoint at `training/data/runs-cloud/2026-05-23T23-40-14Z/checkpoints/epoch_005.pt` is the legacy-format compat case — if those tests break post-PR 3, `load_bc_model`'s format-detection branch is wrong.
- `state.epoch` invariant: update AFTER successful epoch+save, never before. Crash mid-epoch leaves `state.epoch` one behind — correct, and resume relies on it.
- `WarmupSchedule` is narrow on purpose; not a general LR-schedule framework.
- LR not overridable on resume even with `--force-config-mismatch` — deliberate. If a real warm-start workflow is wanted, that's separate design.
- No try-and-fallback for partial-write checkpoints; operator cleans up manually.

## Workflow for each bundle of work (PR)

**Before starting:**

- Carefully read all relevant code (bundle-specific — `train.py` + nearby files for PR 1; consumer files for PR 2; etc.).
- Sketch the end-goal state as a concise bullet-level summary in a session note: `5.28-4.N-train-py-refactor-notes-part-N.md` (N matches the PR number, e.g. `4.1`, `4.2`, ...).
    - Focus on structure, module boundaries and interfaces, data flow, and any notable low-level details.
    - Keep it brief - don't re-state the design doc. The sketch is the bridge between the abstract design and the concrete diff, grounded in the existing code.
- If significant issues or ambiguities surface from the read, flag and discuss before proceeding.
- Otherwise, proceed with implementation.

**During implementation:**

- Stay focused on the PR's scope. Don't get distracted by ruff or pyright — the codebase has lingering lint issues, not our concern here. Same for adjacent refactor opportunities — they're tomorrow's PR or their own thing.

**After each bundle:**

- Run the relevant test subset. For PRs 1 + 2 the contract is zero behavior change — existing tests passing is the verification. PRs 3+ add new tests; same expectation.
- Commit all changes. One commit per PR is the default; small natural sub-commits within a PR are fine.
- Briefly report anything unexpected or notable — implementation-time decisions, complications, things to remember for next bundle. No need to stop for these unless they're real issues; the notes are for understanding how it actually played out.
