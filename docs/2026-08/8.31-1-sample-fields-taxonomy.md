# 8.31-1 — Sample-field taxonomy and naming

Date: 2026-08-31

## Context

We have recently been reworking the code that turns parsed corpus data into sample-level training data, partly in preparation for the goldens first cut and partly as general codebase cleanup. That pipeline, the dataset walk, emits per-frame arrays ("sample fields") that reach the collated batch. The vocabulary used to group them was adopted ad hoc: "targets" served as the umbrella term for every field not output by the walk core, which is inaccurate for fields like alive_mask that are not prediction targets. This note records the field taxonomy we settled on, the renames that follow from it, and the reasoning. It also settles the goldens registry's pending "targets vs emit vocabulary" decision (the 8.12-2 TODO).

## The three usage classes

Every sample field belongs to a single usage class:

1. **Model inputs**: fields used in the model forward pass.
2. **Supervision**: fields used to encode targets or compute loss, in at least one supported config.
3. **Meta**: all other fields. Notable examples: provenance, metrics inputs, bookkeeping.

Fields that qualify for multiple usage classes should be placed in the first one that matches.

A field is classified by where it can be used, not where it is used in a given run, and the classification happens once in the schema. So in a particular run, a supervision field may end up used only by metrics. That is expected and does not change its class. Two supervision fields are conditional members today: alive_mask, which is used in the loss only under the time_bin elim variant, and next_elim_removal_dt, which is used in the loss only when next_elim_target_tau > 0.

## Construction vs usage: two independent axes

Every field has two classifications, which were conflated in the old vocabulary:

- **Construction** — where it is computed: walk core (stateful obs machinery), tail (stateless per-frame lookups), or orchestration (the dataset.py loop).
- **Usage** — how the field is used, as one of the three classes above.

We can still name relevant machinery with construction and process vocabulary (emit_frame, EmitSpec, core/tail). However, this doc proposes that data containers now be named with usage vocabulary (FrameSupervision, FrameMeta).

If the build_mask move and the next_elim_dt re-home land (see Decisions and leans), the two walk containers align: WalkFrame contains only model-input fields, and FrameSupervision contains only supervision fields. One residual case is next_elim_dt, which is computed in the tail but is a meta field by usage.

Fields where the two axes conflict are still possible. A plausible future example is fog/belief-head supervision derived from the walk's memory state: it would most naturally be computed in the core, but it is supervision by usage.

An approach for handling this might be to split the field's computation as cleanly as possible under the new framework: derivation logic goes in the tail, with the other supervision fields, and the walk core exposes any intermediate state needed by the derivation.

A related wrinkle involves cross-frame state. If a supervision field needs data cached across frames, PerspectiveWalk is the natural home for that cache, as the tail is a stateless function. The mismatch (the walk core holding state only used by supervision fields) would be documented as a known caveat.

## Field inventory

Each classification was verified against the field's actual consumers as of this note.

**Model inputs** (used in the model forward pass):

- obs — the main model input.
- valid_mask (board_mask) — a forward-pass argument: `model(obs, valid_mask)`.

**Supervision** (used to encode targets or compute loss, in at least one supported config):

- mask (legality mask) — applied to the policy logits before the policy cross-entropy, in every config.
- action_target — the policy cross-entropy target.
- is_pass — the pass-head BCE target. It also determines which frames are excluded from the policy cross-entropy.
- value_target — the value cross-entropy target.
- elim_bin_target (time_bin variant) — the elim cross-entropy target.
- next_elim_target (next_death variant) — the hard cross-entropy target.
- present_mask (next_death) — restricts the loss's cross-player softmax to present players.
- alive_mask — conditional: among the loss terms, only the time_bin elim term uses it.
- next_elim_removal_dt (next_death) — conditional: used in the loss only when next_elim_target_tau > 0, as the basis of the soft-target distribution.

**Meta** (the remainder: provenance, metrics inputs, etc.):

- sample_idx, frame_t — provenance fields.
- p_start, players_alive — inputs to metrics conditioning.
- next_elim_dt — used only by the dump and offline analysis tooling. Tentatively re-homed here.

**Outside the schema:**

- sim_frame — an analysis-only raw attachment. It is not a tensor and is excluded from the train loop.
- WalkFrame.t — internal (frame_t is the emitted form).

## Decisions and leans

- FrameEmission → FrameSupervision. FrameMeta keeps its name.
- The goldens vocabulary follows the usage-class names, settling the 8.12-2 targets-vs-emit decision: "targets" now refers only to actual targets. Suggested identifiers, as leans to finalize at implementation time: TargetsEntry → SupervisionEntry, compute_targets → compute_supervision, "targets bundle" → "supervision bundle", and targets_compute.py renamed to match.
- build_mask moves from the walk core to the tail, aligning the walk containers. The move follows from the data dependencies: build_mask is stateless, its inputs are exactly the tail's signature, and its placement in WalkFrame came from historical bundling. A side benefit: the special-case handling of mask in compute_targets goes away, and every bundle key is produced by the same per-t stacking.
- next_elim_dt should move out of aux_head_targets. Under the above classification guidelines, it is a meta field, as it is used only by the dump and offline analysis.
    - A tentative plan from this session: the tail keeps computing it, as part of the next_death spec, and returns it separately from the supervision fields in a small meta output. We should discuss and confirm further during implementation, as the aux head code has some warts.
- The "emit" vocabulary survives as process naming only: emit_frame, EmitSpec, PartialEmitSpec, EmitPrecompute. A spec that covers all three usage classes is appropriately named after the process rather than any one class.
- Once the renames land, the classification rule will get clear, concise documentation at one place in the code. One candidate location is near FrameSupervision. The exact spot will be picked during implementation. This note holds the reasoning.

Status: this is the agreed direction, with next_elim_dt tentative as noted. None of it is applied yet.

## Alternatives considered

- **"targets" as the umbrella term** — two of the fields under the umbrella (alive_mask, next_elim_dt) are not targets, and any future non-target field would widen the gap.
- **"emit" or "tail" as the umbrella term** — these are construction words: they describe where the data comes from but not what it is. The appeal of "tail" was that it is vague enough to cover future fields of any kind. But the three usage classes already cover every field, so no catch-all is needed.
- **Config-dependent placement of alive_mask** (supervision when the elim loss uses it, meta otherwise) — alive_mask is a loss input in some configs and a metrics-only field in others. Under this option, its class would change to match: supervision where the loss uses it, meta elsewhere. Each class in the constructed sample would then correctly contain only the fields whose usage in that run matches the definition. While more precise in some respects, this approach was rejected because the ambiguity affects a narrow slice of a subset of configs and yet this would expose it to all readers of these containers. This decision is worth revisiting if the usage-class labels are ever used at runtime, for example by tooling that groups, dumps, or retains data by class.

## Deferred

- Batch key "mask" → "legality_mask": renaming it would be wide mechanical churn across loss, eval, dumps, and the fq tooling. It will be converted slowly as code is touched, under the same policy as valid_mask → board_mask.
- That the meta class includes metrics-only fields is accepted for now. The class's name (or a split) is worth revisiting only if those fields accumulate.
- The PartialEmitSpec shape review: PartialEmitSpec exists to let the analysis toolkits supply the obs config later in their flow.
- The registry transcription (8.12-2) should record that obs references cover obs only, with the mask hashes in the supervision bundle.
