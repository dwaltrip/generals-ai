# Analysis toolkit brittleness: unchecked implicit obs contract

*Date: 2026-08-20. Records a design gap between the analysis toolkits and the obs build. Mainly relevant when changing obs channels (their layout or their content) or `ObsConfig`.*

In the analysis toolkits, each run supplies its own obs config, but the analysis structures contain implicit assumptions about the obs channels (their positions and their meanings), and those assumptions are never checked against the obs build used for a run. This is harmless today: current configs and current obs-builder code satisfy every known assumption. After a future obs change, a mismatch could corrupt analysis results without an error.

## Problem

The two analysis toolkits, fq and the probe toolkit, have a loose two-stage usage pattern:

1. Define the structures for an analysis using the toolkit's contracts. For fq that is `FrameTableSpec`; for the probe toolkit it is `ProbeTask` + `FeatureSource`.
2. Run analyses against those structures: `build_frame_table(spec, samples, obs_cfg)` for fq, `cache_probe_features(source, task, samples, obs_cfg)` for probes.

Stage 1 requires some core configuration details, but the `ObsConfig` is intentionally left unspecified in both (fq's `PartialEmitSpec` leaves `obs` open). The `ObsConfig` is supplied in stage 2, once per run.

Stage-1 structures can still contain assumptions about the obs channels. Some are about positions, for example a deriver that reads fixed channel indices. Others are about content, for example `ARMY_OBS`, which reads a single corner cell (the army planes are constant over the board) and multiplies by 1000 to undo their scaling. These assumptions are implicit: they are not declared anywhere, and there is no complete list of them short of careful code investigation. (The "Affected code" section lists the ones known today.)

There isn't any guard or check that the obs build used for a run (the supplied `ObsConfig` plus the obs-builder code) matches the stage-1 assumptions. That missing check is the gap this doc records.

## Failure modes

A small set of incomplete guards exists. Some are intentional: `join_dump`'s `truth_map` checks join alignment, checkpoint loading is strict, and `GROUND_TRUTH_OBS_CFG` is set to fp32 so `army_obs == army_sim` holds exactly. Others are incidental, side effects rather than designed protection: a changed channel count fails the trunk's `in_ch` where a model consumes the obs (ground-truth fq tables and `RawObsSource` probes run no model, so they have no shape check at all), and an out-of-range channel index raises.

Beyond those, obs changes are entirely unchecked. How exposed an analysis is depends on how it reads the obs tensor: a deriver that only reads `valid_mask` is hard to break, while `ARMY_OBS` (fixed indices, a constant-over-the-board read, an assumed scale) is exposed to many kinds of change.

The unguarded outcome is silent wrongness: the analysis reads a channel that is no longer what it assumes, because its position changed or because the meaning of its values changed, and the results are wrong with no error. (A lesser example: `obs_dtype` fp16 vs fp32 keeps positions and meanings and shifts values by quantization.)

## Current status

A harmful config-driven mismatch cannot happen today. Every channel in the base block (the frozen first 86 channels of the obs tensor) has a fixed index: the dense-history tail comes after the base block, and gated groups are appended at the end. No `ObsConfig` that can be constructed today changes a base-block index.

Test coverage for that claim is partial: a test covers player_status being append-only, while the frozen base block is a convention with no test.

Config-driven mismatch becomes possible if a future change makes channel positions depend on the config: channels inserted or reordered in or before the base block, or a new gated group placed ahead of existing channels.

A change to a channel's content is a separate route, not covered by the current-config argument above: it breaks content assumptions silently under any config. The behavior goldens (once built) will catch unintended obs-build changes, but after a deliberate, accepted change the goldens are updated to match, and the analysis-side assumptions break with no signal.

## Affected code

Where stage-1 obs assumptions live today:

- `ARMY_CH` in `army_derivers.py`: computed once at import time from the default obs config. Used only by the `ARMY_OBS` deriver, which is used only by the `elim_head_debug` spec. `ARMY_OBS` also carries content assumptions: the army planes are constant over the board (it reads one corner cell), fog-independent, and scaled by 1/1000.
- The probe tasks `lowest_army` and `army_regression_task` compute army-channel indices from their own `dense_history_n` value.
- The `GROUND_TRUTH_OBS_CFG` comment in `frame_table.py` says to pin `obs_cfg` to the checkpoint's run when comparing against a model dump. This is a convention in a comment, not a check.

## Possible fixes

These are options, not decisions:

- Compute channel indices in stage 2, from the supplied obs config, instead of at import time from defaults. This requires `get_obs_channel_indices` to take an `ObsConfig` (it already has a TODO for that). The related open question about resolving gated-group channel indices is in [7.12-3 §2](../2026-07/7.12-3-pre-build-item-1-investigation.md).
- Let stage-1 structures declare which channels they read, and check the declaration against the supplied config when a run starts.
- A lighter check: for each assumed index, look up the channel name at that index in the supplied config and compare it to the expected name.

All three options cover only channel positions. Assumptions about channel content (how values are scaled or written) evade every check listed here.

## Relation to the confounds framework, checkpoint configs, and the goldens

Analysis numbers are an artifact class already covered by the [confounds framework](../confounds-framework.md) (probe scores, head-vs-rule gaps, dump-derived metrics). The two docs are complementary: the framework is about the comparability of artifacts across a change boundary, while this doc is about errors in fresh analyses built entirely on current code. One case is a candidate extension to the framework, per its own completeness note: for derivers that read the obs tensor directly, the obs build is part of the analysis-number pipeline, so an obs change that re-encodes the same information (marked in the framework's surface table as not changing number meaning) can still change what obs-derived analysis numbers mean.

The mechanical half of a pin-to-checkpoint fix comes from the checkpoint-config work: once the obs config is recorded in the checkpoint, "this table was built with the checkpoint's obs" is checkable. The behavior goldens catch unintended obs-build changes only. Deliberate changes pass through them (see "Current status").
