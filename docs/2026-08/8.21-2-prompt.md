**Useful software-engineering framings**

Some general software-enginneering wisdom that has been very helpful during this cleanup:

- Look for key interfaces and function signatures that don't feel right.
- Follow the trails and peel away the layers, as we try to make the interfaces are very clean and tight.
- Carve out mini-abstractions that feel conceptually strong and coherent, given the architecture of the related modules (and the broader codebase).
    - E.g. Type with dataclasses! Loose dicts are opaque and provide a much weaker conceptual handle. They are more work up front, but less token-efficient in the long run.
- Don't treat existing code as a stridt contract that must be adhered to.
    - Interfaces for older code should get a fresh look when we touch them.
    - Especially if they haven't received much attention in a while. Or if the new code we are working on isn't fitting together nicely with the older pieces
    - E.g. Have we been circling a design question a few times? is something feel trickier or more confusing than expected? This may indicate that some existing code needs to be improved.

These ideas are generally useful for software work and are good things to keep in mind. Please do so as we work.
