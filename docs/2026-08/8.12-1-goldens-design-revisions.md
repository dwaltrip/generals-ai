## 1. Workflow posture and notes

### Testing posture

- Not all commits need to have a fully passing test suite. E.g. A commit on a feature branch, while we are in the middle of implementing something.
  - Otherwise, in general, we aim to have all tests passing. Once an implementation is complete, barring some specific reason, the tests should be passing.
- Implications for goldens workflow
  - While working on something, it's OK to make commits with the golden tests not passing (e.g. you made a change to obs / targets).
  - The enforcement and system properties provided by the goldens apply **when the test suite is run**.
  - It's test-based, by design. This enables flexibility. We choose when to run the tests and what subset to run. We still get the benefits from other parts of the test suite even if the golden tests are left broken for some duration.

### Mid-development regen

- This is necessary for the goldens to catch additional unexpected changes during continued development. Running the regen tool turns the goldens guard "back on".
  - The printed extent and other info (channel summary report?) can be a helpful check to know if the impact of the new change matches what we expected.
- This is a normal usage of the regen tool and doesn't require checking out a previous commit (unlike the post-implementation workflow, see below).
- The resulting boundary record can be considered temporary / placeholder / throwaway. This allows for the entire test suite to be green without having to precisely lock in a boundary during development. Those temp records can be fixed later when the branch is finished.

### Post-implementation workflow

Satisfying the goldens, after finishing a new feature on some branch:

- Restore golden references to the pre-branch state (usually `main`), delete any temporary placeholder records, then do the "normal" flow: run regen + write a real record(s).
  - If multiple records are desired, check out the appropriate commits, starting with the earliest, and build up the record set.
- The real record(s) should precisely capture the exact set of changes from the branch.

**Useful framings**

Framing 1: *"Done iterating / new feature complete" is a deliberately fuzzy concept.*

By definition, this requires human judgment: Does the feature solve the problem? Is it good enough? Am I happy with this functionality? This is normal and expected, matching the inherent fuzziness of development.

Framing 2: *Collapsing mid-branch entries at land is like collapsing DB migrations on a feature branch before merging.*

### Other notes

- Regen tool should probably create a new record as a mostly-empty skeleton using a template that we setup.
  - Doesn't need to do any fancy work to pre-fill fields, especially not for anything that requires judgment or human interpretation / description.
  - Anything dead-simple should be pre-filled, e.g. the current date. Probably also the list of channels that changed.

## 2. Bootstrap plan for the build

Sequencing plan (same as before):

- Fixture selection is deferred to near the end of the build.
- Until then the build tests against randomly picked fixtures passing the training eligibility filters (`bc/filters.py`).

**New fixture plan, during implementation**:

1. Zero fixtures initially.
2. First bless runs against committed, temporary fixtures.
3. Replace throwaway fixtures later on with proper fixture selection.

Golden tests with zero fixtures do not assert anything, so they will pass by default. This allows the goldens to not block the test suite from being green in this initial phase.

Once we have implemented enough to actually do a "bless" (i.e. when walk + report writers + regen tooling exist), the plan is to produce and commit 2–3 temporary fixtures. Then we can run the machinery for the first time, producing the first (temporary) bless: committed fixtures, references, environment record, registry entries.

Finally, when we do the proper selection later on, the throwaway fixtures will be replaced and the bless re-run. The end state will be a clean set of fixtures, golden references, registry entries. There won't be any trace of the temporary fixtures.

This plan resolves the main issues with deferring fixture selection (identified this session):

- The goldens machinery can run in its designed form during the rest of the implementation work. Committing the temp fixtures removes any "dev seam" complexity, skip-vs-fail dual semantics, etc.

This plan is quite analogous to processes described in section 1: mid-development regen / post-implementation workflow. The steps are basically the same, it's just here we are additionally replacing the entire set of fixtures, not just placeholder boundary records.

Repo size cost of committing interim fixtures:

- ~1-2 MB permanent git packfile growth.
  - **Daniel's read**: This feels totally fine.
- This is a rough estimate: fixtures ~150–250 KB each + references + mid-build re-bless churn. 
- If we squash the commits containing the interim fixtures, this cost goes away entirely. (This requires that the interim blobs never end up reachable from a kept ref: squash-merge, then delete the branch, including any pushed copy.)

## 3. Mental model refresher (config points vs. boundaries)

**An "obs config point" is a column in the coverage matrix.**

It is a concrete config stored on disk. Each (config point, fixture) pair is a cell of the matrix, with its own set of committed golden references. A single cell is about ~10 KB on disk (the hash npz + channel summary) plus about ~0.25 seconds of test runtime. These numbers come from the goldens probe per-cell sizes and walk times (doc 7.15-1).

**An obs boundary is an event** .

The event: an implemented behavior change which (1) fired the goldens and (2) was re-blessed + recorded in the ledger (with a boundary record).

The cost is growth in the git packfile data. During re-bless, the committed references for every affected cell in the coverage matrix are replaced. As these files are mostly composed of hash data, git cannot compress the new versions against the old ones, and the packfile permanently grows. This is in contrast to the size of the repo files outside of `.git/`.

Stated in terms of what they track and represent:

- The registry's config point axis tracks which past states are still runnable (and guarded).
- The ledger tracks the boundary events over time.

Iterating heavily without gating produces many boundaries and zero new config points.

### Config points: gated vs. ungated changes

*a.k.a. where do new obs config points come from?*

With a behavior change, there are two options: gate the change or accept the boundary.

A **gated change** doesn't affect previous behavior. Those code paths are preserved, and older checkpoints and config points are not impacted.

- A new config shape only needs a config point entry in the registry if it is "occupied" with a model checkpoint that we "care about". This means that both:
  - A training run ran with that specific config.
  - We've selected the resulting checkpoints as worth being able to run later, whether for eval or additional analysis.
- The earlier docs stated this more strictly: guard every occupied config point, and defer all pruning to the one-time route-1 policy work. That strictness was solely so we could feel extra safe deferring the policy work. We treat "guard the occupied points" as the ambition rather than a hard rule. Only a handful of older checkpoints will actually matter moving forward, and we can decide which ones when it matters.

An **ungated change** is a boundary. One or more code paths that produced previous behavior are now "broken", in that they do not preserve the previous behavior.

Older checkpoints and configs are impacted. A checkpoint may now:

- Not be runnable at all (throws an error, e.g. channel mismatch).
- Run differently than it did during training.
- Produce different numbers in a given analysis.
- And a variety of other possible impacts (these are described in great detail in the confounds framework doc).

The boundary record in the ledger will describe the specific impact for the given change. Old behavior is accessible via git history (the "rerun recipe").

*Continuity note: 7.12-1 calls this the "gate-or-accept" fork.*

**Existing obs config points**

Both existing obs points arose from gated changes:

- Addition of player status channels behind config field `player_status_channels`. Branch `elim-head-fix-obs-bugs`, committed ~6/18.
- Switch from fp32 obs to fp16 obs, behind config field `obs_dtype`. Branch `obs-data-starvation-debug`, committed ~6/07.

## 4. Repo size cost notes

### Fresh look at actual numbers

Basic formula:

```
git packfile growth over time ≈ boundary count × config points touched × fixture count × ~7 KB per cell. 
```

The ~7 KB figure (for each cell in the coverage matrix) is an estimate.

A cell's references are two files: the hash npz (measured at ~5.5 KB) and the channel summary (estimated around ~4.5 KB). Together this gives the ~10 KB standing size, per cell. This is also what the *first* bless adds to the packfile (both files enter git as new blobs at full size), matching the on disk size.

A re-bless costs less, ~7 KB per cell. The hash npz is effectively random bytes to git, so each new version costs the full ~5.5 KB. The channel summary is plain text, so git stores the new version as a delta against the old blob, and only the changed lines cost anything (~1–2 KB typically). If a re-bless moves every channel's stats (should be uncommon), then the summary delta approaches full size. This is the worst case, ~10 KB per cell.

We will get real numbers for the channel summary when we build the report writer.

As one can see in the formula, these costs scale linearly with the fixture count.

On "config points touched": a change that only affects gated behavior (e.g. inside an optional channel group) only requires re-blessing the specific config points that enable that behavior.

#### The cost of an obs config point

The one-time cost, when a config point is first added, is the initial bless of its new cells: ~10 KB per cell (see above). With 10 fixtures, we would be adding 10 new cells to the coverage matrix, for a total one-time cost of 10 × 10 KB = 100 KB.

The ongoing cost is the packfile growth from each re-bless that touches the config point: ~70 KB at a 10-fixture basis, ~35 KB at 5 fixtures. (The probe measured ~200 KB for a full re-bless of one config point at a 30-fixture basis; the smaller numbers are extrapolations using the ~7 KB per-cell estimate.)

The one-time and ongoing costs are nearly the same thing (new reference blobs entering the packfile, one per coverage matrix cell). The differences are in how those blobs affect the size of the git repo:

- ~10 KB initially (matching the on-disk size) vs.
- ~7 KB for a re-bless (the non-hash content is partially reduced to the delta)

We can prune fixtures or config points to trim the ongoing cost for any re-blesses moving forward. This doesn't affect the accumulated packfile growth from older commits. This is a "policy decision" for what checkpoints we care about and what goldens coverage we want.

#### The cost of targets goldens

Targets-side churn is comparatively small: the references are roughly ~15–25 KB per fixture (mostly measured, see below).

There are four targets config points (`core`, `alive_only`, `time_bin`, `next_death`), but unlike obs, the committed references don't multiply per config point. We commit one bundle of reference values per fixture, holding the union of the target arrays, and the registry's keyset table records which arrays each config point guards. So targets reference size scales with fixture count only.

The 7.15 probe measured the targets arrays at 8.6–16.5 KB per fixture (these full arrays are still the current design). It also measured the legality-mask stack at 20–190 KB per fixture as full arrays, which is now superseded: the mask is stored as per-frame hashes instead (~4.5 KB). The ~15–25 KB bundle estimate is those measured targets arrays plus the mask hashes. We can confirm the real bundle size at first bless.

#### "Big picture" example scenario (Daniel's hypothetical)

Let's look at a "before → after" picture (e.g. after some months of development in the project).

- Fixture count: 5 → 10
- Obs config points: 2 → 10
- Boundaries landed during this period: 20

Assuming linear and independent growth in each factor, the math:

- Boundary churn: the matrix grows from 10 cells (2 × 5) to 100 cells (10 × 10). Averaging the matrix size across the period, each boundary touches ~48 cells. 20 boundaries × ~48 cells × ~7 KB ≈ 6.7 MB.
- Initial blesses: each of the 100 end-state cells is blessed once, at ~10 KB each ≈ 1 MB.
- Committed fixture data: 10 fixtures × ~200 KB ≈ 2 MB.

Total: ~10 MB of accumulated git packfile growth when we reach the "after" state. Moving forward from there, each boundary costs 100 cells × ~7 KB ≈ 700 KB.

Daniel's reaction: This is better than expected and looks pretty fine to me.

Note: This is fully dependent on the ~7 KB estimate for the cost of a single cell in the coverage matrix.

### Fixture subsets per config point: dropped

Fixture subsets per config point: the ability to specify that a goldens config point only applies to a subset of the goldens fixtures.

In Daniel's opinion, this seems a bit thorny to implement and maintain. Based on the math in the "big picture" scenario above, I now think there is also little benefit.

Takeaway: we don't need this. We will do the simple thing for the first cut: every fixture applies for all config points.

### The size-budget test: demoted to optional

Earlier docs listed a size-budget test as a shipped item ("ceilings as tests"). On review, the picture is less compelling: the largest size concern is git packfile growth, which a test over the working tree can't measure (7.10-2 noted this caveat).

We demote it to an optional build-time item, not critical. If included, it could be a simple one-off script that prints size info, or a small test asserting a ceiling on the on-disk size of the goldens directory.

### More misc notes..

- The ongoing costs occur when a new boundary or config point lands for real. Mid-branch re-blesses are uncommitted or collapse at land, so a month of heavy iteration landing as three batches costs three re-blesses.


## 5. Supersession pointers

### Targets reference layout

One bundle npz per fixture + registry keyset table; the legality-mask stack is stored as per-frame hashes, not full arrays — revises 7.15-2 §2's "full arrays at all frames … including the legality-mask stack."

### Reference-fidelity notes

*Stated properly (Daniel's correction this session)*

**obs references → hashes**

The reasoning is that full arrays are quite large and we were able to design the hashes such that we get the important information along with the large repo size cost savings (changed-ticks, changed-channels, and channel summary report). It's a compromise that should hit the sweet spot.

**targets references → full arrays**

For two compounding reasons: (1) they are small relative to obs so the cost is much lower (2) they may be trickier to debug and so the extra fidelity could pay off.

As the cost is lower, the extra fidelity could be worth it. This can be revisited if needed.

One additional note: the upcoming elim-head work is expected to fire the targets goldens frequently and intentionally, so the per-value diffs should get regular use in the near term.

**legality mask → hashes**

These are size-constrained like obs. The plan is sparser tick-level attribution (saves more space). This code is quite simple and should be very stable. We should not be spending much size budget on these.

### Obs config point name update

We gave "content descriptive" names to the two obs config points:

- `fp16_player_status_on` — the current era: fp16 obs, player status channels on.
- `fp32_pre_player_status` — the era before the status channels existed: fp32 obs, no status channels. This is the config that `LEGACY_OBS_CFG` pins for old checkpoints.

Role-based names like "default" were rejected. The registry pins explicit values precisely so that the live default can move away from them. A point named "default" would become mislabeled in every reference path, test ID, and ledger entry on the day the live default changes.

The asymmetry between "on/off" and "pre/post" is deliberate. The name `pre_player_status` is for a config that predates the player status knob entirely.

The registry design sketch describes where and how, in general, config point names will be used.

### Regen tool notes

Notes for the regen tool design work, from this session:

- **Increment vs. net extent.** The printed extent is the same diff mechanically, but it means different things at different moments. Mid-branch, it's the increment since the last regen ("did this change move what I expected?"). At land, after restoring references to the pre-branch state, it's the net extent of the whole branch (what the real record is written from). The report could state which baseline it diffed against.
- **Initial bless vs. changed.** When regen writes references for an entry that had none (a new config point or fixture), that's not a fire. The report should present "newly blessed, no baseline" differently from "changed". Relevant when adding a gated variant, and during the bootstrap phase.
- **Skeleton record creation.** Covered in section 1: regen creates the boundary record as a mostly-empty skeleton from a template, pre-filling only dead-simple fields (date, changed-channel list).
