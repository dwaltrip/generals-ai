## 1. Workflow posture and notes

### Testing posture

- Not all commits need to have a fully passing test suite. E.g. A commit on a feature branch, while we are in the middle of implementing something.
  - Otherwise, in general, we aim to have all tests passing. Once an implementation is complete, barring some specific reason, the tests should be passing.
- Implications for goldens workflow
  - While working on something, it's OK to make commits with the golden tests not passing (e.g. you made a change to obs / targets).
  - The enforcement and system properties provided by the goldens apply **when the test suite is run**.
  - It's test-based, by design. This enables flexibility. We choose when to run the tests and what subset to run. We still get the benefits from other parts of the test suite even if the golden tests are left broken for some duration.

### Mid-development regen

- This is necessary for the goldens to catch additional unexpected changes during continued development. Running the regen tool turns the goldens guard "back on".
  - The printed extent and other info (channel summary report?) can be a helpful check to know if the impact of the new change matches what we expected.
- This is a normal usage of the regen tool and doesn't require checking out a previous commit (unlike the post-implementation workflow, see below).
- The resulting boundary record can be considered temporary / placeholder / throwaway. This allows for the entire test suite to be green without having to precisely lock in a boundary during development. Those temp records can be fixed later when the branch is finished.

### Post-implementation workflow

Satisfying the goldens, after finishing a new feature on some branch:

- Restore golden references to the pre-branch state (usually `main`), delete any temporary placeholder records, then do the "normal" flow: run regen + write a real record(s).
  - If multiple records are desired, check out the appropriate commits, starting with the earliest, and build up the record set.
- The real record(s) should precseily capture the exact set of changes from the branch.

**Useful framings**

Framing 1: *"Done iterating / new feature complete" is a deliberately fuzzy concept.*

By definition, this requires human judgment: Does the feature solve the problem? Is it good enough? Am I happy with this functionality? This normal and expected, matching the inherent fuzziness of development.

Framing 2: *Collapsing mid-branch entries at land is like collapsing DB migrations on a feature branch before merging.*

### Other notes

- Regen tool should probably create a new record as a mostly-empty skeleton using a template that we setup.
  - Doesn't need to any fancy work to pre-fill fields, especially not for anything that requires judgment or human interpretation / description.
  - Anything dead-simple should be pre-filled, e.g. the current date. Probably also the list of channels that changed.

## 2. Bootstrap plan for the build

Sequencing plan (same as before):

- Fixture selection is deferred to near the end of the build.
- Until then the build tests against randomly picked fixtures passing the training eligibility filters (`bc/filters.py`).

**New fixture plan, during implementation**:

1. Zero fixtures initially.
2. First bless runs against committed, temporary fixtures.
3. Replace throwaway fixtures later on with proper fixture selection.

Golden tests with zero fixtures do not assert anything, so they will pass by default. This allows the goldens to not block the test suite from being green in this initial phase.

Once we have implemented enough to actually do a "bless" (i.e. when walk + report writers + regen tooling exist), the plan is to produce and commit 2–3 temporary fixtures. Then we can can run the machinery for the first time, producing the first (temporary) bless: committed fixtures, references, environment record, registry entries.

Finally, when we do the proper selection later on, the  throwaway fixtures will be replaced and re-run the bless. The end state will be a clean set of fixtures, golden references, registry entries. There won't be any trace of the temporary fixtures.

This plan resolves the main isuses with deferring fixture selection that were described in previous desing sketches:

- The goldens machinery can run in its designed form during the rest of the implementation work. Comitting the temp fixtures removes any "dev seam" complexity, skip-vs-fail dual semantics, etc.

This plan is quite analogous to processes described in section 1:  mid-development regen / post-implemetnation workflow. The steps are basically the same, it's just here we are additionally replacing the entire set of fixtures, not just placeholder boundary records.

Repo size cost of comitting interim fixtures:

- ~1-2 MB permanent git packfile growth.

## 3. Mental model refresher (config points vs. boundaries)

**An "obs config point" is a cell in the coverage matrix.**

It is a concrete config stored on disk. A single config point is about ~10 KB in size (the hash npz + channel summary) plus about ~0.25 seconds of tes truntime cost. These numbers come from the goldens probe per-cell sizes and walk times (doc 7.15-1).

**An obs boundary is an event** .

The event: an implemented behavior change which (1) fired the goldens and (2) was re-blessed + recorded in the ledger (with a boundary record).

The cost is due to uncompressble growth in the git packfile data. During re-bless the, the committed references for every cell in the coverage matrix are replaced. As these files are mostly composed of hash data, git cannot compress the diff and the packfile permanently grows. This is in contrast to the size of the repo files outside of `.git/`.

Stated in terms of what they track and represent:

- The registry's config point axis tracks which past states are still runnable (and gaurded).

- The ledger tracks distinct eras. Iterating heavily without gating produces many boundaries and zero points.

### Config points: gated vs. ungated changes

*a.k.a. where do new obs config points come from?*

With a behavior change, there are two options: gate the change or accept the boundary.

A **gated change** doesn't affect previous behavior. Those code paths are preserved, and older checkpoints and config points are not impacted.

- A new config shape only needs a config point entry in the registry if it is "occupied" with a model checkpoint that we "care about". This means that both:
  - A training run ran with that specific config.
  - We've selected the resulting checkpoints as worth being able to run later, whether for eval or additional analysis. 

An **ungated change** is a boundary. One or more code paths that produced previous behavior are now "broken", in that they do not preserver the previuos behavior.

Older checkpoints and configs are impacted. A checkpoint may now:

- Not be runnable at all (throws an error, e.g. channel mismatch).
- Run differently that it did during training.
- Produce different different numbers in a given analysis.
- And a variety of other possible impacts (these are described in great detail in the confounds framework doc).

The boundary record in the ledger will describe the specific impact for the given change. Old behavior is accessible via git history (the "rerun recipe").

*Continuity note: 7.12-1 calls this the "gate-or-accept" fork.*

## 4. Repo size cost notes

### Fresh look at actual numbers

Basic formula:

```
git packfile growth over time ≈ boundary count × config points touched × fixture count × ~7 KB per cell. 
```

The ~7 KB churn-per-cell figure is an estimate: the hash npz  is ~5.5 KB (measured), plus an a bit more for the channel-summary text delta (estimated).

We expect the channel-summary text to almost certainly be smaller than the hash npz, but we will see when we build the channel summary report writer.

The growth scales linearly with the number of fixtures.

#### The cost of an obs config point

The one-time cost, when first added, is the size of the golden references (the hashes) for the obs output from the initial bless. We will have one set of reference values for each new cell in the coverage matrix.

Estimated size of a single obs golden references: ~10 KB.

With 10 fixtures, we would be adding 10 new cells to the coverage matrix. This gives a total one-time cost of 10 x 10 kb = 100 KB.

The ongoing cost is each the packfile growth for from re-bless that touches that config point. 70 KiB at a 10-fixture basis (probe-measured), ~35 KiB at 5 fixtures.

We can prune fixtures or config points to trim the ongoing cost for any re-blesses moving forward. This doesn't affect the accumulated packfile growth from older commits. This a "policy decision" for what checkpionts we care about and what goldens coverage we want.

### Targets reference layout

### Reference-fidelity notes

*Stated properly (Daniel's correction this session)*

**obs references → hashes**

The reasoning is that full arrays are quite large and we were able to design the hashes such that we get the important information along with the large repo size cost savings (changed-ticks, changed-channels, and channel summary report). It's a compromise that should hit the sweet spot.

**targets references → full arrays**

For two compounding reasons: (1) they are small relative to obs so the cost is much lower (2) they may be trickier to debug and so the extra fidelity could pay off.

As the cost is lower, the extra fidelity could be worth it. This can be revisited if needed.

**legality mask → hashes**

These are size-constrained like obs. The plan is sparser tick-level attribution (saves more space). This code is quite simple and should be very stable. We should not be spending much size budget on these.
