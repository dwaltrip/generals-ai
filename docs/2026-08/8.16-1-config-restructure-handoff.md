# Config restructure — handoff

*Date: 2026-08-16. The goldens build's second working session. It focused on a restructure of how the dataset is configured, done ahead of the registry work. This doc carries forward-looking content and key facts we've noted so far.*

## Restructure goals and current status

- The motivation: get the long-term training-config shapes in place now, so the goldens work and everything after builds on them rather than churning through them later.
- The path threads around the genuinely complex pieces. The config version bump and the first real checkpoint-config migration are deliberately deferred, while most of the new long-term shapes still land now. The shapes, and the design discussions that produced them, clarified the config landscape considerably: a stronger foundation for the first cut and beyond.
- We improve interfaces as we hit them, deferring some to the parked list. EmitSpec itself emerged mid-refactor, out of questioning whether alive_mask emission was really a targets-config concern.
- The restructure changes no behavior: each step is verified by comparing the dataset's emitted bytes against a baseline dump.
- It merges three pieces that had been planned separately:
  - Small refactor that decouples `alive_mask` emission from elim head ("next action" in [8.15-3](8.15-3-goldens-build-handoff.md)),
  - Updating the dataset constructor to take TargetsConfig instead of the corresponding loose args (follow-up 1 from [7.28-2](../2026-07/7.28-2-targets-config-design-sketch.md), pulled forward),
  - A minimal implementation of the new "metrics config".
- The steps:
  - Step 0 *(done)*: the baseline byte dump.
  - Step 1 *(done)*: the config package groundwork. The new classes and their builders, the stored-block move, tests. Nothing consumes the new classes yet.
  - Step 2 *(next)*: the dataset constructor switches to EmitSpec, and every construction site updates.
  - Step 3: a design note for the new config concepts and a look at doc de-staling.
- Steps 0 and 1 are squashed into one commit on `goldens-1st-cut-build`.
- After step 3, we return to the goldens sequence where 8.15-3 left it: registry transcription, environment record sketch, checkpoint sweep, tier-2 sketches.

## The baseline dump (step 2's comparison target)

- `tmp/dataset-refactor-byte-compare/hashes_prerestructure.json` holds byte hashes of the dataset's emitted samples (4 configs, 600 samples each), taken just before the restructure began.
- Step 2 is verified against it: after the constructor change, rerun the dump and compare. The expectation is ALL IDENTICAL.
- The file is local-only (tmp/ is gitignored). If it's missing, regenerate it from the pre-restructure commit.

- The dump script (`dump_dataset_bytes.py`) builds the dataset with the old constructor kwargs. Step 2 includes updating its per-config kwargs to build EmitSpecs.

## Step 2: IterableDataset constructor update

- The constructor becomes `(samples, seed, spec: EmitSpec, shuffle_buffer_size, prof_sink)`. The spec replaces `obs_cfg` and five loose kwargs: `include_frame_info`, `elim_bin_edges`, `elim_head_variant`, `emit_alive_mask`, `unsafe_attach_sim_frame`.
- Inside the dataset, three things change:
  - The elim ctx is built when the spec needs it (alive_mask on, or a variant set).
  - alive_mask emission is gated by `spec.alive_mask` alone. Today the gate is `elim_ctx is not None`.
  - `encode_frame` receives the spec plus the ctx. (Current lean, to finalize while building.)
- The signature change breaks every construction site at once, so all sites move in one commit:
  - `build_dataloader` in train.py, via the builders (`metrics_cfg_from` + `emit_spec_from`).
  - The in-loop val chain (train.py -> `run_val` -> `iter_val_forward`). The two elim params threaded through are replaced with an emit spec instance.
  - The offline `capture_val_frames`, via `emit_spec_for_model`.
  - `dataset_args_for` in analysis/probes/core.py maps FrameNeeds to a spec. Its current logic and comment describe the old coupling and will need to be rewritten.
  - Analysis sites (`bc/analysis/`): family_a_victim_baselines.py, victim_gap_distribution.py, elim_head_debug.py (all next_death, passing `alive_mask=True` to keep their emitted keys unchanged), and argmin_toy/spec.py.
  - Tests, via a `make_emit_spec(**overrides)` helper in the test tier. Defaults: the test obs config, core targets, all flags off.
  - fq FrameTable specs. Before starting, grep the live fq specs' `dataset_kwargs` for all six old kwargs. `_archive/` stays stale.
- This work doesn't change any emitted keysets.
- Planned verification is the dump comparison and the existing test suite.

## Notable decisions this session

- **Two layers: run config, and per-build contracts.** This was a key insight. The config layer is TrainConfig and its sub-config blocks: stored, run-scoped, holding recipe values and measurement requests. EmitSpec serves a layer beyond that: it is derived from the train config values and then passed to the dataset instance (which now doesn't even need the config instance). In fact, we can have multiple emit specs per run: the train and val datasets get different specs (frame_info differs).
- **alive_mask has two flags with different meanings.** `EmitSpec.alive_mask` states a fact: the key is emitted. `MetricsConfig.include_alive_mask` records a request: measurement wants the column. The builders connect them: emitted = requested, or the variant is time_bin (whose loss needs the mask). Why it landed this way:
  - 8.15-3 recorded "the OR reading was considered and set aside", but that line (and its related implications) had been written without a detailed analysis or careful ratification from Daniel (attention was spent elsewhere). In this session Daniel pushed more on that, leading to the current combined shape of TargetsConfig + MetricsConfig + EmitSpec. This structure ended up being a much cleaner cut.
  - We isolate the "OR" derivation to the builders. Then downstream code can simply receive and use the derived value.
- **next_death keeps emitting alive_mask.** Last session checked who consumes it in next_death dumps. Nothing in training does. The consumers are offline analyses: masking probs down to the alive players, and the convenience of reading everything from one file. Modest but real, and the column is cheap. The fq toolkit can also recompute it offline, so nothing is locked in. Conclusion: the column is a genuine measurement request, and prod next_death runs get it through the derived request. This keeps every occupied keyset unchanged, which is what lets step 2 expect byte-identical output.
- **The derivation rules.**
  - The request derivation in `metrics_cfg_from` (`variant is not None`) is a placeholder until the request has a stored field. At the version bump it is deleted here and copied into the migration as the historical fill.
  - The OR in `emit_spec_from` is permanent.
  - The edges gating in `targets_cfg_from` (edges flow only for time_bin) becomes a field read at the bump.
- **EmitSpec's home is temporary.** It is currently a top-level `bc` file at `bc/emit_spec.py`. Its future home will likely be a `bc.walk` module (or similar).
- **One version bump, not two.** 7.28-2's second follow-up (elim fields move into a stored targets sub-config) and MetricsConfig's storage happen in a single bump session. Done separately, the two bumps would touch the same field twice, and one migration would have to know about the other's placement. The delicate part of the migration: `include_alive_mask`'s historical value is per-checkpoint (`arch.elim_head_variant is not None`), a conditional fill. Filling it with a constant is exactly the mistake the schema test warns about. The `TODO(config-bump)` markers in the code mark every site the bump touches.
- **`dump_val_frames` stays a flat TrainConfig field until the bump.** Its consumers read the flat field today, and moving it early buys nothing.
- **A consequence for the registry transcription.** [8.12-2](8.12-2-registry-design-sketch.md)'s targets config points still store one flat dict per point. The registry loader now turns each dict into a TargetsConfig plus the alive-mask field of an EmitSpec, and the goldens-side EmitSpec sets `frame_info=False, sim_frame=False` explicitly.

## Parked items that left no trace in the code

- **Deriving the OR's variant condition from the aux-head specs.** The hardcoded `"time_bin"` in `emit_spec_from` states a fact that belongs to the aux-head spec: this variant's loss consumes alive_mask. Eventually a per-spec declaration should carry it, feeding both the OR and EmitSpec's validation. One constraint shapes the options: the config layer can't import the spec registry (torch), so it's either a torch-free spec-metadata module or a structural cross-check test (a natural sibling of the goldens' planned elim cross-check). Trigger: the next variant that needs the mask, or the goldens structural-test work.
- **Extracting LossConfig from loss.py.** loss.py imports torch, which is the reason `train_config` can't be imported torch-free and the config package uses TYPE_CHECKING-only annotations. A torch-free LossConfig module dissolves that. Related to the no-inline-defaults direction in 7.28-2 §7.
- **Splitting migrations out of stored_block.py.** Worth doing once enough real migrations accumulate that the frozen-history entries deserve their own file. Realistically the second or third bump.
- **Moving obs_config/model_config/train_config into bc/config.** The intent is recorded in the package's ckpt-cfg-refactor-note. Mechanical whenever wanted, roughly 60 files of import rewrites.
- **A finishing pass over the whole restructure diff**, after step 2 lands.
- **A pre-existing pyright error** at tests/config/test_config_schema.py:64 (`_check_dataclass` narrowing). It appeared only because the test file moved into the paths a scoped pyright run covers. The code itself is untouched.

## Working style for the rest of the cut

- Comments and docstrings stay very minimal (Daniel's directive). The reasoning: he had observed the repo's legacy verbose style spreading into new drafts by imitation, despite the standing guidance (e.g. global CLAUDE.md). Expanding a sparse comment later is much cheaper than trimming a verbose one with questionable details. Calibration continues through the cut.
- Two calibration outcomes from the first review round:
  - Docstrings state the evergreen contract. Important, transitional status notes go in a `# NOTE` or `# TODO` comment near the top of the file.
  - Session-note references in code need a clear forward-looking purpose. For example, Daniel deleted a reference of the form "Session note MM.DD defines this", which was trivia about provenance (soon to be historical).
