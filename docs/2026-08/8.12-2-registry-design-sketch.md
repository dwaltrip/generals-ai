# Registry design sketch

*Date: 2026-08-12*

This doc records the design for the goldens registry: the piece that enumerates what the golden tests guard. It settles the registry's form (a data-oriented Python module), its contents, the interface its consumers use, and the targets reference layout.

It continues the "registry and config discipline" design work from 7.28-2 (which settled TargetsConfig) and the 7.28-3 handoff. The general design revisions from the same working sessions live in a companion note ([8.12-1](8.12-1-goldens-design-revisions.md)): workflow posture, the build bootstrap plan, repo size costs, and the reference-fidelity rationales.

## Intro

**Scope background**

In the [confounds framework](../confounds-framework.md)'s vocabulary, the code that trains, runs, or measures the model divides into **surfaces**: obs build, targets, loss, metric definitions, and so on (see the table in §1 of the framework doc). This first cut of golden tests is focusing on two surfaces:

1. the obs build path
2. the targets (training labels)

The registry is designed to describe what is covered by the golden tests, and more importantly, provide programmatic enumeration over the pieces of a guarded surface.

**Key constraints (inherited from earlier sketches)**

- The golden test path is numpy-only, no torch imports. The test compares the bytes produced by the prod code against the stored bytes (the blessed references). The logic is that every library in the prod computation path can impact these bytes, and so we reduce the risk of numeric comparison problems by excluding pytorch.
- Stored configs are explicit dicts. They should not be constructed using "default values" from the code. This avoids the issue where defaults changing unintentionally change the comparison done by the golden tests.

*(Aside: There is an argument here to entirely avoid having "defaults" for TrainingConfig and all of the sub configs... We touched on this in 7.28-2 §7)*

## 1. What the registry needs to do

The registry has five concrete jobs. Each design choice below traces back to one or more of them.

1. **Detect changes**: For each cell of the coverage matrix (a specific config point and fixture), a behavior change in the guarded surfaces should automatically trigger a "tripwire" that alerts us to the issue. This is the primary purpose of the golden tests.
2. **Force coverage**: An addition to a guarded surface (a new elim variant, a new gated channel group) should cause a test failure, until it is registered and blessed.
3. **Keep blesses reviewable**: "We now guard X" and "we re-blessed Y" should be readable diffs. The identity of every guarded config point is explicit in the file.
4. **Keep the consumers in agreement**: The golden tests, the regen tool, the parity test, and the structural tests reference a single source of truth that defines what is guarded. This ensures that the different parts of the system remain in sync.
5. **Guard the apparatus itself**: Where possible and reasonable, we set up simple guardrails to help ensure the golden tests function as intended (e.g. orphaned reference files, drifted literals).

## 2. The registry module

The registry is a data-oriented Python module. First, some terms.

* Config point: a named, concrete config for a guarded surface, stored as an explicit dict.
* Coverage matrix: the full set of guarded configurations and code execution paths. It's the cross product of the list of config points and the list of fixtures.
* Registry entry: a single cell in the coverage matrix.

The module has two halves. One is the stored data: the config point dicts, the fixture list, and the keyset table. The other is a code layer that serves as the shared, canonical way to interact with that data. This module will own the logic for how to expand the config points and fixtures into a list of "registry entries", do needed validation (e.g. convert stored dicts into config instances, asserting correctness), derive reference paths, and so on. The aux-heads registry (`training/bc/aux_heads/registry.py`) has some similar patterns we can learn from.

The module will compute the list of registry entries on demand. The obvious alternative, storing the fully expanded entry list as plain data, has several downsides: there would be significant repetition, it would be hard to review manually, and it would require brittle, on-going manual maintenance anytime a fixture or config point changes.

In general, registry data will be stored as plain values only, without any imported symbols or computed values. This plain data can be stored in code (Python literals, plain dicts, etc) or in pure data files (e.g. JSON or some other format). Either way, the data should probably be in the same folder as the registry code.

The question of storing the data in code or pure data files can be resolved during the build. A few brief pros and cons: Python literals can carry comments, don't require loading from a file, and could benefit from typechecking. JSON files, on the other hand, by definition consist of plain values and are more resistant to accreting abstractions.

## 3. Contents

### Config points

This is the list of the known "occupied" config points (occupied = existing checkpoint with this config). In the registry, we could store this data as plain dicts with literal values.

**Format sketch:**

```python
OBS_CONFIG_POINTS = {
    "fp16_player_status_on":  {"dense_history_n": 5, "obs_dtype": "fp16", "player_status_channels": True},
    "fp32_pre_player_status": {"dense_history_n": 5, "obs_dtype": "fp32", "player_status_channels": False},
}

TARGETS_CONFIG_POINTS = {
    "core":       {"elim_enabled": False, "elim_variant": None,         "elim_bin_edges": None},
    "alive_only": {"elim_enabled": True,  "elim_variant": None,         "elim_bin_edges": None},
    "time_bin":   {"elim_enabled": True,  "elim_variant": "time_bin",   "elim_bin_edges": [10, 20, 40, 80, 160, 320, 640]},
    "next_death": {"elim_enabled": True,  "elim_variant": "next_death", "elim_bin_edges": None},
}
```

Notes:

- The dicts are plain values, analogous to pure JSON: no imported symbols or computed values (note: the config class currently converts lists to tuples on init).
- The `time_bin` edges still need confirmation against real checkpoints (see §9).
- The obs config point names (and the reasoning behind them) are covered in 8.12-1 §5.
  - In short, we are using "content descriptive" names, chosen manually by Daniel. The names aren't a formulaic construction (e.g. from the fields), but they still convey what is distinct about the config point. 
  - In the current first cut design, these config point names will appear in reference paths, pytest test IDs, regen output, and ledger entries (this may not be a complete list).
- The `fp32_pre_player_status` dict carries an equality assert against prod's `LEGACY_OBS_CFG` symbol, so the golden and the checkpoint-load path cannot drift apart (7.12-1 §6). This assert will be implemented as a standalone test (see §7 for why it can't run at registry import).

### Fixture list

Each fixture is a `(replay, perspective slot)` pair. We can have a short note explaining its purpose and what it covers (or possibly just rely on code comments).

```python
FIXTURES = [
    FixtureRecord(replay_id="rB3x9k2", slot=4, note="interim random pick, replaced at selection"),
    ...
]
```

### Targets keyset table

This table defines which pieces of data (the specific arrays from the references) need to be guarded for each config point:

```python
TARGETS_KEYSETS = {
    "core":       ("mask", "action_target", "is_pass", "value_target"),
    "alive_only": ("mask", "action_target", "is_pass", "value_target", "alive_mask"),
    "time_bin":   ("mask", "action_target", "is_pass", "value_target", "alive_mask", "elim_bin_target"),
    "next_death": ("mask", "action_target", "is_pass", "value_target", "alive_mask",
                   "next_elim_target", "next_elim_dt", "next_elim_removal_dt", "present_mask"),
}
```

The table has two consumers: the targets golden tests use it to slice the reference bundle per config point, and the parity test uses it as the expected keyset for prod's emitted target dict.

### Registry entries

Registry entries are a simple cross-product of fixtures and config points. We are not implementing custom rules or logic for individual config points. Each config point runs against the full list of fixtures. 

Previously, we considered supporting fixture subsets for config points (dropped, see the note in 8.12-1 §4).

### Coverage guidance

*Continuity note: previous sketches called this "the guard rule".*

A short note kept beside the registry data. This is documentation to help us catch certain types of config changes which aren't automatically guarded.

The structural tests are designed to provide automatic warning of a config point coverage gap, wherever it is possible and reasonable to do so. But not all changes can be easily detected automatically. Automatic checks can only verify regions of the config space that are programmatically enumerable. The most obvious case is the set of fields on the config objects.

A second case is when we have concrete interfaces for interacting with a specific slice of config space. Two examples exist today: (1) `aux_heads.REGISTRY` declares all variants of the elim-head and enables iteration over them and (2) `GATED_CHANNEL_GROUPS` is a recently created abstraction for optional channel groups that also supports enumeration.

In contrast, the cases that are harder to check automatically:

- Config fields are identical but a scalar value has been tweaked (e.g. `dense_history_n` going from 5 to 10).
- A config has a new combination of previously used values.

A conservative baseline is to guard every occupied config point (softened from a hard rule to an ambition in 8.12-1). The guidelines below interpret the baseline. They help clarify when config values count as meaningfully different behavior and should get their own config point.

Guidelines for when config values map to different behavior:

- Enum-valued knobs: The assumption is that each value triggers a different code branch. This means that each value needs to be guarded. So every occupied value should correspond to a config point.
- Scalar knobs: We can try to break up the range of values into "regimes". If this is feasible, then we should have one config point per regime. Here, the mental model is more nuanced: different regimes will map to either different code paths explicitly or two different "categories" of behavior under the same code path.
  - E.g. for dense_history_n, two regimes may be appropriate: 0 vs. greater than 0.
- New combinations of existing values could be treated similarly to scalar knobs. By default, we assume the existing coverage carries over and can add dedicated config points as needed.

This "coverage guidance" documentation can be a reference and reminder during development to help ensure we don't accidentally introduce a coverage gap for a surface guarded by the goldens. The guidelines are currently a tentative sketch. They will likely need tweaking over time.

## 4. The interface

### Two access levels

- **Config points level**: the raw dicts and their validated config instances. Consumers: the parity test and the structural tests.
- **Entries level**: the expanded (config point × fixture) list. Consumers: the golden tests and regen.

The registry module owns the conversion from plain "data dicts" into actual instances of config dataclasses (ObsConfig, TargetsConfig). During this conversion it can apply the strict-keys assert (the dict's keys must match the config class's fields exactly). Other consumers should not construct their own config instances (bypassing the assert).

### Registry entry records

We define two entry types below, as obs and targets entries differ in config type, reference resolution, and comparison logic. They also feed separate test functions.

```python
@dataclass(frozen=True)
class FixtureRecord:
    replay_id: str
    slot: int      # perspective slot: the stable identity
    note: str      # purpose note

    @property
    def id(self) -> str:
        return f"{self.replay_id}-s{self.slot}"    # e.g. "rB3x9k2-s4"


@dataclass(frozen=True)
class ObsEntry:
    point: str                # "fp16_player_status_on"
    cfg: ObsConfig            # validated instance
    fixture: FixtureRecord
    ref_path: Path            # references/obs/<point>/<fixture id>.npz


@dataclass(frozen=True)
class TargetsEntry:
    point: str                # "core" | "alive_only" | "time_bin" | "next_death"
    cfg: TargetsConfig
    keys: tuple[str, ...]     # this point's slice of TARGETS_KEYSETS
    fixture: FixtureRecord
    bundle_path: Path         # references/targets/<fixture id>.npz (shared by the four points)
```

Notes:

- With pytest parametrization, the test ID for an entry will be `f"{cfg_point}-{fixture.id}"`, e.g. `test_obs_golden[fp16_player_status_on-rB3x9k2-s4]`.
- The fixture's identity is the slot (the player's seat in the game). The meta npz indexes perspectives by position `k`, and the slot-to-k resolution happens at fixture load time.
- Paths are resolved during expansion and held as fields. Consumers should not construct their own paths.

### Filepath derivation for `fixtures` and `references`

The registry owns the filepath scheme for the `fixtures/` and `references/` sub-directories. These will likely end up in a centralized `tests/goldens` directory.

```
fixtures/<replay_id>.npz  +  <replay_id>.meta.npz     (shared by that replay's fixtures)
references/obs/<cfg_point>/<fixture id>.npz
references/targets/<fixture id>.npz
```

The broader goldens directory layout is not tied to the registry design, but we did sketch a first draft of this while working on the registry. A possible layout is:

- Everything lives under a single `packages/training/tests/goldens/` directory
- It contains the registry module, the actual golden tests (e.g. `pytest` tests), `fixtures/`, `references/`, the environment record, and the ledger.

This is just a sketch, listed here in case it's a helpful starting point. During the build, the question should be given a fresh look.

## 5. The consumers

**The golden tests.** There is one test function per golden type, parametrized over the registry entries. For each entry, the test loads the fixture, runs the walk or target functions using the entry's config instance, and compares the results against the stored references (hash equality for obs, keyset slices of the references bundle for targets). If an entry's reference files are missing, the test fails with an "unblessed, run regen" message.

**The regen tool.** Regen iterates the same entry list, writing references instead of comparing. The key property is that regen and the tests consume the same expansion from the same module (job 4). Regen's own design is a separate upcoming session: the CLI shape, and the fire report (the printed summary of what changed when goldens fire). Accumulated notes for it are in 8.12-1 §6.

**The parity test.** (*described in detail in 7.23-1 §4*) This test runs committed fixtures through both the prod `IterableDataset` codepath and the goldens-side computation, comparing the emitted sample-dict values byte-for-byte, along with their dtypes. It runs over all config points. The expected keys and dtypes come from the keyset table and the goldens-side dtype declarations.

**The structural tests.** These are small self-checks (job 5). Each one guards a specific failure mode:

- *Elim cross-check*: every variant in `aux_heads.REGISTRY` has a targets config point. This is what forces coverage for a new variant: the cross-check fails until a config point is registered for it, and the new point's golden tests then fail as unblessed until the references are blessed. The alternative would be auto-generating the entries from the aux-heads registry. We checked the code and this doesn't work: a new variant has no stored config yet, and if it brings a new knob, even the shape of its config is unknown. There is nothing to auto-generate.
- *Gated-group check*: every gated obs channel group is enabled in at least one registered obs config point. This is the obs-side counterpart of the elim cross-check.
- *Orphan check*: no reference files exist on disk outside the enumerated entry paths.
- *Bundle-contents check*: each fixture's targets bundle holds exactly the union of the keysets. This ensures the targets bundle and the keyset table stay in sync.

**The mutation test.** This test perturbs an in-memory copy of a walked frame and asserts that the hash comparison fires. It consumes any one entry plus the shared comparison logic. It is the standing proof that the tripwire mechanism works (7.15-2 §4).

## 6. Targets reference layout

The four targets config points overlap heavily in what they emit: the four core keys don't depend on the config, so their bytes are identical across all four points, and `alive_mask` is identical across the three elim points. Storing complete per-point reference files would commit the same bytes four times, and a change to a core target function would rewrite four files per fixture.

Instead, we store the union once per fixture, and the keyset table records which arrays each point guards:

```
references/targets/rB3x9k2-s4.npz
    mask_frame_hashes    [T] uint64      (the legality mask, guarded by hash)
    action_target        [T] int64
    is_pass              [T] bool
    value_target         []  int64
    alive_mask           [T, 8] bool
    elim_bin_target      [T, 8] int64
    next_elim_target, next_elim_dt, next_elim_removal_dt, present_mask
```

A point's golden test compares its keyset slice against the bundle. The `mask` key is the one exception to full-array comparison: the bundle stores per-frame hashes of the legality-mask stack, and the test compares by hash for that key. Regen computes the union once per fixture and writes one file, producing each array with the stored config of a point that guards it.

The reasoning for which references are full arrays and which are hashes, and the sizes involved, live in 8.12-1 (§4 and §5).

## 7. Asserts and where they live

**At registry import** (pure checks, no file IO): the strict-keys assert on every stored dict, and config validation.

**As standalone tests** (they do IO or need heavier imports): the orphan check and the bundle-contents check (both read the filesystem), the mutation test, and the legacy equality assert. The last one has to be a test because of imports: it compares against `LEGACY_OBS_CFG`, and that symbol lives in `checkpoint.py`, which imports torch. The registry module must stay importable from the numpy-only golden test path, so that assert runs in the torch-side test tier.

## 8. Build-time decisions

Most of these are small picks to make while building. One is worth spelling out: the shape of the keyset table literals. This choice also determines how the targets test knows to compare the `mask` key by hash. The two options:

- (a) Bare key tuples, with the targets test special-casing the `mask` key as hash-compared. This is the simplest option, and it works fine while the mask is the only hashed key.
- (b) Per-key metadata, e.g. `key -> (dtype, full | hashed)`. This is more structure, but the parity test's expected dtypes could then live in the same table, instead of as separate declarations.

Current lean: start with (a), and move to (b) if a second hashed key appears or if the dtype declarations would benefit from a more structured home.

The small picks, listed without elaboration: the TargetsConfig module path, whether `value_target` is stored as a scalar or per-frame, how the regen CLI imports the registry module, and the wording of the coverage guidance note.

## 10. Dropped items

**Vacancy check (cut from the structural tests).** This check would have asserted that every config point yields at least one entry. With per-point fixture subsets dropped (8.12-1 §4), the entry list is a pure cross-product, so a point can only be vacant when `FIXTURES` itself is empty. That case is already visible: pytest reports an empty parameter set as a skip, and the orphan check fires on any reference files left unclaimed. If per-point subsets are ever added, this check should be added along with them.
