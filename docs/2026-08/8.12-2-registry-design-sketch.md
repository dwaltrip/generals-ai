# Registry design sketch

*Date: 2026-08-12*

This doc records the design for the goldens registry: the piece that enumerates what the golden tests guard. It settles the registry's medium, its contents, the interface its consumers use, and the targets reference layout.

It continues the "registry and config discipline" design work from 7.28-2 (which settled TargetsConfig) and the 7.28-3 handoff. The general design revisions from the same working sessions live in a companion note ([8.12-1](8.12-1-goldens-design-revisions.md)): workflow posture, the build bootstrap plan, repo size costs, and the reference-fidelity rationales.

Constraints inherited from the earlier sketches:

- The golden test path is numpy-only, no torch imports. Blessed references compare live bytes to stored bytes, so every library in the computation path is part of what can churn or break them (7.28-2, footnote).
- Stored configs are explicit dicts, never built from live defaults. The golden test path reads no live default anywhere (7.28-2 §3).

## 1. What the registry needs to do

Five concrete jobs. Each design choice below traces back to one or more of these.

1. **Detect**: for every occupied config point, on every fixture, a behavior change in the guarded code must fire a test.
2. **Force coverage**: new guarded surface (a new elim variant, a new gated channel group) must fail loudly until it is registered and blessed.
3. **Keep blesses reviewable**: "we now guard X" and "we re-blessed Y" should be readable diffs, and the identity of every guarded point is explicit in the file.
4. **Keep the consumers in agreement**: the golden tests, the regen tool, the parity test, and the structural tests must share one definition of what is guarded. If regen and the tests ever enumerate differently, we can bless things the tests don't check, or the tests can demand things regen never writes.
5. **Guard the apparatus itself**: the machinery's own failure modes (a vacant config point, orphaned reference files, drifted literals) must also be loud.

## 2. Medium: a data-oriented Python module

The registry is one Python module. The reviewable content is literals (config point dicts, the fixture list, the keyset table), and a few lines of code provide what plain data cannot express:

- Expanding the points and fixtures into the entry list that the tests and regen consume.
- Converting stored dicts into validated `ObsConfig` / `TargetsConfig` instances (with the strict-keys assert).
- Deriving reference paths.

A pure data file (JSON/TOML) would still need all of that code somewhere next to it. Keeping the data and its mechanisms in one module gives every consumer a single import and a single definition of what is guarded (job 4). The aux-heads registry (`training/bc/aux_heads/registry.py`) is the in-repo precedent for this shape.

Two genuine virtues of a real data file are kept, converted into small tests (see §7):

- A data file cannot reference live symbols or compute values. The JSON round-trip test enforces the same property on the module's literals.
- With a data file, what you review is what runs. The orphan check covers the gap that expansion code introduces: an expansion bug that silently drops entries leaves orphaned reference files behind, and the check makes that loud.

## 3. Contents

### The config points

Six occupied config points, stored as plain dicts with every field explicit:

```python
OBS_POINTS = {
    "fp16_player_status_on":  {"dense_history_n": 5, "obs_dtype": "fp16", "player_status_channels": True},
    "fp32_pre_player_status": {"dense_history_n": 5, "obs_dtype": "fp32", "player_status_channels": False},
}

TARGETS_POINTS = {
    "core":       {"elim_enabled": False, "elim_variant": None,         "elim_bin_edges": None},
    "alive_only": {"elim_enabled": True,  "elim_variant": None,         "elim_bin_edges": None},
    "time_bin":   {"elim_enabled": True,  "elim_variant": "time_bin",   "elim_bin_edges": [10, 20, 40, 80, 160, 320, 640]},
    "next_death": {"elim_enabled": True,  "elim_variant": "next_death", "elim_bin_edges": None},
}
```

Notes:

- The dicts are JSON-pure: no imported symbols, no computed values, and lists rather than tuples (the config class converts to a tuple at construction). This is what the round-trip test enforces.
- The `time_bin` edges still need confirmation against real checkpoints before the entry is blessed (see §9).
- The obs point names and the reasoning behind them are covered in 8.12-1 §5. The names appear in reference paths, pytest test IDs, regen output, and ledger entries, so they are frozen at creation: renaming one breaks all of those at once.
- The `fp32_pre_player_status` dict carries an equality assert against prod's `LEGACY_OBS_CFG` symbol, so the golden and the checkpoint-load path cannot drift apart (7.12-1 §6). The assert lives test-side (see §7).

### The fixture list

Each fixture is a (replay, perspective slot) pair with a purpose note:

```python
FIXTURES = [
    FixtureRecord(replay_id="rB3x9k2", slot=4, note="interim random pick, replaced at selection"),
    ...
]
```

The note is prose, not machinery. It says why the fixture is in the set ("covers neutralize + long fog span"), and during the build phase it marks the interim fixtures as interim.

### The targets keyset table

Which arrays each targets config point guards:

```python
TARGETS_KEYSETS = {
    "core":       ("mask", "action_target", "is_pass", "value_target"),
    "alive_only": ("mask", "action_target", "is_pass", "value_target", "alive_mask"),
    "time_bin":   ("mask", "action_target", "is_pass", "value_target", "alive_mask", "elim_bin_target"),
    "next_death": ("mask", "action_target", "is_pass", "value_target", "alive_mask",
                   "next_elim_target", "next_elim_dt", "next_elim_removal_dt", "present_mask"),
}
```

This table does double duty: it defines what each targets point guards (§6), and it is what the parity test checks prod's emitted sample dict against (§5).

### The pairing

Entries are the pure cross-product: every config point runs on every fixture. There are no per-point fixture subsets (that option was considered and dropped, see 8.12-1 §4).

### The guard rules

Beside the registry, a short comment or small dict declares the rules for which config points get guarded (7.12-1 §6). Enum-valued knobs guard every occupied value. Scalar knobs guard one point per regime (e.g. `dense_history_n`: 0 vs. greater than 0). The "guard the occupied points" posture is an ambition rather than a hard rule (8.12-1 §3).

## 4. The interface

### Two access levels

- **Points level**: the raw dicts and their validated config instances. Consumers: the parity test and the structural tests.
- **Entries level**: the expanded (config point × fixture) list. Consumers: the golden tests and regen.

The dict-to-instance conversion happens once, inside the registry module, with the strict-keys assert (the dict's keys must match the config class's fields exactly). No consumer can construct its own instance from a stored dict and bypass the assert.

### The entry records

Two entry types rather than one with optional fields: obs and targets entries differ in config type, reference resolution, and comparison logic, and they feed separate test functions.

```python
@dataclass(frozen=True)
class FixtureRecord:
    replay_id: str
    slot: int      # perspective slot: the stable identity
    note: str      # purpose note

    @property
    def id(self) -> str:
        return f"{self.replay_id}-s{self.slot}"    # e.g. "rB3x9k2-s4"


@dataclass(frozen=True)
class ObsEntry:
    point: str                # "fp16_player_status_on"
    cfg: ObsConfig            # validated instance
    fixture: FixtureRecord
    ref_path: Path            # references/obs/<point>/<fixture id>.npz


@dataclass(frozen=True)
class TargetsEntry:
    point: str                # "core" | "alive_only" | "time_bin" | "next_death"
    cfg: TargetsConfig
    keys: tuple[str, ...]     # this point's slice of TARGETS_KEYSETS
    fixture: FixtureRecord
    bundle_path: Path         # references/targets/<fixture id>.npz (shared by the four points)
```

Notes:

- The test ID for an entry is `f"{point}-{fixture.id}"`, e.g. `test_obs_golden[fp16_player_status_on-rB3x9k2-s4]`.
- The fixture's identity is the slot. The meta npz indexes perspectives by position `k`; the slot-to-k resolution happens at fixture load time.
- Paths are resolved during expansion and held as fields. Consumers never construct paths.

### Path derivation: the registry's only layout contract

The registry owns the path scheme for exactly two subtrees:

```
fixtures/<replay_id>.npz  +  <replay_id>.meta.npz     (shared by that replay's fixtures)
references/obs/<point>/<fixture id>.npz
references/targets/<fixture id>.npz
```

The broader directory layout is not registry contract. As loose context, a first-pass picture (to be settled at build time): everything lives under a single `packages/training/tests/goldens/` directory, holding the registry module, the goldens' own test files, `fixtures/`, `references/`, the environment record, and the ledger.

## 5. The consumers

**The golden tests.** One parametrized test function per golden type, over the entries. Per entry: load the fixture, run the walk / target functions using the entry's config instance, compare against the stored references (hash equality for obs, keyset slices of the bundle for targets). Missing reference files fail as "unblessed, run regen".

**The regen tool.** Iterates the same enumeration, writing references instead of comparing. The critical property is that regen and the tests consume the same expansion from the same module (job 4). Regen's own design (CLI shape, fire report) is a separate upcoming session; accumulated notes are in 8.12-1 §6.

**The parity test.** Consumes the points level. It runs a committed fixture through the prod `IterableDataset` and through the goldens-side computation, and compares every emitted sample-dict key byte-for-byte, per config point (7.23-1 §4). The keyset table (plus the declared dtypes) defines what the test expects, and the refactor's `TrainingSample` + `to_dict` is the prod side. This test is torch-side and does not share the goldens' numpy-only constraint.

**The structural tests.** Six small self-checks (job 5), each guarding one named failure mode:

- *Elim cross-check*: every variant in `aux_heads.REGISTRY` has a targets config point. This is the coverage-forcing mechanism for new variants: the check fails until the point is registered, and the new point then fails as unblessed until it is blessed. The cross-check form is deliberate, rather than auto-generating entries from the aux-heads registry: a new variant has no stored config yet (if it brings a new knob, even the shape of its config is unknown), so there is nothing to auto-generate. We confirmed this from the code.
- *Gated-group check*: every gated obs channel group is enabled in at least one registered obs point. The obs-side twin of the cross-check.
- *Vacancy check*: every config point yields at least one entry. Guards against a typo'd point name or a pairing bug producing zero entries. The unblessed failure cannot catch this case: it needs entries to exist. During the bootstrap phase the fixture list is empty and every point is trivially vacant, so the check applies only when `FIXTURES` is non-empty.
- *Orphan check*: no reference files exist on disk outside the enumerated entry paths.
- *Bundle-contents check*: each fixture's targets bundle holds exactly the union of the keysets. No array can sit in a bundle unguarded, and no guarded key can be missing from it.
- *Round-trip check*: every stored dict survives a JSON round-trip unchanged, keeping the literals inert data.

**The mutation test.** Perturbs an in-memory copy of a walked frame and asserts the hash comparison fires. It consumes any one entry plus the shared comparison logic, and is the standing proof that the tripwire mechanism works (7.15-2 §4).

## 6. Targets reference layout

The four targets config points overlap heavily in what they emit: the four core keys are config-independent and byte-identical across all four points, and `alive_mask` is identical across the three elim points. Storing complete per-point reference files would commit the same bytes four times, and a change to a core target function would rewrite four files per fixture.

Instead, we store the union once per fixture, and the keyset table (§3) records which arrays each point guards:

```
references/targets/rB3x9k2-s4.npz
    mask_frame_hashes    [T] uint64      (the legality mask, guarded by hash)
    action_target        [T] int64
    is_pass              [T] bool
    value_target         []  int64
    alive_mask           [T, 8] bool
    elim_bin_target      [T, 8] int64
    next_elim_target, next_elim_dt, next_elim_removal_dt, present_mask
```

A point's golden test compares its keyset slice against the bundle. The `mask` key is the one exception to full-array comparison: the bundle stores per-frame hashes of the legality-mask stack, and the test compares by hash for that key. Regen computes the union once per fixture (each array from its owning point's stored config) and writes one file. The bundle-contents check (§5) asserts the stored arrays are exactly the keyset union, so the bundle and the table cannot drift apart.

The reasoning for which references are full arrays and which are hashes, and the sizes involved, live in 8.12-1 (§4 and §5).

One dtype note: the goldens-side assembly declares the reference dtypes to match prod's sample dict, and the parity test verifies the match (a 7.28-2 cut-list item). If the keyset table grows per-key dtype metadata, that declaration has a natural home there (see §8).

## 7. Asserts and where they live

**At registry import** (pure checks, no file IO): the strict-keys assert on every stored dict, config validation, and the vacancy check.

**As standalone tests** (they do IO or need heavier imports): the round-trip check, the orphan check and the bundle-contents check (both read the filesystem), the mutation test, and the legacy equality assert. The last one is forced test-side by imports: it compares against `LEGACY_OBS_CFG`, which lives in `checkpoint.py`, which imports torch. The registry module must stay importable from the numpy-only golden test path, so that assert runs in the torch-side test tier (next to the parity test).

## 8. Build-time decisions

One decision has real design content. The keyset table's literal shape and the mask comparison dispatch are a single choice:

- (a) Bare key tuples, with the targets test special-casing the `mask` key as hash-compared. Simplest, and fine while mask is the only hashed key.
- (b) Per-key metadata, `key -> (dtype, full | hashed)`. More structure, but it gives the parity test its dtype declarations in the same table instead of a second home.

Current lean: start with (a), move to (b) if the dtype pinning wants a declared home or a second hashed key appears.

The rest are small picks to make while building, listed without elaboration: the TargetsConfig module path, `value_target` stored as scalar vs. per-frame, how the regen CLI imports the registry module, and the wording of the guard-rules declaration.

## 9. Queued empirical checks

Both are needed before the real registry entries are written, and can be done in one sweep over the existing checkpoints:

- Confirm the `time_bin` edge tuple against the checkpoints that actually trained with the elim head (7.28-2 §3 flagged this).
- The occupancy sweep for the 6.07 to 6.18 window: fp16 landed 6.07 and the status channels 6.18, so checkpoints trained in between would occupy a third obs combination (fp16, no status channels). Check whether any exist and matter. The "ambition, not hard rule" posture applies (8.12-1 §3).

## 10. Deferred idea: specs declare their target keys

The keysets are hand-written literals, and the parity test's check against prod emission works precisely because the two sides are independent (deriving the keysets from the aux-head specs would make the comparison circular). A future refinement that keeps the independence: each `AuxHeadSpec` declares its emitted keys (a `target_keys` attribute next to `encode_targets`), and a cross-check asserts the declaration matches the registry literal. Keys would then be authored once, next to the code that emits them, while the registry stays the frozen side of the contract. Trigger: the next new variant, or keyset drift becoming a worry in practice.
