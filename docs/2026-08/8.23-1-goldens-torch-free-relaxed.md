# Goldens: the torch-free requirement is relaxed

*Date: 2026-08-23. Records the decision to relax the numpy-only requirement on the golden test path, and the reasoning behind it. The technical findings that support the decision are in the companion appendix, [8.23-2](8.23-2-torch-numerics-appendix.md). The rest of this session's build work is in the session handoff note, [8.23-3](8.23-3-goldens-build-handoff.md).*

## 1. The change

The goldens design required the golden test path to be numpy-only: no torch imports anywhere between the fixture data and the reference bytes ([7.12-1 §3](../2026-07/7.12-1-behavior-goldens-first-cut-v2-overview.md), [8.12-2](8.12-2-registry-design-sketch.md) intro, [7.28-2](../2026-07/7.28-2-targets-config-design-sketch.md) footnote). That requirement is relaxed. Torch-free is now a nice-to-have for the emission goldens (the obs and targets goldens). It will probably not be achieved in the first cut, and no work is committed to it.

What the goldens do instead: they call the same emission code the training dataset uses (the emission tail split out of `encode_frame`, described in [8.23-3](8.23-3-goldens-build-handoff.md)), and that code is allowed to import torch. Two small guards accompany it: an assert that torch's thread count is pinned to 1, and a small numeric canary (appendix §4).

The guards are not the safety argument. The safety argument is that the emission tail contains no floating-point reductions. Its torch content is `torch.from_numpy` (a zero-copy view of the numpy array) and `torch.tensor(scalar, dtype=...)` (a deterministic conversion). Neither computes anything, so neither can change the bytes. The guards catch future drift away from that property.

The natural point to revisit torch-free is after the aux-heads module refactor and its related cleanups (for example, splitting `LossConfig` out of `loss.py`). Those cleanups would make torch-free cheap, because the aux-head dispatch is the only torch import the emission tail would have left. Revisiting is a check-in, not a commitment. Torch-free stays optional even then.

Nothing else in the goldens design changes: the pinned machine, the environment record (the `uv.lock` hash), exact hash comparison, and the reference formats all stay as they are. `walk.py` stays torch-free on its own merits (the fq toolkit's import-graph rule, [7.23-1 §6](../2026-07/7.23-1-walk-infra-design-sketch.md)), and the config modules stay torch-free as ordinary hygiene (the parked `LossConfig` extraction in [8.16-1](8.16-1-config-restructure-handoff.md) exists for the same reason).

## 2. Why the requirement was weaker than it looked

The docs gave three reasons for torch-free. Re-read with the actual code path in view:

**"Every library in the computation path can move the reference bytes."** True in general, but not for what torch does in our path. Torch's role in the emission code is wrapping: zero-copy views and scalar conversions. No torch kernel runs between the numpy target functions and the bytes, so a torch upgrade cannot move bytes it never computes. The docs treated "torch is imported" and "torch computes" as the same thing.

**"It is nearly free, because the guarded math is already pure numpy."** True for the kernels (`build_obs`, the target functions, `build_mask`), false for the layer that assembles them. `encode_frame`, `spec_for`, and `AuxHeadSpec.encode_targets` all import torch, and `encode_targets` returns torch tensors. Meeting the requirement at that layer is what it cost during the first-cut build: the gutted `aux_heads/__init__`, the asserts exiled to the torch test tier, the duplicated target assembly in the goldens' `compute_targets`, and the aux-head dispatch split that sharing the assembly code would have needed. §5 looks at that bill more carefully.

**"Computation-path purity can't be verified, but import purity can be checked mechanically."** This one holds up completely, and it is the real argument. Without an import boundary, "no torch computation touches the bytes" is a belief kept alive by code review. One casual `.mean()` added a year from now would silently make the references depend on torch, and nobody would notice until a torch upgrade fired the goldens with no attribution story. The import boundary is a ratchet: checkable by a test, immune to drift. But its value accrues over years, and this project retires in about six months. Over that window, with one developer and a handful of changes touching emission code, the ratchet protects very little.

Two points the docs did not make, both of which weaken the case further:

- **The system already detects dependency churn without torch-free.** The environment test fires on any lockfile change, torch included. And the goldens themselves answer "did this bump move the bytes?": bump, run the suite on the pinned machine, green means no. That workflow is the same one-line re-stamp with or without torch in the path. Torch-free buys attribution (at fire time, torch cannot be a suspect), not detection.
- **The isolation was leakier than advertised.** The golden tests run in the same pytest process as every other test, and other tests import torch. Whatever process-level state torch's import sets exists in that process regardless of what the goldens modules import. Real isolation would need the goldens to run in their own process, which was never the design.

One asymmetry favored keeping the requirement: relaxing it later is trivial, while re-tightening it after torch has crept into the reference path is expensive. That only matters if re-tightening is ever wanted before retirement.

## 3. The mechanism, in one paragraph

Everything in the investigation reduces to one distinction. Elementwise operations (add, multiply, casts, comparisons, indexing, `digitize`) produce each output from one input, so they have no combining order and are bit-stable under every library, thread count, and version. Summing-class reductions (`sum`, `mean`, dot products, matmul, conv, softmax denominators) combine many values, float addition is not associative, and so the grouping of the additions changes the last bits. Everything that picks the grouping can change the bytes: thread count, SIMD blocking, the library's internal algorithm, and version bumps. The emission path has no floating-point reductions, which is the structural reason its bytes are stable. A model forward pass is reductions almost by definition, so its bytes are stable only for a fixed combination of library version, machine, thread count, and invocation recipe. Details and the worked example: appendix §1.

## 4. Key findings

Each finding is stated with how it was established. The appendix carries the setups, numbers, and caveats.

- **Thread count moves reduction bytes at our tensor size.** `torch.sum` over an obs-sized tensor (110×32×32) gives a different last bit at 1 thread than at 4 or 8. Any fixed thread count is fully deterministic. Torch's own defaults produce this split in practice: DataLoader workers run at 1 thread, and a test process runs at the core count. (Appendix §2.)
- **Switching the computing library moves bytes on its own.** At a fixed single thread, torch's sum and numpy's sum differ on a large tensor. Different internal blocking, same arithmetic. (Appendix §2.)
- **A model forward pass is bit-identical on the dev laptop at a fixed configuration.** GEMM output is identical across runs, across processes with different memory layouts, and across the BLAS thread-cap setting, with torch's threads pinned to 1. This re-validates 7.09-1's measurement of the real model, and explains why it holds and where its limits are. (Appendix §2 and §6.)
- **The residual same-version risks are all process-state risks.** Thread settings, a SIMD-dispatch environment variable, floating-point flags set at import time. None is load-dependent or time-random. A canary that checks the state at test time catches all of them before a golden is compared. (Appendix §4.)
- **Torch churns across upgrades materially more than numpy, but the cost is per upgrade.** Roughly one more torch upgrade is expected before the project retires, and a byte-moving change in the simple ops the emission path uses is unlikely even then. Expected heavyweight churn events on the horizon: about zero. (Appendix §5.)
- **The harms of torch math in the reference path are bounded.** The worst is loss of trust in fires: config-dependent fires that look like real behavior changes and that no recorded artifact explains. There are no missed detections, and no damage to checkpoints or recorded numbers. (Appendix §3.)

## 5. What the requirement actually cost

The refactoring pain that prompted this investigation was mostly not caused by the torch-free requirement. The goal driving the refactoring was for the goldens to call the same emission orchestration the training dataset uses, instead of re-implementing it. That requires splitting the emission tail out of `encode_frame` regardless, because `encode_frame`'s signature takes walk internals (`vis`, `state`, `bfs_cache`) that the goldens cannot supply. The split is most of the work.

Torch-free's actual increment is the aux-head encode extraction: two small numpy functions (the `time_bin` and `next_death` encoders, each one kernel call plus dict assembly) and a dispatch keyed on `ElimHeadVariant`. Dropping torch-free has its own costs: the thread pinning, the canary and its blessed constants, the doc supersessions, and permanently carrying the story that reference bytes depend on process state guarded by asserts. The two costs are similar. The decision rests on the reasoning in §2, not on cost.

## 6. Forward goldens

Forward goldens (guarding the model's forward pass) are deferred, and [7.09-1 §§4 to 6 and 8](../2026-07/7.09-1-behavior-goldens-design-sketch.md) remain their design. That design never assumed torch-free. Its comparison policy (exact comparison on the pinned CPU platform with threads at 1) is what this investigation re-validated.

Two things are worth keeping for when that tier is built:

- Every torch upgrade should be expected to fire every forward golden. 7.09-1 handles this with scheduled re-blesses and a fire-time classification against measured sensitivity margins.
- The run-time state canary from this investigation fills a gap in that design: 7.09-1 pins the thread count by procedure but has nothing that checks the pin held.

If torch causes trouble later, the two tiers have separate remedies. The forward tier can use tolerance comparison, because its references are full values. The emission tier's remedy would be reviving torch-free. Appendix §6 has the detail.

## 7. If torch-free comes back

The emission tail is being written so that the option stays cheap: a typed return, obs and mask taken as inputs, dtypes finalized on the numpy side, and one generic torch-wrap site above it. Its only torch dependency is then the aux-head dispatch. After the aux-heads refactor severs that dependency, making the goldens numpy-only is roughly one subprocess test asserting torch is absent plus a few NOTE updates.

If torch causes trouble before then, two triggers would justify pulling the work forward: recurring torch-numeric false alarms that outlast the guards, or a second standing environment where torch churns across platforms. The goldens' numpy `compute_targets` from the first sketch is the fallback for that case, already written.
