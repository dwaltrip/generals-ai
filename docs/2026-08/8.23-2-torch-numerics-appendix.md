# Torch numerics and reference bytes: technical appendix

*Date: 2026-08-23. Technical appendix to [8.23-1](8.23-1-goldens-torch-free-relaxed.md), which records the decision to relax the goldens' torch-free requirement. This appendix holds the findings behind that decision: the mechanism that governs byte stability, what was measured, what goes wrong when torch math reaches reference bytes, the hidden process state that matters at a fixed version, upgrade churn, and the implications for forward goldens. It reads on its own, but the decision and its context live in the main note.*

## 1. The mechanism: elementwise operations versus reductions

**Elementwise operations** produce each output element from one input element (or one pair): add, multiply, casts, comparisons, `relu`, `np.digitize`, indexing. There is nothing to combine, so there is no combining order, and every implementation, thread count, and library version produces identical bits.

**Summing-class reductions** combine many elements into one: `sum`, `mean`, dot products, matmul (every output cell is a dot product), conv, the softmax denominator, norms. Combining N values takes N−1 additions, and each addition rounds to the float's precision. Float addition is not associative, so the grouping of those additions changes the rounding, which changes the last bits. The classic float32 example: `(1e8 + 1.0) + -1e8` gives `0.0`, because `1e8 + 1.0` rounds back to `1e8`, while `1e8 + (-1e8 + 1.0)` gives `1.0`.

Everything that picks the grouping can therefore change the bytes:

- the thread count (which decides how a tensor is chunked across threads, each thread summing its chunk before the partials are combined),
- the SIMD blocking strategy inside a kernel,
- the library's internal algorithm (torch and numpy group differently),
- version bumps (which rewrite kernels).

Max-class reductions (`max`, `argmax`) are exempt: picking a maximum does not round.

Three consequences for the goldens:

- The emission path (obs channels, legality mask, targets) consists of elementwise operations, indexing, comparisons, and `digitize`. It has no floating-point reductions. That is the structural reason its bytes are stable, whichever library wraps the results.
- A model forward pass is reductions almost by definition. Its bytes are stable only for a fixed combination of library version, machine, thread count, and invocation recipe.
- Hidden process state (thread settings, CPU flags) only matters where reductions exist.

## 2. Measurements

Platform: torch 2.12.0 on the M1 Max dev laptop. oneDNN (`torch.backends.mkldnn`) is unavailable in this build, OpenMP is available, and the default thread count is 8. Two throwaway scripts produced the numbers (§7).

### Thread-count demo

Setup: a float32 tensor with a wide dynamic range (`randn * 10**uniform(-3, 3)`, seed 0), summed with `torch.sum` at 1, 4, and 8 threads (`torch.set_num_threads`), twice per count, with `numpy.sum` as the control.

- Obs-sized tensor (110×32×32, 112,640 elements): the 1-thread torch sum matched numpy bit for bit. The 4-thread and 8-thread sums differed from it in the last bit. Two runs at any fixed thread count were always identical.
- 8-million-element tensor: three distinct bit patterns across 1, 4, and 8 threads. The 1-thread torch sum differed from numpy's, so at a fixed thread count, switching which library performs the reduction moves the bytes on its own.

The point: the same line of code on bit-identical input produced different bytes, and the only thing that changed was process state.

### GEMM probe

Setup: a 512×2048 by 2048×512 float32 matmul with `set_num_threads(1)`, each run in a fresh subprocess, output bytes hashed. Two runs under the default environment, then one each with `VECLIB_MAXIMUM_THREADS=1` and `=8` (the thread cap for Apple's Accelerate BLAS).

- All four hashes were identical.
- Each run was a separate process with a different heap layout, so the result also does not depend on buffer addresses.

Caveat: one op at one shape. Conv shapes were not probed.

## 3. What goes wrong if torch math enters the reference path

Nothing happens day to day. Every harm below waits for a specific event. Worst first:

1. **Thread-dependent flakiness.** A reduction in the path makes the reference bytes a function of thread count. Because any fixed count is deterministic, the suite passes for months while the configuration is stable, then fires the day the thread context shifts: a new machine, `pytest-xdist`, an import that calls `set_num_threads`, an `OMP_NUM_THREADS` in a shell. The fire looks exactly like a real behavior change, the environment record shows nothing changed (it stamps the lockfile, Python version, and architecture, not thread state), and no recorded artifact explains it. Torch's own defaults produce the split: DataLoader workers run at 1 thread, and a test process runs at the core count. This is the worst harm because a tripwire that fires for unexplained reasons stops being trusted, and an untrusted tripwire is useless long before it misses anything.
2. **Spurious fires at torch upgrades.** A version bump changes a kernel's blocking, bytes move, no code changed. The environment test fires (expected on any bump) and the goldens fire too (unexpected). That escalates the routine one-line re-stamp into the environment-boundary procedure from [7.15-2 §4](../2026-07/7.15-2-goldens-first-cut-scope-revision.md): rebuild the old environment, dump full arrays, classify churn versus real change, write a boundary record. The forced re-bless also pollutes the per-value diff history of the targets references, and a real change landing near the same time is masked inside the churn.
3. **A chronic attribution tax.** Every unexpected fire gains a second suspect. With numpy-only references, the suspect list at a fire is our own code.
4. **Quiet redefinition of the contract.** Subtle torch behaviors (fp16 conversion intermediates, subnormal flushing) would be frozen into the references without anything firing. Rare, and undetectable by construction if prod and goldens share the op.
5. **A narrower path to a second environment.** The deferred off-platform options in 7.15-2 rely on the exact-class channels hashing identically across machines, and torch kernels vary more across architectures than numpy's simple ops do.

Two things that do not go wrong:

- **No missed detections.** A false negative would need torch churn to exactly cancel a real code change, a measure-zero event. The tripwire's core guarantee survives torch entirely.
- **No damage to the science.** The references are measurement apparatus for the goldens system itself. Checkpoints, training curves, and eval numbers are untouched. Every harm above is bounded to the goldens' own reliability and maintenance cost.

The danger is specifically float-computing ops. Integer conversions and byte packing are bit-stable everywhere. The real invariant is "no float math beyond numpy touches the bytes", and the import ban was a coarse, checkable proxy for it.

## 4. Same-version hidden state, and the guards

Setting upgrades aside: what can move bytes at a fixed torch version on the pinned machine?

1. **Torch's intra-op thread count.** The one cause demonstrated to change bytes. Handled by `torch.set_num_threads(1)` plus an assert that the pin held.
2. **BLAS-backend threading.** `set_num_threads` governs torch's own thread pool. Matmul and conv route to a BLAS library (Accelerate here) with its own knobs. The GEMM probe showed no sensitivity, for one op and shape. Rated unconfirmed-low. For the emission path this is covered by a review rule: no matmul or conv-class ops in the emission code.
3. **The `ATEN_CPU_CAPABILITY` environment variable.** Selects the SIMD kernel variant, which changes reduction blocking even at 1 thread. Checkable by asserting it is unset.
4. **Floating-point environment flags (FTZ/DAZ, subnormal flushing).** Per-thread CPU state that some backends set for performance, so it depends on import order. It only affects values below about 1e-38 in float32, which our data rarely produces. A canary with a subnormal input detects it.
5. **Address-alignment-dependent blocking.** Theoretical. The GEMM probe's identical results across processes with different heap layouts is evidence against it.
6. **Torch's documented nondeterministic ops.** Mostly GPU atomics and scatter/index ops. A CPU forward pass of conv, linear, norm, softmax, and pooling uses none of them.

The property shared across the list: every residual risk is a function of process state. None is load-dependent or time-random. A state shift moves bytes deterministically, so a check that the state matches bless time catches all of them at once.

**The guards:**

- **Thread pin and assert.** `torch.set_num_threads(1)` at the goldens entry points (the test conftest, regen), and `assert torch.get_num_threads() == 1` inside the comparison module, so a missed pin fails loudly instead of silently changing bytes.
- **A numeric canary.** A few fixed computations (a wide-range reduction, a small GEMM, an op on a subnormal value) run when the comparison module is imported, with their bits compared to blessed constants. Any hidden-state drift fails the canary before a golden is compared, turning a mystery golden fire into a named "environment state changed" failure.
- **A review rule.** Reduction and elementwise ops only in the emission path. No matmul or conv-class ops.

Limits of the thread pin: it is discipline, not structure (every entry point must set it, which is what the assert is for), it does not govern all backend threading, and the pinned value becomes part of the references' identity without appearing in the environment record.

## 5. Upgrade churn: torch versus numpy

Torch moves bytes across versions materially more often than numpy does, for float math. Four mechanisms:

1. **Policy.** Torch's reproducibility docs state that results are not guaranteed bitwise-identical across versions, commits, or platforms. Its compatibility target is API and model-level tolerance, not bit stability.
2. **Kernel rewrite rate.** CPU kernels are restructured for performance continuously. The torch-versus-numpy single-thread difference in §2 is exactly the kind of internal blocking detail these rewrites move.
3. **Bundled backends.** Torch wheels bundle BLAS and DNN library versions that advance inside torch releases, so byte-moving changes arrive without anything in torch's own changelog looking numeric.
4. **Cadence.** Large releases roughly quarterly.

NumPy, by contrast: elementwise ops and casts are stable, and its reductions have used the same pairwise-summation algorithm for about a decade. Its one churn mechanism is the transcendental functions (`np.log`, `np.exp`), whose SIMD loops have changed across versions and platforms. That mechanism is live for us: the obs tensor has 16 log-scaled channels, and the goldens design already treats them as the churn-sensitive class (the exact/log channel split in 7.15-2, and the fp32 legacy point serving as a churn canary).

For the op classes the emission path uses, both libraries are stable. The difference lives entirely in reductions and transcendentals.

The cost model: churn cost is per upgrade, not per unit of time. No lockfile change means zero exposure, indefinitely. A single upgrade only fires the goldens if that release touched the specific kernels in the path, which most releases do not. Applied to this project: about one torch upgrade in the first six months and about six months of horizon left, so roughly one more upgrade is expected, and the expected number of heavyweight churn events is about zero. Upgrades are also elective and observable: bump, run the suite, let the goldens report whether anything moved, and accept or roll back within minutes. The caveat is a forced upgrade (new OS or Python support, an MPS bug fix), which is unlikely on this horizon.

## 6. Forward-tier implications

Forward goldens are deferred, and [7.09-1 §§4 to 6 and 8](../2026-07/7.09-1-behavior-goldens-design-sketch.md) remain their design. Three findings bear on it.

**The comparison policy is re-validated.** 7.09-1 §6 specifies exact comparison on the canonical platform (CPU, fp32, threads pinned to 1) and measured the real 4.2M-parameter model's forward as bit-identical across processes. §2's probes explain why that holds and where its edges are: reductions are deterministic at a fixed thread count, this build's GEMM is insensitive to the BLAS thread cap and to buffer addresses, and oneDNN (whose algorithm-selection heuristics were the main same-version worry) is not present in this build. At a fixed version and machine, with threads pinned and a fixed invocation recipe (eval mode, `no_grad`, fixed batch shape, contiguous layout), a CPU forward pass is expected to be bit-stable run to run.

**The upgrade story differs from the emission tier.** A forward pass is reductions everywhere, so any kernel change anywhere breaks byte equality, and every torch upgrade should be expected to fire every forward golden. 7.09-1 anticipated this (flow 4: upgrades as scheduled re-bless events) and provides the instrument for handling it. At every bless, the harness records how strongly each weight tensor's perturbation moves the outputs (the mutation floor, around 1e-3). Library churn is diffuse and orders of magnitude smaller (around 1e-6). At a mass fire, per-head max|Δ| against those two scales classifies the event as churn (re-bless with an environment record) or behavior (investigate). This is a fire-time diagnostic, not a tolerance: the standing comparison stays exact, and tolerance comparison exists only in the deferred off-platform mode.

**One addition: the run-time state canary.** 7.09-1 pins the thread count by procedure but has nothing that checks the pin held. The canary from §4 fills that gap. The forward tier would then have three checks with distinct jobs: the bless-time mutation check (does the tripwire have detection power?), the fire-time floor comparison (what kind of fire is this?), and the run-time state canary (is the process state the blessed state?).

Two consequences for the torch-free question. First, torch-free was never available for the forward tier and its design never assumed it, so torch-free is a property of one tier, not of the goldens system. Second, if torch causes trouble later (recurring false alarms, or a second environment), the tiers have different remedies: forward references are full values (35 to 40 KiB per variant), so tolerance mode and per-platform blessing are available, while emission references are hashes, so no tolerance is possible and the remedy would be reviving torch-free.

Scope caveats already recorded in 7.09-1: forward goldens would guard the CPU path while training and eval run on MPS (§3), and the tier may never be built, since its boundary class has produced zero incidents in this project ([7.12-1](../2026-07/7.12-1-behavior-goldens-first-cut-v2-overview.md)).
