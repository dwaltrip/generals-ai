# Measurement config: recipe vs apparatus knobs

*Date: 2026-08-15. A direction for organizing training-run config, settled during the goldens build sessions. Nothing is restructured yet (see the status section).*

## The insight

Some metrics and data collection have to run during training. Sometimes that's absolute (the data exists only mid-run), sometimes practical (recomputing later would cost another full pass over the data). This measurement code can need knobs of its own, and some of those knobs depend on training-config values. Today, configuration like this has no clear pattern for how it is specified or recorded. The question that emerged: Where should a knob like this live? Is it part of TrainConfig?

The direction we settled on: a training run produces the model and, alongside it, measurement artifacts (dumps, recorded metrics). TrainConfig is the single source of truth for producing all of them, so measurement knobs do belong inside it. But they get their own sub-config block, so that the distinction between model-affecting and measurement-only values is explicit in the config structure. The rest of the note defines the three types of config values and lays out the management rules that follow.

**How it surfaced:** while planning a small refactor (making the dataset's `alive_mask` emission an explicit flag instead of a side effect of the elim precompute being enabled), we traced who depends on `alive_mask` being present in next_death dumps. Nothing on the training side does (the next-death head doesn't use it). The consumers are offline analyses, and the column is included in the dumps so those analyses can read everything from one file. So a measurement-only choice was embedded in the training pipeline in an ad-hoc fashion.

## Three types of training config values

Any training-config value falls into one of three types:

- **Recipe**: changing it changes the weights produced by the run. Examples: learning rate, data mix, seed, ObsConfig, the targets.
- **Apparatus**: changing it changes what gets measured or collected, without affecting the weights. Examples: dump columns, dump cadence, metric definitions.
- **Operational**: changes neither. Examples: run_dir, worker count, device.

The first two types map directly onto Test 1 and Test 3 from the [confounds framework](../confounds-framework.md) ("alters training?" and "alters what numbers mean?"), and the framework's boundary rules carry over. After a recipe change, later runs produce different models, and comparisons across the change remain valid. After an apparatus change, numbers recorded before and after no longer mean the same thing (a metrics-change boundary).

The type determines the consequences of a change. Today that classification lives in the reader's head. If the config structure encoded it, the config file itself would show which edits create measurement boundaries and which are recipe changes.

## Why measurement runs in-loop: three couplings

While working through the `alive_mask` case, we found that the ways a measurement can be coupled to a training run fall into three loose categories:

1. **Ephemeral**: the data exists only during the run. Optimizer state, gradients, timing. Capturing it in-loop is the only option.
2. **Expensive to recompute**: the data could be recomputed later, by running a checkpoint over the stored val data, but the loop is already doing that work. The per-epoch val dumps are the example: the val forward pass is already happening each epoch, so writing out its probs and per-frame CE costs almost nothing, while recomputing them later would mean a fresh GPU pass per epoch per checkpoint.
3. **Easily recomputed**: pure functions of stored data, like `alive_mask` or the targets. These are included in dumps so analyses can read everything from one file.

Items move between categories as tooling improves. The fq toolkit moved `alive_mask` into the third: it recomputes per-frame quantities from the stored replays at low cost, after the fact. The general rule: the easier something is to recompute offline, the less reason there is to configure it, or store it, as part of the training run.

## Management rules

- **TrainConfig is the single source of truth for everything the run produces**: the model, and the measurement artifacts recorded alongside it. Don't split the record across files.

- **Apparatus knobs get their own sub-config block** (a metrics/instrumentation config nested inside TrainConfig). The block holds the values that have no effect on the weights, separating them from the recipe. Some values affect both the weights and the measurement side. The elim variant is an example: it alters the trained weights and also determines the dump columns. A value like that belongs to the recipe, and whatever the measurement side needs from it is computed at construction time rather than copied into the block, so each value keeps a single authoritative home. The codebase already does this in places: `build_dataloader` passes bin edges only when the elim variant calls for them, and `build_eval_meter` takes the config and edges as inputs.

- **Producers declare their schemas, and consumers declare their needs.** This holds for dumps and for any other measurement artifact whose contents vary with the config (logged metric keys, report columns). Every producer-consumer dependency is then written down at a defined point on each side, whereas a raw key read is an undeclared dependency: it works until the schema changes, then fails far from the cause. The current instances: each aux-head spec declares its dump columns (the dump hook), so adding a variant includes stating what it writes, and dump readers go through a named accessor (`dump_compat.read_alive_mask`) or an up-front needs declaration (`FrameNeeds`).

- **Prefer offline recomputation when it is inexpensive.** When a dump column becomes easily recomputable, offline consumers can recompute it and the dump copy becomes deletable. Offline measurement can change freely without creating boundaries tied to training runs.

## Status and next steps

- Conceptually, these insights apply to new measurement knobs immediately. The sub-config block should probably be implemented somewhat soon, but the exact timeline is still open. At the very least, we should keep these insights and the new sub-config block in mind as we move forward.
- Restructuring the existing TrainConfig is deferred behind a scoping inventory: classify the current fields into the three types, find apparatus knobs currently outside TrainConfig (`prof_sink` wiring, dump cadence), and check what touches checkpoints and resume paths.
- Default slot for the restructure: after the goldens cut lands. Doing it then has a side benefit: the goldens staying green across the restructure confirms it did not change any guarded behavior.
- Dumps and metrics are an unguarded surface in the goldens first cut (the open rows in [7.12-1 §8](../2026-07/7.12-1-behavior-goldens-first-cut-v2-overview.md)). The declaration patterns above are the current protection, and this note doesn't change that status.
