## Exploratory items, to revisit

These are the leans we arrived at this session, each recorded with its reasoning so that it doesn't have to be re-derived.

**The walk core.** The signature takes a `PerspectiveMeta` and an `ObsConfig`. Context is passed in, and none is yielded back: [7.23-1](../2026-07/7.23-1-walk-infra-design-sketch.md)'s "context bundle" in the yield is not needed, because the caller already has that context (`PerspectiveMeta` carries the slot, slot order, and `end_t`, and the board dims come from the sim). The contract lean is that the core yields the model's per-frame inputs (obs and legality mask). That boundary is defined by the role of the outputs (they are what the model consumes), rather than by how they are computed (e.g. whether they depend on the walk's running state). If the contract were instead "the core yields whatever depends on the running state", it would need to change whenever that set of products changes. Two realistic changes show this. A perf refactor that moves part of the obs build into a per-game precompute would take those pieces out of the core. A future target that reads memory state would have to move into the core, putting target computation inside the loop. Neither change affects what the model consumes, so the boundary is unchanged. Under this contract, the mask stays in the core even though it is stateless.

Forward looking note: we leave the door open for exposing `vis` or `MemoryState` on the frame, e.g. for a memory-derived target (staleness, belief gap).

**"Walk" as a term.** We will keep it for now. As far as we know, there isn't a standard ML term for this operation. A few related terms we considered ("rollout", "unroll") give the wrong idea (e.g. some policy generating a trajectory). Our working definition: a stateful, in-order pass over one recorded game from one player's perspective, emitting each frame's model inputs. One ambiguity caused real confusion this session: "walk" was used for both the core loop (obs and mask) and the dataset's full-sample loop (`_walk`). Two names are needed, something like core walk and dataset walk.

**The targets side does not need the walk today.** Every target is a per-frame function of the recorded game plus the per-game precompute, and the legality mask is stateless. So the targets golden test uses a plain loop over `t` and skips the obs build. This is a property of today's targets, not an invariant.

**Registry stored shape.** The lean is one nested dict per point: `{"targets": {...TargetsConfig fields...}, "emit_alive_mask": bool}`. This stores what is emitted, rather than the source configs that produce it.

- Storing a TargetsConfig plus a MetricsConfig per point was considered and set aside, for three reasons:
  - (1) Different source pairs can produce identical emissions. For example, a time_bin point emits the same bytes whether or not MetricsConfig requested the mask, because the time_bin loss needs the mask and forces its emission. The stored pair would then record a distinction that has no effect on the reference bytes.
  - (2) MetricsConfig is expected to gain more fields over time (see 8.15-2), most of which won't affect emission. Each new field would still require an update to every stored point, even though the emitted bytes are unchanged. Registry diffs would then mix real changes to what is guarded with noise.
  - (3) The two remaining EmitSpec flags (`emit_frame_info`, `attach_sim_frame`) are pinned to constants by the registry under either scheme. So the registry pins some emitted facts in any case, and a pure "store the sources" scheme isn't available.

- Two mechanisms catch any drift between the stored dicts and the config classes:
  - The strict-keys assert checks each dict's keys against its config class's actual field list.
  - EmitSpec has no default values, so a new EmitSpec field breaks the registry loader until the loader supplies it (from the stored dict, or as a pinned constant).

**Axis naming.** The `alive_only` point differs from `core` in no TargetsConfig field, because mask emission is a MetricsConfig request. So "targets config points" is the wrong name for this axis. The lean is "emit points" (`EMIT_POINTS`, `EMIT_KEYSETS`) alongside "obs points", with a one-line comment explaining the split. A `DATASET_` prefix was considered and set aside (the name would apply to the obs points too, and it makes the pair asymmetric). Still open: the final name, and how far the rename reaches into reference paths and test IDs. There is a TODO in `registry.py`. With `emit_alive_mask` stored per point, a small structural check falls out: `alive_mask` is in a point's keyset if and only if `emit_alive_mask` is set.

**Goldens code home.** `training/goldens/` as a package. The repo's pytest runs with `--import-mode=importlib`, so helper modules living beside the tests can't be imported from the tests, and the regen CLI needs to import the registry anyway. The location of the fixtures and references data is still open.

**Comparison helpers.** Pure functions returning `ObsMismatch | None` and `TargetsMismatch | None`, because they have three consumers: the tests assert None, the mutation test asserts not-None, and regen renders the mismatch into the fire report. Loaders return None for a missing reference and stay pytest-free, so the "unblessed, run regen" failure is raised by the tests.

**Torch-free.** Headline change from this session. This core constraint is now relaxed to a nice-to-have. We did a fresh investigation and analysis of the arguments, and they were weaker than expected. The goldens may now call torch-importing emission code somewhat freely (it's still generally useful to not import torch everywhere).

The main caveat is that we must pin torch's thread count to 1. We can add a test asserting that pin, as well as a small torch numerics canary as a backstop. The full analysis and detailed findings are in 8.23-1 and 8.23-2.

## Next: the emission tail

The `encode_frame_np` spike will almost certainly be reverted, but this work will need some thought and discussion. The aim is one emission implementation, numpy throughout except for the torch wrap at the end, shared by prod and the goldens. The goldens' `compute_targets` would then stop re-implementing the target dispatch. Next session should look at this before any design work. Ideas that surfaced, all provisional:

- The name `emit_frame`, to match EmitSpec and emit points.
- A typed return (a dataclass) instead of `dict[str, Any]`.
- Take obs and mask as inputs instead of rebuilding them, since the walk core owns them.
- Finalize dtypes on the numpy side, so the torch wrap is a uniform `from_numpy` pass.
- `encode_targets` returns the aux-head targets as torch tensors. Until that changes, the tail either returns a mixed numpy/torch result or converts them back to numpy.
- Threading `GameMeta` in for H and W, as the spike did, seemed right.

At the dataset migration, `encode_frame` splits: its obs and mask half moves into the walk core, and what remains is the targets, a few small fields such as `valid_mask`, and the torch packing. Before the migration, `encode_frame` keeps its own `build_obs` and `build_mask` calls and `_walk` stays untouched. With torch allowed in the goldens, `compute_targets` becomes a thin wrapper around the tail, and its current numpy version is kept as a fallback in case torch-free comes back. The torch-free aux-encode extraction discussed this session is no longer part of the goldens work. It belongs with the aux-heads restructure, if that happens.

## 7.23-1 status

Its decisions hold: the walk core as shared torch-free infrastructure, targets computed on the consumer side, a parity test guarding the seam, and the dataset migration queued for after the cut. Its details are stale in three places. The API sketch predates EmitSpec, SimFrame, and PerspectiveMeta, so its input and yield shapes no longer match the code. Its constraint that dataset.py is not touched during the cut was superseded by the config restructure ([8.16-1](8.16-1-config-restructure-handoff.md)). And the two extractions it deferred to the migration have landed early: `make_elim_ctx` is already a shared function, and the `end_t` rule now lives on `PerspectiveMeta`.

We also sketched what the migrated `_walk` would look like. For each game it runs `precompute_for`, for each perspective it iterates the walk core, and for each yielded frame it runs the emission tail and torch packing. Everything else stays dataset-side: npz loading, `GameMeta`, `frame_meta` construction, and the grouping and shuffle layers. The dataset's timer sections cut across the loop the core would own. Timers were deliberately set aside for the first-pass design, to be resolved at migration time. There is one consequence for the parity test. Once the goldens compute their references through the same emission tail that prod uses, the only code the two paths don't share is the walk loop itself. So the parity test's real scope shrinks to that seam: core walk versus `_walk`.
