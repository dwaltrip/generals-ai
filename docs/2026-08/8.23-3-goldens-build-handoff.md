## Sequencing

[8.21-1](8.21-1-goldens-1st-cut-build-item-tiers.md)'s tiers put the registry before the walk. The session reversed that and built the walk core first. The reason: the registry discussion (stored shape, axis naming) kept running into questions about the emission layers (what is emitted, by which layer, what "the walk" refers to) that get settled by building the walk itself. Building it first means the registry transcription can land once, with final vocabulary. The reorder paid off, and the tier list should keep being treated as loose.

## Exploratory items, to revisit

These are the leans the session arrived at. Each is recorded with the reasoning that would otherwise be re-derived, but none is locked.

**The walk core.** The signature takes a `PerspectiveMeta` and an `ObsConfig`, and context flows in rather than out: [7.23-1](../2026-07/7.23-1-walk-infra-design-sketch.md)'s "context bundle" in the yield is not needed, because `PerspectiveMeta` already carries the slot, slot order, and `end_t`. The contract lean is that the core yields the model's per-frame inputs (obs and legality mask). That boundary is drawn by purpose, not by an implementation property such as stateful versus stateless. The reasoning: if the boundary were "the core yields the stateful products", it would move whenever statefulness moves. Two realistic changes make that concrete. A perf refactor that hoists part of the obs build into a per-game precompute would evict those products from the core, and a future target that reads memory state would earn a place in it, pushing supervision into the loop. The purpose boundary sits still through both. Under that lean the mask stays in the core even though it is stateless.

A door is left open to expose `vis` or `MemoryState` on the frame later, if a memory-derived target (staleness, belief gap) ever appears. One hazard for that day: the memory state is mutated in place, so a reference on the frame is valid only until the next iteration.

**"Walk" as the term.** Kept. There is no standard ML term for this operation, and the nearby ones (rollout, unroll) imply a policy acting, which is wrong here. The one-line definition: a stateful, in-order pass over one recorded game from one player's perspective, emitting each frame's model inputs. One ambiguity caused real confusion this session: "walk" was covering both the core loop (obs and mask) and the dataset's full-sample loop (`_walk`). Two names are needed, something like core walk and dataset walk.

**The targets side does not need the walk today.** Every target is a per-frame function of the recorded game plus the per-game precompute, and the legality mask is stateless. So the targets golden test uses a plain loop over `t` and skips the obs cost. This is a property of today's targets, not an invariant.

**Registry stored shape.** The lean is one nested dict per point: `{"targets": {...TargetsConfig fields...}, "emit_alive_mask": bool}`. This stores the fact (what is emitted), not the source configs. Storing a TargetsConfig plus a MetricsConfig per point was considered and set aside, for three reasons. Different source pairs can produce identical emissions (a time_bin point emits the same bytes whether or not metrics requested the mask, since the variant forces it), so the pair adds a degree of freedom that never reaches the reference bytes. MetricsConfig will grow fields that never touch emission, and each one would churn the stored points while looking re-bless-relevant. And the two remaining EmitSpec flags (frame info, sim-frame attach) are registry-pinned constants either way, so a pure "store the sources" scheme doesn't exist. Two mechanisms keep the stored dicts honest: the strict-keys assert checks each dict against its config class's real field list, and EmitSpec's no-defaults constructor means a new EmitSpec field breaks the registry loader until the stored shape answers it.

**Axis naming.** The `alive_only` point differs from `core` by zero TargetsConfig fields, because mask emission is a MetricsConfig request. So "targets config points" misnames the axis. The lean is "emit points" (`EMIT_POINTS`, `EMIT_KEYSETS`) beside "obs points", with a one-line comment stating the split. A `DATASET_` prefix was considered and set aside (it does not exclude obs, and it makes the pair asymmetric). Still open: the final name, and how far the rename reaches into reference paths and test IDs. There is a TODO in `registry.py`. A small structural check falls out of the shape: `alive_mask` is in a point's keyset if and only if `emit_alive_mask` is set.

**Goldens code home.** `training/goldens/` as a package. The repo's pytest runs with `--import-mode=importlib`, so helper modules living beside the tests can't be imported by them, and the regen CLI needs to import the registry anyway. The location of the fixtures and references data is still open.

**Comparison helpers.** Pure functions returning `ObsMismatch | None` and `TargetsMismatch | None`, because they have three consumers: the tests assert None, the mutation test asserts not-None, and regen renders the mismatch into the fire report. Loaders return None for a missing reference and stay pytest-free, so the tests own the "unblessed, run regen" failure.

**Torch-free.** Relaxed to a nice-to-have. The goldens may call torch-importing emission code, with a thread-pin assert and a small canary as guards. Reasoning and findings in 8.23-1 and 8.23-2.

## Next: the emission tail

The `encode_frame_np` spike will almost certainly be reverted, but its direction is the next thing to explore: one emission implementation, numpy in substance, shared by prod and the goldens, so that the goldens' `compute_targets` stops re-implementing the target dispatch. This is a discussion for next session, not a design. Ideas that surfaced, all provisional:

- The name `emit_frame`, pairing with EmitSpec and emit points.
- A typed return (a dataclass) instead of `dict[str, Any]`.
- Take obs and mask as inputs instead of rebuilding them, since the walk core owns them.
- Finalize dtypes on the numpy side, so the torch wrap is a uniform `from_numpy` pass.
- The aux-head targets arrive as torch tensors (`encode_targets` returns torch). An interim wart: accept a mixed result, or round-trip them to numpy.
- Threading `GameMeta` in for H and W, as the spike did, seemed right.

At the dataset migration, `encode_frame` splits: its obs and mask half moves into the walk core, and what remains is supervision, bookkeeping, and torch packing. Before the migration, `encode_frame` keeps its own `build_obs` and `build_mask` calls and `_walk` stays untouched. With torch allowed in the goldens, `compute_targets` becomes a thin delegation to the tail, and its current numpy version stays as the fallback. The torch-free aux-encode extraction discussed this session is no longer goldens work. It belongs with the aux-heads restructure, if that happens.

## 7.23-1 status

Its decisions hold: the walk core as shared torch-free infrastructure, targets computed on the consumer side, a parity test guarding the seam, and the dataset migration queued for after the cut. Its mechanics are stale in three places. The API sketch predates EmitSpec, SimFrame, and PerspectiveMeta, so its input and yield shapes no longer match the code. Its constraint that dataset.py is not touched during the cut was superseded by the config restructure ([8.16-1](8.16-1-config-restructure-handoff.md)). And the two extractions it deferred to the migration have landed early: `make_elim_ctx` is already a shared function, and the `end_t` rule now lives on `PerspectiveMeta`.

The session also sketched what the migrated `_walk` would look like. For each game it runs `precompute_for`, for each perspective it iterates the walk core, and for each yielded frame it runs the emission tail and torch packing. Everything else stays dataset-side: npz loading, `GameMeta`, `frame_meta` construction, and the grouping and shuffle layers. The dataset's timer sections cut across the loop the core would own; timers were deliberately set aside for the first-pass design and get resolved at migration time. One consequence for the parity test: once the goldens compute their references through the same emission tail prod uses, the only code the two paths stop sharing is the walk loop itself, so the parity test's real scope shrinks to that seam (core walk versus `_walk`).
