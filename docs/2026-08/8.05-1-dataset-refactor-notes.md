# Dataset refactor — session notes

*Date: 2026-08-05. Records the `refactor-dataset-py` branch: what changed, how it was verified, notes for a possible follow-up kernel sweep, and comments on how it relates to the planned walk consolidation work ([7.23-1](../2026-07/7.23-1-walk-infra-design-sketch.md)).*

## 1. Overview

### Code change summary

`dataset.py` is now much closer to a dumb orchestrator and iterator. The focus of the module has reduced to: grouping samples by game, worker sharding, the shuffle buffer, and yielding the sample tensor dict.

We created several domain objects and new modules:

- `encode_frame.py` - new home for `encode_frame`, owning the per-frame encoding details and domain logic.
- `sim_types.py` - typed views over a game's sim and meta data (`GameMeta`, `PerspectiveMeta`, `SimFrame`).
- `sample.py` - training-sample type (`TrainingSample` and `FrameMeta`).
- `slots.py` owns the fixed-slot contract: the `SlotOrder` type and the `MAX_PLAYERS` capacity constant. The old `canonical_slot_order` function was absorbed into `SlotOrder`.

The contract with the DataLoader is unchanged: each frame is built internally as a `TrainingSample` and then converted to the pre-refactor tensor dict right before the yield.

`build_obs` now takes a `SimFrame`. All four call sites are updated accordingly (the dataset, live inference, the goldens probe walk, the parity test).

### Verification and review

The primary verification methods we used for this refactor:

- The repo test suite (especially the live-vs-training obs parity test).
- Byte-level comparison of the dataset.py walk output against the pre-refactor baseline (see next section).

A fresh-context agent then reviewed the whole branch diff and found no correctness bugs; every contract, design, and prose finding was fixed, declined with a reason, or converted to a TODO. The full review: `tmp/review-artifacts/2026-08-05-refactor-dataset-review.md`.

## 2. Byte-comparison (before vs. after)

We wrote scripts which verified that the refactor's output is byte-identical to the pre-refactor baseline (branch: `goldens-1st-cut-build`). This was throwaway / one-off tooling for the refactor (saved to `tmp/dataset-refactor-byte-compare/`).

- `dump_dataset_bytes.py` — Iterates the dataset deterministically (fixed sample list, fixed seed, no shuffle buffer) and hashes every tensor of every sample. Coverage: 600 frames × 4 configs (default, frame-info + alive mask, and both elim-head variants), from 4 perspectives across 3 games. Example usage: `uv run python path/to/dump_dataset_bytes.py some/path/out.json`.
- `compare_hashes.py` — Diffs two dumps and reports the results: which samples and keys differ.

To run the verification: check out the baseline branch in a git worktree, symlink the corpus dir (`replay-parser/data/intermediate`) into it (settings resolve paths relative to the checkout, and the corpus is gitignored), run the dump script from each side, and then run the comparison script.

Although this was throwaway tooling, it is essentially the same as the one-off byte comparison that 7.23-1 §4 proposes for the dataset migration. So these scripts may be useful during that work as well.

## 3. Forward-looking / follow-up notes

### The "kernel sweep"

There are several remaining per-tick kernels that still receive a spread of primitive arguments: `init_memory`, `step_memory`, `compute_visibility`, `build_mask`, and `policy_pass_target`. The primitive args: sim dict, tick, slot, board dims, etc. `build_obs` is half-converted: it takes a `SimFrame` but still takes the board dims separately. A "kernel sweep" to improve these interfaces is actively on the table, but was not attempted today.

### Known / discovered constraints

These came up during the refactor. Noting for posterity.

In the live path, the sim dict is built incrementally as the game runs. This dict differs from a parser npz load in two ways: 

1. Some keys don't exist at all (e.g. board dimensions). Shared code that operates on both versions of the dict must assume the narrower shape from the live-path.
2. The per-tick fields (`ownership`, `armies`) are Python lists with tick-level numpy arrays appended one by one, compared to the parser's single numpy stacked arrays (which cover all ticks).

### Possible follow-up candidates

Roughly by value:

1. `MemoryState` holds a `SlotOrder` instead of its separate perspective and opponent fields. `build_obs` currently receives the slot order from two independent sources and asserts they agree; this change makes the duplication impossible instead. It also absorbs the standalone player-count parameter.
2. `build_obs` drops its board-dim parameters once `SimFrame` carries them, with the dims passed in at construction (per the constraint above).
3. `build_mask` and `policy_pass_target` take a `SimFrame`; they need nothing it doesn't have.
4. The loosely-typed `sim` mapping on `SimFrame` upgrades to a real per-key schema, if precise sim typing is ever wanted — the sweep is where that work lands.
5. `compute_visibility` likely stays primitive: it takes a single ownership row, a different granularity than the carrier.

**Two additional notes.**

1. The kernel signatures annotate their opponent lists as `list[int]`, which is why `SlotOrder.opp_slots` returns a list. Further work on these interfaces either pushes `SlotOrder` deeper or loosens those annotations.

2. Further refactors touching these signatures should not modify the resulting outputs, which means we can easily re-use the verification script above. This a low-cost way to gain strong confidence in any additional cleanups. The existing test suite is also very valuable here.

## 4. Connection to the walk consolidation

A future walk migration (sketched in 7.23-1) touches the same functions. The shared walk core calls all of these kernels, so the kernel sweep should probably happen with or just before it (otherwise we may end up re-working the same interfaces twice).

This branch already staged some of that migration's prep. The walk-bound formula and the per-perspective meta reads now have their home in `sim_types` (`PerspectiveMeta`). The goldens walk can consume `GameMeta` and possibly other shared structures instead of having to build their own versions.

Two smaller items also parked:

- Analysis consumers could read the `TrainingSample` directly instead of the yielded dict, which would dissolve the seam cast in `to_dict` and the `unsafe_attach_sim_frame` flag.
- A synthetic test pinning the walk-bound and players-alive boundary semantics could be useful (TODO in `sim_types.py`).
