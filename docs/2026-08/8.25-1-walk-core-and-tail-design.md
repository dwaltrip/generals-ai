# Walk core and tail — design update

*Date: 2026-08-25. Design outcomes from the fourth working session of the goldens first-cut build. We settled the shape of the shared emission code (a walk core, an emission tail, and torch packing) and worked out its consequences for the golden tests. It follows the [8.23-3](8.23-3-goldens-build-handoff.md) handoff and revises parts of it.*

*Names. Two renames are proposed in §4.3 and used throughout this note: `mask` → `legality_mask` (which moves are legal at tick `t`) and `valid_mask` → `board_mask` (the unpadded board region). The code still has the old names. Several other terms are tentative and are marked on first use: "state products", `FrameEmission`, `PerspectiveWalk`, the "act vs. train/measure" rule, and "emit point". Core and tail are already in use.*

*Config points. A config point is one explicit, stored config that the goldens guard. The goldens matrix is config points × fixtures, and each cell has its own references. The obs config points are `ObsConfig` values. The targets-side points, which say what targets and metrics columns are emitted, are called emit points here (tentative). §1.4 and §7 depend on the distinction.*

## 1. Findings

The findings below and the surrounding discussion shaped the design considerations for the walk core, the tail, the emitted pieces, and their interactions with the rest of the codebase.

In section 2, we give an updated design sketch for this part of the training pipeline that the goldens will depend on.

### 1.1 The legality mask is not a model input

The forward pass on our model (`BCModel.forward`) receives `obs` and `valid_mask` as the only two arguments.

Meanwhile, the legality mask (`TrainingSample.mask`), is applied to the policy logits *after the forward pass*. It is used in `bc_loss` (via `flatten_policy_logits`), in the val metrics and the val dump, and in the inference decoder (masked argmax or multinomial).

So the legality mask is a constraint on the model's output, consumed by the loss and the decoder, and not an input to the model. Our new framing of the walk contract accomodates this (see below). The previous rule (from 8.23-3) did not: "the core yields the model's per-frame inputs (obs and legality mask)".

### 1.2 Every consumer needs the same state products, and only some need targets

A survey of the ten consumers of per-frame emission (train, val, capture, the analysis toolkits and scripts, the two goldens, the parity test, and live inference) shows two product groups:

- **State products** (tentative term): obs, the legality mask, the board mask. Needed by every consumer, including live inference.
- **Targets, metrics columns, and the alive mask**: `action_target`, `is_pass`, `value_target`, the aux-head targets, and `alive_mask` (the odd one out). Needed by train, val, the analysis toolkits and scripts, the goldens, and the parity test. Live inference does not need them.

Torch is needed only at the DataLoader boundary (train, val, capture, probes). fq, the goldens, the parity test, and inference want numpy. The fq toolkit currently undoes the torch wrap on the target and metrics columns it reads.

### 1.3 Live inference duplicates the core's per-tick body

`BCPerspective.encode` does six things. Three are live-only: append the tick's ownership and armies rows to the growing sim, refresh the dynamic sim fields (cities, events), and append scoreboard rows and refresh player status inside `MemoryState`. The other three match the walk core's loop body (`walk.py`): visibility, `step_memory`, and the build kernels (obs and the masks).

The live sim dict is already compatible with the kernels (inference code already calls them). Inference also shares much of the initial setup with training through `init_memory_common`. It then follows up with ticky-by-tick incremental appends to the sim.

### 1.4 The union targets layout rests on an assumption we don't want

8.12-2 §6 stores one targets bundle per fixture (the union of every key) plus a keyset table saying which keys each emit point covers. This works only if the emit points differ by *which keys* they emit and not by *the bytes of a shared key*. Today that holds: each elim variant owns its own keys, and there is one time_bin edge set. This assumption will be broken by any key that changes the values: a second time_bin edge set, a changed value-target definition, a changed alive-mask rule. 8.12-2's own coverage guidance (enum knobs get one point per value) expects exactly that kind of growth.

Obs already has the opposite property (the same `obs` key, different bytes per config), which is why obs references are per (point × fixture).

## 2. Design sketch

This sketch describes the updated sketch. The design work that produced this sketch is very much the same spirit of previous pre-first-cut work has been slowly refining and cleaning up.

Daniel's "vibe" comment: Most of the ambiguities and design rough edges are starting to feel resolved. This stuff has been quite tricky to get a full handle on and to design clean interfaces and types for. But the slow careful, chipping away is paying off.

We break it down into three layers:

```python
# Core: state products.  bc/walk.py
@dataclass(frozen=True)
class WalkFrame:
    t: int
    obs: np.ndarray
    legality_mask: np.ndarray
    board_mask: np.ndarray            # same array every frame, built once per game
    def to_dict(self) -> dict[str, np.ndarray]: ...

class PerspectiveWalk:                # name tentative
    # Setup: init_memory, bfs cache, board_mask, next_t = 0.
    def __init__(self, sim, slot, H, W, obs_cfg): ...
    # Per tick: assert t is next in order, then visibility, step_memory, build_obs, build_mask.
    def frame(self, t: int) -> WalkFrame: ...

def walk(sim, perspective: PerspectiveMeta, obs_cfg) -> Iterator[WalkFrame]:
    w = PerspectiveWalk(sim, perspective.slot, H, W, obs_cfg)
    for t in range(perspective.end_t):
        yield w.frame(t)


# Tail: targets and metrics columns, numpy. new module
@dataclass(frozen=True)
class FrameEmission:                  # name tentative
    action_target: ...
    is_pass: ...
    value_target: ...
    alive_mask: np.ndarray | None
    aux: dict[str, np.ndarray] | None
    def to_dict(self) -> dict[str, Any]: ...

def emit_frame(sim, t, W, perspective, spec: PartialEmitSpec, pre: EmitPrecompute) -> FrameEmission: ...


# Pack: torch.  bc/encode_frame.py
def pack_sample(frame: WalkFrame, emission: FrameEmission, frame_meta, sim_frame) -> TrainingSample: ...
```

The tail is not given the obs or the masks. It computes only the targets and metrics columns. That is what lets the targets golden skip the obs build, and it matches the two product groups in §1.2. With prod and the goldens sharing the tail, 7.23-1's "targets stay consumer-side" now means only that the tail is not inside the core loop.

Status: settled for the build. §4 to §6 are picks within this shape.

Who calls what (`spec.partial` is the accessor described in §6):

```python
# Obs golden (unchanged)
frames = list(walk(sim, persp, entry.cfg))

# Targets golden
pre = precompute_for(spec, sim)
per_t = [emit_frame(sim, t, W, persp, spec, pre).to_dict() for t in range(persp.end_t)]

# encode_frame, before the dataset migration. Byte-identical to the pre-spike code.
frame = WalkFrame(t, build_obs(...), build_mask(...), board_mask)
return pack_sample(frame, emit_frame(sim, t, W, perspective, spec.partial, pre), frame_meta, sim_frame)

# _walk, after the migration
for frame in walk(sim, persp, spec.obs):
    emission = emit_frame(sim, frame.t, game.W, persp, spec.partial, pre)
    yield pack_sample(frame, emission, frame_meta, sim_frame).to_dict()
```

The dataset migration is `_walk` dropping its own loop and kernel calls for `walk()`. It is 7.23-1's queued follow-up after the cut, and it is outside the build order in §9.

The `encode_frame_np` spike from 8.23-3 (an unfinished numpy split of `encode_frame`) is to be reverted first. It is broken at HEAD (the wrapper and the spike disagree on the dict keys, and the walk test fails). So every "today" statement about `encode_frame` in this note describes the pre-spike code. After the revert, `encode_frame` becomes "build the state products, call the tail, pack". Before the migration it still makes its own kernel calls, and `_walk` is untouched.

**Why "emit", not "targets", for the tail.** `alive_mask` is a MetricsConfig request, emitted whether or not a loss needs it, and future MetricsConfig fields will be measurement-only. A tail named after targets would be inaccurate from the start. This is the same reason 8.23-3 stopped calling the registry axis "targets config points". The "emit" naming is then shared across `EmitSpec`, `emit_frame`, `FrameEmission`, and (tentatively) "emit points" for the registry axis.

## 3. Walk contract (candidate)

The core yields what is needed to **act**: run the forward and decode a move. The tail yields what is needed only to **train or measure**.

Checking this framing against the full list of walk products:

| product | needed to | layer |
|---|---|---|
| obs, board_mask | run the forward | core |
| legality_mask | decode a move | core |
| action_target, is_pass, value_target, aux targets | train (loss inputs) | tail |
| alive_mask | train (time_bin loss) or measure | tail |
| frame_meta, sim_frame | bookkeeping, analysis transport | pack, dataset-side |

Live inference is the concrete check. It consumes the core's outputs and does not consume any tail output.

Two earlier attemps to precisely conceptualize the contract didn't hold up. 8.23-3's "the model's per-frame inputs" names the legality mask as one, but this was incorrect (see finding 1). A second candidate, "derived from the game state alone", put `alive_mask` in the core (despite no consumers needing it) and said nothing useful about the board mask.

This new framing of the walk contract feels robust where the others failed.

One known edge case. A future target that reads `MemoryState` (staleness, belief gap) would be a train-side product that needs core internals. The frame would expose `vis` or the memory state, as 8.23-3 noted. Memory is mutated in place, so such a reference is valid only until the next frame.

Status: a lean. It fits every product in the survey. It has not yet been tested by new code and Daniel hasn't pressure-tested the framing in depth.

## 4. The walk core

### 4.1 A class, with the generator on top

The per-tick body moves into a small class (`PerspectiveWalk`, name tentative) with a recorded-game constructor and a `frame(t)` method. `walk()` stays as the generator the goldens and the dataset use. Four reasons:

- The per-tick body gets one named home, instead of "the loop body of `walk`".
- The in-order guard (frames must be requested in tick order) is written once. Today inference asserts it and the dataset does not.
- `board_mask` is built once per game and reused.
- The inference refactor (§8) becomes "replace the duplicated block with `frame(t)`", with no core changes.

Consumers see only `walk()` and `WalkFrame`, so the class could be added later without consumer churn. Shaping it now costs about twenty lines and fixes the interface that the inference refactor will build on. The live setup variant (`init_memory_common` plus incremental appends) belongs to that work, not to the cut.

### 4.2 `board_mask` on the frame

It is constant per game and is built by hand in two places (the pre-spike `encode_frame` and `inference.py`, per tick). The legality mask cannot be cached the same way: two of its four conditions (source owned, armies ≥ 2) change every tick. Only its static factors (mountains, bounds) could be precomputed, and the gain is small.

### 4.3 Renames

- `mask` → `legality_mask` — Binary mask for move action space, identifying which moves are legal.
- `valid_mask` → `board_mask` — Binary mask for which cells are part of the actual board for the current game. It's static per-game.

These renames are tentative. The old names are a bit vague and easy to mixup. Daniel wanted to "test out" the new names, so we used them during the design work that led to this doc.

Implementing the full rename would be a fairly large change. The names are used across the codebase. For example: the sample dict keys, the loss, eval, the dump, inference, the goldens keyset and reference keys, and fq's `emit_cols`. 

The change would be byte-preserving and should land in one commit. Ideally, it would land before the first bless: a renamed reference key after blessing is a re-bless or a migration.

Status: open, lean twowards writing new code with the names and slowly converting old code as we touch it.

### 4.4 The walk-versus-probe byte compare

Queued in 8.23-3 and not yet done. Everything above builds on `walk.py`, and its output has not been verified against the probe's walk. A one-off over a few corpus games. Do it early.

## 5. The tail

**Signature.** `emit_frame(sim, t, W, perspective, spec, pre)`. It needs `W` (for `policy_pass_target`), the perspective (placement and slot order), the partial spec (§6), and the per-game precompute. Whether it takes `GameMeta` or a bare `W` is open and small: once `board_mask` leaves the tail, `W` is the only thing it reads from the game.

**Return.** `FrameEmission` with a flat `to_dict()`. fq's `emit_cols` reads emitted fields by string key, and the parity test iterates keys, so both `FrameEmission` and `WalkFrame` keep a dict view.

**Aux targets.** `encode_targets` on the aux-head specs returns torch (`from_numpy` wraps, plus two `torch.tensor` scalars in next_death). The tail converts to numpy with `.numpy()`, so `FrameEmission` is all numpy and `pack_sample`'s `from_numpy` is a zero-copy round trip. The torch-free aux-encode extraction stays with the aux-heads restructure (8.23-1 §7).

**Dtype authority (open, lean yes).** Today `compute_targets` declares dtypes by hand, and two TODOs ask where goldens dtypes should live. With one shared tail, the tail is the authority: `FrameEmission` fields carry fixed numpy dtypes, and `pack_sample` and the goldens inherit them. That includes the scalars (`action_target`, `is_pass`, `value_target`, next_death's two), whose dtypes are chosen at `torch.tensor(..., dtype=)` sites today. It closes both TODOs and most of 8.12-2 §8's option (b) (per-key dtype metadata). A dtype change after the first bless is a re-bless, so settle this before it.

**Timer.** The `encode_tail` timer section stays in `encode_frame`, around the tail call and `pack_sample`. The tail does not import `timer`.

## 6. Types and the registry loader

**`PartialEmitSpec` is the tail's input.** `emit_frame` and `precompute_for` read only `targets` and `emit_alive_mask` from a spec. They do not read `obs`, `emit_frame_info`, or `attach_sim_frame`. That pair is also the registry's stored shape, and `PartialEmitSpec` already carries it (plus `attach_sim_frame`, below). So:

- `EmitSpec` gains an accessor that returns the partial (shown as `spec.partial` in §2; the name is a pick). `EmitSpec` stays flat, so no `spec.targets` read site changes.
- `precompute_for(partial, sim)`.
- The goldens do not build a full `EmitSpec`, which would require an `obs` config they don't have.

**The registry loader.** A stored point `{"targets": {...}, "emit_alive_mask": bool}` becomes `TargetsConfig(**d["targets"])` under the strict-keys assert, then `PartialEmitSpec(targets, emit_alive_mask, attach_sim_frame=False)`. `TargetsEntry` holds the partial instead of `cfg` plus `emit_alive_mask`. 8.23-3's "no defaults" drift check now applies to `PartialEmitSpec`. The "store facts, not sources" decision is unchanged.

**`attach_sim_frame` does not belong on the partial.** It tells the dataset to put the raw `SimFrame` on the sample. That is a transport detail decided by `build_frame_table`, not by the author of a `FrameTableSpec`, and `build_frame_table` already asserts it is True. The fix is to drop it from `PartialEmitSpec`, make it a `to_spec` kwarg, and have `build_frame_table` pass `True` at its one `to_spec` call. About six call sites lose a line. Not part of the cut. Until then the tail ignores the field and the loader pins it False.

**Renaming `PartialEmitSpec` to `EmitPoint`.** Deferred. The "emit point" vocabulary is not settled.

## 7. Goldens consequences

### 7.1 Per-point targets references

Decided: drop the union layout (§1.4). Open between two per-point layouts:

- **(a) One npz per (point × fixture)**, matching obs. The simplest code: no union, no merge, and `compare_targets` compares a whole file (the `legality_mask` key stays hash-compared). Cost: shared keys are stored once per point, so roughly 2× to 4× today's 15 to 25 KB per fixture (8.12-1 §4), and re-bless churn for shared keys grows by the same factor. About 1 MB standing at ten fixtures.
- **(b) One `.npy` per (point × fixture × key).** Same generality. Git dedups identical arrays across points by content hash, so the pack cost is about the old union's. Cost: file sprawl (about 250 files at ten fixtures) and per-key loading. An npz can't get this dedup, because a zip is one blob.

Under either layout:

- The keyset table becomes the set of keys in each point's file.
- The bundle-contents structural check becomes a per-file check.
- Regen writes one file per (point, fixture), with no merge step. It still runs the tail once per point, since time_bin and next_death are exclusive variants and no single spec produces every key.
- The legality-mask hashes sit in each point's file like any other key.

One observation to keep. Which layer computes a product (core or tail) and what a product varies with (config point, fixture, or both) are two different questions. The legality mask is a core product, but it depends on the sim and `t` only, so it has no config axis. The reference layout follows the second question, not the first.

### 7.2 `compute_targets`

This new function created for the golden tests currently re-implements logic that already exists in the training flow:

- per-game precompute (`make_elim_ctx`, `precompute_player_status`)
- per-frame dispatch (`policy_pass_target`, `value_target`, `make_alive_mask`, the variant branch)

After refactoring, it should look something like this:

```python
def compute_targets(sim, game, persp, entry):
    spec = entry.spec                                    # PartialEmitSpec, attach pinned False
    pre = precompute_for(spec, sim)
    per_t = [emit_frame(sim, t, game.W, persp, spec, pre).to_dict() for t in range(persp.end_t)]
    out = {k: np.stack([d[k] for d in per_t]) for k in per_t[0]}
    out["legality_mask"] = np.stack([build_mask(sim, t, persp.slot, game.H, game.W) for t in range(persp.end_t)])
    return out
```

What stays goldens-side: the loop over `t`, stacking per-frame values into `[T, ...]`, and the legality-mask stack (a state product, so from `build_mask`, not the tail). The key names will come from prod's `to_dict`. Currently, they are hand-typed and would have had to match the keyset table by discipline.

One consequence is that `compute_targets` will import torch through the tail. Being able to do this refactor without resolving that torch import is an early win for the relaxation of the torch-free constraint (see 8.23-1).

**Minor additional note**: by default, `value_target` is `[T]`  in the golden references, as with per-frame emission it will be stacked. The alternative would be to store it as a scalar (it is constant per-perspective). This is an open decision for the first-cut work (not new, listed as a build-time pick in 8.12-2 §8).

### 7.3 The parity test (lean)

Before the dataset migration, the prod path is `_walk`'s loop plus `encode_frame`'s own kernel calls plus the tail plus packing. The goldens path is the core walk plus the tail. Shared: the tail. Not shared: the loop and the kernel-call sites. So the test's scope is the walk seam. After the migration, both paths run the same code, and the test is trivially true. 7.23-1 §4 left its post-migration fate open. With the tail shared, the lean is to delete it after the migration.

### 7.4 Unchanged by this note

`board_mask` is not guarded (it derives from `H` and `W`, and the obs channel summary catches a board-shape change). The torch guards (thread-pin assert and canary, 8.23-2 §4) are still required, because the tail imports torch through `spec_for`.

## 8. Parked follow-ups

**Live inference** (high priority after the cut). `encode` shrinks to the three live-only steps plus `frame(t)` on the core class. The third step (scoreboard rows, player-status refresh) reaches into `MemoryState` fields and should become a method on it (something like `append_tick`). Needs the live setup variant from §4.1.

**Analysis toolkits.** fq moves to the core plus the tail directly and drops the numpy → torch → numpy round trip and the dataset workarounds, as 7.23-1 §6 planned. The probes are not a walk consumer in that plan, and nothing here changes that. Nothing to do now beyond the `to_dict` views in §5.

**`attach_sim_frame` cleanup.** §6.

## 9. Build order

Every step that touches the dataset path is verified against the baseline byte dump (`tmp/dataset-refactor-byte-compare/`), as the 8.16 restructure was. A plausible order:

1. Revert the `encode_frame_np` spike. This is a precondition: the walk test fails at HEAD (§2).
2. Extract `emit_frame` and `pack_sample` from `encode_frame`. Byte-identical to the pre-spike code.
3. `compute_targets` delegates to them.
4. The core class and `board_mask` on the frame.
5. `precompute_for` takes the partial. The `EmitSpec` accessor. The registry loader produces a `PartialEmitSpec` and `TargetsEntry` holds it (§6).
6. The renames, as their own commit.

The walk-versus-probe compare (§4.4) goes early, before step 4 at the latest. Outside this order: the per-point reference layout (§7.1) lands with the registry transcription and regen, and the dataset migration (§2) stays a post-cut follow-up.
