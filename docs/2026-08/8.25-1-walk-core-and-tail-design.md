# Walk core and tail — design update

*Date: 2026-08-25. Design outcomes from the fourth working session of the goldens first-cut build. We settled the shape of the shared emission code (a walk core, an emission tail, and torch packing) and worked out its consequences for the golden tests. It follows the [8.23-3](8.23-3-goldens-build-handoff.md) handoff and revises parts of it.*

*Names. Two renames are proposed in §4.3 and used throughout this note: `mask` → `legality_mask` (which moves are legal at tick `t`) and `valid_mask` → `board_mask` (the unpadded board region). The code still has the old names. Several other terms are tentative and are marked on first use: "state products", `FrameEmission`, `PerspectiveWalk`, the "take action vs. train/measure" rule, and "emit point". Core and tail are already in use.*

*Config points. A config point is one explicit, stored config that the goldens guard. The goldens matrix is config points × fixtures, and each cell has its own references. The obs config points are `ObsConfig` values. The targets-side points, which say what targets and metrics columns are emitted, are called emit points here (tentative).*

## 1. Findings

The findings below and the surrounding discussion shaped the design considerations for the walk core, the tail, the emitted products, and their interactions with the rest of the codebase.

In section 2, we give an updated design sketch for the per-frame emission code, which the goldens will depend on.

### 1.1 The legality mask is not a model input

The forward pass on our model (`BCModel.forward`) receives `obs` and `valid_mask` as the only two arguments.

Meanwhile, the legality mask (`TrainingSample.mask`) is applied to the policy logits *after the forward pass*. It is used in `bc_loss` (via `flatten_policy_logits`), in the val metrics and the val dump, and in the inference decoder (masked argmax or multinomial).

So the legality mask is a constraint on the model's output, consumed by the loss and the decoder, and not an input to the model. Our new framing of the walk contract accommodates this (see below). The previous rule (from 8.23-3) did not: "the core yields the model's per-frame inputs (obs and legality mask)".

### 1.2 Every consumer needs the same state products, and only some need targets

A survey of the ten consumers of per-frame emission (train, val, capture, the analysis toolkits and scripts, the two goldens, the parity test, and live inference) reveals two usage patterns. We can cleanly categorize these by the sets of products that a consumer uses:

- **State products** (tentative term): obs, the legality mask, the board mask. Needed by every consumer, including live inference.
- **Targets, metrics columns, and the alive mask**: `action_target`, `is_pass`, `value_target`, the aux-head targets, and `alive_mask` (the odd one out). Needed by train, val, the analysis toolkits and scripts, the goldens, and the parity test. Live inference does not need them.

Torch is needed only at the DataLoader boundary (train, val, capture, probes). fq, the goldens, the parity test, and inference all use numpy. In the fq toolkit, we currently undo the torch wrap on the target and metrics columns that it uses.

### 1.3 Live inference duplicates the core's per-tick body

`BCPerspective.encode` does six things. Three are live-only: append the ownership and armies rows for each tick to the growing sim, refresh the dynamic sim fields (cities, events), and append scoreboard rows and refresh player status inside `MemoryState`. The other three match the walk core's loop body (`walk.py`): visibility, `step_memory`, and the build kernels (obs and the masks).

The live sim dict is already compatible with the kernels (inference code already calls them). Inference also shares much of the initial setup with training through `init_memory_common`. It then follows up with tick-by-tick incremental appends to the sim.

### 1.4 The union targets layout depends on an incorrect assumption

8.12-2 §6 stores one targets bundle per fixture (the union of every key) as well as a keyset table saying which keys each emit point covers. This works only if a key's bytes never depend on which emit point produced it: points may differ in *which* keys they emit, but any key two points share must be byte-identical. Today that holds. Each elim variant owns its own keys, and there is one time_bin edge set.

Any config field that tweaks or parameterizes an existing target breaks it. Once the registry stores two values for such a field (and 8.12-2's coverage guidance says it should, one point per value), two points emit the same key with different bytes, and the union has one slot for it. A second time_bin edge set is the nearest example. Being able to iterate on existing targets is essential to targets work in general, so the assumption is flawed and must be dropped.

Fields that add or remove a whole target (`elim_enabled`, a new variant with its own keys) don't break it. Obs already has the opposite property (the same `obs` key, different bytes per config), which is why obs references are per (point × fixture).

## 2. Design sketch

This section describes the updated sketch. The work it describes is very much in the same spirit as other recent refactors. The refinements to the existing code and interfaces are largely necessary for the first-cut work, but they are also a big win for overall code quality.

Daniel's "vibe" comment: Most of the ambiguities and design rough edges are starting to feel resolved. This stuff has been quite tricky to get a full handle on and to design clean interfaces and types for. But the slow, careful chipping away is paying off.

We break it down into three layers:

```python
# Core: state products.  bc/walk.py
@dataclass(frozen=True)
class WalkFrame:
    t: int
    obs: np.ndarray
    legality_mask: np.ndarray
    board_mask: np.ndarray            # same array every frame, built once per game
    def to_dict(self) -> dict[str, np.ndarray]: ...

class PerspectiveWalk:                # name tentative
    # Setup: init_memory, bfs cache, board_mask, next_t = 0.
    def __init__(self, sim, slot, H, W, obs_cfg): ...
    # Per tick: assert t is next in order, then visibility, step_memory, build_obs, build_mask.
    def frame(self, t: int) -> WalkFrame: ...

def walk(sim, perspective: PerspectiveMeta, obs_cfg) -> Iterator[WalkFrame]:
    w = PerspectiveWalk(sim, perspective.slot, H, W, obs_cfg)
    for t in range(perspective.end_t):
        yield w.frame(t)


# Tail: targets and metrics columns, numpy. new module
@dataclass(frozen=True)
class FrameEmission:                  # name tentative
    action_target: ...
    is_pass: ...
    value_target: ...
    alive_mask: np.ndarray | None
    aux: dict[str, np.ndarray] | None
    def to_dict(self) -> dict[str, Any]: ...

def emit_frame(sim, t, W, perspective, spec: PartialEmitSpec, pre: EmitPrecompute) -> FrameEmission: ...


# Pack: torch.  bc/encode_frame.py
def pack_sample(frame: WalkFrame, emission: FrameEmission, frame_meta, sim_frame) -> TrainingSample: ...
```

The tail's inputs are: sim, tick, perspective, spec, and per-game precompute. It does not take the walk core's outputs (obs and the masks), which 8.23-3 had floated as tail inputs, and it computes only the targets and metrics columns. This matches the product split in the findings above: the state products and the targets are separate groups with separate consumers. Another consequence is that the targets goldens can skip the obs build entirely.

Previously, 7.23-1 decided that targets are computed on the consumer side, outside the walk core. With prod and the goldens sharing the tail emission, that decision holds in a softer form: the tail is a separate function that consumers call per frame, after receiving the frame from the walk core.

Status: the three-layer shape is settled for the build. Sections 4 to 6 below describe smaller design decisions within this framing: how the core is built, the tail's signature and types, the registry loader.

Who calls what:

```python
# Obs golden (unchanged)
frames = list(walk(sim, persp, entry.cfg))

# Targets golden
pre = precompute_for(spec, sim)
per_t = [emit_frame(sim, t, W, persp, spec, pre).to_dict() for t in range(persp.end_t)]

# encode_frame, before the dataset migration. Byte-identical to today's code.
frame = WalkFrame(t, build_obs(...), build_mask(...), board_mask)
return pack_sample(frame, emit_frame(sim, t, W, perspective, spec.partial, pre), frame_meta, sim_frame)

# _walk, after the migration
for frame in walk(sim, persp, spec.obs):
    emission = emit_frame(sim, frame.t, game.W, persp, spec.partial, pre)
    yield pack_sample(frame, emission, frame_meta, sim_frame).to_dict()

# Doc note: `spec.partial` is the accessor described in §6
```

In the dataset migration, the loop and kernel calls in the prod `_walk` are replaced with iteration over the new shared walk core.

Once the tail is extracted (build order below), `encode_frame` does three things: build the state products, call the tail, pack. Until the dataset migration, it will call the kernels directly.

**Why "emit", not "targets", for the tail.** `alive_mask` is a MetricsConfig request, emitted whether or not a loss needs it, and future MetricsConfig fields will be measurement-only. A tail named after targets would be inaccurate from the start. This is the same reason 8.23-3 changed the name of one registry axis from "target config points" to "emit points" (tentative). The "emit" naming is then shared across `EmitSpec`, `emit_frame`, `FrameEmission`, and that registry axis.

## 3. Walk contract (candidate)

The core yields what is needed to **take action**: run the forward and decode a move. The tail yields what is needed only to **train or measure**.

Checking this framing against the full list of per-frame products:

| product | needed to | layer |
|---|---|---|
| obs, board_mask | run the forward | core |
| legality_mask | decode a move | core |
| action_target, is_pass, value_target, aux targets | train (loss inputs) | tail |
| alive_mask | train (time_bin loss) or measure | tail |
| frame_meta, sim_frame | bookkeeping, analysis transport | pack, dataset-side |

Currently, the only "action-based" consumer is live inference. It needs all of the proposed walk core outputs and none from the tail. This makes it the only concrete check of the first half of the rule.

Two earlier attempts to precisely conceptualize the contract didn't hold up. 8.23-3's "the model's per-frame inputs" names the legality mask as one, which the findings above showed is not the case. A second candidate, "derived from the game state alone", put `alive_mask` in the core (despite no consumers needing it) and said nothing useful about the board mask.

There is one known edge case. A future target that reads `MemoryState` (staleness, belief gap) would be a train-side product that needs core internals. The frame would expose `vis` or the memory state, as 8.23-3 noted. Memory is mutated in place, so such a reference is valid only until the next frame.

Status: a lean. It fits every product in the survey. It has not yet been tested by new code and Daniel hasn't pressure-tested the framing in depth.

## 4. The walk core

### 4.1 A class, with the generator on top

The per-tick body moves into a small class (`PerspectiveWalk`, name tentative) with a recorded-game constructor and a `frame(t)` method. `walk()` stays as the generator the goldens and the dataset use. Four reasons:

- The per-tick body gets one named home, instead of "the loop body of `walk`".
- The in-order guard (frames must be requested in tick order) is written once. Today inference asserts it and the dataset does not.
- `board_mask` is built once per game and reused.
- The inference refactor (§8) becomes "replace the duplicated block with `frame(t)`", with no core changes.

Consumers see only `walk()` and `WalkFrame`, so the class could be added later without consumer churn. Shaping it now costs about twenty lines and settles the interface that the inference refactor will build on. The live setup variant (`init_memory_common` with incremental appends) belongs to that work, not to the cut.

### 4.2 `board_mask` on the frame

Our model is designed to handle a max board size of 32x32, and we pad smaller boards to that size. `board_mask` is the binary mask for the board tiles that are active during a given game (i.e. it "unpads", so to speak). This mask is constant per game, yet it is rebuilt every tick (in both `encode_frame` and `inference.py`).

The proposed walk core will build it once per game and put it on every `WalkFrame`. This is a relatively minor optimization, as the mask is small, but the resulting code structure should feel sharper. We will then have a clear place for data that only varies at the game level.

The legality mask cannot be cached the same way, as it depends on dynamic game state (source tile ownership and army count). The static factors (mountains and the board bounds) are small and not worth optimizing.

### 4.3 Renames

- `mask` → `legality_mask` — Binary mask for move action space, identifying which moves are legal.
- `valid_mask` → `board_mask` — Binary mask for which cells are part of the actual board for the current game. It's static per-game.

These renames are tentative. The old names are a bit vague and easy to mix up. Daniel wanted to "test out" the new names, so we used them during the design work that led to this doc.

Implementing the full rename would be a fairly large change. The names are used across the codebase. For example: the sample dict keys, the loss, eval, the dump, inference, the goldens keyset and reference keys, and fq's `emit_cols`.

The data-facing names (the sample dict keys, the goldens reference keys, fq's `emit_cols`) should change in one byte-preserving commit, ideally before the first bless: renaming a reference key would require a re-bless or a migration.

Status: open. The lean is to write new code with the new names and convert the code-only uses (variables, docstrings, and the like) as we touch them.

### 4.4 The walk-versus-probe byte compare

Queued in 8.23-3 and not yet done. Everything in this note builds on `walk.py`, and its output has not been verified against the goldens probe walk (`goldens_probe/`). This will be a one-off over a few corpus games, and it should be done early on.

## 5. The tail

This section covers the tail's design details. We discuss the signature, return value, and three smaller matters: converting the aux targets to numpy, where dtypes are declared, and the perf timer.

**Signature.** `emit_frame(sim, t, W, perspective, spec, pre)`. It needs `W` (for `policy_pass_target`), the perspective (placement and slot order), the partial spec (see below), and the per-game precompute. Whether it takes `GameMeta` or a bare `W` is open and small: once `board_mask` moves from `encode_frame` to the walk core, `W` is the only thing it reads from the game.

**Return value.** `FrameEmission` with a flat `to_dict()` (aux targets merged in at the top level). fq's `emit_cols` reads emitted fields by string key, and the parity test iterates keys, so both `FrameEmission` and `WalkFrame` keep a dict view.

**Aux targets (lean).** The tail is numpy throughout, but the aux-head `encode_targets` methods return torch tensors (mostly `from_numpy` wraps). 8.23-3 left two options: return a mixed numpy/torch result, or convert back to numpy. The lean is convert. The tail calls `.numpy()` on them, so `FrameEmission` is uniformly numpy. The round trip is free, as `.numpy()` and `from_numpy` share memory (no data is copied).

Rewriting the aux encode to produce numpy directly is deferred to the aux-heads restructure (8.23-1 §7).

**Dtype authority (open, lean yes).** Today `compute_targets` declares dtypes by hand, and two TODOs ask where goldens dtypes should live. With one shared tail, the tail is the authority: `FrameEmission` fields carry fixed numpy dtypes, and `pack_sample` and the goldens inherit them. That includes the scalars (`action_target`, `is_pass`, `value_target`, next_death's two scalars), whose dtypes are chosen at `torch.tensor(..., dtype=)` sites today. It closes both TODOs, and it removes most of the reason for a per-key dtype table (8.12-2 §8's option (b)), since the dtypes would live on `FrameEmission` instead. A dtype change after the first bless is a re-bless, so settle this before it.

**Timer.** The `encode_tail` timer section stays in `encode_frame`, around the tail call and `pack_sample`. The tail does not import `timer`.

## 6. Types and the registry loader

This section covers the type the tail takes as its spec, how the registry loader produces it, and two cleanups around it.

**`PartialEmitSpec` is the tail's input.** `EmitSpec` has five fields: `obs`, `targets`, `emit_alive_mask`, `emit_frame_info`, and `attach_sim_frame`. Of these, `emit_frame` and `precompute_for` read only `targets` and `emit_alive_mask`. The other three are consumed elsewhere: `obs` by the walk core, and `emit_frame_info` and `attach_sim_frame` by the packing step. So the tail needs only a two-field subset of the spec.

That same two-field subset is what the registry stores per emit point (8.23-3's stored shape). And a type for it already exists: `PartialEmitSpec`, which fq uses to describe an emission without an obs config. It carries `targets` and `emit_alive_mask`, and also `attach_sim_frame`, which is a mismatch (discussed below).

Making `PartialEmitSpec` the tail's spec type has three consequences:

- `EmitSpec` gains an accessor that returns its partial (shown as `spec.partial` in the sketch above, name open). Prod code builds a full `EmitSpec` as it does today and hands the partial to the tail. `EmitSpec` keeps its fields as they are, so existing `spec.targets` reads don't change.
- `precompute_for` takes the partial instead of the full spec, since it also reads only those two fields.
- The targets golden calls the tail with a `PartialEmitSpec` loaded from the registry. It does not need to build a full `EmitSpec`, which would require an `obs` config it doesn't have.

**The registry loader.** A stored point `{"targets": {...}, "emit_alive_mask": bool}` becomes `TargetsConfig(**d["targets"])` under the strict-keys assert, then `PartialEmitSpec(targets, emit_alive_mask, attach_sim_frame=False)`. `TargetsEntry` holds the partial instead of separate `cfg` and `emit_alive_mask` fields. 8.23-3's "no defaults" drift check now applies to `PartialEmitSpec`. The "store facts, not sources" decision is unchanged.

**`attach_sim_frame` does not belong on the partial.** It tells the dataset to put the raw `SimFrame` on the sample. That is a transport detail decided by `build_frame_table`, not by the author of a `FrameTableSpec`, and `build_frame_table` already asserts it is True. The fix is to drop it from `PartialEmitSpec`, make it a `to_spec` kwarg, and have `build_frame_table` pass `True` at its one `to_spec` call (should be small edits). This cleanup is not part of the cut. Until then the tail ignores the field and the loader pins it as False.

**Renaming `PartialEmitSpec` to `EmitPoint`.** Deferred. The "emit point" vocabulary is not settled.

## 7. Goldens consequences

### 7.1 Per-point targets references

The union layout is dropped (see the findings above). Two per-point layouts are open:

- **(a) One npz per (point × fixture)**, matching obs. This is the simplest code: no union and no merge step, and `compare_targets` compares a whole file (the `legality_mask` key is still compared by hash). The cost is that shared keys are stored once per point, so the size is roughly 2× to 4× today's 15 to 25 KB per fixture (8.12-1 §4), at most 1 MB on disk at ten fixtures (could be as low as 300 KB). Re-bless churn for shared keys grows by the same factor.
- **(b) One `.npy` per (point × fixture × key).** This has the same generality as (a). Git dedups identical arrays across points by content hash, so the pack cost is about the same as the union layout's, avoiding (a)'s 2× to 4× growth. The cost is file sprawl (about 250 files at ten fixtures) and per-key loading. An npz can't get this dedup, because a zip is one blob.

Under either layout:

- The keyset table becomes the set of keys in each point's file.
- The bundle-contents structural check becomes a per-file check.
- Regen writes one file per (point, fixture), with no merge step. It still runs the tail once per point, since time_bin and next_death are exclusive variants and no single spec produces every key.
- The legality-mask hashes are stored in each point's file like any other key.

It's helpful to think about two key questions that we are answering with the designs in this doc. The first is which layer computes a product (core or tail). And the second is whether a product varies with config point, fixture, or both.

The two are independent. The legality mask shows this. By the first question it is a core product. By the second, it depends only on the sim and `t`, so it varies with the fixture and not with any config point. Obs is also a core product, but it varies with both. The targets are tail products and also vary with both.

The reference layout is organized by the second question. Each reference file is keyed by (point × fixture), and a product goes in whichever file guards it, regardless of which layer computes it. That is why the legality-mask hashes are stored in the targets references alongside the tail's products, even though the core computes the mask.

### 7.2 `compute_targets`

This new function created for the golden tests currently re-implements logic that already exists in the training flow:

- per-game precompute (`make_elim_ctx`, `precompute_player_status`)
- per-frame dispatch (`policy_pass_target`, `value_target`, `make_alive_mask`, the variant branch)

After refactoring, it should look something like this:

```python
def compute_targets(sim, game, persp, entry):
    spec = entry.spec                                    # PartialEmitSpec, attach pinned False
    pre = precompute_for(spec, sim)
    per_t = [emit_frame(sim, t, game.W, persp, spec, pre).to_dict() for t in range(persp.end_t)]
    out = {k: np.stack([d[k] for d in per_t]) for k in per_t[0]}
    out["legality_mask"] = np.stack([build_mask(sim, t, persp.slot, game.H, game.W) for t in range(persp.end_t)])
    return out
```

Three things stay goldens-side: the loop over `t`, stacking per-frame values into `[T, ...]`, and the legality-mask stack. The mask is a state product, so it comes from `build_mask` rather than the tail.

In the current draft for `compute_targets`, we hand-typed the key names, and nothing ties them to the `TrainingSample` keys in prod. After the refactor, the key names will come from the shared tail's `FrameEmission.to_dict`. This lets the goldens and prod stay in sync by construction.

One consequence is that `compute_targets` will import torch through the tail. Being able to do this refactor without resolving that torch import is an early win for the relaxation of the torch-free constraint (see 8.23-1).

**Minor additional note**: by default, `value_target` is `[T]` in the golden references, because the tail emits one value per frame and the goldens stack them. The alternative would be to store it as a scalar (it is constant per-perspective). This is an open decision for the first-cut work (not new, listed as a build-time pick in 8.12-2 §8).

### 7.3 The parity test (lean)

The parity test guards the one seam the two paths don't share. Before the dataset migration, the goldens path runs the core walk and then the tail, while the prod path runs `_walk`'s own loop and `encode_frame`'s own kernel calls before the same tail. So the test's scope is the walk seam: the loop and the kernel-call sites.

After the migration, both paths run the same code, and the test is trivially true. 7.23-1 §4 left open what happens to the test at that point. With the tail shared, the lean is to delete it then.

### 7.4 Unchanged by this note

`board_mask` is not guarded (it derives from `H` and `W`, and the obs channel summary catches a board-shape change). The torch guards (thread-pin assert and canary, 8.23-2 §4) are still required, because the tail imports torch through `spec_for`.

## 8. Parked follow-ups

**Live inference** (high priority after the cut). `encode` reduces to the three live-only steps and a call to `frame(t)` on the core class. The third step (scoreboard rows, player-status refresh) writes `MemoryState` fields directly and should become a method on it (something like `append_tick`). This needs the live setup variant for the class (see the walk core section above).

**Analysis toolkits.** fq calls the core and the tail directly, which removes the numpy → torch → numpy round trip and the dataset workarounds, as 7.23-1 §6 planned. The probe toolkit is not a walk consumer in that plan, and nothing here changes that. Nothing is needed now beyond the `to_dict` views described in the tail section.

**`attach_sim_frame` cleanup.** Described in the types section above.

## 9. Build order

Every step that touches the dataset path is verified against the baseline byte dump (`tmp/dataset-refactor-byte-compare/`), as the 8.16 restructure was. A plausible order:

1. Extract `emit_frame` and `pack_sample` from `encode_frame`. This is byte-identical to today's code.
2. `compute_targets` delegates to them.
3. The core class and `board_mask` on the frame.
4. `precompute_for` takes the partial, `EmitSpec` gains the accessor, and the registry loader produces a `PartialEmitSpec` that `TargetsEntry` holds (§6).
5. The renames, as their own commit.

The walk-versus-probe compare (§4.4) goes early, before step 3 at the latest. Outside this order: the per-point reference layout (§7.1) lands with the registry transcription and regen, and the dataset migration (§2) stays a post-cut follow-up.

## Appendix A. Small picks and opens

- `GameMeta` vs. bare `W` in the tail's signature (§5).
- `value_target` scalar vs. `[T]` (§7.2).
- The class name (`PerspectiveWalk` or other), and the 8.23-3 "two names" question: class, `walk()`, dataset `_walk`.
- The live setup variant for the class: two constructors, or a prepared `MemoryState` passed in (§8).
- The `MemoryState` exposure for a memory-derived target, and its in-place mutation hazard (§3).
- A name for the whole slice (core, tail, and pack together). "Emission" names only the tail's output. "Frame pipeline" is a candidate to consider.
