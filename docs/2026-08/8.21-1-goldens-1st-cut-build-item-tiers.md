# Behavior goldens first-cut — build item tiers

**Framing / mindset for next session or two**: I'd like to focus on exploring, sketching, and refining the outlines and key interfaces of the main parts of the system. By default, we are **not** building full the detailed implementations for each part, at this stage. It's **completely acceptable and expected** for us to be in an partially complete / non-working state as we progress.

## Breaking the work into tiers

- Tier 1 — We can start here. These items are more settled by existing docs and previous design sessions. The actual code should be less complex as well. 
- Tier 2 — Middle group. Compared to tier 1, these are less specified by existing design notes, have more complexity, and will likely be harder to do.
- Tier 3 — Saved for last. Reasoning: These items (1) have the most ambiguity and open design questions (2) may have more finicky details and implementation complexity or (3) are less critical leaf node of the system that that build off of the other pieces.

These tiers is a very loose, ad-hoc sketch. We can move items around easily and change the order. But you need to start somewhere, and the list is a quick guess at how it could go.

These items are not also not exhaustive. E.g. For example, fixture selection tooling is not listed (currently planned as one of the last implementation tasks).

### Tier 1

- TargetsConfig **(mostly done)**.  Small by itself and straight-forward, in isolation. See design sketch (7.28-2).
  - **Update**: This is mostly done, see recent commits. It isn't fully integrated into TrainConfig or the stored config block in the checkpoint, as that requires config version bump (our first real one).
    - See `TODO(config-bump)` for some notes in the code about this.
    - The config bump shouldn't be a blocker for finishing the first cut work.
- The registry module. This is one of the most core pieces of the system. See design sketch (8.12-2).
  - Details: config-point dicts, keyset table, fixture list, the three record types (FixtureRecord, ObsEntry, TargetsEntry), and the public API for the module.
- The environment record.
  - Most likely, will consist of the persisted record, a tiny dataclass to match it, and the corresponding environment test. TBD if there are any other details.
  - The record itself could be JSON, but the format hasn't been discussed or ratified. List of fields is enumerated in 7.15-2 §4.

### Tier 2

- The actual core tests: golden test functions + structural tests.
  - Parametrization over registry entries, the unblessed-fail path, and the structural checks from 8.12-2 §5.
  - Bodies are comments only. Sketching these validates that the registry interface actually serves its consumers.
- Shared walk core API. One signature for the walk (7.23-1 §3, updated for SimFrame/PerspectiveMeta) 
- The hash builders. The frame/channel hash functions.
  - The 7.15-1 probe has a proof of concept we can take a look at (see:  `goldens_probe/layers.py` ). We **will not** blindly copy that code, as it was written in as a one-off without careful design work.

The shared walk core and the hash builders are not fully settled and should receive some care when sketching.  The yield shape and context-bundle contents are explicitly "confirm at build time" in 7.23-1. The recent refactors will affect how these might land. So these items will need  thoughtful discussion. And we should expect to refine the interfaces with the learnings from the first pass of Tier 3 .
