# Checkpoint & config versioning — critical open questions

*Date: 2026-06-26. The short list of high-leverage decisions that gate the **broader** checkpoint-config design — the ones to settle before committing past chunk-1. Framed as decisions to make, not answered here. Chunk-1 ([6.26-6](6.26-6-checkpoint-config-chunk-1-sketch.md)) is deliberately decoupled from them: it reserves placeholders and keeps the tier machinery as empty structure, so its shape is robust to either resolution. The concepts these decisions rest on are developed in the synthesis ([6.26-5](6.26-5-checkpoint-config-synthesis.md)).*

The two questions are **linked** — Q2's answer largely determines Q1 — so they are best decided together, Q2 first.

## Q1 — Fidelity scope: how many version-boundaries do we keep fidelity across?

Once the codebase starts erecting barriers (non-additive changes that old checkpoints can't be carried past), across how many of them do we maintain the ability to faithfully run an old checkpoint? It is the single lever behind barriers, the Native / Compat / Unsupported tiers, migration granularity (stepwise / squash), and a supported-version short-list.

**What's at stake.** It sets the size of the Compat burden and how much fidelity machinery we build (the Compat builder, golden tests, arch-fidelity enforcement). Keep-fidelity-across-everything is the maximum, unbounded burden; keep-a-recent-window and declare-the-tail-Unsupported is bounded.

**The shape of the decision.** Stepwise-frozen across the supported range; squash or drop (→ Unsupported) the old range. The backward case (support a curated historical subset) just scopes the v0 normalizer and leans on the Unsupported tier — no architecture change. The forward case (support a subset of future checkpoints) bounds the Compat burden, with one trap to avoid: "re-save blessed checkpoints forward to keep them current" updates only config-*shape*, not arch-*behavior*, so it does not escape an arch barrier.

**Where we already lean.** Artifact fidelity for a curated/recent set, with a declared-Unsupported tail to keep Compat manageable. The open part is the precise scope — which set is "blessed," and how aggressively the tail moves to Unsupported.

### Part B (the upstream framing) — accept barriers, or push additive-gated-forever?

A lesser-emphasized but real prior fork: the whole apparatus shrinks if we push additive-gating hard — never delete, manage the sprawl via spec-ification — keeping everything Native and erecting no barriers at all.

A clarification that makes this more viable than it first looks: **a barrier is always a choice, never forced.** Even a bug fix doesn't force one — we can keep the "buggy" path alive like any legacy code (preserving fidelity for checkpoints trained against it), or, if the bug is bad enough that those checkpoints aren't worth running again, declare them Unsupported. So the real question is not "can we avoid barriers" (we can) but "how hard do we push additive-gating before the accretion cost outweighs erecting a barrier." Part B sets that default stance; Q1's headline calibrates the scope once a barrier is accepted.

## Q2 — Co-residency strategy: in-process Compat vs. a repo-copy orchestrator

**The firm requirement.** The eval workflow needs old and new checkpoints co-resident in one process — two checkpoints playing each other in a sweep. This is artifact comparison (the specific trained weights), so it can't be sidestepped by re-running recipes under current code.

**Why it's the hinge.** Co-residency forbids the cheapest fidelity strategy — pin a SHA per checkpoint and check out its code to run it — because two code versions can't be live in one process by checkout. That is precisely what forces keeping old code alive in `main` (the Compat tier). And if a repo-copy approach makes checkout-based co-residency cheap, it largely *answers* Q1 by removing the in-`main` Compat burden — which is why Q2 comes first.

**The two strategies.**

- **In-process Compat** — keep old behavior alive in `main` (the Compat tier / configurable builder). Cost: ongoing maintenance, and the accretion this whole effort is trying to contain.
- **Repo-copy orchestrator** — run each checkpoint in its own pinned repo copy, coordinated through a thin control layer over a frozen wire protocol at the *game-state* level (each copy builds its own obs and runs its own model; the orchestrator passes only game-state and moves). If cheap, it revives pin-SHA-checkout for the co-resident case.

**Repo-copy sharp edges** (why it might not be cheap): per-version *environment* reconstruction — dependencies, not just code, so N venvs; the orchestration plumbing; and migrating the eval path from in-process model handles to RPC.

**Repo-copy scope limit.** It covers *gameplay* co-residency (models playing via moves) but not *introspection* co-residency — the probe path reaches *inside* a model (extracting the trunk), which doesn't cross an RPC boundary cleanly. So even if repo-copy wins for gameplay, cross-version introspection needs something else, or we accept single-version introspection.
