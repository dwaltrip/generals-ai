# fq ↔ probe convergence: a materialize → train substrate

*Date: 2026-06-17. Status: design / direction. This doc is the map, not a committed refactor. The near-term commitment is small — one modest step pulled into existence by the argmin toy experiments (§7). Everything larger here is trigger-gated on a real second consumer, per fq's own "let the second consumer pull the abstraction" principle.*

## 1. Thesis

The `fq` analysis toolkit and the frozen-representation probe framework were built separately, for different jobs — fq to kill val-split-walk boilerplate for numpy analysis, the probe framework to ask "is signal X decodable from representation Y, at what capacity." Looked at by structural affordance — what the code is close to becoming — they are **two halves of one `materialize → train` pipeline**, converging on a shared substrate from opposite sides. fq approaches it from the data side; the probe framework from the training side.

Two independently-motivated tools converging is itself evidence that the shared substrate (the "waist") is real, rather than an abstraction we are inventing to justify a merge.

The convergence is **additive**: we factor out a shared waist and keep each tool's first-class uses distinct and well-furnished. The goal is not to blend two tools into one general-purpose tool that does neither job well — that would degrade both. §4 (use cases) and its rule discussion exist to hold that line.

## 2. The duality at the center

The probe framework's in-memory training container and fq's analysis container are the same object viewed two ways.

```
ProbeCache:  feats[N,C,H,W]   target[N,…]   aux{name→[N,…]}              (torch; no provenance)
FrameTable:  cols{name→[N,…]}                            persp_val_index, frame_t, game_id   (numpy; + provenance)
```

`ProbeCache` is a `FrameTable` in which one column is privileged as `feats`, one as `target`, and the rest as `aux` — minus provenance, in torch instead of numpy. The privileging is a **training-time role assignment**, not a fundamental difference in the data.

Two consequences follow:

- `FeatureSource` is a special case of a `Deriver`. A frozen-trunk feature is just another canonical per-frame quantity — an obs-reading, *model-running* deriver that adds a `trunk_feats` column. (How cleanly this actually fits fq is an open question — see §6.)
- `ProbeTask` factors into `{target deriver}` + `{models, loss, metrics}`. The "which signal" is a derived column; the rest is the training spec.

Run that to its conclusion and the probe framework, fully matured, reduces to `fq (materialize, including model-running derivers)` + `a training engine (sweep small models over a role-assigned table)`. fq owns the better *data model* (named columns, provenance, canonical single-source derivers, representativeness guards). The probe framework owns the *training engine* and the *furniture that sits on top of it as configs*.

## 3. The waist (the shared substrate)

Three layers, with the containers *layered* rather than merged:

- **`FrameTable` (fq)** — the source. Numpy columns + provenance. Training-agnostic; knows nothing about models or loss.
- **role-assignment view** — a thin "these columns are inputs, this is the target, these are aux" wrapper that the *engine* owns (not fq). Keeps fq pure.
- **device tensor bundle** — the engine builds this from a table view for one training run. This is what `ProbeCache` becomes: demoted from "the source" to "the training-time materialization of a row set." `FrameTable` and `ProbeCache` are not unified into one object; they are *source* and *training-time materialization* of the same rows.

The **training engine** is then: *train a sweep of small models over `(table view, models, loss, metrics)`* — cache to device, run the AdamW train/eval loop, record per-epoch curves and metrics. Today this is `cache_probe_features` + `train_probe_head` + `run_probe`; maturing it means replacing the bespoke walk in `cache_probe_features` with "fq table → device bundle," and generalizing the loop's single privileged `feats` tensor to a role-assigned set of input columns. That is a small generalization of code that already exists, not a rewrite.

**Dependency direction, always:** `engine → fq`, never the reverse. fq never imports the training engine. Shared definitions sit in neutral homes that both import (the same rule the existing design already set for `FrameNeeds`).

### The rules, judged against the use cases

Most rules are instrumental — they serve a use case and are relaxable when a use case says so. Two are near-intrinsic *guards*, and even those are justified by concrete cost, not dogma.

- **fq-standalone (serves F1) — near-intrinsic.** The moment fq needs a checkpoint or the training engine to answer a question, F1 dies. So keep the dependency direction (`engine → fq`) — for a use-case reason, not purity.
- **Don't re-implement pandas badly — near-intrinsic scope guard.** Data-processing libraries are a famously deep well of edge cases; a half-reimplemented one is worse than none. So `FrameTable` stays a dumb columnar container and analyses drop to numpy / `pd.DataFrame(t.cols)`. The carve-out: a *super-tight, well-contained thin helper is fine if it demonstrably cannot spill into pandas-reimplementation*. `subset(table, mask)` is safe; a `groupby`/`agg`/`merge`/`pivot` surface is the top of the slope and stays out. This rule is held on engineering risk, not aesthetics.
- **"Derivers are lightweight, dependency-light" — instrumental, and a use case actively pushes to relax it.** The trunk-feature-as-a-column idea (P1/P4 on the unified stack) wants fq to run a model-forward deriver — heavy, torch-model-dependent. Relax the rule exactly as far as the use case demands and no further: model-derivers may exist, but **opt-in**, so F1's light path stays light. The rule becomes "the *base* table is light; model-derivers are an opt-in tier," not "no heavy derivers ever." (Where that tier should live is open — §6.)
- **"Dumb container, no groupby/agg" — held because nothing is *blocked*, not because of purity.** Game-clustered CIs and margin-binning (P3) *want* group-and-aggregate, but numpy at the consumer serves them — more verbose, not blocked. A `groupby`/`agg`/`merge`/`pivot` surface is where reimplementing pandas begins, and stays out. If a real use case is ever blocked, drop the rule without ceremony (subject to the pandas guard above).
- **"Probe decodability stays first-class" — not a structural rule at all, it is P1/P2.** A refactor that generalizes the engine but keeps "point at a checkpoint, ask is-it-decodable" crisp is fine; one that makes P1 clunkier in the name of merging is not. The test is the use case, not the structure.

## 5. Relationship to the prod training loop

There are effectively three loops: prod (`bc/train.py` — `TrainConfig`, `BCModel`, `bc_loss`, the streaming `DataLoader`, MFU instrumentation, checkpointing, Modal), the probe/analysis engine (small models on cached features), and — emerging — the unified training engine of §3. The question is how much the analysis engine and prod should share.

The answer turns on splitting "similar" into two kinds:

- **Semantic similarity** — same *loss*, same *metric*, same *model module*, same *data quantity*. You want this; divergence here is a correctness bug. The clearest example: the probe's `masked_cross_player_ce` is a hand-kept copy of the prod elim loss in `bc/loss.py` — two definitions meant to be identical, kept in sync by discipline. That is a latent version of the army-from-sim/obs bug F2 was built to kill.
- **Mechanical similarity** — same optimizer-step code, batching, epoch driver, checkpointing. You do not need this and should not force it. Prod is streaming-throughput-bound (workers, autocast, MFU, a moving target being learned); analysis is cached-measurement-bound (in-RAM, single-process, frozen substrate, weight inspection, sample-complexity subsetting). The mechanics do not change *what is measured*, only how fast.

**Governing principle: maximize semantic sharing, minimize mechanical coupling.** The analysis engine is semantically faithful to prod (imports the same definitions) but mechanically independent (owns its own loop). Prod sits *outside* the waist; it connects to the convergence only through the shared definition layer and the shared data format (use case X is the proof — online analysis touches prod's state, shares definitions and columns, never the loop).

The detail that matters: a definition gets single-sourced **exactly when a use case requires the analysis result to be faithful to prod** — not "all losses/metrics live in a shared home."

- Cross-player CE: **share** — the toy proxies the elim head (P3 faithfulness) and decodability probes measure the *deployed* head's trainability (P1). Both demand the same loss as prod.
- A tie-aware accuracy or a `W ≈ −I` weight check: **do not share** — a new measurement with no prod counterpart; a shared home would be busywork.
- The army quantity: **already shared** (F2), because cross-analysis agreement demands it.

The sharing boundary is drawn per-definition by faithfulness-requirement, not by type.

## 6. Open questions

- **Where model-running derivers live (the sharpest one).** `FeatureSource ⊂ Deriver` is clean as a statement but collides with fq's lightweight-deriver grain: a trunk-feature deriver is a heavy torch model-forward with a model dependency. Options: a separate "model deriver" tier; ride the deferred lazy-obs `FrameView` (Option-2) path; or `FeatureSource` simply stays as the probe framework's furniture and never retires into fq. Resolve when the §9 (P4) consumer exists, not before.
- **Synthetic / analytic row source (F5).** Should `build_frame_table` accept row sources other than a dataset walk (a generator of controlled distributions)? The toy's analytic labels are the pull. Extrapolation can be had from *filtered real frames* for now, so this is anticipated, not demanded.
- **The neutral home for shared definitions.** Where do single-sourced losses/metrics that must match prod live, such that prod, the analysis engine, and fq all import without circular dependencies? (`FrameNeeds` already has this question on the table; the cross-player CE is the next item.)
- **Exact semantic-share boundary cases.** §5 names the principle; the per-definition calls beyond the three examples need to be made as they come up.
- **What triggers the probe migration.** When does the probe framework's bespoke walk actually move onto the fq table + role-assigned engine? Gated on the engine proving out on a real consumer (the toy is the first; P4 is the one that exercises the trunk-feature path).

## 7. Worked example: the argmin toy

The argmin-toy experiments (design in the 6.17-1 / 6.17-2 docs) are the first consumer that instantiates the waist, and a good test of whether the picture holds. The task: from one frame, predict the index of the alive player with the smallest army — a deliberately isolated cross-player-comparison step, studied across input encodings and architectures.

How it maps to the waist:

- **fq materializes** a per-frame table: `army[8]`, `land[8]`, `alive[8]`, `label` (lowest-index argmin over alive), `margin` (bottom-two gap), `n_alive`, `game_id`. The label and margin already exist as derived columns; only a land deriver is new. This makes the toy **fq's first training consumer (F4)**.
- **The engine sweeps** the model ladder (the linear / equivariant / shared-φ / pooled-MLP / flatten families) over that table, with tie-aware metrics and weight inspection. This is **P3** — learning dynamics on a known-decodable signal.

The modest first step it pulls into existence (the only near-term commitment):

- A land deriver and a lean toy `FrameTableSpec` — small, unambiguously on-fq's-gradient, reusing the existing label/margin derived columns.
- A training loop written to read a table + an explicit role-assignment, rather than hardcoding `army`/`alive` — the *seed of the table-reading engine*, sidestepping the `ProbeCache` costume (the toy's player-axis models take real inputs, not a vestigial `feats`), and promotable later if the §9 consumer pulls it.
- Single-sourcing the cross-player CE into a neutral home (the one definition the toy's faithfulness to the elim head demands — §5).

Explicitly deferred to their trigger consumers: `FeatureSource → deriver` (model-running derivers), migrating the probe framework's walk onto the engine, the synthetic row source, the lazy-obs `FrameView`, and table caching. None are needed for the toy; all fall out for free once a real consumer demands them.

The concrete build steps for the toy are a separate follow-up doc, written with this direction in hand so the small step we take is the *first inch of the right path* rather than a throwaway.
