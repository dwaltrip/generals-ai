## Setup

Four BC trunks, identical except the `arch` width block, fanned out as parallel Modal jobs on A100. Recipe: bs=512, lr=3e-4, weight_decay=1e-4, fp16 (`precision=auto`), seed=0, `value_head=pyramid`, `shuffle_buffer_size=2048`. Data: `cloud_24k` slice (manifest `cloud_24k.json`, intermediate `intermediate-cloud-20k`), `filter_version=v2`, `git_sha=aa32be2`, 22,464 train / 1,182 val pairs.

Launched with `./training/scripts/width_sweep_2026-05-31.sh --epochs 3 --max-batches 1000`. That's more than the plan baked in (plan: `epochs=2, max_batches=800`); as-run is 3 epochs × 1000 batches × 512 = ~1.54M sample-draws per cell, ~3h wall-clock each (non-uniform across cells).

## Width nomenclature

The canonical reference is **width relative to the DeepNash paper architecture** (256/256/320 = 1×). The sweep's launch script re-anchored "1×" onto the current PoC width (128/128/160), which doubled every label — so the sweep's "2×" is actually the *paper's* width, and the sweep's "0.5×" is a quarter of it. Both labels appear in the tables below; the DeepNash-relative column is the one to reason with. The current PoC is **0.5× DeepNash** (128/128/160).

## Reading the result: undertrained, not overfit

The full-width regression is an optimization shortfall, **not overfitting.** The diagnostic: the 1× (paper) cell is worse than 0.75× on *training* policy loss too (E3 train 1.1486 vs 1.0793) — a bigger model fitting the *training* data less well hasn't converged, which rules out overfitting. Its val_policy is still dropping steeply (1.31 → 1.22 → 1.16), nowhere near saturation. The leading explanation is **undertraining** — at fixed lr=3e-4 and only 3 epochs, the 19.7M-param model didn't get the steps to use its capacity — but at one seed and one (unscaled) LR we can't cleanly separate that from an LR-too-high-at-width effect or multi-task interference (the 1× value head also trains differently; see below). What's solid is the direction: this ranking is "best at this short budget" and says nothing about which width wins at the big-run data/step budget.

Supporting reads:

- **No policy overfit — but the budget guarantees that.** Train ≈ val policy at every width (E3 gaps: 0.25× −0.002, 0.5× +0.017, 0.75× +0.014, 1× +0.012), and the gap does not grow with width — the biggest model has nearly the smallest gap. But at 3 epochs with val still descending, no cell *could* have overfit yet, so this confirms "we're not in an overfit regime," not "the wide model would generalize if trained longer."
- **The regime control did its job.** 0.25× (1.2204) is clearly worse than the PoC and above — so capacity is being used; we are *not* in a flat "width doesn't matter" regime, and the sweep can detect width effects.
- This is consistent with the data/epoch-limited regime the plan predicted, where a short sweep can't saturate the wide cells.

## Action heads (policy + pass) and the value head

Every frame the model emits one action: either *pass* or a spatial move. The **pass head** gates that choice and the **policy head** picks the move on non-pass frames — the loss computes policy CE only over non-pass frames ([`training/bc/loss.py`](../../training/bc/loss.py)). The **value head** is auxiliary: it predicts final placement and doesn't feed the action. Its metric name undersells what it is:

- **`pass`** = binary BCE on `is_pass`. Base rate `pass_frac = 0.1673`, so the constant-predict-base-rate BCE is **0.452** and the majority-class ("never pass") accuracy is **0.833**.
- **`value`** = 8-way cross-entropy over **final placement class (0–7)** in the FFA game — *not* a scalar win-value. The uniform/no-knowledge baseline is **ln(8) = 2.079 nats**. (Worth a rename someday, e.g. `placement_ce`, to stop it reading as a value-function.)

**Pass gate — clears its baselines, tracks policy, but width barely moves it.** Val BCE (0.23–0.25) and accuracy (~0.90) beat both baselines → real signal, no overfit (train ≈ val). The width ranking matches policy exactly (0.75× best, 1× regresses), so the gate corroborates the headline. But its width sensitivity is tiny: pass_acc spans only 0.7pp across a 15× FLOPs range, vs policy top1 spanning 3.6pp. **Within the action decision, capacity buys ~5× more on the spatial policy (where to move) than on the pass gate (whether to move at all)** — the gate is near-saturated.

**Value (placement) head — 3 of 4 cells memorized; one generalized.**

- **Weak generalization overall.** Val placement-CE sits ~1.6–1.98 against the 2.079 uniform baseline — only ~0.1–0.45 nats of transferable signal. Placement-from-one-frame at 22k-games scale is hard, and the head is down-weighted (λ=0.5).
- **The memorize/generalize split.** Three cells (0.25×, 0.5×, 1×) memorized — train CE collapsed to 0.67–0.93 while val stayed ~1.9 (a >1-nat gap), and the 0.5×/1× val curves are U-shaped (improved to E2, then slid back toward overfitting by E3). The **0.75× cell alone generalized**: train ≈ val (gap −0.04) with val improving monotonically (1.88 → 1.73 → 1.62).
- **Not a width effect.** The split doesn't track capacity — the *smallest* model memorized hardest (train 0.67) and the *widest* memorized too (1×, gap +1.05, worst val of all four). With n=1 per width, this reads as an optimization-basin effect, not something 0.75× reliably buys.
- **Likely driver: data scale.** The head overfits because the corpus is small; more data should suppress memorization and pull more variants into generalizing. That's a big-run-scale hypothesis, not an in-run trend — within this budget the memorizers were sliding the *wrong* way by E3.
- **Still a good sign.** Value-head generalization is uncommon across our runs, so even one clean instance is encouraging — and the overfitting is head-specific (policy and pass don't show it), so it's not the trunk. Worth chasing: a multi-seed re-run of 0.75× and 1× to separate width from a lucky basin, and a fresh look once eval moves to **4p–8p**. (The plan called the value head OOD-uninterpretable when eval was assumed 2-player; 4p–8p sits much closer to the training FFA distribution, shrinking that gap.)

## Caveats & infra

- **Non-uniform A100.** The 0.75× cell landed on an *A100 80GB PCIe*; the other three on *A100-SXM4-40GB* (`args_cloud.json`). This is a throughput confound only — same math, seed, and data, so the loss/accuracy comparison is untouched. Don't read 0.75×'s throughput against the others.
- **`num_workers=2` ⇒ low-end throughput is uninformative.** Across the three SXM4-40GB cells, train sps clusters ~276–331 despite their FLOPs spanning 15× (3.3 → 49 G) — the small models are **input-pipeline-bound** (the loader can't feed them, so their sps/MFU reflect the loader, not the model). But MFU climbs with width to **72% at 1×**, so the widest cell is *not* loader-bound — it's near compute-saturated, and its ~285 sps is close to its true rate. So treat the small-cell throughput as meaningless and the 1× number as roughly real. The loss/quality ranking is unaffected regardless (all cells shared workers=2 and a seeded data order).
- **`gpu_util.jsonl` failed in all four runs** (`nvidia-ml-py` not installed) — no fine-grained utilization telemetry this round. MFU is still derived from FLOPs/throughput.

## Full-width viability is an open throughput question

Whether the full DeepNash width (1×) is viable for the big run depends on the **samples/sec tradeoff**, which this sweep only partly informs. More FLOPs/sample buys quality but costs throughput, and throughput sets how much data the fixed compute budget can push through — so "is full-width better?" (likely yes; the 1× cell here was budget-limited, not capacity-limited) is a separate question from "is full-width affordable?"

One usable data point survives the `workers=2` bottleneck: even with the starved loader, the 1× cell hit ~285 sps / 72% MFU on a single A100 — full width nearly saturates the card's compute, so a better-fed pipeline would speed it up far less than it would the small cells, and ~285 sps is a reasonable floor. What's unmapped is the rest of the frontier: the small cells were loader-bound (their sps says nothing), and we've only probed the low end on weaker cards — on a **T4** at the PoC width (0.5× DeepNash) the dataloader was no longer the bottleneck (compute-bound, though not necessarily fully saturated). Mapping width × GPU-class throughput with a properly-fed pipeline (workers≥4) is the prerequisite to a full-width commitment.

## Possible follow-ups

- **Head-to-head eval** (the [`5.28-1`](../2026-05/5.28-1-pyramid-eval-sweep.md) protocol, temp=0.5, n≥80, swap-slots + self-vs-self floor) on the E3 checkpoints — loss is a poor skill proxy, and the close 0.5×/0.75×/1× spread is exactly what the plan said to escalate before a width commitment.
- **Give the full DeepNash width a fair shot** — longer schedule and/or tuned lr — before ruling it out; this sweep handicapped it. A **multi-seed re-run of 0.75× and 1×** would also separate the value head's one-off generalization from a real width/regime effect.
- **Re-measure throughput with `num_workers≥4`** (likely 8 on A100) to get usable sps/MFU, and map the width × GPU-class throughput frontier (see above).
- **Switch eval to 4p–8p** and revisit the placement (value) head once it's less OOD.
- Smaller: rename `value`→`placement_*` in metrics; add the nvidia-ml-py dep so the util sidecar runs.
