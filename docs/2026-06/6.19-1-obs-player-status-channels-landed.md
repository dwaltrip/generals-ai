*Date: 2026-06-19. Status: implementation note. Lands §3.A (fix the obs — correctness) and most of the machinery for the obs work in [6.18-9](6.18-9-elim-head-synthesis-and-direction.md). ## What landed

The obs now disambiguates **surrender**. A new per-opponent thermometer — `(is_present, is_alive)`, 14 channels — distinguishes a surrendered-but-not-yet-removed player (`present & ~alive`) from a live one. The only prior status signal was the capture-based `opp_captured_by`, blind to surrender — so without an alive channel the surrender subpopulation ceilings at ~53.5% accuracy vs ~100% with one (6.18-4/7).

Three commits:
1. **`bc/obs.py` → `bc/obs/` package** (pure move): `geometry` / `memory` / `channels` / `build`, public surface re-exported from `__init__` so importers are unchanged.
2. **`bc/player_status.py` + the alive-seam fix**: shared, torch-free per-game status (`death_by_slot`, `removal_by_slot`, `is_real`) consumed by both the obs encoder and the elim targets. `alive`/`present` use `tick >= t` (was `> t`), closing the obs/alive seam (6.18-6).
3. **The channel-group spec + the status channels + live wiring**.

All green (198 training + 11 eval-tools), pyright clean. Old checkpoints load unchanged (status off → original 96-channel obs); the default is now 110 channels.

## Non-obvious decisions (the parts worth remembering)

### The toy "notch needs depth" result was a scaling artifact, not a general carving cost

The most important correction this session. The argmin-toy found a scalar army channel needs depth-1 to carve the `army==0` notch — which reads as evidence against any scalar/ordinal categorical, but isn't. The toy applies `/1000` to army (`encode.py`), so the notch separates `0.0` from `~0.001`: the difficulty is the *near-zero squish* (large weights to carve a sharp step at a tiny absolute gap), **not** a general "carving thresholds is hard." Well-separated integers (a status ordinal `{0,1,2}`) carve trivially. So the toy does **not** condemn an ordinal status — it condemns *squished* scalars. (The toy's own status encodings were binary `{0,1}`, already well-separated, and were linear.) Don't re-cite the notch result as evidence against ordinal categoricals.

### Thermometer `(is_present, is_alive)`, not an ordinal scalar

Given the correction above, the case for the thermometer is narrower than "avoid the notch": it's **linear non-monotonic readout**. The useful response to status is likely a *peak* at "surrendered" (a prime capture target — higher death/opportunity signal than both alive and eliminated). An ordinal scalar needs a 2-threshold bump (depth-1) for that; the thermometer gets it linearly (`a·is_present − b·is_alive`). Cost is +7 channels over an ordinal — cheap insurance. `(is_present, is_alive)` chosen over `(is_alive, is_eliminated)` (they're linearly equivalent — complementary second channel) for the safer zero-default: padding/zero reads as "eliminated/inert," not "surrendered/live-ish."

### `is_present` is event-derived, not `army == 0`

`is_present` = no board-removal event (capture/neutralize) yet; `is_alive` = no DeathEvent yet. The two markers are the surrender window's endpoints. Crucially, `army == 0` is **not** a safe proxy for "gone": a general zeroed to 0 army but not captured (hit by exactly `n+1` on its last tile) is still alive and recovers +1 next production tick. That transient reads `present & alive` correctly under the event-based definition; `army==0` would have produced the impossible `(0,1)` corner.

### `>= t` and the `dt = 0` consequence

Per sim-core's snapshot convention (events fire pre-increment, visible at `snapshot[e+1]`, so `snapshot[e]` is pre-event), a player whose event fires at `t` is still on the board the observer saw at frame `t`. So `alive`/`present` use `>= t`. This shifts the elim-head's `next_death_target`: at the death frame the victim is alive-and-the-victim, so `dt = 0` is now reachable (was excluded under `> t`). Correct, but a target-semantics change — the imminent `dt < 10` regime gains a `dt = 0` bucket. Worth keeping in mind for horizon-stratified reads.

### Channel-group machinery (kept minimal)

The spec governs only *gated/optional* groups; the frozen base + dense-history stay as they are. `obs_config.GATED_CHANNEL_GROUPS` (torch-free: key, enabled-predicate, names) + `obs.channels._GATED_GROUP_BUILDERS` (keyed by the same key); `ObsConfig.channel_names` folds base + dense + enabled groups and `obs_channels = len(channel_names)`, so count and names can't drift. A future obs addition (the 6.18-9 §3.C menu) is one spec entry + one builder + one config field. `attrs` config migration (6.07-2) stays parked; folding dense-history into the spec is deferred.

### Live path: the events belong in `PlayerView`

Death and neutralize are board-wide announcements a live player sees (Daniel's call), so they were added to `game_types.PlayerView` and populated in `sim_adapter.state_to_view`. Training precomputes the status ctx once (full sim); the live `inference` path refreshes it per tick from the cumulative events. These agree because **future events don't change the current-tick mask** — so the train-vs-live obs-path parity test passes with status on, by construction.
