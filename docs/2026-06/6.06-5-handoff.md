# Session handoff 

**Date:** 2026-06-06

## TL;DR

The evidence strongly points to the data-pipeline bottleneck being in the worker→main handoff, not obs-build or other data-pipeline on-worker processing.

The n=20 dense-history slowdown is GPU data-starvation. We've been trying to pin down what exactly is causing it, and how we can fix it.

In the last session, we more precisely located *where it isn't*: not obs-build compute, not volume I/O, and not a worker→main byte copy. The producers sit idle most of the time, the GPU starves in bursty multi-second dips, and the cost lives in the worker→main handoff machinery — which we don't yet instrument.

Planned next steps: add per-span distribution stats to the profiler, then run a small config sweep (`pin_memory` × `prefetch_factor` × N) to hopefully get more insight into the suspected worker-main handoff bottleneck.

The full disk→GPU anatomy with a measured/inferred/blind map is in [`6.06-4`](6.06-4-train-data-flow-profile-summary.md).

## Last session

### Findings

We did fresh a profiling probe of dense-history n=20 and n=5 (for control) last session (with a "good hardware draw" from modal) with improved diagnostics (see below for what we built). Findings:

- **The n=20 slowdown is entirely GPU starvation.** Per batch, n20 is ~25% slower than n5, and the whole difference is added `fetch_wait` (the main loop blocked waiting for data) — the GPU's compute time is identical. n20 isn't doing more work; it's waiting more.
- **The producers are not the bottleneck.** Each DataLoader worker spends 53% (n5) / 58% (n20) of its wall-clock *blocked*, not building observations. There is substantial spare producer capacity.
- **There is no separate worker→main byte copy to optimize.** `collate` stacks the batch directly into shared memory (a PyTorch worker optimization, confirmed in source), so the "IPC copy" we expected doesn't exist as a distinct step — our explicit pre-share probe measured ~0.
- **obs-build is cheap and roughly flat in N; volume reads are negligible.** The larger n=20 observation costs only ~8% more CPU to build, and reading game files off the volume is ~20 µs/sample. Neither explains the slowdown.
- **The starvation is bursty, not uniform.** The n20 GPU stalls in ~22 multi-second dips (4.3 s mean, 14 s worst) covering roughly half the run, and they cluster in time — recurring multi-second stalls, not high-frequency flicker. The typical dip is about as long as the prefetch buffer's runway (~4 s).
- **The hardware draw varies ±5–10% even within the good pool**, so any single run is weak evidence; compare only matched good draws.

What we read into it (less certain):

- **The bottleneck is the worker→main handoff machinery.** Both ends of the pipeline are idle — workers blocked, GPU starved — so the holdup is the conveyor belt between them: the result queue, the single pin-memory thread, the data queue. That stretch is currently uninstrumented; the pin thread is the leading suspect but is not yet measured.
- **"Build the observation directly into the batch buffer" is off the table for this problem.** It speeds up obs-build and collation — work the producers already have spare time for — so it wouldn't move throughput. (It may matter later for other reasons.)

## Next steps

### (a) Add distribution stats to the profiler

Today every producer timing is a *mean* — `timing.py` keeps only a running sum and count per span. Enhance it to also record per-span min/max, variance, and a cheap log-scale histogram, so we can see the *distribution* of each stage, not just its average. This is what distinguishes a stage that occasionally stalls for seconds (a fat tail) from one that runs uniformly — i.e. whether the multi-second GPU dips come from a *producer* stage stalling or from the *downstream* handoff. These stats feed the auto-generated `report.md` as a per-span tails table (p50 / p95 / max), and like all the detailed timing they're gated behind `--profile` (zero cost otherwise).

- Histogram via integer `ns.bit_length()` buckets (power-of-2; no float, negligible overhead for the pipeline).
- The per-span snapshot grows from a tuple to a dict; the worker merge sums histograms elementwise and combines min/max/variance; the report gains the tails table and still reads older runs gracefully.
- Files: `shared/timing.py` (the `Timer`), `shared/timing_run.py` (merge), `bc/run_report.py` (tails table), `tests/test_timing*.py`.
- Caveat: the `handoff` span is bimodal (one big stall per batch among many trivial gaps), so read its `max` and top buckets, not its percentiles.

### (b) Config sweep, read with the new stats

We can't seam inside PyTorch's handoff machinery directly, so localize the bottleneck (Gap B in [`6.06-4`](6.06-4-train-data-flow-profile-summary.md)) by *elimination*: flip the knobs around it and watch where the time moves. The sweep crosses dense-history N (the stressor), `prefetch_factor` (does a deeper buffer absorb the multi-second dips, or is there a hard drain ceiling?), and `pin_memory` (is the single pin thread the serializer?). The new per-span histograms run in every cell, so each run also triages whether a producer stage is fat-tailed.

- Matrix (8 runs): N ∈ {5, 20} × `prefetch_factor` ∈ {2, 4} × `pin_memory` ∈ {True, False}.
- `TrainConfig` already exposes `pin_memory` and `prefetch_factor` (read by `dataloader_kwargs`); set both explicitly in the config JSONs — note an unset `pin_memory` auto-resolves to True on CUDA, so don't rely on the default. Base the variants on `training/tmp/n{5,20}_quick.json`.
- Run protocol: `uv run modal run --detach … --profile --skip-val --max-batches 800`, sequential with a ~20 s stagger, good-draw only (discard non-1 TiB and reroll), pull with `pull_runs.py --no-checkpoints`.
- Read each `report.md`: `fetch_wait` + GPU util (the starvation), block = `handoff − collate − shm_copy` (producer idle), and the new tails table (which stage, if any, spikes) — then compare the deltas across cells.
- Reading the deltas: `pin=off` faster ⇒ the pin path was serializing; `prefetch=4` faster/smoother ⇒ the dips were buffer-absorbable oscillation; both flat ⇒ a hard serial drain ceiling somewhere in the handoff.
- Cost: ~8 × ~4 min, plus reroll overhead.

## Open questions

- We've bracketed the bottleneck to the handoff machinery by elimination but haven't measured inside it. The sweep should narrow it; a direct measurement of the pin thread is possible but needs a thread-safe accumulator (the current `Timer` isn't one), so it's held until the sweep says whether that's worth it.
- What the right fix is — a buffering/scheduling change, limiting or dropping pin, fewer workers, or reducing the bytes that cross the handoff (e.g. fp16 obs, which would halve the pin + H2D bytes) — depends on what the sweep shows. These are all plausible and not mutually exclusive.
- The hardware lottery still isn't understood mechanistically; for now we manage it by logging the draw and comparing only matched good draws.
