### What this session established (new since 6.06-1)

**n5 is GPU-bound; n20 is producer-starved.** Three fresh probes, all good-pool (1 TiB / 17 cores / PCIe gen5) — so not bad-draw-confounded, though still cross-container:

| run | N | prof | region | steady sps | GPU util | fetch_wait | verdict |
|---|---|---|---|---|---|---|---|
| 15-52-29Z | 5 | on | sines-2 | 2612 | 92% | 7.7% | ✅ GPU-BOUND |
| 15-52-56Z | 20 | off | odin | 1947 | 69% | — | (no prof) |
| 15-59-44Z | 20 | on | portugal | 1875 | 68% | 33.5% | ⚠️ PRODUCER-STARVED |

**The slowdown points to bytes-movement, not compute.** obs-build *compute* grew only +14% n5→n20, but `fetch_wait` grew 6× (16→99 ms/batch), `h2d` +38%, `assemble` +30% — so FiLM (−47% channels) and fp16 target this. The off-profile n20 also let us check profiler overhead: the on/off runs differ by ~4%, confounded with host variance.

**The lottery *appears* transient — but we don't have a mechanism.** All three drew 1 TiB hosts this morning; last night's `US-1` / 944-GiB / 426-sps collapse didn't reproduce. Could be time-of-day availability, could be something else — we don't actually know what flips a host into the bad pool. The report's `BAD DRAW` flag + region/RAM logging are what flags it; discard a non-1-TiB draw and reroll until we understand it.

**New seams (`dataset.py`, this session):** `data_load` (per-game npz read + DEFLATE), `collate` (per-batch stack, runs in the worker), and `encode_frame` as a `grouped=False` *reference* span that reconciles against its child seams. Local-smoke reads (M1 — illustrative only; the real signal is Modal): `data_load` ~1%, `collate` ~14%, `encode_frame` ≈ 96% of its children (~4% un-seamed overhead). These three runs in the table **predate the new seams**, so their reports don't have `data_load`/`collate` yet — that's the first step.

### Tooling now available (use these)

- **`report.md`** is auto-written to the run dir every run (next to `summary.json`) — host draw, throughput, GPU util, starvation, producer breakdown, verdict. No manual `build_run_report.py` step.
- **`./training/scripts/pull_runs.py --no-checkpoints <run>...`** — pull artifacts without the checkpoint weight (`--force` to re-pull over existing).
- **Producer seams**: `data_load` + `collate` (grouped leaves, in the TOTAL) and `encode_frame` (reference, below the TOTAL). `timer.section(name, grouped=False)` is the reference-span API; grouped-ness is stored as a record field, rendered as a `ref` row.

### The run — invocation

- Probe: `uv run modal run --detach training/scripts/run_bc_modal.py --config training/tmp/n{5,20}_quick.json --profile --skip-val --max-batches 800` (two separate launches; sequential to avoid fallback-cloud spill).
- Pull: `./training/scripts/pull_runs.py --no-checkpoints <run5> <run20>` — grabs `report.md` + `prof/` + everything but checkpoints.
- Local smoke: `./training/scripts/run_bc_local.py --config training/scripts/smoke-config.json --profile --skip-val --max-batches 5 --num-workers 2` (from repo root; `--skip-val` required — MPS val crash).

### First step

Re-run the n20 probe (+ n5 control) **with the new seams** and pull with `pull_runs.py`. The report now shows `data_load` and `collate`; get the IPC copy by elimination — **per-worker wall (sps ÷ workers) − grouped TOTAL** (valid at n20: a starved GPU means no backpressure to distort the gap). This data new should be telling.

We have a few promising levers based on what we find:

- Build the channels *directly into* the final tensor, skipping extra allocations.
- Big `data_load` → cold-volume-bound → caching/prefetch → FiLM/fp16 won't help this problem.
- Big `collate` + IPC gap → bytes-bound → **FiLM broadcast-elimination** is the largest lever (−47% channels at n5, helps low-N most), **fp16 obs** composes (halves remaining host-side bytes).
    - This is an architectural change that ls a last resort. It's a bit of a dodge as well. We should pursue any and all other options before considering this. Previous docs didn't properly fraem this as a "last resort".

Everything so far points at bytes — but confirm with the real numbers before investing in FiLM (a model change) or fp16 (needs numerics-parity + path gating).
