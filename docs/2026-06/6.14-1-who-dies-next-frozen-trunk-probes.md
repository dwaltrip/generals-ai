# who-dies-next: frozen-trunk probes and the leaderboard question

**Date:** 2026-06-14

**Description:** Built a generic frozen-representation probe framework and used it to localize *why* the who-dies-next aux head trails the lowest-army heuristic (the PoC finding in [`6.13-15`](6.13-15-who-dies-next-poc-results-and-experiment-menu.md)). Covers the new tooling, every experiment run this session with its basic result, a calibrated synthesis (what is and isn't established), and a next-steps menu. The headline behavioral result is solid; two foundation questions are still open, so the over-arching interpretation is held as tentative.

> **⚠️ Known issue (found after this analysis was completed) — baseline mismatch.** The frozen-probe head-vs-rule comparisons (Exps 3–5) reference the lowest-army rule measured on the **full** 11k val split, but each probe head is trained and evaluated on a 110-perspective **sub-split** of that val set, where the rule runs ~1 pt lower (≈0.47 at dt<10, ≈0.46 over dt<25, vs 0.482 / 0.468 full-split). So the head-vs-rule **gaps in Exps 3–5 are ~1.3 pts too large**, and the SE multiples a bit high (the best imminent head is ~1.5 SE below the rule, not ~2). **No conclusion changes** — no head beats the rule on either reference — but several magnitudes are off by a small amount. Aggregate comparisons are unaffected (sub-split agg ≈ full-split). Affected items are tagged **[baseline mismatch]**, with the estimated error in a footnote under the table; the exact matched numbers need a per-cell recomputation on the probes' eval frames (out of scope here). Root cause and the durable fix are at the bottom: [*Known issue: the decoupled baseline*](#known-issue-the-decoupled-baseline-and-the-fix). Worth fixing before the next analysis.

## Context

The `next_death` head predicts which alive player is eliminated next (a cross-player softmax). At sub_5k it did not beat the model-free "lowest total army dies next" rule ([`6.13-15`](6.13-15-who-dies-next-poc-results-and-experiment-menu.md)). This session re-ran it at 11k (data-scale test), then built frozen-representation probes to ask whether the failure is upstream (the trunk doesn't present the signal) or in the head/target.

## The tooling

A generic frozen-representation probe framework. The question it answers: *is signal X decodable from a frozen representation Y, and at what readout capacity?*

- **Two orthogonal axes.** A `FeatureSource` chooses *what representation* to read — `TrunkSource` wraps a frozen trained trunk (point it at any checkpoint), `RawObsSource` is the identity control (reads the obs directly). A `ProbeTask` defines *what signal* — the per-frame target, a zoo of swap-in heads (linear / deployed-shape / fat), the loss, the metrics, and reference baselines. The orchestrator caches the source's features over a held-out val sub-split once, then trains each head on them. A new probe is one new `ProbeTask`; reusing a probe across representations is a swapped `FeatureSource`. It is genuinely target- and representation-agnostic — the who-dies-next tasks are instances, not the framework.
- **Mechanics:** perspective-level train/val split (no frame leakage), frame caps, fp16 feature cache, per-epoch metrics, auto output to `data/analysis/probes/TIMESTAMP-task-source/` (`summary.json` + full `run.log`). Framework in `packages/training/training/analysis/probes/`; one-off tasks in `.../probe_runs/`.
- **Limitations to keep in mind when reading results:**
  - Frozen-trunk only. It measures what a *trained* representation happens to preserve, not what the architecture *could* learn; the raw-obs source is the only "clean signal" reference available without a from-scratch run.
  - The heads are deliberately small (linear / 2-conv). A probe that fails means "not decodable by a small head at this scale," not "absent."
  - Frames are capped (24k train / 10k val here) for memory — not the full val split.
  - Reference baseline lines are hardcoded per task (from `who_dies_next_baselines.py`) and are only valid on the matching split.
  - Single seed, single config per run.
  - **Task-specific (LowestArmyTask):** argmin-identity accuracy saturates — see Exp 2 — so it is a coarse instrument for "is the signal present."

Supporting change: the dataset's elim-target emission was re-gated from `elim_bin_edges` (a time_bin-head concept) to `elim_head_variant`, so `next_death` targets no longer require bin edges.

## Experiments

Common frozen-probe config unless noted: val split of `cloud_24k_sub_11k.json` (550 perspectives) sub-split to 440 train_probe / 110 val_probe perspectives, capped to 24k train / 10k val frames, 6 epochs, three head variants (linear_pool / deployed / fat), MPS. `ELIM_ON` = `sweeps/2026-06-14-yolo-11k-elim-head-v2/runs/2026-06-14T07-47-05Z/checkpoints/epoch_002.pt` (the 11k who-dies-next trunk; also used as the obs-config source for raw-obs runs). `ELIM_OFF` = `sweeps/2026-06-11-seed-replicates/runs/2026-06-12T05-42-32Z/checkpoints/epoch_003.pt` (same arch, policy+value only, **different training manifest**). Model-free baselines from `who_dies_next_baselines.py` on the 11k val split: lowest-army **47.1%** aggregate, **48.2%** at dt<10, **45.8%** at 10–25; army-delta(K25) 44.3%; oracle 56.2%. (The probe scripts print `0.478` as the dt<10 reference line — a constant carried from 6.13-15's 5k split — so the `run.log`/`summary.json` artifacts show 0.478; the full-split value is 0.482, which is what Exp 1 compares against. For the frozen probes (Exps 3–5) the relevant line is lower still — see the **baseline-mismatch** note up top.)

### Exp 1 — 11k data-scale training (who-dies-next head)

`data/training/sweeps/2026-06-14-yolo-11k-elim-head-v2` (run by Daniel). Two cells, `elim0.15-v0.1` (`07-47-05Z`) and `elim0.3-v0.1` (`07-47-22Z`): `cloud_24k_sub_11k`, 5 epochs, seed 0, n20, τ=0.6 pyramid value, width 192/192/240. Top-1 victim computed by the `who_dies_next_baselines.py` join on the 11k dumps.

| cell (ep5) | val next_elim CE (best, ep2) | top-1 agg | top-1 dt<10 |
|---|---|---|---|
| elim0.3 | ~1.55 | 0.435 | 0.378 |
| elim0.15 | ~1.59 | 0.431 | — |
| lowest-army rule | — | 0.471 | 0.482 |

Basic result: doubling data (5k→11k) did **not** lift the head to the rule. The overfit signature deepened — train CE fell lower than at 5k while best val was at ep2 then rose; best val CE stayed worse than the uniform-over-alive floor (1.39). λ_elim 0.15 ≈ 0.3 (no lever). Policy top-1 improved with the extra data (71–72% → 73.1–73.6%), so the data was usable; the elim head specifically did not benefit.

### Exp 2 — LowestArmyTask (argmin-army identity), frozen

Target: which alive player has the lowest army (a clean function of the obs army channels). Metric: top-1 identity accuracy.

| source | linear | deployed | fat | dir |
|---|---|---|---|---|
| ELIM_ON trunk | **0.576** | 0.569 | 0.569 | `data/training/probes/20260614-100311-lowest_army-trunk` |
| raw-obs | 0.532 | 0.529 | 0.612 | `data/training/probes/20260614-100533-lowest_army-raw_obs` |

(These two predate the `data/analysis/probes/` relocation, hence the `data/training/probes/` path.)

Basic result: a linear head recovers argmin-army identity at 0.576 off the trunk, vs 0.532 (linear) to 0.612 (fat) off raw obs. Note that raw obs *contains the exact army values as channels* yet a learned head still only reaches ~0.53–0.61 — so this metric saturates around ~0.6 and cannot, on its own, distinguish "trunk preserves army cleanly" from "trunk preserves it degraded." (The `0.471` line the tool printed is a victim-accuracy reference, not the right comparison for this identity target.)

Same as Exp 3 but trained *and* evaluated only on imminent frames (non-dt<10 frames masked to the `-1` ignore index). Isolates the contested regime. Metric reported is top-1 over dt<10 (val ≈ 1,100 such frames; SE ≈ 1.5%).

| source | linear | deployed | fat | dir |
|---|---|---|---|---|
| ELIM_ON trunk | **0.446** | 0.437 | 0.410 | `20260614-113958-who_dies_next_imminent-trunk` |

| ELIM_OFF trunk | 0.355 | 0.385 | 0.383 | `20260614-114315-who_dies_next_imminent-trunk` |

(rule at dt<10 = 0.482 **[baseline mismatch]**.)

> **[baseline mismatch]** On the probe's val sub-split the dt<10 rule is ≈0.47 (~1.3 pts below the full-split 0.482), so each head's gap to the rule is ~1.3 pts smaller and the best head (0.446) sits ~1.5 SE below, not the ~2 quoted below.

Basic result: targeting the imminent slice directly raised the ELIM_ON trunk's imminent top-1 from 0.401 (Exp 3, aggregate-trained) to 0.446 — the aggregate objective had been costing imminent accuracy. 0.446 is still below the rule (0.446 vs 0.482, ~2 SE). raw-obs (0.410) and ELIM_OFF (0.385) are further below.

## Synthesis

Calibrated to single-seed, single-config, frame-capped runs. Separated into what is robustly supported, what is open, and the tentative reading.

### Robustly supported this session

1. **No learned head beat the lowest-army rule in the imminent (dt<10) regime, from any representation tested.** Best case: ELIM_ON trunk, trained directly on dt<10, **0.446 vs rule 0.482** — ~2 SE below (Exp 4, `20260614-113958-who_dies_next_imminent-trunk`). raw-obs (0.410) and ELIM_OFF (0.385) are clearly below.
2. **Directly targeting the imminent slice helped — the training objective was part of the gap.** ELIM_ON trunk imminent top-1 went 0.401 → 0.446 from aggregate-CE to dt<10-only training (Exp 3 `…-110602…` vs Exp 4 `…-113958…`). Implication: aggregate-trained numbers understate imminent accuracy, so the imminent question must be read off imminent-targeted runs — a head sitting below the rule under aggregate training reflects partly an objective mismatch, not purely an unlearnable residual.
3. **More data did not help.** 5k→11k training widened the train/val gap without reaching the rule (Exp 1, `sweeps/2026-06-14-yolo-11k-elim-head-v2`); and dt<25 (2.5× the near-term frames) did not raise dt<10 accuracy above the dt<10-only run, and clearly trailed its own slice's rule (Exp 5).
4. **The trunk read slightly better than raw obs on these tasks** — imminent 0.446 vs 0.410 (Exp 4), argmin-identity 0.576 vs 0.532 (Exp 2, linear; raw-obs *fat* hits 0.612) — so the trunk does some useful extraction beyond passing raw channels, but it is bounded by the rule.

### Open — not established

1. **Whether the army leaderboard is *reliably* encoded in any trunk is unproven.** LowestArmyTask measured argmin-*identity* (0.576), which saturates: raw obs, which holds the exact army values as channels, yielded only 0.53–0.61 (Exp 2). So that instrument cannot separate "army cleanly preserved" from "army degraded." The clean test — army-value regression / per-player R² — was not run.
2. **The victim-prediction shortfall is ambiguous between "no learnable residual beyond the leaderboard" and "a small conv-pool-softmax head cannot reliably learn argmin-army from broadcast channels."** The raw-obs victim probe had clean army available and still did not beat the rule (0.410 < 0.482, Exp 4 `…-114215…`). So at least part of the shortfall is a learnability/argmin issue that afflicts even clean inputs, independent of any residual.
3. **ELIM_ON vs ELIM_OFF cannot be cleanly compared.** The ELIM_OFF checkpoint saw less data (sub_5k, not the 11k split) and also differs in seed, λ_value, and epoch count, so the ELIM_ON > ELIM_OFF ordering (Exps 3–5) cannot be attributed to the elim head rather than those confounds.

### Tentative reading (labeled as such)

The pattern across experiments is consistent with *"who-dies-next ≈ read the leaderboard, with no learnable signal beyond it in the imminent regime at the scales tested"*: targeting the hard slice and reading a trained trunk both only reach toward the rule (best 0.446 vs 0.482), never exceed it, and more data does not help.

But the two open items above are genuine confounds. Until army-value fidelity (Open 1) and the argmin-learnability wall (Open 2) are characterized, this reading is **suggested, not established**, and the 24k trunk-transfer bet (does the head enrich the trunk for the value head) is **weakened but not conclusively excluded**.

## Takeaways

- Built a reusable frozen-representation probe framework (target- and representation-agnostic) and used it to localize the who-dies-next head's failure cheaply.
- Behavioral result is solid: no learned head beats the lowest-army rule in the imminent regime, from any representation tested; targeting the hard slice helps but only reaches ~the rule; more data does not help.
- The "leaderboard-only / no residual" interpretation is the most consistent story but rests on two unrun checks (army-value fidelity; argmin learnability). It is held as tentative; the transfer bet is parked pending those.

## Known issue: the decoupled baseline (and the fix)

**Root cause.** The probe framework computes no baselines of its own. Each `ProbeTask` carries a *hardcoded* `baselines` dict (e.g. `rule_imminent: 0.478`) that `cli.py` prints as reference lines; the actual lowest-army rule is computed separately by `who_dies_next_baselines.py`, on the full val split. Nothing reconciles the two, so the printed reference describes a different frame population than the probe evaluates — the full val split, or a stale 5k constant, versus the 110-perspective val sub-split the heads actually see. That decoupling is the source of the baseline mismatch flagged above (and of the carried 0.478).

**Fix — make the rule a probe-computed metric.** `extract_target(frame)` already receives the full frame (including the obs), and `LowestArmyTask` already extracts argmin-army from the obs army channels. A who-dies-next task can compute the lowest-army rule's per-frame victim prediction the same way, store it in `aux`, and report its top-1 alongside `top1`/`top1_imminent`. The reference is then measured on the *identical* eval cache by construction — matched for both trunk and raw-obs sources — and the hardcoded `baselines` constant goes away. Small, well-scoped change; worth doing before the next probe analysis.
