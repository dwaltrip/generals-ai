**Date:** 2026-06-16

Built `join_dump` (the deferred Appendix-A piece from the [`6.15-3`](6.15-3-fq-analysis-toolkit-design.md) design), wrote the first real analysis script on top of fq, and used it for a new cut on the who-dies-next head: head-vs-lowest-army-rule stratified by close-call **margin**. ## What landed (code)

### `join_dump` + the `persp_val_index` join key

`FrameTable` now carries `persp_val_index` (the full val-split position) in place of the dataset's subset-relative `sample_idx`. `build_frame_table` records full-split positions from the complete `samples` list *before* the games-cap, then remaps the dataset's emitted `sample_idx` back through them — the same remap the dump harness does on its side. This makes a capped fq table joinable to a model dump that was produced over the full split.

`join_dump(t, dump, truth_map)` inner-joins a dump's per-frame columns onto the table on `(persp_val_index, frame_t)` via an int64 composite key, attaches the dump's columns, warns on partial coverage, and asserts the family-declared shared-truth columns agree on the overlap. The `truth_map` lives on `FrameSpec` (family-owned), so `join_dump` itself stays generic. That truth-assert is the point: it cross-checks fq's `persp_val_index` against the dump's independently-produced one — a self round-trip can't, since it keys both sides on fq's own index.

**Validated against real dumps** (the standing-test packaging is deferred — see below — but the validation was run manually this session):

| scenario | coverage | truth assert | correct? |
|---|---|---|---|
| matching manifest (11k dump) | 100% | passes | ✓ valid join |
| 5k dump (prefix-subset of the 11k split, same seed) | 100% | passes | ✓ legitimately valid |
| synthetic key shift (in-range) | partial, warns | fires | ✓ |
| synthetic key shift (out-of-range) | 0%, warns | n/a (0 rows) | ✓ |
| disjoint-manifest dump (poc_2kish, seed 77) | 58%, warns | fires | ✓ |

The 5k dump joins cleanly for a real reason: both splits derive from the same 24k corpus at seed 42, so the 5k val list is an exact prefix of the 11k val list — a legitimately valid join, not a false pass. The poc_2kish split (seed 77, zero overlap) is the genuine cross-manifest negative control, and both guards fire on it.

### Ergonomics pass (driven by writing the first consumer)

Writing the analysis script as a real fq consumer surfaced two frictions, both fixed:

- **Derived columns weren't attached by `build_frame_table`** — the consumer (and the CLI) had to re-run an attach loop, and a consumer who forgot it would silently have no rule/margin columns (the rule-as-column quietly missing is exactly the failure class fq guards). `build_frame_table` now applies the family's `derived_cols`, so a built family table arrives complete. A prominent NOTE on `FrameSpec.derived_cols` documents the precondition this relies on: derived columns must be **row-local** (each output row a function of that input row only), so build-time compute + later `select` stays correct. A cross-row reduction would have to be recomputed after slicing and does not belong in `derived_cols`.
- **The ground-truth obs config was constructed identically in three places** (CLI, script, test). Hoisted to a shared `GROUND_TRUTH_OBS_CFG` constant. `obs_cfg` stays an explicit `build_frame_table` argument (not defaulted) so the ground-truth-vs-checkpoint-pinned choice stays visible at the call site (Q5).

A third friction — the build always encodes the full obs even for a sim-only analysis — was **deferred deliberately**. The ~90s full-val build runs at ~2,600 frames/s, close to the obs-build-bound rate the training pipeline hits, so the cost is almost certainly the obs *encoding* (not directly profiled this session). Skipping fq *columns* wouldn't help: the obs is encoded by the dataset unconditionally, regardless of which derivers run. The real lever is a sim-only walk that skips obs encoding, which is the design's Option-2 (lazy obs) territory; a quick `skip_obs` flag on `dataset.py` would be a second analysis flag on the training class — itself one of the design's named Option-2 triggers. Not worth building mid-investigation; revisit if sim-only analyses become common.

## The research finding: head vs lowest-army rule, by margin

`training/analysis/scripts/head_vs_rule_by_margin.py` is the first real fq consumer and a one-off durable artifact. Its data plumbing is four fq calls (`build_frame_table` / `join_dump` / `select` / `select`); compare the hand-rolled val-walk + join in `who_dies_next_baselines.py`. It stratifies the next_death head against the lowest-army rule by **bottom-two army margin** (the gap between the two lowest-army alive players) — a cut neither [`6.13-15`](6.13-15-who-dies-next-poc-results-and-experiment-menu.md) nor [`6.14-1`](6.14-1-who-dies-next-frozen-trunk-probes.md) made (both stratified by time-to-death).

**Checkpoint:** `2026-06-14-yolo-11k-elim-head-v2`, elim0.3 cell, full `cloud_24k_sub_11k` val split — exactly [`6.14-1`](6.14-1-who-dies-next-frozen-trunk-probes.md) Exp 1's checkpoint. The script reproduces that doc's numbers to the decimal (ep5 head 37.8% / rule 48.2% at dt<10), which also cross-validates fq against `who_dies_next_baselines.py`.

**ep5, imminent (dt<10), full split (548 games, 26,701 victim frames):**

| margin bin | n | rule | head | gap | head==rule |
|---|---|---|---|---|---|
| [0,10) | 9191 | 27.1% | 21.8% | +5.3 | 21.0% |
| [10,25) | 5400 | 43.4% | 30.7% | +12.7 | 30.3% |
| [25,50) | 3369 | 48.4% | 30.8% | +17.6 | 33.9% |
| [50,100) | 2541 | 64.0% | 40.2% | +23.8 | 44.5% |
| [100,250) | 2390 | 70.0% | 56.5% | +13.5 | 64.2% |
| [250,∞) | 3810 | 81.5% | 79.4% | +2.1 | 84.3% |
| **overall** | 26701 | **48.2%** | **37.8%** | **+10.4** | 39.7% |

Cluster-bootstrap 95% CIs over games (frames are clustered by game): rule 48.2% [46.5, 49.9], head 37.8% [36.1, 39.6], **gap +10.4 [8.4, 12.4]**.

**What's supported (single checkpoint, but robust within it):**

1. **The head reliably trails the rule** — the gap CI excludes zero by a wide margin. (The earlier 8-game read of head ≈ rule was small-sample noise — a recurrence of the [`6.15-2`](6.15-2-army-regression-probe-results.md) representativeness trap; the cluster bootstrap is the guard.)
2. **"The head just reads the leaderboard" is not supported.** Head and rule disagree 60.3% of the time, and on disagreements the rule is right nearly 2× as often (38.2% vs 21.0%). A leaderboard-reader would agree ~100% and match accuracy.
3. **The gap concentrates mid-margin, not in the close calls.** The head tracks the rule at both extremes — tiny margin (both near the uniform-over-alive floor, ~1/n_alive) and huge margin (both ~80%) — but trails by 13–24 pts in the resolvable-by-army middle [25,250).

**Cross-epoch robustness (ep2 = best val *CE*; ep5 = most-trained):** ep2 overall head 34.1% [32.6, 35.6], rule 48.2% (identical, model-free), gap +14.1 [12.0, 16.3]. The finding and the mid-margin signature hold at both epochs, stronger at ep2 — not an ep5-overfit artifact. Note ep2 (best val CE) is *worse* on top-1 than ep5: best-CE ≠ best-top-1; the head's argmax ranking keeps improving toward ep5 even as its calibration overfits. (Two epochs only sketch the trajectory; ep3/ep4 dumps exist if the full curve is wanted.)

**Interpretation (hypothesis, not established):** the head underperforming the rule *most* where army cleanly names the victim points away from "close calls are irreducibly hard" and toward "the head/trunk isn't extracting a usable army *ranking*." This is consistent with [`6.15-2`](6.15-2-army-regression-probe-results.md): the trunk preserves army *value* well (~0.82 R² linear), but a lossy argmin over a well-preserved scalar would still misrank — ranking ≠ value-preservation. It does not resolve [`6.14-1`](6.14-1-who-dies-next-frozen-trunk-probes.md)'s Open 2 (the argmin-learnability wall), but it sharpens where to look.
