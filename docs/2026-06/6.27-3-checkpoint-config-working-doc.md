# Checkpoint-config refactor — working doc

*Date: 2026-06-27 (updated 2026-06-28). The living record for the checkpoint-config refactor: current state, the as-built structure, conventions, traps, and the decisions log. Maintained as work proceeds — not a frozen session note. The as-designed build spec is [6.27-1](6.27-1-checkpoint-config-chunk-1-design.md); the conceptual frame (shape vs. behavior) is [6.26-5](6.26-5-checkpoint-config-synthesis.md). This doc is the as-built design-of-record and supersedes [6.27-1](6.27-1-checkpoint-config-chunk-1-design.md) §4 on structure and homes.*

## 1. Status

Chunk-1 is complete. Runs now write self-describing v1 checkpoints — the full resolved `TrainConfig` behind a `config_version`, plus `code_sha` and `in_ch` — and `load_checkpoint` reconstructs from them, migrating the stored config to the current shape. Steps 1–3 are committed on branch `ckpt-config-refactor`. The behavior axis (does current code reproduce an old checkpoint) is untouched, by design.

A local fresh-run smoke confirmed the end-to-end path: the writer emits v1 and `load_checkpoint` reconstructs the model, arch, and full config from a real `.pt`. A pre-existing bug in the FLOPs measurement (a `ModelOut` accessed by subscript) surfaced during the smoke and was fixed.

Capabilities now in place (structure in §2):

- Runs write v1 checkpoints; `load_checkpoint` reads both v1 and legacy (v0) formats.
- `TrainingState` carries `config` and `code_sha` and serializes them into each checkpoint.
- Resume reads v1 — the runtime keys sit top-level, as before; the resume *rewiring* is deferred.

Git is the detailed record — commits are referenced by description, not hash.

## 2. As-built structure (supersedes 6.27-1 §4)

Homes by concern (config *shape* / model *construction* / `.pt` *format & I/O* / *training state*):

| Home | Holds |
|---|---|
| `bc/config` | config shape: `CONFIG_VERSION`, `MIGRATIONS` + migrate dispatch, `resolve_config`, the `stringify_paths`/`rewrap_paths` serde pair. Torch-free by *data* (it operates on dicts, never tensors) but not by *import* — see §7. |
| `bc/model_builder.py` | `build_model` (the `ModelConfig -> BCModel` seam), `ConfiguredModel`. |
| `bc/storage/checkpoint.py` | the `.pt` adapter: `load_checkpoint`, `serialize_checkpoint` (the v1 writer), `validate_in_ch`, `is_versioned_checkpoint`. |
| `bc/state.py` | `TrainingState` — the runtime state plus the `config`/`code_sha` it was initialized from; `to_dict` (runtime serialization) and `save` (emits v1). |
| old `bc/checkpoint.py` | the legacy reconstruction (`arch_for_load`, `LEGACY_ARCH`/`LEGACY_OBS_CFG`), the discriminators (`is_combined_checkpoint`, `is_arch_bearing`, `is_legacy_checkpoint`), `ckpt_name`. Shrinks as logic migrates into `storage`/`config`. |

Settled structural decisions (the deltas from 6.27-1 §4):

- **`ConfiguredModel` lives in `model_builder`** — the assembled model + config, a model-domain object (chunk-2 makes it the home for `cfg` and the variant-meta). `cfg` is a property delegating to `model.cfg`. `config` is `None` for legacy checkpoints — a v0 `.pt` records only the arch, not the full `TrainConfig`. Whether the `None` ever goes away is the uniform-vs-graded fork (6.27-1 appendix B), still open.
- **Runtime serialization and format are separate.** `TrainingState.to_dict` produces the runtime-state dict (the model/optim/scaler state_dicts plus `epoch`); `serialize_checkpoint(runtime, config, code_sha)` wraps it with the format layer (the config block with `config_version` and stringified Paths, the `in_ch` checksum, `code_sha`). `TrainingState` owns its runtime serialization; `storage` owns the format. This mirrors the read side, where `from_checkpoint` reads the runtime keys and `load_checkpoint` reads the format keys.
- **`code_sha` is a `TrainingState` field** — an immutable initialization fact alongside `config`, required at construction. It is captured at the launch site (the local and Modal entries call `utils.git.git_sha`), not on the remote, which ships source without `.git`.
- **`is_versioned_checkpoint` is a discriminator** — presence of the config block — **not validation**. Validation (migrate + construct + run validators) lives inside `resolve_config`.
- **The strangler arrangement:** the new `storage/checkpoint.py` delegates *back* to old `checkpoint.py` for the legacy path (it imports `arch_for_load`, `is_combined_checkpoint`). Old `checkpoint.py` is not moved — it shrinks later. The dependency edge (new → old) inverts as the reconstruction migrates into `storage`.
- **`build_model` is the single construction seam**, shared by `load_checkpoint` and `TrainingState.fresh`.

## 3. Conventions

- **`# NOTE(ckpt-cfg-refactor-note):` / `# TODO(ckpt-cfg-refactor-note):`** mark transient or placeholder reasoning tied to the refactor — greppable, so a later sweep can confirm each is resolved before the refactor closes.
- **`$NAME` placeholder refs** (e.g. `$LEGACY_EXPLAINER`) stand in for an explanation to be written once and pointed at from several sites, rather than repeated inline. One is currently outstanding (§6).
- **Docstrings, terse-first.** Write the one-line "what" first, then add a further sentence only when a reader acts on it or it states a non-obvious "why" — otherwise leave it out. The failure mode to watch is over-writing: cross-references as trivia ("Mirrors X"), differences from a sibling that belong in a commit message, and asides that only land if you already hold the reasoning. Transient or forward-looking "why" goes into a refactor-note, not the docstring. The new `storage`/`config`/`model_builder` code is the style baseline; the old `checkpoint.py` prose is not.
- **A cold-read pass before each commit.** Re-read every new or changed docstring as a fresh reader who wasn't part of the work, and cut what does not carry weight. Catching this on review is too late — make it a standing step.
- **No step/chunk lingo** ("step 2", "chunk-1") in code prose — it decays. Describe the architecture as-is, or use a refactor-note for genuinely transient state.

## 4. Traps & constraints

- **`in_ch` is a derived `@property`** on `ModelConfig`, not a field, so `asdict(TrainConfig)` omits it. The v1 serializer writes it as a top-level key explicitly; the config block stays a pure `asdict`.
- **Typing a just-loaded checkpoint:** the function that *consumes* the contents takes `Any` (what `torch.load` returns); the discriminators that only *inspect* structure take `object` (+ `TypeGuard`). Mixing them widens to `Any | object` and trips pyright on `load_state_dict`.
- **ruff B018:** a trailing attribute access as a bare statement (e.g. `load_checkpoint(...).model`, notably inside `pytest.raises`) is flagged useless — drop the `.model` (the call raises before it anyway).
- **`_archive` is exempt:** `pyrightconfig.json` excludes `**/_archive/**`, and ruff doesn't resolve import targets, so an archived file importing a since-deleted symbol is fine (matches the existing `_archive/` convention).
- **`weights_only=True`** on every checkpoint load forces the config block's `Path` fields to be stringified on write and re-wrapped on read — see 6.27-1 §2.

## 5. Validation approach

- Run the `training`, `self-play`, and `eval-tools` suites (per affected package).
- Callers without fast-test coverage — smoke manually when touched: `stratified_val_loss_analysis`, `self-play/cli.py`, `eval_poc.py`, `probe_row_independence`.
- Lock load-path invariants with explicit tests — e.g. `is_arch_bearing`'s v0 answer (and thus the inference `model_key`) must stay byte-identical across the §5.1 fix.

## 6. Decisions & open items

**Settled:**

- This doc (6.27-3) is the as-built design-of-record; 6.27-1 is frozen as the as-designed chunk-1.
- The home map (§2) and the `ConfiguredModel` placement.
- **`resolve_config`** — the name drops "checkpoint": it takes a plain dict, never the `.pt`.
- **`bc/config` is one module**, not split into migrate/resolve/serde — the content is small; split when migrations actually accrue.
- **Path serde is a shared `rewrap_paths`/`stringify_paths` pair**, with `resolve_config` and `TrainConfig.from_file` keeping their own assembly otherwise (they differ in the flat-loss shim, CLI `**overrides`, and `config_version` handling). The field set is read off `TrainConfig` via `get_type_hints`, so a new `Path` field needs no edit.
- **`code_sha` is a `TrainingState` field captured at the launch site** — not a `serialize_checkpoint` parameter, and not on `TrainConfig` (it is code provenance, the axis separate from config; see [6.26-5](6.26-5-checkpoint-config-synthesis.md)).
- The manifest's data-provenance SHA log label is renamed `git_sha` → `data_manifest_sha`, distinct from the checkpoint `code_sha` now logged at startup.

**Deferred / outstanding:**

- In-code deferred smells (refactor-notes in place): the `model_key` re-read in `BCModelHandle.load`; the `from_checkpoint` double-read; the now-dormant `from_checkpoint` arch-gate (never fires for v1).

## 7. Follow-ups surfaced building chunk-1 (2026-06-28)

Found while implementing steps 2–3, grouped here so their origin stays clear. The larger deferred design (chunk-2, the behavior axis, the v0→v1 normalizer, the version-bump guardrail) lives in 6.27-1 appendix and is not repeated.

**Code / design:**

- **Type the v1 format contract.** The layout keys (`model`/`optim`/`scaler`/`epoch`/`in_ch`/`config`/`code_sha`) are written and read as plain strings across `to_dict`, `serialize_checkpoint`, `load_checkpoint`, and `from_checkpoint`, with `dict[str, Any]` signatures and no single source of truth. A `TypedDict` (or shared key constants) for the runtime dict and the v1 checkpoint would turn a key typo into a type error. This is the concrete core of the broader "tighten the typing" goal.
- **Decide what the stored config block should contain.** It holds the full `asdict(TrainConfig)` today, including invocation-local fields (`run_dir`, `device`, `num_workers`, `log_every`, ...) that describe one invocation, not the model. Nothing reads them now, but they would mislead resume-from-`.pt`: `config.run_dir` is the parent's directory, not the resume's. Decide whether to filter the block down to arch + recipe (the reproducible identity) or keep the full dump and have readers re-derive operational fields.
- **Remove torch from `bc/config`'s import graph.** `resolve_config` never touches tensors, but importing `bc/config` loads torch via `TrainConfig` → `LossConfig` (in torch-heavy `loss.py`) and → `aux_heads.REGISTRY` (used by `TrainConfig.__post_init__`). Lifting `LossConfig` into a torch-free module is straightforward; the `REGISTRY` edge needs the aux specs to expose a torch-free validation surface, which is an `aux_heads` refactor to scope fresh.
- **Nothing reads `cm.config` yet.** Every v1 `.pt` now carries the full recipe, but inference and eval still read `cm.cfg` (the arch). The payoff arrives only when a reader uses `cm.config` — the first will be resume-from-`.pt` or the `model_key` re-read fold-out (both in 6.27-1 appendix).
- **Two homes for `in_ch` validation:** `validate_in_ch` (v1, top-level) and the check inside `arch_for_load` (v0, in-arch). Converge when v0 support shrinks.
- **`is_versioned_checkpoint` vs. `config_version`.** The discriminator keys on `"config" in obj`, but `migrate` then assumes `config_version` is present inside the block; a malformed block raises a cryptic `KeyError` rather than a clear error.
- **Two classes named `RunArtifacts`** (`bc/perf_report.py` and `bc/run_dir.py`) — spotted while wiring `code_sha`, unrelated to this refactor, but a real naming collision worth resolving.
- **Three config representations in a run dir:** `args.json` (sidecar), `config.input.json` (verbatim `--config`), and now the `.pt` config block. The three should be reconciled as the `.pt` becomes authoritative (overlaps the deferred sidecar rename, 6.26-2).

**Test coverage gaps:**

- **The cloud `code_sha` path is inspection-only.** `train()` captures `git_sha()` locally and threads it through `train_remote.spawn()`; the positional `.spawn` argument order is not type-checked and only surfaces on a live Modal run.
- **Resume end-to-end through `bc_resume`** with a v1 parent. The v1 resume-load is unit-covered (the `test_state` round-trip), but the full `bc_resume` flow (drift check, overlay, segment suffix) is not exercised against a v1 `.pt`.
- **Elim-head configs through v1.** The round-trip tests use direct/pyramid value heads; none round-trips `elim_head_variant="time_bin"` with `elim_bin_weights`, so `LossConfig`'s list→tuple coercion is unexercised on the v1 path.
- **A v0 and a v1 checkpoint loaded together in one process** (e.g. an eval sweep pitting an old checkpoint against a new one). Each path is tested alone, not together.
- **`weights_only` safety for a future non-`Path` field.** Only `Path` is exercised; a config field that later takes a non-allowlisted type would break loads with no guard. A test that a config block survives a `weights_only` load would future-proof.
