# fq — frame-query analysis toolkit (MVP design, 1st draft)

**Date:** 2026-06-15

**Description:** First-draft design for `fq`, a small toolkit for the recurring "walk a data split → derive per-frame quantities → slice/reduce/join" analyses that the who-dies-next / probe work keeps hand-rolling. Focus is the MVP we build now; deferred items are touched only enough to confirm we're not painting ourselves into a corner (notably the `dataset.py` walk seam). A number of interface/API questions are deliberately left open and collected at the end for discussion rather than resolved here. De-risked by two spikes on branch `fq-mvp` (`fq/tier1_spike.py`, `fq/tier1_spike_demo_clean.py`).

## Why

The elim-head debugging arc has produced a steady stream of small, similar analyses ([`6.13-15`](6.13-15-who-dies-next-poc-results-and-experiment-menu.md), [`6.14-1`](6.14-1-who-dies-next-frozen-trunk-probes.md), [`6.15-2`](6.15-2-army-regression-probe-results.md)), and an Opus investigation of the past week's tooling found the real boilerplate isn't in the probe framework (that's a good abstraction) — it's *upstream*, in the val-split walk that derives per-(frame, player) ground-truth columns (army, alive, dt-to-death, victim). That walk is currently reimplemented in at least three incompatible idioms (`who_dies_next_baselines.build_baseline_table`, the probe tasks' `extract_target`, `bc/eval/dump.FrameRecordCapture`), with two quantities (army-from-sim vs army-from-obs) computed two different ways and nothing reconciling them — which is the root cause of the 6.14-1 baseline-mismatch bug. Two correctness traps recur with no shared guard: decoupled hardcoded baselines (6.14-1) and small/skewed-eval variance collapse (6.15-2).

`fq` is the shared substrate for that walk. The goal is to shorten "I have a question about the data or the model's behavior over a population of frames" → "I have a calibrated, trustworthy answer," and to make the single-source-of-truth and representativeness guards structural rather than per-analysis discipline.

## What fq is

Walk a split once; for each frame, compute named quantities via *canonical derivers* (one definitive function per quantity); collect them into a flat, dumb columnar `FrameTable` you slice with numpy; join to model dumps on a stable key; and run ad-hoc questions through a small CLI without writing a script file. That's the whole surface.

## Design principles

These are the load-bearing constraints; every decision below should be checkable against them, and a reviewer should push on anything that violates them.

1. **The container is dumb.** `FrameTable` holds columns and nothing else. Slicing/joining/grouping are free functions or plain numpy. We deliberately never grow `groupby`/`agg`/`pivot`/`merge` — if tempted, that's the signal to drop to numpy, or `pd.DataFrame(t.cols)` for all-`[N]` columns. We are not rebuilding pandas.
2. **Complexity lives in build/derivers, not the consumer surface.** The walk and the canonical derivers are allowed to be substantial (real domain plumbing, written once); what an analyst touches stays tiny and numpy-close.
3. **One canonical decode per quantity.** A derived quantity (e.g. per-player army) is computed in exactly one place, reused everywhere. This is the single-source value and the fix for the army-divergence class of bug.
4. **Correctness guards are baked in, not optional.** Single-source derivers, the join-integrity assert, and the games-not-frames representativeness check are features of the substrate, because the failures they prevent (6.14-1, 6.15-2) cost real iteration cycles.
5. **Abstract from the concrete.** The derivers/spec/CLI shapes are designed from the working spikes, not guessed. Where reuse hasn't been demonstrated yet, prefer the plain version and let the second consumer pull the abstraction into existence.

## The MVP — what we build now

### Walk foundation: the `frame_view` seam (validated)

The walk we need already exists inside `IterableDataset._walk`: it groups by game, holds the full raw `sim` dict per game, builds the elim precompute, and walks each perspective's frames in causal order calling the canonical `encode_frame`. The only gap was that it discarded the raw sim after encoding.

The MVP change (landed, default-off): a `frame_view: bool` flag that attaches a `FrameView` (per-game `sim`/`meta` by reference + this frame's `k`/`t`/slots) to each yielded sample. `fq` iterates the dataset **directly** (no DataLoader, as the probe cache already does), so attaching object references is free and collate never sees it; the training path is untouched. This reuses `encode_frame` verbatim, so there is **zero obs-encoding drift** by construction — the one drift risk that would otherwise invalidate probe comparisons built on it. (Spike: parity below.)

The alternative considered — a from-scratch `fq` walker — was rejected: it would have to replicate the stateful obs pipeline (`init_memory`/`step_memory`/`compute_visibility`/BFS) and reintroduce drift risk, and add a *third* walk skeleton. The `frame_view` flag's cost on `dataset.py` is one dataclass + one flag + one attach. (Its longer-term path off `dataset.py` is the insurance section below.)

### `Frame`: the deriver-facing view

A deriver reads one object unifying the encoded outputs with the raw sim: `obs`, `valid_mask`, `alive` `[8]`, `sim`, `t`, `raw_order` (canonical `[perspective, *opp]` slots). In the demo this is a separate `Frame` class built from the yielded dict; whether it should instead be the dataset's `FrameView` grown to expose obs is an open question (Q1, and it ties to the `dataset.py` path).

### Derivers: canonical single-source columns

A `Deriver` owns the one way to compute a named quantity. Two scopes:

```python
@dataclass
class Deriver:
    name: str
    per_player: bool                       # [N, 8] vs [N]
    fn: Callable[[Frame], np.ndarray]
```

- **Per-frame** (row-local): `army_obs`, `alive`, `placement`.
- **Per-game** (compute once per game, index per frame) via a `per_game(prepare, index)` wrapper that caches `prepare(sim)` on the sim object — formalizing the `id(sim)` cache the spike hand-rolled. This covers `army_sim` (ground truth, reusing the canonical `_army_totals_per_tick`) and, importantly, **army-delta** (`prepare` = per-tick deltas over a window, `index` = read `[t]`) — so the seam already covers the first deferred deriver without a richer form.

Derivers live in a shared module; families reference them. The MVP deriver set: `army_obs`, `army_sim`, `alive`, `victim`, `dt`, plus the derived columns below.

### `FrameSpec`: families

A family declares its dataset emit and its columns:

```python
@dataclass
class FrameSpec:
    name: str
    dataset_kwargs: dict          # MVP: inline IterableDataset kwargs (Q9: -> FrameNeeds)
    emit_cols: dict[str, str]     # dataset-emitted field -> column name (alive/victim/dt)
    derivers: list[Deriver]       # computed columns
```

The MVP ships one family, `ELIM_HEAD_DEBUG` (`elim_head_variant="next_death"` → alive/victim/dt + the army derivers). Families are curated bundles, not a global registry; whether the CLI needs a small name→spec registry is Q7.

### `FrameTable`: the dumb container + free-function ops

```python
@dataclass
class FrameTable:
    cols: dict[str, np.ndarray]   # each [N] or [N, 8]; axis 0 is always the frame index
    sample_idx: np.ndarray        # join key (full-split position, from the dataset)
    frame_t: np.ndarray           # join key
    game_id: np.ndarray           # walk-local game index (representativeness)
    n_games: int

def select(t, mask) -> FrameTable: ...        # mask every column at once; the one convenience
def join_dump(t, dump) -> FrameTable: ...     # inner-join on (sample_idx, frame_t); assert shared truth cols agree
```

The axis-0 invariant (`[N]` or `[N,8]`, frame index first) makes `select` uniform and `t.cols["army"][t.cols["alive"]]` flatten naturally to the long 1-D of alive values. `join_dump`'s design is settled (Q4); a self-contained round-trip test covers it in the MVP, and its first real *use* is the argmin/ranking probe.

### Derived columns and the rule-as-column

Derived columns are plain numpy over a built table — no walk, no library. Inline extension is just assigning to the dumb dict: `t.cols["margin"] = bottom_two_margin(t)`. The MVP includes `lowest_army_victim` and `bottom_two_margin`. The **lowest-army rule becomes a computed column** evaluated on the table's exact frames — so any head-vs-rule comparison is matched by construction, dissolving the 6.14-1 hardcoded-baseline mismatch. (Spike validation: the column reproduces the docs' ~48% imminent rule accuracy.)

### `check_representative`: the correctness helper

A helper (not an auto-gate — build can't know the downstream grouping) that reports per-group game count and target spread, surfacing the 6.15-2 trap before a variance-normalized metric inverts. Called explicitly in analyses/probes that compute per-group metrics. Exact interface in Q3.

### The `fq` CLI

`fq.py` builds (or, later, loads-cached) a family table and execs an ad-hoc snippet with `t`, `np`, `select`, and the family's helpers in scope — turning "little analysis" into a one-liner instead of a file:

```
fq --table elim_head_debug --split val -e "t.cols['army_sim'][t.cols['alive']].mean()"
fq --table elim_head_debug --split val <<'PY'    # multi-line via stdin
imm = select(t, (t.cols['dt'] >= 0) & (t.cols['dt'] < 10))
print(imm.n_games, np.median(imm.cols['margin'][imm.cols['margin'] >= 0]))
PY
```

CLI specifics (input modes, namespace, output convention, the family registry) are Q7; the obs_cfg source is Q5.

### Where it lives / naming

`packages/training/training/analysis/fq/` for the library (`frame_table.py`, `derivers.py`, families), `fq.py` for the CLI. Names — `FrameView`/`Frame`, `Deriver`, `FrameSpec`, `fq` — are provisional (Q10). The spike code lives in the repo-root `fq/` scratch folder and is promoted/deleted when the real package lands.

### MVP deliverables + acceptance

- `frame_view` seam (done), `Frame` view, `Deriver` + `per_game`, `FrameSpec`, `FrameTable` + `select` + `join_dump`, the MVP derivers + derived columns, `check_representative`, `fq.py`, the `ELIM_HEAD_DEBUG` family.
- **Acceptance:** Tier-1 (army distribution + bottom-two margin, overall + dt<10) runs as an `fq` snippet, not a script; army-from-obs == army-from-sim asserted; the lowest-army rule column matches the docs; the dataset suite stays green. One smoke test + the army-parity and `join_dump` round-trip asserts.

## What the spikes validated (branch `fq-mvp`)

- **Walk foundation works.** Direct iteration with `frame_view=True` yields raw sim + obs + the join key; dataset tests green; training path untouched.
- **sim-vs-obs army settled.** `max |army_obs*1000 − army_sim| = 0.0002` over 44k frames — the same quantity, exact modulo float. (Aside: obs default is fp16, which adds a few-army storage quantization; ground-truth analyses should prefer the sim deriver, obs for "what the model sees.")
- **Tier-1 numbers in hand** (100 games / 44k frames): alive army heavily right-skewed (median 94, mean 348, max 7362); bottom-two margin median ~20 in the imminent regime, ~66% under 50 army. Close calls dominate the imminent regime — *suggestive* of the close-call/argmin mechanism (H1, [`6.15-2`](6.15-2-army-regression-probe-results.md)), but the pooled-σ bridge is rough and small margins limit the rule too, so the conclusive test is the head's residual-vs-margin (the argmin/ranking probe), not this.
- **Ergonomics signal** confirmed the deriver model, the dumb-table flow, and the rule-as-column; surfaced the per-game caching seam and the fp16/config-only nuances folded in above.

## Deferred — with painted-into-a-corner insurance

Touched only enough to confirm a strong path exists.

### `dataset.py` sanctity → the Option 2 path (the critical one)

The `frame_view` flag is a small, default-off, additive analysis seam bolted onto a training class. It should be good for a while, but the concern is accretion: more analysis needs pulling more into `dataset.py`. The strong plausible path off it, when warranted:

Extract `_walk`'s per-game/per-tick loop into a shared game-scoped generator that yields a rich `FrameView` with **lazy obs** (`view.obs()` encodes on demand). Then `IterableDataset.__iter__` is a thin wrapper (FrameView → training dict via `encode_frame`), `build_frame_table` is another wrapper (FrameView → columns), and `who_dies_next_baselines` migrates onto it too. This removes the duplicate walk skeletons, keeps obs encoding single-sourced, makes the analysis seam first-class rather than a flag, and lets sim-only consumers skip obs encoding (the perf lever the baselines script currently gets by hand).

Why this is a safe path, not a corner: the walk internals already do everything (proven by the spike), so Option 2 is a behavior-preserving *extract-method* refactor — guarded by the existing suite plus a parity check — not a redesign. **Trigger:** a second non-probe consumer of the walk, a need for lazy-obs speed, or the flag accreting more analysis concerns. Until one fires, `frame_view` stays.

### Other deferred items

- **Caching (stretch).** Tables rebuild each run; most walks are fast enough that the toolkit earns its keep without it. Deferred partly to dodge the cache-invalidation question (Q8) — but the leaning is recorded there so future-us isn't stuck.
- **Richer per-game / cross-frame derivers.** The `per_game(prepare, index)` seam covers per-game-from-sim (incl. army-delta). The richer form — a deriver that sees the perspective's *ordered frames* (for cross-frame over derived/obs quantities, or event-time alignment around eliminations) — lands when something needs it. Correctness preconditions when it does: cap by whole games (never mid-game), window in tick-space (`frame_t`), not row offset.
- **Raw-sim-reading derivers (contact/vision).** The predictability-conditioned eval (6.13-15 menu item 2) needs ownership/contact info not in the obs; the `Frame.sim` access already supports it, so these are new derivers, not new plumbing.
- **Probe-framework consolidation.** Once the deriver set proves out: probe `extract_target`s delegate to derivers (de-dup), `FrameNeeds` moves to a shared home both import, and the probe reference-baseline fix becomes "the rule is a derived column on the eval cache." Gated on FrameTable maturing; not MVP.
- **Misc backlog.** `value_head_probe.py` is ~600 lines the probe framework now subsumes (migrate or delete). `probe_compare` (collate `summary.json` across probe runs) mirrors the existing `compare_runs.py` — cheap, high-use, but separate from `fq`.

## Open design questions (to discuss — not resolved here)

Collected so they're addressed deliberately. Tags: **[lean]** = my recommendation but open; **[open]** = genuinely undecided. Numbered for reference.

### MVP-level (want resolution before/while building)

- **Q1 — deriver input shape.** Separate `Frame` class (demo) vs grow the dataset's `FrameView` to expose obs (lazily) and use it directly. The latter is cleaner (one object) but touches `dataset.py` (ties to the Option-2 path). **[lean]** keep a thin `fq`-side `Frame` for the MVP (no further `dataset.py` change); revisit when Option 2 lands.
- **Q2 — multi-column derivers.** The demo splits "dataset-emitted fields copied via `emit_cols`" from "computed single-column derivers." Do we want derivers that emit several named columns at once (e.g. a victim+dt deriver), and should dataset fields instead be expressed as trivial derivers for uniformity? Trade-off: uniformity vs the dataset already computing them. **[open]**.
- **Q3 — `check_representative` interface.** What it takes (per-group target + grouping) and reports (game count, realized variance), what its default thresholds are, and whether the *common* per-player case should auto-warn inside build while staying a helper elsewhere. **[lean]** helper-only, no auto-gate; thresholds start as one sensible default and resist a per-metric taxonomy.
- **Q4 — `join_dump` semantics.** Confirm: inner-join on the table's rows (table ⊆ dump's full split), add dump columns, assert shared truth columns agree as a generic check (not who-dies-next-specific), warn on unexpected partial coverage. **[lean]** as stated; first validated by the argmin/ranking probe.
- **Q5 — obs_cfg sourcing.** Config-only (the spike showed `OBS_CONFIG_DEFAULTS` works; army channels are `dense_history_n`-independent) vs checkpoint-pinned. The rule likely splits by use: config-only for ground-truth tables; checkpoint-pinned when joining to a specific model's dump/probe (obs encoding must match that run). **[lean]** support both, default config-only, require a checkpoint only for model-joined tables.
- **Q6 — `game_id` stability.** The demo's `game_id` is a walk-local counter (0..n_games−1) — fine for representativeness, but **not** stable across runs/sampling and not joinable to external game identity. Do any use cases need a stable per-game id (from `sim_path`)? **[lean]** walk-local for MVP; add a stable id if a cross-run/cross-table use appears.
- **Q7 — CLI ergonomics.** Snippet input modes (`-e` + stdin; skip `--file`), injected namespace, output convention (print `-e` value; stdin self-prints), and whether a small name→`FrameSpec` registry is worth it for `--table` selection (a registry of *families*, not of columns — bounded). **[lean]** yes to a small family registry; rest as stated.

### Deferred-design (settle when the feature is built)

- **Q8 — cache invalidation (if caching is ever added).** Manual `--rebuild` vs a `version` int per deriver/spec baked into the key vs content-hashing deriver source. **[lean]** version int — explicit, cheap, no false invalidations — but only if/when caching is built.
- **Q9 — `FrameNeeds` routing.** When consolidating with probes, families declare `FrameNeeds` and the engine routes through `dataset_args_for` (replacing inline `dataset_kwargs`); `FrameNeeds` moves to a shared home so `fq` and `probes/` both import it without `fq` depending on `probes/`. **[lean]** do this at consolidation, not MVP.
- **Q10 — naming.** `FrameView` vs `Frame`, `Deriver`, `FrameSpec`, `fq`/`ft`. All provisional; lock before the package lands. **[open]**.
- **Q11 — does the design serve the live research need?** Sanity check against the actual next step (the argmin/ranking probe: head-vs-rule + close-call analysis, [`6.15-2`](6.15-2-army-regression-probe-results.md) menu). It needs `join_dump` + the head's predictions joined to the rule/margin columns — which this design supports, but worth confirming the end-to-end flow before calling the MVP done.
