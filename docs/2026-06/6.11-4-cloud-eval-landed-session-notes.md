## Usage

```sh
# Spawn on Modal (fire-and-forget, like training — the run name + pull command
# print up front; --detach is required or app teardown cancels the run).
# Follow progress: `uv run modal app logs eval-adhoc` or the dashboard.
uv run modal run --detach packages/eval-tools/scripts/run_eval_modal.py \
    --policy checkpoint:data/training/runs-cloud/<run>/checkpoints/epoch_005.pt:force_move=true \
    --policy evalbot \
    --maps set:eval-map-set-v1:sample=20 --gpu T4

# Pull artifacts once done (results + analysis + games; --no-games to skip the bulky npz)
./packages/eval-tools/scripts/pull_eval_runs.py <run-name>
```

On `--concurrent-games`: auto-sizing targets ~32 NN rows per forward (the M1 sweet spot), which undersizes cloud GPUs — e.g. 6 NN per game → only 5 concurrent games. Raise it explicitly for real runs; gains are sublinear since cloud eval is obs-build-bound.

Checkpoint paths are the *local* `data/training/runs-cloud/...` form — the entrypoint rewrites them to the volume mount, and only volume-resident checkpoints are addressable. `--maps` must be a `set:`; the `random:`/`replay_id:` modes need the local DB. Local `run_adhoc.py` accepts `set:` too, and for anything meant to be compared across time it's the right default — `random:N` seeded picks silently shift as the corpus grows (the candidate list is indexed by position), whereas a seeded `sample=K` of a frozen set reproduces forever.

## Gotchas hit (fixed, recorded for pattern-matching)

- **`modal volume get` dest-collapse:** when the local destination directory doesn't exist, modal writes the remote dir *onto* that path (it left a zero-byte file at `data/eval/runs-cloud`, then failed on the children). `pull_runs.py` had the same latent assumption, masked by `data/training/runs-cloud/` always existing; both pull scripts now `mkdir` the dest up front.
- **fjson is the `fracturedjson` crate.** The crates.io `fjson` crate is a library with no binaries — `cargo install fjson` fails. The image installs `fracturedjson` with `--root /usr/local` (`~/.cargo/bin` isn't on PATH in the function runtime), placed before the sim-core layer so sim-core source changes don't retrigger the compile. `json_io`'s install hint said the wrong crate; fixed.
- **First image build is the slow path** (Rust toolchain + sim_core + torch install); subsequent runs attach in ~30s. Changing layers above sim-core re-pays the Rust build once.

## State / observations

- Smoke runs: 2 games (bc-model vs evalbot, 2p set maps) in 7.4s of game time on T4. Single-container cloud eval remains host-bound per [`5.31-1`](../2026-05/5.31-1-eval-perf-cloud-host-bound.md) — the capability's value is colocation and future fan-out, not per-run speed. `--concurrent-games` is worth raising on cloud GPUs (auto-sizing targets the M1's ~32 NN rows).
- The cloud import graph ships without replay-parser/collector (`seed_map`'s parser import is lazy). Their *declared* deps remain on game-runner/self-play — `TODO(deps)` in `seed_map.py`.

## Follow-up: basic perf pass on cloud eval

Settle the default knobs for real runs with a small sweep (one moderate eval config, e.g. 6p NN-vs-NN ~20 maps, timed):

- **GPU class** — T4 vs L4/A10: does a faster card move games/sec at all, given 5.31-1 found cloud eval host-bound? Expectation: barely; confirm and lock in the cheapest adequate card.
- **`--concurrent-games`** — sweep (e.g. 5/16/32/64) at fixed GPU; find the knee. Auto-sizing targets the M1's ~32 NN rows and undersizes cloud.
- **Container CPU allocation** — `eval_remote` doesn't set `cpu=`, so it runs on Modal's default request. If obs-build is the bottleneck, this is plausibly the biggest lever — but check whether the batched runner's host work is even multi-core before paying for cores (if it's single-threaded, more CPUs do nothing without adding workers, which would be a code change, not a knob).

Output: a recommended default combo baked into the entrypoint (gpu/cpu defaults, auto pool sizing that accounts for cloud) + a short note with the numbers.
