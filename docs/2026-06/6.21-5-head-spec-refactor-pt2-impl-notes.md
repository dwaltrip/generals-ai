# Aux-head spec/registry refactor pt2 — implementation notes (slices 2 & 4)

*Date: 2026-06-21. What landed in the second working session on branch `elim-head-work-continues`: slice 2 (accumulator reconstructs `total` from the registry) and slice 4 (config nesting). Successor to the design doc [6.21-1](6.21-1-aux-head-spec-registry-refactor.md) (which holds the full slice plan and the load-bearing invariants) and the mid-impl handoff [6.21-4](6.21-4-aux-head-refactor-handoff.md) (slices 0–1 + the slice-2 setup). This note records the parts that aren't obvious from a read-through of the diff, plus the remaining follow-ups. Slices 0–2 and 4 are committed; slice 3 (naming) is not started.*

## What landed

- **Slice 2** — `LossAccumulator` no longer reconstructs `total` from a hardcoded second term-list. It loops the registry, accumulates each spec's metrics weighted by the spec's own count, and rebuilds `total` from the same `term_key`/`weight_attr` the live `bc_loss` uses. `total` is still assembled in two places (live in the loss, epoch-mean in the accumulator), but both now derive it from the same registry metadata, so they can't silently drift. (Later unified into one `_assemble_total` helper — see the 2026-06-23 update below.)
- **Slice 4** — `TrainConfig` holds one `loss: LossConfig` instead of re-declaring the loss knobs flat. The field triplication (TrainConfig field + LossConfig field, each re-validating, plus the `train.py` hand-copy bridging them) collapses to one definition; `train.py` is `loss_cfg = config.loss`. Loss knobs are accepted both nested under `loss:` and flat (back-compat).

Both slices are numerically identical — the two smoke configs reproduce the pre-refactor baseline exactly, on both the flat and nested config shapes.

## Implementation notes — the non-obvious parts

### Slice 2 (accumulator → registry)

- **Why the spec metadata is static on the class, not carried per-call.** The accumulator only ever sees the flat `losses` dict (`bc_loss`'s return), never the `AuxLossResult`. So "which metric is the trained term / the count's reporting name / the loss weight" had to be lifted to class attributes (`term_key`, `count_key`, `weight_attr`, `metric_keys`) that *both* `bc_loss` and the accumulator read without re-running `loss()`. That's the whole reason those attrs exist — `AuxLossResult` itself slimmed to `metrics` + `count`.
- **The annotation asymmetry on the spec attrs is deliberate.** Only `metric_keys: tuple[str, ...]` carries an explicit annotation — pyright's tuple-invariance rejects the bare literal (`("elim", "elim_soft")` infers narrower than `tuple[str, ...]`). The three `str` attrs don't need it (a str literal satisfies the `str` protocol attr). Not an oversight; annotating the three would imply a constraint that isn't there.
- **The loop is additive-ready; the config is single-gate, on purpose.** Both `bc_loss` and the accumulator now sum per-spec, so they're structured to handle two simultaneously-live heads (untested — the variants are mutually exclusive today, so no run ever has two). The only thing blocking genuinely-additive heads is that both elim specs share `weight_attr = "lambda_elim"` — a second independent head needs its own λ field on `LossConfig`. That boundary is the documented deferral (loop carries over, config gains a field when a head is actually additive), not an omission.
- **The dump CE is still not the loss CE under weighted runs.** Carried-forward invariant: the dump's hard `elim_ce` is unweighted per-bin; it equals the accumulator's `elim` only when `elim_bin_weights is None` (today's default). Don't collapse `dump_records` into a reuse of the loss CE — they diverge by design under a weighted run.

### Slice 4 (config nesting)

- **Why `spec.validate` stays at the `TrainConfig` level (reading `self.loss`), not in `LossConfig`.** The τ-requires-variant rule needs to see the arch (the variant) *and* the loss (the tau) at once. That cross-cut is the structural reason the nesting doesn't fully unify config: arch rides into the `.pt` checkpoint, recipe rides into the run-dir `args.json`, and the validation straddling both has to live where both are visible. Same for the `lambda_elim > 0 requires a built head` rule.
- **There are three back-compat fold sites, not one.** Flat loss keys are folded into the nested shape at `from_file`, at `load_parent_config` (reading a parent's `args.json`), and inside the resume merge (`_resume_config`). The resume path is the subtle one: it merges the parent + overlay dicts *straight into the `TrainConfig` constructor*, bypassing `from_file`, so it needs its own fold rather than inheriting one. All three share the `_extract_loss` helper.
- **The `mu_pass` correctness point in `load_parent_config`.** A pre-nesting `args.json` is fully resolved but has no `mu_pass` key — `mu_pass` was hardcoded to `1.0` in `LossConfig` and was never a `TrainConfig` field, so it never serialized. `load_parent_config` completes a flat parent's loss block from the `LossConfig` defaults. Without that defaults-fill, resuming *any* pre-nesting run would compare a 6-key parent loss against a 7-key effective loss and falsely trip drift on the reshape.
- **Loss is constructed at the boundaries, not coerced from a dict in `__post_init__`.** This mirrors how `arch` is handled in `TrainConfig` (built via `build_model_cfg` at the parse boundaries), *not* how `obs` is coerced from a dict inside `ModelConfig.__post_init__`. The obs-style dict-coercion doesn't earn its place here: nothing does `TrainConfig(**asdict(...))`, so it would be a shim with no consumer, and accepting a dict where the field is typed `LossConfig` creates a pyright type tension at the resume call site. `from_file` and `_resume_config` each build the `LossConfig` explicitly instead.
- **Loss deep-merges like arch on resume.** A resume `--config` that sets one knob continues the parent's other knobs; without per-knob merge (popping `loss` from both parent and overlay, then `{**parent_loss, **overlay_loss}`) an overlay would reset the unset knobs to defaults.
- **`mu_pass` is now config-settable.** Nesting `LossConfig` exposes it as a recipe knob for the first time. Default unchanged (`1.0`), so no behavior change — but it's new surface, and it's why the parent-args defaults-fill above is load-bearing.
- **The resume drift message went coarse.** Loss is now one trajectory-critical key, so a changed knob reports as `loss {…}->{…}` rather than `lambda_elim 0.0->0.3`. Behaviorally identical (still aborts without `--force-config-mismatch`); only the message is less precise. This was a deferred decision (see follow-ups).

## Update — 2026-06-23: activeness ownership + total unification

Follow-on cleanup on branch `code-cleanup`:

- **Aux-head activeness is now owned, not sniffed.** `BCModel` keeps the spec it resolves at construction as `active_aux_specs`; `bc_loss` and `LossAccumulator` take it as a parameter and iterate exactly the built heads. The three key-presence gates in the loss/accumulator — and the `spec_for` re-resolution in `eval/run.py` — are gone. This supersedes the "iterate the registry, act on the spec whose `output_key` is present" gating the slice-2 notes and `registry.py` describe (that docstring is now stale on the loss side). `bc_loss` asserts each declared head emitted its logits, so a model/spec-list mismatch is loud, not a silent no-op. `spec_for` now runs in exactly two places: `BCModel` (the owner) and the dataset workers (no model there).
- **`total` is unified** (resolves the slice-2 caveat above). The base policy/value/pass line and the weighted aux sum, previously written in both `bc_loss` and the accumulator, route through one `_assemble_total` helper — polymorphic over tensor (live) and float (epoch-mean), so per-batch and epoch totals can't drift.
- **Zero-count guard warns.** The accumulator's `count <= 0` path is now purely a div-by-zero guard and warns (the degenerate empty-epoch / smoke-run case) rather than silently skipping.

This drains the **loss/accumulator** portion of follow-up 3 below; the `train.py` JSONL/console formatters and the `eval/dump.py` `output_key in out` site are untouched and still open.

## Follow-ups / open threads

Ordered by priority.

1. **Naming cleanup (slice 3) — wants its own scoping discussion first.** The names drifted: `next_death_target` keys on board-removal (a function named "death" computing removal), the `elim_*` / `next_elim_*` prefixes encode silo-history not meaning, and the variant string `"next_death"` is config/dump/checkpoint-facing. Two scopes: the surgical `next_death_target → next_removal_target` (function + its import + tests, no serialized strings touched), or a full `elim_`/`next_elim_` rename that reaches checkpoint/dump/config strings and needs the `dump_compat` aliasing pattern. Slice 2 concentrated part of the rename surface onto the spec attrs (the `metric_keys` / `weight_attr` literals are now in one place per spec), but the serialized-string reach is unchanged. Don't pick the scheme without settling scope.

2. **Loss config → `.pt` checkpoint** (with a `LEGACY_LOSS` pin mirroring `LEGACY_ARCH`). The objective is the one resume-critical piece with no durable per-checkpoint pin — optimizer state and arch are in the `.pt`, but the recipe lives only in `args.json` and leans on "default == historical behavior" (the gap the `TrainConfig` NOTE flags). Slice 4 made this nearly free: `config.loss` is one object to `asdict` into the save payload. It's a checkpoint-format change with a back-compat tail, so it's its own yes/no decision.

3. **Reporting / metrics cleanup — drain the residual variant-gated surface.** *(Partially done 2026-06-23 — the loss/accumulator sites are drained via `active_aux_specs`; the `train.py` formatters below remain.)* The spec abstraction collapsed the loss/target/dump/eval-meter dispatch, but a few variant-gated sites remain that still make "understand one variant" mean grepping the reporting code: `train.py`'s per-batch JSONL + console formatters branch `if "elim" in … elif "next_elim" in …` (they key on metric-presence, so they don't break, but they're un-drained), and the `train.py` time_bin bin-edges dump-meta line is a documented residual. The `eval/run.py` meter path is already routed through `build_eval_meter` / `eval_summary` on the spec, so this is mostly the `train.py` formatters. Worth a spec method only if it comes out cheap — that's the thing to assess when picking this up.

4. **`loss.py` → folder (re-measure first).** The file is still substantial because policy/value/pass aren't moving and `LossAccumulator` stayed. Whether to split into a `loss/` package (`config.py` / `core.py` / `accumulator.py`) is a call best made on the post-refactor size — re-measure before deciding. The lean from 6.21-1 is *partial vertical*: the per-variant loss/target/dump logic already relocated into the spec modules; the head `nn.Module`s stay in `model/heads/` (moving them churns import paths for no gain).

Lower priority:

- **Drift-message granularity.** Keep coarse (`loss {…}->{…}`) or special-case `loss` in `check_drift` to report `loss.lambda_elim 0.0->0.3`-style per-subfield diffs. Parked during slice 4; now visible in `check_drift` to eyeball in context.
- **Migration-shim removal.** The `_extract_loss` flat-key acceptance is a marked shim. Verified (this session) that it is **not** needed for loading old checkpoints (loss config isn't in the `.pt` — `TrainingState.save` writes `model`/`arch`/optim/`epoch` only) nor for analyzing old runs (no path reconstructs a `TrainConfig` from an old `args.json`; analysis tools read `args.json` as a raw dict, shape-agnostic). Its only two consumers are resuming a pre-nesting run and re-running existing flat `--config` files (local sweep + smoke configs). So with no in-flight runs, it can be dropped once those local flat configs are rewritten to the nested shape and you don't intend to resume a completed pre-nesting run — the `from_file` flat-acceptance and the resume-side normalization are separable and can be removed independently.
