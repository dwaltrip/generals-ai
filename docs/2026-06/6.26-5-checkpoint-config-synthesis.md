# Checkpoint & config versioning — synthesis: the shape axis and the behavior axis

*Date: 2026-06-26. A follow-up to the checkpoint-config-versioning design ([6.24-4](6.24-4-checkpoint-config-versioning-design.md)), carrying forward the conceptual insights from the session that followed it. The through-line: a checkpoint's faithfulness has **two separate axes** — config **shape** and model **behavior** — and behavior is the larger, mostly-unsolved one. 6.24-4 designed the shape axis; this doc maps the behavior axis, with the shape axis re-stated as context. Organized by concept, not chronology; meant as a standalone, durable reference. Companions: the boundary surveys ([6.26-1](6.26-1-survey-pt-checkpoint-io.md) / [6.26-2](6.26-2-survey-sidecar-config-io.md) / [6.26-3](6.26-3-survey-model-usage-trace.md)), the discussion catalog ([6.26-4](6.26-4-ckpt-config-big-discussion-catalog.md)), the focused chunk-1 plan, and the critical-open-questions doc. "→ chunk-1" marks where a concept has a concrete footprint in the chunk-1 implementation. Material tagged **(deferred)** or **(aspirational)** is not committed work.*

## The frame: two axes, historically conflated

A checkpoint is faithful along two independent axes:

- **Shape** — does the stored config have the *current field structure*, so live code can consume it without branching on version? This is what 6.24-4's migrate-once seam delivers: a raw config of any historical shape is migrated to a current-shape `TrainConfig`, and the rest of the code never inspects a version or an old field.
- **Behavior** — does running *current code* against that current-shape config *reproduce what the checkpoint actually did* — the same forward outputs, built from the same obs, scored by the same metrics? The seam does not deliver this, and structurally cannot.

The conflation to guard against: it is natural to assume that a current-shape config means a faithful reconstruction. It does not. The seam produces a current-shape `TrainConfig`; whether the model that config builds *behaves* like the original depends on code the config does not capture and the seam never touches. Shape is necessary for fidelity but not sufficient.

This matters because the project's core workflow — comparing checkpoints in eval sweeps — loads weeks-old checkpoints alongside fresh ones. If an old checkpoint is reconstructed with code that has drifted, the comparison is silently wrong.

### Recurring through-lines

Three ideas thread through everything below; worth holding while reading:

1. **Shape ≠ behavior.** The organizing frame, and its corollary discipline: *don't let a shape-fix stand in for a behavior-fix.* The same mistake recurs in several forms — `config_version` mistaken for an architecture version; "re-save a checkpoint forward to keep it current," which updates only shape.
2. **Frozen vs. live.** Anything that must reproduce the past may depend only on *frozen* things — fixed key names, fixed historical values — never on *live* code or defaults that drift. This governs both the migration discipline and the behavior-fidelity problem.
3. **One fidelity-scope knob.** Barriers, the support tiers, migration granularity, and the supported-version short-list are all the same lever: *how many version-boundaries do we keep fidelity across?*

A fourth idea is a posture rather than a concept: **decouple** — isolate version-complexity behind one boundary, and build the part that doesn't bet on the open questions. The migrate-once seam and the chunk-1 regroup are both this.

## The shape axis (handled — re-stated as context)

6.24-4 specifies this axis in full; the core, restated so this doc stands alone:

**The goal.** Make the checkpoint self-describing (store the full resolved `TrainConfig` in the `.pt`) and isolate all config-format/version complexity behind a single boundary, so the rest of the code holds a current-shape config and never reasons about versions.

**The mechanism.** One migrate-once seam on load: read the raw config off disk → `migrate(raw)` up the version chain → construct a current-shape `TrainConfig` (validators run on guaranteed-current data). Outside this seam, no code branches on version. The enforceable invariant: an `if "old_field" in …` or a version check *anywhere but inside a migration* is a leak.

**The operation taxonomy** (from the 18 historical config changes; detail in the survey 6.24-3): add-field (fill a missing field with its frozen historical value), rename, nest/move-a-group, drop, and rename-plus-value-map. The overwhelming majority are additive.

Two refinements:

**Frozen vs. live — the migration discipline.** A migration may depend only on frozen literals: fixed key names and fixed historical fill-values. It must never reach for live code or live defaults, which drift. The cautionary example is in the current code: `_arch_for_load` reconstructs legacy archs via `asdict(LEGACY_ARCH)`, where `LEGACY_ARCH` is a frozen *instance* but of the *live* `ModelConfig` class — so it produces "whatever the current shape is" (collapse-to-current), not "a fixed historical version." That single, hand-maintained, live-typed snapshot is exactly what the versioned design should replace: per-version frozen fills, each frozen to its target version forever and never edited again. The `vN.json` schema snapshots are the frozen reference that makes the chain checkable — each migration is contracted as "given a valid `vN` dict, produce a valid `v(N+1)` dict," testable per link.

**Migration granularity is a knob.** Stepwise-frozen (one migrator per version boundary, append-only, never edit the old ones) is the low-drift default — a link breaks the chain only if it isn't truly frozen, which the per-link snapshot tests catch. A single "master migrator" edited each version is the edit-in-place, high-drift extreme (it re-introduces the frozen-in-time problem). Squash — periodically collapsing a run of old migrators into one — is the tunable middle, and it turns out to be the *same lever* as the support tiers (see the behavior axis below).

→ chunk-1: the Migrator skeleton (an empty chain at v1, plus the dispatch with a `v > CURRENT` guard). The v0→v1 normalizer is a near follow-up; note it straddles the two axes — mechanically it is shape (produce a current-shape dict), but its frozen-fill *values* are behavioral pins (e.g. the legacy obs dtype that reproduces old inputs). The frozen-fill is the one place where shape-migration carries behavioral fidelity.

## The behavior axis (the unversioned-code problem)

The core finding: **behavior is a function of two factors — the config and the code that interprets it.** The config — and its version stamp — pins one factor. The *code* is unversioned. So a silent code change reproduces an old checkpoint differently, with no field change and no version bump to signal it.

Stated as a principle: **config/data-interpreting code is unversioned, so a silent code change breaks cross-version faithfulness.**

### Two faces

The principle has two distinct faces, and keeping them distinct matters:

**Behavioral-reproduction — does the reconstructed thing *do* what it did?** This is the **model forward and the obs encoder**, both described by `config.arch` (the obs config nests under the arch). The obs are the model's *inputs*, so a silent obs-encoder change makes the model see different inputs and produce different outputs as surely as a forward-path change does — obs belongs *with* the model here. A single forward-level golden test (game-state → build obs → forward → hash the output) exercises both at once.

**Measurement-comparability — are measurements *on* checkpoints comparable across versions?** This is **loss and metrics**. A silent loss- or metric-code change does *not* alter what the checkpoint does — its weights are fixed, its outputs are fixed — it alters how those outputs are *scored*, which breaks cross-run comparison (load two checkpoints, compute val-loss for both with current code; if the code drifted, the numbers aren't comparable). This is the "metrics leak," and it is a *different* problem from behavioral-reproduction, with its own home.

The discipline that falls out: **obs goes with the model (behavioral); loss goes with metrics (measurement).** Lumping them — the natural first instinct — mis-files the problem.

Consumers already lean on this surface: obs is built from the loaded model's own config (`model.cfg.obs`), and some consumers reach *into* model internals (e.g. extracting the trunk and forwarding on it). So the architecture surface — `model.cfg`, `.trunk` — is itself a pinned contract.

→ chunk-1: that obs is already sourced from the loaded config *validates the whole self-describing direction* (it is the existing idiom, not a new bet); the refactor must keep `model.cfg.obs` and `.trunk` reachable; and the stale `value_head_probe.py` — the one consumer that builds obs from hardcoded defaults instead of the loaded config — gets archived.

### Exposure is graded

The principle is uniform; the *severity* is not.

- Behavioral-reproduction (forward + obs) is **high exposure** — it runs on *every* inference, eval, and probe load of a checkpoint.
- Measurement-comparability (loss + metrics) is **lower and narrower** — loss runs only in val-loss analysis and on resume, never in gameplay/policy eval.

So priority concentrates on the model+obs face.

### Why the seam can't reach this

The migrate-once seam produces a current-*shape* config; it has no leverage over what the code *does* with that config. `load_state_dict(strict=True)` is a partial guard on the behavioral side — it catches any change that alters parameter names or shapes (added/removed/resized layers, renames — the structural majority of arch drift). But it is blind to the residual: a *param-preserving computation change* — swapping an activation, reordering ops, rewiring a path with no parameters — which moves no stamp and raises no error. That residual is the silent case no existing guard catches.

Two consequences worth stating plainly:

- **The self-describing checkpoint is necessary but not sufficient.** It is a *prerequisite* for any behavioral-fidelity strategy — you cannot reconstruct faithfully without the exact arch and recipe — but it does not, by itself, deliver fidelity.
- **This is pre-existing, not introduced by the versioning work.** Today, `strict=True` plus current forward code already runs every old checkpoint with today's code. The versioning design *surfaces* the behavior problem; it does not create it.

## Strategies for the behavior axis

These are the options for *coping with* and *detecting* behavior drift. Most are **(deferred)** or **(aspirational)** — the option space, not a committed plan.

### Barriers

Frame each code change as erecting a barrier or not. An **additive, config-gated** change (a new optional variant, old paths surviving as gated branches) erects *no barrier* — current code reproduces both sides. A **non-additive** change (delete a variant, redefine a knob's meaning, a behavior-changing refactor) erects a *barrier* — configs from before it can no longer be carried to current.

Today the repo is **barrier-free**: the model and obs evolution has been additive and config-gated, which is *why* one current codebase reconstructs all of history. This is maintained deliberately, not by luck. What's costly right now is not barriers but staying barrier-free: additive-gated code accretes, and `if/else` branches multiply (the elim-head's several variants leaking even into the train loop, metrics, and logging).

### Capability-defined tiers: Native / Compat / Unsupported

- **Native** — current code can reach it (no barrier between it and HEAD).
- **Compat** — behind a barrier, served by a fallback that still knows its behavior.
- **Unsupported** — not loadable; re-train if it's needed.

The boundary is **capability-defined** (does current code reach it?), not taste-defined. Curation — importance, usage — operates *within* the supported set, deciding what to bless and test, not where the line falls. Today everything is Native; the cost of keeping it that way is rising, so some versions will move to Compat and Unsupported over time. (deferred)

→ chunk-1: the **LoadPlan tagged union** (`Native` real; `Compat` / `Unsupported` as reserved, currently-empty arms) is the structural firewall that lets these tiers be filled in later without re-plumbing callers. The public loader returns a `BCModel` regardless — the tiering stays internal until a caller needs it.

### The configurable builder is Compat, not the whole system

A fully configurable "build any historical model/obs/loss from config" engine feels like overkill as the *whole* system, and it would be. But it is the right shape for **Compat specifically**: Native stays hand-written and legible (you develop against it; there is only ever one current model plus its additive-gated neighbors), while Compat is the general, less-ergonomic fallback where generality is worth the trade because nobody develops there — it only reproduces frozen behavior. Build it lazily: it stays empty until the first barrier. (aspirational)

### The fidelity contract — the honest caveat

Moving old behavior into Compat reduces *cognitive* load (Native reads clean) but not *total* fidelity-code — unless you also accept *degraded* fidelity for the tail. So the real lever is a per-barrier choice: **faithful** (carry the old path forever), **best-effort** (approximate, warn), or **unsupported** (don't load; re-train). The tier machinery only earns its complexity if some barriers get best-effort or unsupported. (deferred)

### One fidelity-scope knob

Barriers, the three tiers, migration granularity (stepwise/squash/master), and a "short-list of supported versions" are all the same lever: **how many version-boundaries do we keep fidelity across?** Stepwise-frozen across the supported recent range; squash or drop (→ Unsupported) the old range.

- **Backward** (support a historical subset): just scopes the v0 work and leans on the Unsupported tier — no change to the core architecture.
- **Forward** (support a subset of *future* checkpoints): bounds the Compat burden. But the trap is the shape-vs-behavior conflation again — "re-save blessed checkpoints forward to keep them current" updates only config-*shape*; the weights stay tied to the old arch, so an arch barrier still forces Compat-or-re-train. The forward case is a critical open question (see below).

### Co-residency is the hinge

The strategy choice turns on one requirement: the project needs old and new checkpoints **co-resident in one process** (eval sweeps — two models play each other). Co-residency is what breaks the cheapest fidelity strategy — pin a SHA per checkpoint and check out the old code to run it — because you cannot have two code versions live in one process by checkout. So this forces keeping old code alive in `main` (Compat).

The one possible escape: a **repo-copy orchestrator** — run each checkpoint in its own pinned repo copy and coordinate them through a thin control layer over a frozen wire protocol at the *game-state* level (each copy builds its own obs and runs its own model; the orchestrator passes only game-state and moves). If it can be made cheap, it revives pin-SHA-checkout for the co-resident case and could remove most of the Compat burden. There are sharp edges to solve — per-version *environment* reconstruction (not just code, but dependencies), the orchestration plumbing, and migrating the eval path from in-process handles to RPC — and it has one scope limit: it covers *gameplay* co-residency (models playing via moves) but not *introspection* co-residency (the probe path reaches *inside* a model, which doesn't cross an RPC boundary). This is a critical open question (see the critical-questions doc). (aspirational)

### Detection — the signal ladder

Even with `strict=True`, the residual silent subclass needs its own signal. From cheap-and-loose to tight:

- **param count** — trivial, collides easily.
- **param signature** (names + shapes) ≈ what `strict=True` already checks.
- **module-repr hash** — catches registered-structure changes (activations, ordering) that strict-load misses; slightly brittle.
- **forward golden test** (seeded init + fixed input → hash output) — catches *any* computation change, including inline-functional ones; needs determinism (run on CPU).
- **source SHA** — catches all code changes; over-triggers (provenance, not precise detection).

The common pattern elsewhere is strict-load + a characterization/golden test + discipline + a stored code-SHA; formal architecture-hashing is uncommon. (Hugging Face leans on an architecture-class identifier plus integration tests; torchvision ties weights to code via versioned weight enums.) The current lean is a **manually-incremented `arch_version` constant + a per-version golden test** (config → expected output hash); the golden test guards the manual bump the way the config key-set check guards `config_version` — it fails if behavior changes without a bump.

Four distinct stamps, easy to conflate, each on its own axis:

- `config_version` — versions the config *dict shape* → drives migration.
- `arch_version` — pins the *architecture* (config plus build-code) → behavioral-drift detection.
- `code_sha` — provenance ("which commit produced this"); complements, doesn't replace, the arch stamp.
- `in_ch` — a narrow input-channel checksum (the arch stamp's narrow cousin).

→ chunk-1: reserve a nullable `arch_version` field and populate `code_sha` (placeholders now; the scheme and enforcement are deferred). These are save-time-only facts — they cannot be retrofitted, so the *slots* must land in the first format even though the *mechanisms* come later.

## What this reshaped: the regroup and decoupling

Designing the whole behavior axis up front was too much to hold at once. The response was to **decouple**: build the part that does not bet on the open behavior-axis questions.

That part is **chunk-1**: the self-describing v1 format and the migrate-once read seam — the shape axis — built behavior-preserving, with the behavior-axis placeholders (`arch_version`, `code_sha`) reserved and the fidelity machinery (the Compat builder, golden tests, the repo-copy orchestrator) deferred. Chunk-1's shape is robust to *either* resolution of the open questions; that robustness is the point of cutting it this way. (See the chunk-1 plan for the focused design.)

The questions that gate the *broader* design — not chunk-1 — are two, and they are linked:

- **How many version-boundaries do we keep fidelity across?** (the fidelity-scope knob).
- **Can we get co-residency cheaply via a repo-copy system?** — which, if yes, largely *answers* the first by removing the in-`main` Compat burden.

These are collected in the critical-open-questions doc as the decisions to make before committing the broader path.
