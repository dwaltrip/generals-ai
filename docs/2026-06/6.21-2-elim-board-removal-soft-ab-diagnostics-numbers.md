## Shared facts

Stated once so the per-analysis pointers stay short.

- **The A/B.** `data/training/sweeps/2026-06-20-elim-head-board-removal-soft-ab/`, two cells, both on the board-removal / present-domain target, seed 0, λ_elim 0.15, 5 epochs, constant LR, corrected (player-status) obs, `cloud_24k_sub_5k`. `removal-hard` is the hard one-hot control; `removal-soft-tau15` is the time-based soft target `p_i ∝ exp(-removal_dt_i/τ)` with τ=15. The death→removal switch and the soft target are described in [6.20-3](6.20-3-elim-soft-target-implementation-handoff.md).
- **The value-A/B baseline is reused, not re-run.** The elim-off cell from the 6.19 gate (`2026-06-19-elim-head-coherent-ab/runs/elim-off`, 3 epochs) is the do-no-harm reference; constant LR makes its ep1–3 comparable to these runs' ep1–3 (pre-registered in the sweep `_note`).
- **Dumps.** Per-epoch full-val dumps (`runs/<cell>/analysis/stratified_val_epoch_00N.npz`), 112,975 frames, of which 95,546 carry a valid next-removal target (`next_elim_target >= 0`). The dump's `next_elim_ce` is the hard one-hot CE for both cells (it equals `val.next_elim` in `epochs.jsonl`), so soft-vs-hard CE comparisons are apples-to-apples on the same one-hot truth.
- **Reading the "first-pass read."** Each analysis's read stays narrow — what that table shows, with at most simple and explicitly-flagged links to a sibling analysis. Confounds are noted per analysis; the big-picture synthesis is a separate doc.
- **Provenance labels.** *Lifted* = the formulation comes from a prior note/script, re-run here on the new data. *Devised this session* = not pulled directly from a prior analysis note/script (several are semi-obvious cuts, not claimed as novel).

### 11. Endgame target artifact (present=2) — *[devised this session]*
**Description.** A targeted check of *why* present=2 is anomalously soft: the true next-victim's removal horizon vs. the winner's, and whether the winner's horizon tracks game-end. The "winner" = the last player standing, identified as the present player with the largest removal horizon (never removed except, by convention, at game end). *(Devised this session — not from a prior note; a debug check of the suspicious analysis-10 number.)*

| quantity                       | present=2 | present=8 |
| ------------------------------ | --------- | --------- |
| victim removal_dt (median)     | 140       | —         |
| winner removal_dt (median)     | 143       | 520       |
| frame_t (median)               | 546       | 46        |
| winner removal_dt + frame_t    | ~762      | ~560      |

(Rows are independent per-frame medians; `winner removal_dt + frame_t` is the median of the per-frame *sum* — the absolute game-end tick — so it does not equal the sum of the row medians above: 143+546 ≠ 762 under skew.)

Global present removal_dt percentiles (p50/90/99/100): 175 / 556 / 988 / 1506.

**First-pass read.** At present=2 the next-victim and the winner have near-equal removal horizons (140 vs 143): the game ends ~3 ticks after the loser is captured, and the winner — never actually removed — is conventionally stamped as removed at game end (`removal_dt + frame_t` ≈ a per-game constant). So the soft target at endgame splits ~50/50 between the loser (correctly the hard target's argmin) and the winner. At present=8 the same convention applies, but the winner's horizon is far off (520 ticks, since the game is young), so it draws little mass — the artifact only bites in the endgame. A soft-kernel construction effect, not a property of the hard target.

> *Repro: `fq` over `elim_head_debug`; at `present_mask.sum(1)==2`, compare `removal_dt` at the victim channel vs. the other present channel, and `removal_dt + frame_t`.*

## Methodological notes (observations, not synthesis)

Surfaced while consolidating; recorded here because they bear on how the numbers above should be read, not as cross-analysis conclusions.

- **The CE minimum shifted from ep3 to ep4.** The death-target gate ([6.19-2](6.19-2-elim-head-gate-result.md), [6.20-1](6.20-1-elim-head-diagnostics-numbers.md) analysis 2) bottomed at ep3; both board-removal cells bottom at ep4 (analysis 1). Confounded: the gate's ep4/ep5 came from a combined-checkpoint *resume* (ep1–3 in the A/B, then resumed to 5), so its ep3-min straddles a resume boundary, whereas these runs are continuous 5-epoch. Cause (target change vs. resume artifact) not isolated; single seed. The soft cell's curve is also non-monotonic (ep1 nearly as low as the ep4 min), so its min at ep4 is less clear-cut.
- **Best-val falls at different epochs for different heads.** Value CE minimizes at ep3, elim CE at ep4, hard-trunk army-R² peaks at ep4. The value A/B (analysis 4) and the trunk probes (analysis 5) were read at ep3 (value's best); the elim head's own best is ep4. State which head's best-val a given read is taken at.
- **The soft trunk's army-R² is flat across epochs while the hard trunk ramps** (analysis 6: soft 0.701/0.707/0.701 vs hard 0.630/0.683/0.708). Unexplained; the soft trunk's army fidelity and its elim CE move independently (CE still falling through ep4). Single seed / single probe seed.
- **The endgame artifact (analysis 11) is soft-kernel-only, and objectively wrong — not a close-fight feature.** The hard target is correct at present=2 (argmin removal_dt is the loser); only the soft kernel's `sentinel − t` treatment of the winner puts mass on a never-removed player. Why it's wrong (and not a legitimate "this 1v1 is a coin-flip" signal): the target is built with hindsight — the replay already says who won — so "who's removed next" has a definite answer, the actual loser, and the winner is never removed. A close fight makes the *model's prediction* uncertain, not the *target*; the calibrated coin-flip should come from one-hot targets on the actual loser across many close-1v1 frames, not from softening a single frame's target onto the winner (which is hindsight-contaminated and frame-specific). This is also what separates it from legitimate early-game smoothing: there the soft target spreads over two *real* near-simultaneous removals whose order is genuinely ambiguous; here it spreads one real removal plus a sentinel fiction. The fix (winner `removal_dt → +inf`) keys on exactly that distinction — real removal event vs. sentinel — and collapses present=2 back to one-hot (soft == hard there). Wanting mass on the winner would require redefining the head from "who's removed next" (realized outcome) to "who's at risk" (predictive) — a semantics change, not a fix.
