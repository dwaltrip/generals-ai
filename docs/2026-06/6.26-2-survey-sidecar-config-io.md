# Survey: sidecar config file I/O boundary (`args.json` → `config.json`)

Task B of the checkpoint-config-versioning refactor blast-radius survey. Read-only. Maps every reader/writer of the run-directory config sidecars and the impact of renaming the resolved-`TrainConfig` sidecar `args.json` → `config.json`.

The three sidecars in scope:

- `args.json` — the fully resolved `TrainConfig` (`asdict`), dropped at run start. **The rename target.**
- `args_resume_NN.json` — per-resume-segment resolved config + a `_resume_meta` block. Shares the `args` prefix, so a lockstep rename question.
- `args_cloud.json` (+ `args_cloud_resume_NN.json`) — cloud provenance (gpu, region, host); written only by the Modal entry point.

Two same-named files that are **out of scope** and must not be swept by the rename (see "Name-collision traps"): `value_head_probe.py`'s probe-dir `args.json` (an argparse Namespace dump, not a `TrainConfig`), and eval-tools' eval-run `config.json` (a different file in a different dir tree).

## Rename blast-radius

**Writers (3 emit sites, all in 2 files):** `initialize_run_dir` (`run_dir.py:43`) and `write_args_resume` (`run_dir.py:264`) for the resolved config; `_write_args_cloud` (`run_bc_modal.py:137`) is independent and stays `args_cloud*`.

**Readers that break and MUST fall back to `args.json`** — historical run dirs on disk (and on the Modal Volume) still hold `args.json`; these all run over historical dirs, so each needs `try config.json, else args.json`:

- `prepare_resume` (`run_dir.py:157`) — resuming any pre-rename run. The `n==1` parent name is hard-coded `"args.json"`; resume-segment names are `args_resume_NN.json`. **Highest-stakes**: this is live operational code, not just analysis, and a missing fallback aborts the resume (`load_parent_config` calls `abort` on a missing parent path).
- `run_metrics.py:147` and `:163` — quality/floor analysis over old runs.
- `quality_report.py:38`.
- `perf_report.py:76`.

`load_parent_config` (`run_dir.py:181`) reads whatever path `prepare_resume` hands it, so fixing the fallback at `prepare_resume` covers it — no second fallback needed there.

**Lockstep question for resume segments:** if `args.json` → `config.json`, does `args_resume_NN.json` → `config_resume_NN.json`? `prepare_resume` builds the parent name from the same `"args"` stem (`"args.json"` for n==1, else `f"args_resume_{n-1:02d}.json"`), and `write_args_resume` writes `f"args{suffix}.json"`. Renaming only the fresh sidecar but not the resume sidecars splits the prefix and complicates the parent-chain walk. Recommend the implementer decide explicitly: either rename the whole family (`config.json` / `config_resume_NN.json`) or none. The chain-walk in `prepare_resume` couples them, so a half-rename is the trap.

**Centralization: none.** There is no shared sidecar helper. `json.load`/`json.dump` against these literal filenames is scattered across ~6 sites in 4 modules (`run_dir.py`, `run_metrics.py`, `quality_report.py`, `perf_report.py` — the last via a module-local `_read_json`). The rename is therefore **many-line, multi-file**, not one-line. This is the moment to consider introducing one read helper (e.g. `read_run_config(run_dir)` that tries `config.json` then `args.json`) so the fallback lives in exactly one place instead of being re-implemented at five read sites.

## `args_cloud.json` notes

**Carries:** `gpu`, `cuda_device_name`, `modal_region`, `python`, `hostname`, `written_at` (`run_bc_modal.py:127`). Only `gpu` overlaps what the resolved config also carries (`gpu` is a `TrainConfig` field, so it's in `args.json`/`config.json` too).

**Only reader:** `perf_report.py` (loaded at `:77`, consumed in `_compute_header:161` and `_compute_host:171`).

**Read-precedence the rename could disturb? No.** The precedence is a runtime `or`-coalesce, decoupled from filenames:

- header `gpu`: `(args_cloud or {}).get("gpu") or args.get("gpu")` (`perf_report.py:161`) — cloud value wins, falls back to the config's `gpu`.
- host `gpu`: `cloud.get("gpu") or host.get("gpu_name")` (`:171`).

`args_cloud.json` is read into its own field and merged at compute time; there is no on-disk merge between the two files. The rename leaves this intact **as long as the renamed config is still read into `a.args`** (i.e. perf_report's `args.json` read gets the fallback). The `args_cloud.gpu` → config-`gpu` precedence is preserved automatically.

## Name-collision traps (do NOT sweep these)

- **`value_head_probe.py:885`** writes `args.json` into a probe `out_dir` — it's `vars(args)` from the probe's own argparse Namespace, a different schema entirely. Its only reader is the scratch `tmp/analyze_probes.py` (which actually points at training `runs-cloud/.../args.json`, not the probe dir). A blanket find/replace on `"args.json"` would wrongly rename the probe artifact. Scope the rename to the `TrainConfig` sidecar sites listed in the writer rows.
- **eval-tools `config.json`** (`eval_tools/runner.py:464` write; `run_analysis/loader.py:71` read; plus `policy_spec.py`, `run_spec.py`, archived sweep script) is the **eval** run config, in eval run dirs — unrelated to training. The rename target name `config.json` is therefore already in use elsewhere in the repo, but in a disjoint directory tree, so no real collision. Worth knowing the name isn't novel.
- **`config.input.json`** already exists in training run dirs (verbatim `--config` input text, written at `run_dir.py:46`). After the rename a training run dir holds both `config.json` (resolved) and `config.input.json` (raw input) — close names; confirm that's the intended pairing and not a confusion risk.
- **`scripts/one_offs/survey_config_keysets.py:46`** rglobs `args.json` across historical dirs by design. It's a historical audit, so it should keep matching `args.json`; if it's ever re-run post-rename it'll want to also catch `config.json`. One-off, low priority — note, don't fix.
