# Eval methodology — planning note (`6.02-3`)

**Date:** 2026-06-02
**Status:** Planning / WIP — frames the design space and a provisional recommendation; the decisions themselves aren't made yet. Update as eval work proceeds.
**Purpose:** A standing reference for how we evaluate bot *skill* (game outcomes), as distinct from training-loss eval. Covers the FFA setup question (player count, composition), how to keep a metric comparable as the agent pool grows, and how skill eval could fold into the training loop. Also captures the cloud-eval bring-up plan, since that's the infrastructure that will run it.

Grounding: [`5.28-1`](../2026-05/5.28-1-pyramid-eval-sweep.md) (existing 1v1 protocol + "loss is a poor proxy for skill"), [`5.31-1`](../2026-05/5.31-1-eval-perf-cloud-host-bound.md) (cloud eval is host-bound), [`6.02-2`](./6.02-2-width-sweep-results.md) (placement head goes in-distribution at 4p–8p).

## Where we are

We already have a working **1v1 (2-player) skill-eval protocol** (`5.28-1`): head-to-head checkpoints (or vs the hand-coded eval-bot), `--swap-slots` to cancel seat bias, a self-vs-self noise floor, temp=0.5 for the cleanest signal, n≥80, Wilson CI + binomial p, and per-tick diagnostics that read *what* a model is doing, not just who won. The load-bearing meta-finding from that work: **loss is a poor proxy for skill** — a 1.5% val_policy gap surfaced as ~13pp in head-to-head win rate. Skill eval is not optional; loss curves alone mislead on magnitude.

So this is not a from-scratch design. The open questions are narrower:

1. **Do we add an FFA (N-player) eval, and if so at what player count and composition?**
2. **How do we get a single comparable number across an agent pool that grows over time** (more checkpoints, more eval-bot variants)?

The rest of this note is the design space for those two, framed as four decisions.

## Decision 1 — What is the eval *game*?

Guiding principle: **the eval game does not have to be the deployment game.** We target 8p FFA, but the cleanest *skill* measurement isn't necessarily 8p.

- **1v1 (have it).** Zero-sum, low variance, Elo applies directly, seat bias fully cancellable by swapping the two seats. Cost: strategically a *different game* — no third-party dynamics, different expand-vs-attack incentives — and placement collapses to win/lose, so the placement (value) head is out-of-distribution and uninterpretable here.
- **8p FFA (deployment).** Matches the real task, exercises multiplayer-specific skill (third-party engagement timing, expansion under threat), and puts the **placement head in-distribution**. Cost: high outcome variance, composition-dependent results, seat/spawn effects that can't be fully swapped away, and only ~1 candidate per game unless the lobby is mixed.
- **4p (middle ground).** Multiplayer dynamics present, placement head much closer to in-distribution, lower variance and cheaper than 8p, and 4p maps exist in the corpus. A deliberate option rather than jumping straight to 8p.

This cascades into the metric (D2), composition (D3), and which maps to curate (D4) — so it's the first to settle.

**Provisional lean:** keep 1v1 as the fast, clean A/B gate (already built and trusted), and add an FFA protocol as the "real-task" measure run less often. They answer different questions: 1v1 = "is A's policy better than B's"; FFA = "is it better at the game we actually target."

## Decision 2 — What's the *metric*?

Metric resolution should shift along the skill arc — denser signals early, ratings late:

- **Win rate** — binary, high variance, degenerate at the extremes. Weak BC checkpoints may sit near 0% vs the eval-bot (no gradient); strong ones saturate at 100% vs a fixed baseline. Poor early signal.
- **Placement** (avg finish 1–N) — much denser than win rate, and we already have a **placement head**, so there's a natural symmetry. *Recommended primary FFA metric.*
- **Dense game metrics** (turns survived, peak land, land-over-time) — denser still; useful in the weak-bot regime where even placement is coarse. The `MetricsCollector` already records land/army curves, so this is largely free.
- **Rating systems** — the answer to "comparable number across a growing pool":
  - **Elo** — 2-player only (chess lineage). Fine for the 1v1 gate.
  - **TrueSkill** (Microsoft Research; Herbrich–Minka–Graepel 2006, the rating system behind Xbox Live matchmaking) is built for N-player free-for-all and team ranking. It ingests per-game *placements* and maintains each agent's skill as a Gaussian (μ, σ) — so a newly added checkpoint starts uncertain and converges with games, which fits a *growing pool* well. Rank by a conservative estimate (e.g. μ − 3σ). Generals.io's own star/rank ladder is a real-world FFA-rating precedent in this exact game.
  - *Limitation to record:* a scalar rating assumes near-transitive skill. FFA has non-transitive elements (counter-strategies, king-making) a single number can't capture. TrueSkill is still the best available cross-pool summary; just don't treat it as ground truth about a strategy's quality.

**Key dynamic — the metric ceilings out unless the pool advances.** A fixed reference (e.g. the eval-bot) gives a gradient only while our bots are near its level. Once they pass it, win rate pins at ~100% and placement-vs-that-pool flattens — the yardstick stops measuring. This is the self-play league insight in miniature: the opponent set has to keep pace with the candidates, which is exactly what a *growing frozen pool* (D3) provides.

## Decision 3 — Opponent *composition*

- **Gauntlet** — candidate vs a frozen reference lobby (e.g. 1 candidate + 7 eval-bots). Simple, isolates "how good vs the baseline." Costs: only 1 candidate placement per game (expensive to drive variance down), saturates once our bots pass the baseline, and risks overfitting to one opponent's quirks.
- **Frozen pool / "league"** — maintain a set of past checkpoints + eval-bot variants as opponents; fill lobbies from the pool; feed all placements into TrueSkill. This is the AlphaStar (DeepMind, StarCraft II) / OpenAI Five (Dota 2) lineage — both kept pools of past agents as opponents. It resists single-opponent overfitting, yields a relative-progress curve, and *naturally absorbs a pool that grows over time* — directly serving the second open question.
  - **Right-size it.** At the BC stage we want the *principle* (a frozen reference pool + ratings), not the heavyweight league machinery (exploiter agents, prioritized fictitious self-play). That apparatus only becomes load-bearing at RL self-play — at which point the eval pool and the self-play opponent pool converge. Design the pool abstraction now so it extends into that phase rather than being rebuilt.
- **Sample-efficiency.** Filling lobbies with a *mix* (candidate + several references + eval-bots, everyone scored) yields many placements per game vs. one-candidate gauntlets — and with batched GPU eval, more agents per lobby is nearly free. Tradeoff: mixed-lobby placements are *coupled* (a placement depends on who else was in the lobby), but that coupling is exactly what TrueSkill is built to disentangle across many games. Isolated gauntlets are simpler to interpret; mixed-lobby + TrueSkill is the cheaper path to a stable pool rating.

## Decision 4 — What's *frozen and versioned* (this is what "standardized" means)

A rating or win rate is only comparable within a fixed context. To make eval a stable yardstick:

- **Frozen map set** — diverse, representative, bucketed by player count, curated and prepped into a convenient format. This is the backbone, not a convenience: it both fixes the comparison and controls FFA spawn fairness (see gotchas).
- **Frozen opponent pool** — `eval-pool-v1` = {these checkpoints, this eval-bot config}.
- **Fixed sampling** — temp (0.5, per `5.28-1`) and a per-game seed policy (seeded `torch.Generator` per game/perspective, per the `5.30-1` RNG note) for reproducibility.
- **Version the protocol.** The moment the map set or pool changes, prior ratings/win-rates stop being comparable — bump `eval-protocol-vN` and re-baseline. Silently editing the eval set and comparing across the edit is the classic way "standardized eval" quietly stops being standardized.

## Training-loop integration

Skill eval is *expensive* (full rollouts) relative to the cheap val-loss pass — so don't make one protocol do both jobs:

- **Cheap in-loop gate:** small n, a couple of *frozen* reference opponents, a small fixed map subset, every N epochs → log one scalar (avg placement, or win-rate-vs-reference). The opponent must be **frozen**, never the current/moving policy, or the curve isn't comparable across the run (or across runs).
- **Full offline eval:** large n, full pool, TrueSkill — run at milestones (run end, pre-big-run commit).

**Synthesis with cloud eval.** The natural way to run in-loop skill eval without stealing the training GPU is a *separate* Modal eval container that watches the `training-runs` volume and evaluates checkpoints as they land (checkpoints + maps already live on volumes — see the cloud-eval section). This is the concrete payoff of the cloud-eval capability for the training loop.

## Domain gotchas for generals FFA

- **Seat/spawn bias can't be fully swapped in FFA.** In 1v1, swap-slots cancels seat bias exactly. With N>2 there are N! seat assignments — instead rely on a large/diverse map set to average out spawn-adjacency, and optionally replay each map with rotated seat assignments. Spawn positions are a property of *(map, seat assignment)* — general locations are fixed per map (`StaticMap.initial_generals` is indexed by slot) — which is another reason the map set is load-bearing for fairness.
- **Player count is map-constrained.** An N-player map has exactly N general positions. 4p eval needs 4p maps; 8p needs 8p maps. The curated set must bucket by player count (the npz reconstruction already filters on exact general count).
- **High variance / king-making.** In FFA a player can be eliminated by someone other than the eventual winner; outcomes are noisier than 1v1 → budget more games for a stable signal.
- **Weak-bot regime.** Current BC checkpoints are weak enough that the eval-bot wins a meaningful share (`5.28-1`). Lean on dense metrics (survival, land) and placement before win rate has resolution; advance the reference pool as bots strengthen so the metric doesn't ceiling out.

## Provisional recommended shape (to confirm, not committed)

- **Two protocols, both off a frozen, versioned map set + frozen pool:**
  1. **1v1 gate** — reuse the `5.28-1` protocol as-is. Fast A/B and the in-loop scalar.
  2. **FFA** — start at **4p** (option to add 8p), placement-scored, lobby mixed from the frozen pool, TrueSkill for cross-time / cross-pool rating.
- **Metric:** placement primary (+ survival/land in the weak regime); TrueSkill as the pool rating; win rate as a secondary headline.
- **Pool:** the few early checkpoints + the eval-bot as `eval-pool-v1`, versioned and grown deliberately.
- **Design the pool + map-set abstractions to extend into RL self-play**, where the eval pool becomes the opponent pool.

## Open questions / next decisions (in order)

1. **Settle Decision 1** — 1v1-only, add 4p, add 8p, or both. Everything else cascades from this.
2. **FFA metric details** — exact placement scoring (mean? full distribution?), and whether to stand up TrueSkill now or start with raw placement and add rating later.
3. **Define `eval-pool-v1` and `eval-map-set-v1`** — which checkpoints, which eval-bot config, how many maps per player-count bucket, what on-disk format.
4. **In-loop gate spec** — n, opponents, map subset, cadence — kept deliberately small.
5. **Then** wire the chosen FFA protocol into the cloud-eval entrypoint (below).

## Cloud eval bring-up (infrastructure half)

Captured here so eval planning lives in one place; the proven groundwork is in [`5.31-1`](../2026-05/5.31-1-eval-perf-cloud-host-bound.md) and [`5.21-9`](../2026-05/5.21-9-cloud-poc-and-modal.md).

**What's proven.** The perf probe already runs the *real* batched runner on a cloud GPU with both volumes mounted (checkpoints ← `training-runs`, maps ← `parsed-replays`) and no uploads; sim_core (Rust) builds in the image. The hard parts are done.

**Goal (this round).** Capability parity — a reusable cloud eval entrypoint mirroring `run_bc_modal.py`, returning summary + `results.jsonl`. Not fan-out, not full-artifact pull-back yet.

**Approach — reuse `run_adhoc.run()`, don't duplicate it** (the parity-faithful move; mirrors how training reuses `bc_run`). Two seams to loosen:

- **Map source.** Today `run_adhoc` → `seed_map` reads the local SQLite DB. Introduce a `MapSource` with `list_ids(num_players)` + `load(replay_id) → StaticMap`; two impls — SQLite (local) and npz-volume (cloud). The cloud impl works because intermediate npz are sharded by replay_id (`<rid[:2]>/<rid>.npz`), so full `replay_id` lookup works with no DB; reconstruct `StaticMap` from the npz (synthesize `usernames`, which only sets player count). Bonus: this severs the `replay_collector.config` import from the cloud graph.
- **Output.** Add a summary-only mode that writes `results.jsonl` + returns the summary, skipping per-game npz — useful locally too. No output volume needed for the MVP.

**Entrypoint.** Mirror `run_bc_modal.py`, but use `.remote()` (synchronous, returns the summary) rather than training's `.spawn()` — eval is short and we want the number back. Image is the probe's; volumes are the same two; GPU defaulted with a `--gpu` override.

**Deferred (extends cleanly later).** Fan-out across containers (a loop of `.remote()` calls in the entrypoint) and full-artifact staging to a volume (the output seam grows a "stage to volume" mode).

**Perf reality check.** A single cloud container is host-bound and *not* faster than the M1 (`5.31-1`). Cloud eval's value is colocation with checkpoints and (later) horizontal fan-out, not per-run speed. Obs-build perf work (the Phase B direction) is what would make a single cloud eval fast — and it compounds if eval runs in the training loop.
