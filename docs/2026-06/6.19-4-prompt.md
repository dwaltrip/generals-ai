## What we're aiming for

Short-term — the gate: get the head *sound*. (a) val top-1 beats the best model-free heuristic (today lowest-army 47.2%) and wins its disagreements with the rule, and (b) a healthy curve — val loss at least plateaus, ideally keeps falling (the current ep3-peak-then-degrade fails this).

Long-term — the actual goal: the elim-head should *improve the value head* (the original motivating impulse), via representation enrichment and trunk regularization. That's gated behind the head being sound — a memorizing aux head is an anti-regularizer (it pushes idiosyncratic gradients into the shared trunk), so a healthy curve is plausibly the precondition for helping value, not just a milestone before it. Gap-1/Gap-2 are two measurement frames on the same representation issues, so the levers below interact.

## Possible next moves

The diagnostics are listed first as they are lower-effort and may provide valuable insight that informs further work, including the other items on this list.

### Cheap diagnostics first (model-free or frozen-rep, no training run)

- **Value-off vs value-on army-R² probe** (frozen). 6.15-2 only checked elim-on/off for army fidelity, never value-on/off. If value-off has materially higher army R², the value head is corrupting the shared trunk's army representation — which would explain *both* the sub-floor ceiling and part of the overfit. Cheaper than doing an actual training run.
- **Pull the existing army-delta numbers** from the gate sweep (`2026-06-19-elim-head-coherent-ab`). `who_dies_next_baselines.py` *already* computes army-delta (K=1/5/10/25) + a combined oracle and prints them per run — so we may already know whether army-*trend* beats lowest-army-*level*. Free; do before planning any rate-channel work.
- **Add lowest-land / land-delta baselines** to `who_dies_next_baselines.py` (a few lines; `land_totals_per_tick` already exists next to `army_totals_per_tick`). Is land a stickier floor than army?

### Reduce overfit

#### Strategy 1: General reductions (low/no downside, kept permanently on their own merit)

- **Dropout / weight decay.** Standard regularizers; cheap to A/B (no in-codebase evidence yet that they bite).
- **Imminence-weighted soft target** (parked, 6.18-9 §3.C). The sharp one: soft targets are exactly what fixed the value head's overfit, and the elim-head is the one head still on **hard CE** (6.13-14) — the one now overfitting. Known remedy, matching symptom, and it removes no signal. Reframed from 6.18-9's "tick-latency fix" to double duty.
- **Survey the literature for more.** Scan for other low-downside regularizers that fit this setup (aux head on a shared conv trunk, small-data regime) — e.g. label smoothing, stochastic depth, mixup-style input perturbation, early-stop/SWA, ensembling — and pull in anything with a good cost/fit. A standing research thread, not a one-off.

#### Strategy 2: Tamp high-fingerprint memory channels

- Remove parts of the "easy path" so the model has nowhere to go but the harder road where real generalization lives.
    - *Possibly temporary:* once the true signal extracts robustly, consider bringing the channel back — not necessarily as-was, maybe in a **less-fingerprinty form** (summarized / lower-resolution / lower-capacity, keeping the signal without the memorization affordance — something to explore), judged on its own merit and decoupled from elim-head overfit.

- **n=5 dense-history** — the clearest example: n=20→n=5 had a strong effect on value-head overfit before. Note it does *both* — tamps the handle *and* removes border-local signal (the Gap-2 half) — so a null under n=5 is ambiguous (lever failed vs. signal starved); read it alongside a purer Strategy 1 control.
- *Caveat (untested premise):* the tamp-then-restore tactic is a just-formed hypothesis. The general principle is grounded (shortcut-learning / spurious-feature literature; input/feature dropout), but the specific remove-then-reintroduce protocol is bespoke, not a confirmed standard practice — worth a literature check before leaning on it.

This "easy-path" degeneracy seems like a potential risk with *any* dense or semi-dense memory channel. Anything that hands the model a strong fingerprint for what game that frame belongs to could in theory cause the issue we saw with the value-head.

#### Bonus question: Does value-head overfitting affect the elim-head?

Are there *structural / head interactions*? Does one head's overfit worsen the other's via the shared trunk? The value-head still suffers from partial overfitting — this is something that has plagued us for the entire project. And the value-head and elim-head are, by design, closely related: they both deal with player placement.

This hypothesis provides additional motivation for the **frozen value-off / value-on probe** mentioned earlier. If the probe comes back positive, an elim-on / value-off training run would be worth trying. The exact analysis needed for this probe variant is TBD.

### Give the head better signal

*(§3.C — the extraction/completeness fork, chosen by what the diagnostics reveal)*

- **Extraction** (signal present, not delivered cleanly — the leading read from 6.15-2's ~0.82 army R²): an **auxiliary army-reconstruction loss** to push the trunk past the residual (cheap to pre-test in the toy, ports to prod); or an elim-head-specific pooling/attention over players. Could move both Tier-0 symptoms at once.
- **Completeness** (add absent signal): land / army-rate channels to the obs — but this is a Gap-2 move, and the gate says we can't yet match the Gap-1 floor with the army the obs *already* carries, so it may be premature.

*Note on scale/epochs:* 6.19-2 ruled out scale for the *ceiling* — but only ambiguously for the *overfit turn* (the 11k late-overfit was partly a step-count artifact). If "val keeps falling" is now a named goal, more data at matched step budget could delay the turn — but would likely give the falling curve *without* crossing 47.2%. Those can dissociate.
