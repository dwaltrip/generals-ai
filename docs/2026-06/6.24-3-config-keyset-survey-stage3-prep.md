# Config key-set survey — Stage-3 prep for the checkpoint-config refactor

*Date: 2026-06-24. Companion to the checkpoint/TrainConfig-into-`.pt` design discussion ([6.24-1](6.24-1-session-notes.md) open item #1, [6.24-2](6.24-2-daniels-disorganized-ckpt-config-notes.md)). This note is the empirical backing for the design's "the v0→v1 legacy normalizer is bounded and meetable" claim. The greenfield mechanism is specified separately; here we just measure what the actual historical configs look like.*

## What and how

Surveyed every resolved `args.json` under `data/training/{runs,runs-cloud,sweeps}` (116 files) and grouped runs by the frozenset of dotted key paths, then diffed against the code's current v1 keyset (`asdict(TrainConfig)`). Tool: [`scripts/one_offs/survey_config_keysets.py`](../../scripts/one_offs/survey_config_keysets.py). Scope: `args.json` only — not `args_resume_NN.json` (supersets with a `_resume_meta` block, no new config shapes) and not the `.pt` structural eras (the known bare / combined-no-`arch` / combined-with-`arch` split).

## Findings

- 116 runs, **18 unique on-disk key-sets**, spanning 2026-05-21 → 06-21. History is overwhelmingly **additive**: key count climbs 11 → 45, almost entirely by single-field additions.
- Code v1 keyset = 46 keys; union of all on-disk keys = 49.
- **No genuinely homeless concepts, no unrecoverable fields.** Every key that ever appeared on disk but is absent from v1 maps cleanly to a v1 home (rename / nest / drop). The 10-key "homeless" list and its resolutions:

| On-disk key(s) | v1 home | Transform |
|---|---|---|
| `lambda_value`, `value_target_tau`, `lambda_elim`, `elim_target_tau`, `next_elim_target_tau`, `elim_bin_weights` | `loss.*` | flat→nested loss |
| `value_head_variant` | `arch.value_head_variant` | flat→nested arch |
| `out_dir` | `run_dir` | rename |
| `arch.elim_head_enabled` | `arch.elim_head_variant` | rename + value map (`enabled`→`time_bin`/`None`) |
| `arch.in_ch` | — | drop (derived property; leaked into serialization for a ~2-day window, 06-03..06-05) |

## The v0→v1 normalizer (the bounded Stage-3 core)

Because we normalize *any* pre-v1 shape straight to v1 — rather than replaying the ~17 historical transitions — the entire legacy past collapses into one normalizer: five structural transforms plus a frozen-default fill.

1. `out_dir` → `run_dir`
2. nest flat arch params → `arch.*` / `arch.obs.*` (the 05-28→06-03 restructure; includes `value_head_variant`)
3. drop `arch.in_ch`
4. `arch.elim_head_enabled` → `arch.elim_head_variant`
5. nest flat loss knobs → `loss.*`
6. fill any still-missing v1 key from a frozen legacy-default table (absorbs the ~13 purely-additive cases)

## The flat→nested loss move touches every run

No on-disk run has nested loss. The flat→nested loss move (#5) and the new `loss.mu_pass` field both post-date the newest run here (06-21), so transform #5 touches **all 116** runs, and `mu_pass` is a genuinely new field (its frozen default is the value that reproduces pre-`mu_pass` behavior). When re-running the survey, diff against the code's keyset (`asdict(TrainConfig)`), not the newest on-disk run — the newest run is itself flat-loss, so a newest-on-disk reference misses this move entirely.
