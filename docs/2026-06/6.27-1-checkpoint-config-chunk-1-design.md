# Checkpoint & config versioning — chunk-1 design

*Date: 2026-06-27. The implementation design for chunk-1: the self-describing **v1 checkpoint format** and the **migrate-once read seam** — the shape axis — built behavior-preserving. Supersedes the loose [6.26-6](6.26-6-checkpoint-config-chunk-1-sketch.md) sketch as the authoritative chunk-1 design. For the conceptual frame (shape vs. behavior, the tiers, the open questions) see the synthesis [6.26-5](6.26-5-checkpoint-config-synthesis.md); for the migrate-once mechanism and the schema-manifest tooling see the design doc [6.24-4](6.24-4-checkpoint-config-versioning-design.md); for the gating decisions see the critical-questions doc [6.26-7](6.26-7-checkpoint-config-critical-questions.md); for the implementation blast radius see the boundary surveys [6.26-1](6.26-1-survey-pt-checkpoint-io.md) / [6.26-2](6.26-2-survey-sidecar-config-io.md) / [6.26-3](6.26-3-survey-model-usage-trace.md). Post-chunk-1 design decisions reached in the surrounding discussion are collected in the appendix below.*

> **As-built note:** Structure/home decisions, live status, and conventions are tracked in the refactor working doc [6.27-3](6.27-3-checkpoint-config-working-doc.md), which supersedes §4 where they differ. This doc remains the as-designed spec for the v1 format (§2), read flow (§3), mandatory fixes (§5), and build phases (§7).

## 1. Scope & framing

Chunk-1 delivers the **shape axis**: a checkpoint's stored config gains the current field structure (behind a single migrate-once boundary), so live code consumes it without branching on a version. The **behavior axis** — does current code *reproduce* what an old checkpoint did — is mapped in the synthesis and deferred.

Concretely, chunk-1 stands up:

- the **v1 `.pt` layout** (the full resolved `TrainConfig` stored in the checkpoint, plus the version/provenance stamps);
- a new **read pipeline** — `load_checkpoint → resolve_checkpoint_config` (or the legacy delegate) `→ build_model → ConfiguredModel`;
- the **reserved `code_sha` stamp** — a save-time provenance fact that can't be retrofitted, so the slot must land in the first format even though its enforcement is deferred (the behavior-drift stamp `arch_version` is deferred entirely — added with the behavior axis; see appendix §D);
- the **writer-flip** (capstone) so new runs emit v1.

It is cut to be robust to either resolution of the open behavior-axis questions (co-residency strategy, fidelity-scope; see [6.26-7](6.26-7-checkpoint-config-critical-questions.md)) — it builds no tier machinery and bets on neither answer, so neither forces a rework. Three goals: conservative / low-risk, real groundwork on the checkpoint+config side (a self-describing format + consolidated loaders — the recipe-in-`.pt` payoff is unlocked later, not in chunk-1), and a flexible foundation for the deferred work.

**Deliberately out of chunk-1** (appendix): the `BCModel` re-scope that moves `cfg` onto the wrapper (chunk-2), the v0→v1 normalizer, resume rewiring, the `args.json → config.json` sidecar rename, and the schema-manifest tooling (per-version key-set files + the forgot-to-bump pytest check, which earns its keep at the first real v1→v2 change — see [6.24-4](6.24-4-checkpoint-config-versioning-design.md)).

## 2. The v1 format

Top-level layout of the saved dict:

| key | contents | role |
|---|---|---|
| `model` | `state_dict` | runtime state |
| `optim` | `state_dict` | runtime state |
| `scaler` | `state_dict` | runtime state |
| `epoch` | `int` | progress |
| `in_ch` | `int` | input-channel checksum (relocated out of `arch`) |
| `config` | `asdict(TrainConfig)` + `config_version` | the self-describing config block |
| `code_sha` | `str` | provenance, populated at the writer-flip |

- **`config`** is a pure `asdict(TrainConfig)` with `config_version` inside it. `arch` nests at `config.arch` (with `obs` under it), `loss` at `config.loss`; recipe and operational fields ride alongside. The version lives *inside* `config` so the block is self-describing on its own.
- **`in_ch`** moves out of the arch dict to its own top-level key. It is a derived checksum (channels implied by `obs`), not a config field, so pulling it out keeps `config` a pure `asdict`.
- **`config_version`** is a single integer for the whole config (any sub-config shape change increments it). Current shape = **v1**; an unstamped artifact = **v0** (legacy).

**The save-time stamps, each on its own axis** (detail in [6.26-5](6.26-5-checkpoint-config-synthesis.md)): `config_version` (config shape → migration), `code_sha` (provenance), `in_ch` (narrow input-channel checksum). A fourth, `arch_version` (architecture → behavior-drift detection), belongs to the behavior axis and is deferred — added later, likely as a `ModelConfig` field (appendix §D), not reserved as a null slot now. They are easy to conflate and are intentionally kept distinct.

**The one hard serialization constraint.** Every checkpoint load is `torch.load(weights_only=True)`, which rejects non-allowlisted classes. After `asdict(TrainConfig)`, the only offenders are the three `Path` fields (`manifest`, `intermediate`, `run_dir`) — `pathlib.Path` is not in the default allowlist. So the serializer **stringifies** them on write and the reader **re-wraps** them on read. The re-wrap introspects the `Path`-typed fields rather than hardcoding the three names, so it doesn't rot when a `Path` field is added.

**The sidecar.** Chunk-1 makes the **`.pt`** self-describing. The on-disk `args.json` sidecar is untouched here; its rename to `config.json` is a separate deferred chunk (traps mapped in survey [6.26-2](6.26-2-survey-sidecar-config-io.md)).

The migrate-once mechanism (dispatch, the `MIGRATIONS` registry, fill-if-absent) is owned by [6.24-4](6.24-4-checkpoint-config-versioning-design.md); this section owns the v1 layout.

## 3. The read flow

```
load_checkpoint(path, device, value_head_variant="direct") -> ConfiguredModel
│
├─ raw = torch.load(path, map_location=device, weights_only=True)
│
├─ DISCRIMINATE on top-level key:
│   ├─ "config" in raw   → STAMPED (v1+)
│   └─ else              → LEGACY (v0: top-level "arch", or a bare state_dict)
│
├─ STAMPED path:
│   ├─ tcfg = resolve_checkpoint_config(raw["config"])   # migrate(no-op@v1) → TrainConfig
│   ├─ arch = tcfg.arch
│   └─ (full config available)
│
├─ LEGACY path:
│   ├─ arch = legacy_arch_for_load(raw, value_head_variant)   # today's _arch_for_load
│   └─ tcfg = None                                            # no full config in a v0 .pt
│
├─ model = build_model(arch)                       # ModelConfig -> BCModel
├─ validate_in_ch(raw, model.cfg)                  # stored checksum vs derived obs channels
├─ model.load_state_dict(state_dict_of(raw))       # strict=True
├─ model.to(device).eval()
│
└─ return ConfiguredModel(model=model, config=tcfg)   # .cfg property -> model.cfg
```

The single discriminator — `"config" in raw` — is the only routing chunk-1 needs. The earlier `LoadPlan` tagged union is dropped: it was reaching ahead to be the behavior-tier firewall (Native / Compat / Unsupported), which is deferred. A two-way shape-version branch does not warrant a named union.

`in_ch` validation runs **before** `load_state_dict`, preserving today's behavior of raising a clear error (stored count vs. the count the resolved `obs` implies) rather than a cryptic state-dict shape mismatch. The STAMPED path reads `in_ch` top-level; the LEGACY path reads it from inside `arch` (the legacy delegate, as today).

## 4. Components

| Component | Signature | Home | Responsibility |
|---|---|---|---|
| `load_checkpoint` | `path, device, value_head_variant -> ConfiguredModel` | torch (checkpoint I/O module) | orchestrate: read bytes, discriminate, resolve-or-legacy, build, validate `in_ch`, load weights, wrap |
| `resolve_checkpoint_config` | `config_dict -> TrainConfig` | **torch-free** (`bc/config`) | migrate (no-op at v1) → construct `TrainConfig` (validators run). v1-only. |
| `legacy_arch_for_load` | `raw, value_head_variant -> ModelConfig` | torch (checkpoint I/O) | today's `_arch_for_load`, behavior-unchanged — the v0 delegate |
| `build_model` | `arch: ModelConfig -> BCModel` | torch (model) | construction seam; `BCModel(arch)` today; future Native/Compat build paths land here |
| `ConfiguredModel` | dataclass: `model: BCModel`, `config: TrainConfig \| None` | torch | the wrapper; `cfg` property delegates to `model.cfg` |

Mid-level notes:

- **`resolve_checkpoint_config` takes the `config` sub-dict, not the whole checkpoint.** That is what keeps `bc/config` torch-free — it never sees `model`/`optim` tensors. `load_checkpoint` extracts `raw["config"]` and hands it over. Its body mirrors today's `TrainConfig.from_file` minus `json.loads`: migrate (empty chain at v1) → pop `arch` → `build_model_cfg(**arch)` (coerces the nested `obs` dict and `elim_bin_edges` list→tuple) → extract `loss` → `LossConfig(**…)` (coerces `elim_bin_weights` list→tuple) → re-wrap the three `Path` fields → splat the rest → `__post_init__` validators run on guaranteed-current data. (Reconstruction mechanics: [6.24-4](6.24-4-checkpoint-config-versioning-design.md).)
- **The migrate step is a skeleton at v1.** `CONFIG_VERSION = 1`, `MIGRATIONS = {}` (empty). The dispatch still lands: read `config_version`, a `v > CURRENT` guard (reject a checkpoint written by newer code), and the (currently no-op) `range(v, CURRENT)` loop. The v0→v1 normalizer is deferred; v0 is served by `legacy_arch_for_load`, not by a migration.
- **`build_model` returns a bare `BCModel`.** It only has the arch, and the arch is intrinsic to `BCModel` (`model.cfg`), so a wrapper it produced would carry nothing extra. The wrapper is assembled by whoever holds the full config — `load_checkpoint` here, and `TrainingState.fresh` on the training side (both already extract `arch` to build). This keeps `build_model` the one pure construction seam shared by both.

`bc/config` is created as a torch-free package; `resolve_checkpoint_config`, the `CONFIG_VERSION` constant, and the empty migrate chain start there. Physically relocating the existing config dataclasses (`train_config`, `model_config`, `obs_config`, `loss`) into it is a separate change, not required for chunk-1 — `bc/config` imports them wherever they live.

## 5. Mandatory correctness fixes

The reshape `arch → config.arch` and `in_ch → top-level` breaks code that structurally keys on the old layout (sites enumerated in survey [6.26-1](6.26-1-survey-pt-checkpoint-io.md)). These fixes land *with* the reshape — bundled into the writer-flip or done as a final reshape step, per the two sequencing paths in §7. How chunk-1 handles each:

1. **`is_arch_bearing` — the one mandatory correctness fix.** Today it answers "does this checkpoint record its architecture?" via `is_combined_checkpoint(obj) and "arch" in obj`. A v1 checkpoint stores its arch at `config.arch`, not top-level `"arch"`, so the predicate returns **False** for every v1 checkpoint and misclassifies it as legacy. That corrupts the inference `model_key`: `value_head_variant` enters the key *only for non-arch-bearing* checkpoints (it is ignored when the arch is recorded), so a mis-classified v1 checkpoint loaded with differing `value_head_variant` args lands under different keys — defeating the handle-cache de-dup and the shared-forward grouping in `game-runner/.../batched.py`. The fix is **additive**: recognize the stamped case while leaving the v0 answer byte-for-byte unchanged — roughly `is_combined_checkpoint(obj) and ("config" in obj or "arch" in obj)`. A v1 checkpoint is always arch-bearing (it always carries `config.arch`). **Invariant to assert:** the fix must not change any existing v0 checkpoint's answer (and thus its `model_key`); since it only adds the `"config" in obj` arm, v0 answers are preserved.

   *Sibling gate (non-mandatory).* `TrainingState.from_checkpoint` has the same top-level-`"arch"` pattern (`if "arch" in obj`, gating a redundant arch-match assert). For a v1 resume this gate goes always-False, so the assert silently stops running — but it is redundant in practice (the real gate is `run_dir.check_drift`, which compares the resume config against the *sidecar's* recorded arch — equivalent to the dormant assert as long as the sidecar and `.pt` agree, which they do, being written together), so no correctness is lost. Resume is unchanged in chunk-1, so the clean call is to **leave this for the resume rewiring** and note it; fixing it in lockstep with `is_arch_bearing` is a cheap option if preferred.

2. **`_arch_for_load` — kept, not edited.** It becomes the `legacy_arch_for_load` v0 delegate, behavior-unchanged. The reshape does **not** edit it in place: v0 checkpoints on disk still carry top-level `arch` and `in_ch`-inside-`arch`, so the delegate reads them exactly as today. The new v1 layout is handled by the parallel `resolve_checkpoint_config` + top-level `in_ch` validation, not by touching the legacy path.

3. **`in_ch` validation — relocated for v1.** The stored-vs-derived check moves to `load_checkpoint` (torch side, a weight-integrity concern), reading the top-level `in_ch` against the resolved `model.cfg`-derived channels, before `load_state_dict`. The v0 path keeps the in-`arch` check inside the legacy delegate.

4. **`TrainingState.save` — the writer.** Redefined at the capstone (step 3) to emit the v1 layout. Covered under build phases.

`is_combined_checkpoint` keys only on top-level `"model"`, which stays put — **safe, no change**. The filename-scheme sites (kind 4 in the survey) never open the file and are untouched.

## 6. Settled chunk-1 decisions

- **`ConfiguredModel.config: TrainConfig | None`.** The STAMPED path populates it; the LEGACY path leaves it `None` (a v0 `.pt` doesn't carry the full recipe). Read consumers key on `cfg` (the arch, always present via the property), and must never assume `config` is populated. This type is forward-safe under either resolution of the "is `config` ever `None` long-term" question (appendix).
- **`cfg` delegates to `model.cfg`.** In chunk-1 `BCModel` keeps its `cfg`, and `ConfiguredModel.cfg` is a property returning `self.model.cfg` — a single source, no duplication. The storage flip (cfg moves *onto* the wrapper, `BCModel` becomes pure torch) is chunk-2; the property is the indirection that makes that flip contained.
- **`LoadPlan` dropped.** Routing is the single `"config" in raw` branch inside `load_checkpoint`.
- **`value_head_variant` stays on `load_checkpoint`'s signature.** It is a legacy-only fallback (used by the v0 delegate for non-arch-bearing checkpoints), and real current callers pass it (`stratified_val_loss_analysis`, `probe_row_independence` with `"pyramid"`). It can't leave the signature while those legacy checkpoints are loaded with it; its removal is unlocked by route-1 (appendix).
- **`build_model` returns a bare `BCModel`** (rationale above); the wrapper is assembled by the caller that holds the full config.
- **Single loader.** `load_checkpoint` is the only loader; the current `load_bc_model` is removed. Call sites that want a plain `BCModel` take `load_checkpoint(...).model`; `BCModelHandle.load` holds the `ConfiguredModel` as the first real consumer, and `load_frozen_model` takes `.model` and keeps returning a bare `BCModel`. Migrating consumers to *read off* the wrapper (`model.cfg` → `cm.cfg`) stays chunk-2.

## 7. Build phases (strangler-fig)

Plant the new module, route every load site through `load_checkpoint` (delegating to today's reconstruction at first), then grow the v1 logic in. Migrating/auditing every caller is deliberate — it forces an honest read of scope, catches breakage, and audits whether callers are well-abstracted. The pass is **behavior-preserving**: record abstraction smells (the `from_checkpoint` double-read, the `model_key` re-read, the legacy-only `value_head_variant`), don't fix them here.

**Module homes.** A fresh checkpoint I/O module (torch-heavy: reads bytes, builds models) plus the torch-free `bc/config` package. Keep them separate so torch doesn't leak into the config layer. (The sketch's working name `checkpoints_v2.py` carries a transient `_v2`; pick the end-state name — see §8.)

- **Step 1 — strangler seam.** New module + `load_checkpoint` returning `ConfiguredModel`, delegating to the existing reconstruction (every load hits the LEGACY branch — no v1 checkpoints exist yet, so `config` is `None` throughout). Rewrite every load call site onto `load_checkpoint`, auditing each as you go — bare-model sites take `.model` (`from_checkpoint`, `stratified_val_loss_analysis`, `load_frozen_model`); `BCModelHandle.load` holds the `ConfiguredModel`. Remove `load_bc_model`. Confirm-and-archive `value_head_probe.py` (and its `load_frozen_trunk`) — verified to have no live importers. Zero behavior change. Validated by the existing checkpoint/state tests plus a manual smoke on the untested callers (`scripts/`, `self-play/cli.py`, `eval_poc.py`).
- **Step 2 — v1 read path + round-trip test.** Grow the STAMPED branch into `load_checkpoint`: the v1 serializer (builds the v1 dict, Paths stringified), `resolve_checkpoint_config`, top-level `in_ch` validation, and the `is_arch_bearing` fix. Prove it with a construct → serialize → read → build round-trip test, which exercises the `Path` / `weights_only` constraint and the full v1 layout end to end.
- **Step 3 (capstone) — writer-flip.** `TrainingState.save` emits v1 (calling the step-2 serializer). Pulls in `TrainingState`-carries-config, `code_sha` population, and disambiguating the `git_sha` log label in `train.py`. First live-path change; gated behind step 2. (Why save is last: once runs emit v1, something must read them and `is_arch_bearing` must already be fixed.)

**Sequencing the reshape — two paths (decide next session).** Steps 2–3 above describe **path 1**: the writer-flip emits the single-home reshaped layout directly, bundling the §5 fixes (`is_arch_bearing`, the `in_ch` relocation, the `from_checkpoint` gate). **Path 2** splits it: the writer-flip first emits an *additive* layout — the `config` block alongside the retained top-level `arch`/`in_ch` (nested as today) — which is strictly behavior-preserving (every predicate and fixture keeps working via the top-level `arch`; no §5 fixes yet), and then a final chunk-1 step does the reshape (drop the vestigial top-level `arch`, relocate `in_ch`, apply the §5 fixes, update the cross-package fixtures). Both paths keep the reshape inside chunk-1 and land at the same format; path 2 trades an extra step and a transient additive format for isolating the reshape into its own independently-validatable step. The reshape's surface is low-complexity and largely self-validating (the round-trip test and the existing suite fail loudly on a missed site), so path 1 is the simpler default and path 2 is the extra-caution option.

## 8. Chunk-1-internal opens

Unsettled details, all chunk-1-scoped — to settle during implementation:

- **`code_sha` capture point.** Almost certainly capture-at-launch and thread through; reuse the `_git_sha` helper from `splits.py`. Note the two distinct SHAs — manifest = data-provenance vs. checkpoint = training-code-provenance — and the cloud-`.git` caveat (capture fresh at launch). Disambiguate the ambiguous `git_sha` log label in `train.py`.
- **Naming.** The checkpoint I/O module's permanent name (avoid the transient `_v2`); the `bc/config` package name; `ConfiguredModel` (good-enough, may revisit); the working names `resolve_checkpoint_config` / `build_model` / `legacy_arch_for_load`.
- **`value_head_variant` containment.** Kept on the signature for chunk-1; quarantine off the modern path once route-1 makes the legacy checkpoints unsupported.

## Appendix — post-chunk-1 design

*Captured-not-scoped: design decisions reached in the discussion around chunk-1, preserved so they don't have to be reconstructed later. Each is independently deferrable and out of chunk-1. They sit on the conceptual frame in [6.26-5](6.26-5-checkpoint-config-synthesis.md) and the gating decisions in [6.26-7](6.26-7-checkpoint-config-critical-questions.md).*

**Sequencing (a lean, not a commitment).** The version-bump guardrail (§C) is the most time-sensitive — it guards correctness by the first config change, whereas the `BCModel` re-scope (§A) buys cleanliness — so the guardrail likely comes first. Resume rewiring, the sidecar rename, and route-1 are independent follow-ons. Final ordering is open.

### A. Chunk-2 — the `BCModel` re-scope

Goal: `BCModel` becomes pure torch (the `nn.Module` + `forward`); `cfg` and the variant-meta move onto the wrapper, which becomes the home for the variant-interpretation logic currently scattered across metrics, eval, logging, loss, and analytics.

- **The line is mostly real already.** `forward` is cfg-free today — it operates on submodules (`self.trunk`, `self.elim_head`, `if self.elim_head is not None`), never on `self.cfg`. Variants are resolved into submodules at construction, so the torch computation doesn't branch on config. The re-scope is therefore mostly *relocation*, not a forward rewrite.
- **The one real refactor.** `forward` currently bakes `elim_output_key` and `active_aux_specs` into `ModelOut`, so those two pieces of meta can't simply relocate. The seam: let the head submodule own its `output_key` (intrinsic to the head — `forward` reads it off the head), and move the richer spec (bin edges, pooling, variant name — the analytics-facing meta) onto the wrapper.
- **Blast radius — why it's its own chunk.** ~10 sites read `model.cfg` off a bare instance (inference, self-play, `eval_poc`, `capture_val_frames`, `run_val`, `train.py`, `probes/cli`, `stratified_val_loss_analysis`; survey [6.26-3](6.26-3-survey-model-usage-trace.md)). Each must hold the wrapper instead. That is not behavior-preserving (callers change), so it cannot ride in chunk-1's strangler pass.
- **The strangler mechanism.** Chunk-1 makes `ConfiguredModel.cfg` a property delegating to `model.cfg` (single source). Chunk-2 inverts the storage — `cfg` lives on the wrapper, dropped from `BCModel` — and because readers already go through the wrapper's accessor, the storage flip doesn't touch them a second time.
- **Then `BCModelHandle`.** Once the wrapper carries model + cfg + variant-meta, revisit Handle — plausibly wrapper + device + decode, or dissolved into the wrapper.

### B. v0→v1 resolution, and the "`config` never `None`" fork

The v0→v1 normalizer reconstructs a current-shape config dict from a legacy checkpoint — the sidecar key-reshapes, a frozen-default fill, and the relocated `_arch_for_load` assembly — behind the v0 entry's output contract.

- **The subtlety that shapes it.** A v0 `.pt` carries only `arch`; the recipe (loss, lr, seed, paths) lived in the run dir's `args.json`. So a *full* `TrainConfig` for a v0 checkpoint can't come from the `.pt` alone — hence the v0 entry signature `(pt_obj, run_dir | None) → v1_dict`, with `run_dir` optional (a bare `.pt` may have no reachable sidecar).
- **The fork (decide at chunk-2/3).** Once the normalizer exists: **uniform** — every checkpoint resolves to a full `TrainConfig`, so `ConfiguredModel.config` is never `None`, but the read/gameplay path does recipe-reconstruction it never reads and gets coupled to the sidecar for v0; vs **graded** — v1 resolves full, v0 stays arch-only (`config` is `None`/partial) unless something explicitly needs the recipe (resume).
- **Why chunk-1 doesn't have to choose.** `config: TrainConfig | None` is forward-safe under both — under uniform, `None` simply never occurs in practice; under graded, `None` keeps its meaning.

### C. The version-bump guardrail (schema-manifest tooling)

Creating a new config version after chunk-1 is *mechanically* possible — the `CONFIG_VERSION` constant, the `MIGRATIONS` registry, the dispatch loop, and the fill-if-absent convention all land in chunk-1. What's deferred is the **guardrail** that catches a config-shape change made without a matching version bump + migration.

- **The unguarded failure mode is the silent-drift bug itself.** Add a field to a config dataclass and forget to bump: old checkpoints (lacking the field) either load with its *default* silently — the drift this work is meant to prevent — or crash with a missing-kwarg `TypeError`. The forgot-to-bump check turns that into a loud test failure.
- **The trigger.** Needed by the **first post-chunk-1 config shape change**. Given the cadence (~18 shape changes in a month, [6.24-3](6.24-3-config-keyset-survey-stage3-prep.md)) and that those changes come from other work, that's imminent and not fully controllable — so this is high priority.
- **Cheap-now.** Freezing `v1.json` (the current key-set, the anchor the checks rest on) is the most time-sensitive piece — pin it at chunk-1 time, at the known-correct moment, even while deferring the pytest checks. Otherwise a shape change could slip in first and the "v1 baseline" gets reconstructed after a drift. (Recoverable via git either way; this just avoids the awkward reconstruction.)
- **Contents when built** (detail in [6.24-4](6.24-4-checkpoint-config-versioning-design.md) Stage 2): per-version key-set files, the forgot-to-bump pytest check, `CONFIG_VERSION == max(vN.json)`, migration coverage of `0..CONFIG_VERSION-1`, and an optional runtime final-output key-set check.

Not part of this bucket: chunk-1's own reconstruction correctness (the `Path` re-wrap in `resolve_checkpoint_config`) is covered by the step-2 round-trip test, which exercises `Path` fields end to end.

### D. Other deferred follow-ons

- **Resume rewiring.** Source the resume config from the `.pt` for v1 (dropping the sidecar dependency that self-describing checkpoints make redundant), fold out the `from_checkpoint` double-read (it re-opens the `.pt` for optim/scaler/epoch after the loader already read it), and fix the sibling arch-gate (`from_checkpoint`'s `if "arch" in obj`, the non-mandatory v1 case from §5).
- **`model_key` re-read fold-out.** `BCModelHandle.load` computes `model_key` via a second file read through `is_arch_bearing`; once it holds the loaded `ConfiguredModel`, the key can come from that instead of re-reading.
- **Sidecar rename** (`args.json` → `config.json`). Traps mapped in survey [6.26-2](6.26-2-survey-sidecar-config-io.md): a single `read_run_config` helper with old-name fallback, the `args_resume_NN.json` lockstep question, and collision names.
- **`arch_version` placement.** Chunk-1 reserves no top-level `arch_version` slot — the "can't-retrofit" argument is weak when the value is null and the detection scheme is deferred. It's added with the behavior axis, leaning toward a field on `ModelConfig` (so `build_model` reads it from its single input, and it rides inside the versioned `config` block as a plain `asdict` member).

### E. Route-1 — the supported-checkpoint policy call, and what it unlocks

Which historical checkpoints stay loadable (supported) vs. declared Unsupported. It's a policy decision, decidable now with no machinery, and it scopes everything downstream. (Broader fidelity-scope framing: [6.26-7](6.26-7-checkpoint-config-critical-questions.md).)

Unlocks:

- removing `value_head_variant` from the loader signature, once the pre-arch checkpoints that need it are unsupported;
- **deleting** rather than relocating the legacy reconstruction code in chunk-2 — it shrinks the surface instead of moving it;
- bounding the v0→v1 normalizer's scope (§B) to the supported set.
