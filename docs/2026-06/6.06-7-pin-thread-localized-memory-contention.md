# Pin thread localized: the n=20 ceiling is the pin-memory copy, slowed by worker memory contention (`6.06-7`)

**Date:** 2026-06-06

## TL;DR

- We instrumented PyTorch's single pin-memory thread (the one stretch of the data path we couldn't seam from our own code) and **measured** that it is the throughput ceiling for n=20: it spends ~93% of every batch period inside the `pin_memory()` copy (~233 ms/batch), while the GPU starves.
- The cost is the **copy itself**, not tensor destruction (the GIL/munmap mechanism the reference doc leads with), not the queues, and not per-batch allocation. Several prior hypotheses are ruled out by direct measurement.
- The copy is **~5× slower live than in isolation** (~233 ms vs ~47 ms for the same 252 MiB). The cause is **memory-subsystem contention** from the concurrent workers — confirmed in direction by a dose-response, with the magnitude partly inferred.
- Leading lever: **move fewer bytes** (fp16/uint8 obs) and **lighten obs-build** — both shrink the pin copy and the worker traffic that starves it. Next steps are a menu below, not yet chosen.

## What we built this session

- `bc/pin_instrument.py` — monkeypatches torch 2.12.0's `_pin_memory_loop` with a faithful copy that times each iteration as four spans: `pin_get` (wait for a worker batch), `pin_copy` (`pin_memory()`), `pin_destruct` (free the source shm), `pin_put` (hand off to the main loop). An explicit `del r` isolates the destruction cost from the queue wait. Gated behind `--profile`; an import-time guard hard-aborts if torch drifts from 2.12.0.
- `shared/timing.py` — `LockedTimer`, a thread-safe `Timer` subclass (the pin thread records off the main thread).
- `bc/run_report.py` — renders the pin spans as a per-batch table plus a `work / period` ratio, and folds the pin spans into the distribution-tails table.
- `training/scripts/one_offs/bench_pin_memory.py` — a standalone Modal micro-bench that isolates the pin cost (alloc vs memcpy, fp32 vs fp16) and tests memory-bandwidth contention.

## Headline: the pin thread is the ceiling — measured

Across four instrumented H100 runs (two n=5, two n=20, different host draws), the pin thread's own work fills ~91–93% of the batch period, with the consumer-side wait (`pin_put`) at ~0 and the input wait (`pin_get`) small. Decomposition for the n=20 CANADA-2 run (`runs-cloud/2026-06-07T04-43-03Z`):

| span | ms/batch | reading |
|---|---|---|
| pin_get | 12.3 | small → not starved for input (workers keep up) |
| **pin_copy** | **232.1** | the copy fills the period |
| pin_destruct | 3.0 | tiny → tensor destruction is not the cost |
| pin_put | 0.0 | never blocked downstream → the GPU is starving, not the limiter |
| **work (copy+destruct)** | **235.1** | |
| batch period | 252.7 | = batch_size / sps |
| **work / period** | **93.1%** | the thread is busy almost the whole time |

A serial pipeline stage is the bottleneck exactly when it is busy with its own work and not blocked on either neighbor — which is what these numbers show. The pin copy runs at ~1.06 GiB/s effective (252 MiB / 233 ms). Throughput tracks 1/pin_copy: ~2100 sps observed vs a ~2840 sps GPU ceiling (~180 ms/batch GPU compute), so closing this is worth ~30%.

## What it rules out (by measurement)

| candidate | verdict | evidence |
|---|---|---|
| GIL contention on tensor destruction | ruled out | `pin_destruct` ~3 ms mean, max ~10 ms — the reference doc's leading mechanism is a non-factor here |
| result-queue / data-queue IPC | ruled out | `pin_get` small, `pin_put` ~0 |
| per-batch `cudaHostAlloc` | ruled out | micro-bench: `pin_memory()` ≈ reused-buffer `copy_` (the host allocator reuses pinned buffers) |
| raw single-thread bandwidth | ruled out | isolated copy ~5.4 GiB/s (~11 GB/s read+write traffic) — a normal single-core rate |
| shared-memory backing of the source | ruled out | micro-bench: pinning a `share_memory_` tensor ≈ a plain one |
| prefetch depth | ruled out | prefetch 2 vs 4 flat (`6.06-6`) |
| PCIe generation | ruled out as the driver | gen affects only `h2d` (~2×, ~4–8 ms, async/overlapped); see below |

## The freezes are a non-factor

The multi-second tail stalls are essentially a single startup event, not a recurring drag. From the span histograms (n=20): `pin_get` p99 ≈ 15 ms, p99.9 ≈ 60–237 ms, with exactly one event ≥ 0.67 s (~3.8 s, almost certainly first-batch warmup) ≈ 2% of the run. `pin_copy` and `pin_destruct` have **zero** events ≥ 0.67 s (`pin_copy` max ~0.5 s, `pin_destruct` max ~10 ms). The earlier "~22 multi-second dips" framing (`6.06-5`, read off the 1 Hz GPU-util series) was the steady-starvation buffer oscillation, not discrete freezes. Steady-state `pin_copy` is the whole story.

## In isolation the copy is fast — the cost is the live workload

Run in isolation (`bench_pin_memory.py`, H100, no pipeline), the same `pin_memory()` on a 252 MiB obs-batch shape is **~47 ms** — about 5× faster than the ~233 ms the live pin thread spends. In isolation: `pin ≈ copy` (alloc is free), shm-backed ≈ plain, single-thread ~5.4 GiB/s (normal), `h2d` ~4.8 ms at ~51 GiB/s. So the copy is not slow on its own. The ~5× appears only under the live workload. This rules out the pre-allocated-ring-buffer and multi-threaded-pinning fixes: there is no per-batch alloc to remove, and a saturated memory bus won't be helped by more copy threads.

## The cause: memory-subsystem contention

The micro-bench's contention sweep times the pinned copy while N background threads run clean `memcpy` load (n=20, 252 MiB copy):

| load threads | copy min ms | GiB/s | vs N=0 |
|---|---|---|---|
| 0 | 37 | 6.6 | 1.0× |
| 2 | 40 | 6.2 | 1.1× |
| 4 | 40 | 6.2 | 1.1× |
| 8 | 56 | 4.4 | 1.5× |
| 12 | 58 | 4.3 | 1.6× |
| 16 | 76 | 3.2 | 2.1× |

**Confirmed:** contention is real and monotonic — the copy slows as memory pressure rises. **Not fully reproduced:** clean `memcpy` load at 8 threads (matching 8 workers) reaches only ~1.5×, far short of the live ~5×. The residual is **inferred**, not measured: the real workers are heavier antagonists than clean copies because their work is cache-hostile — the strided scatter of `collate` (820 µs/sample, the dominant producer cost), the ~45-of-86 base channels materialized as `np.full` constant planes, `astype` conversions, and per-channel temp-array churn. Cache-inefficient access holds memory resources longer per useful byte and evicts the pin thread's streaming data from shared cache, so eight such workers degrade the copy more than eight tidy `memcpy`s. The constraint is memory **bandwidth and shared cache**, not RAM capacity (the host has 1 TiB, mostly free).

Rough bandwidth picture (host `cpu_model` reported "unknown", so these are estimates): single-thread copy ~5.4 GiB/s (~11 GB/s read+write traffic); our 17-core slice sustains on the order of ~50–100 GB/s aggregate before heavy throttling (inferred from the sweep); the full H100 node is likely a dual-socket DDR5 server at ~500–900 GB/s aggregate shared across tenants.

## Corroborations

- **"More workers made it worse"** (`6.05-3`: 8→12 workers dropped util 76%→69%) now fits cleanly — more workers means more memory antagonists, a slower pin copy, lower throughput. This was hard to explain under a producer-bound model.
- **The original memory-bandwidth hypothesis** (`6.05-3`) was directionally right, just mislocated: the bandwidth limit binds in the pin copy under contention, not in obs-build compute.
- **PCIe gen is a draw-quality marker, not a cause.** gen4 runs came in lower-sps, but every gen4 sample we have is the same slow host (us-east5); the gen affects only `h2d` (tiny, overlapped). The throughput gap between draws is host `pin_copy` variance (a gen5 host, sines-2, was as slow as the gen4 one), not the bus.

## Corrections to prior docs

- `6.05-3` listed "Consumer (pin_memory / H2D)" as ruled out, on the rationale "pin thread far faster than the batch rate." **Overturned** — the pin thread is the bottleneck.
- The pin-memory reference doc (`docs/pytorch-dataloader-pin-memory-bottleneck.md`) leads with two mechanisms (serial memcpy throughput, GIL contention on destruction). In our case both are non-factors as written: the copy is fast in isolation, and destruction is ~3 ms. The real mechanism is contention against the copy. The reference doc should be updated to record this measured outcome.

## fp16 projection

Halving the obs bytes (fp16) takes the n=20 copy from 252 MiB to 126 MiB. Even if the per-byte rate under contention is unchanged, that is ~117 ms — below the ~180 ms GPU floor, which would flip n=20 to GPU-bound. fp16 also halves the workers' `collate` write traffic, attacking the contention source, so the live result could be better than a naive halving. Caveat: the residual ~3× of the slowdown is not purely bandwidth, so this is a well-founded expectation rather than a guarantee — it needs a live measurement to confirm.

## Next steps — menu (to discuss, not chosen)

Byte / contention reduction:
- **fp16 obs** — the leading lever. Real work: numerics-parity check across channels, and the fp32/MPS path runs without autocast, so the fp16-obs path needs gating (noted in `6.05-3`).
- **uint8 for mask / categorical channels** — 4× on the integer-valued subset; a mixed-dtype obs could beat blanket fp16, at a larger correctness surface.
- **`np.full` constant planes → conv bias / FiLM** — deletes ~45 redundant per-sample write-passes outright (a model change).
- **Build channels directly into the obs buffer** — removes per-channel temp allocations (cache churn).
- **num_workers sweep** — a contention knob (fewer antagonists vs less production); cheap to test now that we understand why more workers hurt.

Diagnostics (optional):
- **Hardware-confirm probe** — `lscpu` / `numactl --hardware` / a multi-thread STREAM sweep to pin the slice's real aggregate bandwidth and the CPU model.

Housekeeping:
- Update the pin-memory reference doc with the measured outcome; refresh the auto-memory dense-history pointer.

For the record, demoted by this session's measurements: pre-allocated pinned ring buffer (alloc is free), TensorDict multi-threaded pinning and free-threaded Python (no GIL/copy-thread win against a saturated bus), SPDL / DALI (GIL- or image-pipeline-oriented), CUDA-stream prefetcher (h2d is already small).
