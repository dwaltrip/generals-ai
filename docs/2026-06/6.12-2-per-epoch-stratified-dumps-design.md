# Per-epoch in-training stratified val dumps — design (`6.12-2`)

**Date:** 2026-06-12

**Status:** Implemented 2026-06-12.

**Purpose:** Make every training run optionally write the per-frame stratified dump for each epoch's val pass, so erosion/optimum questions (which epoch is the value head's true optimum, what the late-game signal does over training) are answerable without manual per-checkpoint offline dumps.

Grounding: [`6.10-6`](./6.10-6-session-summary.md) follow-up #2 (the motivation: would have answered the ep2-vs-ep6 question with zero extra passes), [`6.11-1`](./6.11-1-policy-entropy-metric-and-mps-race-fix.md) (named `bc/eval/dump.py` as the seam). The offline harness this extends: `packages/training/scripts/stratified_val_loss_analysis.py`.

## Shape: one schema, two producers, one consumer

The offline `dump` subcommand's per-frame record (14 columns: `frame_t`, `players_alive`, `p_start`, `placement`, `is_pass`, `value_probs [N,8]`, `value_ce`, `policy_ce`, `policy_entropy`, `n_legal`, `top1`, `top3`, `pass_prob`, `persp_val_index`) becomes the shared format. Record-building relocates to `training/bc/eval/dump.py`; the in-training val pass and the offline script both produce it; the existing `report` subcommand consumes either unchanged.

Pairing across epochs is free: `sample_idx` indexes into `samples_for_split(manifest, "val", intermediate)`, which both `train.py` and the offline tool resolve identically — stable across epochs, resume segments, and producers. Row *order* can differ (multi-worker interleave), so any future paired `--diff` (6.10-6 follow-up #5) joins on `(sample_idx, frame_t)`, not row position. Nothing here precludes that mode.

## Module layout

**New `training/bc/eval/dump.py`:**

- `FrameRecordCapture` — per-batch accumulator. `add_batch(host_batch, moved_batch, out)` grabs the host-side scalars (`frame_t`, `players_alive`, `p_start`, `sample_idx`, `value_target`→`placement`, `is_pass`) from the pre-move batch and computes the derived columns (value log-softmax/CE, policy CE/entropy/top-k, pass prob — the math currently in the offline `_val_pass`, including its `.float()` casts) from the model outputs, stashing plain-numpy copies on CPU (copies, so DataLoader pinned buffers aren't retained). `finalize(persp_index_map=None)` returns the concatenated column dict — the offline producer passes its `--sample-frac` remap array; in-training passes `None` (identity `persp_val_index`).
- `dump_path(run_dir, epoch)` + `save_dump(records, path, meta)` (npz + `.meta.json`) — relocated from the offline script.
- Later, follow-up #3's report-layer IO seam (`load_dump`) also belongs here; renderers stay pure per the 6.09-3 rule. Not built now.

**`eval/run.py` — `run_val`:** one new optional param, `capture: FrameRecordCapture | None = None`. When set: build the val dataset with `include_frame_info=True`, keep the host batch reference before `move_batch`, call `capture.add_batch(...)` after the forward. When `None` (default): no change of any kind. No file IO in `run_val`.

**`train.py` — `train_loop`:** owns the write, next to the other run artifacts. When `config.dump_val_frames`: build the capture, pass to `run_val`, `save_dump` to `<run>/analysis/stratified_val_epoch_NNN.npz` after the pass. Epoch numbers are monotonic across resume segments, so no filename suffix is needed. Also print a one-line cross-check into `run.log` — dump-aggregated mean `value_ce` vs `val_summary["value"]`, frame counts — the same correctness guard the offline tool runs against `epochs.jsonl`, nearly free here since both come from the same pass.

**Offline script:** `_val_pass` shrinks to loader + loop + `capture.add_batch` + `finalize(chosen_arr)`. The `report` subcommand, sample-frac logic, and CLI are unchanged.

## Config plumbing

`dump_val_frames: bool = False` on `TrainConfig`, supplied via the `--config` file — no CLI flag. `TrainConfig.from_file` passes any field from the JSON through to the constructor and `validate_partial` accepts any `TrainConfig` field, so no plumbing change is needed beyond the field itself; this gives per-sweep-cell control for free (`prep_sweep` cells are config files). `__post_init__` rejects `dump_val_frames` + `skip_val` together. Recorded in `args.json` as usual. Flag-off runs are behavior-identical to today (the levers convention from 6.10-3).

The field follows the `gpu` precedent: a config-file field that doesn't affect the training trajectory and is added to `_DRIFT_EXCLUDED`, so a resume overlay can toggle it freely — which is the 6.10-6 use case verbatim ("resume the bonus run with per-epoch dumps") — and parents predating the field (whose `args.json` lacks the key) don't spuriously trip the drift check.

## Artifact format, size, dtypes

Same filenames and meta as the offline producer: `stratified_val_epoch_NNN.npz` + `.meta.json` under `<run>/analysis/`. Meta keeps all existing keys (`sample_frac: 1.0`, `seed`, `checkpoint`, `n_perspectives[_total]`, `n_frames`, `device`) and adds `producer: "train" | "offline"` and `forward_dtype: "fp16" | "fp32"`. `report` only reads keys that remain present, so old and new dumps interleave.

**Size (measured, not the 6.10-6 estimate):** the saved 6.10 cloud-run dump is 11.7 MB at frac 0.5 / 256k frames (~46 B/frame compressed) — so full-frac at that val-set scale is ~23 MB/epoch, ~190 MB per 8-epoch run, 30–100× the 1–6 MB/epoch the 6.10-6 note guessed. Re-encoding that dump shows where the bytes live:

| variant | size | vs orig |
|---|---|---|
| current (fp32 / int64) | 11.72 MB | 100% |
| `value_probs` → fp16 | 7.49 MB | 64% |
| + int columns narrowed | 7.38 MB | 63% |
| + derived floats (CE etc.) → fp16 | 5.52 MB | 47% |

**Decision: store `value_probs` as fp16; everything else keeps its current dtype.** The probs feed only display-grade aggregates, and the measured precision impact is negligible (pred-entropy max abs diff 2.9e-4; argmax flips on 0.02% of frames, i.e. fp16-resolution ties). Int narrowing is skipped — DEFLATE already crushes the small-valued int64 columns, so it buys ~1%. fp16 on the derived floats is declined: `value_ce` is the load-bearing column (bucket means, Δ vs floor, the future paired diff) and fp16 quantizes it at ~4e-3 abs — small, but real headroom given away for 1.9 MB. Both producers emit the slim format from day one; the six existing fp32 dumps stay valid (`report` is dtype-indifferent).

## Caveats

- **fp16-derived records on cloud.** Cloud val runs under autocast, so in-training dumps derive from an fp16 forward where offline dumps were fp32 — same `.float()` casts before softmax/CE, but the logits differ at fp16 resolution. `forward_dtype` in the meta records this; comparisons across the two producers carry that caveat.
- **Memory/throughput.** CPU stash peaks ~50 MB for a 512k-frame full-frac pass. The per-batch D2H copies add no new sync points of consequence — `run_val` already syncs every batch via its `int(.sum())` counters. Dataset-side frame-info cost is a `searchsorted` + four scalar tensors per frame. Expected low-single-digit % on the val pass; smoke test confirms.
- **Artifact pull.** No changes needed: `pull_runs.py --no-checkpoints` already pulls every non-checkpoint top-level entry, so `analysis/` comes back automatically; whole-run `modal volume get` trivially includes it.

## Out of scope (this implementation)

Report-layer changes (stratified table in `quality.md` — 6.10-6 follow-up #3, next session), the paired `report --diff` mode (follow-up #5), and any offline-script change beyond relocating shared record-building.
