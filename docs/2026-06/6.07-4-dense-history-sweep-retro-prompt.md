# Dense-history-sweep (obs channel) Discussion

## Intro and Session Goal

A few days ago, we finished our first dense-history sweep for `n`, using values n=5,10,20. The `n` here refers to the numberr of previous ticks for which we show detailed per-tile tactical info (ownership changes and army movements).

My goals for this session:

1. Analyze these results and discuss the implications and improvements I might want to make next, based on what we learn and synthesize.
2. Discuss the value head architecture and how we can improve it to reduce overfitting and learn better overall. We can also explore alternatives to the value head. We will be trying self-play PPO as a phase 2 beyond the behavior-cloning we are currently doing, so we need to keep that in mind.

## Sweep Basics

* Sweep dir with the outputs for all 3 runs: data/training/sweeps/2026-06-05-dense-history-n
* Manifeset with 5k total perspectives (5% saved for val): cloud_24k_sub_5k.json

More recently (last night), I did also ran much more substantial single run with n=20:

* Run dir: data/training/runs-cloud/2026-06-07T08-41-55Z

All of these were with the 0.75x "model width" (compared to the DeepNash 1x full-width that are architecture is heavily based on). We also used the larger "pyramid" value head variant.

## Misc Notes

* I cut the n=20 run short after 2 epochs because there was an issue with n=20 being much slower, and we already had enough info from the completed 3-epoch runs with n=5 and n=10, and the 2 epochs from n=20.
* We then took a big detour to fix the slowdown issue with n=20. That landed, n=20 runs now at full H100 GPU utilization just like n=5 and n=10. So nothing we need to worry about in this session.

## Results

### Sweep

The main result of the sweep was rather disappointing.

* Based on my initial asesssment, increasing the size of recent history seemed to produce worse results. Looking at all val loss (policy, value, and pass): n=10 was worse than n=5 and n=20 was worse than n=10 across all epochs.
* The value head also shows signs of increased over-fitting at larger N: `train_value` is going down rapidly while `val_value` stays high.

See the table below for the exact numbers.

### Recent large run

With the more recent run, I was hoping that the much larger data size (5k perspectives to ~24k perspectives) would potentially help with the overfitting problem. 

It may have helped a bit, as the train_value was actually slowly going up instead of down. `val_value` did jump down on epoch 2 and then only inched up a bit in epochs 3 and 4. I can't tell if that's noise or not though.

We don't have a direct comparison here with n=5 or n=10 on this data size. But regardless, as this was the largest run I've done by a decent margin (now that we've tuned our data pipeline to work well with H100) and the val_value was still pretty bad.
