# Fog-memory re-derivation prompt

## 1. Instructions

You are computing, from first principles, the evolving fog-memory state for one player's perspective in a game of generals.io, across a sequence of game ticks.

The memory system tracks what the perspective player knows, remembers, and can infer about the board as it processes each tick's snapshot. Your task is to derive the state of specific tracked fields at five checkpoint ticks.

**Hard constraints:**

The rules stated in this document (§3) are the project-specific memory-state tracking rules, which are not game mechanics and live nowhere in that reference.
- **Do not** read any source code or test file in this repository. The entire point of this is to independently re-derive the values. Your results will be used to validate the test.
- The game states below are **synthetic** — hand-authored for testing. Do **not** try to validate them for physical/move-legal plausibility (e.g. whether ownership could really have evolved this way). Take each tick's ownership and army values as **ground truth** and derive everything downstream from them.

**Show your work.** For every checkpoint tick, before giving the final field values, write down the intermediate quantities you derived, so a disagreement can be localized:

- The perspective player's **current-tick vision set** (which cells it can see at that tick), and how you got it.
- The **cumulative historically_seen** through that tick.
- For each **structure** cell entering vision for the first time at or before that checkpoint: whether its type is resolved as mountain, city, or general, and why.
- The state of each tracked field listed in the checkpoint.

Then give the specific values requested at each checkpoint, each with a one-line reason.

## 3. The rules: fog-memory update policy

These are project-specific tracking rules for the model's memory state, **not** generals.io mechanics. The memory system processes game snapshots sequentially from tick 0 onward. At each tick, vision is first computed from that tick's ownership, then each tracked field is updated.

### 3.1 Initialization (before the first tick is processed)

All fields start at their "nothing known" state:

- **historically_seen** `[H, W] bool`: all False.
- **known_mountain** `[H, W] bool`: all False.
- **known_city** `[H, W] bool`: all False.
- **known_general** `[H, W] bool`: False everywhere **except** the perspective's own general, which is always known from the start.
- **general_locations** `[P] int`: the perspective's own slot stores their general's cell index. All other slots store **-1** (unknown).
- **last_seen_owner** `[H, W] int`: all **-2** (never-seen sentinel).
- **last_seen_armies** `[H, W] int`: all **-1** (never-seen sentinel).
- **turns_since_seen** `[H, W] int`: all **-1** (never-seen sentinel).
- **opp_contacted** `[P] bool`: all False.
- **opp_captured_by** `[P] int`: all **-1** (alive).
- **opp_has_seen** `[P, H, W] bool`: all False.

### 3.2 Per-tick update (applied at each tick t, in order)

**Step A — Vision.** Compute the current vision set from the mechanics doc's visibility rule (Moore neighborhood of every cell the perspective owns at tick t). Then:

```
historically_seen  |=  current_vision
```

Monotonic — once True, stays True forever.

**Step B — Structure resolution.** Three sub-steps, each using the current-tick vision:

1. **known_mountain.** A cell becomes a known mountain when it is **currently visible** and is a **mountain**. Once set, never cleared.

2. **known_city.** A cell becomes a known city when it is **currently visible** and is a **city at this tick**. The "at this tick" qualifier matters for captured generals: a captured general converts to a city at a specific snapshot (stated in §4). Until that snapshot, the cell is not a city for this rule — even if the capture event has already fired. Once set, never cleared.

3. **known_general.** A cell becomes a known general when it is **currently visible** and is an **active general** — meaning it is in the initial generals list **and** has **not yet become a city** at this tick. Once set, **never cleared** — even after the cell later converts to a city. This is documented stale-flag behavior: the known_general bit persists at that cell.

   When a general is newly discovered, **general_locations** for that player's slot is set to the cell index. One-shot: once set, never updated.

**Step C — Last-seen values.** For every cell that is **currently visible**:

- **last_seen_owner** ← the cell's current owner at this tick. Owners: 0 = perspective, 1 = opponent, -1 = neutral (unowned). Mountains have a distinct ownership value (-2) but the test does not query mountains for last_seen_owner.
- **last_seen_armies** ← the cell's current army count at this tick.

Non-visible cells retain their previous values (or sentinels if never seen).

**Step D — Turns since seen.**

- Currently visible cells: **turns_since_seen = 0** (reset).
- Previously seen but currently fogged (in historically_seen but **not** in current vision): **turns_since_seen += 1** (increment by one).
- Never-seen cells (not in historically_seen): remain at **-1** (untouched).

**Step E — Opponent tracking.**

For each opponent p (not self):

1. Find all cells that are both **currently visible** to the perspective **and** owned by opponent p at this tick.
2. If any such cells exist:
   - **opp_contacted[p] = True** (monotonic; once True, stays True).
   - Compute the **Moore dilation** of those cells (each cell plus its 8 neighbors, clipped to board bounds) and OR into **opp_has_seen[p]**. Rationale: if the perspective sees a cell owned by p, then p had Moore-neighborhood vision around that cell.

**Step F — Capture events.**

Capture events carry a timestamp. When a capture event's timestamp matches the current tick:

- **opp_captured_by[captured_player]** is set to the captor's slot. One-shot write.
- This is a global event — processed regardless of fog.
- **Important timing:** the capture event fires at an action tick. The snapshot at that tick shows the **pre-action** state (the captured player still owns their general in the ownership array). The ownership flip to the captor appears in the **next** snapshot.

## 7. Flagged conventions (reason about these explicitly; don't assume)

- **Structure existence vs. type resolution.** Per the game mechanics doc, structure existence (mountain or city) is always visible regardless of fog, but structure *type* is indistinguishable behind fog — you need vision to tell mountain from city. The memory system tracks type resolution separately. A structure the perspective has never had vision of is **neither** known_mountain **nor** known_city. Make sure your derivations treat existence and type as separate facts.

- **Opponent generals are fully hidden.** Unlike mountains and cities, enemy generals behind fog are completely invisible — they look like ordinary empty tiles. The perspective cannot detect their existence until it gains direct vision. An unseen opponent general does not count as a structure.

- **known_general is never cleared (stale-flag behavior).** Once known_general is set for a cell, it stays True even after the general converts to a city via capture. The known_city bit will also become True at the conversion snapshot. Both flags coexist at the same cell. This is the current documented behavior, not a bug — explicitly check that your t=7 derivation reflects it.

- **Capture event timing vs. ownership timing.** The capture event fires at the action tick (t=6 in this trajectory). At that tick's snapshot, the captured player **still owns** their general in the ownership array. The ownership flip appears in the **next** snapshot (t=7). opp_captured_by updates at the event tick; last_seen_owner reflects the snapshot. Make sure your t=6 and t=7 derivations handle this split correctly.

- **General-to-city conversion timing.** The captured general becomes a city at a specific snapshot (here: snapshot 7). The known_city rule's "is a city at this tick" condition uses this timing. At tick 6, the cell is not yet a city — even though the capture event has fired. At tick 7, it is. Reason about this explicitly for the t=6 and t=7 checkpoints.

- **opp_has_seen is driven by currently-visible opponent cells, not all known opponent cells.** The Moore dilation fires only for cells the perspective **currently sees** that are owned by the opponent **at this tick**. If the opponent loses all territory (post-capture), or if the perspective can no longer see the opponent's cells, no new dilation occurs. Between t=5 and t=7, does opp_has_seen grow? Derive it from the ownership and vision at each tick.

- **turns_since_seen three-way logic.** The three states are: currently visible → reset to 0; previously seen but currently fogged → increment by 1; never seen → stays at -1 (untouched). Don't confuse the increment path with the sentinel path. Cell (0,0) at t=0 is a useful test case.
