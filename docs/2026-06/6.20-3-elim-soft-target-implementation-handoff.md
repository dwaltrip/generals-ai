*Date: 2026-06-20. Implementation of the soft-target direction from [6.20-2](6.20-2-elim-head-diagnostics-and-direction.md) (numbers: [6.20-1](6.20-1-elim-head-diagnostics-numbers.md)). The death-vs-removal distinction it leans on is single-sourced in `bc/player_status.py`.*

Two commits on branch `elim-head-work-continues`: "board-removal target + time-based soft target" (the change), then "address review — probe domain + tie test" (Opus review follow-ups).

## What the change does

The who-dies-next (`next_death`) aux head got two coupled changes:

1. **Target event: death → board-removal.** It now predicts who is *removed from the board* next (capture/neutralize, tiles cleared) over the **present** domain, instead of who *stops playing* next (death: surrender or capture) over the alive domain. Rationale: removal is the more value-relevant "the player is gone" signal — a surrendered player still on the board hasn't changed the survivors' position; the tile transfer at removal is what does. The aux head exists to help the value head, so value-relevance is the tiebreaker.

2. **Time-based soft target**, off by default: `p_i ∝ exp(-(removal_dt_i - removal_dt_min)/τ)` over the present players, τ in ticks. Set to **15** for the planned A/B. The hard one-hot CE stays as the reporting metric; the soft CE is the trained objective (mirrors `value`/`value_soft`).

## Death vs removal (the reference you'll want)

From `bc/player_status.py`:

- `death_by_slot` — first DeathEvent (surrender OR capture-while-alive). Drives `alive_mask` (`death >= t`). "Stops playing."
- `removal_by_slot` — board-removal (capture OR neutralize that clears tiles). Drives `present_mask` (`removal >= t`). "Army leaves the board."
- Surrender window = `~alive & present` (surrendered, tiles not yet cleared) — ~1% of frames. This is the only place death and removal disagree.

Both masks use `>= t` (present/alive through `snapshot[e]`, gone from `e+1`) — the obs's pre-event board-snapshot convention. The obs encoder already emits present/alive player-status channels (`obs/channels.py`, landed [6.19-1](6.19-1-obs-player-status-channels-landed.md)), so the head reading the trunk and the loss masking to `present` are consistent with what the trunk sees.

## How to judge a soft run (don't "fix" expected behavior)

Per [6.20-2](6.20-2-elim-head-diagnostics-and-direction.md): judge on the **training curve** (does the epoch-3 elim-CE overfit turnover flatten?) and the **value A/B** (policy tax + value CE) — **not** on top-1. Top-1 is *expected* not to beat the 47% lowest-army rule; a calibrated soft target's best output on a near-tie is roughly the prior over the bottom cluster, which is what the rule already encodes. So a soft run that sits at ~the rule on top-1 while flattening the curve is the success case, not a regression. The policy tax and value A/B must be **re-measured** after a soft run (the elim gradient changed shape), not assumed from the hard-target gate.

τ=15 is a compromise between 10 and 25 from the calibration (gap distribution in [6.20-1](6.20-1-elim-head-diagnostics-numbers.md) / the `victim_gap_distribution.py` run). The soft target auto-adapts to game phase with no explicit term: crowded early boards have tight removal gaps → softer targets; sparse late boards → near one-hot.

## Intentional debt — looks wrong, is deliberate

1. **The names say "death/elim" but the event is board-removal.** `next_death` (variant string), `next_death_target` (function), `next_elim_*` (dump columns, loss keys), `next_elim_dt` (now ticks-to-next-*removal*). Kept to bound the diff. See the rename section below before touching.

2. **The dump pushes BOTH `present_mask` and `alive_mask` for next_death** (`eval/dump.py`). Not redundant: `present_mask` is the head's real domain (the CE is computed over it); `alive_mask` rides along so `family_a_victim_baselines.py`'s `join_dump` cross-check still works and the surrender-window (alive-vs-present gap) stays analyzable. Dropping alive_mask breaks both.

3. **The dataset emits `alive_mask` unconditionally even for next_death** (`dataset.py`), which the next_death *loss* no longer reads. It's still consumed downstream (the dump pushes it, per #2), and the emission is shared with the time_bin and alive-only paths. Leave it.

4. **`next_elim_removal_dt` [8] looks unused if you grep dump/eval** — only the loss's soft branch reads it. It's emitted unconditionally (not gated on τ>0) on purpose: τ is a loss knob unknown at encode time, so emitting the per-channel horizon always keeps τ sweepable without re-encoding the dataset.

5. **`ElimCtx` carries `removal_by_slot` but the time_bin head ignores it.** ElimCtx serves both variants; time_bin keys on death/alive, next_death on removal/present. Not dead weight.

6. **`elim_head_debug.py` and `victim_gap_distribution.py` still use the alive/death domain for next_death analysis.** Deliberate, with a NOTE in `elim_head_debug.py`. `victim_gap_distribution.py` is the as-run (death-based) τ-calibration record. Aligning these to removal/present is deferred (see Open items) — it's not a one-liner.

## Fragilities — looks fine, is fragile

1. **`ElimCtx` is built by positional splat:** `ElimCtx(edges, *precompute_elim(...))`, field order `(edges, death_by_slot, removal_by_slot, is_real, sentinel)` matching `precompute_elim`'s 4-tuple return `(death, removal, is_real, sentinel)`. Reordering the dataclass fields silently misassigns (e.g. removal↔is_real) with no type error — they're all arrays/ints. Change field order and the return tuple in lockstep, or switch to keyword construction.

2. **The soft-CE `logp = where(present_mask, logp, 0)` line in `loss.py` is load-bearing**, not defensive cruft. It zeroes log-probs on absent channels before the `soft_target * logp` product, avoiding `0·(-inf)=nan` (absent channels have `soft_target == 0` and `logp == -inf`). `test_next_death_soft_target_shape_and_winner_mass` guards it; the reason isn't visible in the code.

3. **`removal_dt.to(torch.float32)` in the soft branch is intentional.** The winner's horizon is sentinel-scale (~thousands of ticks); fp32 makes the `exp` underflow to 0 cleanly and is immune to fp16 overflow. Don't drop the explicit cast when simplifying (cloud runs are fp16/autocast).

4. **The `total` identity uses the *soft* term** (`next_elim_soft`), not the hard reporting CE — in both `bc_loss` and `LossAccumulator.summary`, mirroring `value_soft`. If you refactor the accumulator, keep `total` on the soft term; `next_elim` (hard) is reporting-only.

5. **τ=0 must give `next_elim_soft` literally equal to `next_elim`** (same tensor, the `else` branch). The accumulator and total both key on the soft term, so any drift here silently changes the τ=0 ≡ hard-behavior guarantee that keeps existing runs reproducible.

## If you rename `next_death` → `removal`

The single biggest cleanup candidate. Two options:

**Surgical (low risk, recommended first):** rename only `next_death_target` → `next_removal_target` (function + docstrings) and fix its one import in `dataset.py`, `__all__`, and the test references. This kills the sharpest lie (a function named "death" that keys on removal) without touching any config/dump/checkpoint-facing string. The variant name "next_death" and the `next_elim_*` keys are defensible as "who's eliminated next" and can stay.

**Full rename (higher risk):** if you want end-to-end consistency, the touch surface is:
- Variant string `"next_death"` in `ELIM_HEAD_VARIANTS` (`model_config.py`) — **checkpoint/config-facing.** Existing sweep configs and saved checkpoints carry `elim_head_variant="next_death"` in their arch dict. Needs a back-compat alias on load, not a blind replace.
- Dump column names `next_elim_probs`/`_ce`/`_target`/`_dt` (`eval/dump.py`) — **reads of existing dumps break.** `eval/dump_compat.py` (`_LEGACY_ALIVE_MASK_KEYS` + `read_alive_mask`) is the existing pattern for aliasing renamed dump keys; follow it.
- Config field `next_elim_target_tau` (`train_config.py` + `loss.py`), loss keys `next_elim`/`next_elim_soft`/`n_next_elim`, eval summary key `next_elim` (`eval/run.py`), sample keys `next_elim_target`/`next_elim_dt`/`next_elim_removal_dt`/`present_mask` (`dataset.py`).
- Head module `model/heads/elim_next_death.py` + its wiring in `model/bc_model.py`, `model/__init__.py`.
- Analysis: `family_a_victim_baselines.py`, `elim_head_debug.py`, `head_vs_rule_by_margin.py`, `who_dies_next.py`, `victim_gap_distribution.py`.

My read: do the surgical rename, leave the config/dump strings alone (with the module docstrings clearly stating "next_death = board-removal"), unless there's appetite for the full back-compat exercise.
