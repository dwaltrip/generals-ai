## Shared facts

Two shared facts up front so the per-analysis pointers stay short:

- **Baseline analyses (1, 8–11):** model-free, full val of `cloud_24k_sub_5k` (~112.7k frames), window **K=25**, scored against the same `next_death_target` truth the head trains on. Scratch scripts preserved at `tmp/elim-baseline-scratch/` (gitignored); the committed fq replacement `family_a_victim_baselines.py` is being built.
- **Probe / noise analyses (3–6):** `cloud_24k_sub_11k` (the 6.15-2 setup); trunk = the 11k checkpoint `2026-06-14-yolo-11k-elim-head-v2/.../2026-06-14T07-47-05Z/checkpoints/epoch_002.pt`.
- **Reading the oracle figures (1, 8, 9, 11):** `oracle(level OR X)` credits a frame if *either* rule names the victim, i.e. it assumes a perfect per-frame choice between them — so it is an upper bound on what a level+X ensemble could reach, not an achievable single-rule accuracy.

## Results

### 1. Heuristic baseline pull — *[model-free baseline]*
**Description.** Re-ran the incumbent baseline script on the gate sweep to pull the army-delta and oracle numbers the gate doc never reported. The "army-delta K" rule names the player with the most-negative *net* army change over the trailing K ticks (an endpoint difference, `army[t]−army[t−K]`); the oracle is the fraction where *either* lowest-army or the best delta names the true victim.

| baseline                        | top-1                      |
| ------------------------------- | -------------------------- |
| lowest total army               | 47.2%                      |
| army-delta K=1 / 5 / 10 / 25    | 31.5 / 42.2 / 42.2 / 44.7% |
| ORACLE(lowest-army OR delta-25) | 56.3%                      |

*(Corpus context: victim time-to-death CDF <10:12% <50:47% median 54; victim-channel marginal 10–16% per slot.)*

**Read.** Army *rate* (best 44.7%) is weaker than army *level* (47.2%), but the 56.3% oracle looked like ~+9pp of complementary headroom — a read that analyses 9 & 11 later overturn.

> *Repro: `./training/analysis/scripts/who_dies_next_baselines.py ../../data/training/sweeps/2026-06-19-elim-head-coherent-ab` from `packages/training`; stage-0 table prints first (the head-join then crashes on the elim-off run — stale key). Cached at the sweep's `runs/baselines_stage0.npz`.*

### 2. Overfit localization — *[trained-model dump diagnostic]*
**Description.** Averaged per-frame `next_elim_ce` and `value_ce` from each epoch's val dump of the next-death run, to test whether the elim overfit is the elim head alone or the whole shared trunk memorizing.

| ep    | elim CE   | elim top-1 | value CE |
| ----- | --------- | ---------- | -------- |
| 1     | 1.646     | 41.2%      | 1.408    |
| 2     | 1.516     | 41.7%      | 1.440    |
| **3** | **1.501** | **44.8%**  | 1.355    |
| 4     | 1.568     | 42.3%      | 1.351    |
| 5     | 1.616     | 41.2%      | 1.354    |

**Read.** Elim CE turns over hard at ep3 while value CE on the same trunk just plateaus — so the overfit is confined to features outside value's working set, pointing the fix at elim-local regularizers rather than trunk-wide data scaling (an indication, not proof). The head's peak (44.8% top-1 at ep3) is itself below the 47.2% lowest-army rule — the gap that analyses 3–6 explain.

### 3. regress-then-argmin, trunk — *[frozen-rep probe]*
**Description.** Resurfaced an undocumented 6.16 probe: regress each alive player's army off the frozen trunk (the proven 0.82-R² task), then take an *exact arithmetic* argmin of the predicted armies and compare to the true weakest player. The exact argmin removes the "can the head learn argmin?" confound, isolating army *fidelity*.

| source           | R²    | argmin-identity |
| ---------------- | ----- | --------------- |
| trunk (11k ckpt) | 0.806 | **0.523**       |

**Read.** Even with a perfect argmin, the trunk's army resolves the true weakest player only ~52% of the time — the residual misranks the bottom of the leaderboard.

> *Repro: `./training/analysis/probe_runs/regress_then_argmin.py --source trunk --checkpoint <11k epoch_002.pt> --manifest .../cloud_24k_sub_11k.json --epochs 40 --val-frac 0.5 --max-train-frames 24000 --max-val-frames 40000`. Output: `data/analysis/probes/20260616-200151-regress_then_argmin-trunk/`.*

### 4. regress-then-argmin, raw-obs control — *[frozen-rep probe]*
**Description.** The missing control for #3: same probe, but reading from raw obs (which carries exact army as a broadcast channel) instead of the trunk. Establishes the ceiling — how well the *best possible* army representation resolves the weakest player.

| source  | R²    | argmin-identity |
| ------- | ----- | --------------- |
| raw obs | 0.994 | **0.711**       |

**Read.** Even near-perfect army (R² 0.994) finds the true weakest only 71% of the time, so the trunk's leak (0.711→0.523) is ~19pp, *not* the ~43pp I'd predicted — and there is a large intrinsic ceiling because the argmin lives where R² has no resolving power.

> *Repro: identical to #3 with `--source raw_obs`. Output: `data/analysis/probes/20260620-081309-regress_then_argmin-raw_obs/`.*

### 5. Argmin noise Monte-Carlo + bottom-gap distribution — *[noise-model simulation]*
**Description.** A no-model check of whether #3/#4 are real: take true army, add homoscedastic noise calibrated to each R² (`σ = √(1−R²)·per-slot-std`), and measure the argmin flip rate. Also measured the gap between the two weakest alive players, the quantity the argmin actually decides on.

| R²    | probe argmin | Monte-Carlo argmin |
| ----- | ------------ | ------------------ |
| 0.994 | 0.711        | 0.691              |
| 0.806 | 0.523        | 0.529              |

| bottom-two army gap        | value           |
| -------------------------- | --------------- |
| median / p25 / p10         | 82 / 8 / 1 army |
| frames within 25 / 10 army | 36.4% / 26.9%   |

**Read.** The Monte-Carlo reproduces the probe (so the numbers aren't a bug), and the gap distribution explains why: ~27% of frames have the two weakest within 10 army, far below the ±54-army residual a 0.994-R² fit carries.

> *Repro: `tmp/elim-baseline-scratch/argmin_noise_check.py` (40 games of `cloud_24k_sub_11k`). Per-slot army std ≈ 500–1200.*

### 6. Cross-sectional vs longitudinal R² — *[noise-model simulation]*
**Description.** Scored the *same* calibrated noise three ways: longitudinally (per-player over its own trajectory — the probe's metric), cross-sectionally (across players at each frame — the ranking-relevant cut), and cross-sectional restricted to the bottom-3 (the argmin-relevant cluster).

| noise calibrated to | longitudinal | cross-sectional | cross-sec bottom-3 |
| ------------------- | ------------ | --------------- | ------------------ |
| 0.994 (raw-obs)     | 0.994        | 0.965           | 0.919              |
| 0.806 (trunk)       | 0.806        | −0.130          | −1.617             |

**Read.** The same noise that reads as R² 0.99 longitudinally is ~0 (raw) or strongly negative (trunk) cross-sectionally at the bottom — R² is a longitudinal fit and the elim head's task is cross-sectional, so they share no information where it matters.

> *Repro: `tmp/elim-baseline-scratch/xsec_r2_check.py`. Homoscedastic-noise proxy, validated by the #5 argmin match; longitudinal reproduces the target exactly under global per-slot centering (matching the probe).*

### 7. Metric-methodology audits — *[methodology audit]*
**Description.** Two verifications to make sure the surprising numbers above weren't computation artifacts: how the probe's R² is computed, and how the per-epoch CEs are averaged.

- **R²** (`army_regression_task.py:81–104`): per-player, pooled over the whole split, centered on each player's *global* mean → a longitudinal fit against army's full dynamic range. Identical code for trunk and raw-obs (fair comparison).
- **CE** (dump meta): `sample_frac 1.0`, 250/250 perspectives → full val, 112,975 frames, 100% valid, no nans; a plain unweighted per-frame mean.

**Read.** Both numbers are computed as assumed — the R² paradox is structural (longitudinal vs cross-sectional), not a bug, and the elim-vs-value CE comparison is apples-to-apples on the same frames.

> *Repro: read `metrics()` in `army_regression_task.py`; inspect a `stratified_val_epoch_003.npz` + its `.meta.json` (`sample_frac`, `n_perspectives`, `next_elim_target>=0` fraction).*

### 8. Rate-construction sweep — *[model-free baseline]*
**Description.** Swept the new per-tick-delta constructions you proposed — worst single-tick drop (`max`), mean of the N worst ticks (`topN`), and the .90/.95 percentile of per-tick losses — each in absolute and relative-to-own-army form, scored on standalone victim accuracy and oracle-with-level.

| construction                  | standalone         | oracle(level OR)   |
| ----------------------------- | ------------------ | ------------------ |
| pct90 / pct95 (abs)           | 28.5 / 28.5        | 58.2 / 57.9        |
| top5avg / top3avg (abs)       | 30.8 / 29.8        | 57.8 / 57.5        |
| max_dec (abs)                 | 26.7               | 56.8               |
| endpoint-25 (abs)             | 44.8               | 56.5               |
| rel_pct90 / rel_pct95         | 41.3 / 40.4        | 56.8 / 56.4        |
| rel_top3 / rel_top5 / rel_max | 39.9 / 40.5 / 39.4 | 55.2 / 55.2 / 54.9 |

*(low_army reference on this walk: 47.3% — 0.1pp above #1's 47.2% because this walk starts at t≥1, needing ≥1 delta.)*

**Read.** Absolute worst-tick is big-player-biased and near-useless standalone (~27–31%) but scores high *oracle*; relative is the reverse (good standalone ~41%, lower oracle) — a tension that flags the oracle as the metric to scrutinize (→ #9, #11).

> *Repro: `tmp/elim-baseline-scratch/delta_constructions.py` (full val, `cloud_24k_sub_5k`). Relative denominators differ by construction: endpoint ÷ army at window start; per-tick stats ÷ army just before each tick.*

### 9. Rank + random controls — *[model-free baseline]*
**Description.** Added the controls that calibrate the oracle: the 2nd/3rd-lowest-army players (more of the level ranking) and a uniform-random alive pointer (the null complement — what *any* independent second guess buys).

| candidate       | standalone | oracle(level OR) |
| --------------- | ---------- | ---------------- |
| 2nd-lowest army | 23.8%      | **71.0%**        |
| random pointer  | 28.8%      | 59.2%            |
| 3rd-lowest army | 11.1%      | 58.4%            |
| pct90 (abs)     | 28.5%      | 58.2%            |
| rel_pct90       | 41.3%      | 56.8%            |
| endpoint-25     | 44.8%      | 56.5%            |

**Read.** `oracle(level OR random)` is 59.2% from free coverage alone (one random draw; #11 gives the exact expectation, 59.0%), and *every* rate construction lands below it. The rank controls instead carry real signal: the victim is in the army bottom-2 71% of the time, bottom-3 ≈82% (47.3 + 23.8 + 11.1) — a statement about the army *ranking*, distinct from #10's death-*order* softening even though the magnitudes are close.

> *Repro: `tmp/elim-baseline-scratch/delta_controls.py`.*

### 10. Soft-target eval — *[model-free baseline]*
**Description.** Scored each heuristic's single pick against a *softened* truth: is it among the next-k players to die (k=1,2,3), using per-game death-tick ordering. Also evaluated your relative-endpoint moment here.

| heuristic       | next-1 | next-2 | next-3 |
| --------------- | ------ | ------ | ------ |
| low_army        | 47.3%  | 66.1%  | 74.9%  |
| endpoint-25     | 44.8%  | 62.3%  | 70.7%  |
| rel_pct90       | 41.3%  | 57.6%  | 65.3%  |
| rel_endpoint-25 | 39.7%  | 57.1%  | 65.6%  |
| pct90 (abs)     | 28.5%  | 42.2%  | 50.2%  |
| random          | 28.8%  | 44.7%  | 54.3%  |

**Read.** The lowest-army player is among the next-3 to die 75% of the time — so it isn't looking at the wrong players, it just isn't reliably *first*; the 28pp top-1→next-3 gap is the order-ambiguity a soft target reclaims, and absolute-pct ties random at every k (noise). This is death-*order* softening ("is the pick among the next-k to die"), distinct from #9's army-*rank* bottom-k even though both land near 71–82%.

### 11. Beat-(level OR random) test — *[model-free baseline]*
**Description.** The decisive test: compute the exact expected `(level OR random)` bar in closed form (`mean(level_ok + (1−level_ok)/n_alive)`) and ask which constructions in the full menu beat it.

| candidate                      | oracle(level OR)   | beats bar? |
| ------------------------------ | ------------------ | ---------- |
| **BAR: level OR random**       | **59.0%**          | —          |
| 2nd-lowest army                | 71.0%              | ✅         |
| 3rd-lowest army                | 58.4%              | ❌         |
| pct90 / pct95 / top3 (abs)     | 58.2 / 57.9 / 57.5 | ❌         |
| rel_endpoint-25                | 57.9%              | ❌         |
| rel_pct90 / max (abs)          | 56.8 / 56.8        | ❌         |
| endpoint-25                    | 56.5%              | ❌         |
| rel_pct95 / rel_top3 / rel_max | 56.4 / 55.2 / 54.9 | ❌         |

**Read.** Only `2nd_lowest` clears the bar; no rate construction — absolute or relative, net-change, worst-tick, top-N, or percentile — adds more victim information to the lowest-army rule than a random guess does.

> *Repro: `tmp/elim-baseline-scratch/beat_random.py` (full menu, exact bar). This supersedes the #1/#8 oracle reads.*
