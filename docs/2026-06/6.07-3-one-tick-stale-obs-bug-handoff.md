# Session handoff

**Date:** 2026-06-07

## TL;DR

The pervasive A/B/A/B army alternation we've seen in eval games — two armies advancing one tile each, in strict lockstep, for dozens of moves — is a bug in the **live inference path**, not a property of the policy. `BCPerspective` was feeding the model a one-tick-stale observation: the model never saw the effect of its own previous move, so it kept continuing the army it had moved *two* ticks ago. Fixed this session on branch `fix-stale-live-obs`.

**Consequence worth flagging up front:** every eval-tools head-to-head and sweep run *before this fix* used the stale obs, so their move quality and win-rates are contaminated. The training pipeline was unaffected (the training path reads `snap_t` directly — no double-seed), so checkpoints don't need retraining — but the checkpoints are very likely stronger than the contaminated evals made them look.

## Last session

### What we found

Starting point: while watching head-to-head replays (`run_adhoc`), even the best checkpoints alternate between two armies for long stretches — something humans do only briefly in a tactical pinch, never across most of a game.

- **It's pervasive.** On `data/eval-runs/2026-06-07T09-04-58` (base epoch_005 vs pyramid epoch_004), ~57% / ~53% of *all* moves were the A/B/A/B interleave, about half of them in sustained runs of ≥4 moves, with single runs up to 67 moves long. Present in nearly every game, both checkpoints. (Measured by classifying each move by the smallest `k` with `src[i] == dst[i-k]`: gap-1 = a normal contiguous push, gap-2 = resuming the army moved two moves ago = the interleave.)
- **The interleaved chains are real, productive marches** — two separate armies each covering new ground, not wiggling in place. The bot wasn't stuck; it just refused to finish one push before starting the other.
- **Not sampling noise.** A strict 67-move alternation is essentially impossible under temperature sampling between two near-tied options (it would shatter into random clumps). The policy was *confidently* choosing the alternating move each tick (median top-1 ≈ 0.66 at temperature 1.0, sharpened further at the eval temperature of 0.5). So the cause lived in the policy's mode — i.e. in the logits, and therefore in the observation feeding them.
- **Root cause: a one-tick-stale observation in the live path.** `BCPerspective.reset()` seeds tick 0 (it primes the snapshot + scoreboard history from the t=0 view), and the batched runner *then also* calls `encode()` for tick 0, which appended those rows a second time. That duplicate row shifts every subsequent `build_obs(sim, t)` read back to `snap_{t-1}`. Confirmed directly by replaying a recorded game through the real `BCPerspective`: its internal history equalled `snap_{t-1}` on 321/321 ticks.
- **Why that produces alternation.** Deciding move *t* from `snap_{t-1}`, the model can't see the army it just moved (its own previous move isn't reflected in that board yet); the most-recently-moved army it *can* see is the one from two ticks ago, so it continues that one. Symmetric the next tick → strict A/B/A/B. Fed the *correct* board, the model instead continues the army it just moved (i.e. it chains) — confirmed by reading the logits on fresh vs stale boards for the same game.
- **It's a train/eval mismatch, not inherent BC.** The training obs path (`init_memory` + `build_obs` over the full snapshot array) reads `snap_t` correctly. Only the live path was stale. So this is a wiring bug between two obs implementations — not the behavior-cloning exposure bias we'd hypothesized before finding it.

### Why no test caught it

- The two obs construction paths (the training `dataset` walk vs the live `reset` + per-tick `encode`) re-implement the same accumulation and were **never cross-checked** against each other.
- The one test that drives the live path, `test_parity`, is a frozen-fingerprint regression lock — and its reference fingerprint was captured *with the bug already present*. So it enshrined the buggy behavior as "correct," couldn't detect the bug, and failed on the fix until the fingerprint was regenerated.

### Code changes (branch `fix-stale-live-obs`)

The test and then the fix:

- **Equivalence test + fixture loader.** New `packages/eval-tools/tests/test_obs_path_parity.py`: a *differential* test (no golden values) asserting the training obs path and the live `BCPerspective` path produce identical obs tensors + masks for the same game, tick-by-tick, for both perspectives. Terrain comes from a single ASCII fixture (`training/tests/fixtures/small-1.txt`, now using slot-tagged `g0`/`g1` generals) via a new `packages/game-runner/game_runner/ascii_map.py` loader; the trajectory comes from `sim_core` (the general accumulates, then marches an open lane). Hermetic — needs no checkpoint or DB, so it always runs in CI. Two design choices make it catch this whole class: it drives the live side exactly as the runner does (`reset`, then `encode` every tick *from t=0*), so the sequencing bug is reproduced rather than tidied away; and the board changes every tick, so a one-tick shift can't hide on an unchanged frame. It was committed red — it caught the bug at tick 2, on the army-magnitude / scoreboard / army-delta channels.
- **The fix.** `BCPerspective` now makes `encode()` the *single owner* of per-tick history: `reset()` builds the scaffolding then clears the seed rows, and `encode()` appends exactly one snapshot + scoreboard row per tick, with an assert that fails loudly on any out-of-order or repeat call. This was chosen deliberately over a minimal idempotent guard, which would have *silently tolerated* the redundant call and masked future sequencing bugs. Regenerated `parity_fingerprint.json` (the behavior change is intentional). Greens the new equivalence test.

### Validation

On the parity game (same map, before vs after the fix): interleaved gap-2 moves **49% → 0%**, contiguous gap-1 pushes **≈26% → ≈85%**, for both players. The model plays coherent army pushes once it can see its own last move. This is a single game (the `test_parity` fixture); confirming the effect at scale across a fresh eval run is step (a) below.

## Next steps

Suggestions to explore, not decisions — we'll choose next session. Confidence/urgency below are my estimates.

### (a) Re-run the contaminated evals — *high value, medium urgency*

Every eval-tools head-to-head and sweep before the fix ran on stale obs, so their move quality and win-rates don't reflect the checkpoints. Re-running the 2026-06-07 head-to-head and re-measuring win-rate + gap-2 would both confirm the fix at scale and give us numbers we can trust. Open: how far back to re-validate — just that head-to-head, or also the 5.30/5.31 eval-perf runs and the 6.04 width-eval. The perf/throughput benchmarks are training-side and almost certainly unaffected (the training obs path was correct) — worth a quick confirm rather than a re-run.

### (b) Fix `WorldModel` (eval_bot) — *medium value, low urgency*

It has the identical double-seed pattern, but milder: its returned view is built from the fresh board, so only the `step_memory`-derived fog memory (last-seen, contact, dense-history) is stale-by-one. The clean fix is the same single-owner shape we applied to `BCPerspective`, plus its own equivalence test. This is also the natural moment to weigh the deeper structural option: **merge the two obs paths into one shared encoder** so this class of bug can't recur. The equivalence test guards the divergence for now; de-duplicating would remove the foot-gun entirely — but it's a bigger change, and the training path's `init_memory` is deliberately vectorized (precomputes all scoreboard rows) for hot-loop speed, so the two would need reconciling.

### (c) Promote the alternation probe — *low urgency, cheap*

The gap-analysis probe (per-checkpoint interleave rate, sustained-run length distribution) is a reusable eval diagnostic; moving it into `eval-tools/scripts/` would let us watch this metric on every future eval run. The two bug-specific probes (the stale-obs confirmation and the logit-flip check) were one-off and can be dropped.

## Open questions
