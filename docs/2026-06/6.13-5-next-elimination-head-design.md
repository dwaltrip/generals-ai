# Next-elimination auxiliary head — design sketch

**Date:** 2026-06-13

Implementation-ready design for the first auxiliary head: a per-player, per-frame **time-to-elimination** prediction read off the shared trunk. Intended for a separate implementation session — this is the spec, not the code.

Motivation and lit grounding: [`6.13-4`](6.13-4-aux-head-literature-synthesis.md) (aux-head synthesis), built on the Wave A conclusion that the value head's within-bucket placement signal is starved at sub_5k ([`6.12-4`](6.12-4-wave-a-results-and-synthesis.md)) and the aux-head direction in [`6.09-1`](6.09-1-value-head-direction-and-head-metrics.md). Full reports: [`6.13-2`](6.13-2-aux-heads-fundamentals.md), [`6.13-3`](6.13-3-aux-heads-applied-per-entity-hidden-info.md).

## What this head is, and why this form

For each frame and each player, predict **how soon that player is eliminated**, as an ordinal-bucketed categorical (soft-ordinal targets). The eventual winner falls in a terminal "never" bucket.

The form was chosen over a categorical "who dies next" (single identity) head because it carries strictly more of the signal the value head lacks. Predicting per-player time-to-death recovers "who dies next" as the arg-min, *and* yields a full predicted elimination **ordering** across all alive players — which is the reverse of placement order, i.e. exactly the within-bucket discrimination ("which survivor wins") that every Wave A value-head config failed to learn. It is also per-frame-varying (a countdown), so it sidesteps the memorization risk a piecewise-constant identity target carries, and its targets are free from the replay's elimination schedule.

This is an **auxiliary** head, not a value-head redesign: the value head predicts the *perspective's own* final placement; this head predicts the *whole field's* elimination dynamics. Its job is to shape the shared trunk (which the BC policy and the future PPO critic both inherit), not to replace the value target.

Precedents (verified, see [`6.13-4`](6.13-4-aux-head-literature-synthesis.md)): OpenAI Five's net-worth-rank head (per-entity end-of-game ordering, value-style, off a shared trunk), ToMnet's per-object future-event head, Agent-Modeling-as-Auxiliary (predicting others enriches a shared conv trunk), Terminal Prediction (dense per-frame time-to-terminal regression as a trunk-shaping aux).

## Decisions locked

- **Target:** per-player time-to-elimination, ordinal-bucketed, soft-ordinal targets (τ), masked to *real, currently-alive* players.
- **Bins:** 8 classes, geometric, with the top bin merged — edges `(10, 20, 40, 80, 160, 320, 640)`, giving `[0,10) [10,20) [20,40) [40,80) [80,160) [160,320) [320,640) [≥640-or-never]`. (Revised from the original 9-bin `(5,…)` scheme by merging the starved bottom two bins; see [`6.13-6`](6.13-6-elim-head-stage0-corpus-measurements.md) for the Stage 0 stratified evidence.)
- **"never":** the top ordinal class (merged with "dies ≥640 ticks out"); see *Known limitations*.
- **Head shape:** `Conv2d(C → 8·n_bins)` → masked global average pool → `[B, 8, n_bins]`. No ReLU. Global pool (not footprint-masked) for v1.
- **Gradient into trunk:** on, at a small weight `ν = 0.15` (the head's purpose is to shape the trunk; `stop_gradient` is the documented fallback if it harms policy/value).
- **`τ_elim = 1.0`** (rationale under *Defaults grounding*).
- **Arch-gated:** the head is constructed only when `elim_head_enabled`, so every existing checkpoint still loads `strict=True`.

## Target definition

Per-game precompute (once per sim load, alongside the scoreboard precompute):

- `real_slots` — the slots that actually played: `np.unique(sim["ownership"][0])` filtered to `>= 0`. **This mask is load-bearing.** The obs encoder always runs at `P=8` and `opp_slots` always yields 7 raw ids from `range(8)`, but generals.io FFA games can start with fewer than 8 players (no player-count filter in `filters.py`). A non-existent slot is absent from `death_events`, so without this mask it would fall through to the winner sentinel and be mislabeled "alive, never dies" on every frame — flooding the loss and teaching the trunk the inverse of the elimination-ordering signal.
- `death_by_slot[s]` for `s ∈ real_slots`: elimination timestep from `sim["death_events"]` (rows `(timestep, slot)` — confirm column order at impl), or a **large finite int sentinel** (e.g. `T + max_edge`; not `np.inf`, the array is integer-typed) for the winner — the one real slot absent from `death_events`. `real_slots` resolves the winner-vs-phantom ambiguity: the winner is *in* `real_slots` and absent from `death_events`; a phantom is *not in* `real_slots`.

In `encode_frame`, for each canonical channel `i ∈ 0..7` (channel 0 = perspective via `perspective_slot`; channels 1..7 via `opp_slots[i-1]`, the per-opp ordering the obs uses):

- `raw = perspective_slot if i == 0 else opp_slots[i-1]`
- `alive = (raw in real_slots) and death_by_slot[raw] > t` — the `> t` matches the existing aliveness convention (a player eliminated at `t` counts dead at frame `t`).
- if alive: `Δ = death_by_slot[raw] − t`; `bin = np.digitize(Δ, edges, right=False)` (winner's large Δ → bin 7, the top class, merged with "never"; no special-casing). Minimum live `Δ` is 1 (a player dead at `t` is masked at `t`), so bin 0 = `[0,10)` covers `Δ ∈ {1..9}`. `alive_mask[i] = True`.
- else (dead or phantom): `alive_mask[i] = False`, `bin = 0` (ignored by the mask).

New sample keys (collate stacks to `[B, 8]`): `elim_bin_target` int64 `[8]`, `elim_alive_mask` bool `[8]`.

Channel 0 (self) is always alive within the perspective's own trajectory (frames stop at the perspective's elimination — `dataset.py` `end_t = min(T-1, elim_t)`), so it always carries a target: the perspective's own survival horizon (a finite bin near trajectory end for non-winners, the "never" bin for winners). Two consequences: (1) it guarantees `alive_mask.sum() ≥ B` on every batch, so the loss divide cannot hit zero; (2) channel 0 is a *different estimand* from the opponent channels (own vs. opponent survival; it never carries a "dead" mask in-trajectory, and "never" fires only for winners), so a per-channel stratified floor (deferred) must treat it separately rather than pooling it with channels 1–7.

## Bins and known limitations

The geometric scheme concentrates resolution at the short end, which is where the value-relevant signal lives — imminent eliminations are the high-information frames, and they cluster in the late game / endgame, exactly the regime where the value head is starved. The coarse top end captures "safe for a long time / wins."

**NOTE — the top-bin merge.** Merging "dies ≥640 ticks out" with "never" loses information only in a minority regime: a slow endgame where a losing player survives 640+ more ticks before dying lands in the same bin as the winner. In typical games the field is down to 2–3 players well within ~640 ticks, so the finite `Δ ≥ 640` tail is sparse and the bin is dominated by genuine winners; the late-game discrimination we care about (winner = "never" vs. soon-loser = a low bin) is preserved. Revisit if the stratified-by-players-alive reads show the top bin doing heavy lifting at 2-alive — the refinement is splitting `≥640` from `never`, or making bins game-phase-conditional.

**NOTE — absolute ticks vs. game phase.** Bins are absolute ticks. Time-to-elimination is correlated with game phase (players-alive), and the trunk already has players-alive available, so the head can condition on phase. Absolute bins keep "imminent danger" meaning game-length-independent. Normalized-by-game-length bins are a deferred alternative.

**NOTE — tick scale unmeasured.** Edges were set from domain knowledge, not a corpus death-Δ histogram. Harmless: empty/rare bins simply get no gradient. The histogram measurement is folded into Stage 0 below — it also feeds class weighting.

## Model

### `ModelConfig` (`model_config.py`)

New fields (validated in `__post_init__`, matching the existing idiom — `ValueError` naming the offending value):

- `elim_head_enabled: bool`
- `elim_bin_edges: tuple[int, ...]` — strictly increasing, positive. `n_bins = len(edges) + 1` is derived (single source of truth; the head sizes its output from it).

`MODEL_CONFIG_DEFAULTS`: `elim_head_enabled=False`, `elim_bin_edges=(10,20,40,80,160,320,640)`. The head is opt-in; the experiment config sets `arch.elim_head_enabled=True`. `validate_partial` derives valid field names from `fields(cls)`, so new fields are auto-covered — no edit there.

### Backward-compat — the load-bearing constraint (`checkpoint.py`)

The head adds parameters, so a checkpoint with it has extra `state_dict` keys. Add the same fields to **`LEGACY_ARCH`** with `elim_head_enabled=False` and `elim_bin_edges` as a **hardcoded literal tuple** (not aliased to `MODEL_CONFIG_DEFAULTS` — per the "DO NOT EDIT / divergence-allowed" contract at the top of `checkpoint.py`). `_arch_for_load` back-fills missing keys from `LEGACY_ARCH`, so every pre-elim checkpoint reconstructs as "no elim head" and `load_state_dict(strict=True)` still passes. This is the entire reason the head is arch-gated rather than always-constructed.

### `BCModel` (`model/bc_model.py`)

Construct `self.elim_head` only when `cfg.elim_head_enabled` (no unconditional parameter/buffer in the head's module path, so a disabled model has zero extra `state_dict` keys). `forward` adds `"elim_logits"` to the output dict only when the head exists; everything downstream presence-gates on that key. (`inference.py` reads named keys explicitly, never iterating the dict, so the extra key is inert there — no inference edit.)

### Head module (`model/heads/elimination.py`, new)

```
trunk [B, C, H, W]
  → Conv2d(C → 8·n_bins, k=3, pad=1)     # per-(player, bin) per-cell evidence
  → × valid_mask
  → masked global avg-pool over the unpadded board   # like PassHead's pool
  → reshape [B, 8, n_bins]               # per-player bin logits
```

No ReLU (we pool straight to logits; a ReLU would discard signed evidence). Global masked-avg-pool, not footprint-masked, for v1. ~74k params at C=128, n_bins=8 — modest vs. the policy head's ~1.1M; Wave A found head capacity is not a strong lever, so the head is deliberately minimal. Alive-masking is applied at loss time, not in the head (the head always emits all 8 channels). Knobs flagged for later A/B: ReLU, footprint/attention pooling, deeper head.

## Loss (`loss.py`)

`LossConfig` new fields: `lambda_elim: float = 0.0`, `elim_target_tau: float = 0.0`, and `elim_bin_weights: tuple[float, ...] | None = None` (optional per-bin CE weights for class imbalance — see Stage 0 / staging; `None` = unweighted).

`bc_loss` computes the elim term **only if `"elim_logits" in model_out`** (a disabled head is a clean no-op; existing consumers unaffected):

- soft targets: reuse `_soft_target_kernel(elim_target_tau, n_bins, device)` (cached per `(τ, n_classes, device)`; the value and elim heads now share `n_classes=8` but differ in τ — 0.6 vs 1.0 — so their cache entries don't collide). `kernel[elim_bin_target]` → `[B, 8, n_bins]`.
- per-player CE: reshape logits to `[B·8, n_bins]`, targets likewise; `F.cross_entropy(reduction="none", weight=elim_bin_weights)` → `[B·8]` → reshape `[B, 8]`; multiply by `elim_alive_mask` (cast to the loss dtype, broadcast over `[B, 8]`); `sum / alive_mask.sum().clamp(min=1)` → mean over alive (player, frame) pairs. The `clamp(min=1)` mirrors the policy-CE safe divide; it is defensive here (channel 0 guarantees ≥1 alive per frame) but cheap insurance.
- returns `elim` (hard CE against the bin label — the reporting metric) and `elim_soft` (the trained objective; equals `elim` at τ=0), plus `n_elim` = `alive_mask.sum()` (the accumulator weight).
- `total += lambda_elim · elim_soft`.

This mirrors the value head's `value`/`value_soft` split, with the per-player masked-mean reduction added.

`LossAccumulator` — three concrete edits, easy to under-do:
1. add `lambda_elim` to `LossConfig` (above) — `summary()` reads weights off `self.cfg`.
2. add `sum_elim` / `sum_elim_soft` fields and a **third weighted-mean denominator `n_elim`** (distinct from `n_non_pass` and `n_samples`); `update()` folds `sum_elim += elim.item() * n_elim_batch`, and `summary()` divides `sum_elim` by the running `n_elim`, not by `n_samples`.
3. the `total` line in `summary()` is a **hardcoded literal expression** (`policy + cfg.lambda_value*value_soft + cfg.mu_pass*pass_`) — it must be edited to add `+ cfg.lambda_elim * elim_soft`, or the component-sum identity silently breaks for elim runs. Presence-gate so non-elim runs are unchanged.

## Plumbing

- **`TrainConfig` (`train_config.py`):** add `lambda_elim: float = 0.0`, `elim_target_tau: float = 0.0` (recipe fields; defaults reproduce historical "no elim head"). Build into `LossConfig` at the `loss_cfg = LossConfig(...)` site in `train.py`. Validate `>= 0`. Add a consistency check: `lambda_elim > 0` requires `arch.elim_head_enabled` (no weight on an absent head). Same resume-legacy-pinning caveat as `lambda_value`/`value_target_tau` applies — defaulting to 0 keeps pre-field runs correctly described.
- **Per-batch JSONL (`train.py` `log_batch`):** add `elim` / `elim_soft` when present.
- **Per-epoch JSONL:** flows automatically via the `val` summary.

## Metrics (`eval/run.py`, `eval/metrics.py`)

`run_val` pulls `elim` / `elim_soft` from `acc.summary()` and feeds a new **`ElimMeter`** (in `metrics.py`, sibling to `PolicyEntropyMeter`), accumulating over alive (player, frame) entries:

- **top-1 bin accuracy** — argmax bin == target bin.
- **prediction entropy** — the collapse check, over the per-player bin softmax.
- **soft-target marginal floor** — the head's trivial baseline. **Use the soft floor, not a hard-CE floor.** At τ=1.0 a head that knows the task still pays a softness tax in *hard* CE (~0.4–0.5 nats over the 8-class axis), so `elim` (hard CE) `< hard floor` is a known false-negative — the same tax confound the value-head arc had to fix (6.12-4 closure item #2). The self-consistent in-loop check is `elim_soft < soft-marginal-floor` (the CE of predicting the soft-target marginal). The hard-CE-vs-tax-adjusted-floor read is reserved for the stratified report (deferred; the value arc needs that tool anyway).

New `run_val` return keys: `elim_soft`, `elim` (recorded but not the health metric at τ>0), `elim_top1`, `elim_soft_floor`, `elim_pred_entropy`. All presence-gated so non-elim runs are unchanged.

## Defaults grounding

- **`ν = 0.15` — a sweep start, not a cited value.** OpenAI Five specifies its aux-head trunk-gradient weight only as "very small" (1912.06680, Appendix D); no scalar appears in the text or hyperparameter table. The transferable precedent is structural (one head leaks a small gradient to the trunk, the rest `stop_gradient`), which we adopt; the magnitude is ours to sweep. Also consistent with the Wave A damage law (trunk harm tracks the value gradient's magnitude) — keep the new pressure modest.
- **`τ_elim = 1.0` — softer than the value head's 0.6, on two independent signals.** (1) HL-Gauss (Farebrother 2024, 2403.03950) uses σ ≈ 0.75 bin-widths and reports the optimum is robust and ~independent of bin count ("pick a sensible value") — softer than τ=0.6's near-peaked kernel. (2) Wave A found `tau1.0` was the strongest value-head cell ([`6.12-4`](6.12-4-wave-a-results-and-synthesis.md)). Both lean softer than 0.6. Tempered by our coarse 8-bin axis (HL-Gauss tuned σ on 21–201-bin axes, where wide smoothing is relatively narrow; on 8 bins over-softening washes toward uniform), so τ=1.0 rather than chasing HL-Gauss's literal width. Cheap to A/B once the head exists. SORD (Diaz & Marathe 2019) uses no separate temperature — smoothing is the distance metric's scale; not directly portable.

## Success criteria and staging

The head's purpose is trunk transfer to the value head, so the primary criterion is the **value head's within-bucket stratified reads, with vs. without the elim head** (the Wave A measurement, repurposed) — does the below-conditional-floor margin in the 2-/3-alive buckets improve when the elim head is present? Plus **do-no-harm to policy/value** (val_policy not degraded), and a **gradient-conflict diagnostic** (cosine between the elim-head trunk gradient and the policy/value trunk gradient; persistent negative cosine = real conflict, candidate for the `stop_gradient` fallback or PCGrad).

**Confound to keep in view (don't over-read Stage 2).** Turning the elim head on adds a *second* trunk-gradient source at ν=0.15. Wave A's damage law says trunk health tracks gradient *magnitude*, and the aux-task literature (2204.00565) shows even random/misaligned aux targets improve representations — so a positive within-bucket movement is confounded between "elimination *signal* enriched the trunk" and "extra gradient *pressure* perturbed it." A positive Stage-2 result is therefore *suggestive, not attributive*. The clean attribution requires a degenerate/shuffled-target control arm (same ν, no real signal) — carried as a deferred follow-up, run only once there's a positive signal worth attributing.

The elim head's own health is the nearer milestone: beats its soft-marginal floor, no prediction-entropy collapse, bounded train−val gap.

Staging:
- **Stage 0 (read-only corpus measurement, before any run):** (a) player-count distribution — the blast radius of the phantom-slot mask and a check that sub-8 games are handled; (b) death-Δ histogram — confirms the top bins are populated, validates the bin edges, and is the input to inverse-frequency `elim_bin_weights`. Both are cheap and de-risk the run.
- **Stage 1 (sub_5k, cheap):** does the head learn its task above the soft floor, do no harm to policy/value, no collapse, bounded gap? Exercises all new plumbing before committing compute. (Within-bucket *value* transfer is not expected to be readable here — Wave A showed within-bucket value signal only appears at scale.) **Pre-registered:** a Stage-1 floor miss triggers the class-weighting and footprint-pooling A/Bs *before* concluding the target itself is wrong — the abundant "safe for a long time" bins drowning the rare imminent-death bins (class imbalance) and the global pool washing out localized evidence are the two leading non-target suspects.
- **Stage 2 (24k):** does the value head's within-bucket signal move? The actual transfer test; needs the scale where within-bucket signal can appear (read with the confound caveat above).

## Deferred / fast-follow

- **S3 attribution control arm:** an elim head at the same ν with a degenerate/shuffled target, to isolate the elimination *signal* from raw trunk-gradient pressure. Run once Stage 2 shows a positive signal worth attributing.
- **Stratified dump** (`eval/dump.py` `FrameRecordCapture`): add `elim_probs` / `elim_ce` / `elim_bin_target` / `elim_alive_mask` columns + the report extension. Targets are already in `host_batch` once added in `encode_frame`.
- **Tax-adjusted hard-CE floor** + **conditional floor by players-alive** (the value head's conditional-floor analog; the value arc needs the tax-adjusted floor regardless); per-channel breakdown (treating channel 0 separately, per *Target definition*).
- **"never" as a separate (non-ordinal) class** — A/B against the merged-ordinal choice if the head shows promise. Driven by whether "identify the winner" sharply matters.
- **Footprint / attention pooling** A/B; ReLU; deeper head.
- **Top-bin split** (`≥640` vs `never`) and **game-phase-normalized bins**, if the stratified reads show the merge/absolute-tick scheme losing late-game resolution.
- **Time-to-elimination as regression** (Terminal-Prediction form) as a sibling A/B against the bucketed-categorical form.
