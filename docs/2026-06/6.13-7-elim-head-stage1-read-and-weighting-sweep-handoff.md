## 1. The thread this sits on (the past ~week)

The strategically hard thing for the bot to understand is *who is winning* — specifically, among the players still alive, which one goes on to take 1st. Call it **within-bucket discrimination**: the "bucket" is how many players are still alive; "within" is telling the survivors apart. Survivor-*counting* (how many are left) is easy and the model learns it readily; survivor-*ranking* (who outlasts whom) is the hard, valuable signal.

- **The value head** predicts the perspective player's final placement (1st–8th, 8 classes). **Wave A** ([`6.12-4`](6.12-4-wave-a-results-and-synthesis.md)) swept its knobs and reached a clear conclusion: we can add the value head *without hurting the policy* ("do-no-harm," solved two independent ways), but **no knob setting makes it learn the within-bucket signal** at our small data scale (`sub_5k` ≈ a 5k-game subset). Every tamed config learns only survivor-counting, which a baseline (the "conditional floor") already gives away. The within-bucket question stopped being a knob question and became a **data-scale** question (maybe it only emerges at 24k+ games) and a **target-design** question (maybe one placement label per game is too sparse to teach ranking).

- The target-design branch is the **aux-head direction** ([`6.13-4`](6.13-4-aux-head-literature-synthesis.md) synthesizes the lit). Idea: instead of leaning on the value head's one-label-per-game target, add an *auxiliary* head with a dense, per-frame signal whose job is to shape the **shared trunk** — the convolutional body that both the BC policy and the future PPO critic read from. A richer trunk helps everything downstream, not just the value head.

- The first aux head is the **next-elimination head** ([`6.13-5`](6.13-5-next-elimination-head-design.md) is the design). For each of the 8 player slots, every frame, predict *how soon that player is eliminated*, bucketed into 8 ordinal time bins (`[0,10)` ticks, `[10,20)`, …, `[≥640/never]`). The point of this target: predicting per-player time-to-death is the same as predicting the **elimination order**, which is the reverse of final placement — i.e. it is *exactly* the within-bucket "who outlasts whom" signal the value head couldn't learn, but supplied densely (every frame, every player) instead of once per game.

- Implementation landed across 6.13 (steps 1–6). **Stage 0** ([`6.13-6`](6.13-6-elim-head-stage0-corpus-measurements.md)) measured the corpus and set the 8-bin edges and the class-weight vectors we're now using.

So the chain is: *value head can't learn within-bucket at sub_5k → add an aux head with a denser, ranking-shaped target → see whether it learns, and whether it shapes the trunk enough to help the value head.* The work below is the front half of that.

## 2. Stage 1 — what the first elim runs showed

Stage 1 = three sub_5k cells (`data/training/sweeps/2026-06-13-elim-head-stage1/`): two with the elim head on at trunk-gradient weights `lambda_elim` ∈ {0.05, 0.15} (both on the standard λ_value 0.5 / τ0.6 value backdrop), and one closure cell (value λ0.1+τ0.6, elim off). Results:

- **Do-no-harm: clean.** Both elim cells' matched-epoch-3 val_policy (0.9649 / 0.9667) sit inside the 3-seed value-head anchor band (0.964 ± 0.005). The value head also stayed healthy. So adding the elim head at either weight didn't damage the policy — the first bar is met.

- **Head health: marginal, and the same "data-scale" shape the value head has.** The elim head beats its own trivial baseline (the soft-marginal floor) only *barely* on validation (margin ~+0.01–0.03 nats, best at epoch 4) but *clearly* on training (~+0.11–0.13). That train-learns / val-flat split is the signature of a signal the model can fit but can't yet generalize at this data scale — the same wall the value head hit. No prediction-entropy collapse; the train–val gap is mild.

- **Closure cell confirmed a separate open item.** λ_value 0.1 + τ0.6 lands the policy at the "trunk at peace" ceiling (0.9601 ≈ the λ=0 reference 0.9615) *with* a working (below-floor) value head — the config-of-record Wave A predicted but never ran.

The marginal val signal raised the obvious question — *is the head learning a little of everything, or a lot of the easy part and none of the hard part?* — which the new tooling (next section) answered.

## 3. The diagnostic tooling we built last session

The per-frame **stratified val dump** (`eval/dump.py` capture + `scripts/stratified_val_loss_analysis.py report`) already existed for the value head; last session extended it to the elim head (committed as "Elim head: stratified val-dump capture + report"). It now captures, per checkpoint, the elim head's full per-(player, frame) bin distribution + CE + target + alive mask, and the `report` subcommand prints three elim tables:

- **per-true-bin** — for each true time-bin, how often the head's top prediction lands on it (recall), mean CE, prediction entropy. This is the *which-bins-does-it-learn* view.
- **by players-alive** — the same metrics stratified by how many players remain.
- **self vs opponents** — channel 0 (the perspective's own survival) is a different estimand from the 7 opponent channels, so they're reported apart.

Running it on the Stage-1 `elim-lam0.15` checkpoint (only a 5% subsample, so the numbers are approximate, but the pattern is clear) gave the key Stage-1 finding:

**The head starves the imminent-death bins.** Per-true-bin recall was ~67% on `never` and double-digit on the common mid bins, but **~8% / 0.4% / 2.5% on bins 0–2** (the imminent bins, `<40` ticks to death) — where it also pays its highest CE (~3 nats, confidently wrong). This is the **class-imbalance lazy-head** signature: the imminent bins are ~10× rarer than `never` pooled (and steeper in the late game), so an unweighted loss is minimized by predicting the common bins and eating the small total penalty on the rare ones. And the rare imminent bins are *the value-relevant part* (imminent elimination ordering = the within-bucket ranking). The self-vs-opp split also validated the wiring: self ~51% `never` vs opp ~19%, consistent with Stage 0's 47.6% / 19.4%.

(Note: that 5% offline pass overwrote `elim-lam0.15`'s epoch-4 in-training dump with a subsample — a full-frac offline re-dump restores it and gives a clean unweighted baseline to compare the weighting cells against; see §4.)

## 4. Reading the weighting sweep when it lands

The sweep (`data/training/sweeps/2026-06-13-elim-head-weighting/`) is the cheap, pre-registered remedy for that starvation, and a discriminator between two explanations for it. It's one knob, three points: `elim_bin_weights = (1/freq)^β`, mean-normalized, with **β ∈ {0.5 (sqrt, ~3.2× span), 0.75 (~5.7×), 1.0 (raw, ~10.2×)}**. Bigger β upweights the rare imminent bins harder. Everything else equals the Stage-1 `elim-lam0.15` cell, so weighting is the only variable.

**Convenience vs Stage 1:** these runs were trained on current code (the dump tooling is committed), so their **in-training val dumps already carry elim columns, at full-frac** — unlike the Stage-1 runs, which predate the tooling. So once fetched you can go straight to `report`, no offline re-dump needed.

How to read it:

1. **Fetch:** `./data/training/sweeps/2026-06-13-elim-head-weighting/fetch.sh` (pulls checkpoints + the `analysis/` dumps).
2. **Imminent-bin recall (the headline):** `./packages/training/scripts/stratified_val_loss_analysis.py report data/training/sweeps/2026-06-13-elim-head-weighting/runs/elim-w0.75 --epochs all`, and look at the **per-true-bin `top1 (recall)`** column for bins 0–2. Does it climb above the unweighted Stage-1 baseline (~8% / 0.4% / 2.5%)? Does it climb with β? For a matched full-frac unweighted baseline, offline-dump the Stage-1 cell: `stratified_val_loss_analysis.py dump data/training/sweeps/2026-06-13-elim-head-stage1/runs/elim-lam0.15 --epochs all` (this also restores its overwritten epoch-4 dump).
3. **Do-no-harm:** `compare_runs.py --no-summary` for matched-epoch-3 val_policy vs the anchor band (0.964 ± 0.005). Watch the higher-β cells especially — heavier weighting perturbs the trunk gradient more, so it's the most likely to cost policy.
4. **The β curve / what each shape would mean** (hypotheses, to be read off the data, not assumed):
   - *Recall rises with β while policy stays in-band* → the starvation was class imbalance, weighting is a real lever, and there's a β to carry into a 24k run. The sweet spot is plausibly the middle, since sqrt may under-correct and raw may over-correct.
   - *Even β=1.0 doesn't lift imminent recall* → it's **not** (just) imbalance. Then the live suspects shift to data-scale, the global-average pooling washing out localized evidence (a pre-registered footprint-pooling A/B exists for this, not yet built), or the target itself.
   - *High β lifts imminent recall but breaks do-no-harm, or tanks the common/`never` recall* → over-correction; the head has been pushed too hard toward the rare bins. Check the common/`never` recall columns, not just the imminent ones.

**Two interpretation gotchas under weighting** (worth internalizing — they're the kind of thing that quietly misleads):
   - The `elim` / `elim_soft` numbers in `epochs.jsonl` are now **weighted** CEs, while the head's `elim_soft_floor` (the soft-marginal floor) is **unweighted** — so the "beats the soft floor" margin is no longer apples-to-apples, and the raw `elim` numbers are **not comparable across β cells** (each is weighted differently). Lean on **per-bin recall** (top-1 — a property of predictions, independent of training weights) and **do-no-harm** as the clean reads. A weighted floor would restore the margin comparison (a small future tooling item).
   - The report's per-bin **CE** column is computed *unweighted* by design, so per-bin CE *is* comparable across cells — but recall is the more legible headline.

## 5. The open map (questions, not a plan)

These are the live questions and what each result would *imply* — not a chosen path.

- **Is the sub_5k starvation imbalance or data-scale?** The weighting sweep is the discriminator (§4). Both outcomes are informative — one says "weighting is the lever," the other says "the lever is elsewhere (scale / pooling / target)."

- **Does a *working* elim head actually transfer to the value head?** This is the question that actually matters, and it's a **24k (Stage 2)** question — within-bucket *value* signal isn't visible at sub_5k for either head, so transfer can't be read here. A Stage-2 design is on the table but un-launched: one with-elim 24k run reusing the existing **6.10 run** (`data/training/runs-cloud/2026-06-10T09-20-33Z`; cloud_24k.json, λ_value 0.5, τ0.6, 6 epochs, seed 0) as the *without-elim* arm, since the test is a with-vs-without delta and that run's config matches everything except the head — with the caveats that it's single-seed and cross-code (it predated the session's code, though the value/policy path is unchanged because the head is arch-gated). The weighting result is meant to inform what elim config that run carries — including whether to weight at all.

- **The Stage-2 attribution confound** (carry it forward): turning the elim head on adds a *second* trunk-gradient source. Even if value within-bucket signal improves, the result is confounded between "the elimination *signal* enriched the trunk" and "the extra gradient *pressure* perturbed it" — the aux-task literature shows even random/misaligned aux targets can improve representations. A clean attribution needs a shuffled-target control arm (same weight, no real signal), flagged as a deferred follow-up to run only if Stage 2 is positive.

- **ν (`lambda_elim`) magnitude.** 0.15 is validated do-no-harm; whether to push it higher for more trunk pressure at 24k is open. Note sub_5k can only confirm do-no-harm at a given ν, not transfer — so a ν decision for Stage 2 is partly a judgment call.

- **The meta-pattern worth keeping in view.** We've now hit the same wall — discriminative / within-bucket signal absent at sub_5k — with *both* the value head and the elim head. The honest current hypothesis is that this is fundamentally a data-scale phenomenon, and the sub_5k work is plumbing + de-risking for the 24k runs where the real question gets answered. The aux-head bet is that a *denser, ranking-shaped target* changes that calculus where knob-tuning the value head didn't. That bet is genuinely unresolved; the weighting sweep + a Stage-2 run are how it gets tested, not assumed.

### Mini-glossary (terms used above)

- **trunk** — the shared conv body feeding all heads; the thing aux tasks are meant to improve.
- **within-bucket discrimination** — ranking the survivors (who wins among those still alive), vs merely counting them. The hard signal.
- **conditional floor** — the loss a baseline pays by predicting a bucket's label frequencies; beating it means the model knows something *beyond* bucket membership.
- **soft-marginal floor** — the elim head's analogous trivial baseline (predict the smoothed class marginal); its in-loop health check is "beat this."
- **do-no-harm** — adding the head doesn't degrade the BC policy.
- **ν / `lambda_elim`** — weight on the elim loss = how hard its gradient pushes the trunk.
- **β** — exponent on inverse-frequency class weights; the single knob this sweep varies.
- **softness tax** — at τ>0 the targets are smoothed, so even a perfect head pays extra hard-CE; it confounds CE-vs-floor margins but not recall/entropy.
