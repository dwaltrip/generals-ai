# Argmin toy: surrender re-admission — design

*Date: 2026-06-18. Status: design note (Phase 0c). Designs the surrender re-admission slice of the argmin toy: drop the MVP surrender filter, study the full population where `alive ≢ army>0`, and treat the result as a clean single-frame proxy for a target-definition decision the elim-head faces. Grounds the surrender state machine in the sim, fixes the head taxonomy, sets the encoding × target grid with measured ceilings and per-cell predictions, and lists the build steps and risks. Builds on 6.18-3 (grid read, which chose this direction), 6.18-1 §12 (the original surrender follow-up sketch), and 6.17-1 (experiment design).*

## 1. Framing

The MVP filtered surrender frames so that `alive ≡ (army > 0)` held and the encoding ladder was about *optimization difficulty* (the notch). Re-admitting them adds a third player status — out of the game yet holding army on the board — where army alone is no longer a sufficient statistic for "who's the weakest live player." That turns the encoding question from optimization difficulty into **information sufficiency**: do the inputs even carry what's needed to exclude the right players?

This is more than pedagogy. The toy's label-set choice (below) is a faithful single-frame proxy for a decision the **elim-head** has to make about its target, and the surrender population is where prod's own obs encoding is provably blind. The goal of this slice is to establish the encoding-sufficiency facts cleanly, so they inform that decision in a later session.

### Head taxonomy (for accuracy of the connection)

The BC agent carries four heads. Stating them so this note doesn't mischaracterize the downstream:

- **pass head** — make a move this tick or not.
- **policy head** — which move.
- **value head** — the perspective player's final **placement** (1st–8th in FFA). Built for the later PPO self-play phase; rides along as an auxiliary signal during BC. *Not* a positional value net.
- **elim-head** — identity of the **next player eliminated/captured**. Purely auxiliary, and valued because it is far easier to debug and analyze than placement — the more debuggable head. Its target is what the surrender state machine makes ambiguous.

## 2. The surrender state machine (verified from `sim-core`)

A player who leaves moves through distinct states; the replay's `afks` list carries two entries (`process_pending_afks`, `state.rs`):

```
alive ──surrender (T_s)──▶ surrendered-present ──┬── captured by another (T_c < T_n) ──▶ eliminated
        kill_player:                  ~alive,     │   capture_player: tiles→captor,
        alive=false, DeathEvent,       army>0,    │   CaptureEvent, army→0
        tiles+general remain           general    │
                                       capturable  └── neutralize (T_n) ────────────────▶ eliminated
                                                       try_neutralize_player: tiles→neutral,
                                                       NeutralizeEvent, army→0
```

Verified specifics:
- Surrender fires a **DeathEvent** at `T_s` (so `alive` reads false from then on) but does **not** touch tiles — `generals[p]` stays valid, army stays on the board.
- During `[T_s, T_n)` the player is exactly `~alive & army>0` with a live, undefended general that nearby players can capture — and plausibly a frequent next-capture target (an expectation, not measured here).
- A capture mid-window pushes a **CaptureEvent** and transfers tiles (army→0); because the player is already dead, `capture_player` does **not** re-kill (no second DeathEvent).
- Normal capture-while-alive is atomic within a tick (tiles transfer + kill in the same step), so it never produces a transient `~alive & army>0` frame. Therefore **`~alive & army>0` cleanly identifies surrendered-present players**, and every other dead player (captured or neutralized) is at `army==0`.
- Throughout, "army→0" / "army==0" means the per-player **total** (sum over owned tiles — the quantity the toy uses), which reaches 0 because no tile stays owned: `try_neutralize_player` and capture reassign *ownership* but do not zero `armies[i]` per cell.

## 3. Two targets — the elim-head's ambiguity, made concrete

"Next eliminated/captured" is ambiguous exactly on surrendered-present players, and the two readings map onto two label sets for the toy's argmin:

| elim-head target reading | a surrendered-present player is… | toy set (argmin over) |
|---|---|---|
| **next DeathEvent** (current `elim_head_debug` target, `death_events`-based) | already eliminated at `T_s` → not a future candidate | **`alive`** (excluded) |
| **next board-removal** (capture/neutralize) | still on board, prime capture target → a strong candidate | **`army>0`** / general-present (included) |

Both targets are **first-class**. `alive` = "weakest agent still playing"; `army>0` ≈ general-present = "weakest player with army still on the board." `army>0` is "degenerate" only in its *encoding requirement* — set membership is army-derivable, so the encoding axis collapses under it — while the question it poses is a genuinely different, meaningful one.

What transfers to the elim-head is the **set/encoding question** — can the inputs support excluding surrendered players? — not the predictive target itself (the elim-head predicts real eliminations, the toy computes argmin-of-army as the heuristic stand-in). The toy informs the target decision; it does not pre-empt it.

## 4. The encoding axis (status-sufficiency ladder)

Four encodings, on the full (unfiltered) population. All but `capture_status` are derivable from `(alive, army_sim)` we already have.

- **`none`** — army only. Eliminated players (`army==0`) are excludable via the army-zero notch; surrendered players (`army>0`) are **indistinguishable from live**.
- **`capture_status`** — prod's actual channel (`opp_N_captured_by`, capture-based: `0=alive`, captor index otherwise). Flags general-captures; blind to surrender. (Needs the new `captured` deriver; §6.)
- **`boolean`** — the true `alive` mask as a channel (= the MVP's `explicit_mask`). Excludes all not-alive.
- **`categorical`** — 3-way alive / surrendered / eliminated, derivable from `(alive, army>0)`.

**`none ≡ capture_status` for this task (a provable identity, not just a hypothesis).** A captured player has `army==0` (tiles transferred), so a `none` model already excludes them via the zero-notch — the capture flag adds nothing. (The real prod channel encodes *which* opponent captured — `1..7` — but that identity is irrelevant here: a captured player is army-0-excluded regardless of *who* took them, so collapsing the channel to a binary captured/not flag is lossless for this argument.) A neutralized player is also `army==0` and is *not* flagged by `capture_status` (shown `0=alive`), so it still needs the notch. A surrendered-present player (`army>0`) is shown `0=alive` — invisible exactly where it would matter. So `capture_status` carries zero discriminating power over raw army for argmin-over-alive. Prediction: the `none` and `capture_status` cells land on the same ceiling (possibly by different internal mechanisms — the army-zero notch vs the capture flag). This *is* the core prod statement — **prod's status channel cannot help exclude surrendered players.**

## 5. Measured ceilings (`cloud_24k_sub_5k` val, 112,975 frames / 250 games)

- **Surrender-frame incidence: 6.58%** (7,437 frames) — ≈1.8× probe_500's 3.71% (cloud games run longer, see more eliminations).
- **`none` irreducible error** under the `alive` target — the fraction where the on-board argmin (smallest `army>0`) is a surrendered player, so a perfect notch-carving `none` model still misranks:

| population | irreducible error | `none` accuracy ceiling |
|---|---|---|
| all frames | 3.06% | ~96.9% |
| mixed (`n_alive < 8`) | 3.76% | ~96.2% |
| **surrender subpopulation** | **46.5%** | **~53.5%** |

Aggregate dilutes the effect to ~3 pts; the signal lives in the **surrender subpopulation**, where `none` cannot exceed ~53.5% while `boolean` reaches ~100%. The 46.5% is domain-meaningful: when a player surrenders, ~half the time they hold the lowest on-board army — consistent with players leaving when they're losing.

*Provenance:* these figures are from an `fq` numpy pass over the *unfiltered* `elim_head_debug` table (`cloud_24k_sub_5k` val) — irreducible error = the rate at which the smallest-`army>0` player is surrendered, equivalently the disagreement between argmin-over-`alive` and argmin-over-`army>0`:

```sh
./scripts/fq.py --table elim_head_debug --split val \
    --manifest data/training/splits/cloud_24k_sub_5k.json <<'PY'
alive = t.cols['alive'].astype(bool)
army  = t.cols['army_sim'].astype(np.int64)
INF   = np.iinfo(np.int64).max
surr_frame = ((~alive) & (army > 0)).sum(1) > 0           # frame with a surrendered-present slot
mixed      = alive.sum(1) < 8
# none-encoding irreducible error: argmin-over-alive disagrees with argmin-over-(army>0)
diff = np.where(alive, army, INF).argmin(1) != np.where(army > 0, army, INF).argmin(1)
err  = lambda m: f"{diff[m].mean():.4%} (n={int(m.sum())})"
print("incidence:", f"{surr_frame.mean():.4%} ({int(surr_frame.sum())})")
print("ceiling err   all:", err(np.ones_like(surr_frame)),
      "  mixed:", err(mixed), "  surr:", err(surr_frame))
PY
```

They are not yet a committed artifact — build step 1 (§9) recomputes them on the actual train/val split as a logged check, which also resolves the per-split count gate (§8 #3).

The one non-surrender disagreement in the whole val set was a single `alive & army==0` slot — a transient zero-army general (attacked to 0 but not captured, its only tile; recovers +1 next production tick). Negligible (1 frame in 113k), and a different phenomenon from surrender.

## 6. The grid

**Full data, no surrender filter. Slice the metrics by surrender-status** (the within-data contrast replaces a separate filtered cell). The expensive fq table is built **once** (raw `army_sim` / `land_sim` / `alive`); the `(label, margin, argmin_set)` trio is computed **per target** from the chosen mask predicate; the driver runs the grid **once per target** (so tie-semantics stay consistent for free — only one target's columns are ever live). The artifact gains a `target` dimension.

**Cells:**
- **`alive` target:** all 4 encodings × the A–E spine (A1 / B1 / D1 / E1). The spine runs once for completeness; early-stop trims the converged/floored cells.
- **`army>0` target:** only `none` + `capture_status` × the spine (`boolean`/`categorical` are overkill — status is army-derivable here, so they're pruned).

**New plumbing:** one `captured` deriver in `families/army_derivers.py` (mirrors `LAND_SIM`: `prepare(sim)` walks `capture_events` — present in the sim dict — into a `[T,8]` "captured by tick t" boolean, indexed per frame via `f.raw_order`; ~8 lines). The `capture_status` encoding consumes it as a binary captured flag (the captor *identity* is irrelevant to argmin, so dropped; swap in the integer later only if a use needs prod-exact fidelity).

## 7. Predictions

The full-data `none`/`capture_status` cells stack **two** difficulties; the spine and the surrender-slice disentangle them:

1. **the notch** — exclude `army==0` eliminated players — *architecture-dependent*, depth-1 required (same notch as the MVP).
2. **the surrender ceiling** — can't exclude `army>0` surrendered players — *information limit*, architecture-independent.

| encoding | target | linear (A1, D1) | depth-1† — non-surr mixed | depth-1† — surrender subpop |
|---|---|---|---|---|
| `none` | `alive` | fails notch (picks an `army==0` player) | ~100% (notch carved) | **~53.5% (ceiling)** |
| `capture_status` | `alive` | fails notch (neutralized still at 0) | ~100% | **~53.5% (≡ `none`)** |
| `boolean` | `alive` | **~100%** (status channel excludes, no notch) | ~100% | ~100% |
| `categorical` | `alive` | **~100%** | ~100% | ~100% |
| `none` | `army>0` | fails notch | ~100% | **~100% (no ceiling)** |
| `capture_status` | `army>0` | fails notch | ~100% | ~100% |

† Depth-1 entries are the **E1_mlp** / ceiling values — the trustworthy legs. **B1** is the volatile model and is strongly data-scale-sensitive: on the `zero_overload` notch cell it ran ≈0.9 at full scale (6.18-3) but only ≈0.36–0.43 in a 40-game dev run, and it diverges late on val. So treat B1 as the least reliable prediction — expect it at or below E1_mlp. The surrender-subpopulation figures are achievable *ceilings* (best possible given army-only information); E1_mlp is the leg that should approach them.

The two load-bearing contrasts:
- **Same model, same frames, target flipped:** `none`/depth-1 on the surrender subpopulation = **~53.5%** under `alive` vs **~100%** under `army>0`. Isolates the surrender ambiguity as the sole cause of the ceiling. (The ~100% is not the model *handling* surrender — under `army>0` surrendered players are valid targets, so the task collapses to "smallest positive army past the notch"; flipping the target removes the need to exclude them at all.)
- **Status channel removes both difficulties:** `boolean`/`categorical` reach ~100% even linearly (the channel does the exclusion, so no notch and no ceiling) — vs `none`/`capture_status`, which need depth for the notch and still ceiling on surrender.

`boolean` vs `categorical` is a confirmatory negative: categorical's extra surrendered-vs-eliminated split buys nothing for the `alive` target (alive-vs-rest suffices).

## 8. Risks / things to get right

1. **Notch-vs-ceiling conflation (primary).** Aggregate `none`/`alive` accuracy blends a capacity failure (notch) with an information limit (ceiling). Metrics must be **sliced**: non-surrender mixed (notch only), surrender subpopulation (ceiling), and all. Without the slice the result is uninterpretable. New work in `metrics.py`.
2. **Per-target trio consistency.** `label`/`margin`/`argmin_set` move out of the fq spec's build-time `derived_cols` into a per-target prep step keyed off the target's masked-army (`alive`-masked vs `army>0`-masked). Run-twice keeps each run single-target, so the three never disagree — the tie-semantics-consistency requirement (6.18-1 Risk #6), satisfied by construction.
3. **Surrender counts per split — a gate, not an afterthought.** The surrender subpopulation *is* the headline result, and `split_by_game` holds out whole *games* (~50 at `val_frac=0.2`) while surrender frames cluster by game (one rage-quitter → many). So the naive ~7.4k / 250-games → val ≈ 1.5k estimate is optimistic: if surrender concentrates in a minority of games, the held-out subpopulation could be small and the ~53.5% metric high-variance. Gate the run on an actual per-split surrender count (it falls out of the §5 ceiling computation); raise `val_frac` or pool across seeds if it's thin.
4. **Proxy-transfer calibration (interpretation).** The toy is argmin-of-army; the elim-head predicts real eliminations. State the transfer at the set/encoding altitude only; do not claim the toy decides the elim-head target.
5. **Ceiling vs failure in reporting.** A `none`/`alive` val-loss that plateaus at a nonzero floor is the *expected* information ceiling, not a bug. Reporting should show the ceiling reference line so a floored cell reads as "at ceiling," not "broken."

## 9. Build order

1. **Recompute the §5 ceilings + per-split surrender counts** on the `cloud_24k_sub_5k` train/val split — the de-risk gate: a committed, logged version of the §5 `fq` pass. Confirms the headline ~53.5% and that the held-out surrender subpopulation is large enough to read a stable metric (§8 #3) *before* any model trains. Cheap, and it validates the slice's whole premise.
2. `captured` deriver (`army_derivers.py`) + a smoke test on `capture_events`.
3. Data layer: drop the filter from the default path; add the surrender-subpopulation selector; move `(label, margin, argmin_set)` to a per-target prep keyed off the mask predicate; keep `n_alive` (target-independent).
4. `encode.py`: add `none` (raw army on full data), `capture_status` (consumes the new channel), `categorical`; keep `boolean` (= existing `explicit_mask`). Encoder correctness test extended per encoding.
5. `metrics.py`: surrender-status slicing + the ceiling reference.
6. `run.py`: target as an outer loop; the pruned grid (§6); `target` in the artifact; per-target report.
7. Run on `cloud_24k_sub_5k`; read against §7.
