# fp16 obs landed — the n=20 data-starvation is resolved (`6.07-1`)

**Date:** 2026-06-07

## TL;DR

- The obs tensor now assembles as **fp16** by default (`ObsConfig.obs_dtype`), halving every host-side byte on the worker→GPU handoff path. This was the leading lever identified in [`6.06-7`](6.06-7-pin-thread-localized-memory-contention.md).
- Measured on H100 (`runs-cloud/2026-06-07T08-02-21Z`): n=20 went **~2084 → 2709 sps (+30%)** and **76% → 97% GPU util — now GPU-bound.** The dense-history data-starvation arc (`6.05-3` → `6.06-7`) is closed for n=20; it's now GPU-bound like n=5/n=10.
- The change was **low-risk by construction**: under CUDA autocast the model's first conv already casts the fp32 obs to fp16, so fp16-built obs is bit-identical at the conv. Confirmed offline (bit-for-bit) and live (loss trained normally).
- **Mixed-dtype (uint8) obs is not needed.** We're GPU-bound, so further obs byte reduction wouldn't add throughput. The next bottleneck is GPU compute itself.

## The result

| metric | A: fp32 (`6.06-7`) | B: fp16 (this run) | |
|---|---|---|---|
| steady sps | ~2084 | **2709** | **+30%** |
| GPU util | ~76% (starved) | **97%** | GPU-bound |
| `pin_copy` ms/batch | 232 | **112** | ~halved |
| `work / period` | 93% | **58%** | pin thread no longer the ceiling |
| `collate` µs/sample | ~852 | 389 | ~halved |
| `h2d` ms/batch | ~5 | 2.5 | ~halved |
| batch period ms | 253 | 198 | |

**Host-controlled proof (not a lucky draw).** The effective per-byte copy rate is ~1.1 GiB/s in *both* runs (252 MiB/232 ms vs 126 MiB/112 ms). Same contention-limited rate, half the bytes, half the time — so the `pin_copy` halving is the dtype change, not a faster host (odin is no faster per byte than CANADA-2), matching the ~117 ms projection. With `pin_put`≈0 and `pin_get` now *growing* to 76 ms (the pin thread idling on workers), the thread is no longer the bottleneck.

Notably, the per-byte rate did **not** improve (~1.1 GiB/s both) — the win was purely fewer bytes, not eased contention. That distinction matters for future iteration; see "The contention is routed around, not removed" below.

## Why this was low-risk

- **Numerically free on the training path.** The first op on obs is `initial_conv` (`nn.Conv2d`, autocast-eligible). Under autocast the fp32 obs was *already* cast to fp16 at that conv; building obs as fp16 just moves the same round-to-nearest from conv-time to assembly-time, on the same values. The conv sees identical bits either way.
- **Verified, not assumed.** An offline parity test (`test_obs_fp16_matches_fp32_downcast`, 640 real frames) asserts the fp16 build equals the fp32 build cast to fp16 **bit-for-bit**, and that no channel overflows fp16. Live training loss behaved normally — the end-to-end confirmation.
- **Values are tiny.** Every obs value is a 0/1 mask, a small categorical, a log-compressed magnitude, or a hand-normalized ratio — all single-digit, nowhere near fp16's 65504 ceiling. Range is a non-issue; only the continuous channels carry any rounding (~0.1%), and they feed deliberately-rough heuristic features.
- **Backward-compatible.** Old checkpoints lacking the `obs_dtype` key back-fill `fp32` from the frozen `LEGACY_OBS_CFG`, so flipping the live default to fp16 never re-describes an existing fp32 model. A resume from a pre-fp16 checkpoint therefore stays fp32; only fresh runs default to fp16.

## Obs tensor composition (and why fp16 fits it)

The obs is `[C, 32, 32]`, `C = 86 + 2n` (126 at n=20). Authoritative layout: `_BASE_OBS_CHANNEL_NAMES` in `bc/constants.py` and the stack order in `bc.obs.build_obs`; the table below is a category-level summary.

| category | count | values | fp16 |
|---|---|---|---|
| visibility | 1 | 0/1 | exact |
| visible state | 9 | 8 ownership masks (0/1) + 1 log-army | mostly exact |
| persistent map | 4 | 0/1 (mtn/city/gen/fog-struct) | exact |
| memory | 19 | 17 one-hot/mask + 2 log (last-seen-armies, turns-since) | mostly exact |
| BFS distance | 8 | log1p(distance), −1 sentinel | ~0.1% |
| self broadcast | 3 | army/1000, land/100, t/1000 | ~0.1% |
| opp broadcast | 14 | per-opp army/land, normalized | ~0.1% |
| scoreboard | 14 | 7 city-inference (0 today) + 7 land-delta, normalized | ~0.1% |
| contact/capture | 14 | 7 contacted (0/1) + 7 captured-by (int −1..7) | exact |
| dense history (×n) | n | ownership-transition (⅛-multiples) | fp16-exact |
| dense history (×n) | n | army-delta (signed-log) | ~0.1% |

Roughly **~50 of 126 channels are 0/1 or small-integer** (bit-exact in fp16), ~20 are ⅛-multiple categoricals (also fp16-exact), and ~55 are genuinely continuous (the only ~0.1%-rounding channels). That a board-state tensor is mostly masks and log-compressed small numbers is why fp16 is close to a best case here.

**dtype journey of one observation:** `int8/int16 on disk → fp32 channel builders → fp16 assembly buffer → fp16 through collate / IPC / pin copy / h2d → fp16 at the conv under autocast (CUDA), or upcast to fp32 at the model boundary (MPS / inference)`. The single fp32→fp16 point is the assembly write; builders stay fp32, and `shared.device.obs_for_model` handles the no-autocast upcast.

## The contention is routed around, not removed — and why that matters later

fp16 didn't relieve the memory-bandwidth contention; it sidestepped it. The pin copy's effective rate stayed throttled at ~1.1 GiB/s (vs ~5.4 GiB/s for the same copy in isolation, `6.06-7`) — we just push half as many bytes through the same throttled channel, so it finishes in half the time. The ~5× throttle is still fully present; it stopped binding only because the shorter copy now fits under the ~180 ms GPU floor. (Analogy: the pipe is still clogged at the same flow rate; we just have half as much to drain.)

The non-obvious part: fp16 *also* halved the workers' `collate` write traffic (852→389 µs/sample), so total host memory traffic dropped too — yet the per-byte pin rate didn't improve. **Hypothesis:** the throttle is driven by the workers' cache-hostile *access pattern* — the ~45 `np.full` constant planes and the strided `collate` scatter flagged in `6.06-7` — not by raw write *byte volume*. Halving the obs byte count doesn't change the access pattern: the workers still touch every channel and evict the pin thread's streaming data from shared cache; they just store the result in fewer bytes. So fewer bytes shortened the copy but left the per-byte rate pinned.

Caveat: A (CANADA-2) and B (odin) were different H100 hosts, so "~1.1 GiB/s in both" is suggestive, not a controlled per-byte measurement. A same-host fp32-vs-fp16 A/B would settle it — not worth a run now (GPU-bound), but it's the clean test if the question becomes load-bearing.

**Why this matters for later.** We're GPU-bound now, so the residual contention doesn't bite (the pin thread idles — `work/period` 58%, `pin_get` grew to 76 ms). But a future model-design change could re-expose the pin copy as the ceiling: a smaller or faster model, less compute per sample, or a larger obs (deeper history, more channels) that re-inflates the copy. If that happens, **dtype shrinking is mostly spent** — we're already at fp16, and uint8 buys only ~20% more (`6.06-7`). The next lever would be attacking the access pattern itself, which targets the *cause* rather than routing around it:

- `np.full` constant planes → conv bias / FiLM — deletes ~45 per-sample write-passes outright (a model change).
- Build channels directly into the obs buffer — drops the per-channel temp allocations (cache churn).

These reduce how cache-hostile the workers are, which is what the hypothesis says actually sets the per-byte throttle.
