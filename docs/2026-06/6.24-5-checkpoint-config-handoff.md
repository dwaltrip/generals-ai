## Resume-domain context (for the resume open questions)

The resume merge and drift rules carry non-obvious semantics that should inform answering 6.24-4's resume open questions:

- **Three drift buckets** (`run_dir.py:check_drift`, `:200-235`): *checkpoint-owned, always abort* = `arch`, `lr`, `weight_decay`; *free* (`_DRIFT_EXCLUDED`) = `epochs`, `manifest`, `intermediate`, `run_dir`, `gpu`, `dump_val_frames`; *trajectory-critical, abort unless `--force-config-mismatch`* = everything else, including `loss`, `seed`, `batch_size`, `precision`.
- **`lr`/`weight_decay` are checkpoint-owned** (pinned by AdamW state) — so the *only* freely-overlaid recipe field is `epochs`. And the lr-pin is a *policy* (reproducible-trajectory discipline), not a hard mechanism: AdamW stores moment estimates, not the LR, so a different LR on resume is mechanically possible; the repo chooses to forbid it.
- **`loss` is trajectory-critical and gated behind `--force`, never overlaid in practice** — which is the empirical reason it belongs with the run's *identity* (alongside `arch`), supporting storing it in the checkpoint.
- **Resume has been used exactly twice, both "train longer"** (raise `epochs`). Overlayability of anything else is hypothetical; the conservative resume is fine and not worth expanding now.
- Two leanings these produce: the resume merge likely **normalizes each input to current shape → merges → constructs once**; and `check_drift` / `_DRIFT_EXCLUDED` / `_CHECKPOINT_OWNED` should move into `bc/config` (they encode config-field semantics, not run-dir glue).

## How-much-to-build reasoning (Q4, for Stage-1 scoping)

- The config changes ~18 times/month, which **cuts both ways**: mistakes are likely (want a guard) *and* per-change ceremony is paid often (keep it cheap) → the light apparatus (pytest check), hook/command deferred.
- **Staging quarantines the heaviness**: Stage 1 (the valuable core) is small; the manifest/tooling is Stage 2/3 and you can stop anywhere.
- The version **stamp** is the only piece expensive to retrofit, so it's the one must-ship-with-Stage-1 item. The migration pipeline is ~empty at v1; the manifest/check can follow when the first real v1→v2 change lands.

## The fresh-eyes review (what it changed)

An independent Opus review (fresh context — doc + survey + code) found the architecture sound and caught: the `TrainingState`-carries-config gap and the `is_arch_bearing` discriminator bug (both now open items), and pushed the proportionality call to the lighter Stage 2. Two nuances it surfaced, now in the doc: the pytest check is the *only* guard for non-arch drift (strict-load only catches arch shape), and v0 meetability holds because the `.pt`-assembly half is existing working code being relocated, not a new unknown — though the survey only measured the sidecar half, so the `.pt`-era half still needs validating in Stage 3.
