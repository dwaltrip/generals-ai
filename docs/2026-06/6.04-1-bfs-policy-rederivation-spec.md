# BFS-passability re-derivation spec (`test_bfs_policy`)

## Goal

A fresh agent independently re-derives the expected passability of each cell from game state alone, with no access to the implementation or existing test. We compare its answers to what the test asserts; disagreements flag a possible correlated bug (code + test agree but are both wrong), a derivation error, or a spec ambiguity.

## How it works

Two documents:

- **This spec** (not shown to the agent): describes the testing intent, the design philosophy of the prompt, and the full answer key with derivations.
- **The prompt doc** (`6.04-2-bfs-policy-rederivation-prompt.md`): everything the agent sees. Contains the board, the passability policy, the scenarios, and instructions for showing work. References `docs/generals-io-game-mechanics.md` for fog-of-war and structure-visibility rules.

### Prompt design principles

The prompt provides game states and the rule, then asks the agent to derive verdicts. To keep the derivation independent:

- **No visibility giveaways.** The prompt never states whether a cell is visible or fogged — the agent derives vision from ownership + Moore-neighborhood rules in the mechanics doc.
- **No category labels.** Cells to judge are identified by ground-truth type (from the §2 board table), not by the passability category they fall into (e.g. "structure," not "fog-structure").
- **Scenario descriptions are structural, not outcome-based.** Titles describe what changes between scenarios (ownership footprint, tick count), not what the agent should find (fogged city, stale army).
- **Probing hints say what to attend to, not the answers.** The "what each variant is probing" section frames questions ("does total army matter here?"), not conclusions.
- **§7 flags reasoning traps as questions.** Each bullet asks the agent to reason about a convention explicitly, without pre-stating the correct resolution.

## The rule under test

BFS-passability policy — a project-specific design decision for the model's distance map, not a generals.io mechanic. Stated in full in the prompt doc §3. Four impassable categories: known mountain, unresolved structure in fog, discovered enemy general, unaffordable non-self city. Everything else is passable.

## Answer key

The expected derivations and verdicts for comparing against the agent's output.

### Scenario A — single tick

The perspective owns (0,0), (0,2), (3,3). Vision (Moore neighborhood of each): (0,1), (1,0), (1,1) from (0,0); (0,1), (0,3), (1,1), (1,2), (1,3) from (0,2); (2,2), (2,3), (3,2) from (3,3). Key visibility facts:

- (2,2) Ce — **visible** from (3,3)
- (0,3) G1 — **visible** from (0,2)
- (1,3) M — **visible** from (0,2)
- (1,1) Cn — **visible** from (0,0) and (0,2)
- (3,1) Fs — **never seen** (not adjacent to any owned cell)

**A1** (total_army=10000):
- (1,3) **impassable** — known mountain, visible (category 1). Army irrelevant.
- (3,1) **impassable** — unresolved structure, never seen (category 2). Army irrelevant.
- (0,3) **impassable** — discovered enemy general, visible from (0,2) (category 3). Army irrelevant.

**A2** (total_army=3):
- (0,0) **passable** — self general, always passable.
- (3,3) **passable** — self city, always passable (affordability doesn't apply).
- (2,0) **passable** — never-seen land tile, not a structure, falls into no impassable category.

**A3** (total_army=160):
- (1,1) **impassable** — neutral city, garrison 40, visible. 160 > 40×4=160? No (strict >). At the threshold.

**A4** (total_army=161):
- (1,1) **passable** — same city. 161 > 160? Yes. One above threshold.

**A5** (total_army=200):
- (2,2) **impassable** — enemy city, garrison 50, visible from (3,3) (perspective sees current army directly). 200 > 50×4=200? No (strict >).

**A6** (total_army=201):
- (2,2) **passable** — same city, same visibility. 201 > 200? Yes.

### Scenario B — two ticks, fogged enemy city

At tick 0 the perspective owns (0,0) and (2,3), giving it vision of (2,2) Ce (garrison 50). Between ticks the enemy captures (2,3), so at tick 1 the perspective owns only (0,0) — (2,2) is now **fogged**. The garrison has secretly grown to 999, but the perspective's last-seen value is still 50. Tests that the affordability rule uses the **stale last-seen army** (50), not the hidden ground-truth (999).

**B1** (total_army=200):
- (2,2) **impassable** — last-seen city_army=50. 200 > 50×4=200? No (strict >). At the threshold using stale value.

**B2** (total_army=201):
- (2,2) **passable** — same stale value. 201 > 200? Yes.
