# Aux-head variant machinery: spec + registry refactor plan

*Date: 2026-06-21. Plan for a structural cleanup of the elimination (and future) aux-head variant machinery on branch `elim-head-work-continues`. Successor to the [6.20-3](6.20-3-elim-soft-target-implementation-handoff.md) implementation handoff, which is the source for the load-bearing invariants this refactor must preserve (its "intentional debt" and "fragilities" sections). Pure structural change: numerically identical, staged into independently-green slices.*

## Scope

Training code only — the model, dataset, loss, and config under `packages/training/training/bc/`. The analysis families (`analysis/families/elim_head_debug.py` and siblings) are out of scope; their alignment to the removal/present domain is handled separately in the run-analysis work. This plan does not change what any variant computes; it changes where the variant-specific code lives and how the pipeline dispatches to it.

## Why

The elimination aux head has accreted roughly five conceptual variants — time-bin, time-bin soft, who-dies-next, who-dies-next over board-removal, and that removal variant softened. In the code these reduce to two variant strings plus two temperature knobs, but the machinery for them is a **vertical slice smeared across eight files**. Reading `loss.py` shows every variant tangled together; understanding one variant means grepping eight files; adding or changing a variant means threading the same edit through all of them, each with its own branch. That friction scales badly given how fast these variants turn over, and more aux heads (beyond elimination) are plausible.

The goal is an abstraction where iterating on a variant — or adding a new aux head — is *implement one spec and register it*, not edit eight sites.

## Current variant surface

There are three orthogonal axes of variation, but the code treats only one as an axis and hard-couples the other two:

| Axis | Options | Representation today |
|---|---|---|
| **Target structure** | ordinal time-bins (per-player categorical over *time*) vs. who's-next (single categorical over *players*) | the `elim_head_variant` gate: `"time_bin"` / `"next_death"` |
| **Event + domain** | death / `alive_mask` vs. board-removal / `present_mask` | hard-coupled to structure: `time_bin`→death, `next_death`→removal |
| **Soft target** | hard vs. τ-softened | two separate knobs: `elim_target_tau` (ordinal-bin smoothing), `next_elim_target_tau` (removal-time distribution) |

`ELIM_HEAD_VARIANTS = ("time_bin", "next_death")` is the registry-of-sorts today. The variation branches at **eight sites** (table below), each rediscovering "which variant" — `bc_model` emits `elim_logits` *or* `next_elim_logits`, and `loss.py` / `dump.py` / `eval/run.py` then branch on which key is present, or on the variant string, rather than from a single source of truth. Beyond those eight, the per-batch JSONL and console formatters in `train.py` also branch `if "elim" in … elif "next_elim" in …` to decide what to print; those key on metric-presence so the refactor doesn't break them, but they're residual "grep N files to understand one variant" surface the spec abstraction doesn't fully collapse. The naming forked by accident of history: `elim_*` vs `next_elim_*` key prefixes, `alive_mask` vs `present_mask`, `elim_target_tau` vs `next_elim_target_tau`. The prefixes encode *which silo*, not *what the thing is*.

## The abstraction: one spec per variant

Lift each variant's slice into a single **spec** object — the answers to "what does this variant need at each site," bundled. Every site then looks up the active spec and delegates; the key-presence branching disappears.

```python
class AuxHeadSpec(Protocol):  # sketch — exact shape settles in slice 0
    name: str          # registry key / variant string, e.g. "next_death"
    output_key: str    # what bc_model.forward emits, e.g. "next_elim_logits"

    def precompute(self, sim) -> Ctx: ...                    # numpy, per game, in workers
    def encode_targets(self, ctx, raw_order, t) -> dict: ... # numpy, per frame, in workers
    def build_head(self, arch) -> nn.Module: ...             # torch
    def loss(self, model_out, targets, loss_cfg) -> AuxLossResult: ...
    def dump_records(self, out, batch) -> dict: ...
    def build_eval_meter(self, loss_cfg) -> Meter | None: ... # in-loop eval diagnostics, or None
    def eval_summary(self, meter) -> dict: ...                # the meter's reported metrics
    def validate(self, arch, loss_cfg) -> None: ...          # cross-cutting config rules
```

A registry maps variant-string → spec. `active_specs` is derived from config — today the single `elim_head_variant`, a list of 0 or 1. The **loss loop** generalizes cleanly to *additive* aux heads (several on at once): `AuxLossResult.weight` is already per-spec, so the loop sums `weight·term` over whatever is active. The **config** does not yet — both elim variants share a single `lambda_elim`, and the mutual-exclusivity invariant is what makes "two terms, one λ, only one nonzero" safe. A genuinely-additive head needs a per-head λ added to `TrainConfig`/`LossConfig` — a config change deferred until a second head is actually additive. So: the loop carries over without rework; the config gains one field when the time comes. The config stays single-gate for elimination now.

Sibling specs share their own internals — the two elim specs keep sharing `ElimCtx` / `precompute_elim` among themselves. The central machinery does not need to know; it calls `spec.precompute(sim)` once per game and threads the returned ctx into `spec.encode_targets`.

The only conceptually loaded part is the loss return, which carries two things expressed today as scattered comments:

```python
@dataclass
class AuxLossResult:  # sketch
    metrics: dict[str, Tensor]  # all reported quantities by key; includes the trained term
    term_key: str               # metrics[term_key] is the trained objective (feeds total)
    weight: float               # the λ for this head (e.g. lambda_elim)
    count: Tensor               # 0-d int; this head's denominator (NOT n_samples)
    count_key: str              # reporting name for the count, e.g. "n_next_elim"
```

`total` is then assembled in one place — the single source that both the live loss and (later) the accumulator's reconstruction read:

```python
total = policy + cfg.mu_pass * pass_ + cfg.lambda_value * value_soft
for spec, res in active_results:
    out.update(res.metrics)
    out[res.count_key] = res.count
    total = total + res.weight * res.metrics[res.term_key]
```

Two pieces of tribal knowledge become spec properties: *total uses the **soft** term, not the hard reporting CE* (`term_key` points at `next_elim_soft`), and *elim means weight by alive-pair count, not n_samples* (`count`). The summary-dict keys (`next_elim`, `next_elim_soft`, `n_next_elim`) stay named strings owned by the spec, so logs look identical; only the plumbing becomes a loop.

Scope of the abstraction is the **variant-gated aux heads** (elimination today). `value` and `pass` stay as the always-on core, untouched — but the interface is head-neutral (nothing says "elim"), so they could adopt it later if it earns its keep.

## The eight sites: before → after

| # | Site | Spec provides | Difficulty |
|---|---|---|---|
| 1 | `model_config` | the variant is a registry key; validation = `name in registry` | trivial |
| 2 | `bc_model.forward` | `output_key` + `build_head(arch)` | mechanical |
| 3 | per-game precompute (`_walk`) | `precompute(sim) → ctx` (elim specs share `ElimCtx`) | mechanical |
| 4 | `dataset.encode_frame` | `encode_targets(ctx, raw_order, t) → {sample keys}` | mechanical |
| 5 | `dump.py` | `dump_records(out, batch) → {eval records}` | mechanical |
| 6 | `bc_loss` | `loss(...) → AuxLossResult`; total via the generic loop | the hard one |
| 7 | `LossAccumulator` | folds/reports the head's metrics by key | the hard one |
| 8 | `eval/run.py` | in-loop eval diagnostics — `build_eval_meter` + `eval_summary` (the `time_bin` `ElimMeter`) | own slot, see open question |

Five of these are pure mechanical relocation — cut the `if/elif` body, move it into a spec method, no logic change. The risk concentrates in 6 and 7, where the numerics and the per-head weighting live; the slice plan gives those two the care and keeps the mechanical ones low-stakes. Site 8 is the one the contract above doesn't cover: `eval/run.py` builds an `ElimMeter` gated on `elim_head_variant == "time_bin"` and emits `elim_top1`/`elim_soft_floor`/`elim_pred_entropy` — **in-loop eval diagnostics, not loss-accumulator state**, so they sit outside `AuxLossResult`. next_death has no in-loop meter today (its diagnostics are computed offline from the dump). Whether specs own this (the `build_eval_meter`/`eval_summary` slot above) or it stays explicitly out of scope is an open question (below); if left out, slice 1 leaves a `variant == "time_bin"` gate standing in a file it otherwise drains.

## Invariants to preserve

The refactor is numerically identical. These load-bearing behaviors (from 6.20-3) must hold exactly afterward; the named tests are the safety net:

- **τ=0 ⇒ `next_elim_soft` is literally `next_elim`** (same tensor, the `else` branch). The accumulator and total key on the soft term, so any drift here changes the τ=0≡hard reproducibility guarantee for existing runs. (`test_loss.py`: τ=0 ≡ hard, exact.)
- **`total` carries the *soft* term, never the hard reporting CE** — in both `bc_loss` and the accumulator. The hard CE is reporting-only (the heuristic baseline).
- **The soft-CE nan-guard**: `logp = where(present_mask, logp, 0)` before the `soft_target * logp` product, avoiding `0·(-inf)=nan` on absent channels. Looks defensive; is load-bearing. (`test_next_death_soft_target_shape_and_winner_mass`.)
- **`removal_dt.to(float32)` in the soft branch** — sentinel-scale horizons need fp32 for clean `exp` underflow and immunity to fp16 overflow under cloud autocast.
- **Per-head accumulation weights by the head's own count** — alive-pair count for time_bin, defined-next-victim count for next_death — not `n_samples`. This is exactly the `AuxLossResult.count`.
- **Mutual exclusivity**: at most one elim head is built today, so `active_specs` is ≤1. The loop generalizes, but the present invariant still holds.
- **The `ElimCtx` positional-splat hazard** (`ElimCtx(edges, *precompute_elim(...))`, fields all arrays/ints so a reorder misassigns silently) — slice 1 replaces it with keyword construction. This is the one fragility the refactor actively removes rather than preserves.
- **`dump_records` is not the loss CE.** The dump's hard `elim_ce` is an unweighted per-bin log-softmax (`dump.py`); it matches the accumulator's `elim` only when `elim_bin_weights is None` (today's default). When relocating dump logic into a spec, do **not** collapse `dump_records` into a reuse of `spec.loss`'s CE — under a weighted run they diverge by design.

The full suite (204 passed, 1 skipped on the current branch) is the regression net; each slice must stay green. The loss contract above was checked against the current `bc_loss` and `LossAccumulator` by an independent review (2026-06-21) and found faithful and complete — nothing in the live loss is inexpressible in `AuxLossResult`; the corrections from that review were to the site enumeration (the eighth site and the residual `train.py` reporting branches), not the numerics.

## Settled decisions

- Flat registry, **one spec per variant**; sibling specs factor their shared internals themselves.
- **Generic loop in `bc_loss`**, single source for `total`. The "explicit total identity" the current code maintains is a hand-kept cross-check compensating for there being two term-lists (live in `bc_loss`, reconstructed in the accumulator); collapsing to one registry makes that guard structural instead of vigilance-based. The spec declares which metric is the trained `term` vs reporting-only.
- **Scope = variant-gated aux heads only.** `value`/`pass` unchanged; interface designed head-neutral.
- **Cross-cutting config validation moves into specs** (e.g. `next_elim_target_tau > 0 requires variant == "next_death"`, currently in `TrainConfig.__post_init__`). Adding a variant's constraint then touches only its spec. Cheap, no config-file change — done within the dispatch refactor.
- **Numerically identical**, staged into independently-green slices.

## Config

A single loss knob lives in **three** places today: a `TrainConfig` field (+ validation), a `LossConfig` field (+ the same validation), and the field-by-field hand-copy at `train.py:608` that bridges them. Adding a knob means editing all three and writing the `≥ 0` check twice.

The bound on how far this can be unified: a variant's config **straddles two serialization domains**, and that split is load-bearing, not accidental.

- **arch** (model shape: variant name, `n_bins`, `pool`) is needed to *reconstruct the `nn.Module`*, so it rides into the `.pt` checkpoint (and gets `LEGACY_ARCH` pins so old checkpoints stay correctly described).
- **recipe** (loss weights, taus) is the *training objective and schedule*; it lives in the run dir's `args.json`, overlay-able on resume, and is not needed to reconstruct the module.

The proof a variant straddles both: the `tau-requires-variant` rule needs to see arch (the variant) *and* loss (the tau) at once — it cannot live in `LossConfig` alone. So we do not get one config object per variant; we get an arch-slice and a loss-slice, and the cross-cutting validation lives where both are visible (the spec).

Decisions:

- **Dispatch refactor reads the existing flat config as-is.** No config-file change in slices 0–3. Specs read the typed fields they need; cross-validation moves into specs.
- **Config nesting is a separate slice (slice 4).** Make `TrainConfig` *hold* a `LossConfig` (composition) instead of re-declaring its fields. This is the "nested loss dict" and the de-duplication in one move: one field definition, one validation, and the `train.py:608` hand-copy disappears (`loss_cfg = config.loss`). It is config-file-facing — existing run configs carry `lambda_value:` at the top level — so it needs back-compat parsing (accept both shapes for a window) and earns its own slice.

## Slice plan

Each slice is independently diff-able against the test suite.

| Slice | What | Risk |
|---|---|---|
| **0** | Spec interface + registry; register the two existing variants. No call sites changed — pure addition, specs exist but unused. | trivial |
| **1** | Route sites 1–6 (and site 8, the `eval/run.py` meters, if the open question resolves to specs-own-them) through the registry; delete the `if/elif` bodies; variant loss/target/dump logic relocates into spec modules. Accumulator (site 7) untouched — it still reads metrics by string key, so specs must emit the same keys (`next_elim`, `next_elim_soft`, `n_next_elim`). Includes the `ElimCtx` keyword-construction fix and moving cross-validation into specs. | the bulk; prove numerically identical |
| **2** | Collapse the accumulator's second total-list (site 7): accumulate each spec's `metrics` weighted by its `count`, reconstruct `total` from the same specs. | the riskiest numerics; own diff |
| **3** | Naming normalization (see below). | mechanical but wide |
| **4** | Config nesting: `TrainConfig` holds `LossConfig`; kill the triplication + hand-copy; back-compat parse for flat configs. | config-file-facing |

Slices 3 and 4 are independent of each other and reorderable. Slices 0 and 1 are the core of this plan; 2–4 are committed in principle but re-examined when reached.

## Deferred / follow-up

- **Loss config → `.pt` checkpoint (decide after slice 4; leaning yes).** Today the objective is the one resume-critical piece with no durable per-checkpoint pin: the optimizer state is in the `.pt`, arch is in the `.pt` with `LEGACY_ARCH` pins, but the recipe lives only in `args.json` and leans on "default == historical behavior" — a gap the `TrainConfig` NOTE already flags. Option: persist `asdict(config.loss)` into the save payload next to `arch`, with a `LEGACY_LOSS` pin mirroring `LEGACY_ARCH`, so a checkpoint self-describes its objective and resume can pin from it. It is a checkpoint-format change with a back-compat tail, so it is its own decision — but slice 4 (nesting `LossConfig` into one object) makes it nearly free, which is why it waits until then.
- **Naming (slice 3, wants its own discussion).** The names have gone wonky: `next_death_target` keys on board-removal (a function named "death" computing removal), the `elim_*` / `next_elim_*` prefixes are silo-history not meaning, and the variant string `"next_death"` is config/dump/checkpoint-facing. The low-risk surgical move is renaming `next_death_target` → `next_removal_target` (function + its one import + `__all__` + tests), leaving the config/dump/checkpoint strings alone. A full end-to-end rename touches serialized strings and needs the `dump_compat` aliasing pattern; whether to go that far is the open part. Don't decide the scheme in this plan.
- **`loss.py` → folder (re-measure first).** It is ~500 lines now; the refactor drains the variant-specific bulk into spec modules, leaving `LossConfig`, a slim `bc_loss` core (policy/value/pass + the head loop), and `LossAccumulator` — still substantial because policy/value/pass aren't moving. Whether to split into a `loss/` package (`config.py` / `core.py` / `accumulator.py`) is a smaller call best made on the post-refactor size. Underneath it is the vertical-vs-horizontal layout question; the lean is **partial vertical** — relocate the loss/target/dump logic per variant (which delivers the iteration win and drains `loss.py`) but leave the head `nn.Module` in `model/heads/` for now (moving it churns import paths for no real gain).

## Open questions

- **Eval diagnostics (site 8): specs own them, or scope them out?** `eval/run.py`'s `ElimMeter` is in-loop eval state, not loss-accumulator state, so it sits outside `AuxLossResult`. Lean is **specs own it** — a `build_eval_meter(loss_cfg) -> Meter | None` + `eval_summary(meter) -> dict` pair on the spec, with `eval/run.py` looping over active specs the same way it will loop for loss. This collapses the last `variant == "time_bin"` gate and gives next_death a clean home if its offline diagnostics ever move in-loop. The alternative — leave `run.py`'s meters explicitly out of scope — is smaller but leaves variant-gating standing in a file slice 1 otherwise drains. Settle before slice 1 (it shapes the Protocol); doesn't affect slice 0.
- **Config read mechanism: typed nested read vs. dynamic blob.** Lean is typed read (`loss_cfg.next_elim_target_tau` as a real field — pyright sees it, IDE completes it; adding a knob is a typed field + a read), accepting "field declared in config, used in spec" as declaration-vs-use rather than real duplication. The alternative — a `loss.head_params: dict[str, Any]` the spec validates — makes adding a knob touch only the spec but drops static typing on those fields. To settle before slice 0, since it shapes the spec/config interface.
