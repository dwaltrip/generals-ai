# Checkpoint & config versioning — chunk-1 sketch (high-level)

*Date: 2026-06-26. The focused, implementation-first slice of the checkpoint-config-versioning work: the self-describing v1 format and the migrate-once read seam — the **shape axis** — built behavior-preserving. A narrow branch of the broader design. See the synthesis ([6.26-5](6.26-5-checkpoint-config-synthesis.md)) for the conceptual frame (shape vs. behavior, the tiers, the open questions), [6.24-4](6.24-4-checkpoint-config-versioning-design.md) for the migrate-once mechanism, and the boundary surveys ([6.26-1](6.26-1-survey-pt-checkpoint-io.md) / [6.26-2](6.26-2-survey-sidecar-config-io.md) / [6.26-3](6.26-3-survey-model-usage-trace.md)) for the blast radius. High-level by intent; implementation detail comes in later passes. Concepts are restated briefly and may overlap the synthesis; the concrete specs live here.*

## Scope & framing

Chunk-1 stands up a new checkpoint-load module and the **v1 self-describing format** on the read side, behavior-preserving, with reserved placeholders for deferred work. The capstone flips the writer so new runs produce v1 checkpoints.

It delivers the **shape axis only**. Brief restatement (full treatment in 6.26-5): a checkpoint's faithfulness has two axes — config *shape* (does the stored config have the current field structure, so live code consumes it without version-branching?) and model *behavior* (does current code reproduce what the checkpoint actually did?). Chunk-1 delivers shape; the behavior axis is mapped in the synthesis and mostly deferred.

Three goals: conservative / low-risk, a real improvement on the checkpoint+config side, and a flexible foundation for the deferred work.

**Why this cut is safe — decoupling.** Chunk-1 reserves placeholders and keeps the tier machinery as empty structure, so its shape is robust to *either* resolution of the open behavior-axis questions (co-residency strategy, fidelity-scope). Those questions are not chunk-1 — they live in the critical-questions doc.

## The v1 format (spec)

Top-level layout:

- `model`, `optim`, `scaler`, `epoch` — runtime state + progress (unchanged from today).
- `in_ch` — input-channel checksum, relocated out of `arch` to the top level.
- `config` — `asdict(TrainConfig)` + `config_version`. The version lives *inside* `config`. `arch` nests at `config.arch`, `loss` at `config.loss`.
- `arch_version` — reserved, null in v1 (a behavior-axis placeholder; save-time-only, so it can't be retrofitted).
- `code_sha` — provenance, populated at the writer-flip.

**The one hard constraint.** Every checkpoint load is `weights_only=True`, which rejects non-allowlisted classes. After `asdict`, the only offenders are the `Path` fields (`manifest`, `intermediate`, `run_dir`) — so the serializer stringifies them on write and the reader re-wraps them on read (introspecting Path-typed fields, so it doesn't rot when a Path field is added).

**The four save-time stamps, each on its own axis** (detail in 6.26-5): `config_version` (config shape → migration), `arch_version` (architecture → behavior-drift detection, deferred), `code_sha` (provenance), `in_ch` (narrow input-channel checksum).

**The sidecar.** Chunk-1 makes the **`.pt`** self-describing. The on-disk `args.json` sidecar is untouched here; its rename to `config.json` is a separate deferred chunk.

The migrate-once mechanism itself is owned by 6.24-4; this section owns the v1 layout.

## The read path & LoadPlan

Pipeline (working names, may collapse): **CheckpointReader → Migrator → ConfigResolver → LoadPlan → ModelBuilder.**

- `load_checkpoint(path, device, …) -> BCModel` is the public entry. The `LoadPlan` (`Native | Legacy | Unsupported`) is internal routing — callers get a `BCModel`, the same contract as today.
- The **Migrator is an empty chain at v1** (current shape = v1, nothing to migrate). The dispatch skeleton still lands now: read the stamp, a `v > CURRENT` guard, and the (currently no-op) version loop.
- **v0 (unstamped)** routes to `Legacy`, which delegates to today's reconstruction (`_arch_for_load` and the related helpers), unchanged. The v0→v1 normalizer is deferred — a near shape-axis follow-up.

## High-level flows

How the components connect, as understood so far.

**Load (read) — the main flow.** `load_checkpoint(path)`:

1. CheckpointReader: `torch.load(weights_only=True)`, then read the top-level stamp (is `config_version` present?).
2. ConfigResolver routes to a `LoadPlan`:
   - **stamped (v1)** → Migrator (no-op at v1) → reconstruct `TrainConfig` (re-wrap Paths, validators run) → `Native(config)`.
   - **unstamped (v0)** → `Legacy` → today's `_arch_for_load` reconstruction.
   - unrecognizable → `Unsupported(reason)` (raises).
3. ModelBuilder builds the `BCModel` from the resolved arch; `load_state_dict(strict=True)`; return it on-device in eval mode.

The `LoadPlan` is consumed here, inside `load_checkpoint`; only a `BCModel` leaves.

**Save (write) — the capstone flow.** `TrainingState.save` (now carrying the resolved `TrainConfig`):

1. The serializer assembles the v1 dict: `asdict(config)` with Paths stringified, `config_version` inside `config`; top-level `in_ch` checksum; `arch_version = null`; `code_sha` (captured at launch, threaded in).
2. `torch.save`.

The `args.json` sidecar is still written separately by `run_dir`, unchanged (rename deferred).

**Resume — unchanged in chunk-1.** Resume keeps its current path: it reads the parent config from the `args.json` sidecar, and `from_checkpoint` does its own second `torch.load` for optim/scaler/epoch. Chunk-1 does not rewire this. (Sourcing config from the `.pt` and folding out the double-read are a deferred follow-on.)

**Dependency note.** The writer-flip must follow the v1 read path: once runs emit v1 checkpoints, something has to read them, and the inspectors (`is_arch_bearing`) must be fixed. That is why save is the capstone, gated behind steps 1–2.

## Build approach & phases (strangler-fig)

**Module homes.** A fresh `bc/checkpoints_v2.py` (torch-heavy: reads bytes, builds models) plus a new `bc/config` package (torch-free: config shape, migration, resolution). Keep them separate so torch doesn't leak into the config layer; whether they ever merge is a later question, and the torch boundary argues against it.

**Strangler-fig.** Plant the new module, migrate every caller to `load_checkpoint`, delegate to today's reconstruction at first, then grow real logic in over the steps. Migrating all callers is deliberate — it forces an honest read of scope, catches breakage, and audits whether callers are well-abstracted. The pass is **behavior-preserving** — record abstraction smells (the redundant file reads, the vestigial `value_head_variant`, the `load_frozen_*` wrappers), don't fix them here. The core `load_checkpoint` lives in the new module; the wrappers (`BCModelHandle.load`, `load_frozen_model`) repoint to it and stay where they are.

Phases:

- **Step 1 — strangler seam.** New module + `load_checkpoint` delegating to existing reconstruction; migrate all callers; returns `BCModel`; zero behavior change. Validated by the existing checkpoint/state tests plus a manual smoke on the untested callers (`scripts/`, `self-play/cli.py`, `eval_poc.py`).
- **Step 2 — v1 read path + round-trip test.** Grow the v1 read into the module; prove it with a construct → serialize → read → build round-trip (which exercises the Path / `weights_only` constraint).
- **Step 3 (capstone) — writer-flip.** `TrainingState.save` emits v1. Pulls in TrainingState-carries-config, the `is_arch_bearing` fix, and `code_sha` population (and disambiguates the `git_sha` log label in `train.py`). First live-path change; gated behind step 2.

## Cross-cutting anchors

These are behavior-axis concepts (full treatment in 6.26-5) that carry a concrete chunk-1 footprint — anchored here so they aren't lost to the deferred bucket:

- **Reserve `arch_version` / populate `code_sha`** — save-time-only facts; the slots must land in the first format even though arch-fidelity enforcement is deferred.
- **The LoadPlan firewall** — `Native | Legacy | Unsupported` as a tagged union (Native real; the other arms reserved and empty) lets the tiers fill in later without re-plumbing callers.
- **Keep `.trunk` and `model.cfg` reachable** — probe consumers forward on `model.trunk`, and consumers read `model.cfg.obs` / `.elim_*` off the loaded model. The strangler migration must preserve this surface.
- **Archive `value_head_probe.py`** — removes the one consumer that builds obs from hardcoded defaults (and one `.trunk` extractor), shrinking both the migration and the trunk coupling. Pending a quick confirm that nothing live-imports it or `load_frozen_trunk`.
- **Migrator skeleton** — the dispatch lands at v1 even though the chain is empty; the v0 normalizer grows behind the `Legacy` arm later. Its frozen fills are where shape-migration carries behavioral pins — the one place the two axes touch.

## Deferred & open

Deferred (each safe to defer; see 6.26-5 and the surveys):

- **v0→v1 normalizer** — a near shape-axis follow-up; existing checkpoints load via the `Legacy` delegate meanwhile.
- **Resume rewiring** — sourcing config from the `.pt`, plus the double-read collapse.
- **Sidecar rename** (`args.json` → `config.json`) — survey 6.26-2 mapped the traps (a single `read_run_config` helper with old-name fallback; the lockstep question for `args_resume_NN.json`; collision names).
- **arch-fidelity enforcement** — the golden test + load-time compare; only the placeholder field lands now.
- **The gating questions** — co-residency strategy and fidelity-scope — are out of chunk-1; they live in the critical-questions doc.

Chunk-1-internal opens:

- `code_sha` capture point — almost certainly capture-at-launch and thread through; an easy detail to settle in implementation.
- `value_head_variant` containment — quarantine the legacy-only arg off the modern signature.
- Target-version Migrator signature (`to_version`) — for migrate-to-nearest later.
- Working names (LoadPlan variants, pipeline module names) may collapse.
