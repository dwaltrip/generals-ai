## Step 2 vs step 3 (the scope cut)

**Step 2 lands the v1 read path and the serializer, but the writer stays old.** `TrainingState.save` keeps emitting the legacy format, so no real v1 checkpoints exist yet and every real load still takes the legacy branch. `is_versioned_checkpoint` (becoming `"config" in obj`) and the `is_arch_bearing` fix both land in step 2 but stay **dormant** on real checkpoints — exercised only by the round-trip test. Step 2 is therefore behavior-preserving for real checkpoints.

**Step 3 flips the writer.** `TrainingState.save` emits v1 (calling the step-2 serializer), `code_sha` is captured, and the ambiguous `git_sha` log label in `train.py` is disambiguated. Save is last because once runs emit v1, the read path and the `is_arch_bearing` fix must already be in place.

## Build order + round-trip test

6.27-1 §7 has the phase breakdown. Proposed within-step-2 order:

1. Create `bc/config` (torch-free): `CONFIG_VERSION = 1`, `MIGRATIONS = {}`, the migrate dispatch (read `config_version`, a `v > CURRENT` guard, the no-op `range(v, CURRENT)` loop), `resolve_checkpoint_config`, and the Path stringify/re-wrap helpers. Unit-test `resolve_checkpoint_config` on a dict.
2. The v1 serializer in `storage` (assemble the v1 dict, Paths stringified) — the thing step-3 `save` will call.
3. `validate_in_ch` in `storage` (top-level `in_ch` vs `model.cfg.in_ch`).
4. Wire the STAMPED arm into `load_checkpoint` and implement `is_versioned_checkpoint` (`"config" in obj`).
5. The `is_arch_bearing` additive fix (6.27-1 §5.1) + its v0-invariant test.
6. The round-trip test: construct a `TrainConfig` → serialize → write → `load_checkpoint` → assert (cfg and config round-trip, the `Path` fields survive `weights_only`, `in_ch` validates, weights load) — exercising the full v1 layout end to end.

## Open decisions to settle early (discuss with Daniel)

- **`resolve_checkpoint_config` naming** — it's torch-free and takes a plain dict, so "checkpoint" in the name is off (`resolve_config` / `config_from_dict`?).
- **`bc/config` layout** — one module, or split (`migrate` / `resolve` / `serde`)?
- **The `from_file` overlap** — `resolve_checkpoint_config` mirrors `TrainConfig.from_file` minus `json.loads`, but it operates on a *fully-resolved* dict and re-wraps three `Path` fields (incl. `run_dir`) vs `from_file`'s two. Share a "build `TrainConfig` from a jsonable dict" helper, or keep them independent?
- **`code_sha`** — step-2 serializer parameter (the round-trip passes a dummy) vs step-3 wiring.

Record resolutions in 6.27-3 §6.
