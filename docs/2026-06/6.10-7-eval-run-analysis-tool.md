# Eval-run analysis tool landed

Date: 2026-06-10

`packages/eval-tools/scripts/analyze_eval.py` analyzes a finished eval run dir (the `run_adhoc.py` output format) into `<run-dir>/analysis/`: `report.md` (headline, paired-by-map tests, lead-conversion, kills, economy shares by alive-count stage, behavioral fingerprints, outlier scan, per-slot noise appendix), `distributions.md` (full percentile tables), `metrics.json`, two share-curve PNGs, and two flat CSVs (`player_games.csv`, `stage_snapshots.csv`) that all aggregates derive from — ad-hoc follow-up questions read the CSVs, not the npz files. `--reuse` re-renders from the CSVs (verified lossless against fresh extraction).

Library code is `eval_tools/run_analysis/` (loader / extract / stats / aggregate / report). Design notes that matter for reuse:

- Comparison unit is the *policy-spec group* (seats sharing a checkpoint), derived from `config.json` — nothing assumes the 3v3 shape; future powered evals or k-way runs work unchanged.
- Stage axis is alive-count spans between eliminations; snapshots at mid-span (entry is biased by the capture transfer). The axis is pluggable — `extract.tick_spans` already produces degenerate tick-grid spans (used for the early-land plot), so the deferred "every 50–100 ticks" alternative axis is mostly plumbing.
- Bootstrap resamples games (seats within a game are correlated); paired tests operate on map pairs. Stats are numpy-only (exact binomial sign test; no scipy dep).
- matplotlib added to eval-tools deps (was already in the workspace lock via training).

## Results — 0607-ep4 baseline vs 0610-ep6 lever run, 360 games

Two runs against the same checkpoint pair (0607-ep4 no-lever baseline vs 0610-ep6 lever run, both n20/pyramid, temp 0.5, 6-player 3v3): `data/eval-runs/2026-06-10T11-12-09` (60 maps × 2 rotations) and `data/eval-runs/2026-06-10T13-47-05` (120 fresh maps × 2 rotations). Details and tables: each run dir's `analysis/report.md` / `distributions.md`.

- **No detectable strength difference.** Combined 171–176 with 13 draws; resolution ~±5 win-points. The two runs' headlines individually pointed opposite ways (65–53 baseline, then 123–106 lever) — outcome-linked reads at this scale, including the per-stage lead-conversion splits, track the noise.
- **The lever model farms better — replicated almost digit-for-digit across both runs.** Land share at the 6-alive stage 0.176 vs ~0.157 in both, ahead at every stage, with small SEs. The behavioral difference is real even though the strength difference is unresolved: the longer/lever-trained checkpoint demonstrably learned a stronger economy game, consistent with its better val_policy.
- **No endgame utilization deficit.** P(win | army share at 2-alive), from the CSVs, is steep and near-identical for both models (≤0.35 share → ~10% win, ≥0.65 → ~90%), lever equal-or-better at fixed share — final duels are material-determined for both checkpoints.
- The 6.10-6 always-passing-loser loose end resolved to a handful of player-games per run (pass rate ~0.6–0.84, mostly placed 6th, dead early), listed with game ids in each report's outlier table.

Open thread for sizing future evals: the val_policy→win-rate exchange rate is uncalibrated; a cheap probe is an ep1-vs-ep6 eval of the lever run (Δ ≈ 0.10 nats).
