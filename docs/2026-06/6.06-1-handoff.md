### What this session established (new since 6.05-3)

**The hardware lottery is first-order, not noise.** Identical configs swung **426–1844 sps** purely on which Modal host they drew, while the obs-build CPU cost stayed flat (~640–690 µs/sample) the whole time. Region/RAM logging (added this session) caught it:

| draw | N | region | RAM | sps | GPU util | note |
|---|---|---|---|---|---|---|
| 1 | n5 | (pre-logging) | 1 TiB | 1707 | 69% | ~17% slower CPU |
| 1 | n20 | (pre-logging) | 1 TiB | 1844 | 74% | **n20 > n5 — inverted** |
| 2 | n5 | `us-east4` (GCP) | 1 TiB | 1729 | 66% | normal |
| 2 | n20 | `US-1` | **944 GiB** | **426** | **15%** | catastrophic; CPU ~10% *faster* |
| yours | n20 | `CANADA-2` | 1 TiB | 1785 | — | good pool |
| yours | n5 | `sines-2` | 1 TiB | 2169 | — | good pool |

Pattern so far: **1 TiB RAM = good pool (~1700–2200 sps); 944 GiB / `US-1` = bad draw (~426 sps).** The bad host's CPU was *fine* (faster, even) — the collapse is in data delivery, not compute. (Prior-session baselines on the good pool were higher still: n5 2680 / n20 2100 — there's within-good-pool variance too.)

**The profiler has a blind spot exactly where the n=20 collapse lives.** Our producer seams time obs-build *compute* (`channel_build`, `assemble`, …) but **not** the path around it: `/data` volume reads, worker→main IPC (pickling the 252 MiB/batch obs), pin, H2D. On the `US-1` draw the obs-build CPU was normal (666 µs/sample) while the GPU sat **83% idle** — i.e. ~70% of per-sample wall time is outside the seams. **`py-spy --subprocesses` on a bad draw is the right next probe** to split volume-I/O vs IPC (needs `py-spy` in the image + a wrapper).

**Obs-build breakdown (valid within one container; n=5):** `channel_build` ~40% (biggest, **N-independent**), `step_memory` ~23%, `assemble` ~22%; TOTAL ~689 µs/sample. CPU-normalized N-scaling: `channel_build` is **flat** in N; **`assemble` is linear in channels** (pure byte movement) — that's the only region that grows with N. (M1 baseline was ~354 µs/sample, so Modal cores are ~2× slower per the bandwidth-bound stages.)

**Channel census (`obs.py` / `constants.py`):** of 86 base channels, **45 are spatially-constant broadcasts** (`np.full(scalar)`) = 47% of the obs tensor at n=5. Of those, **7 are literally constant zero** (`opp_city_inference`, a TODO shipping nothing end-to-end); 38 carry a real per-sample scalar.

**Lever ranking (all are model changes):**

- **broadcast→FiLM elimination** — biggest. A spatially-constant input channel ≈ a first-conv bias, so injecting the 38 scalars via FiLM and dropping the 7 zeros is information-preserving and removes ~47% of channels at n=5 → cuts `assemble` + IPC + H2D bytes, and helps low-N (production) most.
- **fp16 obs** — halves remaining host-side bytes; composes with the above. Lowest-effort variant: make the (already single-pass) assemble buffer fp16. Needs numerics-parity check + gating (the fp32/MPS path runs without autocast).
- **drop the 7 dead-zero channels** — cheap independent cleanup (or implement the city-inference feature).

### The run — invocation gotchas (cost trial-and-error this session)

- Modal probe: `./training/scripts/run_bc_modal.py --config training/tmp/n{5,20}_quick.json --profile --skip-val --max-batches 800 --detach`. **800, not 400** — dilutes cold-start so steady-state dominates the average.
- **`modal volume get` of a multi-file dir collapses files onto one path if the local dest doesn't exist.** Pull into a *pre-created* directory, or pull the whole run dir. The poller pattern that worked: wait ~120s, poll `modal volume ls <run>/prof` for `summary.json`, then pull.
- For a **full report**, pull `args.json` + `epochs.jsonl` too (the poller only grabbed `prof/` + `gpu_util.jsonl` + `batches.jsonl` + `args_cloud.json`).
- A slow draw can run ~16 min (vs ~4) — size the poller window accordingly; volume `run.log` is stale mid-run (committed near the end), so it's not a live progress signal.
- Local smoke: `./training/scripts/run_bc_local.py --config training/scripts/smoke-config.json --profile --skip-val --max-batches 5 --num-workers 2` (from repo root; `--skip-val` required — MPS val crash).

### Suggested approach per goal

- **Goal 1 (n20 == n5):** you can't compare across containers — the lottery is ±4×. Either build the **W2 single-process driver** (sweep N in one process/container = same hardware, the only clean cross-N measurement) or **discard bad draws on sight** (the report's `BAD DRAW` flag / non-1-TiB RAM) and compare only good-pool runs. Then the real lever for n=20 is `assemble` + the I/O/IPC bytes → FiLM broadcast-elimination (−47% channels) is the big hammer.
- **Goal 2 (pipeline hardening):** General goal. Some possibilities: FiLM + fp16 + drop the 7 dead-zero channels. We should consider building channels straight into the preallocated buffer (drops per-channel allocs). We can also investigate the I/O/IPC blind spot (py-spy) since that's what actually broke on `US-1`.
- **Goal 3 (prove tooling):** auto-gen the report at run-end (call `build_report` in `train_remote`, write `report.md` to the run dir — unblocked now that `tabulate` is in the image); then the multi-run **compare mode** (compute layer is already shaped for it).
- **Goal 4 (the lottery):** cloud/region **pinning is ruled out** (Team/Enterprise-gated, too costly). Practical mitigations: prefer **sequential** launches (concurrent raises spill-to-fallback-cloud odds), an **early-sps reroll guard** (kill+respawn if the first ~50 batches are <~800 sps — a `US-1` draw is obvious in ~20s), and lean on the new region/RAM logging to label + discard bad draws. Open question worth a `py-spy` capture: *why* is `US-1`'s data path so slow (volume bandwidth vs shm/IPC vs noisy neighbor)?
  - The hardware lottery issue was especially confusing as nearly identical probes in a previous session didn't seem to have this level of variation. It's currently the next morning, so this session will be a good re-test to see if it was a semi-transient hardware availability issue.
