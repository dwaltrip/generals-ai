## Design decisions (settled this session)

### Frozen eval map set: manifest + pack

- **Manifest** (checked into git): replay IDs bucketed by player count, with per-map fields (player count, month, replay version). Versioned as `eval-map-set-v1`. The manifest doubles as the **training exclusion list** — the split-builder subtracts these IDs in all future manifest builds. Existing training manifests are untouched (they already exclude these IDs by construction).
- **Pack** (derived artifact, not in git): `StaticMap`s extracted from the DB's wire blobs, under `data/eval/map-sets/eval-map-set-v1/`. Deterministic from manifest + DB, so regenerable.
- **Pack format:** one gzipped JSONL per bucket (`maps-<N>p.jsonl.gz`), one map per line: replay ID + provenance (month, version) + the `StaticMap` int-list fields. `usernames` is synthesized at load (`p0..pN-1`), not stored. Line order is the canonical order — seeded `sample=K` indexes into this frozen sequence, so it stays stable forever. A `manifest.json` copy sits in the pack dir so the volume is self-describing without a git checkout; git holds the authoritative copy. Buckets are ~1 MB gzipped; loading is stdlib `gzip`+`json`, keeping the loader free of SQLite/parser imports. Packs are immutable once published — a future set is a new directory, never an edit.
- **Eligibility:** v15+, vanilla (`is_vanilla_ffa` — no teams/custom map/swamps/modifiers/special tiles), and **never in any training manifest**. The ever-trained set is the ID union over `data/training/splits/` (train + val rows): 20,780 IDs, all 8-player.
- **Bucket sizes:** `min(2000, available)` per player count, 2p–8p. Measured vanilla never-trained pools: 2p ≈ 1.1k, 3p ≈ 0.5k, 4p ≈ 3.2k, 5p ≈ 1.8k, 6p ≈ 2.4k, 7p ≈ 4.5k, 8p ≈ 136k. So 2p/3p (and roughly 5p) are take-all; 8p samples 2k.
- **Sampling:** monthly-stratified over the collection window (2025-04 – 2026-05 for v1; earlier `started` timestamps exist in the DB but don't survive the bucket filters): round-robin over months, so shortfall redistributes automatically and any prefix of the canonical order is month-balanced. Vanilla check runs during sampling (rejection sampling), so final counts are reported at build time. The build prints distribution sanity stats (board size, mountain/city counts).
- **Manifest records the collection window** — map generation drifts across game versions (not paradigm shifts, but non-trivial), so sets built from different windows sample slightly different map distributions.

### Holdout rationale (recorded for the methodology doc)

- Memorization risk is judged low but non-zero: each map is a procgen singleton (one game in the corpus), and policy labels come from a fog-limited human — but the value/placement head regresses on outcomes, which do depend on hidden info (enemy spawns, city-vs-mountain identity). Impossible to rule out post-hoc, nearly free to eliminate, so eval maps are held out.
- The holdout is **retroactively valid**: existing checkpoints trained only on the 20,780 manifest IDs, so they never saw these maps either.
- **Growth strategy: collect, don't hoard.** No reservation tier beyond the active set. Future sets (v2, thicker mid-player-count buckets, refreshes, etc) come from fresh collection — new replays are never-trained by construction, and games without strong players are a large untapped same-window source that training (which requires strong players) can never claim. Generator drift across windows is the one caveat, recorded per-set.

### Cloud eval

- **New volume `generals-ai.eval-runs`** (the `generals-ai.<role>` convention): holds the map pack and run output dirs. With the pack on the volume, the cloud run does **not** need the parsed-replays volume — maps stop depending on SQLite or intermediate npz entirely, locally and on cloud. Volumes mounted: `training-runs` (checkpoints) + `eval-runs` (pack in, artifacts out).
- **`run_eval` seams:** a `set:` maps mode (`set:<name>` for a whole bucket, optional `sample=K,seed=S` — seeded sampling is stable now that the set is frozen; the existing `random:`-over-corpus mode stays for local ad-hoc exploration) and a parameterized output root (local default unchanged for now; the `data/eval/runs` move is deferred).
- **Entrypoint** `packages/eval-tools/scripts/run_eval_modal.py`, mirroring `run_bc_modal.py`: probe-pattern image (Rust toolchain + sim_core build + `eval-tools` modal_requirements + `add_local_python_source` for the eval package graph), tethered `.remote()` (eval is short; summary comes back; `modal run --detach` still available), T4 default with `--gpu` override (host-bound per 5.31-1, so cheap card; GPU selection optimization deferred). Analysis pipeline runs in-container as it does locally, so the volume holds the full run dir including `analysis/`.
- **Pull:** `packages/eval-tools/scripts/pull_eval_runs.py` cloned from `pull_runs.py` — volume `generals-ai.eval-runs`, dest `data/eval/runs-cloud/`, `--no-games` (analog of `--no-checkpoints`: skips the bulky per-game npz, keeps `results.jsonl` + `analysis/` + logs), `--force`.
- **Scope:** single-container adhoc runs only. Fan-out, in-loop training-gate eval, and the mini map subset are all deferred (6.02-3 open questions #4–5).
