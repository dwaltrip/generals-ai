## Open Items

### 1. Loss config → `.pt` checkpoint

- Store the loss config in the checkpoint, similar to how we store `ModelConfig` (under the `arch` key).
- Why it matters: the loss recipe is the one resume-critical piece with no durable per-checkpoint pin. Optimizer state and arch already ride in the `.pt` — the recipe is the lone exception, living only in `args.json` and leaning on "default == historical behavior". There's already a `NOTE` in `TrainConfig` flagging this gap.
- Counter-consideration: the recipe lives in `args.json` partly *by design* — it's the training objective/schedule, overlay-able on resume and not needed to reconstruct the module. So pinning it in the `.pt` has to preserve resume-overlay, not just relocate the data.
- Nesting `LossConfig` under `config.loss` made this much easier — it's now one object to serialize, vs. the previous flat top-level keys.
- Old checkpoints won't carry a loss config, so loading them needs a `LEGACY_LOSS` pin — the historical defaults — mirroring `LEGACY_ARCH`. Without it they'd silently re-interpret under whatever the current default is, which is the exact fragility this change is meant to remove. This is the back-compat tail.
- The core change is mechanically small (serialize the one `config.loss` object); that back-compat pin is the careful part. Whether to take the whole thing on is a deliberate go/no-go — it's a checkpoint-format change, and not urgent.

### 2. Elim-head variants naming cleanup

*Known as Slice 3 during the refactor.*

The names have drifted and now encode silo-history rather than meaning:

- `next_death_target` actually keys on board *removal* — a function named "death" that computes removal.
- The `elim_` / `next_elim_` prefixes mark *which variant silo* a thing came from, not *what it is*.
- The variant string `"next_death"` is config/dump/checkpoint-facing, so renaming it reaches serialized data.

Slice 2 already pulled part of the rename surface into one place (the `metric_keys` / `weight_attr` literals are now one-per-spec), but the serialized-string reach is unchanged.

Two possible scopes:

- Surgical: `next_death_target → next_removal_target` (the function + its import + tests, no serialized strings touched).
- Full: an `elim_` / `next_elim_` rename that reaches checkpoint/dump/config strings and may need something like the `dump_compat` aliasing pattern.

Settle the scope before picking a naming scheme.

### 3. Aux-spec metric-roles seam

An aux head emits two metrics: a *hard* one (the cross-run-comparable reporting number) and a *soft* one (the trained objective folded into the total). At τ=0 they're computed identically, so they come out equal.

We explored making "reporting" a first-class role on the spec (a `report_key`) so the console could just show the one reporting number — and rejected it. Both numbers carry real signal, and they only coincide at τ=0, so the console should show both, not pick one.

The reframed direction: the τ=0 duplicate isn't a display bug. It's that the static `metric_keys` 2-tuple asserts two metrics when, at τ=0, the head really has one. The fix would be a **config-derived / mode-dependent metric set**: one metric at τ=0 (both reported and trained), two at τ>0. That would make `term_key` mode-aware too, and the duplicate would never get created in the first place.

- Wrinkle to weigh: the console wants the collapsed view, but the JSONL log probably wants a stable column schema. So likely "log the full set, expose a mode-aware view for display".
- Interim: the τ=0 display hack (`_aux_keys_without_tau0_dup`, landed this session) collapses the pair when equal. Its `TODO` points here.
