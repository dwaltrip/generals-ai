# Throughput bench — GPU compute ceiling (`6.05-1`)

**Date:** 2026-06-05

**Status:** Probe A (GPU compute ceiling) complete across T4/L4/A100/H100. Probe B (data-pipeline ceiling) validated on a sanity cell; full grid **deferred until after obs-perf work** (its numbers are a direct function of obs-build cost — see [The real lever](#the-real-lever-obs-construction-perf)). Tooling: [`training/scripts/bench_throughput.py`](../../training/scripts/bench_throughput.py).

## TL;DR

- The [`5.31-3`](../2026-05/5.31-3-width-sweep-plan.md) width sweep's "flat samples/sec across widths" was **the 2-worker data pipeline, not the model.** With data loading removed, the same A100 does **6.6×** the sweep's rate at the smallest width — it was running at 15–26% of its compute ceiling.
- Measured GPU ceilings (bs=512, fp16 AMP): the model is **far from compute-bound** (5–17% of fp16 tensor-core peak) because the 32×32 spatial grid has low arithmetic intensity. So real-run throughput is gated by the **data pipeline**, not the card.
- **The data pipeline = obs construction.** Probe B is really an obs-build benchmark; its rate is `1 / per-sample-obs-build-time`. That makes **obs-construction perf the highest-leverage knob on training throughput** — more than GPU class or model width.
- Bigger batch is a **gentle plateau** (+5–9% from bs=512→2048), not worth the OOM risk.
- New reusable tooling + a sourced fp16 tensor-core peak table in `shared.perf` (`peak_tflops_fp16`).

## GPU compute ceiling (bs=512, fp16 AMP)

samples/sec · achieved TFLOPS · MFU vs **dense fp16 tensor-core peak**. (Full batch-size sweep in the [appendix](#appendix-full-batch-size-sweep).)

| width | T4 (65 TF) | L4 (121 TF) | A100 (312 TF) | H100 (989.5 TF) |
|---|---|---|---|---|
| 0.5x (128w) | OOM | 525 · 6.6 · 5.5% | 2,165 · 27.3 · 8.7% | 4,267 · 53.7 · 5.4% |
| 0.75x (192w) | OOM | OOM | 1,438 · 40.2 · 12.9% | 2,806 · 78.4 · 7.9% |
| 1x (256w) | OOM | OOM | 1,088 · 53.7 · 17.2% | 2,202 · 108.7 · 11.0% |

## What it means

- **The sweep measured the pipeline.** A100 at 128w: 2,165 sps ceiling vs ~327 in the starved sweep (2 workers) = 6.6×. At 256w, 1,088 vs ~285 = 3.8×. The MFU(fp32)>100% the run printed is the same story read backward — once the GPU runs flat-out it sails past the fp32-ALU peak (the work is on fp16 tensor cores). That's *why* we switched the denominator to fp16.
- **Low MFU is structural, not a bug.** 5–17% of fp16 peak at 32×32 — small spatial → low arithmetic intensity + kernel-launch overhead + the per-step `bc_loss` `.item()` sync. Wider models use the card better (A100 0.5x→1x: 8.7%→17.2%), but none are close to compute-bound.
- **Card fit at bs=512 + pyramid head:** T4 (16 GB) OOMs even the 128w model (matches the 5.31-3 note); L4 (24 GB) fits only 128w; A100 (40 GB) fits all three; H100 (80 GB) fits all three with batch headroom. H100 is ~2× A100 throughout.
- **The pipeline is the binding constraint.** At ~180 sps/worker (Probe B sanity cell), feeding these ceilings needs roughly:

  | | A100 | H100 |
  |---|---|---|
  | 0.5x (128w) | ~12 workers | ~24 workers |
  | 0.75x (192w) | ~8 | ~16 |
  | 1x (256w) | ~6 | ~12 |

  i.e. a 256w run on A100 needs only ~6 productive cores, but a 128w run on H100 needs ~24. **These numbers are a direct function of obs-build cost — see below.**

## The real lever: obs-construction perf

Probe B is not really a "dataloader" benchmark — it's an **obs-construction benchmark**. The pipeline does nothing else of substance: each sample is one `encode_frame` (`compute_visibility` + `step_memory` + `build_obs` (96 ch, incl. per-frame BFS) + `build_mask` + `actions.encode`); `np.load` amortizes to ~nothing across a game's frames. So:

```
per-worker sps = 1 / (per-sample obs-build time)
```

The ~180 sps/worker ⇒ **~5.5 ms of obs-build per sample** on a Modal core. Everything in the feedability analysis scales inversely with it: `max pipeline sps = workers / obs_build_time`, and `workers-to-feed = GPU_ceiling × obs_build_time`.

**This is the highest-leverage knob on training throughput — more than card or width.** Probe A showed the model is 5–17% of fp16 peak (not compute-bound), so a faster GPU barely moves real wall-clock; but a 2× obs-build speedup doubles the pipeline ceiling, halves the cores rented for the whole run, and can flip "H100@128w unfeedable" to "trivially fed."

**Prime suspect: the per-frame BFS.** `dataset._walk` invalidates the BFS graph cache *every frame* (city passability depends on per-tick army values), so BFS is rebuilt per sample with no cache reuse — and there's a standing TODO there to revisit. It's computed inside `build_obs`, so it's folded into that ~5.5 ms. The 6.04 BFS-policy + fog-parity rederivations touched exactly this code, so the ~180 reflects the *current* (heavier) obs-build, not the 5.31-1 eval probe's pre-rederivation `build_obs` (~0.44 ms/row).

**Consequence for these results:** the feedability numbers above are **conditional on current obs-build perf** and will move as soon as that's optimized. The GPU ceilings (Probe A) are stable; the pipeline side is a moving target tied to obs code.

## Caveats

- **OOM boundary is pessimistic.** `cudnn.benchmark=True` allocates fat autotuning workspaces and all cells share one process (fragmentation across build/OOM cycles), so the largest-batch-that-fits is likely understated vs a real run (`benchmark=False`, fresh process). The bs=512 throughput numbers are unaffected.
- **MFU denominator = dense fp16, FP32-accumulate** (the AMP regime), SXM/HBM3 for H100 (what Modal provisions; PCIe H100 is ~756 dense).

## Open / next

- **Obs-construction perf is the lever** ([above](#the-real-lever-obs-construction-perf)) — the next throughput work, not GPU/width tuning.
- **Profile `encode_frame` regions** (BFS vs channel builders vs `step_memory` vs visibility) before the obs work — the training-side analog of the 5.31-1 eval tick-timer — so the optimization targets the real cost.
- **Hold the full Probe B until after obs-perf.** Its headline (workers-to-feed) is a direct function of obs-build cost, so running it now measures a soon-stale baseline. The one obs-build-*independent* question it'd settle — does the single-threaded collate plateau below the H100@128w target (~4,267 sps)? — is worth grabbing eventually but is lower priority than the obs work. The CPU hard-cap is already validated (`cpu=(request, limit)`; 8 workers on 4 capped cores gave +13%, not 2×).
- **`cudnn.benchmark=True` in `train.py`** is free for our fixed 32×32 shapes, but changes nothing while obs-build binds — it only pays once obs-perf flips the bottleneck to the GPU. Enable it then (harmless now); we haven't measured our specific delta.
- **Low fp16 MFU is a standing question:** channels-last, GroupNorm cost, and the small spatial size are candidate levers *if* GPU efficiency ever becomes the bottleneck (it isn't while the pipeline binds).
