# Throughput bench — cloud training throughput analysis (`6.05-1`)

**Date:** 2026-06-05

**Status:** Both probes complete. This doc is the comprehensive reference for GPU compute ceilings, data-pipeline throughput, and the feedability analysis that connects them. Tooling: [`training/scripts/bench_throughput.py`](../../training/scripts/bench_throughput.py).

## TL;DR

- **Not pipeline-bottlenecked.** With modest worker counts (3–11 depending on GPU and width), every GPU/width combo runs at its GPU compute ceiling. The pipeline is not the binding constraint.
- **GPU ceilings are low but structural.** 5–17% of fp16 tensor-core peak (bs=512, fp16 AMP) because the 32×32 spatial grid has low arithmetic intensity. This is what the GPU can actually do with this workload, not a starvation artifact.
- **Wider models are a better time deal than they look.** 1× (256w, 19.7M params) costs ~2× the wall-time per sample vs 0.5× (128w, 5.0M) — but has ~4× the params and FLOPs. The fixed per-step overhead (kernel launches, syncs) is a large fraction at these small model sizes, so doubling params doesn't double step time.
- **Per-worker pipeline rate: ~426 sps** on Modal CPUs (post obs-perf work). Scaling is roughly linear up to ~4 workers; matching workers to cores beats over-provisioning (NUMA locality effect).
- Bigger batch is a **gentle plateau** (+5–9% from bs=512→2048), not worth the OOM risk.
- New reusable tooling + a sourced fp16 tensor-core peak table in `shared.perf` (`peak_tflops_fp16`).

## What it means

- **Low MFU is structural, not a bug.** 5–17% of fp16 peak at 32×32 — small spatial → low arithmetic intensity + kernel-launch overhead + the per-step `bc_loss` `.item()` sync. Wider models use the card better (A100 0.5x→1x: 8.7%→17.2%), but none are close to compute-bound.
- **Card fit at bs=512 + pyramid head:** T4 (16 GB) OOMs even the 128w model (matches the 5.31-3 note); L4 (24 GB) fits only 128w; A100 (40 GB) fits all three; H100 (80 GB) fits all three with batch headroom. H100 is ~2× A100 throughout.
- **Feedability.** At ~400 sps/worker (Probe B, post obs-perf), the workers needed to saturate each GPU:

  | | A100 | H100 |
  |---|---|---|
  | 0.5x (128w) | ~6 workers | ~11 workers |
  | 0.75x (192w) | ~4 | ~8 |
  | 1x (256w) | ~3 | ~6 |

  All configs are feedable with modest core counts. Match `num_workers` to provisioned cores for best per-worker efficiency (see [Probe B](#data-pipeline-ceiling-probe-b)).

## Obs-construction perf

The data pipeline is really an **obs-construction benchmark**. Each sample is one `encode_frame` (`compute_visibility` + `step_memory` + `build_obs` (96 ch, incl. per-frame BFS) + `build_mask` + `actions.encode`); `np.load` amortizes to ~nothing across a game's frames. So:

```
per-worker sps ≈ 1 / (per-sample obs-build time)
```

The measured ~426 sps/worker ⇒ **~2.3 ms of obs-build per sample** on a Modal core (post obs-perf work: BFS cache invalidation by mask equality, dense-history caching on MemoryState, numpy BFS rewrite). The feedability table scales inversely with this: `workers-to-feed = GPU_ceiling × obs_build_time`.

Obs-build perf remains the highest-leverage knob on CPU cost — further improvements reduce the core count (and thus CPU rental) needed to saturate the GPU. The GPU ceilings (Probe A) are stable; the pipeline side moves with obs code.

## Data-pipeline ceiling (Probe B)

Full 12-cell grid, post obs-perf work. Cells run sequentially (shared Volume).

**Clean scaling curve** (cpu=32, cores never the bottleneck — isolates per-worker rate):

| cpu | workers | total sps | per-worker sps |
|---|---|---|---|
| 32 | 1 | 426 | 426 |
| 32 | 2 | 853 | 427 |
| 32 | 4 | 1,541 | 385 |
| 32 | 8 | 2,864 | 358 |
| 32 | 16 | 5,677 | 355 |
| 32 | 32 | 8,679 | 271 |

**Contention probe** (workers = cores and 2× cores):

| cpu | workers | total sps | per-worker sps |
|---|---|---|---|
| 4 | 4 | 927 | 232 |
| 4 | 8 | 1,466 | 183 |
| 8 | 8 | 3,857 | 482 |
| 8 | 16 | 4,875 | 305 |
| 16 | 16 | 6,057 | 379 |
| 16 | 32 | 8,296 | 259 |

Key findings:

- **Per-worker rate: ~426 sps** at 1–2 workers (cpu=32). Scaling is roughly linear up to ~4 workers; above that, per-worker efficiency degrades (271 sps/worker at 32 workers = 64% of peak).
- **Workers = cores beats over-provisioning.** cpu=8 w=8 (482/worker) beats cpu=32 w=8 (358/worker) by 35%. cpu=16 w=16 (379/worker) beats cpu=32 w=16 (355/worker) by 7%. Likely NUMA locality — fewer cores stay on one socket. Below ~4 cores the container is resource-starved and the effect doesn't hold.
- **2× oversubscription costs 30–37%** at cpu ≥ 8 (e.g. cpu=8 w=16: 305/worker vs cpu=8 w=8: 482/worker). At cpu=4 the penalty is only ~21%, likely because the container is already resource-starved at 1:1.
- **Collate is not the bottleneck.** 8,679 sps at 32 workers is well above the highest GPU ceiling (H100@0.5x = 4,267 sps).
- **Practical recommendation:** provision `num_workers ≈ cores ≈ GPU_ceiling / 400`, matching workers to cores.

## Width-vs-time tradeoff

Wider models cost less wall-time per sample than FLOPs would predict, because fixed per-step overhead (kernel launches, `.item()` sync, optimizer bookkeeping) is a large fraction at these small model sizes.

| width | params | FLOPs/sample | params ratio | sps ratio (A100) | sps ratio (H100) |
|---|---|---|---|---|---|
| 0.5x | 5.0M | 12.59 GF | 1.0× | 1.0× | 1.0× |
| 0.75x | 11.2M | 27.95 GF | 2.24× | 0.66× | 0.66× |
| 1x | 19.7M | 49.34 GF | 3.94× | 0.50× | 0.52× |

~4× the params/FLOPs costs only ~2× in wall-time. MFU rises with width (A100: 8.7% → 17.2%) as the compute-to-overhead ratio improves.

**Params × sps** (a crude proxy for parameter-updates per GPU-second):

| width | A100 | H100 |
|---|---|---|
| 0.5x | 10.8B | 21.3B |
| 0.75x | 16.1B | 31.4B |
| 1x | 21.4B | 43.4B |

The wider model delivers ~2× the param-updates-per-second despite processing half the samples. Whether this translates to faster learning depends on whether the extra capacity is useful — an empirical question for the loss curves.

## Cost analysis

Based on [Modal pricing](modal-pricing.md). CPU cost is 4–13% of total across all configs — GPU rental dominates.

| GPU | width | sps | cores needed | GPU $/hr | CPU $/hr | total $/hr | $/M samples |
|---|---|---|---|---|---|---|---|
| L4 | 0.5x | 525 | 2 | $0.80 | $0.09 | $0.89 | $0.47 |
| A100 | 0.5x | 2,165 | 6 | $2.10 | $0.28 | $2.38 | $0.31 |
| A100 | 0.75x | 1,438 | 4 | $2.10 | $0.19 | $2.29 | $0.44 |
| A100 | 1x | 1,088 | 4 | $2.10 | $0.19 | $2.29 | $0.58 |
| H100 | 0.5x | 4,267 | 12 | $3.95 | $0.57 | $4.52 | $0.29 |
| H100 | 0.75x | 2,806 | 8 | $3.95 | $0.38 | $4.33 | $0.43 |
| H100 | 1x | 2,202 | 6 | $3.95 | $0.28 | $4.23 | $0.53 |

Observations:

- **H100 dominates A100.** Slightly cheaper per sample at every width *and* 2× faster in wall-clock. It costs 1.88× per hour but delivers ~2× the sps. Prefer H100 unless availability is an issue.
- **L4 is worst $/sample** despite being the cheapest per hour ($0.47/M vs $0.29/M on H100 for 0.5x). Low utilization on a cheap card isn't cost-efficient.
- **Width cost in dollars:** 1x costs ~1.8× of 0.5x per sample (H100: $0.53 vs $0.29/M). Since 1x has ~4× the params and FLOPs, that's ~2.2× more param-compute per dollar.
- **Param-compute per dollar caveat.** The 2.2× figure assumes all parameter-updates contribute equally to learning. In general this doesn't hold — wider models can have redundant capacity or diminishing returns per added parameter. At these sizes (5–20M params for a complex strategy game with 96-channel obs), the models are small enough that we expect the extra capacity to be productive, not redundant. The width-sweep loss curves are the direct test.
- **Fixed-time-budget tradeoff.** With a data surplus (more unique samples than any single run will see), capping run duration introduces a data-vs-compute tradeoff: 0.5x sees ~2× more unique game states in the same wall-clock, but 1x spends ~2× more total FLOPs (each sample does ~4× the compute at ~half the sps). Whether more unique data or more compute-per-sample matters more depends on whether the model is capacity-limited — if 0.5x can't represent the strategy space, extra data won't help.

## Caveats

- **OOM boundary is pessimistic.** `cudnn.benchmark=True` allocates fat autotuning workspaces and all cells share one process (fragmentation across build/OOM cycles), so the largest-batch-that-fits is likely understated vs a real run (`benchmark=False`, fresh process). The bs=512 throughput numbers are unaffected.
- **MFU denominator = dense fp16, FP32-accumulate** (the AMP regime), SXM/HBM3 for H100 (what Modal provisions; PCIe H100 is ~756 dense).
- **Probe B ran on CPU-only containers.** The CPU model may differ from CPUs on GPU-provisioned nodes. If feedability margins are tight for a config, validate with a pipeline bench on the actual GPU container (GPU idle).
- **Probe B measures cold-Volume reads** (each game file read once, no re-read). Multi-epoch steady state may be faster due to OS page cache; these numbers are conservative.

## Open / next

- **`cudnn.benchmark=True` in `train.py`** — free for our fixed 32×32 shapes, already used in the bench. Harmless to enable now; we haven't measured the specific delta.
- **Further obs-build profiling** — the remaining ~2.3 ms/sample could have more wins. Profile `encode_frame` regions (BFS vs channel builders vs `step_memory` vs visibility) to find the next target. Further improvement reduces the CPU core count needed to saturate the GPU.
- **`.item()` sync in `bc_loss`** — `n_non_pass.item()` forces a CPU-GPU sync every step. It's baked into the Probe A ceiling (so the numbers are realistic), but removing it would lift the GPU ceiling modestly.
- **Validate CPU parity** — if feedability margins are tight for a chosen config, run a pipeline cell on the actual GPU container to confirm the CPU model matches Probe B's CPU-only containers.
- **Low fp16 MFU is structural.** The 32×32 spatial grid produces small matrix multiplications that can't saturate tensor cores regardless of memory layout or normalization choice. Channels-last and GroupNorm alternatives could improve MFU modestly, but the arithmetic intensity ceiling is set by the board size.

## Data sources

Probe A and Probe B results are stored in `training/data/bench/` as timestamped JSON files alongside `.log` files of the terminal output. The tables in this doc can be reconstructed from these files:

- Probe A: `training/data/bench/gpu_ceiling_*.json` — per-cell `samples_per_sec`, `achieved_tflops`, `mfu_fp32`, `flops_per_sample`, `params`. MFU(fp16) in the doc tables is derived as `achieved_tflops / peak_fp16` (the fp16 peak table was added after the initial Probe A run).
- Probe B: `training/data/bench/dataloader_*.json` — per-cell `samples_per_sec`, `per_worker_sps`, `cpu`, `num_workers`.

The width-vs-time and feedability tables are derived: `workers_to_feed ≈ gpu_ceiling_sps / per_worker_sps`, `params × sps = params × gpu_ceiling_sps`.
