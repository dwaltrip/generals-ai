# The obs/alive tick seam: board-snapshot-time vs event-time

*Date: 2026-06-18. Status: finding note (deferred fix). A one-tick inconsistency between how prod builds the obs army channel and how it builds the `alive` target: they describe opposite ends of the same tick. Surfaced while building the argmin-toy `captured` deriver (6.18-4 step 2); it corrects 6.18-4 §2's atomicity claim. Not being fixed now — recorded as a concrete input to the coming obs-tensor + model-head rework. Code TODOs at both sites point here.*

## TL;DR

The obs per-player army channel reads the **pre-resolution board snapshot** (`ownership[t]`), while the `alive` target uses **event-time** (`death > t`). They're paired at the same frame `t`. At a **capture-while-alive** tick the two disagree for exactly one frame: the obs shows the captured player still on the board with army, while the alive target already reads them dead. ~1,118 frames (~1% of the `cloud_24k_sub_5k` val split). It's small and bounded (one frame per capture-while-alive event), but it's a real inconsistency the model trains on, and it lives in **prod** code, not the analysis layer.

## Mechanism

Two prod functions, paired per frame in BC training:

- **obs army channel** (`bc/obs.py`, `scoreboard_row` / `init_memory`): `army[p] = (armies * (ownership[t] == p)).sum()`. This is the board *before* tick `t`'s captures resolve — the state the acting player observed. A captured player's tiles transfer at `t+1`, so their army reads nonzero at `t` and zero at `t+1`.
- **alive target** (`bc/targets/elim_targets.py`, `alive_mask`): `is_real & (death_by_slot > t)`. A player whose `DeathEvent` fires at tick `t` reads **dead at frame `t`** — event-time, the moment the kill is recorded.

Each convention is individually reasonable. The seam is that they're paired at the same frame index while describing different moments *within* the tick: the target is end-of-tick (death recorded), the obs is start-of-tick (pre-resolution board).

## Evidence

The obs the model actually sees carries the army — this isn't an artifact of the sim-derived `army_sim` deriver. At every sampled transient frame, `army_obs == army_sim` (the obs army channel, built by the obs builder, shows the captured player's full army), while `alive` reads false.

The bug is cleanly isolable from the (legitimate) surrender population by **run length**: a capture-while-alive flips `alive` and zeroes the obs board one tick apart, so the `~alive & army>0` signature appears for *exactly one* frame; a genuine surrender holds army for many ticks, so the signature runs ≥2. (Neutralize only applies to already-surrendered players, so capture is the only while-alive board-removal — run = 1 is unambiguously the capture transient.)

On `cloud_24k_sub_5k` val (112,975 frames / 250 games):

| population | slots | frames | share |
|---|---|---|---|
| `~alive & army>0` (all) | 7,872 | 7,437 | 6.58% |
| **capture transient (run = 1)** — the seam bug | **1,118** | **1,112** | **0.98%** |
| sustained surrender (run ≥ 2) — legitimate state | 6,754 | 6,392 | 5.66% |

## Surrender is not this bug

A surrendered player is genuinely dead-but-holds-army: `DeathEvent` at surrender, army stays on the board (no transfer) until a later capture/neutralize. There `~alive & army>0` is the **correct** representation — obs rightly shows army, target rightly shows dead. That's the population the argmin toy studies on purpose (6.18-4). Only the **run-1 capture transient** is the seam bug. (6.18-4 §2 wrongly claimed normal captures are atomic and produce no transient — corrected there.) Excluding the ~1% transients shifts the toy's §5 surrender ceiling by <1 pt, so the toy's conclusions are unaffected.

## fq reproduction

`elim_head_debug` carries the two columns this needs (`army_obs`, `alive`) plus `game_id`. fq has no prev/next-frame accessor — `FrameTable` is a row-local container — but the build walk is contiguous and tick-ordered (`shuffle_buffer_size=0`, asserted), so adjacency is reconstructable with a `game_id`-boundaried shift.

```sh
./scripts/fq.py --table elim_head_debug --split val \
    --manifest data/training/splits/cloud_24k_sub_5k.json <<'PY'
alive = t.cols['alive'].astype(bool)
aobs  = t.cols['army_obs']
g     = t.game_id
# NOTE: hand-rolled prev/next-frame access. fq has no such accessor by design
# (FrameTable is row-local); this leans on the walk being contiguous + tick-ordered
# (shuffle_buffer_size=0) so adj[j] marks rows j, j+1 as the same game's t, t+1.
adj   = g[1:] == g[:-1]
present_dead = (~alive) & (aobs > 0)             # obs shows on-board w/ army; target says dead

# isolated single-frame present_dead (run length 1) = capture-while-alive transient.
iso = present_dead.copy()
iso[1:]  &= ~(present_dead[:-1] & adj[:, None])  # left neighbor present_dead, same walk
iso[:-1] &= ~(present_dead[1:]  & adj[:, None])  # right neighbor present_dead, same walk
sustained = present_dead & ~iso                  # run >= 2 = genuine surrendered-present

print("present-dead frames:", int(present_dead.any(1).sum()))
print("  capture transient (run=1):  ", int(iso.any(1).sum()), f"({iso.any(1).mean():.4%})")
print("  sustained surrender (run>=2):", int(sustained.any(1).sum()), f"({sustained.any(1).mean():.4%})")
PY
```

## Where it lives, and the decision

Prominent `TODO(obs-alive-tick-seam)` banners mark both sites, each naming its convention and pointing here:

- `bc/obs.py` — `scoreboard_row` / `init_memory` (board-snapshot-time).
- `bc/targets/elim_targets.py` — `alive_mask` (event-time).

**Not fixing now.** Recent sessions already establish that the obs tensor and model heads need rework; this is one concrete, well-characterized seam to fold into that pass. The fix is a convention decision (align the obs snapshot and the alive target to the same within-tick moment), not a local patch, and it touches the elim-head's own target semantics — so it belongs with that redesign, not ahead of it.

## Open: does the 1-tick label timing matter for the elim-head?

The alive/elim target reads a death one tick before the obs reflects it. For the who-dies-next head, that's a 1-tick lookahead in the label relative to the input. Whether it measurably affects the head — especially in the imminent (`dt < 10`) regime where the head already struggles — is unverified and worth a look during the rework.
