## Biggest thing missing from "happy path" design

The design sketch, as a high-level skeleton for the naive "happy path", looks good as written!

We should consider carefully what happens in the future when the config changes (new fields, etc). Can consider specific sub-cases: `arch`, `loss`, top-level fields, etc.

If the naive happy path is Stage 1, this is then "Stage 2".

The full "Stage 3" version is making everything work smoothly, *including all existing legacy checkpoints* -- the careful back-compat work.

Stage 2 is distinctly different and easier. The goal for stage 2 is: proactively design our system so that, when we inevitably do change the config, we can support these now "older" config formats as cleanly and simply as possible.

Right now, the existing back-compat code is slowly getting a bit more complex and crusty. For this work, Stage 2 is attempting to strongly mitigate that moving forward. It's not terrible, but it's something to out for. Now is the perfect time to take another stab at that.

After the Stage 2 design looks good, stage 3 then freshly re-considers what *additional work / design affordances* are needed to maintain back-compat with existing, and tries to do in a robust and minimally disruptive way.

## Code smells (may not be relevant for first pass)

Code smells I noticed, can consider later. Should do a quick pass to see if any of this fits naturally in the initial set of work.

### `run_dir.py`

- `check_drift`, `_DRIFT_EXCLUDED`, `_CHECKPOINT_OWNED` - these probably don't belong here. `run_dir.py` should be mostly "dumb" glue logic. I think these symbols fit more naturally in modules that are more pure config / checkpoint.

### `checkpoint.py`

- `_arch_for_load`
    - `value_head_variant` param is the passed-in arg (from CLI or config.json), and may conflict with the checkpoint value. The name of the param is unclear. The docstring clarifies but the name should be better.
    - I've explored this briefly before and nothing simple emerged... but ideally `checkpoint.py` wouldn't have special logic for validating individual fields on a sub-config. It would be nice if `ModelConfig` has its own dedicated, well-contained validation logic.

### `train_config.py`

- helpers like `_assert_non_negative` (currently in `loss.py`) would be quite helpful for slimming up `__post_init__`.

### Cross-cutting

- As I'm looking through the groups of code related to this work (checkpoint, configs, run_dir, etc), I'm thinking we need a new parent module (folder) or two inside of `bc` to group some of this stuff.
    - The 2 candidates I could think of for new parent modules: `runner` and `config`.
