# Checkpoint config storage + config versioning — design

*Date: 2026-06-24. Design for [6.24-1](6.24-1-session-notes.md) open item #1, drawing on [6.24-2](6.24-2-daniels-disorganized-ckpt-config-notes.md) (Daniel's notes) and the key-set survey in [6.24-3](6.24-3-config-keyset-survey-stage3-prep.md). This draft settles the greenfield mechanism; the legacy-data specifics and the resume-path mechanics are deliberately left partly open (see Scope and Open Questions).*

## Problem & motivation

The `.pt` checkpoint is not self-contained. It stores `model / arch / optim / scaler / epoch`; the rest of the training config (loss recipe, lr, seed, data paths, …) lives only in the run dir's `args.json`, and resume hard-depends on that sidecar (`load_parent_config` aborts if it's missing). The loss recipe in particular has no durable per-checkpoint pin — it leans on "the current default equals the historical behavior," which the `TrainConfig` NOTE already flags as a latent silent-drift bug.

Two goals:

1. **Make the checkpoint self-describing.** Store the full resolved `TrainConfig` in the `.pt`, so the artifact carries its own config and resume need not depend on a sidecar.
2. **Isolate config-format/version complexity behind one boundary.** The config shape has changed ~18 times in the last month (6.24-3). We want a single place that absorbs "this config could be any historical shape," so the rest of the code holds a current-shape `TrainConfig` and never reasons about versions.

## Scope: what this draft settles, what it defers

Settled here (greenfield):

- The checkpoint format and the `config` block.
- The migrate-once boundary and the reconstruction seam.
- The version stamp, dispatch, and migration-registry shape (registry shape proposed, not final).
- The schema manifest (per-version key-set files + a `CONFIG_VERSION` constant) and its pytest check.
- The `bc/config` module home.

Deferred:

- **The v0 legacy normalizer's guts** — the actual transforms for *our* historical configs. The survey (6.24-3) enumerated the sidecar (`args.json`) key-reshapes and found them meetable, but it measured the sidecar half *only*; the v0 normalizer must also absorb the existing `.pt`-assembly logic in `_arch_for_load` (the structural eras, `LEGACY_ARCH`/`OBS` back-fill, `elim_head_enabled`→`variant`, `in_ch`) — already-working code being relocated, not a new unknown, but not bounded by the survey. Filling all of this in (and validating the `.pt`-era half) is Stage 3.
- **Resume-path mechanics** — listed under Open Questions, not dug into. The resume rewire that *consumes* the checkpoint's config is door-open (MVP or first follow-up).
- **The "is this too heavy?" judgment (Q4)** — deferred until this doc exists, to be weighed from the full picture.

## The checkpoint format

`model / optim / scaler / epoch` stay top-level (runtime state and progress). The architecture stops being its own top-level key and moves inside a new `config` block:

| key | contents | role |
|---|---|---|
| `model` | `state_dict` | runtime state |
| `optim` | `state_dict` | runtime state |
| `scaler` | `state_dict` | runtime state |
| `epoch` | `int` | progress |
| `in_ch` | `int` | weight/obs integrity checksum |
| `config` | `asdict(TrainConfig)` + `config_version` | the self-describing config block |

- **`config`** is a pure `asdict(TrainConfig)`, JSON-native (so it survives `torch.load(weights_only=True)` — already true of today's `arch` dict, so de-risked, but worth one smoke test on the full block). `arch` nests at `config.arch` (with `obs` under it), `loss` at `config.loss`; recipe and operational fields ride alongside (operational fields are inert on reload — re-supplied per invocation).
- **`in_ch`** moves *out* of the arch dict to its own top-level checkpoint key. It's a derived checksum (input channels implied by `obs`), not a config field; pulling it out keeps `config` a pure `asdict` and makes the checkpoint's `config` block and `config.json` the same payload. Its validation (checksum vs. reconstructed obs channels) stays in checkpoint I/O — it's a weight-integrity check, not config shape.
- **`config_version`** lives inside the `config` block, so `config.json` is self-describing too. Single whole-config version (any sub-config change increments it).

On-disk mirror: `args.json` → `config.json`, both written from the same resolved `TrainConfig` via `asdict`. They're equal by *convention*, not construction — two write sites at two times (`config.json` before training, the `.pt` per-epoch), so the aim is to keep each write's code-path distance to the authoritative config object minimal rather than to claim a single source. Storing the full config in the `.pt` also requires `save` to gain a `TrainConfig` reference — today `TrainingState` holds only `model/optim/scaler/epoch` (impact flagged under Open Questions). The checkpoint is authoritative on resume; `config.json` is the human-readable mirror (grep, inspection). `args_cloud.json` is separate cloud provenance, unaffected by the rename (a coherence-only follow-up — note it also carries `gpu`, which `config.json` now duplicates, so the follow-up must not re-introduce a read-precedence split).

## The boundary: migrate once on load

There is exactly one place where "this config could be any historical shape" is true — reading raw config off disk. A reconstruction seam crosses it once:

```
train_config_from_dict(raw) = migrate(raw) → split arch/loss → re-wrap Paths → TrainConfig(**…)  # validators run
```

`TrainConfig.from_file` becomes this minus `json.loads`. Outside this seam, all code holds a current-shape `TrainConfig` and never branches on version. The enforceable invariant: **a `if "old_field" in …` or a version check anywhere but inside a migration is a leak.**

**Boundary scope (this draft):** the seam covers the **model-load path** (arch reconstruction in `checkpoint.py` / `load_bc_model`, which inference, probe, eval, and self-play all reach through). Resume *consuming* the checkpoint's config as its base is door-open — MVP or first follow-up (Open Questions). Analysis readers (`quality_report`, `perf_report`) stay best-effort raw reads, outside the migration contract — they already degrade gracefully on missing keys.

## Versioning & migration mechanism

### Version stamp & bump policy

`config_version` is a single integer for the whole config. Current shape = **v1**; an unstamped artifact = **v0** (legacy). What triggers a bump:

- **Shape change** (add / remove / rename / nest a key) → bump. This is what the key-set check guards, and the survey showed 18/18 historical changes were shape-visible.
- **Type change** (same key, different value type) → needs a migration, but the key-set check won't flag a *missing* one; the post-construct type assert (below) is the backstop.
- **Default-value change** → needs nothing. Because we serialize fully-resolved configs, every key is explicit on disk, so defaults are never consulted at load — old data carries its own values. (This full-resolution property is load-bearing for the whole design and is stated as a precondition.)

### Dispatch

```
v = raw.get("config_version", 0)       # explicit; default 0 = legacy
if v > CURRENT:                        # written by newer code than this binary
    raise ...                          # else the loop silently no-ops on a future shape
for i in range(v, CURRENT):            # range loop
    raw = MIGRATIONS[i](raw)
```

Identify (read the stamp) and apply (range loop) are separate, and neither inspects shape. The `v > CURRENT` guard rejects a checkpoint written by newer code — without it the loop silently no-ops and a future-shaped config loads as if current. Because the loop starts at the artifact's actual version, migrations don't re-run in the trusted-stamp case.

### Migration registry & signatures (proposed)

**Proposed first choice:** a dict keyed by source version, `MIGRATIONS: dict[int, Callable]`, where entry `i` maps a v`i` dict to a v`i+1` dict.

- **v1+ migrations:** pure `dict → dict`. Small, ordered, self-contained — each encodes one historical change.
- **v0 entry:** a *different* signature — `(pt_obj, run_dir | None) → v1_dict` — because legacy input isn't a single config dict (it's assembled from the top-level `arch`, the sidecar, and frozen pins). This asymmetry lives entirely in the loader, behind the boundary, where version-awareness is allowed, and never leaks past it. Its guts are Stage 3 (6.24-3); a stub satisfies the migration-coverage check until then.

Reasonable alternatives, noted but not chosen: an ordered list (implicit integer keys); or an Alembic-style per-file-per-version module with explicit `down_revision` links (heavier, more ceremony than a small dict warrants here).

### Migration convention: fill-if-absent

Additive migrations fill a missing field with its **frozen** historical value (what the field's absence meant), written as fill-if-absent (`setdefault`-style), never overwrite. The load-bearing point: field-filling happens only inside migrations, with frozen values — never from live defaults. The fill-if-absent form is also harmless insurance — if a config is ever loaded with a stamp behind its actual shape (e.g. a checkpoint written mid-development before the version was bumped), a migration that would add an already-present field leaves the real value untouched rather than clobbering it.

## Schema manifest & tooling

Kept deliberately light. The job is to catch "you changed the dataclass shape but forgot to bump the version / add a migration." That needs a frozen record of each version's shape and one test — not a command and not a hook.

### What's recorded

- **Per-version key-sets:** one frozen file per version in a dir, `bc/config/config_schema/vN.json` (sorted dotted key paths). Written once, never modified — the per-file structure makes "each version is frozen forever" structural and keeps a bump to a clean `+ one file`.
- **Current version:** a hand-edited `CONFIG_VERSION` code constant in `bc/config`. A bump is a deliberate, reviewed one-line change, and runtime stays code-only (no data-file read to learn the version). Chosen over an auto-generated `config-version.txt` head pointer — whose cross-check against the file count is circular, guarding only a redundancy it introduces — and over deriving the version implicitly from the file count.

The key-set files are dev-time / documentation artifacts; runtime load/save uses the `CONFIG_VERSION` constant + the in-code migration registry + the derived current key-set, and reads no files.

### The checks

- **Forgot-to-bump (pytest):** `derive_keyset(dataclasses) == load(v{CONFIG_VERSION}.json)`, plus `CONFIG_VERSION == max(vN.json)` and migration coverage of `0..CONFIG_VERSION-1`. This is the primary safety — and the *only* guard for non-arch drift: an arch-shape mismatch would also trip `load_state_dict(strict=True)`, but a forgotten loss/recipe bump would otherwise pass silently.
- **Final-output (runtime):** the migrated dict's key-set matches the derived current key-set before construction. Cheap, code-only.
- **Type fidelity (post-construct):** `isinstance` assert on the `Path` fields, since the key-set guards shape, not Python types, and dataclasses aren't runtime-type-checked.

Not done (a later graduation if a migration bug ever slips through): per-step migration verification and per-version load-time integrity.

### A pytest test, not a command + hook

Bumping is manual and small: add `vN.json`, write the migration, bump `CONFIG_VERSION`, run the tests. A `pytest` check (`tests/test_config_schema.py`) does the job in place of a `tools/bump_*` command and pre-commit hook. The reasons:

- the repo's config dataclasses are already guarded by pytest, not hooks;
- the `regen_modal_reqs` hook this would have mirrored is itself effectively dead (hooks rot);
- a commit-blocking hook adds extra complexity without gaining anything over the pytest check:
    - a script implementing the hook
    - `--no-verify` escape hatch 
    - `SKIP_` sub-hatch when we have other hooks we don't want to skip

The cost of pytest-over-hook is timing (you find out at test-run, not at commit), which for a solo project is fine. The command + hook stay deferred until a real schema mistake slips through and costs time.

## Config reconstruction mechanics

From the round-trip survey, `train_config_from_dict` must replicate `from_file`'s body minus `json.loads`:

- Pop `arch` → `build_model_cfg(**arch_dict)` (its `__post_init__` coerces the nested `obs` dict and the `elim_bin_edges` list→tuple).
- Extract `loss` → `LossConfig(**…)` (its `__post_init__` coerces `elim_bin_weights` list→tuple — the second JSON-list-vs-tuple field, alongside `arch.elim_bin_edges`).
- Re-wrap the three `Path` fields (`manifest`, `intermediate`, `run_dir`) — nothing coerces `str`→`Path`, so a missed re-wrap is a silent type bug (hence the post-construct assert).
- Splat the rest; all `__post_init__` validators then run on guaranteed-current data.
- `in_ch` is not a config field and isn't present in `asdict(TrainConfig)` — no stripping needed (it's the separate top-level checkpoint key now).

## Module structure

A new **`bc/config`** package owns config shape + validation + the migration registry + the key-set manifest + tooling, and the field-role classification (`_DRIFT_EXCLUDED` / `_CHECKPOINT_OWNED` / `check_drift`, which today sit awkwardly in `run_dir.py`). Consequences:

- `checkpoint.py` slims toward dumb I/O: load bytes → hand the `config` dict to `bc/config` (migrate + reconstruct) → return typed pieces. It keeps the `in_ch` integrity check; it sheds the per-field legacy branches (those become migrations). The three sites that currently *tolerate* `in_ch` as a config key — the pops in `build_model_cfg` and `_arch_for_load`, the `valid.add("in_ch")` in `ModelConfig.validate_partial` — become v0-only and move into the v0 normalizer rather than staying in the hot path, since v1 configs never carry `arch.in_ch`.
- `state.from_checkpoint` sheds format knowledge — it consumes typed pieces and does runtime wiring (model/optim/scaler), no `obj["arch"]` reads, no arch-match assert (that's drift, which moves to the config/resume layer).

Existing files (`train_config`, `model_config`, `obs_config`, `loss`) migrate into `bc/config` as needed; new code starts there. The exact carve-out order is its own change, not a prerequisite for the format work.

## Stages / build order

- **Stage 1 — greenfield core.** The format (config block + stamp + `in_ch` relocation), the `config.json` rename, the reconstruction seam wired into the model-load path, the migration *seam* (empty/stub chain — current shape is v1, nothing to migrate yet). This is the small, foundational piece.
- **Stage 2 — the mechanism.** The per-version key-set files, the `CONFIG_VERSION` constant, and the pytest schema check. Earns its keep at the first real v1→v2 change, which the cadence puts days out. (The bump command + pre-commit hook are deferred — see Schema manifest & tooling.)
- **Stage 3 — the legacy normalizer.** The v0→v1 guts: the survey's sidecar key-reshapes + a frozen-default fill (6.24-3), **plus** the relocated `.pt`-assembly logic from `_arch_for_load` (not measured by the survey — validating that `.pt`-era half is part of this stage). Self-contained behind the v0 entry's output contract. Because every existing run is flat-loss (v0), resuming an *existing* run through the new path needs this stage; resuming a *new* (v1) run does not.

How far past Stage 1 to build, and when, is the deferred Q4 judgment.

## Open questions & deferred decisions

- **`TrainingState` must carry the `TrainConfig`**: `save` serializes only `asdict(self.model.cfg)` today; storing the full config means `TrainingState` (or `save`) gains a `TrainConfig` reference. Impact and scope to be investigated.
- **`checkpoint.py` / `train_config.py` cleanup blast-radius** (post-MVP follow-up to scope): the format change forces some changes and invites others. One *mandatory* correctness change — `is_arch_bearing` keys on a top-level `"arch"` (`checkpoint.py:107`) that moves to `config.arch`, so left unfixed it returns `False` for every new checkpoint and breaks the inference `model_key` de-dup. (`is_combined_checkpoint`, keyed on top-level `"model"`, is unaffected.) Beyond that one, much of `checkpoint.py` / `train_config.py` is begging to be refactored once the core lands; that pass needs its own scoping.
- **Resume path (not dug into this draft):**
  - Does the merge operate on dicts or typed objects? (Leaning: normalize each input to current shape → merge → construct once.)
  - Where do `check_drift` / `_DRIFT_EXCLUDED` / `_CHECKPOINT_OWNED` land, and are the drift roles affected by config-in-checkpoint?
  - What happens to `prepare_resume`'s args-chain walker (it largely collapses once resume sources from the checkpoint)?
  - Do `config_resume_NN.json` segment mirrors persist?
  - Legacy resume still needs the `args.json` sidecar (self-contained resume is a v1+ property) — how does that interact with the above?
  - When does resume switch to a checkpoint-sourced base — Stage 1 MVP or first follow-up?
- **Boundary for resume:** whether the resume read goes through the seam in the MVP or as the first follow-up (the model-load path is in scope regardless).
- **Migration registry shape:** dict-keyed-by-source-version (proposed) vs. ordered list vs. Alembic-style per-file.
- **Migration file specifics:** What does the process of writing of a specific migration look like? What are the types of operations that will be common in the migration logic?
- **Q4 — how heavy:** resolved toward the lighter shape — pytest check + `CONFIG_VERSION` constant + per-version key-set files; the bump command, pre-commit hook, `config-version.txt`, and cross-check are deferred until a real mistake earns them. (See Schema manifest & tooling.)
